# LeanExe

LeanExe compiles functions written in a restricted dialect of Lean to WebAssembly, C, AArch64 machine code, WGSL, PTX, and Thumb-2 machine code for the STM32F767ZI microcontroller, an Arm Cortex-M7, on ST's NUCLEO-F767ZI development board, and proves in Lean that the compiled code computes those functions.

![LeanExe toolchain: source, reflection, intermediate languages, backends and their theorems, and platforms](docs/toolchain-summary.png)

`verified_compile` reflects a Lean definition into a typed intermediate language, and each backend produces code together with a theorem that the code computes the definition's result.  The theorems hold in Talos's WebAssembly semantics, in the Lean copy of CompCert's Clight, in a Lean model of an AArch64 machine from boot, in a Lean model of the Cortex-M7 microcontroller from reset, and under statements of the Vulkan and PTX memory models, and a Rocq proof carries the theorem of a bare-metal C program to CompCert's Asm.  The names in parentheses are the artifact codes of [the table below](#artifacts), and [the overview](#overview) shows the full toolchain.

The compiler has one correctness theorem for every typed source program that it accepts.  The WebAssembly theorems hold in [Talos](https://github.com/cajal-technologies/talos)'s semantics, and an execution theorem may allow a trap at `unreachable`, which the theorem `p.f.trapFree` excludes under its allocation and call-depth premises.  The compiled modules also translate to a subset of [CompCert](https://compcert.org/compcert-C.html)'s C, with a theorem about each C function in the Lean copy of CompCert's Clight, and CompCert compiles the C for x86-64 and AArch64 under an operating system, for bare-metal AArch64, and for the Cortex-M7 of QEMU's `mps2-an500` and the Cortex-M7 microcontroller.  A bare-metal C program has a theorem about the whole program, which a Rocq proof transfers to CompCert's Asm: a termination with the result's bytes or a trap's status, or a loop that runs a step function forever with a stated trace in each window, the form of every Cortex-M7 program with a theorem.  An executable under an operating system also depends on a C host that no theorem covers.  A separate back end compiles the same modules to AArch64 machine code without C and writes an arm64 Image whose theorem covers the whole run from boot, the startup included, in a Lean model of the machine, and Lean proofs compare the model's instruction forms with traces of Arm's specification from Isla, with the results of Arm's floating-point functions taken as equations with Talos's IEEE 754 functions.  Another back end without C compiles the step functions of programs with requests to Thumb-2 machine code for the Cortex-M7 microcontroller and writes a flash image whose theorem covers every window of the run from reset in a Lean model of the microcontroller.  Array builds compile to WGSL and PTX kernels with theorems under statements of the Vulkan and PTX memory models, and Lean actions with stdin, stdout, stderr, and exit compile to WASI Preview 1 modules.

## Background

This project is inspired by small languages designed to simplify analysis, implementation, and verification: [PreScheme](https://dustycloud.org/misc/prescheme.pdf), [Low\*](https://arxiv.org/abs/1703.00053), [ACL2](https://doi.org/10.1109/32.588534), [CompCert C / Clight](https://xavierleroy.org/publi/Clight.pdf), [CakeML](https://cakeml.org/popl14.pdf), and [TinyGo](https://tinygo.org/).

Donald Knuth's [The Art of Computer Programming](https://cs.stanford.edu/~knuth/taocp.html) and in particular its "Seminumerical Algorithms" are major inspirations as well.  We are explicitly organizing some development in a similar spirit.  For example, see the current set of [elementary and special functions](https://github.com/jsmorph/leanexe/blob/main/index.md#6-elementary-and-special-functions).

We strive to be both pragmatic and demanding.  For example, floating-point operations have been in scope since the beginning of the project.  IEEE 754 is an impressive, challenging beast.  See David Goldberg's ["What Every Computer Scientist Should Know About
Floating-Point Arithmetic"](https://dl.acm.org/doi/10.1145/103162.103163).  We are building machinery for complete floating-point accuracy.  The [fused multiply-add](https://github.com/jsmorph/leanexe/blob/main/Library/Numerics/Arithmetic/Fma/FmaTheorem.lean#L144-L149) development is a good example.

These days rewriting a large codebase in a different source language is almost automatic (given appropriate stern oversight).  So inventing a new language today doesn't necessarily impose the classic high hurdles to adoption.  However, AI is of course trained on existing corpora.  Lean in particular continues to receive a lot of investment by AI companies.  So we decided to proceed from a [strict subset of Lean](https://github.com/jsmorph/leanexe/tree/main/docs).  A major benefit is being able to use fancy Lean (including Mathlib) to prove things about executable artifacts themselves.

## Demos

Here are some of the demos in this repo:

- [Binary32 GPT-2](Demos/Gpt32/README.md): one generation step of GPT-2 124M in `Float32`, compiled to WGSL kernels with dispatch theorems, to PTX kernels with launch theorems, and to WebAssembly.  `generate_host` composes the kernels' theorems into the step's scores on either GPU target, a browser page runs the model on WebGPU and in WebAssembly and compares the scores, and a CUDA session runs it on an NVIDIA GPU.
- [Binary64 GPT-2](Demos/Gpt/README.md): the model in `Float`, with `steps_exact`, which proves that cached generation equals full inference bit for bit, and `forward_causal`.
- [Euler solvers](Demos/Euler/README.md): finite-volume solvers for the compressible Euler equations.  `euler_solve_call` proves that the module returns the solvers' results without a trap within a memory cap, the balance theorems bound the rounding error of conservation, and the solver also runs as C, as a bare-metal AArch64 program, and as an arm64 Image whose theorem states that it writes the solver's result on a grid of 4 by 4 cells.
- [Drone planner](Demos/Drone/README.md): flights over terrain that `drone_compute` and `drone_safe` prove optimal and safe in a point-mass model.
- [Slew planner](Demos/Slew/README.md): spacecraft attitude slews that keep body vectors outside keep-out cones and inside keep-in cones, with `plan_safe` for the constraints and `plan_optimal` for least duration.
- [Conjunction probability](Demos/Conjunction/README.md): an interval that contains the two-dimensional probability of collision of two space objects, with `pc_enclosure` for the inclusion of the model's integral and `assess_sound` for the verdict against a threshold.
- [SGP4](Demos/Sgp4/README.md): the near-Earth SGP4 propagator of catalog element sets, as a model over the reals, a binary64 program that agrees with the reference states of the Vallado code within half a unit of the last printed digit, and an enclosing program with `sgp4Box_sound` for the inclusion of the model's position and velocity in its intervals.
- [Running sums](Demos/RunningSum/README.md): WASI programs that read numbers from stdin and print cumulative totals, with proofs of canonical output and eventual exit.  [The binary64 version](Demos/RunningSumFp/README.md) composes proved parsing, IEEE 754 addition, and printing.
- [Energy authorizer](Demos/Energy/README.md): decides whether a gateway may send proposed battery power limits to the inverter of a solar-and-battery site for one window of time.  `authorize_sound` proves that, under accepted limits, every trajectory that the model admits keeps the site's energy and grid limits or stays no further outside them than a return to the inverter's fallback mode would, and `energy_authorize` transfers the decision to the module's bytes.  Its gateway [ran a simulated day on the board](Demos/Energy/README.md#a-day-on-a-nucleo-f767zi), through CompCert and through [the Cortex-M7 back end](docs/m7-bare-metal.md), whose image has a theorem from reset, with output records equal to native Lean's in both runs.
- [BMS protection](Demos/Bms/README.md): the protection layer of a battery management system for a pack of four lithium iron phosphate cells, a machine that answers each record of a bridge with the permits of three relays.  `m1` proves that an answer with a nonzero permit follows a reset acceptance, a start, and records that passed every check in sequence, and that `NORMAL` follows a record with the precharge condition, and `bms_board_safe` carries `m1` to every answer with a nonzero permit that [the Cortex-M7 image](#cortex-m7-images) writes from reset.  The image [ran the requirements' fault-injection schedule on the board](Demos/Bms/README.md#a-run-on-a-nucleo-f767zi), and a replay in native Lean found every answer equal to the specification's.
- [Order book](Demos/OrderBook/README.md): a central limit order book for one instrument, with price-time matching of limit, market, post-only, cancel, and reduce commands and self-trade prevention.  `run_eq` proves that the array program computes the list specification of its English requirements, and `run_call` transfers the proof to the module's `run` export.  A WASI process runs the book over command records on stdin, and `initial_terminates` proves that its module writes exactly the specification's event records to stdout and exits.
- [Ranked-choice tabulation](Demos/Rcv/README.md): a tabulator for single-winner ranked-choice contests under Oakland City Charter §1105.  `tabulate_callSpec` proves that the module returns the specification's report of every file, `initial_terminates` that its WASI process writes that report and exits, and `tabulate_native` that its C translation returns it.  The majority-holder theorem relates its rounds to Alameda County's practice, the batch theorem relates them to a count without batches, and [the case study](Demos/Rcv/README.md#case-study-school-director-district-4-2022) recounts the 2022 contest for School Director, District 4: the module's figures equal those of the County's corrected report, and the County's faulty setting, applied by a Python script, gives the figures that the County first certified.  [A second module](Demos/Rcv/Maine/README.md) counts contests under Maine's 21-A M.R.S. §723-A, with its own WASI process and C translation and the same kinds of theorems.
- [SHA-256](#a-worked-example-sha-256): from a transcription of FIPS 180-4 to WebAssembly, C, and a bare-metal AArch64 image whose whole-program theorem a Rocq proof transfers to CompCert's Asm.  An [arm64 Image](#aarch64-images) of `shaCheck`, a wrapper of the library's `sha256With`, writes the digest of `abc`, with a theorem from boot, and [a Cortex-M7 step](#cortex-m7-images) built on the library's `compress` answers each block of 64 bytes on the Cortex-M7 microcontroller, with `sha_board`, which states that the answers begin the FIPS 180-4 digests of the prefixes of the blocks read.
- [CIC decimation filter](Library/Numerics/Filters/Cic/README.md): a cascaded integrator–comb filter whose AArch64 bare-metal Image, from [the back end that compiles WebAssembly to AArch64 directly](docs/a64-bare-metal.md), has `cic_outputs`: in the model of the boot machine, the Image writes to the UART the filter's outputs over ℤ, as its specification defines them, on a fixed table of 64 samples.
- [Elementary and special functions](index.md#6-elementary-and-special-functions): binary64 implementations with proved accuracy bounds, and a software [fused multiply-add](Library/Numerics/Arithmetic/Fma/README.md) proved equal to IEEE 754's fusedMultiplyAdd for all operands.

## Overview

![LeanExe toolchain in detail](docs/toolchain.png)

`verified_compile` and `verified_compile_wasi` reflect Lean definitions and WASI actions into typed source languages, and Lean's kernel checks the proofs that they generate, so the reflector is outside the trusted base.  `compileWith` translates the typed source language `Verified.Expr` to a WebAssembly module, and one universal theorem, `Prog.correctStaticWith`, gives each compiled function its execution theorem in Talos's semantics.  The WASI compiler does the same for programs with effects through `EffectProg.correctWith`.  `decode_encode` carries the theorems to the module's encoded bytes, and the file theorems state that the `.wasm` file holds those bytes.

The C backend translates a module without imports to the Lean copy of CompCert's Clight, where `translate_correct` gives each C function a theorem from the module's theorem.  CompCert compiles the printed C only after `clightgen` reads it back as the same Clight program.  For bare-metal AArch64, `bare_program` adds a generated `main` and proves a theorem about the whole program, which a Rocq proof carries to CompCert's Asm.  A generated `main` can also run a step function forever, on AArch64 or on the Cortex-M7, and `ctl_program` and `req_program` then prove the judgment `LoopReacts` of the whole program, which `clight2_loop_to_asm` carries to a reactive behavior of the Asm program.  The GPU backends lower array builds to the kernel source language and translate them to WGSL and PTX, with theorems about every consistent execution under statements of the Vulkan and PTX memory models, and a proved parser reads each printed kernel back.

The AArch64 back end takes a module without imports to machine code directly.  `genProgram` generates the module's instructions, and the simulation theorem `program_sim` relates their run in a Lean model of an AArch64 machine to the module's run in the reference interpreter.  `genImage` places the code between a startup routine and a translation table in an arm64 Image, and `image_run_at` proves, from a boot state whose memory holds the Image at any base in RAM that is a multiple of 4096, that the machine reaches PSCI SYSTEM_OFF after writing the function's value to the UART.  Lean's kernel compares the written file with `genImage`'s output, and Lean proofs compare every instruction form on which a program's model runs with traces of Arm's specification that Isla produces.  The proofs of the floating-point forms take as hypotheses equations between the results of Arm's floating-point functions and Talos's IEEE 754 functions, and those equations rest on tests and on proofs over Sail's Lean translation of the functions, which `tools/sail/check.sh` checks outside the repository's build.  [The AArch64 document](docs/a64-bare-metal.md) gives each link of the chain and its evidence.

The Cortex-M7 back end takes the step function of a program with requests to Thumb-2 machine code for the Cortex-M7 microcontroller.  `genProgram` of `LeanExe/M7` generates a `main` that calls the step forever and performs each request as one device access, `step_call` relates the generated step's run in a Lean model of the Cortex-M7 microcontroller to its run in the reference interpreter, and `board_run` proves, from every state that reset gives, that the image performs the board's initialization and then the requested accesses of every window, as `areaBoard_run` does for a program with linear memory, whose image first sets up the area of the module's globals and memory in DTCM.  Lean's kernel compares each flash image with the generator's output, Lean proofs compare every instruction form of the model with Isla's traces of Arm's A-profile specification in AArch32 Thumb state, and co-simulation on QEMU and on the board tests the model.  [The Cortex-M7 document](docs/m7-bare-metal.md) gives each link of the chain and its evidence.

Applying the theorems on the platforms rests on the items of [the trusted-base document](docs/trusted-base.md), among them Talos's semantics, the decoder, the C host, the AArch64 machine model with its floating-point equations, `ptxas`, and the GPU drivers.  Applying the Cortex-M7 image theorems on the board rests on the model of the Cortex-M7 microcontroller, the reading of the M-profile pseudocode against the A-profile's, the reader of the image file, reset, which must be a power-on reset or an NRST reset with the debug registers at their power-on values, USART3 and the ST-LINK's virtual COM port, and the timing of each window, whose margins rest on cycle measurements.  The Mermaid sources of the diagrams are [`docs/toolchain.mmd`](docs/toolchain.mmd) and [`docs/toolchain-summary.mmd`](docs/toolchain-summary.mmd).  `mmdc -i docs/toolchain.mmd -o docs/toolchain.png -b white -s 2 -w 1800`, from `@mermaid-js/mermaid-cli`, renders the full diagram, and the same options render the summary.  Where Puppeteer's own browser does not run, as on AArch64 Linux, `-p` names a Puppeteer configuration whose `executablePath` is an installed Chromium.

## Compiler

### Pure functions

`Verified.compileWith` translates a typed source program to a module.  The universal theorem `Prog.correctStaticWith` proves that the module computes the source meaning, `denote`, under its heap and static-data premises.  `verified_compile p := [f, …]` reflects Lean definitions into that source language and proves their correspondence.  It derives `p.f.implements` from those equations and the universal theorem, and Lean's kernel checks the generated proofs.

The command also generates each function's allocation bound and a trap-free theorem under that bound.  For a scalar function of a program without byte literals, when its rules prove that execution does not depend on the store, it generates `p.f.pure`: from any store, the call returns the Lean result and leaves the store unchanged, which lets other compiled programs call the function.  [The verified compiler manual](docs/verified-manual.md) states the type restrictions, ownership rules, generated declarations, and proof premises, and [the internals guide](Verified/README.md) describes the compiler and its universal proof.  [The verified-request skill](.claude/skills/verified-request/SKILL.md) turns an English request into a specification that a fresh agent reviews, a program, and a theorem `Verified.CallSpec` that the program's export returns the specification's value without a trap under its generated allocation bound, which [`tools/verified-request-check`](tools/verified-request-check) states and checks.

The dialect covers words, signed 64-bit integers, Booleans, floats of both widths, tuples, structures, enumerations, sums, arrays, records with array fields, packed bytes, lists, and recursive types, and each row below links fixtures that compile them.  [The verified compiler manual](docs/verified-manual.md#the-dialect) states the representations, ownership rules, and restrictions.  Integers are `UInt64` and `Int64`, so a program and its module compute the same values, wraparound included.

### WASI programs

`verified_compile_wasi` compiles `LeanExe.Wasi.Action` definitions with stdin reads, stdout and stderr writes, bounded effectful loops, and exit.  Actions use Lean `do` notation and `UInt64` counts, lengths, and statuses.  Callable-entry and `_start` theorems relate exported execution to the native actions, preserving ordered effects and effects committed before an error or trap.  Total execution requires a typed resource-prefix bound and assumptions about reached host operations.  [The WASI manual](docs/wasi.md) defines the API, export forms, proof premises, native interpreter, and Wasmtime's exit-acceptance policy.

`LeanExe.Wasi.Process` composes bounded actions through an unbounded outer loop.  [The running-sum application](Demos/RunningSum/README.md) reads decimal integers through EOF, prints each cumulative total, and handles short writes, and [its compiled theorem](Demos/RunningSum/Correct.lean) proves canonical output and eventual accepted exit under limits on the bytes of each line and the digits of each total.  The theorem also assumes a Talos host environment that meets the specifications of the three imports, a host whose reads return the input stream without an error and whose writes make progress, and a host that accepts the exit statuses 0 and 28.  [The floating-point version](Demos/RunningSumFp/README.md) parses binary64 values and prints each sequential binary64 total, and its proofs compose the parser and printer theorems with IEEE 754 addition and the process proof.  Each application proves the allocation charges of each step from limits on its input, and corollaries cover lines of up to 9,000,000 bytes and totals of up to 9,000,000 digits for the integer sum and lines of up to 50,000,000 bytes for the floating-point sum.  [The order book's process](Demos/OrderBook/README.md#the-wasi-process) reads command records in reads of at most 4,096 bytes and writes the events of each read before the next.  Its compiled theorem proves exact output and accepted exit under the same host assumptions for every input of fewer than 2^64 − 1 records, with one charge for every step, since the book's arrays have fixed sizes and a read holds at most 74 records.

## Native code

### The translation to C

The translator, `LeanExe.Native.translate`, accepts the modules that pass a decidable check of its subset of WebAssembly.  It writes one C function for each WebAssembly function that it translates and holds the linear memory in a static array, whose size `verified_compile` sets to `nativeCap`, 4,096 pages or 256 MiB.  Its simulation theorem, `translate_correct`, relates every Talos run that ends in a return or a trap to a terminating execution in the Lean copy of CompCert 3.18's Clight, and `p.f.native` follows from it and `p.f.implements` for each function.  The `clightgen` comparison of each build covers the printer and the written file, so neither needs a theorem.  [The translator's design](docs/native-translator.md) gives the subset, the translation scheme, the proof layers, and the trusted base.

Every module of [the module registry](tests/verified/modules.txt) lies inside the subset.  `tests/native/verified.sh` translates each module, compiles it with CompCert and the C host `tools/native-host.c`, and compares every case that the translation can run with the line that the Wasmtime host gives, with the same rules for traps and allocation counters.  `tests/native/run.sh` compares translated programs with Talos's runs, `tests/native/bytes.sh` runs the byte and literal examples, and `tests/native/clight.sh` compares the Lean copy of Clight with `ccomp -interp` on random programs under the NaN parameters of either target.

### The translation without the alignment test

The translation option `alignedAccess` makes every 64-bit load and store read or write one word of `lx_mem` after the bounds check, without the test of the address's low three bits and the eight byte accesses of an unaligned address.  With `set_option verified_compile.alignedNative true`, `verified_compile` also emits that translation, `p.translationAligned`, and the theorem `p.f.nativeAligned`, whose statement `NativeAlignedImpl` or `NativeTablesAlignedImpl` adds the premise `AlignedInput` and concludes, in addition to the conclusions of `p.f.native`, an aligned final heap and a result whose blocks meet `AlignedOutput`.  `tests/native/aligned.sh` tests the refusal of `native-verified build --aligned` for a module without those theorems, and a program with byte literals has none.

`tests/native/bench.sh` times corpus workloads in their native form and in Wasmtime.  CompCert aligns a function to 4 bytes on AArch64, so `--placements` also links each native program at sixteen code offsets and reports the mean over them, as [the benchmark method](docs/native-translator.md#benchmark-method) describes.  The placement benchmark ran on AArch64 only, with CompCert built from the 3.18 sources and Wasmtime's C API 44.0.0, and gave these mean times per call:

### Bare-metal programs

A bare-metal program that terminates is the translation of a module, a volatile global `lx_out` at the UART's data register of QEMU's `virt` machine, and a generated `main` that calls `lx_init`, calls one entry on arguments fixed when the program is built, and writes the bytes of the result to `lx_out`.  `bare_program p.f x [args] r` proves `p.f.program`: the whole program terminates with result 0 and a trace of one volatile store per byte of the result's encoding or, when the entry may abort, with result 1 and an empty trace.  The Rocq theorem `clight2_bigstep_to_asm` in [the Rocq composition](rocq/Clight2Asm.v) composes CompCert's forward simulations from Clight to Asm, and `clight2_bigstep_asm_unique` shows that, for a trace without inputs, such a termination is the only behavior of the Asm program.  Both Rocq theorems take the termination as a judgment of CompCert's own Clight in Coq, and the step from the Lean theorem to that judgment depends on the Lean copy's agreement with CompCert's definitions and on the `clightgen` comparison of each build, which no proof covers.  The startup code in `tools/baremetal/` turns on the MMU and the caches.  The build fails when the static stack bound of `main` exceeds the stack or when the assembly contains an instruction that requires an aligned access.  [The bare-metal design](docs/native-bare-metal.md) gives the statement, the startup code, the input path, the stack bound, and the trusted base.

### AArch64 Images

The back end in `LeanExe/A64` generates machine code from a module without imports, places it in an arm64 Image with a proved startup routine, and proves the run from boot in a Lean model of the machine.  No C compiler, assembler, or linker takes part, so an Image's theorem trusts the machine model, the reader of the image file, QEMU's loader, and the machine in place of CompCert and the Rocq step.  Each theorem holds at every base in the RAM GiB that is a multiple of 4096, and it allows the outcomes that the program's compiler theorems leave: the result alone where `p.f.trapFree` and the stack's bound cover the program, and otherwise also status 1, the trap at `unreachable`, or status 4, an overflow of the stack.  [The AArch64 document](docs/a64-bare-metal.md) states the generator, the simulation theorem, the model, the image, the startup, the trusted base, and the final theorem.

### Cortex-M7 images

The back end in `LeanExe/M7` generates Thumb-2 code from the step function of a program with requests, places it in a flat image of the Cortex-M7 microcontroller's flash after a vector table, the setup of the area of a program with linear memory, and the board's initialization, and proves the run from reset in a Lean model of the microcontroller.  No C compiler, assembler, or linker takes part, so an image's theorem trusts the model, the reading of the M-profile pseudocode against the A-profile specification that Isla traces, the reader of the image file, reset, USART3 and the ST-LINK's virtual COM port, and the timing of each window.  Each theorem allows no trap: the step's compiler theorem excludes the traps, and the stack's bound fits in DTCM.  [The Cortex-M7 document](docs/m7-bare-metal.md) states the model, the generator, the simulation theorem, the loop, reset, the area's setup, the images, the final theorems, the trusted base, the Isla check, the tests, the timing, and the limits.

For every sequence of the values that device reads return and every number of windows, below 2^62 for the SHA-256 step, the board's theorems state that the model reaches the initialization's accesses followed by those of the windows, and the theorems whose names end in `_runs` state that the model never stops.  `gw_board_prefix`, `crc_board_prefix`, `sha_board`, and `dl_board_prefix` add that the bytes written to `USART_TDR` begin the gateway's output records for the records read, the low bytes of the CRC-32 of the prefixes of the bytes read, the SHA-256 digests of the prefixes of the blocks read, and the encoded answers to the nonempty segments of the bytes read, all of them whenever a window reads a byte.  `bms_board_prefix` adds that they begin the BMS machine's encoded answers to the nonempty segments of the bytes read, and `bms_board_safe` that every complete answer among them with a nonzero permit is the machine's answer to its segment and satisfies the demo's theorem `m1`.  The generator also writes images of the steps `cmsdkTick`, `gwTick`, `crcCmsdkTick`, `shaCmsdkTick`, `sgCmsdkTick`, `dlCmsdkTick`, and `bmsTick` for QEMU's `mps2-an500`, whose theorems `echo_qemu`, `gw_qemu`, `crc_qemu`, `sha_qemu`, `sg_qemu`, `dl_qemu`, and `bms_qemu` have the same form, and Renode's model of the board runs the board's images.

The theorems hold of the processor under the run conditions that `LeanExe/M7/Proof/Board.lean` and the theorem files state: a power-on reset, or an NRST reset with DHCSR, DEMCR, the FPB, the DWT, the ITM, and the DBGMCU registers at their power-on values, with BOOT0 low and BOOT_ADD0 `0x0080`, software watchdogs, and no interrupt, NMI, debug halt, debugger access, or DMA during the run.  The reset of `st-flash` leaves DHCSR's C_DEBUGEN set and `DBGMCU_APB1_FZ` at `0x1800`, while `tools/baremetal/stlink_nrst.py` sets the debug registers that a system reset keeps to their power-on values over SWD and then drives NRST, and a diagnostic image read those values after each of nine such resets.  The runs of the echo and the CRC-32 step from a power-on with no SWD session, and those of the gateway, the SHA-256 step, the signed step, the echo of records, and the BMS step after the reset of `stlink_nrst.py`, meet the conditions, and the runs after the reset of `st-flash` do not.

USART3 holds one received byte, so each window that runs while bytes may arrive must end in time for the next byte at 4,800 baud.  `echo_board_steps`, `gw_board_steps`, `crc_board_steps`, and `sg_board_steps` bound every window by 1,440, 17,553, 1,482, and 1,404 instructions of the model, but no theorem bounds the SHA-256 step's windows or any window's time, so the margins rest on cycle measurements on the board.  The bounds keep the windows in time at up to 5.78 cycles an instruction for the echo, 5.62 for the CRC-32 step, 5.93 for the signed step, and 0.94 for the gateway, and the board measured 0.99 to 1.13 for the echo and the CRC-32 step and about 0.65 for the gateway, while the SHA-256 step's longest such window took 1,445 cycles, about 9% of half a byte time.  `dl_board_steps` bounds every window of the echo of records by 151,558 instructions, the cost of the window that decodes a segment and encodes its answer while the far end waits, and `dl_board_poll` bounds every other window by 2,036, which keeps it in time at up to 8.18 cycles an instruction.  `bms_board_steps` bounds every window of the BMS step by 202,799 instructions, the cost of the window of a delimiter after a nonempty segment, which decodes the record, runs the machine, and encodes the answer, and `bms_board_poll` bounds every other window by 3,301, which keeps it in time at up to 5.04 cycles an instruction, against 0.68 to 0.73 measured on the board.

`tests/baremetal/m7-image.sh`, `tests/baremetal/m7-qemu.sh`, and `tests/baremetal/m7-board.sh check` have the kernel check the images and their theorems.  `m7-qemu.sh` then runs the QEMU images with the far end of the UART, and `m7-board.sh` runs the board's images in Renode and on the board, after the reset of `st-flash` with `run`, after that of `stlink_nrst.py` with `nrst`, or from the power-on of a replug with `host`, and runs the co-simulation of the model's forms on the board.  `tests/isla/m7-theorems.sh` checks the proofs that compare the model's forms with the traces that `tests/isla/m7-traces.sh` produces, as [the Isla check](docs/m7-bare-metal.md#the-isla-check) describes.

## Trusted base

[The trusted-base document](docs/trusted-base.md) lists, for each artifact code, what its theorem trusts, how the project checks each item, and where each item is stated, and it gathers the definitions that the statements depend on.  Every theorem trusts Lean's kernel, at the release candidate 4.34.0-rc2, whose kernel rejects a reproduction of a defect that earlier kernels accepted, and the core definitions that give a Lean program its meaning.  The WebAssembly theorems also trust Talos's execution semantics and the binary decoder, and a file without a file theorem also trusts Lean's compiled code for its emission.  The native theorems use Talos only as an intermediate language and trust the Lean copy of CompCert 3.18's Clight, which review, differential tests, and the `clightgen` comparison of each build check, and the bare-metal theorems add the Rocq composition, the startup code, the stack-bound tool, and the machine.  The theorems of AArch64 Images trust no compiler, assembler, or linker: they trust the model of the boot machine, whose instruction forms Lean proofs compare with Isla's traces of Arm's specification, the equations between Arm's floating-point functions and Talos's IEEE 754 functions, which rest on tests and on proofs over Sail's Lean translation checked outside the repository's build, the reader of the image file, QEMU's loader, and the machine.  The theorems of Cortex-M7 images trust the model of the Cortex-M7 microcontroller, whose forms Lean proofs compare with Isla's traces of Arm's A-profile specification, a reading of the M-profile pseudocode against the A-profile's, the reader of the image file and the flash's copy of its bytes, and reset from the vector table that BOOT_ADD0 names.  Applying them on the board also rests on the run conditions, among them a power-on reset or an NRST reset with the debug registers at their power-on values, which `tools/baremetal/stlink_nrst.py` gives, on the initialization's effect on USART3, on USART3 and the ST-LINK's virtual COM port, which must deliver every byte once and in order, and on the timing of each window at 4,800 baud, whose margins rest on cycle measurements, since no proof bounds time.  The WASI theorems trust a model of the Preview 1 host.  The WGSL theorems trust an invocation semantics, a statement of the Vulkan memory model, and strict binary32 arithmetic, and the PTX theorems trust a thread semantics and a statement of the PTX memory model.  Both GPU targets also assume that no thread on the device runs past a point where its semantics stops.  Every specification theorem trusts its transcription of a standard or its definitions from Mathlib.

## Commands

Commands run from the repository root.  They require Lean through Elan at the version in [the toolchain file](lean-toolchain), the dependencies in [the Lake manifest](lake-manifest.json), `wasm-tools` at [the pinned version](.wasm-tools-version), and a C compiler for the Wasmtime host, with Elan's tools, `wasm-tools`, and `uv`, which runs the Python tools, on the search path.  On Linux, the Lean runner requires a systemd user session with cgroup controls.  [The host setup](docs/verified-manual.md#the-wasmtime-host) also covers macOS.

The GCD example builds the verified compilation of GCD, writes the module, validates it, and runs a call, which prints `6`.  Every Lean or Lake command uses [the resource-limited runner](tools/leanrun), as [the repository instructions](AGENTS.md) require, and the test drivers call the runner themselves.  A focused build, such as `tools/leanrun --timeout 60m lake build Library.Random.Lcg.Verified`, builds that module and its imports.

```sh
tools/download-wasmtime.sh
tools/build-wasmtime-host.sh
tools/leanrun --timeout 60m lake build Library.Numerics.Arithmetic.Gcd.Compiled
mkdir -p build/verified
tools/leanrun --timeout 10m lake env lean --run tools/Emit.lean \
  Library.Numerics.Arithmetic.Gcd.Compiled Library.Numerics.Arithmetic.Gcd.compiled.module \
  build/verified/gcd.wasm
wasm-tools validate build/verified/gcd.wasm
build/tools/leanexe-wasmtime-host call build/verified/gcd.wasm gcd i64 i64:48 i64:18
```

The default build covers `LeanExe`, `Examples`, and `Demos`.  The `Verified` aggregate also imports `Demos.Verified`, which compiles the applications with `verified_compile`.  The complete `Library` build includes the numerical proofs and can take several hours.

```sh
tools/leanrun --timeout 60m lake build
tools/leanrun --timeout 60m lake build Verified
```

[The full check](docs/verified-manual.md#the-full-check), `tools/full-check`, builds every library with the test executables, runs the module, native, WASI, bare-metal, GPU, knowledge-base, Rocq, and Talos checks, and writes each step's output to `build/full-check/` and a record of the commit, the toolchain, and each step's status, duration, and counts to `STATUS.md` at the root, which Git ignores.  On a machine with about 12 GiB of memory, a cold proof cache first needs [one-worker builds of the memory-heavy numerical proofs](docs/verified-manual.md#memory-heavy-numerical-proofs), with a 10 GiB memory high limit and a 12 GiB maximum.  The order book's allocation charges need more than 10 GiB at one thread, so under that limit their module completes only while the kernel throttles it.  The manual gives the full check's resource settings.

[The verified driver](tests/verified/run.sh) writes modules to `build/verified/` and compares them with native Lean on [the shared case corpus](Verified/Examples/Cases.lean), then checks numerical file theorems and accuracy tests.  [The binary64 GPT driver](tests/gpt/run.sh), the other scripts of `tests/gpt/`, [the drone driver](tests/drone/run.sh), [the level sessions](tests/modules/chunks.py), [the SplitMix64 comparison](tests/prng/compare.py), and [the GPT-2 text generator](tools/gpt2.py) run the verified modules in `build/verified/` unless given the path of another module.  `tests/wasi/run.sh` checks the WASI proofs, reflected modules, byte ownership, and native and WebAssembly I/O, and its `--foundations-only` form runs the proof and semantic checks without the external-engine tests.

The native drivers need CompCert 3.18's `ccomp` and `clightgen`, built from one source tree for the target, which the variables `CCOMP` and `CLIGHTGEN` name when they are not on the search path.  The bare-metal drivers also need `qemu-system-aarch64`, and the Cortex-M7 drivers `qemu-system-arm`, the GNU Arm binutils, Renode 1.17.0, and for the board `st-flash` 1.8.0, with libusb and the ST-LINK firmware V2J39M27 for the reset of `tools/baremetal/stlink_nrst.py`.  Each script's header states its checks, its options, and the other tools that it needs.

```sh
tests/native/verified.sh              # the registry's modules in C, against Wasmtime
tests/native/verified.sh --aligned    # modules without the alignment test
tests/native/aligned.sh               # the refusal of modules without aligned theorems
tests/native/bench.sh --placements    # native and Wasmtime times at sixteen placements
tests/baremetal/programs.sh           # the programs with a generated main
tests/baremetal/inputs.sh             # SHA-256 of messages that QEMU's loader places
tests/baremetal/verified.sh           # the registry's cases on bare-metal AArch64
ACCEL=kvm tests/baremetal/programs.sh # the same programs under KVM
tests/baremetal/a64-images.sh         # the AArch64 Images and their theorems
ACCEL=kvm tests/baremetal/a64-images.sh # the Images under KVM
tests/baremetal/a64-uart.sh           # the Images that read their input from the UART
tests/baremetal/a64-encode.sh         # LDR Wt and LDRB against the GNU assembler
tests/isla/theorems.sh                # the model's forms against Isla's traces
tests/baremetal/m7-image.sh           # the Cortex-M7 code images and their checks
tests/baremetal/m7-qemu.sh gateway    # a Cortex-M7 image and its theorem under QEMU
tests/baremetal/m7-board.sh check gateway # the board's image and its theorems
tests/baremetal/m7-board.sh nrst sha DEVICE # an image on the board after an NRST reset
tests/isla/m7-theorems.sh             # the Cortex-M7 forms against Isla's traces
```

`uv run tests/web/serve.py` serves, on http://127.0.0.1:8000/, a page that runs the WGSL kernel tests on a browser's WebGPU and a page that runs GPT-2 with its kernels on WebGPU, in WebAssembly, or on both and compares the scores.  The GPT-2 page needs the binary32 weights that `uv run tests/gpt32/generate.py --export` writes.  [The browser test guide](tests/web/README.md) covers setup and proof scope.
