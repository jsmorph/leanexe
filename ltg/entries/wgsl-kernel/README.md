# WGSL kernels from IR builds

Use this entry for a WGSL kernel.  `LeanExe.WGSL.Module.print` prints a kernel in a restricted format, one space or newline between tokens, every number as eight hexadecimal digits, and every binary expression in parentheses, and `Module.parse_print` proves that `Module.parse` reads the text back as the kernel when its indices fit in eight digits.  For a concrete kernel, `Module.parse_print_of_wfb` with `decide` gives the same.  `Module.invoke` runs one invocation on the read-only buffers and returns its stores to the read-write buffer, which it may not read; `Module.dispatch` applies the stores of invocations `0` to `count - 1` in order; and `Module.RaceFree` states that distinct invocations store to distinct words, which makes the order irrelevant under WGSL's memory model.

A kernel comes from a compiled build, `buildWith dst limit index (get c) body element`, whose count local `c` is a `u64` parameter or the local of an `arraySize` statement before the build.  A `Spec` names the parameters' kinds, the index local, the count, the locals the body assigns with their types, a bound on the IR locals, the body, and the element, and `Spec.wfb` checks its indices by `decide`.  `Spec.module` builds the kernel: one buffer per parameter, the index pair, the parameters' variables, a `var` per assigned local, a return when the index is not below the count, the translations of the body (`trStmt`) and the element (`trExpr`, one `let` per IR node), and the stores of the element's halves.  An assignment becomes the expression's `let`s and an assignment to the local's `var`, and the compiler's loop becomes a `while` on `lt64`, which runs in lockstep with the denotation's loop.  Both test the condition at most `loopBound` (2^64) times.  `Spec.dispatch_eq` proves the kernel from one fact: for each `k` below the count, `body.denote` succeeds and `element.denote` of its result gives `f k`.

The same fact proves the Wasm function.  `Stmt.denote_spec` turns the body's denotation into a `Triple` that ends in a state agreeing with the denoted locals, and `Expr.eval_denote` turns the element's denotation into `Stmt.buildWith_spec`'s element hypothesis.  `Stmt.denote_loop` gives the denotation of the compiler's loop template as `LeanExe.loop` from a fact about one run of its body.  `Examples.Binary32.matVecRow_denote` is such a fact for `matVec32`.  `Examples.Binary32.matVec32_implements` uses it through `Stmt.buildWith_spec`, and `Examples.Binary32.matVecKernel_dispatch` through `Spec.dispatch_eq`.  For a build with no body, `Examples.Binary32.axpyArrayElement_denote` is one `simp` call with `getElem!_map_toBits32` and `F32Bits`.

In proofs about one invocation, prove one lemma per statement and keep buffer contents behind hypotheses so that `simp` never unfolds `arrayWords`.  When a hypothesis states the value of a subexpression, `generalize` that subexpression before `simp`.  State `UInt32` facts through `toNat` (`UInt32.toNat_add`, `toNat_mul`, `toNat_sub`, `toNat_div`, `toNat_ofNat'`) and close them with `omega`, since `simp` rewrites `UInt32.ofNat (2 + 2 * n)` into `2 + 2 * UInt32.ofNat n`.  Generalize the halves of a `u64` before `simp` for the same reason.

`u64` addition and multiplication are `add64` and `mul64` on pairs.  `mul64` computes the high half of the low halves' product from 16-bit halves by division and multiplication by `65536u`, and its proof uses `grind` for the ring identity and `omega` after generalizing the products.  A long loop can exceed a GPU's watchdog, and one dispatch covers at most 65,535 workgroups of 64 invocations.  The model describes neither, so the host must reject counts it cannot cover.
