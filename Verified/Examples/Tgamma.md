# The gamma function

[The implementation](Tgamma.lean) exports `tgamma`, a port of CORE-MATH's correctly rounded `cr_tgamma` [1, 2] that calls [the software fused multiply-add](Fma.lean) wherever the C code calls `__builtin_fma`.  The decided bound is one representable step, `F64SignedRounding.WithinSteps 1`, from the nearest-even rounding of `Γ`, which is weaker than the correct rounding that CORE-MATH claims for its code.  `tests/verified/run.sh` checks the port natively against an integer reference at 74,373 arguments, and every result equals the reference.  `transcendentals` proves the exact results at `±0`, `±∞`, and NaN and the fast path below `1/4` within one step, under the hypotheses that the Theorems section names, and track `arc` is proving the other paths.  The module's `verified_compile` call is commented out until the compiler change that [the plan's section "Resuming the work"](../../transcendentals.md#resuming-the-work) describes.  `transcendentals` also proves [the software fused multiply-add](Fma.md) correct and holds the mathematical foundations of the proof from track `erf` (commit `0efc1d87`): identities of `Γ`, the overflow and underflow thresholds, Stirling's series with a proved remainder, and kernel-checked Taylor models of `Γ` and `lgamma`.  `TgammaApprox` states the bounds on CORE-MATH's polynomials and tables, and track `erf` is proving them.

## Specification

`tgamma` computes `Γ` of the value of its argument.  [Mathlib's `Real.Gamma`](https://github.com/leanprover-community/mathlib4/blob/85e3a25e006c35636f0e53b0e9296caca2685bc0/Mathlib/Analysis/SpecialFunctions/Gamma/Basic.lean) is Euler's integral (DLMF 5.2.1) [4] for positive arguments, extended to the other reals by the recurrence `Γ (s + 1) = s Γ (s)`, and it takes the value 0 at zero and the negative integers by convention (`Real.Gamma_neg_nat_eq_zero`) [5].  The poles are therefore outside the domain of the accuracy statement, and their results are exceptional values.  The domain of the bound is every finite double other than zero and the negative integers.

The decided statement for such an `x` is `F64SignedRounding.WithinSteps 1 (Real.Gamma (value x.toBits)) (Tgamma.tgamma x).toBits`, with `WithinSteps` from [the signed rounding reference](../../LeanExe/ProofKit/F64SignedRounding.lean) as for the other functions: the word is not a NaN, and its position on the ordered line of doubles lies within one step of the position of the signed nearest-even reference.  The reference is `±∞` beyond the overflow threshold `2^1024 - 2^970` of IEEE 754-2019 clause 4.3.1 [6], which `Γ` crosses at about 171.62, and `±0` at or below half the smallest subnormal, which holds for every non-integer `x ≤ -184`.  The bound is the decision of 2026-10-10 recorded in [the journal](../../devnotes.md#2026-10-10-decisions-after-the-review-of-gamma-bessel-and-worst-inputs) and in [the plan](../../transcendentals.md#decisions), and the review of the same day recommended the special values in the table.

| Input | Result of the port | Source of the rule |
|---|---|---|
| `+0`, `-0` | `+∞`, `-∞` | C99 F.9.5.4 [7]; POSIX [8] |
| a negative integer | the canonical NaN | C99 F.9.5.4; POSIX on IEC 60559 systems |
| `-∞` | the canonical NaN | C99 F.9.5.4; POSIX |
| `+∞` | `+∞` | C99 F.9.5.4; POSIX |
| NaN | the canonical NaN | C99 F.9 paragraph 11; the deterministic profile of WebAssembly [9] |
| `x ≥ 0x1.573fae561f648p+7` | `+∞`, as `0x1.fp1023 + 0x1.fp1023` | overflow, POSIX |
| non-integer `x ≤ -184` | `±0` with the sign of `Γ x`, as `2^-1022 · (±2^-1022)` | underflow, POSIX |
| `x = 2^-1024` | `+∞`, as `0x1.fffffffffffffp+1023 + 0x1p+970` | overflow: `Γ x` exceeds the threshold |

IEEE 754-2019 lists no gamma function among its recommended operations [6], so C99's Annex F and POSIX fix the special values.  The port's NaN results are the canonical NaN, as every NaN result of the dialect is.  CORE-MATH sets `errno` when built with `CORE_MATH_SUPPORT_ERRNO` and raises the floating-point exceptions of these paths, and the port does neither.

## Algorithm

CORE-MATH's method evaluates `Γ` in double-double arithmetic, a pair `h + l` of doubles, with an explicit error bound `eps` for each path.  The project's paper describes the method: a fast path computes an approximation `y` with an error bound `ε`, a rounding test checks whether `[y - ε, y + ε]` crosses a rounding boundary, and otherwise an accurate path returns the correctly rounded value [3].  In `cr_tgamma`, when `h + (l + eps)` and `h + (l - eps)` round to the same double, the fast path returns that double, and otherwise `as_tgamma_accurate` evaluates `Γ` to about 100 bits, with a table of 57 hard cases for the inputs whose rounding test that path fails.  The structure below comes from the source [1].

| Range | Fast path |
|---|---|
| `\|x\| < 2^-112` | `1/x`, the leading term of `Γ x = 1/x - γ + ⋯`, and the correction for an exact `1/x` changes only the inexact flag and the directed roundings |
| `2^-112 ≤ \|x\| < 1/4` | `1/x` plus a polynomial of degree 20 in `x`, whose constant term is `-γ` |
| `-3 ≤ x ≤ 4`, not an integer | a polynomial of degree 17 in `d = x - (i + 3.5)` that approximates `Γ` on `[3, 4]`, divided by the product `x (x + 1) ⋯ (x + m - 1)` of the shifts that carry `x` there, the recurrence of DLMF 5.5.1 [4] |
| positive integers | `(x - 1)!` as a product in double-double, rounded once |
| `4 < x < 0x1.573fae561f648p+7` | `exp (lgamma x)`, with `lgamma` from Stirling's series (DLMF 5.11.1) by `as_lgamma_asym` and the exponential by `as_expd`, both in double-double |
| `-184 < x < -3`, not an integer | the reflection `Γ x = π/(sin (π x) Γ (1 - x))` (DLMF 5.5.3), with `Γ (1 - x)` from Stirling's series and `sin (π x)` from `as_sinpid`.  Below -170 the code tests whether the result is subnormal and then rounds it at the subnormal position. |

The accurate path `as_tgamma_accurate` uses polynomials in triple or double-double arithmetic, a series of 28 double-double terms below `1/4` and polynomials on nine ranges above it, and rounds once.  The fast path's error bounds, such as `1e-21` relative on `[-3, 4]` and `2e-21 + 1.84e-22 x` relative above 4, are constants of the source, and no Lean proof establishes them.  The decided one-step bound needs a proof that every path's error stays below one and a half spacings of the result, at least `1.5 · 2^-53 ≈ 1.7e-16` relative, about five orders of magnitude weaker than the bound `1e-21` that the rounding test on `[-3, 4]` assumes.

## Implementation

The source is `src/binary64/tgamma/tgamma.c` of CORE-MATH at commit `ff2f71f635e95d395a6646b7e7b2c72e7b03a5d8` [1], `Copyright (c) 2024 Alexei Sibidanov`, under the MIT license [2].  The module docstring of [the implementation](Tgamma.lean) gives the copyright line and names the MIT license, and it omits the license's permission notice, which the license requires in all copies or substantial portions.  The port follows the C code operation for operation in the Verified dialect, the subset of Lean that [the Verified compiler](../README.md) translates to WebAssembly.  The commented `verified_compile` call lists 40 functions: the 14 of `Fma` and 26 of this module, among them the double-double operations `fastTwoSum`, `twoSum`, `fastSum`, `sumDD`, `mulDD`, `mulDD3`, `mulDDD`, and `polyDDD`, the helpers `asLogd`, `asExpd`, `asSinpid`, and `asLgammaAsym` for the logarithm, the exponential, `sin (π x)`, and Stirling's series, `database`, `accurate`, `tgammaWith`, and `tgamma`.

## Theorems

`transcendentals` contains no accuracy theorem about `Tgamma.tgamma`.  The Lean module defines no `compiled` WebAssembly module, so there is no byte theorem and no file theorem, and `tests/verified/run.sh` writes no `tgamma.wasm` and runs [the accuracy check](TgammaAccuracy.lean) natively.  The intended results follow the other functions: `WithinSteps 1` against `Real.Gamma` on the domain above, exact words for the exceptional values in the table, a byte theorem of the form of `ExpTheorem.exp_bytes_accuracy` with the eight tables borrowed, and a file theorem.  `FmaSpecTheorem.fma_nearest` states that [the software fused multiply-add](Fma.md) returns a nearest double to `a · b + c`, which is the hypothesis `FmaSpec.FmaNearest` of every path of the proof.  The Proof section lists the mathematical facts toward the accuracy theorem.

`TgammaSpecial` proves the first exceptional results, for `tgammaWith` with any tables and hence for `Tgamma.tgamma`.  `tgamma_pos_zero` and `tgamma_neg_zero` give `+∞` and `-∞` at `+0` and `-0`, `tgamma_pos_inf` gives `+∞` at `+∞`, and `tgamma_neg_inf` and `tgamma_nan` give the canonical NaN at `-∞` and at every NaN.  Their axiom report in `gamma-special-2.log` lists only `propext`, `Classical.choice`, and `Quot.sound`.  `TgammaSmallPath.smallPath_within` proves the fast path from `2^-112` to `1/4` in magnitude within one step of `Γ`, from the hypotheses `FmaSpec.FmaNearest` and `TgammaApprox.SmallFact` and the hypothesis that the accurate path is within one step at the same input, which covers the case where the rounding test sends the input there.  In `transcendentals`, the results at the negative integers, at `2^-1024`, and from the overflow and underflow thresholds are open, as are the other paths and the accuracy theorem of `Tgamma.tgamma`.

Branch `w/poly` proves more results that are not merged.  At commit `171f956a`, `TgammaMainPath.mainPath_within` proves the path on `(-3, 4)` within one step for every finite non-integer `x` with `-3 < x < 4` and `|x| ≥ 1/4`, from `FmaSpec.FmaNearest`, `TgammaApprox.MainFact`, and the accurate path at the same input.  At commit `eb4f3983`, four more paths are within one step without the accurate path: `TgammaTiny.tinyPath_within` covers every nonzero finite `x` below `2^-112` in magnitude, `TgammaInt.intPath_within` the integers from 1 to 171, `TgammaEdge.overflowPath_within` every argument from `0x1.573fae561f648p+7` on, where the result is `+∞`, and `TgammaEdge.underflowPath_within` the non-integers at or below -184, where the result is a zero.  `TgammaEdge.intPath_neg` gives the canonical NaN at the negative integers.  The paths above 4 and below -3, the accurate path, and the accuracy theorem are open on the branch as well.

## Proof

The proof has four parts.  The first is a theorem for `Fma.fma`, which the review of 2026-10-10 proposed to prove once with ProofKit's rounding of scaled rationals ([the review](../../devnotes.md#2026-10-10-review-of-the-options-for-stages-7-and-8)), and which `FmaSpecTheorem.fma_nearest` provides.  The second is the set of mathematical facts that the algorithm uses and Mathlib lacks: Mathlib has `Real.Gamma` with the recurrence `Real.Gamma_add_one` and Euler's reflection formula `Real.Gamma_mul_Gamma_one_sub` [5] and no Stirling series with a remainder for `log Γ` at real arguments, so the proof needs a remainder bound, such as those of DLMF 5.11(ii) [4].  The decision of 2026-10-12 is to prove these facts only to the precision that a one-step bound needs ([the integration notes](../../devnotes.md#2026-10-12-integration-of-expm1-tanh-erf-log1p-atan-atan2-asin-and-acos-first-push)), and track `erf` proved the foundations in six ProofKit modules on branch `w/erf` at commit `0efc1d87`, which `131e6ff6` merged into `transcendentals`.  The third is an error analysis of each fast path, the accurate path, and the 57 hard cases against one and a half spacings of the result, with the subnormal results below -170 and the overflow and underflow boundaries.  The fourth is the byte and file theorems, once `verified_compile` runs.

The six modules are `GammaBasic`, `GammaStirling`, `RatExpLog`, `GammaThresholds`, `TaylorModel`, and `GammaModels` in `LeanExe/ProofKit`.  Their 42 axiom reports list only `propext`, `Classical.choice`, and `Quot.sound` (`erf-gamma-12.log` in `build/transcendentals` on the build host), and [the journal](../../devnotes.md#2026-10-11-foundations-for-core-maths-tgamma-and-lgamma-track-erf) lists the facts with the C source lines that use them.  The table gives the results that `tgamma`'s proof uses.

Stirling's remainder comes from Mathlib's limit `Real.BohrMollerup.tendsto_log_gamma` and Stirling's formula for `n!`: the remainder `R` satisfies `R y - R (y + 1) = ρ y` with an elementary `ρ`, the kernel bounds `ρ` by a polynomial certificate in `1/y`, and the bound telescopes.  Each fact about a CORE-MATH polynomial then becomes a kernel check of Taylor models on pieces of its interval, with `π` from Mathlib's 20-digit bounds, which limit a model's error to about `10 ^ -21`.  The one-step bound needs about `2 ^ -60` relative error per approximation, so each fact is proved to that precision, which is weaker than the `1e-21` of CORE-MATH's rounding test.  The bounds on the polynomials about 3.5 and below `1/4`, on the Stirling fits of `as_lgamma_asym`, on the tables of `as_logd`, `as_sinpid`, and `as_expd`, on the accurate path, and on the 57 hard cases are open, and track `erf` is proving them.

Track `arc` is doing the third part.  `TgammaApprox` (commit `b92f7941`) states, as propositions that the floating-point proof takes as hypotheses and that track `erf` is to prove, the approximation facts that the code relies on.  These are the polynomials below `1/4` and on `[3, 4]`, the accurate path's polynomial below `1/4` and its nine ranges against `Real.Gamma`, Stirling's two forms against `log Γ`, and the kernels, tables, and constants of the logarithm, the exponential, and `sin (π x)`, each built from the exact values of the table words.  Each tolerance leaves a factor of at least 8 over the largest error that a 90-digit evaluation found at dense sample points, while the analysis needs only a total relative error well below `2^-53` before the final rounding.  Commit `d06760e6` widens the interval of `MainFact` to `\|d\| ≤ 1/2 + 2^-50`, because the code rounds `x - 7/2` before it chooses the nearest integer, so that `d` exceeds `1/2` by up to `2^-51`, at `x = 1 - 2^-53` for example.  On branch `w/poly`, `ExpFact` states the kernel of `asExpd` for `\|X\| ≤ 5/8` instead of `\|X\| ≤ 513/1024`, with the same tolerance `2^-74`.  `asLogd` returns a low part up to `2^-22` without renormalizing it, the product in `asLgammaAsym` turns that into a low part up to about `2^-14.5`, and the first product of `asExpd` carries it into the kernel's argument, up to about `0.566`.  A 60-digit sampling of the kernel at 4001 points of each interval gives a largest error of `2^-76.89` on `[-5/8, 5/8]`, a factor above 7 below the tolerance. The compilation failure sets the order of the work.  With its `verified_compile` call, the module's build ran 25 minutes of CPU time at the runner's limits of 4.2 GB of memory and 1 GB of swap before `tools/leanrun` stopped it.  Probes that chain `let (h, l) := mulDD …` bindings showed the objects of the generated program growing from 5,093 at 10 bindings to 15,413 at 20, while the distinct subterms grew from 491 to 851, and a probe of 40 bindings exhausted the memory ([the journal](../../devnotes.md#2026-10-11-a-software-fused-multiply-add-core-maths-gamma-functions-and-fdlibms-bessel-functions)).  `Ctx.ctx` in `Verified/Reflect/Command.lean` rebuilds the expression of the whole context at each of its 23 uses, and a first change that shares it, commit `a95ae82b` on branch `w/reflect`, made the program term linear, while the kernel's checking still grows faster than linearly.  The plan records the measured cause: the kernel's evaluation of the code generator in the `decide +kernel` proof that `encode p.module` succeeds, where `Expr.code` in `Verified/Compile.lean` keeps the live variables as a chain of closures, at least cubic in the nesting depth of lets.  The decided change computes liveness as data, and the ported functions are not to be split.  Track `ports` has made that change on branch `w/reflect` and is measuring it ([the plan](../../transcendentals.md#decisions-not-yet-completed)).

## Tests

[The accuracy check](TgammaAccuracy.lean) compares `Tgamma.tgamma` natively with the double nearest to `Γ x` from [the gamma reference](GammaReference.lean), and it fails at the first result more than one step away.  Its 74,373 arguments are 30,001 evenly spaced values from -185 to 172 and 20,001 from -4 to 5, 20,000 hashed values over the exponents from `2^-1074` to `2^7` with both signs, the integers from -200 to 172, the five doubles at and around each integer from -190 to 172 and each half-integer from -189.5 to 172.5, the doubles around the thresholds `2^-112`, `1/4`, 3, 4, `0x1.573fae561f648p+7`, and -184 and their negations, the 57 hard cases and their neighbors, the ten inputs of `WorstCases.tgamma`, and 13 special values.  The ten worst-case inputs give the largest known `tgamma` errors in Tables 4 to 11 of Gladman, Innocente, Mather, Ozaki, and Zimmermann's report [10], whose Table 3 lists 0.500 units for GNU libc 2.44 and 1.03e3 for FreeBSD 15.1.  The fast paths rarely reach the accurate path, so the check also calls `Tgamma.accurate` directly at every eighth argument from -184 to 171 above `2^-112` in magnitude, other than the integers, and at the 57 hard cases, 7,002 arguments.

The reference computes `lgamma y` for `y > 0` as `lgamma (y + N) - ln (y (y + 1) ⋯ (y + N - 1))` with `y + N ≥ 300`, Stirling's series with 60 terms and a remainder below `2^-650`, and one logarithm of the exact product, and for `x < 0` the reflection with `Reference.sinCosTurns`.  `Γ` is the exponential of `lgamma` with the sign of `sin (π x)`.  The Bernoulli numbers come in exact fractions from the algorithm that the module attributes to Akiyama and Tanigawa, and a Python model of the reference at 600 bits gave the same doubles as compiled CORE-MATH at 3,500 arguments.  The truncation errors are stated in docstrings and are not proved.

In `opus-verified-tests-14.log`, the run of `tests/verified/run.sh` in `build/transcendentals` on the build host after the `sinh` merge, all 74,373 results equal the reference, so the largest measured distance is 0 steps against the decided bound of 1, and the 7,002 results of the accurate path also equal the reference.  The first run, `ports-TgammaAccuracy-1.log` in `build/transcendentals` on the build host, gave the same results.  The runs use the module built without its `verified_compile` call, so they test the Lean function that the compiler will translate, and no compiled WebAssembly.

## Limits

Every result for `tgamma` is a test of the Lean function, and the decided theorems are open.  Until the compiler change is merged and `verified_compile` runs, no WebAssembly module exists.  After that, the limits of the compiled functions apply as for [the exponential](Exp.md#limits): Talos and the decoder are trusted, the file theorem trusts `binary_file%`, the theorems cover the canonical NaN argument only, and host actions between calls need their own theorem.  The port depends on `Fma.fma` at every path, and that function has only a native check, `FmaAccuracy.lean`, which found 763,816 operand triples equal to the exact value rounded to nearest and which `tests/verified/run.sh` does not run.

The decided bound allows one step where CORE-MATH's code is designed to be correctly rounded, so a proof of the bound will not establish CORE-MATH's claim.  A theorem of correct rounding would need CORE-MATH's search for hard cases as a verified input, which the review did not recommend.  The port drops `errno` and the floating-point exceptions, which C99 and POSIX specify for the poles, the overflow, and the underflow.
