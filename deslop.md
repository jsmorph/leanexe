# Deslop status

Last updated 2026-10-01 on branch `deslop`.  The repository is one Lake package at its root, with the libraries `LeanExe` (source programs) and `Project` (IR, compiler, pipeline, proofs).  `README.md` gives the layout and commands, and `devnotes.md` is the development journal.

## Goal

The deslop replaces the repository's parallel proof routes with one pipeline and removes everything else.  A compiler translates a Lean function to an IR, `compile` translates the IR to a Talos `Wasm.Module`, `encode` produces the bytes, and a per-program proof shows that the module computes the Lean function exactly.  A binary decoder, tested against the official WebAssembly testsuite, defines what the bytes mean, and `decode_encode` carries each theorem to the bytes.  The user treats the deslop as a clean, new development with no concern for legacy code.

## Design

The compiler is not verified at first.  Its rules are verified one at a time, and each proved rule enters the LTG knowledge base, so per-program proofs shrink while the trusted base stays the same.  The system stays as small as possible, and per-program proofs carry the rest of the burden with help from LTG.

| Component | Design | State |
|---|---|---|
| IR | Embedded in Lean: expressions over locals, assignment, `if`, `while`, loads, stores, and calls.  Values are 64-bit words, Booleans, or binary64 bit patterns.  It has no arrays, structures, or ownership. | Expressions and statements exist.  `f64` expressions read locals, take literals, add, subtract, multiply, divide, take square roots and absolute values, compare, and branch.  Assignment works at any type, and a load reads a stored word as a 64-bit word or as an `f64`.  Expressions read memory: `Expr.read` loads an array element after comparing the position with the length word. |
| Translation | `compile : IR → Wasm.Module`, with one `wp` rule per construct proved once against Talos.  The IR means what its compiled code does. | `Expr.program_spec`, a `Triple` rule for each statement, and the frame notion `State.Frame` with `Expr.eval_frame`.  `Triple` takes the module, so the call rule can use the callee's specification. |
| Compiler | Lean to IR, reading each definition's unfolding equation.  Verifying a rule means proving that its template implements its source construct, stated in terms of Lean's own functions, so no `Lean.Expr` semantics is trusted. | `UInt64` arithmetic, comparisons, `if`, tail recursion, `Array UInt64` parameters, and `Array.foldl` over an array parameter or an array literal, which becomes a temporary released after the fold.  `xs.size.toUInt64` loads the length word, and a function may return an array literal.  `Float` parameters, results, and literals, with `+`, `-`, `*`, `/`, negation, `Float.sqrt`, `Float.abs`, `min`, `max`, comparisons, `==`, and `if`.  `Array Float` parameters, and folds over them.  A fold's accumulator is `UInt64` or `Float`.  `UInt64.toFloat` and `Float.toUInt64`, and `xs.size.toUInt64` for either array type.  `LeanExe.loop` with a state of words, floats, or pairs of them; pattern matches on pairs; `have` in loop bodies; `min` on `UInt64`; and `xs[i.toNat]!` on an `Array UInt64` parameter.  An array result may be an array literal, `xs.set! i.toNat v`, `xs.insertIdx! i.toNat v`, or `LeanExe.build n f`, which compile to a copying template, or an array parameter, which is copied.  A pair result compiles to several WebAssembly results.  `LeanExe.loop` also takes an `Array Float` state, which starts as a copy of an array variable, with a body that is one call of a compiled function.  The tail-recursion, fold, array-size, array-literal, release, float-arithmetic, and array-state loop rules are proved. |
| Hints | Untrusted annotations: the rule behind each fragment, its source term, its instruction path in the decoded module, and the name of each local.  A wrong hint costs proof time and cannot produce a false theorem. | Emitted for every IR node. |
| Runtime | `alloc` and `release`, specified and proved once.  Every object has one owner, so its count is 1; the compiler places `release`, and per-program proofs check the placement until a rule lemma covers it. | Both functions are in every module and pass host tests.  `alloc_spec_or_abort` covers every request, and `release_run` covers an owned array with no child pointers.  `release` traps unless the count is 1.  The release of nested objects is not specified. |
| Statement | `Implements`, over a `Represent` class that says how a value appears as WASM values and heap data.  A call either returns the correct result or traps at `unreachable`, with no premise about free memory.  It includes a frame clause: every array borrowed or owned before the call is still borrowed or owned after it, and the memory's maximum size is unchanged. | Instances for `UInt64`, `Float`, tuples of scalars, `Array UInt64`, `Array Float`, and pairs of any represented types.  `Func.implements_heap` takes arguments and a result of any `Represent` type and a body that may allocate and free. |
| Bytes | The encoder, `decode_encode`, and one decoder. | Done, with `f64.const`, `f64.eq`, `f64.lt`, `f64.le`, and `f64.abs` added for floats. |
| Floating point | The WebAssembly deterministic profile.  See "Floating point". | Binary32 and binary64 equality proofs for addition, subtraction, multiplication, division, and square root; binary64 comparisons, negation, and absolute value. |

The trusted base is Lean's kernel, Talos's semantics, the decoder, and any I/O adapter.  The source dialect has fixed-width integers and IEEE floats, compiles `panic` to `default`, allows recursive values, and does I/O through a pure step function driven by a fixed adapter.  Rule lemmas must state what their templates leave unchanged, meaning the locals they do not write and the memory outside the blocks they allocate or write, because lemmas for nested templates do not compose otherwise.

## Proved

`scale_implements` states that `scale.module` implements `scale a b c = a * b / c + 1` on every triple of `UInt64` arguments.  Its proof applies `Func.implements` and one `simp` call; the only remaining step is Lean's `a * b / 0 = 0`.

`gcd_implements` states that `gcd.module` implements Euclid's algorithm on every pair of `UInt64` arguments.  The compiler produced a `while` loop over a `done` flag whose body branches on `b = 0`.  The proof applies `Func.tail_implements` and proves only `gcd_step`, one iteration, in 29 lines; the first proof, which gave the invariant, state measure, entry, and exit directly to `Stmt.while_spec`, took 63 lines by the same count (non-blank, non-comment).

`sumArray_implements` states that `sumArray.module` implements `sumArray xs = xs.foldl (· + ·) 0` on every borrowed `Array UInt64`.  The compiler produced an assignment of 0 to an accumulator followed by `Stmt.fold`, a loop that loads the length word and then each element.  The proof applies `Func.implements`, the assignment rule, and `Stmt.fold_spec`, and it takes 20 lines including the statement.  `Stmt.fold_spec` needs the array's layout in memory, which `Heap.Borrowed` provides, and an obligation that the fold body evaluates to `g a e`.

`pairSum_implements` states that `pairSum.module` implements `pairSum a b = #[a, b].foldl (· + ·) 0` on every pair of `UInt64` arguments, allocating at most 72 bytes.  The compiled code calls `alloc`, stores the length and the two elements, folds, and calls `release`.  The proof applies `Func.implements_heap`, `Stmt.arrayLiteral_spec`, the assignment rule, `Stmt.fold_spec`, and `Stmt.release_spec` with `Heap.At.release`, in 56 lines including the statement.  The runtime proofs under it are `alloc_spec`, which reuses ProofKit's proof of the allocation program, and `release_run`, which steps through `release`'s code for an array with count one.

`sumCount_implements` states that `sumCount.module` implements `sumCount xs = #[xs.foldl (· + ·) 0, xs.size.toUInt64]` on every borrowed `Array UInt64`: the result is an array that the caller owns, the argument stays borrowed, and the call allocates at most 72 bytes.  The proof applies `Func.implements_heap`, `Stmt.fold_spec`, `Stmt.arraySize_spec`, and `Stmt.arrayLiteral_spec`, whose preservation clause keeps the argument borrowed, in 55 lines including the statement.

`axpy_implements` states that `axpy.module` computes `axpy a x y = a * x + y` bit for bit on every triple of `Float` arguments, NaN included.  The proof applies `Func.implements` and one `simp` call with `F64Bits.toBits_add` and `toBits_mul`.  `scaledHypot_implements` does the same for `scaledHypot x y s = (x * x + y * y).sqrt / s`, adding `toBits_div` and `toBits_sqrt`.  `piecewise_implements` covers a function with `==`, `<`, `≤`, negation, `Float.abs`, `min`, `max`, three literals, and nested `if`, in 29 lines including the statement.

`sumSquares_implements` states that `sumSquares.module` computes `sumSquares xs = xs.foldl (fun acc x => acc + x * x) 0.0` bit for bit on every borrowed `Array Float`.  An `Array Float` is stored as the `Array UInt64` of its elements' bit patterns, and the fold's accumulator and element locals have type `f64`.  The proof applies `Stmt.fold_spec` with a step on bit patterns, in 21 lines including the statement, and a 7-line lemma converts the result with core's `Array.foldl_map` and `Array.foldl_hom`.

`mean_implements` proves `mean xs = xs.foldl (· + ·) 0.0 / xs.size.toUInt64.toFloat` bit for bit, with the fold, the array-size rule, and `F64Convert.toBits_toFloat`.  `bucket_implements` proves `bucket x lo width = ((x - lo) / width).toUInt64`, a histogram index, with one `simp` call and `F64Convert.toUInt64_eq`.  Both conversion theorems cover NaN, the infinities, and out-of-range values.

`marketBuy_implements` proves the first CLOB operation: `marketBuy askPrices askSizes qty` walks the ask levels with `LeanExe.loop`, taking `min remaining askSizes[i]!` at each level, and returns `#[filled, cost]`, an array the caller owns.  The source equals a loop over a named step function by `rfl`.  The loop rule `Stmt.loop_spec` needs one obligation about the body, which `body_run` proves in 16 lines by computing the body's effect with `Stmt.run` and `simp`, including two bounds-checked reads.  The whole proof takes 75 lines including the statement; the assignments before the loop are proved the same way, and the result array by `Stmt.arrayLiteral_spec`.

`fillLevel_implements` proves the second CLOB operation, `fillLevel sizes k amount = sizes.set! k.toNat (sizes[k.toNat]! - amount)`, which returns a new array the caller owns.  The copying template's rule `Stmt.build_spec`, 198 lines proved once, allocates the array and stores each element; `set!_eq_build` equates `set!` with it by `Array.ext`.  The per-program proof takes 60 lines including the statement, and its allocation bound is `48 + 8 * (sizes.size + 1)` bytes.

`insertLevel_implements` proves the third, `insertLevel prices sizes k price size = (prices.insertIdx! k.toNat price, sizes.insertIdx! k.toNat size)`, which returns two new arrays as two WebAssembly results.  `Func` now holds a list of results, and `Implements` states the owned result in declaration order: Talos lists results with the top of the stack first, as it does arguments.  Chaining two copying templates required new runtime lemmas: an owned object stays owned after another allocation and after writes to the new block (`Heap.Owned.allocate`, `Heap.Owned.writesWithin`), and room for both allocations leaves room for the second (`Heap.Room.after_allocate`).  The proof takes 137 lines including the statement.

`setLevel_implements` proves `setLevel prices sizes k size = (prices, sizes.set! k.toNat size)` in 86 lines.  Its first result is a copy of the prices, which the compiler emits as `Stmt.copy`, the array's size followed by the copying template, and `Stmt.copy_spec` (55 lines) proves once.  `addBid` and `cancelBid` call `findLevel` and then, depending on whether the level at that position has the price, `setLevel`, `insertLevel`, or `removeLevel`, or copy both arrays.  `bid_spec` proves the part the two share, the search call, the number of levels, and the condition, once for any number of locals, in 116 lines.  `pairCall_spec` (47 lines) proves a call whose two arrays become the caller's result, and `pairCopy_spec` (57 lines) proves copies of two arrays as the result, both for any result locals and caller arguments.  With them, `addBid_implements` takes 51 lines and `cancelBid_implements` 85.  The previous `addBid` proof took 207 lines with the search inline, and its branches repeated the same steps.

`applyCommand_implements` proves `applyCommand prices sizes kind price size`, which calls `addBid` for kind 0 and `cancelBid` for kind 1 and returns copies of both arrays for any other kind.  A command is plain words, the user's choice until structures are decided.  The proof applies `pairCall_spec` twice and `pairCopy_spec` once, in 77 lines.

Two changes made these proofs possible.  The compiler now allocates a conditional's result locals before its branches, and a call or array build in a branch writes into them directly, so no branch copies results between locals.  `Implements` also states that the memory's maximum size is unchanged, which the user chose on 2026-09-29.  A call after another call needs room in the store the first leaves, and `Heap.Room.after` derives it from that fact.

`depth_implements` proves `depth prices sizes limit`, the total size of the levels priced at or above `limit`, a loop whose state is one word.  It follows `marketBuy`'s proof without the result array, applying `Func.implements` and `Stmt.loop_spec` with a 16-line body lemma, and it takes 52 lines including the statement.

`findLevel_implements` proves `findLevel prices price`, the search loop of `addBid` as its own function, in 45 lines.  `removeLevel_implements` proves `removeLevel prices sizes k = (prices.eraseIdxIfInBounds k.toNat, sizes.eraseIdxIfInBounds k.toNat)` in 129 lines, following `insertLevel`'s proof.  `eraseIdxIfInBounds_eq_build` equates the operation with the copying template in 37 lines, using core's `getElem_eraseIdx`.

`dot_implements` proves the first CPU GPT kernel, `dot xs ys`, a loop that sums `xs[i]! * ys[i]!` over the length of `xs`, bit for bit.  An `Array Float` read compiles to `Expr.ofBits` around the word read, and `Expr.ofBits` compiles to `f64.reinterpret_i64` and leaves the bit pattern unchanged.  `getElem!_map_toBits` relates the read of the bit patterns to Lean's read, which yields `UInt64.toFloat 0`, bit pattern 0, past the end.  The proof follows `depth`'s, with `F64Bits.toBits_add` and `toBits_mul` for the arithmetic, in 50 lines.

`matVec_implements` proves `matVec m v rows cols`, the product of a `rows × cols` matrix stored by rows and a vector, returned as a new `Array Float`, bit for bit.  Each element is a loop over a row, so the copying template gained a statement per element: `Stmt.buildWith` runs it before it stores the element, and `Stmt.build` is the case with `.skip`, which emits no instructions, so no module's bytes changed.  `Stmt.buildWith_spec` (201 lines) replaced `build_spec`'s proof, and `build_spec` is now its corollary.  The compiler translates the element in a block whose statements become the per-element statement, and it rejects allocation and calls there, so that statement keeps the store.  A float element is stored through `Expr.toBits`, which compiles to `i64.reinterpret_f64`.  The proof takes 68 lines plus a 20-line lemma for the row loop's body.  The user chose this design (option A) on 2026-09-30.

`layerNorm_implements` proves `layerNorm xs g b eps`: the mean and the variance by two loops, `1.0 / (var + eps).sqrt`, and a new array whose element `i` is `(xs[i]! - mean) * inv * g[i]! + b[i]!`, bit for bit.  It needed no new rule: two applications of `Stmt.loop_spec`, straight-line runs for the float assignments, and `Stmt.build_spec`.  The proof takes 190 lines plus 30 for the two loop bodies, most of them spent carrying local values from one step to the next.

`exp_implements` proves that the compiled `exp` computes the Lean definition `exp` bit for bit, the user's option A of 2026-09-30.  `exp` reduces `x` to `k·ln 2 + r` with a two-part `ln 2`, evaluates the Taylor polynomial of degree 13 for `e^r`, and multiplies by `2^k` as a product of two powers of two built from their bits with `Float.ofBits`.  It returns `x` for NaN, infinity above 709.8, and 0 below -745.2.  `Float.ofBits` compiles to `f64.reinterpret_i64`, which keeps a NaN payload while Lean's model does not, so the proof shows that `v <<< 52` is never a NaN pattern (`F64Bits.shiftLeft_52_not_nan`).  The proof takes 113 lines, going assignment by assignment and unfolding one local's definition at each step, so that terms do not grow.  No theorem bounds the error against the true exponential.  Against the C library's `exp` in native Lean, the error is at most 1 unit in the last place on 400,000 points from -745 to 710 (90 percent exact), and the special values match exactly.

`softmax_implements` proves `softmax xs`, which takes the maximum by a loop, sums `exp (xs[i] - max)` by a second loop, and builds the array of each exponential divided by the sum, bit for bit.  It calls `exp` in its sum loop and in each element, which the user's option A of 2026-09-30 allows.  A second predicate, `ImplementsPure`, states that a function of scalars returns `f x` and keeps the store, for every store.  `Func.implementsPure` proves it for a compiled function whose body keeps the store, `ImplementsPure.implements` derives `Implements`, and `Stmt.callPure_spec` proves a call that keeps the store.  Call arguments became typed expressions, so a call can pass a float; the emitted instructions did not change.  The compiler allows calls in loop bodies and array elements when every argument and result is a scalar.  The proof takes 157 lines, plus 30 for the sum loop's body with its call and 14 for the maximum loop's body.

`matVec2_implements` proves `matVec2 w1 w2 x hidden d = matVec w2 (matVec w1 x hidden d) d hidden`, in which the intermediate vector is a temporary array: a `let` at the top of the body binds it, the second call borrows it, and the compiler releases it at the end of the function, the user's choices of 2026-09-30.  Releasing it requires that every array still live lies apart from it, so `Implements` gained a freshness clause: every object the result owns lies apart from each array borrowed or owned before the call, stated through a new `Represent` method, `outside`.  The keep clause for owned arrays now also keeps their capacity, since an owned array's block is measured with it.  Each existing proof supplied these facts from `Heap.NewArray`, with `Heap.NewArray.two` for two allocations in a row.  The proof of `matVec2` takes 132 lines.

`matMul_implements` proves `matMul a b n k m`, the product of an `n × k` and a `k × m` matrix stored by rows, bit for bit.  Each element is a loop over the shared dimension, with read positions that use unsigned division and remainder by `m`; the proof splits on `m = 0`, where the IR's operations test for a zero divisor and Lean's define that case directly.  The proof follows `matVec`'s and takes 72 lines.

The MLP of a transformer block is proved in pieces.  `add` (element-wise sum, 54 lines) and `geluArray` (62 lines) are kernels built with the copying template.  `tanh z = 1 - 2 / (e^(2z) + 1)` (21 lines) and GPT-2's `gelu` (31 lines) are functions that keep the store, proved with `Func.implementsPure`, so `geluArray`'s elements may call `gelu`, which calls `tanh`, which calls `exp`.  `mlp x w1 w2 t d f = matMul (geluArray (matMul x w1 t d f)) w2 t f d` is a composite with two temporaries; `Live` proves it in 104 lines.

Row-wise layer norm normalizes each of the `t` rows of a `t × d` matrix stored by rows.  Computing a row's mean and deviation inside each element would repeat both loops for every element of the row, so two kernels compute them once per row: `rowMeans` (73 lines, plus 24 for its loop body) and `rowInvStd` (84 lines, plus 30), each a build whose element runs a loop over the row, as in `matMul`.  `normalizeRows` (60 lines) builds each element from five reads at positions `e`, `e / d`, and `e % d`, and splits on `d = 0` as `matMul` does.  `layerNormRows x g b t d eps` calls the three kernels in turn and holds the means and the inverse deviations as temporaries; `Live` proves it in 126 lines.

Masked attention follows the same plan, with `nh` heads of width `dh` on rows of width `d = nh · dh`, as GPT-2 splits them.  `maskedScores q k t nh dh scale` builds `t` rows of `nh` blocks of `t` scores: element `(i, h, j)` is `scale · (q[i] · k[j])` over the columns of head `h` where `j ≤ i`; a masked element's loop runs zero times, so its score is `0 · scale` plus negative infinity and it reads no key (108 lines, plus 20 for its loop body).  Storing the scores by position first keeps rows `0` to `i` a prefix of every array.  The compiler rejects a loop inside a branch, so the mask is added to the score rather than selected.  Row-wise softmax consists of `rowMax` (71 lines, plus 15), `rowSumExp` (69 lines, plus 32), whose loop calls `exp`, and `softmaxApply` (67 lines), joined by the composite `softmaxRows` (113 lines).  `causalMatMul p v t nh dh` multiplies each head's weights by that head's columns of the values, with row `i` summing over rows `0` to `i` of `v` only (87 lines, plus 20).  `attention x wq wk wv wo t nh dh` computes `q`, `k`, and `v` with `matMul`, the masked scores with `scale = 1 / √dh`, the softmax of each of the `t · nh` rows of scores, the product with `v` by `causalMatMul`, and the product of that with `wo`.  It holds six temporaries, and `Live` proves it.  With `nh = 1` every function returns the same bits as the single-head version for all 484 earlier test inputs.

The first version read every key and used `matMul` for the product with `v`, and a later row could change an earlier one: row 0 of `attention` on `[1e150]` was `1e150`, and on `[1e150, 1e200]` it was NaN, because the masked score `1e150 · 1e200` overflowed and `+∞ - ∞` is NaN.  An infinite value in a later row also reached earlier rows through `0 · ∞` in the product with `v`.  `Project/Gpt/Causal.lean` proves `attention_rows` and `block_rows`: when two inputs agree on rows `0` to `i`, so do the outputs, for `t`, `nh`, and `dh` below `2 ^ 16` and `f` below `2 ^ 32`, which exclude overflow in the `UInt64` index arithmetic.  The two inputs may have different numbers of rows `t` and `t'`, both above `i`.  The theorems concern the Lean definitions, and `Implements` carries them to the bytes.

`forward` is the forward pass of GPT-2 with `layers` blocks: `embed` adds row `tokens[i]` of the token embeddings to row `i` of the position embeddings (49 lines), a loop over the layers applies the blocks, then a final layer norm, and `matMulT` scores each position against every token embedding, a product with the transposed embedding matrix (74 lines, plus 20).  The sixteen weight arrays of the blocks stack the layers one after another.  `linear`, `normalizeRows`, and the functions that call them take a layer index `l` and read layer `l` at an offset: `w[l · k · m + …]` for a `k × m` matrix and `b[l · m + …]` for its bias.  The loop is `LeanExe.loop layers x0 fun l x => block x … l …`, which the compiler translates to `Stmt.arrayLoop`: a copy of `x0` into the loop's state, then one call of `block` per layer, each followed by the release of the previous state.  `Live.arrayLoop` proves the statement, and `Live` proves `forward`, which takes 28 arguments and holds three temporaries.  `forward_prefix` proves that row `i` of the scores depends only on tokens `0` to `i`, whatever the number of tokens, under the same bounds with `vocab` added, by induction over the layers; `layers_rows` states the same for the input of every layer, and `forward_causal` is the case of equal numbers of tokens, for any `i`.

`steps_exact` states that `step` run on tokens `0` to `p` from an empty cache, followed by `scores`, equals row `p` of `forward` on any `T > p` tokens, as `Array Float`: the same floating-point values bit for bit.  The hypotheses bound the dimensions so that no `UInt64` index wraps: `T`, `nh`, `dh`, and `layers` below `2 ^ 16`, `f` and `vocab` below `2 ^ 32`, `nh` and `dh` positive, and the whole cache, `T · (2 · layers + 1) · nh · dh` values, below `2 ^ 32`.  The proof uses an invariant on the cache: block `j` holds row `j` of the last layer's input and rows `j` of each layer's keys and values, as `forward` on all `T` tokens computes them.  Each kernel that `layerStep` runs on one row is shown to compute the corresponding row of `block`'s kernel, and the attention kernels `stepScores`, `stepSoftmax`, and `stepMix` to compute row `p` of `maskedScores`, `softmaxRows`, and `causalMatMul` from the cached keys and values; induction over the layers and then over the positions gives the theorem.  With `step_implements` and `scores_implements`, the compiled cached generation computes `forward`'s rows exactly.

`block x g1 b1 wq wk wv wo g2 b2 w1 w2 t nh dh f eps` is one transformer block in the form of GPT-2's: `r = x + attention (layerNormRows x g1 b1)`, then `r + mlp (layerNormRows r g2 b2)`.  Its four linear layers use `linear x w b n k m`, the product `x · w` plus the bias `b` in each column, summed before the bias is added, as in GPT-2's `conv1d`.  It calls the composites proved above and `add`, holds five temporaries, and `Live` proves it.

`Project/Gpt/SampleVerify.lean` proves the sampler.  `negInfs` is a build (28 lines), `insertTop` a build whose position comes from a loop counting the buffer entries not below the new score (125 lines), and `sampleFrom` a function that keeps the store (218 lines, plus 71 for the body of its second loop): one loop sums the weights of the kept scores, and the other chooses the token, with calls of `exp`, `splitMix`, and `unitFloat`, whose theorems `splitMix_pure` and `unitFloat_pure` hold in any module that contains them.  `topKBuffer` is an array-state loop of `insertTop` calls that starts from `negInfs k` (111 lines), and `sampleTopK` calls `topKBuffer`, passes the buffer to `sampleFrom`, and releases it (124 lines).  Two `Live` rules were added for `sampleTopK`: `Live.callScalar_seq`, for a call that returns scalars and keeps the temporaries live, and `Live.releaseFirst`, for the release of the newest temporary.

`scale_bytes`, `gcd_bytes`, `sumArray_bytes`, `pairSum_bytes`, `sumCount_bytes`, `axpy_bytes`, `scaledHypot_bytes`, `piecewise_bytes`, `sumSquares_bytes`, `mean_bytes`, `bucket_bytes`, `clob_bytes`, `gpt_bytes`, and `prng_bytes` combine these with `round_trip`: `encode` succeeds on the module, and the decoder reads the bytes back as a module that implements the function, or all five functions for `clob_bytes`.  The kernel checks that encoding succeeds by evaluating the encoder (`decide +kernel`), in about half a second per module.  All of these theorems, the rule lemmas, the runtime specifications, and `decode_encode` depend only on `propext`, `Classical.choice`, and `Quot.sound`.  An audit found that CodeLib's `Mem.read64_write64_same`, a `simp` lemma proved with `bv_decide`, had added an axiom for compiled code to `pairSum_bytes`.  The proofs now use ProofKit's kernel-checked `Memory.read64_write64` and remove CodeLib's lemma from the `simp` set in `RuntimeSpec.lean`.

`alloc` and `release` follow Knuth's first fit and liberation with a sorted list (TAOCP vol. 1, §2.5, Algorithms A and B).  `alloc` takes the first free block that fits; when at least 56 bytes would remain, it lowers the block's size word and places the object at the block's upper end, so the free block keeps its place and link.  `release` walks the free list, which is in address order, to the first block above the freed one, then merges the freed block with that block and with the block before it when their regions touch.  `FixedArrayReuse.program_spec` proves the split, `findPlace_spec` the walk, `joinProgram_spec` one merge, and `freeObject_spec` the whole return of a block.  `Heap.At`, `FreeListAt`, `Heap.Owned`, `Heap.Borrowed`, and `Heap.Room` keep their definitions: safety does not depend on the order of the list, and a merged block's region is the union of two free regions.  `FreeListAt.release` proves that the list stays laid out, `insertFree_cover` that every new block starts and ends where an old block or the freed block does, and `insertFree_apart` that a region apart from the freed block and every free block stays apart from every new block.  `Heap.Borrowed.release` and `Heap.Owned.release` now take `Heap.At`, because `release` writes the header of the free block below the freed one.  The proofs bound `top` within one call; memory across a session is tested.

## Floating point

Lean 4.34 defines `Float` and `Float32` through `Float.Model` and `Float32.Model`, IEEE binary64 and binary32 with round-to-nearest, ties to even.  Every NaN in both models is the positive quiet NaN with only the top fraction bit set, `0x7FF8000000000000` or `0x7FC00000`, and `ofBits` converts every NaN input to it.  Talos's `IEEE64` and `IEEE32` return the same constants for every NaN result.

ProofKit proves `LeanExe.Float32.xBits = Wasm.IEEE32.x` for `add`, `sub`, `mul`, `div`, and `sqrt`, for all inputs including NaN, in 25 files and 2,101 lines.  The binary64 counterparts for all five operations are 21 files in `F64*.lean`, plus `F64Bits`, 1,831 lines in all, translated from the binary32 files with a script that maps the format constants.  Lemmas that do not depend on the format moved to `FloatRounding`, `FloatShift`, `FloatRationalRounding`, `FloatSqrtRounding`, and `FloatCommon`, which both chains import.  One lemma is new: `IEEE64.roundDyadicMagnitude` and `roundRationalMagnitude` pass `rounded * 2^shift` to `roundScaledMagnitude` where the binary32 rounders encode the fields directly, and `roundScaled_mul_pow` bridges the two forms.  `F64Bits` restates the results as `(a + b).toBits = IEEE64.add a.toBits b.toBits` for Lean floats.  The wrappers are thin: `LeanExe.Float32.addBits` applies Lean's `Float32` addition to decoded bits, so the theorems also justify compiling Lean's float types directly.

Lean and WASM differ in three places:
1. Lean's `neg` and `abs` return the positive canonical NaN for a NaN input.  WASM `fneg` and `fabs` change only the sign bit.
2. Lean's `ofBits` canonicalizes NaN.  WASM `reinterpret` keeps the payload.
3. Lean's `min` and `max` choose an operand by `≤`.  WASM `fmin` and `fmax` return NaN for a NaN operand and order `-0` below `+0`.

The WebAssembly specification ([numerics](https://webassembly.github.io/spec/core/exec/numerics.html)) makes the sign of a generated NaN nondeterministic and its payload canonical only when every NaN input is canonical.  Its deterministic profile ([profiles](https://webassembly.github.io/spec/core/appendix/profiles.html)) requires that "All NaN values generated by floating-point instructions are canonical and positive," and Talos implements that behavior.  `tools/wasmtime-host.c` enables Cranelift's NaN canonicalization.  Browsers do not implement the profile, and on x86 `0/0` produces a negative NaN.  On this aarch64 machine, native Lean's `toBits` returned `0x7FF8000000000000` for a NaN with a payload, for `0/0`, and for `-(0/0)`.  Modeling the full profile in Talos, with an oracle choosing NaN results and the compiler canonicalizing NaN where bits become observable, remains the route if theorems must cover results computed in a browser.

`IEEE64` has the same functions as `IEEE32` and calls `IEEE32.roundShift`, `roundQuotient`, and `roundSqrtIntegral` directly, so lemmas about those helpers are imported, not copied.  The binary32 chain states its format constants about 270 times, and proofs with the larger binary64 constants may behave differently under `decide`, `omega`, and `simp`.  The binary64 translation needed no changes for `decide`, `omega`, or `simp` behavior with the larger constants.  Binary64 comparisons rest on a new lemma, `F64Compare.compare_canonical`, since the binary32 chain has no comparisons.  Decoding a non-NaN bit pattern gives a canonical unpacked float whose value is Talos's `scaledValue`, and Lean's comparison of canonical floats orders them by value.  Negation compiles to `-0.0 - x` (`F64Sign.sub_negZero`), absolute value to `f64.abs`, and `min` and `max` to a comparison and a conditional, which removes the three differences listed above.  Conversions have no theorems yet, and binary32 has no comparison or sign theorems.

## Scope of the theorem

1. The claim is about Talos's semantics.  Wasmtime appears only in tests, and the Talos interpreter and the decoder are trusted.
2. The premises `Heap.At` and `Heap.Borrowed`, and a memory cap of at most 65,535 pages, are assumed; every compiled module declares that maximum.  No theorem covers instantiation or the host.  A call may trap at `unreachable` when memory cannot grow or an array would exceed 32-bit memory, and the theorems state the result of every call that does not trap; a module that always traps would satisfy them.  Talos's `memory.grow` succeeds whenever the new page count is within the maximum, while the WebAssembly specification lets an engine refuse growth for its own reasons.  `alloc` checks the result of `memory.grow` and executes `unreachable` on failure (`MemoryGrowth.growProgram`), so on such an engine the call traps and returns no result, a path the theorems do not describe.
3. `Implements` protects only the arguments and the allocator invariant.  It states nothing about other live objects.  Decision 7 (2026-09-29) adds a frame clause for borrowed and owned arrays, which calls between compiled functions need, and later decisions add that the memory's maximum size is unchanged and that a result's objects are fresh.
4. `Emit.lean` evaluates `encode` with compiled Lean code.  For `gpt.wasm`, `gpt_file` in `Project/Gpt/File.lean`, checked after the file is written, proves that the file holds `encode gpt.module`; the elaborator `binary_file%` that reads the file is trusted.  No theorem covers the other modules' files.
5. Until 2026-09-29, each `_bytes` theorem assumed `encode m = .ok bytes` and held vacuously if encoding failed, as `piecewise_bytes` did until the encoder gained the float comparison and constant instructions.  Each now proves that encoding succeeds.

The user doubted that items 2 and 3 need work, and no work on them is planned.
