# Repository tools

## Lean execution and emission

[The Lean runner](leanrun) selects the pinned toolchain, takes the machine-wide lock, and
applies the resource and timeout settings described in
[the development procedure](../docs/leanexe-manual.md#development-practice).  Repository drivers
invoke it themselves.  [The remote runner](leanrun-dev) supports source synchronization and
checks on the development host.  The runner's resource controls and the rules for local mode
are stated in [the repository instructions](../AGENTS.md#lean-process-limits).

[The WebAssembly emitter](Emit.lean) takes a Lean module name, a module constant, and an output
path.  It imports the compiled module through Lake's search path, evaluates the constant,
encodes it, checks that the decoder reads the bytes back as
the same module, and writes the file.  [The WGSL emitter](EmitWgsl.lean) prints a kernel and
checks that the parser reads it back.  The
[compilation procedure](../docs/verified-manual.md#emitting-and-running) gives the build and
emission commands.  A file theorem identifies the bytes of a particular emitted file.

[The specification checker](demo-check) implements the acceptance procedure for an example
made from an English request: specification hashes, its bytes theorem, theorem axioms,
and samples executed in Wasmtime.  Its `--freeze` mode records specification hashes.
[The verified-executable procedure](../docs/leanexe-manual.md#from-an-english-request) explains
when that record is made and how the subsequent check uses it.

## Execution hosts

[The Wasmtime download](download-wasmtime.sh) obtains the pinned C API, and
[the host build](build-wasmtime-host.sh) builds the host from [its C source](wasmtime-host.c).
The host calls exports, handles persistent sessions and allocation counters, and runs WASI
commands.  [The host manual](../docs/leanexe-manual.md#the-wasmtime-host) defines its argument
and result formats.  [The WASI manual](../docs/wasi.md#wasmtime-host) defines stream and exit
behavior.

[The WebGPU download](download-wgpu-native.sh) and [build](build-webgpu-host.sh) prepare
[the kernel host](webgpu-host.c).  [The WGSL tests](../tests/README.md#selecting-tests) compare
its output on SwiftShader and llvmpipe with native Lean.

[The native host](native-host.c) and [its API](native-host.h) call the C functions generated by
`native-verified`.  That executable is defined under
[native test support](../tests/TestSupport/Native/Verified.lean).  Its build command prints C,
compares `clightgen`'s result with the translation, and invokes CompCert.  The
[translator design](../docs/native-translator.md) states the theorem and host assumptions.
[The bare-metal build](baremetal/build.sh) adds startup and reporting code, links the image,
and checks its stack bound and instructions.  [The bare-metal design](../docs/native-bare-metal.md)
explains that procedure and the QEMU execution tests.

## Numerical generators and application tools

Python programs use `uv run PATH` with the dependencies declared in their script headers.
[The decimal generators](strconv) compute parser and printer cases with exact rationals,
as [Test inputs](../data/README.md#decimal-conversion) describes.
[The arcsine analysis tools](arc/asin) and [Bessel tools](bessel) choose constants and bounds
used in generated Lean proofs.  The [arcsine guide](../Library/Numerics/Float64/Asin/README.md#proof)
and [Bessel guide](../Library/Numerics/Float64/Bessel/README.md#proof)
identify their outputs and how the kernel checks them.

[The Euler runner](euler-run.py) and [GPT tool](gpt2.py) perform application I/O around compiled
calls.  The [Euler](../Demos/Euler/README.md) and [GPT](../Demos/Gpt/README.md) documents give
their input formats and reproduction commands, with the theorem premises for compiled calls.

## Repository checks

[The documentation checker](check-doc-links.mjs) follows relative links from the root README
through the Markdown documents and READMEs and reports missing paths, missing anchors, and
documents that no link path reaches.  [The source-layout checker](source-layout) checks that
internal imports name existing modules and form no cycle, that compiler modules import no
library, application, example, or test modules, and that library modules import no examples,
demos, or test support.  It also checks that `Library.Native` imports each library program,
that no program reaches the compilers through its imports, and that each module registry
entry names an existing module.  [The documentation tests](../tests/README.md#documentation-tests)
give the checker's commands.
