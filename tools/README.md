# Repository tools

## Lean execution and emission

[The Lean runner](leanrun) selects the pinned toolchain, takes the machine-wide lock, and
applies the resource and timeout settings described in
[the development procedure](../docs/verified-manual.md#development-practice).  Repository drivers
invoke it themselves.  [The remote runner](leanrun-dev) supports source synchronization and
checks on the development host.  The runner's resource controls and the rules for local mode
are stated in [the repository instructions](../AGENTS.md#lean-process-limits).

[The WebAssembly emitter](Emit.lean) takes a Lean module name, a module constant, and an output
path.  It imports the compiled module through Lake's search path, evaluates the constant,
encodes it, checks that the decoder reads the bytes back as
the same module, and writes the file.  [The WGSL emitter](EmitWgsl.lean) prints a kernel and
checks that the parser reads it back.  The
[compilation procedure](../docs/verified-manual.md#emitting-and-running) gives the build and
emission commands.  A file theorem identifies the bytes of a particular emitted file.

## Execution hosts

[The Wasmtime download](download-wasmtime.sh) obtains the pinned C API, and
[the host build](build-wasmtime-host.sh) builds the host from [its C source](wasmtime-host.c).
The host calls exports, handles persistent sessions and allocation counters, and runs WASI
commands.  [The host manual](../docs/verified-manual.md#the-wasmtime-host) defines its argument
and result formats.  [The WASI manual](../docs/wasi.md#wasmtime-host) defines stream and exit
behavior.  [The WebGPU download](download-wgpu-native.sh) and [build](build-webgpu-host.sh)
prepare [the kernel host](webgpu-host.c).  [The WGSL tests](../tests/README.md#selecting-tests)
compare its output on SwiftShader and llvmpipe with native Lean.  [The CUDA host
build](build-cuda-host.sh) builds [the PTX kernel host](cuda-host.c) against the CUDA driver API,
and [the PTX tests](../tests/ptx/run.sh) compare its output on an NVIDIA GPU with native Lean.  Its
session mode reads the commands of the WebGPU host's session, with `kernel NAME PATH` in place of
`shader`, and queues its copies, memsets, and launches on one stream.  For `run`, its answer `ok`
means that the launch is queued, and an error of the launch ends the process at the next command
that synchronizes the stream.  The comment at the start of [`cuda-host.c`](cuda-host.c) defines
the commands.

[The native host](native-host.c) and [its API](native-host.h) call the C functions generated by
`native-verified`.  That executable is defined under
[native test support](../tests/TestSupport/Native/Verified.lean).  Its build command prints C,
compares `clightgen`'s result with the translation, and invokes CompCert.  The
[translator design](../docs/native-translator.md) states the theorem and host assumptions.
[The bare-metal build](baremetal/build.sh) adds startup and reporting code, links the image,
and checks its stack bound and instructions.  [The bare-metal design](../docs/native-bare-metal.md)
explains that procedure and the QEMU execution tests.

## Numerical generators and application tools

Python programs use `uv run PATH` with the dependencies declared in their script headers.
[The decimal generators](strconv) compute parser and printer cases with exact rationals,
as [Test inputs](../data/README.md#decimal-conversion) describes.
[The arcsine analysis tools](arc/asin) and [Bessel tools](bessel) choose constants and bounds
used in generated Lean proofs.  The [arcsine guide](../Library/Numerics/Float64/Asin/README.md#proof)
and [Bessel guide](../Library/Numerics/Float64/Bessel/README.md#proof)
identify their outputs and how the kernel checks them.  [The Euler runner](euler-run.py) and
[GPT tool](gpt2.py) perform application I/O around compiled calls.  The
[Euler](../Demos/Euler/README.md) and [GPT](../Demos/Gpt/README.md) documents give their input
formats and reproduction commands, with the theorem premises for compiled calls.

## Sail translation

[The Sail scripts](sail/README.md) translate the floating-point functions of the Armv9.4-A Sail
model into Lean with Sail's Lean back end, elaborate the output with Lean v4.29.0 and with the
repository's toolchain, test it with exact rationals and with Sail's C emulator against Talos's
binary64 functions, and prove that the translated FPAdd and FPMul at 64 bits compute Talos's
`f64Add` and `f64Mul`.  Their README gives the versions, the sources, the edits that the output
needs before it elaborates, the state hypothesis, the tests, the proofs' measures, the join with
the Isla equations, the check that regenerates the translation, what the proofs trust, and the
commands.  The A64 model and its proofs do not use them.

## Repository checks

[The documentation checker](check-doc-links.mjs) follows relative links from the root README
through the Markdown documents and READMEs and reports missing paths, missing anchors, and
documents that no link path reaches.  [The source-layout checker](source-layout) checks that
internal imports name existing modules and form no cycle, that the modules of `LeanExe`, and of
`Verified` outside `Verified/Examples`, import no library, application, example, or test
modules, and that library modules import no examples, demos, or test support.  It also checks
that `Library.Native` imports each library program, that no library program reaches `Verified`
through its imports, and that each module registry entry names an existing module.
[The documentation tests](../tests/README.md#documentation-tests) give the commands of the
documentation checker and its tests.

[The request checker](verified-request-check) checks an example that [the verified-request
skill](../.claude/skills/verified-request/SKILL.md) makes from an English request.  Its `--spec`
mode prints each sample with the specification's output, `--freeze` records the hashes of the
reviewed `Spec.lean` and `Samples.lean`, and `--run` emits the module and runs the samples in
Wasmtime.  Without a mode, it checks the hashes, requires the example's call theorem to prove the
`Verified.CallSpec` statement that the checker writes, with no axioms beyond `propext`,
`Classical.choice`, and `Quot.sound`, and runs the samples in Wasmtime and, when CompCert's `ccomp`
and `clightgen` are present, in the module's translation to C.

[The full check](full-check) builds every module of the libraries `LeanExe`, `Verified`,
`Library`, `Demos`, `Examples`, and `TestSupport` and the test executables, runs the drivers of
the verified compiler's modules and of their C, bare-metal, WASI, and WGSL forms, checks the VKB
and the Rocq composition, and runs Talos's conformance driver.  It writes
[the status record](../STATUS.md), which names the checked commit and gives each step's status,
duration, and counts.  [The verified compiler manual](../docs/verified-manual.md#the-full-check)
describes its steps, its variables, and the steps that run only where their tools are present.
