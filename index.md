# Algorithms, I/O, and applications

This index lists, for each library algorithm, WASI operation, application, and compiler example, its compiled forms, its implementation, its behavior, and the theorems that state its claims.  Sections 1 to 13 hold the reusable algorithms of [the library](Library/README.md), grouped by subject, section 14 the WASI actions of `LeanExe.Wasi`, section 15 [the application demos](Demos/README.md), and section 16 the compiler examples of `Examples` and `Verified/Examples`, one row for each example.  A function defined in an application or an example appears in the row of that application or example, so the subject sections list only code that other programs import.  [The aggregate of the library's Lean definitions](Library/Native.lean) imports the reusable implementations, and [the verified compiler manual](docs/verified-manual.md) describes the dialect.

An execution theorem states that a module computes a Lean definition: `p.f.implements`, which `verified_compile p := [… f …]` generates for each function `f`.  Most library modules name the program `compiled`, so their rows cite theorems such as `compiled.sha256.implements`.  A bytes theorem, `p.bytes` or a theorem named `NAME_bytes`, states that the module's encoding decodes to a module whose exports satisfy the execution theorems.  A specification theorem states a further property of the definition or of the module, such as an accuracy bound or equality with a transcription of a standard, and one named `NAME_call` or `NAME_callSpec` states it for one export called from a store that meets its premises.  A store has room for `n` bytes when the allocator's `top` can rise by `n` bytes within the memory cap, as `heap.Within` states, and the generated bound `p.f.bound` bounds that rise for a call of `f`.  A file theorem pair, `NAME_file` and `NAME_file_decode`, states that a file under `build/` holds the module's encoding and decodes to the module, and [the file-theorem registry](tests/verified/numerics.txt) names the Lean file that declares the pair.  The rows give the file theorems, the native theorem `p.f.native`, and the aligned native theorem `p.f.nativeAligned` by their codes alone.

Execution theorems use Talos's semantics of WebAssembly with the deterministic floating-point profile.  They assume the allocator invariant and, for some functions, borrowed tables, static byte data, and bounds on memory and recursion depth.  WASI theorems also assume a host that satisfies the modeled host assumptions.  An execution theorem can permit a trap at `unreachable`, and the generated trap-free theorem `p.f.trapFree` proves a return under its allocation and depth conditions.  Each linked guide states its domains, exceptional inputs, and host assumptions.

The Forms column lists a row's codes in the order of the key below.  Codes that another module contributes, where an application, an example, or another library module compiles the same definition among other functions, follow that module's name in parentheses, as in `V F C (gpt32: A G)`.  The name is a module name of [the module registry](tests/verified/modules.txt), except `RunningSumFp`, which names the WASI module of the floating-point running sum of section 15.  The names `lists`, `updates`, and `grids` belong to fixtures of the verified compiler, so the modules of the examples `Lists`, `Updates`, and `Grids` are `exampleLists`, `exampleUpdates`, and `exampleGrids`, and the module of `Trees` takes the same form, `exampleTrees`.  A dash marks an entry that has none of the forms.  The Implementation column links the guide that documents the entry, a `README.md` beside the code or in its family's directory, or the Lean file that defines the entry where no guide documents it.  The last column names each theorem that states a claim and links the file that declares it, in the order of the codes: the execution theorem, the specification theorems, each with its claim and then its premises or limits, and the call theorem.  The README's [artifact section](README.md#artifacts) gives, for each code other than S, the tool that writes the artifact, the semantics of its theorem, and where it runs.

## 1. Arithmetic

[The limb representation](Library/Numerics/Arithmetic/Uscale/README.md) stores natural numbers in little-endian arrays of 32-bit limbs held in `UInt64` words.  `val a` denotes the represented natural number, and `Limbs a` requires every element to be below `2^32`.  The limb theorems assume that property and their stated array-size, shift, and quotient bounds.  The decimal parsers and printers of section 9 compile the limb routines in their own modules, the multiple-precision module compiles `mulSmall` and `wordBits`, and the complementary error function, gamma, and log-gamma modules compile the fused multiply-add.  Each call theorem of the section composes the generated `p.f.trapFree`, or `p.f.pure` for `gcd_call` and `primeFactors_call`, with the row's equality theorem.

## 2. Arrays, lists, trees, and sorting

These algorithms use `UInt64` words, counts, and indices, with arithmetic modulo `2^64`.  Their modules belong to [the module registry](tests/verified/modules.txt), whose modules the native drivers translate and run, and the examples of section 16 compile several of them again with cases of their own.  [The array guide](Library/Arrays/README.md) states the common array conventions, and the insertion-sort module also proves the theorems of the translation without the alignment test.

## 4. Reductions

A reduction combines the elements of an array into one value in a fixed order.  The word reductions are `Array.foldl` folds, and the binary64 reductions are `LeanExe.loop` loops over the indices, except `sumRange`, which halves its range recursively.  The verified compiler compiles both families into modules of [the module registry](tests/verified/modules.txt), and examples of section 16 compile several of the functions again.

### 4.1. Word reductions

Word reductions use `UInt64` arithmetic modulo `2^64` and start from zero, one, and zero.  `sumArray`, `productArray`, and `xorArray` fold addition, multiplication, and exclusive or from left to right.  [The folds example](Examples/SumArray/README.md) also compiles `sumArray` in a module of its own and the other two in the module `folds`.

## 11. Hash functions

[The hashing guide](Library/Hashing/README.md) describes the arguments: a message of `n` bytes is an `Array UInt64` with eight bytes per word in little-endian order.  A digest of SHA-2, HMAC, or a SHA-3 hash function is a structure of words in the same packing, a SHAKE output is an array of words, and a CRC, SipHash, or XXH64 result is one word.  Each specification theorem `NAME_call` states that the export, called from a ready store with borrowed arrays, returns without a trap the result of its family's transcription for the message's bytes, and that the caller's heap keeps its bytes.  Each row states the limits on the lengths.  The verified compiler's allocation bound, `bound_eq`, is zero for every export except SHAKE, whose bound is its output array.

The SHA-2 specification is a literate transcription of FIPS 180-4, copied with its implementation and equivalence proofs from fips-180-4-lean, and the HMAC specification transcribes FIPS 198-1 over it.  The SHA-2 and HMAC specification theorems read message, key, and digest bytes most significant bit first, as FIPS 180-4 does.  [The Merkle–Damgård module](Library/Hashing/MerkleDamgard.lean) proves that two distinct messages with equal SHA-256 or SHA-512 digests give a collision of the compression function of FIPS 180-4.  The SHA-3 specification transcribes FIPS 202 and agrees with every CAVP vector, and its specification theorems read message and digest bytes least significant bit first, as FIPS 202 does.  The CRC specification transcribes ITU-T V.42 and RFC 3720 with Mathlib's polynomials over GF(2), and its result is the CRC as zlib and the Linux kernel report it.  The SipHash and XXH64 specifications transcribe the SipHash paper and the xxHash specification on 64-bit words.  Independent reviews compared the SHA-3, CRC, SipHash, and XXH64 transcriptions with their sources.

## 16. Compiler examples

Compiler examples demonstrate language forms, ownership, and proof procedures, with one row for each example, whose functions the row summarizes.  Execution theorems relate compiled programs to their Lean definitions under the verified compiler's premises, word arithmetic wraps modulo `2^64`, and the WGSL dispatch results assume the device model's shape, buffer, and invocation bounds.  [The verified compiler manual](docs/verified-manual.md#examples) describes the examples in more detail.
