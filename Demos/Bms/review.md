# BMS protection requirements: decisions and review

[The requirements](requirements.md) specify the first iteration of the BMS protection demo from the design document `bms-tagged-uart-design.md`, with the simplifications and answers to its open questions that the user agreed to.  This record gives each decision with its reason, the resolution of each gap that a check of the design against the repository found, and the findings of a fresh agent's review with the verification and response for each.  The decisions that change what a theorem assumes or what is trusted went through the standard procedure: a recommendation here, the review, and a revision.

## Decisions agreed with the user

| Decision | Choice | Reason |
|---|---|---|
| Records | One scan record per scan, carrying every field, with the tag kept as a format identifier | Tags per source are not a goal.  One record per scan removes the scan's position, order, and clean flag from the machine, so every check is a check of one record and the answer to it |
| Answers | One answer per record, in lockstep | No byte arrives while the window after a delimiter runs or while the answer is sent, the condition under which the earlier board runs passed |
| Pack | 4 cells as `u16` mV, 2 temperature sensors as `i16` tenths of a degree, pack current `i32` mA, pack and bus voltage `u32` mV | The record has 35 raw bytes, 37 on the wire, and an exchange takes 116.667 ms at 4,800 baud |
| Supervisor | Bit 5 of the digital word, `RUN` | No supervisor record or counter |
| Decoding | COBS decoding, the CRCs, the machine, and the answer's encoding in the window after the delimiter; polling windows only store bytes | The polling windows stay short, and lockstep lets the long window run while no byte arrives |
| CRC | Bitwise CRC-32, no area | No linear memory and no area setup.  Eight steps a byte over the record's 31 bytes and the answer's 13 run in the long window |
| Simulator | A simple pack simulator | Enough to drive every scenario of the schedule |
| Kept | Precharge, auxiliary-contact monitoring, the stop input, the restart interlock with a reset edge, the limits, the sensor ranges, the cell-sum check, the latched first-fault code, the bridge's leases, and theorems on QEMU's `mps2-an500` and the board | |
| Open questions | Communication faults latch, with a resynchronization rule; a standby request in `NORMAL` opens at once; the stop circuit is single-channel; no further warning levels | |

## Resolution of the gaps

| Gap | Resolution | Reason |
|---|---|---|
| 1. Sequence number and state after a communication fault | Every good record, one that passes the length, CRC, and tag checks, sets the expected number to its own plus one, even when it fails the sequence check.  A segment that fails decoding, length, CRC, or tag clears synchronization, and the next good record synchronizes without a sequence check.  The state goes to `FAULT` and stays there until a reset acceptance | Whether a record passes the sequence check depends only on the segment before it, so a fault never makes later records fail (M9), and M1 can state the sequence condition over the history alone.  Clearing synchronization after a sequence fault as well would leave the record after it unchecked and make the condition depend on two segments |
| 2. No answer within a stated time | BR4: after `T_ans` without a current answer, the bridge discards any partial answer, sends one `0x00`, and waits for a current answer or for `T_ans` of quiet after the `0x00`, then sends the next record | The `0x00` ends a segment whose delimiter was lost, so the board answers it, and the wait keeps any byte from arriving while the board sends that answer |
| 3. Main safety theorem | M1: a nonzero permit implies a last reset acceptance `i` and a last start `j`, every record from `i` on good, in sequence, passing every content check with the stop circuit closed, and, for `NORMAL`, the precharge condition between `j` and `n` | The statement names only the segments and the answers, so it does not restate the machine's code, and it implies the design's theorems on permits, stop, faults, and board resets |
| 4. Previous `RESET` bit after a board reset; hold time | `prevReset` starts at 1 and takes the `RESET` bit of each record that passes the communication checks.  A synchronizing record never accepts a reset.  The operator holds the button at least 500 ms after a release of at least 500 ms | A reset acceptance needs a good record before it, so a button held at boot forms no edge.  BR5 bounds the time between samples, at most 176.7 ms in normal operation with the estimated latency |
| 5. USART3 after an overrun | The image's initialization is the board's list plus a write of `0x00001000`, `OVRDIS`, to `USART_CR3` before the write of `USART_CR1` that sets `UE`.  Boot and the board theorems are being generalized over the list, and the existing images keep the shared list | Board tests found that with `OVRDIS` clear an overrun stops reception until a write of `ORECF` to `USART_ICR`, which a program confined to three registers cannot make.  With `OVRDIS` set, reception continues and the record checks report the lost bytes.  The decision followed the standard procedure on another task, and the requirements state its consequences: the trusted behavior of USART3, the read of `USART_CR3` after the initialization, and lost bytes counted from the answers since `ORE` stays 0 |
| 6. The virtual COM port | The port belongs to the black channel.  Of the device, only the effect of the accesses of the initialization and of `USART_ISR`, `USART_RDR`, and `USART_TDR` is trusted: they change nothing the model represents other than the trace | B1 and B5 hold for every sequence of values read, so no property of the bytes that reach USART3 enters a safety claim |
| 7. The state passes through every window | B3a bounds the polling windows, and the program phase measures them | At the gateway's 46 words of state its longest window while bytes may arrive took 2,374 cycles, a seventh of half a byte time |
| 8. CRC from a link constant | The CRC covers the link identifier `LeanExe-BMS-0001` followed by the record's bytes, computed as `zlib.crc32(raw, zlib.crc32(LINK))` | OPC 10000-15 section 5.3 requires a set of identifiers, the instance of IEC 61784-3's connection authentication, against masquerade and addressing errors.  An identifier inside the CRC rejects a record from another bridge, board, or protocol version at no cost in bytes or cycles, since only the CRC register's initial value changes.  The check remains a CRC-32 of a defined byte string, and zlib computes the vectors |
| 9. Diagnostics of a lost byte or delimiter | The table of [lost, inserted, and changed bytes](requirements.md#lost-inserted-and-changed-bytes), computed by `tests/baremetal/bms_proto.py faults` over every single-byte fault of the test vector with the bytes that BR3 and BR4 send next, and M12 | A lost byte gives `0x1001` or `0x1003`, never `0x1004`, because COBS decoding of `k` bytes gives at most `k − 1`.  A lost delimiter gives no fault, since BR4's `0x00` ends the segment |

## Further decisions

| Decision | Choice | Reason |
|---|---|---|
| Diagnostic codes | Renumbered so that the order of the codes is the order of the checks; sensor ranges before limits | A reading outside its sensor range, such as an open thermistor, reports a sensor fault and not a limit |
| Charging temperature | Charging, a current above `I_chg_detect`, is allowed from 0 to 45 °C, one code for both ends | The datasheet allows 1C only from 0 to 45 °C and gives no current from 45 to 55 °C, and the first iteration has no derating |
| Auxiliary-contact check | Each relay has an age, the records since its permit bit last changed, and a relay may disagree only while its age is below `D_edm` | A count of disagreeing records let NEG read open in the records after the change to `NORMAL`.  A single mask of the last change's bits took the tolerance from a relay that changed one record earlier (finding 11) |
| Ages after a board reset | 0, and segment 0 counts as a change of every relay | The bridge may hold relays closed from before the reset until the first answer, whose permit is 0, reaches it, and the contacts then get two exchanges to open |
| The state field `first` | True after a board reset and false after the first answer; the age rule sets every age to 0 when it holds | The rule that every relay gets age 0 at segment 0 needs the machine to recognize segment 0, and no other field identifies it: `answers` wraps at 2^32, and the other fields' values at segment 0 recur.  Without the field, a record that passes the communication checks at segment 0 would raise each age to 1, against the history definition of age that M1 uses.  `RESET_REQUIRED` with `synced` false holds only at segment 0, so a program may test that instead under an invariant, but the specification states the rule with the field |
| Reset acceptance | Requires `RUN` 0 | A reset never starts precharge by itself, so the supervisor's change of `RUN` from 0 to 1 is the start command |
| Bridge validity | An answer acts when it is current: authentic, answering the latest record sent, and the first such answer to that record.  The board sequence number serves the bridge's log alone | The answered sequence number rejects every answer to an earlier record, and the first-answer rule rejects a second answer to the latest one, so the board sequence number adds no protection.  A window over the board sequence number failed twice: one lost answer blocked it (finding 2), and a board reset whose first answer was lost blocked it for hours (follow-up finding 1) |
| Revocation | Any authentic answer with a relay's bit clear ends the relay's lease, and an answer that fails authentication does not | The board's `FAULT` answer to a damaged segment reaches the relays at once (finding 22), while a corrupted answer leaves the lease to bound the reaction.  A stale authentic answer can only release relays, after which BR6 applies |
| Lease | Expires `T_lease` after the sampling of the record that the answer answers | The board has no clock, and a lease counted from the sampling bounds the age of the data behind a permit, whatever the delay in either direction |
| Re-energization | BR6: at power-up, and after a lease ends other than through a current answer with the bit clear, no relay until a current answer with permit 0 | A rule that admits any answer to a record sampled after the release fails when NEG's contact still reads closed at that sampling (finding 3).  Waiting for permit 0 makes every later permit depend, by M1, on a start and a precharge sampled after the release, with no premise on relay timing.  A release that a current answer commands needs no latch, since the board's state then has permit 0 |
| Sampling | BR5: after the previous exchange and the answers that ended it, within `T_sample` of its end | A record then reports the relays as the last answer commanded them, and the bound on the time between samples supports the hold time and the lease margins (finding 9) |
| Answered number of a failed segment | `0xFFFFFFFF` when the segment does not decode to 35 bytes with a matching CRC | The field of such a segment is not authentic.  A coincidence with a real number gives an answer with permit 0 |
| Timing values | `T_ans` 100 ms, `T_lease` 500 ms, `T_sample` 20 ms, `T_act` 20 ms | `T_ans` covers the answer's 39.6 ms, the long window, and latency.  `T_lease` survives a lost delimiter, with 64.6 ms of margin under the estimated latency, and expires after a lost answer, as [the bridge's requirements](requirements.md#the-bridges-requirements) derive.  The runs confirm them |
| `I_chg_detect` | 2,800 mA, 0.01C | Above the offset of a typical current sensor for a 280 Ah cell |
| Sensor ranges | Cells 1,000 to 4,500 mV, temperatures −40.0 to 125.0 °C, pack and bus up to 20,000 mV | An open or shorted sensor reads outside them, and the pack range lies above four cells at 4,500 mV |
| `tol_sum` | 300 mV | Four cell errors, the pack sensor's error at 14.6 V, and the drop across three busbars at 1C |
| `tol_pc` | 500 mV | About 4% of the nominal 12.8 V, inside the usual end of precharge at 95% |
| `N_pc`, `D_edm` | 10 and 2 records | Precharge of the simulator's bus within a few records, and two exchanges for a relay to move |
| Board theorems | B5 composes B1 with M1, and B3a bounds the polling windows apart from the long window | B5 states the safety claim about the bytes that leave the board.  B3's single bound covers the long window and gives no usable baud rate (finding 6) |
| CRC in the specification | `crc32Eval` of `Division.lean`, with `crc32_eq` to `Spec.crc32` | `Spec.crc32` is not computable, and the specification must reproduce the vectors (finding 16) |
| Vector script | `tests/baremetal/bms_proto.py`, with PEP 723 metadata | The simulator of the later phase uses its codec |

## Review

A fresh agent reviewed the draft against the user's design, the agreed decisions, and the gap list.  It recomputed the vectors, the CRCs, the line times, and the fault table with its own encoder and zlib, read the datasheet's pages, and tested M1 on random runs of a machine built from the transition rules.  It found the offsets, lengths, vectors, CRCs, line times, profile values, the fault table's counts, and M2 to M11 correct, every state and input with exactly one outcome, and no removed feature left in the text.  Each finding below was checked against the rules or the sources before the response.

| Finding | Verification | Response |
|---|---|---|
| 1. M1 fails for a run with two starts after one reset acceptance: item 4 forces `j` to the last start and item 5 then requires `STANDBY` through a `PRECHARGE` | Confirmed on the run sync, reset, `RUN` 1, `RUN` 0, `RUN` 1 | `i` and `j` are the last reset acceptance and the last start, and item 5 requires `STANDBY` only of `a_i` and `a_{j−1}` and excludes `RESET_REQUIRED` and `FAULT` from `a_i` to `a_n` |
| 2. One lost answer makes every later answer out of order | Confirmed: "one more than the last in-order answer" never advances after a gap | The board sequence number left the bridge's validity, as follow-up finding 1 records |
| 3. BR6 and check 17 do not keep POS from closing when NEG's contact still reads closed at the first sampling after the release | Confirmed: check 17 then passes in `NORMAL`, and BR6 admitted the answer | BR6 now admits no relay until a current answer with permit 0, after which M1 requires a start and a precharge in later records |
| 4. A byte inserted after the delimiter joins the next record's segment, since BR3 sends the next record without a `0x00` | Confirmed: the script appended a `0x00` after every faulty stream | The script now sends the next record, or BR4's `0x00` and the next record when no current answer came, and the row gives `0x1002` for the next record |
| 5. The two answers of a `0x00` inside a record need the board to receive while it answers, and a change of the last byte to `0x00` gives one answer | Confirmed against the timing of the long window and the script's output | The table and the schedule give one or two answers and state the script's lack of timing; with `OVRDIS` the bytes that arrive while the board answers are lost except the last |
| 6. B3's single bound is dominated by the long window and gives no baud rate; the answer's CRC is omitted | Agreed: no bound is computed yet, but the gateway's step reaches 17,537 instructions without a CRC, and the BMS step adds 352 bit steps and COBS | B3a added, with the dispatch structure and the lemma it needs; both CRCs named |
| 7. The trusted base omits the initialization's accesses to RCC, GPIOD, and USART3's configuration | Confirmed: B1 includes them and B2 confined only the windows | The trusted item covers the initialization's accesses, and B2 states both confinements |
| 8. BR4's and BR2's quiet wait is met at once on a line already quiet | Confirmed | The wait starts at the end of the `0x00` |
| 9. BR5 bounds no delay before sampling, so the 200 ms between samples and the hold time do not follow | Confirmed | BR5 samples within `T_sample` of the exchange's end, and the requirements derive 176.7 ms |
| 10. After a lost delimiter the next answer leaves about 25 ms against `T_lease`, unstated | Confirmed for the old BR4 | BR4 ends its wait on a current answer, and the table states the 64.6 ms margin |
| 11. Replacing the mask at each change takes the tolerance from a relay that changed one record earlier; after a board reset the contacts get one exchange, not two | Confirmed with `PRECHARGE` to `NORMAL` followed by `RUN` 0 | Per-relay ages, and segment 0 counts as a change of every relay |
| 12. M1's items omit check 17 between `i` and `j`, and `i` is not the last reset acceptance, so "in particular" claims too much | Confirmed | Check 17 has a history definition through the ages, item 2 covers checks 7 to 17, and `i` is the last reset acceptance |
| 13. A press counts after a good segment, not after a record that passed the communication checks | Confirmed against rule 3 and the reset row | Wording corrected |
| 14. The answer to a record sampled before the release in the lost-answer case is `0x05 NORMAL`; `FAULT` holds in `NORMAL` only | Confirmed | The schedule row and the paragraph state both |
| 15. Identifiers with equal CRC-32 act as one link | Confirmed: the identifier enters only through the register value | Stated, with the requirement of distinct CRC-32 values |
| 16. `Spec.crc32` is not computable | Confirmed at `Library/Hashing/Crc/Spec.lean` line 78 | The specification uses `crc32Eval` with `crc32_eq` |
| 17. `T_chg_max` is attributed to item 5, which bounds current; the datasheet's ranges are ambient, item 6 says "preference value", and the scope calls the values maximum safety limits | Confirmed against the datasheet | `T_chg_max` marked a design choice, the ambient ranges and preference values stated, and the scope says limits taken from the datasheet |
| 18. The code rule does not cover the precharge timeout, and rule 4's "changes nothing" conflicts with rules 2 and 3 | Confirmed | Both reworded |
| 19. The scope's exclusions omit warning levels and derating | Confirmed | Declined: the brief directs that the requirements not describe the features the simplifications removed |
| 20. M12 mixes a framing property, and states 37 bytes where the framing's rule is more than 36 | Confirmed | M12 keeps only the lost byte, through L1 |
| 21. Paragraphs of fewer than three sentences, undefined labels, a branch named, and a figure that covers only status reads | Confirmed | Paragraphs merged or completed, the artifact codes defined, the branch removed, and the figure replaced by the longest window while bytes may arrive |
| 22. An authentic `FAULT` answer to a damaged segment is not current and does not release the relays | Confirmed | An authentic answer with a bit clear now ends the relay's lease |

## Follow-up review

The same agent checked the revision.  It reran its machine with per-relay ages and found the revised M1 true on 10,964 answers with a nonzero permit, 879 of them after several starts, and it recomputed the timing table and the revised fault table exactly.  It found no path by which POS closes onto a bus that was not precharged after a release, outside replayed records and wrong readings, which the requirements already list.

| Finding | Verification | Response |
|---|---|---|
| 1. The forward window over the board sequence number blocks every answer for hours when the board's first answer after a reset is lost | Confirmed: answers numbered below the last in-order number fall outside the window until the board's count passes it | The board sequence number left the bridge's validity, and any authentic answer with a bit clear ends a lease |
| 2. Check 17 tested "age is `D_edm`" against an uncapped history age | Confirmed; the text had been corrected to "at least `D_edm`" during the follow-up | No further change |
| 3. In the lost-answer case a record sampled before NEG's contact opens still gets `0x05 NORMAL` | Confirmed from the timing table and `T_act` | The schedule row and the paragraph state it, BR6 keeps the relays open, and the simulator's relays get operate and release times |
| 4. A lost delimiter gives no fault, and the answers count damaged segments, not lost bytes | Confirmed | Both statements corrected |
| 5. A read of `USART_CR3` during a run is a debugger access | Confirmed against the run conditions | The read happens over SWD after each run |
| 6. The artifact codes appeared only in the purpose, and M7 also names a theorem | Confirmed | The codes moved to the theorems' introduction, which separates the code M7 from theorem M7 |
| 7. Two names for the long window, and the lemma of B3a missing from the open items | Confirmed | One name, the window that receives a delimiter, and the lemma added |
| 8. "Never" ignored the CRC's residual error and the condition of distinct CRC-32 values | Confirmed | The sentence states both |
| 9. Short paragraphs, a count of open items, an unclear antecedent, and a mislabeled timing table | Confirmed | Paragraphs completed, the count removed, the antecedent named, and the table measured from the sampling of the case's record `k` |

## Open items

The lemma of B3a remains open, as [the requirements' open items](requirements.md#open-items) state, and the board's run of the schedule confirmed the timing values `T_ans`, `T_lease`, `T_sample`, and `T_act`, so none of them changed.  The overrun behavior is settled by the board tests and the decision of gap 5.  No VKB entry follows from this task, which proved nothing.
