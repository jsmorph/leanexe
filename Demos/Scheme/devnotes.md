## Decisions

The user's decisions of 2026-11-27 limit the work to the design's milestones 1 and 2, with WebAssembly as the only target.  Exact integers use the fixnum profile, with the reference semantics over `Int` and the 61-bit range as a separate restriction predicate, so that a later bignum library replaces one numeric layer.  The heap reserves an object kind for integers of several words, and the bignum library `Library/Numerics/Bignum/`, which is not yet in this tree, will decide that kind's fields.  Adequacy against §7.2, the collector's proofs, and the space theorem are outside the request.

The stage-1 design was approved with these choices: the coverage of the reference semantics and the machine that [the inventory](inventory.md) marks *this request*, no non-essential extras, the export ABI `run mode cap outCap fuel src` with a status byte first, a typed outcome for every detectable error, and an attempt at a kernel-checked theorem that the export returns `(13 3)`.  The encoding of §7.2 waits for the user's choice between a defunctionalized transcription and a deep embedding of the report's metalanguage.  `Report.lean` comes last in the reference-semantics stage, and the work stops there for that choice if it has not arrived.

The report makes `if` with one arm, `=>` clauses, `let*`, `do`, named `let`, and `delay` non-essential, so the profile omits them, although the stage-1 design report had listed `let*`, `do`, and `=>` clauses among the forms to implement.  The rewrite rules of §7.3 for `cond` and `case` use only two-armed `if`, and the rule for `(cond)` asks for "some expression returning an unspecified value", which the core syntax supplies as a constant.

## Stage 3: the reference semantics

The reference semantics lives in `Demos/Scheme/Semantics/`: the data, the numeric layer, the reader, the core syntax, the expander, the machine, and the outcomes.  The machine is one total function `step` over configurations, with `Steps` as its iteration, so the rules are the function's clauses and a run reaches at most one final configuration (`final_unique`).  An inductive relation with one constructor for each rule would read the same and would need a proof of its agreement with an executable step for the derived results, and the function makes that agreement definitional.  Every definition recurses structurally or on a fuel, so the kernel evaluates runs: the `or` case takes 25 rules, repeated escape 136, and `letrec` re-entry 88, and `decide +kernel` checks the three results in about five seconds.

Three choices of representation came from Lean's checks.  `deriving DecidableEq` fails for a datum type with a `List Datum` field, a nested inductive type, so a vector holds its elements as a proper-list datum, and the type is an ordinary inductive type with derived equality, which the statements of the results need.  The expander first had a function `expandForm s rest` that `expand` called on the operands of a special form, and Lean rejected the structural recursion, because `expandForm` passed the same `rest` to `expandBody`, which is no smaller argument; the special forms now sit in `expand`'s own arm.  A recursive call on an `@`-pattern variable, as in `qq D a` after `.pair a@(.pair (.sym s) _) rest`, also failed: in the branch Lean replaces `a` by its pattern, which is no subterm.  Computing the call before the inner `match a` works, as `qq` does with `pairCore`.

A quoted constant must denote one object at every evaluation of its quotation, also when a continuation re-enters a top-level form, as the executable's reader allocates the program's text once.  `start` therefore expands every datum of the program before the run and allocates each compound literal of each expansion once, immutable, and the expansion refers to it by location.  A datum whose expansion fails keeps its syntax error, which the run reports when it reaches that form.  The expansion of a temporary needs no counter: each rule binds its temporaries around a body that names only them, or for `letrec` around the assignments, so a temporary of a fixed index per role is fresh in its region, and an inner rule that reuses an index encloses no reference to the outer one.

[The corpus](Corpus.lean) holds 104 programs with outcomes written by hand from the report and the profile, among them the capture cases of temporaries, of quasiquote's `cons`, and of `case`'s `memv`, the re-entry of a `map` callback and of a top-level form, and the range limits.  The reference semantics met every expected outcome on the first run.  `corpus_outcomes` checks the corpus in the kernel.  With 98 programs as one declaration its check took 38 s and peaked at 10.6 GiB, since the kernel keeps every reduction of a declaration until it ends, and in chunks of ten programs, one declaration each, it took 39 s and peaked at 2.8 GiB.  With 104 programs it takes 47 s and peaks at 3.0 GiB.

An independent review of the three results' statements found them about the reference rules, on the request's programs byte for byte, and not vacuous.  It ran variants of `step` against the statements and the corpus and found that no case told apart operands evaluated from right to left, an operator evaluated last, a `letrec` that assigns each variable as its initializer returns when the initializers run from right to left, an `or` that evaluates a test twice, and a `let` that reuses its location when a continuation re-enters it.  The cases `operand-order`, `operator-first`, `letrec-staging`, `or-once`, `and-once`, and `fresh-reentry` now tell each apart, and the reference semantics meets them.  The review also observed that §7.3's thunk rule for `or` places no source expression in the scope of its temporaries, so `or-42` rejects an expansion that binds `_` around the second test, not a wrong choice of the temporaries' names.

## The transcription of §7.2

The user chose the defunctionalized transcription.  `Report.lean` follows §7.2 equation by equation, with its own abstract syntax of §7.2.1, which keeps the three lambda forms and `if` with one arm, and with the constants replaced by their values before the run, since `K` has no store argument and a quoted compound datum must denote an object in the store.  The three programs take 85, 413, and 268 clauses, against 25, 136, and 88 rules of the reference machine, since the equations pass sequences of values through `single`, `tievals`, and the continuations of `E*`.  `cross_check` states that the transcription's answers equal the reference semantics's results on the three programs, and the kernel checks the module in 10 s with a peak of 1.7 GiB.

Of the corpus's programs, the transcription starts 81, those whose constants lie within §7.2, and it agrees with the reference semantics on 48 of them.  Each of the other 33 calls a procedure that §7.2.4 does not define, which the transcription's initial environment leaves unbound, calls `+` or `<` with three arguments, where §7.2's `add` and `less` take two, exceeds the fixnum range, which §7.2 does not restrict, or compares two empty vectors, which are `eqv` as sequences of no locations under Ev = L* × T and distinct objects under the profile.  An escape procedure called with two values passes both to its continuation, as the equation of `cwcc` states, where the profile, after §6.9's escape procedure "of one argument", signals an error.

An independent review compared every clause of `Report.lean` with the PDF's equations and pages and found no departure, no missing equation, and no wrong citation.  It found supplied rules that the module's table did not record: the deduplication of a variable that a program defines twice, the error text of `cdr`, the identity locations of the initial store, the fixnum reader of the front end, the defaults for locations off the store, and the observation of answers; the table records them now.  It also ran mutants of the transcription against the three programs: a one-shot escape, a store restored at escape, swapped `cons` fields, a `tievals` that binds locations in reverse, a reversed `permute` without its inverse, and swapped `if` arms each changed a result, while a `truish` that treats `()` as false, a `single` that takes the first of several values, a missing check for `undefined`, and a lookup of the outermost binding did not.  The three programs never reach a rest list, `apply`, `car`, `cdr`, `setcar`, `eqv`, or the translation of definitions, so `cross_check_more` adds nine programs that do and states their agreement with the reference semantics.

## Stage 4: the reader and the expander in the dialect

Before the machine, a skeleton checked the shape of the allocation bound.  It kept an arena of five-word slots and an output array in one record, ran a `LeanExe.repeatWhile` loop over listed step functions that take the record by move and write its arrays with `set!`, and copied the output into a byte buffer at the end.  `verified_compile` generated the bound 0 for every step function, and the bound of the run was the arena's block, the output array's block, and the final copy, with no charge for a pass of the loop; a closed form of `40 cap + 9 outCap + 167` bytes followed from `Verified.blockCost_eq` and `Verified.allocationCost_le`.  The skeleton then left the tree, since the machine's own bound states the same.

The machine's modules live in `Demos/Scheme/Machine/`.  `State.lean` fixes the value words and the slots, `Codes.lean` and `Names.lean` the table of keywords, procedures, and fixed texts that the export will pass to the program as a table, `Text.lean` the interning of symbols and the strings and vectors of chunks, `Read.lean` the reader, `Expand.lean` the expander, `Convert.lean` the tagged form of code that mode 1 writes, `Print.lean` the printer, and `Run.lean` the dispatch and the outcome's bytes.  The reader handles one token at each step and keeps the data under construction in frames.  The expander follows the reference expander function by function, with each pending computation in a frame, so its core syntax and the order of its checks are the reference's; a lexical address replaces each variable's name.  The tests of `tests/TestSupport/Scheme/Cases.lean` run every program of the corpus and 60 programs of syntax in modes 0 and 1 in native Lean and compare the bytes with the reference reader's and the reference expander's, through `TestSupport.Scheme.Oracle`.

The comparison found three faults of the machine.  The reader interned the abbreviations' keywords one entry early, so `'x` read as `(quasi x)`; a `cond` clause passed its lambda node where `beginCore` takes the lambda's body, which left a chain cell of code 0 and made the conversion of mode 1 loop until the arena ran out; and `tableEntry` returned entry 0, the keyword `=>`, for an identifier longer than 32 bytes.  The interpreted `#eval` of the comparison missed the last, which only the compiled case executable's list of programs reached.  A record update whose fields continue on the next line after a trailing comma fails to parse in Lean v4.36.0, with "unexpected identifier; expected '}'", and fields on separate lines without commas parse.  `mut` is a keyword, so it cannot name a parameter.

## Stage 5: the evaluator and `call/cc`

`Eval.lean` holds the rules of the reference machine over code, environments, and frames in the arena.  An environment is a chain of cells, one location for each variable, so closures share the cells that `set!` writes; a call binds fresh cells and builds a fresh rest list from the surplus arguments; and the frames, which no rule changes once a later frame refers to them, form a continuation that an escape procedure holds and reinstates as often as it is called.  The arguments of a call are a list whose last argument is first, which the operand frames build by consing, so binding the fixed variables and the rest list takes one pass.  The reference's frame of an operand holds the operator's value, the values so far, the operands left, and the environment, five words where a slot has four fields, so the machine keeps the operator's value in a frame `E_FNV` below the operand frames.  `Numeric.lean` holds every numeric procedure, which `Numeric.apply` reaches from the machine's arguments, so a layer of integers of any size replaces that module alone.

The corpus's 104 programs gave their expected outcomes in mode 2 on the first native run, as did the comparison with the reference semantics on all 170 programs.  The first run of the case executable with an arena of `2^24` slots did not finish in 16 minutes of CPU, and the cause was an ownership fault with a consequence beyond speed.  The step functions bound `let h := m.heap` and read `h` after a write to the arena, so the old array stayed alive, and every write copied the arena: in native Lean a copy of the whole array at each step, and in the compiled module a copied block that the generated bound charges.  A compiled test confirmed it: a function that reads the old array after `set!` gets the bound `Verified.blockCost (m.heap.size * 5)` and a borrowed parameter, and the same function with the read moved before the write gets the bound 0 and a moved parameter.  Each step function now reads every word it needs before its first write, from the slot of the frame on top and the objects it names, and after a write reads only the current record.  A read of `fa m.heap v` after a call that consumed `m`, as in `pushFrame (emit m 40) P_TAIL (fb m.heap v) 0 0`, is the same fault.  With the change the case executable runs its 517 cases, the loop of 100,000 calls on an arena of `2^24` slots among them, in 1.7 s.
