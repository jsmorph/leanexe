# Calculator of arbitrary-precision integers

## The message and its line

The calculator reads one message and writes one line, with the text exports of [the bignum library](../../Library/Numerics/Bignum/README.md).  A message names an operation and gives its operands, separated by single spaces: `neg a`, or `name a b` for `name` one of `cmp`, `add`, `sub`, `mul`, `tdiv`, `tmod`, `ediv`, and `emod`, with operands in the library's grammar `"0" / ["-"] nonzero *digit`.  [`Message.lean`](Message.lean) defines the line, `calcSpec`, with `List.splitOn` and the grammar's `denote`: `0`, a space, and Lean's text of the exact result, the sign of `a - b` for `cmp`, or one digit, `1` or `2` for a first or second operand outside the grammar, `3` for a division by zero, and `4` for a message of more than 65,536 bytes, a name of no operation, or wrong separators.  Wrong separators are a number of spaces other than the operation's, or an empty part from a leading, a trailing, or a doubled space, as in `add  1` or `add 1 `.  The faults are tested in the order length, separators, name, first operand, second operand, and divisor, so `tdiv x 0` gives `1` when `x` is outside the grammar.  Another byte, such as a tab or a newline, belongs to the part that holds it, so `add 1 2\n` gives `2`.  The line ends without a newline, and no line holds the byte 0 (`zero_not_mem_calcSpec`).

[`MessageProgram.lean`](MessageProgram.lean) implements the line in the verified dialect over the text exports, and [`MessageCompiled.lean`](MessageCompiled.lean) compiles it with the library's functions as `messageCompiled`, a module separate from the library's `compiled`.  `calcLine_eq` states that the calculator returns `calcSpec`'s line for every message, and `calcWords_eq` that the bare-metal entry, on the words that hold the message, returns the line packed eight bytes to a word.  `calcWords_bound_le` bounds the entry's allocation by `2^25` bytes for every input, through `calcLine_bound_le`, `400 n + 4096` bytes for a message of `n ≤ 65,536` bytes, and the closed forms of the text exports, which [`MessageBound.lean`](MessageBound.lean) carries to `messageCompiled` by equations between the two modules' generated bounds.  [The review](review.md) records the independent reviews of the message's specification, the bare-metal program, and the Image, with the answers to their findings.

## The bare-metal program

[`Bare.lean`](Bare.lean) states the program's theorem.  The program is the C translation of `messageCompiled.module` with `lx_mem` of 256 MiB, followed by leanexe's `main` for input, `inMain`, around function 44, `calcWords`: it reads an eight-byte length, the lowest byte first, and the message through volatile loads of `lx_in`, where QEMU's loader places the input file at `0x70000000`, copies the message into an array, calls the entry, and writes the result's length word and words to `lx_out`.  `calc_program` states that for every sequence of values that the loads read the program terminates, with the result 0 and the stores of the packed line when the length is at most `inMax`, `2^24 − 8`, and with the result 64 after reading the length otherwise, and that its trace satisfies the premise of leanexe's Rocq theorem `clight2_bigstep_asm_reads`, which carries the termination to CompCert's assembly program.  `calc_line` writes the output as bytes, the line's number of words, the line, and zeros to the end of its last word, and `calc_unary`, `calc_binary`, and `calc_zero_divisor` join it to the main claims for messages written as an operation's name and Lean's texts of integers.  The program answers messages of up to 65,536 bytes, writes the line `4` for longer messages up to `inMax`, and stops with the status 64 beyond.

## The AArch64 Image

The Image runs the same calculator without CompCert.  Its entry is `calcBytes`, function 45 of `messageCompiled`, which reads the message as `LeanExe.Bytes` and returns the line's bytes.  [`BytesBare.lean`](BytesBare.lean) states `output_eq`, that the entry's output is `calcSpec`'s line for every message of at most 65,536 bytes, `calcBytes_bound`, that it allocates at most 27,000,000 bytes, which fits a memory of 512 pages above the heap, and `calc_runs`, the program's theorem in leanexe's form `BytesRuns` for the program that `genBytesProgram` writes at any base.  The program reads an eight-byte length and that many bytes from the UART, writes the line, and returns with the status 0, or, for a length above 65,536 or a byte with the receiver's error flag, reaches its exit with the status 64 or 65 after writing nothing, with no trap and no overflow of its stack of 512 KiB.  [`Image.lean`](Image.lean) reads the file `bignum-calc.img` with `file_nat%`, and the kernel checks that its bytes are those of `genBytesImage` (`calc_file_image`).  `calc_uart` then states, for a boot state whose memory holds the file at a base `B` aligned to 4,096 bytes in the RAM GiB, that the machine reaches PSCI's `SYSTEM_OFF` after writing the line of a delivered message and the status byte 0, and `calc_uart_unary`, `calc_uart_binary`, and `calc_uart_zero_divisor` give the line for messages written as an operation's name and Lean's texts of integers; `calc_uart_over` and `calc_uart_flag` give the statuses 64 and 65.  `calc_fits` states that the Image's memory fits the RAM GiB from `imageBase`, `0x40200000`.  The three theorems of runs cover every record of the receiver, and since no line holds the byte 0 the status byte follows the line unambiguously.

## Building, running, and testing

```sh
tools/leanrun --timeout 3h lake build Demos.BignumCalc.BytesBare
tests/bignum-calc/bare.sh
tests/bignum-calc/image.sh --check
```

[`tests/bignum-calc/bare.sh`](../../tests/bignum-calc/bare.sh) builds `Bare.lean`, writes `message.c` with [`tests/bignum-calc/EmitNative.lean`](../../tests/bignum-calc/EmitNative.lean), has `clightgen` read it back and compares that reading with the theorem's whole program, and compiles it with `tools/baremetal/build.sh`, which bounds the stack of `main`.  [`tests/bignum-calc/messages.mjs`](../../tests/bignum-calc/messages.mjs) writes 1,120 messages and the bytes that each must give, from Node's `BigInt` alone: every operation on the values 0, ±1, ±(2^32 − 1), ±2^32, ±(2^64 − 1), and ±7 in all pairs and on random operands of up to 600 digits, operands outside the grammar, names of no operation, wrong spaces and empty operands, a product of two 32,765-digit operands in 65,536 bytes, and the same message with one more byte.  The program must write the expected bytes with the status 0 on every message, with a stack within its bound, and a length of `inMax + 1` must give the status 64 and no output.  [`tests/bignum-calc/image.sh`](../../tests/bignum-calc/image.sh) writes the Image with [`tests/bignum-calc/EmitImage.lean`](../../tests/bignum-calc/EmitImage.lean), checks with `tests/baremetal/a64-loadcheck.sh` that QEMU places it at `0x40200000`, and with `--check` elaborates `Image.lean` in the directory of the Image, whose kernel check compares the file with the generator's bytes.  QEMU then runs the Image on every message, one message also from a pipe in pieces, the empty message, the length `2^64 − 1`, and a break into the empty receiver.  `ACCEL=kvm` runs both scripts under KVM on an AArch64 host, and `BARE_COUNT` and `IMAGE_COUNT` keep the first messages for runs under TCG.

## Limits

The bare-metal program's theorem covers the whole program in leanexe's copy of Clight, and leanexe's Rocq composition carries a termination with its reads to CompCert's assembly program, so its reader trusts the items of code METAL of [the trusted-base document](../../docs/trusted-base.md).  Clight's semantics gives each frame unbounded memory, so the stack bound rests on the stack-bound tool.  The Image's theorems hold in leanexe's model of the boot machine and cover the generated code, the startup, and the Image's layout, and the kernel compares the file's bytes with the generator's output, so no compiler, assembler, or linker is trusted; their reader trusts the items of code A64.  leanexe's form `BytesRuns` states the output and the end of a run but not the number of bytes that the program reads, so the theorems hold for an Image that waited for bytes after the message; the QEMU runs, whose input files hold the length and the message alone, show that this Image does not.  `lake build` does not check `Image.lean`, so after the Image is rebuilt, `image.sh --check` must run again for its theorems to concern the new file.
