# Review of the specification

Two fresh agents reviewed [the specification](Spec.lean) and [the case inputs](../../../tests/TestSupport/Modules/Kmp.lean) against [the request](request.txt), from the files alone, each with an independent Python model of the program at 64-bit words and an oracle of the request that tests every position.  Both found that `expected` states the request's result on every input, with lengths beyond the bytes of the arrays, the empty pattern, a pattern longer than the text, and lengths near `2^64`, and their models agreed with their oracles on 32,016 and 200,012 inputs.  Both checked that the table of `failure` holds the longest proper border of each prefix, and the second checked the claims of `fall_spec`, `step_spec`, `next_state`, and `positions_spec` on hundreds of thousands of states.

Both found that the program scans the text twice, once in `count` and once to record the positions, while the request asked for one scan in which no byte of the text is read twice.  The two requirements of that request conflict: one scan cannot know the number of occurrences before it allocates the result, so a single scan must extend the result block by block.  The request now asks for two scans, the first to count and the second to record the occurrences in a result of that size, each reading each byte of the text once, and the specification's comment states the method in those terms.  Both found that for the empty pattern the program built an array of `n` words and extended it, a second block, and it now builds one block of `n + 1` words whenever `n + 1` is a word.

Both found sentences that said more than the code: the program's comment called the scan's state the longest prefix that ends at the current byte where it is the longest shorter than `m`, the proof's comment left out that `step` starts from the longest prefix, the docstrings of `fall_spec` and `step_spec` left out their premises on the table and the count of steps, and the docstrings of `pre_trans` and `pre_border` spoke of prefixes of the text where they concern prefixes of the pattern.  The comments now state these exactly.  The docstring of the case inputs gave 4,181 bytes for a Fibonacci word of 2,584, claimed deep fall-backs that the Fibonacci cases do not reach, and claimed a pattern length beyond its array that no case had.

Both ran wrong programs on the case inputs.  The cases missed a fall-back limited to one step on a byte, a fall-back with too few steps, a byte mask of 127, and a pattern clipped to its array, and they now add `a⁹b` in `a⁹c`, whose fall-back takes 9 steps on one byte, `aaa` in `aabaa` and `aa` in `aba`, bytes that differ only in bit 7, a pattern length beyond its array, a text array with nonzero bytes past its length, an empty text array with a length of 4, a pattern array with a whole word past its length, a pattern as long as a text it differs from, and the empty pattern on texts of 1 and 17 bytes.  The cases compare the module with `expected` itself, so they test the compiled code and the allocation count, and no case can tell one scan from two.
