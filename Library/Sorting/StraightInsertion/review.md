# Review of the specification

Two fresh agents reviewed [the specification](Spec.lean) and [the case inputs](../../../tests/TestSupport/Modules/StraightInsertion.lean) against [the request](request.txt), from the files alone, with a Python model of Algorithm S.  The first review found no input on which `expected` differs from the request and confirmed every concrete claim of the inputs' docstring.  It found that the comment's claim of a stack that does not grow lacked evidence, that "cannot state that the program follows Algorithm S" overstated the limit, since another theorem could state the method, and that the comment did not mention "in place".  The comment now cites the generated `trapFree` theorem, which has no call-depth premise, says that the specification does not distinguish Algorithm S from other methods, and derives "in place" from the allocation theorem.  It named the class of insertions that move 1,000 or more words, which the decreasing array of 1,500 words now covers, and it found that the docstring did not mention `[2^64 - 1, 0]` and `[0, 2^64 - 1, 0]`, which it now names.

The second review found no disagreement.  It found that the docstring's "the long arrays" left out the seven long arrays of `sortInputs`, and that the comment described the compiler's translation of the program, which the specification file cannot support.  The docstring now names the long arrays it adds, and the comment no longer describes the translation.  Its model showed that the cases detect signed comparison, comparison of 32 bits of a word, a skipped comparison with the first word, a skipped last word, a write of the moved word in place of the saved word, and comparison through `Float64`.  It recorded one class without inputs: an implementation whose inner loop stops after 1,499 or more moves, which only arrays longer than 1,500 words could expose and which the main theorem covers.  Both reviews noted that the theorem certifies the result and not the method, so only the program text shows Algorithm S.
