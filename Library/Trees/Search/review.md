# Review of the specification

Two fresh agents reviewed [the specification](Spec.lean) and [the case inputs](../../../tests/TestSupport/Modules/TreeSearch.lean) against [the request](request.txt), from the files alone, each with Python models at 64-bit words.  Their models of `search`, `descend`, and `ascend` returned the result of `algorithmT` on every case input.  Both found no input on which `algorithmT` or `SearchTree` disagrees with the request, including the empty tree, keys at the root and deep in the tree, absent keys, keys of `2^63` and above, and trees that are not search trees.  Both found that `Ordered` defines a binary search tree with distinct keys, which the comment stated only through the word "increase", and the comment now says so, as the keys of Knuth's tables are distinct.  The first found that `algorithmT` also meets the guarantees on trees whose keys in symmetric order do not decrease, which `searchTree` does not state.

Both found that the comment left out the consequence of a search that passes by a key off the path: the insertion then adds a second node with that key, as on the mirror image of the seven-node tree with the key 8, and the comment now states it.  The comment now separates `SearchTree`, which carries no hypothesis, from the theorem `searchTree`, which proves it for every binary search tree, and it records that the module computes the flag and the tree in separate exports, `search` on a lent tree and `insert` on a tree that the caller hands over.  The second review found that the property `ordered` follows from `keys`, and it remains because it states the request's words, which the comment now says.  It also found that `SearchTree` does not fix the shape of the tree, since an insertion at the root meets it, while `algorithmT` fixes the result and the call theorems state `algorithmT`.  Its finding that "changes one link and keeps every other node" described values, which have no links, led to the present wording, the old tree with one empty subtree replaced.

Both found that the statements are weaker than the request's words on storage.  The bound on `top` does not count blocks that the allocator takes from its free list, and no statement relates the blocks of the result to those of the argument, so a program that copies the path into free blocks, or releases each node and allocates its replacement, meets the statements.  The comment now says that the program text and the compiler's charge for every allocation show the reuse, and the comments of the compilation describe the generated bound and attribute the rebuilding in place to the compiler's ownership rules.  Both found that the comment's account of the call stack states the compiler's rule from the manual, which no theorem states, while Talos's semantics bounds no call depth, and the comment now says that the reading rests on that rule.  The proof's comment had claimed the properties of `SearchTree` for the library's `KeyTree.insert`, where the file proves the equality with the tree of `algorithmT`, membership, and ordering, and it now names those.

Both confirmed the claims of the inputs' docstrings except two.  The arbitrary tree of 2 nodes is a search tree under unsigned comparison, and the search on the tree of three nodes with the key 5 stops at the root, so the docstring's statement that the comparisons pass by a held key applies to neither.  The cases detected every wrong program that changes a result or an allocation count: signed comparisons, comparisons of the low 32 bits, `2^64 - 1` as a sentinel, a search or an insertion that stops at the root, step T5 on the wrong side, the insertion of a key already present, rebuilds that exchange children or lose a subtree, copies of the path, insertion at the root, a search for a key anywhere in the tree, and guarded recursion, which traps on the chains.  The reviews named inputs that no case covered, and the cases now include a chain of 1,000 nodes at the limit of guarded recursion, a left chain of the keys 1 to 10,000 down which the key 0 passes every node, a search tree of 2,000 keys whose deepest path changes direction at every node, and a tree with an equal key below the node that holds it.

The cases leave three classes uncovered.  A limit on the path of 10,000 nodes or more passes them, since a longer chain approaches the host's limit of 128 KiB on one command-line argument, and `insert_implements` excludes every such limit.  The host prints the result of `search` and not the lent tree after the call, so a search that leaves the links reversed passes every case, while the frame of `search_implements` excludes it.  Every case starts from a heap with an empty free list and room for the new node, and the theorems cover a nonempty free list and require the room.
