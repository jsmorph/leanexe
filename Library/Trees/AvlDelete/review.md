# Review of the specification

Two fresh agents reviewed [the specification](Spec.lean) and [the case inputs](../../../tests/TestSupport/Modules/AvlDelete.lean) against [the request](request.txt), from the files alone, each with an independent Python model of the deletion.  The first compared `deleteA` with a model that rebalances from heights on 4,782,184 deletions over every balanced shape of height at most 5 and on 510,954 deletions in random sequences that empty trees of up to 300 keys.  The second compared it with a model of Knuth's procedure, Algorithm D with the successor's node relinked and the cases of §6.2.3, on 2,554,607 deletions.  Neither found a balanced binary search tree on which `deleteA` differs from the request, in shape, keys, factors, or flag, and both found that the program's loops give `deleteA` on every case input.

Both found that `Removes` did not state the request's sentence that an absent key leaves the tree unchanged, since another balanced tree with the same keys and height meets its other fields.  `Removes` now has the field `unchanged`, and `deleteA_of_searchA` states that a failed search leaves every tree as it is, factors included.  Both found that the comment attributed to Algorithm D a rule that differs from it: Knuth's step D1 tests only the right link, and his steps move the successor's node into the deleted node's place, while the specification replaces a node with an empty left subtree by its right subtree and gives the node with `x` the successor's key, and the program keeps that node's block.  The two give the same tree on a balanced tree, and the comment and the request now describe the method as the symmetric form of Algorithm D, and the comment states the difference.  Both found that "the least key of its right subtree" holds only on a search tree, and the comments now name the leftmost node.

Both found that the comment's rule for the rotation did not match the code for factor words other than 0, 1, and `2^64 - 1`, and that it left out a node that would rotate but has no child on the other side.  The comment now states the rotation as single when the child on the other side is balanced or higher on its outer side and double otherwise, and records the choices at the node, the child, and the grandchild, and for a missing child or grandchild.  The second found that the docstring of `delete_implements` left out the allocator invariant, the memory cap, and the separation of the tree's blocks, and the docstring of `delete` claimed a restored balance on any tree and the removal of the node that holds `x`, and both docstrings now state the premises and the method.  The second also found that the property `ordered` follows from `keyList`, and that `heightAfter` and `shrank` together state the request's rule on the height.

Both computed the coverage of the cases and found that the ten trees missed eleven of the 105 combinations of location, side, case, and depth that balanced trees admit, of which the insertion's trees covered seven.  The four double rotations three or more levels below the root had no case, and two sequences of 35 and 38 keys from the first review now give them, which a Python model confirms against the 105 combinations.  Both named the input classes that no case covered on trees that are not balanced: a child or a node with the factor word 7 in a rotation, a missing inner grandchild, a missing child below the root, a rotation and a successor search on stored factors, and repeated keys.  The cases now hold a tree for each.  The cases detect every wrong program that changes a result on a balanced search tree, among them wrong factors or a continued shrink after the rotation around a balanced child, the predecessor in place of the successor, the insertion's rule that every rotation stops the shrink, and signed comparisons, while no case can tell which block a deletion frees.
