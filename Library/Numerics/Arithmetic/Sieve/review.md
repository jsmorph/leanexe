# Review of the specification

Two fresh agents reviewed [the specification](Spec.lean) and [the case inputs](../../../../tests/TestSupport/Modules/Sieve.lean) against [the request](request.txt), from the files alone, each with an independent Python model of the program at 64-bit words and an oracle by trial division.  Both found that `expected` states the request's result on every word `N`: `Nat.Prime` is Mathlib's primality, the filter keeps the primes below `N` in increasing order, and every one of them is its own word.  The models agreed with the oracles for every `N` up to 3,000 and 5,000 and on every case input, and the second checked the proof's invariant, that the flags when the sieve reaches `p` are those of `Struck p`, at every step for every `N` up to 2,000.  Both checked the word arithmetic near `2^64` and found that the test `p ≤ (N - 1) / p` agrees with `p·p < N` on every word, that no index or count wraps, and that `N - 1` wraps only for `N = 0`, where the test `p < N` fails.

Both found that the theorems read "allocate only the flags and the result" as a rise of `top` of at most two blocks, which permits allocations from free blocks and states nothing about the release of the flags, and that the heap premise admits `N` only up to about `5.1 × 10^8`.  The specification's comment and the README now state both, and they name the two theorems that the reading needs, `primes_implements` and `primes_bound`, where the comment had named one.  The docstring of `primes_implements` and the README now state its premises of the allocator invariant and the memory cap.

Both found sentences that said something different from the code.  The docstring of `sieveFrom` said that the multiples of `p` lose their primality where the code sets their flags, and it and the README said that the test of `p` prevents every wrap, where `N - 1` wraps for `N = 0`.  The README said that three passes read `N` flags each, where the build writes them and the sieve reads only the flags of the `p` with `p·p < N`, and the proof's comment said that the multiples of `p` are the numbers that `Struck (p + 1)` adds, where some of them are in `Struck p` already.  The first found that the docstring of `crossOff` stated `p·p < N` without saying that the product is exact, that the README's row of `crossOff_spec` left out the premise of `N` flags, and that the README named a header where each block adds a header and a length word.  Both found that "powers of 2 and of 10" described only some of those powers.  The sentences now state what the code and the theorems do.

Both ran wrong programs on the case inputs and found that the cases detect every one of them whose result differs from the request's at a bound up to 3,000.  The wrong programs that no case detects give the same result as the program on every word, such as crossing off from `2p`, or differ only at bounds whose flags no memory holds, and `primes_eq` excludes the latter, while only the program text shows that the method follows the request.  Both found no case of a prime square above 31², no case between 1,000,001 and the premise's limit, and no trap case apart from `2^29`, which the guard on the length of an array also meets.  The cases now hold the squares of 37 and of 1,009 with their neighbors, 1,000,004 and 2,000,003, and trap cases at `2^29 - 1`, where only the memory cap stops the call, and at `2^32` and `2^64 - 1`.
