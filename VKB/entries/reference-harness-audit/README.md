# Code around an executable reference

The entry applies when a check compares a model with an executable reference, such as Isla's traces of Arm's specification, Sail's Lean translation of Arm's floating-point functions, or a reference written as a script, and when a harness function, a configuration, a patch of the tool, or an edit of the reference's IR or translation is written or changed.  Such code lies outside the specification and inside the check.  A value that it fixes narrows what the check tests, and an error that it swallows makes a failed path look complete.  In either case every test still passes.  The rows "The Isla check" of [the trusted base's A64 section](../../../docs/trusted-base.md#a64-aarch64-images) and [its M7 section](../../../docs/trusted-base.md#m7-cortex-m7-images) list this code among the trusted items, and their evidence includes the controls and comparisons below.

A review reads each harness function, fetch loop, configuration value, exception handler, patch, and IR edit against the architecture manual and the reference's source and records what each changes, as the independent review of the M7 row did for the harness and the semantics of traces.  Isla's harness `isla_footprint_common` calls the decoder in a try block whose handler clears every exception, so a path on which the decoder throws SEE, UNDEFINED, or UNPREDICTABLE looks complete.  `tests/isla/armv9p4-checked.diff` keeps the handler for the exception that every exception entry throws and makes every other exception fail a Sail assertion, which ends Isla's run, and a control input shows the edit at work: with the permanently undefined encoding UDF, the unedited IR gives a trace that looks complete, and the edited IR stops (the diff's header).  The Sail model's fetch loop sets `__currentCond` to AL outside an IT block, so the unedited model branches on every B<cond>.W and its condition field goes untested.  `tests/isla/armv9p4-t32.diff` moves the value into the reference's own clause: the decode clause of B T3 writes the opcode's cond field to `__currentCond`, the condition that CurrentCond() of DDI 0403E.e section A7.3.1 gives, and the harness sets AL before the decode, as `__InstructionExecute` does.  A profile names the source of each register value that it fixes, as the headers of `tests/isla/traces.sh`, `LeanExe/A64/Isla/Profile.lean`, and `LeanExe/M7/Isla/Profile.lean` do for `LeanExe.A64.Isla.Profile.sys` and `LeanExe.M7.Isla.sys`.

A comparison shows that an edit changes nothing that it does not target.  An edit of Isla's IR keeps the index of every statement that a jump names, as `armv9p4-t32.diff` does by removing a statement that no other statement reads, and the comparison regenerates every existing trace from the edited IR and compares it with the trace from the IR before the edit, normalizing only what the tool reorders.  Isla prints a struct's fields in an order that varies between runs, since it keeps them in a hash map with a random seed, and the reader drops the fields whose order varies ([the Cortex-M7 document's section on the Isla check](../../../docs/m7-bare-metal.md#the-isla-check)).  The traces of the other forms from the floating-point edit equal those from the IR before it byte for byte, except the loads and stores, whose traces differ only in that order ([the AArch64 document's section on Isla](../../../docs/a64-bare-metal.md#isla)).  A patch of the tool runs as the original without its new options, as the header of `tests/isla/isla-e9b5d945.patch` states, and the A64 row lists the patch's validation against unpatched runs.  For a translation, `tools/sail/ConstDump.lean` hashes each constant's type and value, `tools/sail/srcdiff.py` maps the changed lines of two source trees to the definitions of the translation, and the table of [the Sail README's section on elaboration](../../../tools/sail/README.md#elaboration) gives, for each edit, the comparison that shows it changes nothing else.

A script checks the readings that a proof rests on over the reference's call graph.  The theorems of the floating-point forms take each abstract call's equation as a hypothesis, which needs the original functions to raise no exception and to read and write only the registers that the theorems list.  `tests/isla/fp-callgraph.py` follows the IR's statements from each function's entry, removes only the edges that the startup's FPCR, AArch64 state at EL1, or the pseudocode rules out, prints each removed edge and fails when its statement is not a jump to the edge's target, and then checks that no reached statement sets an exception, no function recurses, and the registers read and written are those the readings allow.  A test evaluates a trusted translation at negative and extreme operands, by `rfl` or by evaluation.  lean-sail's coercion `CoeT Int x Nat` maps a negative integer to 0, and with `asl_Int`'s result typed Nat from its first branch, SInt and FixedToFP of a signed operand gave 0 for every negative value, which the deletion of the coercion in `tools/sail/lean-sail-v6.diff` and the edits of `tools/sail/fix-output.sh` remove (the section on elaboration and the header of `tools/sail/F7/FixedToFP32.lean`).  [The section on what the proofs trust](../../../tools/sail/README.md#what-the-proofs-trust) records a defect that remains, `set_slice_int` giving −1 for one input, on a branch that no theorem enters.

A second implementation of a specification, such as RCTab against the ranked-choice counts, is a reference whose configuration and comparison are code of this kind.  Map each setting of the configuration to the provision that it expresses, and read the tool's source at the pinned tag where its documentation leaves a behavior open, as the tables of [the corpus's RCTab section](../../../tests/rcv/README.md#rctab) and [the Maine corpus's RCTab section](../../../tests/rcv/maine/README.md#rctab) do.  Where no setting expresses a provision, the comparison predicts the tool's output from the specification's by a named rule that restates cited lines of the tool's source, compares every round with the prediction, and fails on every difference that no rule states, and `tests/rcv/rctab.py compare` reports how many comparisons each rule explained.  Where the tool and the specification divide a quantity into different categories, the comparison compares sums of categories, as the Oakland comparison does for RCTab's exhausted choices against the reasons `exhausted` and `uncounted`, or it splits a category by a second statement of the rule, as the Maine comparison does to compare RCTab's skipped rankings with the ballots that rule 1 of the interpretation makes inactive.  RCTab exits with status 0 when a tabulation fails, so `tests/rcv/rctab.sh` reads its console output for the pinned version, for lines marked SEVERE, and for the results directory, as [the entry on checks that can fail](../discriminating-checks/README.md) requires of a check's pass criterion.

Tests of the model through a harness that swallows exceptions pass on paths that the reference never completes, and a configuration that fixes a value the check must vary passes for every value of the opcode's field.  An edit validated only on the forms it targets can change others unseen, and a translation tested only at nonnegative operands passes with a coercion that maps every negative operand to 0.  [The entry on checks that can fail](../discriminating-checks/README.md) states the general rule that a check needs a control input that it rejects, and [the entry on types that elaboration chooses](../elaborated-types/README.md) covers the coercion as a failure of elaboration.

The worked examples are the headers of `tests/isla/armv9p4-checked.diff` and `tests/isla/armv9p4-t32.diff`, the script `tests/isla/fp-callgraph.py`, the comparisons of the Sail README's sections on sources and elaboration, and the rows "The Isla check" of the trusted base.  [The entry on instruction forms against Isla](../isla-form-proofs/README.md) covers the theorems over the traces, [the entry on floating-point equations from Sail](../sail-fp-equations/README.md) the proofs over the translation, and [the entry on encodings and co-simulation of machine forms](../machine-form-validation/README.md) the other evidence for a form.
