# Loops and builds of the dialect

A dialect program iterates with `LeanExe.loop n init f`, which applies `f` to the indices `0` through `n - 1` in order, and constructs arrays with `LeanExe.build n f`.  A proof that such a program meets its specification needs an invariant for each loop and the elements of each built array.  These lemmas concern the Lean definitions and name no compiled code.

`LeanExe.Dialect.loop_induction` extends a predicate `P k s` from `P 0 init` through every step `k < n.toNat` to `P n.toNat (LeanExe.loop n init f)`.  State `P` over the natural-number index `k`, and inside the step convert `(UInt64.ofNat k).toNat` back to `k` with `UInt64.toNat_ofNat_of_lt'` and the bound `k < n.toNat < 2 ^ 64`.  `LeanExe.Dialect.loop_congr` replaces a loop's step by one that agrees at every index below `n`.  For builds, `LeanExe.Dialect.build_size` gives the size, `build_get` gives the element at `m < n.toNat`, `build_get_out` gives `default` beyond it, and `build_congr` replaces the function.

Write the invariant to describe the state after `k` steps exactly, including the facts that the steps at earlier indices established, as `Library.Arrays.Search.firstZero_cases` does with its two cases: no zero among the first `k` words, or the first zero found at some `j < k`.  An invariant that holds only at the end fails at the step case.  The SHA-3 sponge and SHAKE proofs and the regex matcher's proofs use the same lemma for longer loops.

A loop that accepts while every index passes a test, `LeanExe.loop n true (fun k ok => if !ok then false else P k)`, gives `P` at every index when it returns `true`, which `Demos.Slew.Check.loop_all` proves once for the slew planner's edge and attitude checks.  A loop whose state is a word read as a set of positions takes an invariant on each position, as `Library.Regex.RunProof.runInput_bit` does with the bits of the automaton's states.  A loop that folds a specification's list keeps the equation with the fold over the first `k` elements, as `Library.Hashing.Sha3.SpongeProof.absorb_spec` does with the absorbed blocks.

State an invariant of several facts as a structure, with step lemmas over arbitrary states instead of the program's step, so that every program whose loop keeps the facts reuses the lemmas.  `Library.Graphs.UnionFind.Inv` states the facts of the merging loop after `t` pairs: the parent links form a forest, every link joins equivalent elements, and the two elements of every pair taken so far that lie below `n` have one root.  `inv_keep` extends it to the next pair when that pair needs no link, `link_inv` extends it when the program links the root of one element of the pair to the root of the other in either direction, and `labels_spec` proves the labeling loop for any links that satisfy it, so `Library.Graphs.WeightedUnionFind.classes_spec` reuses all three with its own `unite_inv` and path compression.  `Library.Graphs.TopologicalSort.topoSort_spec` follows the same form with the structure `QueueInv`, the invariants `OuterInv` and `InnerInv`, and the step lemmas `outer_step` and `inner_step`, which `process_spec` passes to `loop_induction`.

`apply loop_induction` leaves `P` to higher-order unification against the goal, which fails for the loops of steps D4 and D6 of the multi-precision division.  Naming the invariant and passing it, `refine loop_induction (P := MulsubInv w vn qh j) ?_ ?_`, avoids the unification, as `Library.Numerics.MultiPrecision.mulsub_spec` and `addback_spec` do.  When the theorem's count is a natural number of the model, such as a number of burns, state the invariant as a definition whose last two explicit arguments are the count and the state, state the theorem as that definition at the model's count, rewrite the count into the program's word count with `rw [← hN]`, unfold the program, and apply `refine loop_induction (Inv …) ?_ ?_`, as `Demos.PassiveSafety.positionI_encloses` does with `Demos.PassiveSafety.PosInv`.  The rewrite touches only the explicit count, since the definition's body stays folded, and the unifier matches `LeanExe.loop N init f` through the program's `let` bindings.  A search that refines cells level by level takes `Demos.Screening.loop_cover`, which [the entry on searches over interval enclosures](../interval-searches/README.md) describes.  `Library.Random.Orbit.loop_eq_iterate` states `LeanExe.loop n x (fun _ s => f s) = f^[n.toNat] x` for a loop whose step ignores the index, so that Mathlib's lemmas about iterates apply.  The generators instantiate it, as `Library.Random.Xorshift.advance_eq_iterate` does, and `Demos.Slew.Search.loop_const` is a copy.  `Library.Numerics.Arithmetic.Uscale.UscaleTheorem.loop_inv` restates `loop_induction` with its arguments explicit, and `Library/Numerics/Arithmetic/Uscale/UscaleDiv.lean` and `Library/Numerics/Decimal/ParseFloat/ParseFloatDigits.lean` use it.

`LeanExe.loop` unfolds to `Nat.fold`, while specifications and copied implementations often fold with `Fin.foldl` or over `List.range`.  `Library.Hashing.Words.finFoldl_eq_fold` rewrites a `Fin.foldl` as `Nat.fold`, and the SHA-256 and SHA-512 compression proofs use it to match the implementation's 64-round and 80-round folds.  `Library.Hashing.XxHash64.Proof.fold_eq` rewrites `Nat.fold` as a fold over `List.range`.  For allocation bounds, `Verified.loop_push_size` gives the size of the array in the first component of a loop's state when each pass extends it by one element.

`LeanExe.repeatWhile fuel init cond step` unfolds to `LeanExe.repeatWhile.go cond step fuel.toNat init`, and induction on the natural fuel, with the index and the partial result in the hypothesis, proves its result, as `Examples.Below100.keep_go` does for a filter built by pushes.  `Examples.Increment.compute_eq` and `Examples.RemoveZero.compute_eq` prove builds equal to `Array.map` and `Array.eraseIdx!` with `Array.ext`, `LeanExe.Dialect.build_size`, and `LeanExe.Dialect.build_get`.  These proofs are in the examples' proof modules, such as `Examples/Increment/Proof.lean`, which import the program, the specification, and `LeanExe.Dialect.Lemmas`, so the theorems of the verified compilations use them.

A loop over a literal count, such as the ten passes of `Examples.Lookup.compute`, unfolds with `simp only [LeanExe.loop]`, after which `by_cases` on each pass's test closes the cases, as `Examples.Lookup.compute_eq` does.  `Examples.TreeLookup.compute_eq` states one lemma for the inner passes and one for the leaf pass and unfolds the loop with them.

An unrolled sequence of conditional steps, `let r := if k < n then step k r else r` for `k` from 0 to `K - 1`, equals a loop over `min n K` indices, and a program without a loop needs this form when a bound such as the Cortex-M7 back end's `staticCost` must exist.  `Library.Hashing.Crc.Bitwise.fold_min_succ` states `Nat.fold (min N (j + 1)) (fun i _ s => F i s) init = if j < N then F j (Nat.fold (min N j) …) else Nat.fold (min N j) …`, and `Library.Hashing.Crc.Bitwise.regIf_fold` extends the equation by one conditional step of the program.  `Library.Hashing.Crc.Bitwise.crc32Word_eq` nests eight applications of `regIf_fold` from `Nat.fold 0`, each taking the previous equation as its hypothesis, so that unification builds the program's chain.  It states the program's equality with the fold in a `have` closed by `rw [← e]; rfl`, unfolds `LeanExe.loop`, and rewrites `(min n 8).toNat` with `UInt64.toNat_min`.

A loop that writes `f i` at each index of an array with `set!` builds the array of `f` when the array has `n` elements.  `Demos.Euler.Buffered.loop_set` states `LeanExe.loop n out (fun i acc => acc.set! i.toNat (f i)) = LeanExe.build n f` under `out.size = n.toNat`, by induction on `Nat.fold` with the invariant that the size stays `n.toNat` and the first `j` entries equal `f`.  Apply it with `exact` after unfolding both definitions, as `Demos.Euler.Buffered.sweepInto_eq` does, so that unification takes `f` from the loop's body through its `let`s.  `Demos.Euler.Buffered.repeatWhile_map` maps a `LeanExe.repeatWhile` onto a second one under a projection `π`, when `π` commutes with the condition and the step at every state of an invariant that the step keeps.  The conditions and steps that a definition elaborates match on their tuples, so name them with `generalize hR : LeanExe.repeatWhile 2048 (9, dt, grid, a, b) _ _ = R`, rewrite with `← hR` before applying the lemma, and close the obligation on the conditions with `rintro ⟨_, _, _, _, _⟩ _; rfl`, as `Demos.Euler.Buffered.advanceInto_eq` does.  The bound `j < UInt64.size` that `UInt64.toNat_ofNat_of_lt'` needs closes with `omega` only after `simp only [UInt64.size]` replaces `UInt64.size` with its value.
