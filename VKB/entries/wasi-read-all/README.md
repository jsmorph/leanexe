# Programs that read their whole input

The entry applies to a WASI program that needs its whole standard input before it computes, such as a tabulator or the parser of a file, and to its process theorem under StreamFold's host assumptions.  A process that gathers its input in its state through its steps copies that state after every step, since the compiled process compacts the state between steps, so with reads of 4,096 bytes its run time grows with the square of the input.  The section "Run time" of `Demos/StreamFold/README.md` measures that growth for a long line in the running sums.

Read the input with `LeanExe.Wasi.readAll limit` in `begin`, and compute in `begin` or in a pure function that it calls, so that the steps only write.  The compiled code allocates one buffer of `limit + 4096` bytes and reads into its tail (header of `Verified/Wasi/ReadAllCode.lean`), and the command's charge is `Verified.Wasi.readAllCost limit`, a function of the limit alone, so the charge of `begin` is a closed number when the limit is a literal.  `Verified.Wasi.Resource.Returns.readAll_size` bounds the bytes returned by `limit + 4096` in the resource rules, `Verified.Wasi.Resource.PrefixBound.readAll` gives the command's prefix bound, and a test of the size against the limit in the program bounds the input of the computation by `limit`.  Under the host assumptions, `Demos.StreamFold.StreamHost.readAll` states what a run returns, `Demos.StreamFold.StreamHost.readAll_whole` gives the whole input at EOF for an input of at most `limit` bytes, and `Demos.StreamFold.StreamHost.readAll_long` gives more than `limit` bytes for a longer one, with the output unchanged in both cases.

A whole-input read defined by recursion on a fuel, or by well-founded recursion, has the same meaning, but the kernel's check of a generated `start` or `total` theorem unfolds it once per unit of the recursion and stops with `(kernel) deep recursion detected`, at a limit of 10,000 in the case that the section "Reads, writes, and exit" of `docs/verified-wasi-design.md` records.  `LeanExe.Wasi.readAll` is a `LeanExe.Wasi.Action.loop` of `limit + 2` passes, which unfolds to one node whatever the limit.  Another action that iterates a number of times that a literal fixes can meet the same failure, and the remedy of expressing the iteration with the constructor that holds it rests on this one case.

The tabulators' processes are the worked examples.  `Demos.Rcv.Process.begin_report` and `Demos.Rcv.Process.begin_long` state what the Oakland process's `begin` does on an input of at most and of more than `limit` bytes, through `Demos.Rcv.Process.beginWith_report` and `Demos.Rcv.Process.beginWith_long` for any report function, `Demos.Rcv.Process.begin_bounded` bounds its charge, and `Demos.Rcv.Process.processMemory_le` is the closed room condition.  `Demos.Rcv.Process.Compiled.target_terminates` takes the status at which `begin` stops, so that `Demos.Rcv.Process.Compiled.terminates_of_room` and `Demos.Rcv.Process.Compiled.exits_long_of_room` give both `Demos.Rcv.Process.initial_terminates` and `Demos.Rcv.Process.initial_exits_long`, neither with a memory premise.  `Demos.Rcv.Process.Compiled` bundles a compiled process whose `begin` reads in this way with the facts that those theorems take, and the Maine process applies the same theorems with its own report in `Demos.Rcv.Maine.Process.initial_terminates` and `Demos.Rcv.Maine.Process.initial_exits_long`.  `Verified.Examples.WasiReadAll.main` is a command that copies its input, with `tests/wasi/readall-run.sh` as its driver.  [The entry on WASI process totality](../wasi-process-total/README.md) gives the process theorem's premises, and [the entry on WASI effect charges](../wasi-effect-charges/README.md) the prefix bounds.
