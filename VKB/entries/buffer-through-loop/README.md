# One buffer through a loop

The entry applies when a loop reads or draws into a buffer at every pass and the program should allocate the buffer once.  A call that fills a buffer, `LeanExe.Wasi.readStdin` or a flat call such as `LeanExe.Wasi.randomGet`, takes the buffer: the compiled code moves an owned buffer whose variable dies at the call and copies it otherwise, and the result returns it.  `Verified.Wasi.wp_take_with` proves the take for both kinds of call, and `Verified.Wasi.Resource.PureContext.sysTakeCost` charges the copy and nothing for the move.

Keep the buffer in the loop's state, use it as the call's buffer as its last use in the pass, and return the result's buffer as the new state.  The frontend splits the state at the start of each step and the call's result where the step binds it, so the state's buffer is an owned variable that dies at the call, and `sysTakeCost` reduces to 0 under `Verified.Wasi.sysTakeLive` of the step's liveness.  A write before the call borrows the buffer and charges nothing.  `Verified.Examples.WasiRetain.retain` writes its state's buffer and reads into it at each pass, and the private lemmas of `Verified/Examples/WasiRetainBudget.lean` bound the loop by the buffer's 56 bytes for any number of passes.  State the step's bound for the liveness `shift 2 outer`, the form that `Verified.Wasi.Resource.ResourceLoopExec` gives the step, since the take's charge depends on whether the state stays live after the step, and the loop's state never does.

A use of the buffer after the call, or a buffer that the step borrows, copies the buffer at the call.  A process step borrows its state, so a process cannot carry a buffer from one step to the next this way: its read step builds a buffer, and the process entry's compaction copies the whole state after each step, so a state that keeps the read's whole buffer copies all of it at every step.
