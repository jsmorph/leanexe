# Line-oriented WASI processes

`Demos.StreamFold` holds a WASI process that reads its input in chunks, splits it into lines, and applies a line kernel to each line, together with the proofs about it.  A program that reads lines and writes output for each line can instantiate it with a kernel and take termination, the output, and the exit status from the shared proofs.  The integer and binary64 running sums are its applications.  A program that needs all of its input before it writes reads it in one call instead, as [the entry on programs that read their whole input](../wasi-read-all/README.md) describes.

A kernel `Demos.StreamFold.Kernel Acc` maps an accumulator and a line to a validity bit, the next accumulator, and the bytes to write.  `KernelSpec` gives an invariant `Good` of the accumulator and a size condition `Room` for a line, and it requires that an accepted line keep `Good` and produce nonempty output.  `process kernel seed` is the process.  `initial_terminates_output` states that, from the initial state, it returns the status of `Model.foldOutcome kernel seed (Model.lines input)` after writing the outputs of the same fold, under `StreamHost` and `Demos.StreamFold.Model.LineRooms`, and `process_exec_correct` and `process_terminates` give the same for any state that satisfies the stream invariant.

An application states its own specification with `Model.LineValues Denotes lines values status`, where `values` holds the values of the lines before the first line without a value and `status` is 0 or 28.  It proves that `foldOutcome` of its kernel matches `LineValues` for its predicate, and `Demos.StreamFold.Model.LineValues.unique` then shows that a functional predicate determines both the values and the status.  An application states its own process and relates it to `process` by `LeanExe.Wasi.Process.Rel` in its stream view, and `repeatWhile_map` maps its loop onto the shared one.

The allocation charges of [the entry on WASI effect charges](../wasi-effect-charges/README.md) need bounds on the sizes of the buffers.  `Demos.StreamFold.step_within` keeps the input buffer within one read and the output buffer within a bound on the kernel's output whatever the host replies, and `Demos.StreamFold.Model.pending_le` and `Demos.StreamFold.StreamFuture.line_le` bound the pending line by any line length that `Room` implies, since the pending line is a prefix of a line whose `Room` holds.  The theorems cover successful transfers, and an I/O error stops the process with its errno, which the application drivers test.

The termination modules of `Demos/RunningSum` and `Demos/RunningSumFp`, `Demos/RunningSum/Termination.lean`, `Demos/RunningSum/TerminationTyped.lean`, and `Demos/RunningSum/TerminationTarget.lean` and their namesakes, differ in their imports, namespaces, and initial states, and `Demos/RunningSumFp/TerminationTyped.lean` adds `Demos.RunningSumFp.Termination.true_advances`.  `Demos/RunningSum/Termination.lean` imports `Demos.StreamFold.Host` and restates StreamFold's `Safe`, `Rank`, and progress conditions for the application's own state, as `Demos.RunningSum.Termination.Safe` does through `bufferState`, so a further application should move those proofs into StreamFold rather than copy them again.  `Demos/RunningSum/TerminationTarget.lean` holds `target_terminates`, which applies `Verified.Wasi.compiled_process_total_run` to the step's invariant and charges and names no StreamFold declaration directly.  `Demos/OrderBook/ProcessTermination.lean` repeats its text, apart from the initial state, for the order book's process, which takes StreamFold's host assumptions and `StreamProgress` but defines its own `Safe` and `Rank`.  The two copies therefore resolve the same text to different definitions, and a lemma that replaces both must take the state's safety predicate, its rank, and the process as parameters.
