# Changes that keep statements and bytes

The entry applies when a shared definition must grow to serve a new case: the verified compiler, a back end's generator or initialization, a predicate that theorems state, or the premises of a general theorem.  Every board, Image, and Isla theorem and every emitted module and image may depend on such a definition, and a change that alters their statements or their bytes requires each of them to be checked and run again, many by drivers that the full check does not run ([the entry on theorems outside the full check](../out-of-build-checks/README.md)).  Shape the change so that existing theorems keep their statements and existing artifacts keep their bytes, and then show that they did.

Add the new case beside the old one, by means that keep the old values as instances.  An argument with a default keeps the existing calls: `LeanExe.A64.program_runs` takes the parameter types `ts` with the default `args.map fun _ => .i64` and the premise on `LeanExe.A64.entryOk` with the default `by decide +kernel`, and `Verified.compileWith` takes its literal pool and its least number of pages with defaults.  A list whose old value stays an instance keeps the old images: `LeanExe.M7.Nucleo.init` is `initConfig ++ [.write usartCr1 0xD]`, and `LeanExe.M7.Nucleo.initOvrdis`, which also disables USART3's overrun detection, is `initConfig ++ [.write usartCr3 0x1000, .write usartCr1 0xD]` beside it, with `LeanExe.M7.Nucleo.initConfig` the accesses that both share.  A generator whose old form is an instance of a general one keeps the old images in the same way: `LeanExe.A64.genProgram` and `LeanExe.A64.genImage` are `LeanExe.A64.genProgramWith` and `LeanExe.A64.genImageWith` with the entry routine of fixed arguments, `LeanExe.A64.genMain`, and `LeanExe.A64.genInProgram` and `LeanExe.A64.genInImage` give them the routine that reads the UART.  A generator that must emit a form for values that its encoding cannot hold keeps the old code where the value fits and emits an alternative of the same length elsewhere, so that the size of every function, the layout of every image, and the bytes of every existing image stay as they are: for a cap below 4,096 pages, `LeanExe.A64.growNarrow` compares the new page count of `memory.grow` with the cap as the 12-bit immediate of `SUBS`, and for a larger cap `LeanExe.A64.growWide` compares sizes with the cap built in a register, in the same 16 instructions, so that `LeanExe.A64.instrSize` does not depend on the cap (header of `LeanExe/A64/Gen.lean`).  `LeanExe.A64.gen_memoryGrow` states the two codes as a disjunction, and `LeanExe.A64.run_grow` gives the run of either, so `LeanExe.A64.sim_memoryGrow` rests on one lemma for both.  The frames of `LeanExe.A64.genFunction` follow the same rule.  The model's `SUB` and `ADD` of SP take an unshifted immediate below 4096, so a frame of 4,096 bytes or more takes a list of `SUB`s, whose immediates `LeanExe.A64.frameSteps` gives, and the same `ADD`s at the return, which `LeanExe.A64.run_sp_down` and `LeanExe.A64.run_sp_up` follow by induction on the list.  The stack check of such a frame, `LeanExe.A64.stackCmp`, compares the bytes from the stack's limit up to SP, divided by 16, with the frame divided by 16 (`LeanExe.A64.run_check_wide`), since SP less the frame wraps when SP lies below the frame, which `LeanExe.A64.StackOk` admits.  A frame below 4,096 bytes keeps the check `SUB X16, SP, #fs` and `CMP X16, X18` and one `SUB` of SP, which `LeanExe.A64.gen_function_small` states, and `LeanExe.A64.run_frame` and `LeanExe.A64.run_epilogue` keep their statements as instances of `LeanExe.A64.run_frame_steps` and `LeanExe.A64.run_epilogue_steps` at one step.  `LeanExe.A64.genProgramWith` refuses a function whose frame reaches 4,096 bytes (`LeanExe.A64.framesSmall`, `LeanExe.A64.genProgramWith_frames`), since `LeanExe.A64.programWith_sim` and the theorems built on it state that a function without calls never overflows a stack's room of 4,096 bytes, so their statements stay as they were, while `LeanExe.A64.genWasiProgram` takes the large frames.  A field that moves into a substructure keeps the statements that read it when a definition with the field's name reads it there: `LeanExe.A64.State.out` is `s.io.out`, and a statement that writes `s.out` applies the constant `LeanExe.A64.State.out` to the state whether that constant is a projection or a definition, so its type and hash stay the same.  A general theorem whose old names are instances keeps the old statements: `LeanExe.M7.Nucleo.boardWith_run` takes the initialization as a list, and `LeanExe.M7.Nucleo.board_run` is its instance for `init`, as [the entry on Cortex-M7 board theorems](../m7-board-theorem/README.md) describes.  The definitions of the A64 simulation have general forms over `LeanExe.A64.Machine` that equal, imply, or are equivalent to the old definitions at `LeanExe.A64.bare`, and the old theorems follow from the general ones with their statements kept, as [the entry on simulations over a machine](../simulation-over-a-machine/README.md) describes.  A predicate beside the old one keeps the theorems that need nothing new: `LeanExe.A64.Isla.AgreesAll` takes the meanings of a trace's abstract functions and lets the trace's paths end with different registers outside the model, while a form whose trace has one outcome and no abstract call keeps `LeanExe.A64.Isla.Agrees`.

An effect that the machine model lacks enters beside the model's step when the effect's instruction word decodes to nothing.  `LeanExe.A64.pstep` takes one step of a Linux process, `LeanExe.A64.Proc`, which holds the program's state with the value of FPCR and the trace of the process's system calls: at the word of `SVC #0`, which `LeanExe.A64.decode` rejects (`LeanExe.A64.decode_svcWord`), it applies `LeanExe.A64.Kernel.svc`, at `MSR FPCR, Xt`, whose `exec` fails, it sets the process's FPCR, and at every other word it runs `LeanExe.A64.exec`, a floating-point form only while FPCR holds `LeanExe.A64.fpcrValue`, and only when the next program counter lies below 2^55.  `LeanExe.A64.ProcReach.of_reach'` lifts a run of `LeanExe.A64.step` into a run of the process when the code map holds words only below 2^55, the run ends below 2^55, and the process's FPCR holds `fpcrValue`.  Each step of the lift needs the bound on its next program counter, which a run of `step` does not state: `LeanExe.A64.Reach.start` gives it for every state of the run but the last, each of which fetched a word from the code map, and the premise on the run's end gives it for the last.  `LeanExe.A64.Instr`, `decode`, `exec`, and `step` stay as they are, while a constructor of `Instr` for `SVC` would change `LeanExe.A64.decodeNat`, `exec`, the type's recursor, and every proof that cases on an instruction.

A second rule for a word that an existing step already runs enters as a second step relation beside the first.  A rule for every Linux call inside `LeanExe.A64.Kernel.svc` would keep the flip executable's theorems true and remove a consequence of them: that a run of `LeanExe.A64.ProcReach` makes only reads of descriptor 0 and writes of descriptor 1.  `LeanExe.A64.pstepWith` therefore takes `SVC #0` through the Linux call layer beside `pstep`, never applies `LeanExe.A64.Kernel.svc`, and ends the run at a call outside its table, so a theorem over `LeanExe.A64.ProcReachWith` names the calls that its run may make.  The steps that the two relations share, at every word but `SVC #0`, form a third definition, `LeanExe.A64.istep`, beside `pstep`, whose text stays as it was.  `LeanExe.A64.pstep_eq_istep` and `LeanExe.A64.pstepWith_istep` relate both steps to it, and `LeanExe.A64.IReach.toProcReach` and `LeanExe.A64.IReach.toWith` lift its runs, so a lemma about the runtime's instructions serves both relations.  Restating `pstep` as `istep` with a case for `SVC #0` would keep its meaning and change its value hash, after which a comparison of hashes could no longer show that the statements that name it kept their meaning.

`LeanExe.A64.Event`, the event type of the flip executable's statements, has a constructor for the layer's events, `LeanExe.A64.Event.sys`, beside those that `LeanExe.A64.Kernel.svc` produces.  A constructor added to an inductive type changes the types of the type's recursor, `recOn`, and `casesOn`, the values of the auxiliary declarations that Lean generates from them, such as the `_sparseCasesOn_1` through which Lean defines the matcher of a `match` with a wildcard, and the matcher of a `match` that lists every constructor.  A written function whose `match` reaches the new constructor through a wildcard, as `LeanExe.A64.Event.inBytes` and `LeanExe.A64.Event.outBytes` do, keeps its matcher's hashes and its own, and so does every statement that names it, while a `match` that lists every constructor no longer covers the type and needs a new case.  Statements over the relation without the new rule keep their meaning when no step of that relation produces the new constructor, as `LeanExe.A64.Kernel.svc` produces none, and every function of the statements maps it to nothing, as `inBytes` and `outBytes` map it to `[]`.  A theorem over the relation with the new rule states the converse: `LeanExe.A64.ProcReachWith.trace_sys`, by induction on the relation, states that a run from a trace of the layer's events appends only such events, and `LeanExe.A64.stamp_bytes_run_any` concludes that the final trace is `(sysEvents p'.trace).map Event.sys`.

A WebAssembly module numbers its imported functions before its defined ones, so an import added to a module moves the index of every defined function and changes every definition and statement that holds the old number of imports.  The WASI compiler keeps its statements by giving each layout definition a form over the list of imported flat calls and defining the old name as that form at `[]`: `Verified.Wasi.Relocation.program` is `programWith []`, `Verified.Wasi.compile` is `compileCalls []`, and `Verified.Wasi.hostSpecWith_nil` states that `hostSpecWith host []` is `hostSpec host`.  Each theorem about an old form takes its proof from a general twin with the suffix `_with`: the tactic `layout_instance` of `Verified/Wasi/Relocation.lean` applies the twin at `(calls := [])` and closes its premises by assumption or by a conversion such as `Verified.Wasi.Relocation.Layout.toWith`, and a later file adds its conversions to the tactics `layout_convert` and `layout_back` with further `macro_rules`, as `Verified/Wasi/CompilerFacts.lean` adds `Verified.Wasi.CompilerFacts.toWith`.  A condition that the general form needs joins a premise that the existing lemmas already pass along, at the cost of one projection at each use: `Verified.Wasi.Command.ReadyWith` holds `command.callsReady calls = true` beside the old conditions of readiness, and `Verified.Wasi.Command.Ready` is `ReadyWith []`.  A new premise of a predicate such as `Verified.Wasi.CommandCodeSpecWith` would leave every theorem that proves the predicate provable at the old instance and break every lemma that takes the predicate as a hypothesis, such as a loop body's specification, which has no source for the new premise.  The general form at `[]` has the old meaning but another type, since its statement names `compileCalls []` and `hostSpecWith host []`, so the frontend applies the general forms only to a program whose source holds a `Verified.Wasi.Command.sys` (`Verified.Wasi.Reflect.ProgramReflection.usesCalls`), and every other program keeps the generated theorems that it had.  The frontend assigns the binders of the theorems that it specializes by name, so the general forms name the list of calls `calls` and the old correctness argument `effectCalls`.

A definition that gains an argument list, such as the input variables and then the buffers of a `sys` command, keeps the old statements in the same way when its general form, at the empty list, takes the old definition's branch for every argument, including the arguments that the list would serve.  `Verified.Wasi.flatArgsWith` gives an `input` parameter no argument when no input is left, as `Verified.Wasi.flatArgs` gives it none, and `Verified.Wasi.flatCapacityWith` consumes a word at such a parameter, as `Verified.Wasi.flatCapacity` does, so `Verified.Wasi.flatArgsWith_nil` and `Verified.Wasi.flatCapacityWith_nil` hold for every parameter list by induction.  A charge that the general form extends puts the new part last: the charge of a `sys` command is `Verified.Wasi.sysCost form call trace` plus `Verified.Wasi.Resource.PureContext.sysTakeCost`, the charge of the take of its buffer, which is 0 at the empty list of buffers by its `match`.  `Verified.Wasi.wp_sys_plain_with` states that equation by `rfl`, rewrites with it and `Nat.add_zero`, and then applies `Verified.Wasi.wp_sys_released_with`, whose charge is `sysCost` alone.  A disjunction that the general form extends puts the new part first: `Verified.Wasi.Command.uses` of a `sys` command is `(buffers.any …) || ((inputs.any …) || args.any …)`, and at the empty list `[].any` reduces to `false` and `false || b` to `b`, so the general form is definitionally the old value.  The live set `fun i => (inputs.any …) || live i` that `Verified.Wasi.wp_sys_result_with` keeps after the command is in the same way definitionally `live` at the empty list.

A theorem that carries one checked case to the others removes repeated checks.  `LeanExe.A64.genImage_shift` states that the image that `LeanExe.A64.genImage` writes at `image + d`, for `d` a multiple of 4096 with both images in the RAM GiB, has the bytes of the image at `image` and its layout shifted by `d`, and `LeanExe.A64.bytesOk_shift` carries the kernel's check of a file at one address to every such address.  A change that moves an Image's load address within those conditions therefore keeps the file and its check.

Show that the change kept them.  Write every module and image from a baseline tree before the change and from the changed tree, and compare the bytes: `tests/verified/run.sh --check-bytes DIRECTORY` compares the emitted modules with saved reference modules ([the manual's section on types](../../../docs/verified-manual.md#types)), and the images that `a64-images.sh`, `m7-image.sh`, `m7-board.sh check`, and `m7-qemu.sh` write compare as files.  Compare the statement of each theorem that the changed definitions reach in the two trees after normalizing whitespace, and run the drivers of the file modules again, since they read the changed definitions.  For a change meant to alter code, show where the bytes differ, for a module by a comparison of the texts that `wasm-tools print` gives for the two trees, so that each difference lies at a changed form.  For bounds, evaluate each bound before and after the change, since a theorem that states an upper bound stays true when the bound rises.  A change that only reformats source, such as rewrapping its lines, keeps the type and the value of every constant, which hashes of both in the two trees show: `tools/sail/ConstDump.lean` writes the name and the two hashes of each constant of a Sail translation, and the dumps of two builds compare line by line after sorting.  Its selection of constants by a component of their names serves the translations, and `tools/DeclHashes.lean` writes the same hashes for every constant that each named module declares, which serves any built module.  The output of `tools/DeclHashes.lean` for the modules that a change reaches, written before and after the change, shows by equal type hashes that their statements stayed the same and by equal value hashes that their proof terms did, up to collisions of the hash.  `tools/DeclHashes.lean` imports the named modules into one environment, and the import fails when two of them declare a root `main`, as `Demos/OrderBook/ProcessNative.lean` and `Demos/Rcv/ProcessNative.lean` do, so each such module runs in a call of its own.  Lean reuses a matcher that the module already holds when it elaborates a `match` of the same shape (`Lean.Meta.Match.mkMatcherAuxDefinition`), so an old theorem whose statement holds a `match`, elaborated after a general twin with the same `match`, names the twin's matcher, and its type hash changes although its text did not.  Declaring the old theorem first, or moving the `match` into a definition that both statements use, as `Verified.Wasi.Wrappers.outputPosition` does, keeps the hash.  The auxiliary declarations that elaboration generates, such as matchers and the proofs that it abstracts, change their names and number with the source, and `tools/DeclHashes.lean` prints them with the rest, so the reader of the two outputs sets aside the names whose last component has a form such as `match_1`, `_sparseCasesOn_1`, or `proof_1` and compares every written declaration.

A comparison of statements alone misses a change of a definition that the statements name: `LeanExe.M7.Nucleo.board_run` names `init`, so a write added to the definition of `init` would keep its statement and change every board image's bytes and the initialization's trace.  A passing build shows that the theorems hold and says nothing about whether their statements, the artifacts, or the bounds changed.  The comparison of bytes covers what the comparison of statements misses, so the two run together.

The worked examples are `TestSupport.M7.Sha.sha_loop`, which applies `LeanExe.M7.Nucleo.areaBoard_run` with `init`, and `TestSupport.M7.Sha.shaOvrdis_loop`, which applies `LeanExe.M7.Nucleo.areaBoardWith_run` with `initOvrdis` to the same step, so that `sha.bin` and `sha-ovrdis.bin` both have board theorems.  `LeanExe/A64/Proof/ImageTheorem.lean` applies `bytesOk_shift` to an Image's check.  `LeanExe.A64.sysProgram_run` of `LeanExe/A64/Proof/LinuxProgram.lean` lifts the runs of the program's code into the process with `LeanExe.A64.ProcReach.of_reach'`, and `Verified.Wasi.compile_entry_export` takes its proof from `Verified.Wasi.compile_entry_export_with` by `layout_instance`.  [The entry on image files](../image-file-checks/README.md) describes the kernel's checks of the files, which the drivers repeat on every run whether or not the bytes changed.
