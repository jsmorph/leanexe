# A proof about a value that a later argument fixes

A lemma may take a proof about a value that only a later argument determines, such as a proof about the program's tables when only the readiness hypothesis names them.  Lean elaborates the arguments of an application in order, so it elaborates the proof while the value is still a metavariable.  A term such as `List.mem_singleton.mp ht` then fails to unify with `tableAddr ?tables 0`, and the error has the form `Application type mismatch … expected to have type x ∈ [(tableAddr ?m 0, ?m[0])]`.

Make the value an explicit argument placed before the proof, as `Verified.ImplementsTables.call` takes `tables` before the proof that the entry's tables are among the program's.  A proof stated once as a named lemma at the concrete value avoids the problem as well, as `Library.Hashing.Crc.crc32c_table` does, and `Verified.tables_at` states the fact for a list of table indices.  A tactic block also elaborates, because Lean postpones it to the end of the application, but the explicit argument keeps the call readable and the error local.

The first form of the generic call theorem took the tables from the readiness hypothesis, after the table proof, and every call site failed in this way until the order changed.  `Library.Hashing.Sha256.sha256_call` passes `compiled.tables` and then `fun _ ht => ⟨0, by decide, List.mem_singleton.mp ht⟩`, and `Library.Numerics.Float64.Bessel.BesselBytes.y0_entry_call` passes `Verified.tables_at [0, 1, 4, 5, 2] (by decide) rfl`.  The `rfl` evaluates the sizes of the tables before the last index, so a declaration that uses it beyond the first table raises `maxRecDepth`, as the Bessel entries do.
