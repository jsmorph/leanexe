# Rounding-error bounds for binary64 code

A numerical program's safety or accuracy theorem compares the floats it computes with real formulas.  The comparison needs, for each value, a bound on the distance between the float and the real number it stands for, carried through a chain of rounded operations.  `LeanExe.ProofKit.F64Approx` supplies that bookkeeping, and the slew planner's edge-check, safety, and NaN-freedom proofs and many proofs of the numerical library build on it.

`LeanExe.ProofKit.F64Approx.Approx w v e` states that the word `w` is finite and lies within `e` of the real number `v`, and `FApprox x v e` states the same of a Lean `Float`.  `fapprox_add`, `fapprox_sub`, `fapprox_mul`, `fapprox_div`, `fapprox_sqrt`, and `fapprox_neg` carry it through one operation: the result approximates the exact operation on the reals, with the input errors propagated and the rounding error added.  Each rule asks for magnitude bounds, such as `|va + vb| + (ea + eb) ≤ B` with `B < 2 ^ 1023` for an addition or a lower bound `mb ≤ |vb|` above the divisor's error for a division, and the caller discharges them with `norm_num` or `linarith`.  `fapprox_ofBits` starts a chain at a finite constant, `Approx.mono` weakens an error, and `within_one_of_error` turns a total error below one and a half spacings of a binade into one representable step of the nearest-even reference.

For a long chain, wrap the bounds in a structure whose numbers stay numerals.  `Demos.Slew.Rounding.Bnd x X e M` holds `FApprox x X e` and `|X| ≤ M`, and `Bnd.add`, `Bnd.sub`, `Bnd.mul`, and `Bnd.neg` produce the next bound, so that `norm_num` checks each constant.  `LeanExe.ProofKit.F64Approx.SApprox` does the same at a scale `s ≤ 1`, so that `M` and `e` stay numerals while the scale carries the size of the input.  The slew planner bounds its rounding errors against the program's own formulas evaluated exactly on the given inputs and adds the error of normalizing those inputs only at the end, which kept the errors at its stationary-point tests below their tolerance.

The rules need finite operands, while a program often tests finiteness late or not at all.  `Demos.Slew.Valid.finite_of_add`, `finite_of_sub`, and `finite_of_mul` show that a finite result of an addition, a subtraction, or a multiplication has finite operands, and `fin_add`, `fin_sub`, and `fin_mul` state the same for `Float`.  `lower_of_enclosure` bounds a finite rounded result from below by any nonnegative float below the exact value, which shows, for example, that a norm test fails when a component exceeds its limit.  These lemmas hold for any program, although they live in the slew planner's namespace.

For finite operands, Lean's comparisons, `min`, and `max` follow the reals, as `Demos.Slew.Rounding.le_iff_val`, `lt_iff_val`, `min_val`, and `max_val` state.  `max a b` is `if a ≤ b then b else a`, so it returns `a` when `b` is a NaN, and a test written with `max` can drop a NaN without failing.  Write each acceptance test so that a false comparison rejects, and derive the finiteness of every value that a test reads from the error bounds, as `Demos.Slew.Check.edgeOk_sound` does.  `Demos.Slew.NanFree.plan_finite` then states that every float the planner binds is finite for every validated input, and `Demos.Slew.Safety.plan_safe` uses the same bounds for the safety of whole plans.
