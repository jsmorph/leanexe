# Rounding-error bounds for binary64 code

A numerical program's safety or accuracy theorem compares the floats it computes with real formulas.  The comparison needs, for each value, a bound on the distance between the float and the real number it represents, kept through a chain of rounded operations.  `LeanExe.ProofKit.F64Approx` supplies the definitions and rules for those bounds, and the slew planner's edge-check, safety, and NaN-freedom proofs and many proofs of the numerical library use it.

`LeanExe.ProofKit.F64Approx.Approx w v e` states that the word `w` is finite and lies within `e` of the real number `v`, and `FApprox x v e` states the same of a Lean `Float`.  `fapprox_add`, `fapprox_sub`, `fapprox_mul`, `fapprox_div`, `fapprox_sqrt`, and `fapprox_neg` propagate it through one operation: the result approximates the exact operation on the reals, with the input errors propagated and the rounding error added.  Each rule requires magnitude bounds, such as `|va + vb| + (ea + eb) ≤ B` with `B < 2 ^ 1023` for an addition or a lower bound `mb ≤ |vb|` above the divisor's error for a division, and the caller discharges them with `norm_num` or `linarith`.  `fapprox_ofBits` starts a chain at a finite constant, `LeanExe.ProofKit.F64Approx.Approx.mono` weakens an error, and `within_one_of_error` turns a total error below one and a half spacings of a binade into one representable step of the nearest-even reference.  [The entry on accuracy against real functions](../real-function-accuracy/README.md) gives the other criteria that turn an error into steps and the transfer of an accuracy theorem to a compiled module.

For a long chain, wrap the bounds in a structure whose numbers stay numerals.  `Demos.Slew.Rounding.Bnd x X e M` holds `FApprox x X e` and `|X| ≤ M`, and `Demos.Slew.Rounding.Bnd.add`, `Demos.Slew.Rounding.Bnd.sub`, `Demos.Slew.Rounding.Bnd.mul`, and `Demos.Slew.Rounding.Bnd.neg` produce the next bound, so that `norm_num` checks each constant.  `LeanExe.ProofKit.F64Approx.SApprox` does the same at a scale `s ≤ 1`, so that `M` and `e` stay numerals while the scale holds the size of the input.  The slew planner bounds its rounding errors against the program's own formulas evaluated exactly on the given inputs and adds the error of normalizing those inputs only at the end, which keeps the errors at its stationary-point tests below their tolerance.

A correctly rounded operation enters a chain through its nearest property.  `Library.Numerics.Arithmetic.Fma.FmaSpec.FmaNearest` states that the software fused multiply-add returns a finite word no farther from the exact `a · b + c` than any finite word, for finite operands and `|a · b + c| ≤ 2 ^ 1023`, and [the entry on correct rounding](../correct-rounding/README.md) describes its proof.  The proofs of erfc, tgamma, and lgamma take it as a hypothesis, and `LeanExe.ProofKit.F64NearReal.nearest_bound` converts it into the error `|S| / 2 ^ 53 + 2 ^ -1075` for `|S| ≤ 2 ^ 1000`.  `Library.Numerics.Float64.Tgamma.TgammaDD.fma_approx` states that error as an `FApprox` for the gamma and log-gamma proofs, while `Library.Numerics.Float64.Erfc.ErfcOps.fma_f` repeats the conversion through its own `Library.Numerics.Float64.Erfc.ErfcOps.nearest_err`, and `Library.Numerics.Float64.Erfc.ErfcTrack.tr_fma` carries it into erfc's bounds `Tr`.

An enclosure replaces an approximation when a program must bound a real quantity from one side.  `LeanExe.ProofKit.F64Outward.add` and its siblings for subtraction, multiplication, division, and square root move the rounded result one step outward with `nextUp` or `nextDown`, and they reject with status 1 a non-finite operand or result, a zero divisor, and a negative operand of the square root.  `LeanExe.ProofKit.F64Outward.add_accepted` states that an accepted result is finite and bounds the exact operation from the chosen side (`LeanExe.ProofKit.F64Outward.Sound`), with no premise on magnitudes, since the program tests the status when it runs.  `Library.Numerics.Bounds.outAdd_word` equates the library's operation on `Float` with the operation on words, `Library.Numerics.Bounds.outAdd_accepted` transfers the result, and the Euler solver's bounds on kinetic energy and wave speed use them (`Demos.Euler.kineticLower_le`, `Demos.Euler.speedUpper_ge`).

An operation that selects an operand or a sign adds no rounding error.  The minmod limiter on `Float` returns the operand of smaller magnitude when the signs agree and 0 otherwise, and `Library.Numerics.Limiters.Minmod.real_minmod` proves that its value is the real minmod of its inputs' values.  The program compares magnitudes through the encodings with the sign bit cleared, which `LeanExe.ProofKit.F64Order.abs_value_mono` relates to the magnitudes of the values.

The rules need finite operands, while a program often tests finiteness late or not at all.  `Demos.Slew.Valid.finite_of_add`, `finite_of_sub`, and `finite_of_mul` show that a finite result of an addition, a subtraction, or a multiplication has finite operands, and `fin_add`, `fin_sub`, and `fin_mul` state the same for `Float`.  `lower_of_enclosure` bounds a finite rounded result from below by any nonnegative float below the exact value, which shows, for example, that a norm test fails when a component exceeds its limit.  These lemmas hold for any program, although they are declared in the slew planner's namespace.

For finite operands, Lean's comparisons, `min`, and `max` agree with the reals, as `Demos.Slew.Rounding.le_iff_val`, `lt_iff_val`, `min_val`, and `max_val` state.  `max a b` is `if a ≤ b then b else a`, so it returns `a` when `b` is a NaN, and a test written with `max` can drop a NaN without failing.  Write each acceptance test so that a false comparison rejects, and derive the finiteness of every value that a test reads from the error bounds, as `Demos.Slew.Check.edgeOk_sound` does.  `Demos.Slew.NanFree.plan_finite` then states that every float the planner binds is finite for every validated input, and `Demos.Slew.Safety.plan_safe` uses the same bounds for the safety of whole plans.
