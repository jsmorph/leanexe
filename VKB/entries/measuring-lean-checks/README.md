# Measuring Lean checks

The entry applies when the time or memory of a Lean check decides a limit, a split, or a choice between two forms: a kernel check that may exceed a driver's cap, a module that stops at the runner's limits, or a change whose cost must be compared with that of the code it replaces.  The elapsed time of a check depends on its CPU quota and on the load of the host, and its peak memory on the number of threads that elaborate at once, so a figure can be compared with another only when it states the quota, the thread count, the memory limits, and the host of its run.  A declaration's own cost comes only from a run that elaborates that declaration alone or one declaration at a time.

Run the check through `tools/leanrun`, whose memory and swap limits apply to the whole job, so that its threads share one `MemoryHigh` ([the repository instructions on Lean process limits](../../../AGENTS.md#lean-process-limits)).  The image drivers `tests/baremetal/m7-board.sh`, `tests/baremetal/m7-qemu.sh`, and `tests/baremetal/m7-image.sh` run `tools/leanrun` under GNU `/usr/bin/time -v` and print the elapsed time and the maximum resident set size, and `tools/sail/run.sh` does the same for the Sail proofs.  That maximum is the resident set of the job's largest process ([getrusage(2)](https://man7.org/linux/man-pages/man2/getrusage.2.html)), which measures a job of one `lean` process and understates a build whose workers run at the same time.  The file `memory.peak` of the job's cgroup holds the largest memory use recorded for the cgroup and its descendants, which covers every process of the job ([the kernel's documentation of the cgroup v2 memory interface](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files)).  `tools/leanrun` reports no peak and runs the job in a transient scope that ends with it, so a job that needs the cgroup's figure reads `memory.peak` before it exits, in the directory under `/sys/fs/cgroup` that `/proc/self/cgroup` names, where `tools/leanrun` reads the scope's limits.  A reading sampled during the run, such as `memory.current` or a resident set from `ps`, misses the peaks between samples and gives a lower bound.  The section "The Isla check" of `docs/m7-bare-metal.md` gives each module's elapsed time and peak memory together with the runs' quota and cap, 4 CPUs under an 8 GiB cap.

Locate a cost in one declaration before changing code.  A probe file that imports what the module imports and holds one declaration, run alone under a short timeout, measures that declaration.  `set_option Elab.async false` at the head of a module makes its declarations elaborate one after another, so that the module's peak is that of its costliest declaration, as `tests/TestSupport/A64/Isla/Ldr.lean` and `Library/Numerics/Float64/Log2/Log2Power.lean` use it ([the entry on instruction forms against Isla](../isla-form-proofs/README.md) and [the entry on kernel checks over ℚ](../kernel-rational-checks/README.md)).  Mathlib's `#count_heartbeats in`, in `Mathlib/Util/CountHeartbeats.lean`, prints the heartbeats of the command that follows it, which it reads from `IO.getNumHeartbeats`, the count of small allocations of the current thread.  `lean` on the command line elaborates asynchronously, on several threads where possible (the description of the option in Lean's `Lean/CoreM.lean`), so the command form can miss work that runs on another thread, and a count of a theorem's proof runs under `set_option Elab.async false`, which the same file's `guard_min_heartbeats` and the tactic form of `#count_heartbeats` also set.  `set_option debug.skipKernelTC true` separates the kernel's share: a declaration that passes quickly with it spends its time or memory in the kernel's check, and [the entry on kernel evaluation costs](../kernel-evaluation-costs/README.md) gives the steps that locate the comparison responsible.  The option serves diagnosis only, since the declaration that it admits has had no kernel check.

Lean's profiler and diagnostics name the costly work.  `set_option trace.profiler true` with a threshold in milliseconds in `trace.profiler.threshold`, under `set_option Elab.async false` so that kernel checks run inside their commands, prints each kernel check above the threshold as a `Kernel` node that names the declarations it checks (`Lean/AddDecl.lean` in the toolchain's sources) and each tactic step above it, and `lake env lean -Dtrace.profiler=true FILE` sets the option for a whole file.  `set_option profiler true` reports the time of each profiled operation above `profiler.threshold` when the operation finishes, and the totals by category, such as tactic execution and type checking, at the end, so an operation that a timeout stops reports nothing.  A probe that a timeout may stop therefore appends a line to a file before and after each theorem, with `IO.FS.withFile` in an `#eval`, and the last line names the theorem that was running.  `set_option diagnostics true` with `diagnostics.threshold` lists the declarations that the elaborator and the kernel unfolded more often than the threshold (`Lean/Meta/Diagnostics.lean` in the toolchain's sources), and the resident set of one process counts the mapped `.olean` files of its imports, so a monitor of one process reads `RssAnon` in its `/proc/PID/status`.  [The entry on diagnosing slow checks](../slow-check-diagnosis/README.md) orders these measurements into the steps that find a slow check's cause.

Compare a change with its baseline on one host, with the same toolchain, quota, threads, and limits, in runs that alternate between the two trees, so that the load of other jobs and the host's memory pressure fall on both alike.  A peak at the job's `MemoryHigh` does not measure the job's need, because the kernel throttles a cgroup whose use goes over that limit and puts it under heavy reclaim (the kernel's documentation of `memory.high`, on the page cited above).  The section "The full check" of `docs/verified-manual.md` records such a case: `Demos/OrderBook/ProcessCharges.lean` at one thread completes under a limit of 10G while the kernel throttles it, in 201 seconds with a peak of 10.4 GiB on an 8-CPU x86-64 host, and a limit of 16G or more avoids the throttling.  A bisection by truncated proofs or by `sorry` can drop the costly step from the proof term and measure a different proof, as the entry on kernel evaluation costs describes.

The worked examples are the drivers' reports and the documents' tables.  The section "The images and their kernel checks" of `docs/m7-bare-metal.md` gives the time and peak of each M7 image's kernel check, which `m7-board.sh`, `m7-qemu.sh`, and `m7-image.sh` print from GNU `time`, and its section "Running the tests" gives the cap of each driver.  [The Sail README's section on the check](../../../tools/sail/README.md#the-check) gives the runs of the Sail proofs with their CPU quotas, and [the entry on image files](../image-file-checks/README.md) gives the caps under which the kernel checks of images run.
