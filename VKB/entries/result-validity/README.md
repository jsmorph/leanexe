# Results that show a check passed

The entry applies when a build, a driver, or the full check reports a result, and the result decides whether a theorem is accepted, a change is merged, or an earlier run is reused.  A report shows that a check passed only when it is the check's own output, from the run in question, on a tree known to hold the commit under review.  A stale output file, a status that no one tested, a line from another build, or a tree that differs from the commit each gives a pass for a check that did not run or did not succeed.

Take the verdict from the check's own output and from the tree that it ran on.  The full check writes its record, STATUS.md at the root, with the checked commit, the paths that differ from it, the toolchain, the platform, and each step's status (the header of `tools/full-check` and [the manual's section on the full check](../../../docs/verified-manual.md#the-full-check)), so the record shows whether the tree held the commit.  A checkout copied to another host is known to hold the commit after a comparison of its files with the commit's, and a report that a copy matches a branch without that comparison shows nothing.

Count a theorem's own axiom report, from a build that completed.  [The repository instructions](../../../AGENTS.md#proof-iteration) accept a theorem only after the full build of its target completes, its diagnostics have been reviewed, and its axiom report names no axiom beyond `propext`, `Classical.choice`, and `Quot.sound`, and a report printed before a later failure of the same build needs a separate successful build.  A line that reports the build of a module's imports says nothing about the module: `tests/isla/theorems.sh` builds the Isla modules' imports with Lake and then elaborates each module with `lean`, so a module's result is its elaboration's status and its own `#print axioms` lines.  A driver that reads axiom reports fails when it finds none, as `check_axioms` of `tests/verified/run.sh` does, since a parser that reads another line, such as an audit's summary, passes a run that printed no report.

Count every producer's exit status, and remove its earlier outputs before it runs.  The drivers run under `set -euo pipefail`, and Bash ignores errexit in a function called in the condition of an `if` or before `||`, so a driver tests each such command's status with an `if` of its own ([The Set Builtin](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)).  A producer whose failure goes unseen leaves the output file of an earlier run, which a later comparison then passes.  `tests/baremetal/m7.sh` empties its output directory and refuses an input directory inside it, `a64-images.sh` and `m7-image.sh` remove theirs, `m7-board.sh check` removes the earlier products of the image it checks, and the gateway's run in `m7-board.sh` removes the records files before the host script writes them.

`lake env lean FILE` loads the existing build of each import without rebuilding it, so a check of a file whose imports changed follows `lake build` of those imports, and a check can pass against the stale build of a module whose source was renamed until it imports the old and the new module together ([the manual's section on the runner](../../../docs/verified-manual.md#toolsleanrun-and-the-shared-lock)).  `tests/verified/run.sh` builds every module that it and the scripts it calls load before it loads any, since `lean` and `lean --run` read a module's compiled file without checking it against the source.  `theorems.sh` and the image drivers build the imports of the modules that they elaborate in the same way.

A result holds for the tree and the inputs that it ran on.  Reusing it at a later commit requires that no module in the import closure of the check's modules changed between the two commits and that the driver and its inputs are identical.  Run each check in a checkout of its own and change no file there until it ends, since files copied into a checkout while a job runs give the job a mix of two trees, which no commit holds.  [The entry on theorems outside the full check](../out-of-build-checks/README.md) lists the drivers whose results the full check does not give, and [the entry on checks that can fail](../discriminating-checks/README.md) states when a passing check counts as evidence.

The worked examples are the record STATUS.md of `tools/full-check`, the elaboration of each module by `tests/isla/theorems.sh` after the build of its imports, and `check_axioms` of `tests/verified/run.sh`.  `tests/baremetal/m7.sh` shows the emptied output directory, and `m7-board.sh` the removal of an image's earlier products and of the gateway's records.  The header of `tests/verified/run.sh` states why it builds before it loads.
