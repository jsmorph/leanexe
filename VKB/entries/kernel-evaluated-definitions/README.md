# Definitions that the kernel evaluates

The entry applies when `decide +kernel` or another kernel check runs a definition on concrete data, such as the code generator and the encoder under the byte theorem of a `verified_compile` program, the iteration of a generator, or a comparison of byte arrays, and the check's time or memory grows faster than the data.  The kernel reuses a reduction only for a term that recurs exactly, keeps every reduction until it finishes the declaration, and holds an `Array` as its list, so a definition that runs fast as compiled code can cost the kernel a traversal for each query, a walk down a list for each index, or a step for each successor.  [The entry on diagnosing slow checks](../slow-check-diagnosis/README.md) gives the steps that find such a definition.

Give the kernel a form that computes each value once as data, prove it equal to the form that the proofs use, and rewrite with that equation where the proofs unfold the definition.  `Verified.Expr.uses` answers whether an expression reads a variable by traversing the expression, and the code generator asks it about every variable at every binding.  `Verified.Expr.useMask` computes the variables that an expression reads as the bits of one number, `Verified.Expr.usesFast` tests a bit, and `Verified.Expr.usesFast_eq` lets the proofs keep `uses` (the docstring of `useMask`).  `Verified.Flags.params` and `Verified.Flags.result` read a function's flags by its index in a list, because the kernel reduced a match on `Flags S` and `FVar S g` together in tens of milliseconds for each step of the index (their docstring).  `Library.Random.ParkMiller.advance_eq_iterate` rewrites a loop as `Nat.iterate` before `decide +kernel`, since the kernel's evaluation of `LeanExe.loop` takes about eight times as long when the count doubles (the docstring of `Library.Random.ParkMiller.check_value`).  The kernel compares two `ByteArray` values by reading the elements of their lists by index, which takes time quadratic in the length, so `LeanExe.Pipeline.encode_eq_of_toList` turns an equality of the lists `data.toList` into the equality of the arrays.  [The entry on image files](../image-file-checks/README.md) gives the forms of the image generators: a set of locals as the bits of a number, numbers of bytes formed in rounds, appends nested to the right, a fuel equal to the need, and data segments written into a list of zeros.  [The entry on kernel checks over ℚ](../kernel-rational-checks/README.md) gives integer coefficients in place of rationals.

When compiled code computes a result that the kernel would derive slowly, compute it natively and let the kernel check a claim about the literal.  `verified_compile` evaluates the compiled module with `Verified.Reflect.evalModule`, adds the bytes of each function body as a literal, and proves each body's encoding by a `decide +kernel` of its own, from which `Wasm.Encoding.encode_of_parts` assembles the encoding of the module, so that one check holds one function and its memory is that of the largest function (the comment at that step of `Verified/Reflect/Command.lean`).  The native evaluation supplies only literals, and the kernel checks every claim about them, so the trusted base does not change.  [The entry on kernel checks over ℚ](../kernel-rational-checks/README.md) applies the same rule to certificates that a script computes.

The form of a decided statement sets the kernel's work as the form of a definition does.  `∀ x ∈ l, ∀ y ∈ l, f x = f y → x = y` evaluates `f` at every pair of members of `l`, and over the occurrences of identifiers in a translated program, a list that repeats each identifier many times, the kernel's check of a renaming's injectivity in that form exhausted the memory of its job.  `ClightN.Proof.inj_of_nodup_map` of `LeanExe/Native/ClightN/Instance.lean` derives the statement from `(l.map f).Nodup`, so the instances of N decide that each occurrence lies in the list of the program's identifiers and that the renaming's image of that list has no repetitions, which keeps the kernel's work in proportion to the occurrences, as the section "The programs" of `clightn/README.md` states.  `ClightN.Proof.InstOk.inj` of `LeanExe/Native/ClightN/Instance.lean` joins the two checks for every instance.

The kernel does not evaluate a definition by well-founded recursion, and a `decide +kernel` whose evaluation reaches one fails as an application type mismatch, since the decision does not reduce to `true`.  Lean compiles a recursive definition by well-founded recursion, without a message, when it finds no structural recursion, and a recursive call on the name that an as-pattern gives to the tail of a matched list is such a case.  `LeanExe.Native.initStores`, whose stores the instances of N evaluate for the data of a module, therefore writes its patterns out in full and states `termination_by structural`, under which Lean compiles it by structural recursion or reports an error.  The equation lemmas and the functional induction principle of the written-out form state the same equations as those of the as-pattern, so a proof such as `LeanExe.Native.exec_initStores`, which inducts with `initStores.induct`, holds for both.

A raised memory limit lets a larger input pass while the cost keeps its growth, and the next larger program meets the limit again.  A form that the kernel evaluates in time linear in the input removes the growth.  A form that changes the definition the proofs unfold changes every proof that unfolds it, so keep the proofs' definition and add the equation, as `Verified.Expr.usesFast_eq` does.

`Library.Random.ParkMiller.check_value` is the worked example of a rewritten evaluation, and the byte theorem of every `verified_compile` program, whose function claims `Wasm.Encoding.encode_of_parts` joins, is the worked example of a native evaluation checked by the kernel.
