# Hardware facts and trusted assumptions

The entry applies when a model, a premise, an initialization, a timing argument, or a row of `docs/trusted-base.md` uses a fact about a processor, a device, a board, a probe, a WebAssembly engine, or the Linux kernel, and when a proof outside the repository's build serves as evidence for a trusted item.  The kernel checks the theorems against the model and never against the hardware, so a wrong fact makes a theorem's use on the hardware false while every proof still checks.  Each fact therefore needs a source for the revision at hand, and each row of the trusted base keeps what it assumes apart from the evidence for it.  [The opening of the trusted base](../../../docs/trusted-base.md) states that a row marked "Not trusted" names a part that a check of each build or a kernel-checked step removes from the trusted base.

Each fact cites the primary source for the revision in use, by section.  [The section on resets on the board](../../../docs/m7-bare-metal.md#resets-on-the-board) gives, for each debug and reset register, the section of DDI 0403E.e or RM0410 that resets or keeps it.  [The section on reset and the initialization](../../../docs/m7-bare-metal.md#reset-and-the-initialization) states that the addresses, offsets, fields, and reset values it uses read the same in RM0410 Rev 4 and Rev 5, and it marks as an inference the one link that neither revision names, that ST drives INITVTOR from BOOT_ADD0.  [The AArch64 startup](../../../docs/a64-bare-metal.md#the-startup) cites section C5.2.8 for FPCR's reset value and fields.  A fact that the device can report comes from the device: OPTCR1 read over SWD gives BOOT_ADD0 `0x0080`, which only forum reports state for the board as shipped ([the section on the NUCLEO-F767ZI](../../../docs/native-bare-metal.md#the-nucleo-f767zi) and the row "Reset" of [the Cortex-M7 trusted base](../../../docs/m7-bare-metal.md#trusted-base)).  A reading of the errata classifies each against the run conditions: the row on the model's fidelity cites Arm's SDEN-1068427 and ST's ES0334 for the core's revision r1p0 and the device's revision Z, in which no erratum concerns the emitted forms under the run conditions.  Erratum 486321, which miscounts stall cycles in the DWT's other counters, is why the measurement images of `tests/TestSupport/M7/Dwt.lean` enable `DWT_CYCCNT` alone ([the section on timing](../../../docs/m7-bare-metal.md#timing)).

When the manual does not settle a behavior that a program depends on, a board test with the alternative setting as its control decides it.  The decision that follows goes through a recommendation, a fresh agent's review, and a revision, the procedure that the opening of `Demos/Bms/review.md` records for the BMS decisions that change what a theorem assumes or what is trusted.  The row "USART3 and the channel" gives board tests as the evidence for USART3's behavior after an overrun with `LeanExe.M7.Nucleo.init`: runs of `sha.bin` with a block sent ahead, a write of `ORECF` over SWD after which reception resumed, and reads with the core halted in which no received byte reached `USART_RDR` while `ORE` was set.  Its behavior with `OVRDIS` set rests on RM0410 section 34.8.3 and a test with the bit set and the core halted, in which each received byte replaced the one in `USART_RDR`.  Such tests access registers over SWD with the core halted, outside the run conditions, so they settle the device's behavior and support no theorem's run.  The decision of gap 5 of [the BMS review](../../../Demos/Bms/review.md#resolution-of-the-gaps) keeps the existing images and theorems: `LeanExe.M7.Nucleo.initOvrdis` and `LeanExe.M7.Nucleo.init` share `LeanExe.M7.Nucleo.initConfig` and differ only in the write of `OVRDIS`, and the rows "The initialization's effect" and "USART3 and the channel" give each list its own evidence.

A WebAssembly engine's behavior that a host semantics models needs the same evidence, and a run of the engine decides it where a reading of the engine's source admits another answer.  Wasmtime 44's implementation of Preview 1, [`crates/wasi/src/p1.rs`](https://github.com/bytecodealliance/wasmtime/blob/v44.0.0/crates/wasi/src/p1.rs), maps an invalid enum or flags value to errno `inval`, but that mapping covers errors that a function raises, while the glue that wiggle generates converts each core argument before the function runs, and a conversion error traps.  `clock_time_get` with clock id 4 therefore traps, `LeanExe.Wasi.Call.clockTimeGet` gives the clock id the kind `enum32 4`, whose rejection in `LeanExe.Wasi.Call.reject` returns errno 28 before the host is called, and `tests/wasi/sys/clock-invalid.wat` keeps the observation as a test, whose trap message `tests/wasi/sys-run.sh` requires.  A probe of an argument needs a case in which the function reads the argument, since a function that fails first on another argument, such as a file function given a descriptor that it rejects with `badf`, shows only that the probed argument's conversion passed.  `LeanExe.Wasi.Call.reject`, with its rule for each kind of parameter, `LeanExe.Wasi.Param.reject`, belongs to the row "Flat call specification" of [the trusted base](../../../docs/trusted-base.md#wasi-wasi-preview-1-modules), so `tests/wasi/sys-run.sh` tests both sides of each rule for every enum and flags parameter of the flat calls.  `uv run tools/wasi-calls.py --reject-sweep DIR` writes one module for the last value of each enum parameter, one for the next value, and one for each single bit of each flags parameter, and it prints for each module whether the rule rejects the value.  `tests/wasi/SysSweep.lean` requires each printed expectation to equal what `LeanExe.Wasi.Call.reject` computes for the module's arguments, and `tests/wasi/sys-run.sh` requires Wasmtime to trap with a message that contains `at convert` on each rejected value and to exit on each other one.  `tests/wasi/sys-run.sh` also runs `tests/wasi/SysSweep.lean` on the list with one expectation flipped and fails when that run passes.

Records and arrays that a function reads from memory need probes of their own.  A function decodes a record in memory after the glue has converted the core arguments, so an invalid enum or flags value in a field gives errno 28 through the conversion of a `GuestError` to an errno in `p1.rs`, where the same value as a core argument traps, and the descriptions of `poll_oneoff`, whose subscriptions the code writes into memory (`LeanExe.Wasi.Param.subscriptions`), reject a field only when its value does not fit its width (`LeanExe.Wasi.rejectFields`, and [the manual's section on nested calls](../../../docs/wasi.md#nested-calls)).  Wasmtime 44's `fd_read`, `fd_pread`, `fd_write`, and `fd_pwrite` read or write only the first non-empty element of their iovec array (`first_non_empty_iovec` and `first_non_empty_ciovec` in `p1.rs`), which a probe of one element cannot tell from the witx's gather and scatter, so a probe of an array uses several elements, and `LeanExe.Wasi.Param.iovec` passes arrays of one element.

A kernel's handling of a system call that a rule models needs the same evidence: the kernel's source at the version in use, read in the order of its checks, and probes of each call against guard pages.  Linux 7.0 checks only that a buffer's addresses lie in the process's range (`access_ok`) and copies until a fault, so a `read`, `write`, or `getrandom` of a regular file or of random bytes whose buffer runs into an unmapped page returns a partial count, a `read` or `write` of a pipe returns `EFAULT` or the count of the pieces before the one that faulted, after `pipe_read` may have written part of that piece into memory (`fs/pipe.c`), and `clock_gettime` returns `EFAULT` after `copy_to_user` in `put_timespec64` (`kernel/time/time.c`) has written part of the record.  The order of the checks differs between calls: `vfs_read` checks `access_ok` of the whole count before it clamps the count to `MAX_RW_COUNT` (`fs/read_write.c`), while `getrandom` clamps first (`import_ubuf` in `lib/iov_iter.c`), so with a count of 2^63 at a mapped address `read` returns `EFAULT` and `getrandom` writes.  These runs lie outside the premise of `LeanExe.Linux.step` that every byte of every region is accessible, which excludes every run whose effect depends on a fault, so the rule states none of them.  Linux reads a call's number from the low 32 bits of X8 and casts each argument to its parameter's C type (`__SC_CAST` in `include/linux/syscalls.h`), so it reads a descriptor or a flag word as its low 32 bits, while `LeanExe.A64.pstepWith` compares all 64 bits of X8 with the table's numbers, and a run in which X8 holds a table call's number in its low 32 bits and a set bit above bit 31 ends in the model where Linux makes the call.  Linux 7.0 refuses with `ETXTBSY` to open the running executable for writing (`exe_file_deny_write_access` in `fs/exec.c`) unless a fanotify pre-content watch covers the file, a fact on which the frame of `write` rests.  The rows "The kernel's agreement with the frame rule" and "QEMU's user-mode emulator" of [the trusted base's section on AArch64 Linux executables](../../../docs/trusted-base.md#a64l-aarch64-linux-executables) state these assumptions, [the entry on runs on boards and emulators](../run-evidence/README.md) states what a run under QEMU's user-mode emulator shows, and [the entry on Linux calls through the call layer](../linux-call-layer/README.md) describes the rule.

A specification of a WASI host built on Linux rests on facts of the engine and of the kernel together.  `Verified.Shim.openCheck` makes Wasmtime 44's checks of `path_open` before any call, for a directory that the repository's host preopens for reading and writing (`tools/wasmtime-host.c`), in the order of `path_open` in `crates/wasi/src/p1.rs` and `open_at` in `crates/wasi/src/filesystem.rs`: the path's UTF-8, the directory descriptor, the `sync` flags, and `directory` with `creat`, `excl`, or `trunc`.  A probe whose every case has one fault cannot tell that order from another, so a probe of an order combines faults.  Plain `openat` follows `..`, an absolute path, or a symbolic link out of the directory ([openat2(2)](https://man7.org/linux/man-pages/man2/openat2.2.html)), so the shim opens a path with `openat2` and the resolution flags `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS` that cap-std 3.4.5 passes, and makes the call again after `EAGAIN` up to four calls in all, as cap-std does (`Verified.Shim.openHowBytes` and `Verified.Shim.OpenCalls`).  Linux reads the directory of `openat2` as an `int` (`fs/open.c`), so the word `0xFFFFFF9C` as the directory names `AT_FDCWD`, the process's working directory, and the shim refuses that WASI descriptor as it refuses every number outside `Verified.Shim.openNumbers`.  The values of `O_DIRECTORY` and `O_NOFOLLOW` differ between arm64's `arch/arm64/include/uapi/asm/fcntl.h` and the generic `include/uapi/asm-generic/fcntl.h` that x86-64 uses, where arm64's values are `O_DIRECT` and `O_LARGEFILE`, so a specification shared by the architectures takes them as a parameter, `Verified.Shim.OpenFlags`, with `Verified.Shim.arm64Flags` for arm64.  `getrandom` returns fewer bytes than asked when a signal is pending at a page boundary after the first page (`get_random_bytes_user` in `drivers/char/random.c`), so `random_get` calls it until the buffer is full (`Verified.Shim.RandomCalls`).  A read of at most a page leaves the loop of `get_random_bytes_user` in Linux 6.12 when the iterator is exhausted, before the test for a pending signal, so it returns every byte unless the copy faults, and getrandom(2) guarantees every byte of a read of up to 256 bytes once the urandom source is initialized.  The random histogram and the random choice therefore draw at most 4,096 bytes at a time, and a condition that each such `getrandom` returns its count holds of Linux's replies once the urandom source is initialized ([the histogram's section on the native executable](../../../Demos/RandomHistogram/README.md#the-native-executable-writes-the-counts)).  `bprm_stack_limits` of `fs/exec.c` in v6.12 limits the strings of `argv` and `envp`, the file name, and their pointers together to the smaller of 6 MiB, three quarters of `_STK_LIM`, and a quarter of the stack's soft limit, and to at least 128 KiB, and `get_arg_page` makes the check from v4.13.  A premise that the strings of the arguments, each with its zero byte, and their eight-byte pointers take at most 6 MiB, `Demos.RandomHistogram.argsLimit`, therefore holds for every process that Linux 4.13 or later starts.  The table of [the WASI manual's differences from Wasmtime](../../../docs/wasi.md#differences-from-wasmtime) gives each case in which the shim's reply differs from that of the repository's Wasmtime host.

Where the architecture or a boot protocol leaves a value UNKNOWN or unspecified, the code writes the whole register, the code canonicalizes the value before anything observes it, or the model takes the value as arbitrary or stops in the states that the value governs.  Every field of FPCR is UNKNOWN after a warm reset, so the AArch64 startup writes the whole register as `LeanExe.A64.fpcrValue`, `0x02000000`, with DN set, and Linux's boot protocol fixes no value of the system registers, so the startup writes a complete value into every system register that it relies on ([the AArch64 document's section on the image and the boot protocol](../../../docs/a64-bare-metal.md#the-image-and-the-boot-protocol)).  PTX leaves single-precision NaN results unspecified, so the PTX translation replaces a NaN result by `0x7fc00000`, and `LeanExe.canonical32` with `LeanExe.canonical_f32_bin` show that the replacement gives Talos's result ([the manual's section on PTX kernels](../../../docs/verified-manual.md#ptx-kernels)).  `LeanExe.M7.Reset` leaves r0 to r12, the flags, and memory arbitrary, as section B1.5.5 of DDI 0403E.e leaves the registers and flags UNKNOWN, and the M7 model stops in every state that the two fields of CCR govern, so that no field of a system register enters the theorem.

A trusted item stays trusted until a build-checked chain replaces it, and a proof outside the build appears among the row's evidence while the row keeps its claim.  The A64 row "Floating-point equations" of [the trusted base](../../../docs/trusted-base.md#a64-aarch64-images) keeps the equations as trusted and lists the proofs over Sail's Lean translation as evidence, since `tools/sail/check.sh` checks them outside the repository's build and their links to Isla's calls rest on review.  [The Sail README's section on what the proofs trust](../../../tools/sail/README.md#what-the-proofs-trust) lists what those proofs assume.  Work on the trusted base goes first to the item whose evidence is weakest.

A forum report, a brief, or a model of the device is no source for a fact.  BOOT_ADD0 as shipped rests on forum reports, and the board's own OPTCR1 replaced them for the test board.  Renode checks USART3's registers but not the clocks, the pins, or the baud rate, so a run in Renode is no evidence for the initialization's effect on them (the row "The initialization's effect").  Evidence for one setting does not carry to another: `ORE` clear after a run shows that no overrun occurred with `init` and shows nothing for an image with `OVRDIS` set, which forces `ORE` to 0.

The worked examples are the sections "Resets on the board", "Timing", and "Trusted base" of `docs/m7-bare-metal.md`, the AArch64 startup's write of FPCR, gap 5 of the BMS review with the two initialization lists of `LeanExe/M7/Board.lean`, and the A64 row "Floating-point equations" with the Sail proofs.  [The entry on runs on boards and emulators](../run-evidence/README.md) covers the runs that test these facts, [the entry on Cortex-M7 board theorems](../m7-board-theorem/README.md) the theorems over either initialization, and [the entry on floating-point equations from Sail](../sail-fp-equations/README.md) the proofs that the A64 row lists as evidence.
