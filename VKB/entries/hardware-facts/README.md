# Hardware facts and trusted assumptions

The entry applies when a model, a premise, an initialization, a timing argument, or a row of `docs/trusted-base.md` uses a fact about a processor, a device, a board, or a probe, and when a proof outside the repository's build serves as evidence for a trusted item.  The kernel checks the theorems against the model and never against the hardware, so a wrong fact makes a theorem's use on the hardware false while every proof still checks.  Each fact therefore needs a source for the revision at hand, and each row of the trusted base keeps what it assumes apart from the evidence for it.  [The opening of the trusted base](../../../docs/trusted-base.md) states that a row marked "Not trusted" names a part that a check of each build or a kernel-checked step removes from the trusted base.

Each fact cites the primary source for the revision in use, by section.  [The section on resets on the board](../../../docs/m7-bare-metal.md#resets-on-the-board) gives, for each debug and reset register, the section of DDI 0403E.e or RM0410 that resets or keeps it.  [The section on reset and the initialization](../../../docs/m7-bare-metal.md#reset-and-the-initialization) states that the addresses, offsets, fields, and reset values it uses read the same in RM0410 Rev 4 and Rev 5, and it marks as an inference the one link that neither revision names, that ST drives INITVTOR from BOOT_ADD0.  [The AArch64 startup](../../../docs/a64-bare-metal.md#the-startup) cites section C5.2.8 for FPCR's reset value and fields.  A fact that the device can report comes from the device: OPTCR1 read over SWD gives BOOT_ADD0 `0x0080`, which only forum reports state for the board as shipped ([the section on the NUCLEO-F767ZI](../../../docs/native-bare-metal.md#the-nucleo-f767zi) and the row "Reset" of [the Cortex-M7 trusted base](../../../docs/m7-bare-metal.md#trusted-base)).  A reading of the errata classifies each against the run conditions: the row on the model's fidelity cites Arm's SDEN-1068427 and ST's ES0334 for the core's revision r1p0 and the device's revision Z, in which no erratum concerns the emitted forms under the run conditions.  Erratum 486321, which miscounts stall cycles in the DWT's other counters, is why the measurement images of `tests/TestSupport/M7/Dwt.lean` enable `DWT_CYCCNT` alone ([the section on timing](../../../docs/m7-bare-metal.md#timing)).

When the manual does not settle a behavior that a program depends on, a board test with the alternative setting as its control decides it.  The decision that follows goes through a recommendation, a fresh agent's review, and a revision, the procedure that the opening of `Demos/Bms/review.md` records for the BMS decisions that change what a theorem assumes or what is trusted.  The row "USART3 and the channel" gives board tests as the evidence for USART3's behavior after an overrun with `LeanExe.M7.Nucleo.init`: runs of `sha.bin` with a block sent ahead, a write of `ORECF` over SWD after which reception resumed, and reads with the core halted in which no received byte reached `USART_RDR` while `ORE` was set.  Its behavior with `OVRDIS` set rests on RM0410 section 34.8.3 and a test with the bit set and the core halted, in which each received byte replaced the one in `USART_RDR`.  Such tests access registers over SWD with the core halted, outside the run conditions, so they settle the device's behavior and support no theorem's run.  The decision of gap 5 of [the BMS review](../../../Demos/Bms/review.md#resolution-of-the-gaps) keeps the existing images and theorems: `LeanExe.M7.Nucleo.initOvrdis` and `LeanExe.M7.Nucleo.init` share `LeanExe.M7.Nucleo.initConfig` and differ only in the write of `OVRDIS`, and the rows "The initialization's effect" and "USART3 and the channel" give each list its own evidence.

Where the architecture or a boot protocol leaves a value UNKNOWN or unspecified, the code writes the whole register, the code canonicalizes the value before anything observes it, or the model takes the value as arbitrary or stops in the states that the value governs.  Every field of FPCR is UNKNOWN after a warm reset, so the AArch64 startup writes the whole register as `LeanExe.A64.fpcrValue`, `0x02000000`, with DN set, and Linux's boot protocol fixes no value of the system registers, so the startup writes a complete value into every system register that it relies on ([the AArch64 document's section on the image and the boot protocol](../../../docs/a64-bare-metal.md#the-image-and-the-boot-protocol)).  PTX leaves single-precision NaN results unspecified, so the PTX translation replaces a NaN result by `0x7fc00000`, and `LeanExe.canonical32` with `LeanExe.canonical_f32_bin` show that the replacement gives Talos's result ([the manual's section on PTX kernels](../../../docs/verified-manual.md#ptx-kernels)).  `LeanExe.M7.Reset` leaves r0 to r12, the flags, and memory arbitrary, as section B1.5.5 of DDI 0403E.e leaves the registers and flags UNKNOWN, and the M7 model stops in every state that the two fields of CCR govern, so that no field of a system register enters the theorem.

A trusted item stays trusted until a build-checked chain replaces it, and a proof outside the build appears among the row's evidence while the row keeps its claim.  The A64 row "Floating-point equations" of [the trusted base](../../../docs/trusted-base.md#a64-aarch64-images) keeps the equations as trusted and lists the proofs over Sail's Lean translation as evidence, since `tools/sail/check.sh` checks them outside the repository's build and their links to Isla's calls rest on review.  [The Sail README's section on what the proofs trust](../../../tools/sail/README.md#what-the-proofs-trust) lists what those proofs assume.  Work on the trusted base goes first to the item whose evidence is weakest.

A forum report, a brief, or a model of the device is no source for a fact.  BOOT_ADD0 as shipped rests on forum reports, and the board's own OPTCR1 replaced them for the test board.  Renode checks USART3's registers but not the clocks, the pins, or the baud rate, so a run in Renode is no evidence for the initialization's effect on them (the row "The initialization's effect").  Evidence for one setting does not carry to another: `ORE` clear after a run shows that no overrun occurred with `init` and shows nothing for an image with `OVRDIS` set, which forces `ORE` to 0.

The worked examples are the sections "Resets on the board", "Timing", and "Trusted base" of `docs/m7-bare-metal.md`, the AArch64 startup's write of FPCR, gap 5 of the BMS review with the two initialization lists of `LeanExe/M7/Board.lean`, and the A64 row "Floating-point equations" with the Sail proofs.  [The entry on runs on boards and emulators](../run-evidence/README.md) covers the runs that test these facts, [the entry on Cortex-M7 board theorems](../m7-board-theorem/README.md) the theorems over either initialization, and [the entry on floating-point equations from Sail](../sail-fp-equations/README.md) the proofs that the A64 row lists as evidence.
