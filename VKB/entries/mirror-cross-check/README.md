# Executable mirrors of a specification

The entry applies when an executable mirror of a Lean specification judges runs on QEMU, in Renode, or on a board, or supplies the expected answers of a host script, as the Python machine of `tests/baremetal/bms_proto.py` does for the BMS step.  The comparisons of those runs rest on the mirror, so a mirror that shares a defect with the image passes it.  A native replay of the specification checks the mirror at scale, byte for byte, and the scenarios that test the image take their expected answers from the requirements.  [The entry on runs on boards and emulators](../run-evidence/README.md) states what a run shows once its judge is checked, and [the entry on testing a statement before its proof](../statement-testing/README.md) uses executable models of the requirements before a proof.

Replay the specification in native Lean on the logs of a run.  `bms-replay`, the program of `tests/TestSupport/Bms/Replay.lean`, computes `LeanExe.Requests.delimAnswers` with `Demos.Bms.Spec.machine` from the state after a board reset for each part of the input log between `reset` lines, and it compares the answers line by line with the output log, with no Python code in the comparison.  By `Demos.Bms.Spec.delimAnswers_eq`, those answers are the answers of the machine's run over the part's non-empty segments, which the items M1 to M12 of the requirements describe, so a passing replay shows that each answer in the output log is the specification's answer to the bytes in the input log, provided that the board read exactly those bytes and started from a board reset at each `reset` line ([the replay against the specification](../../../Demos/Bms/Host.md#the-replay-against-the-specification)).  `split` and `answerRun` of `LeanExe/Requests/Delimited.lean` append to the end of a list at each segment, and the `csimp` theorems `LeanExe.Requests.split_eq_splitLinear` and `LeanExe.Requests.answerRun_eq_answerRunLinear` make compiled code compute linear forms while the replay evaluates the definitions, as [the entry on compiled forms of list specifications](../linear-compiled-folds/README.md) describes.

Cross-check the mirror with the replay on generated logs whose inputs reach the cases that a schedule of scenarios does not.  `bms_proto.py gen` writes a log of a bridge's random writes and the mirror's answers in the format of a run's logs, `bms-replay` compares the mirror with the specification on every segment, and `bms_proto.py cover` counts the transitions, the first failing checks, the fields at and beside each limit, and the other cases that the inputs reach ([the Python machine against the specification](../../../Demos/Bms/Host.md#the-python-machine-against-the-specification)).  The generator divides the writes into parts that board resets end, and each part draws its own rates of faults.  A quarter of the parts carry no fault, so that the machine stays in `NORMAL` for long runs, and three parts in ten number their records from just below 2^32, so that the numbers wrap.  The counts of `cover` come from the mirror's run, which the replay confirms only through the answers.

State each scenario's expected answers from the requirements and never from the mirror.  The scenarios of `tests/baremetal/uart_bms.py` state `N_pc`, `D_edm`, `tol_pc`, the limits, and the precharge condition themselves, and the table of [the scenarios](../../../Demos/Bms/Host.md#scenarios) gives each scenario's expected answers beside the answers of the mirror run.  The bridge keeps lockstep while it injects faults, so that the board reads exactly the bytes that the bridge wrote, which the replay's premise requires.

Show that the replay fails on altered logs, as [the entry on checks that can fail](../discriminating-checks/README.md) asks of every check: a changed digit of an answer, a missing answer, an extra answer, a missing `reset` line, and an input line that is not hexadecimal each made `bms-replay` fail at the altered line.  Record what stays untested beside the results.  No generated part reaches 2^32 answers, so the wrap of the board sequence number goes untested.  No scenario delivers an answer that straddles the bridge's deadline, so the bridge's discard of a partial answer goes untested, and the checks of the lease's timing use the bridge's own `T_lease`, so a wrong value of that constant passes them ([limits](../../../Demos/Bms/Host.md#limits)).

`uart_bms.py replay` replays a run with the Python machine, and every run performs that replay on its own logs, which shows that the run agrees with the mirror and nothing about the mirror.  A scenario that took a constant from the mirror would pass with the mirror's error in it.  Inputs drawn at one uniform rate over long parts leave most answers in `FAULT`, where a failing check leaves the answer unchanged and the replay cannot tell one check from another, so the rates vary by part and the counts of `cover` show which cases the inputs reached.

The worked examples are `bms-replay` with the logs of `bms_proto.py gen` and the counts of `bms_proto.py cover`, and the replay that `tests/baremetal/m7-qemu.sh bms` runs after QEMU's run and that `tests/baremetal/m7-board.sh replay` runs on the board's logs.  `tests/baremetal/delim-mirror.sh` checks a smaller mirror: it answers generated records, corrupted encodings, and streams with the Lean definitions of `LeanExe/Requests/Delimited.lean` under `lake env lean --run`, and it requires every answer of the mirror `tests/baremetal/delim_frame.py` to equal Lean's and the mirror's encodings of the design's two records to equal the design's wire bytes.  `tests/energy/replay.py check` implements the energy authorizer's acceptance rule a second time in Python and compares its decisions with those of native Lean on the module cases that `verified-cases-energy` prints ([Energy: replay study](../../../Demos/Energy/Replay.md)).  [The entry on safety theorems over a machine's history](../history-safety-theorems/README.md) states the theorems over the answers that the replay computes.
