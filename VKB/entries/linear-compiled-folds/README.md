# Compiled forms of list specifications

A specification written as a fold that appends to the end of its result, `acc ++ [x]` or `acc ++ chunk` at each step, reads well and proves well, but compiled code evaluates `List.append` by copying its first argument, so a native run over `n` steps takes time quadratic in `n`.  The entry applies when native Lean evaluates such a specification on long inputs, as a replay of a board's logs or a check of test vectors does, and the proofs must keep the definition as it is.

Define a form that accumulates in reverse, `x :: acc` with one `List.reverse` at the end, or in an `Array`, with `Array.push` and the append of a list to an array, and prove `@[csimp] theorem f_eq_fLinear : @f = @fLinear`.  The proof is an induction over the input that generalizes the accumulator: it states the definition's fold from an arbitrary accumulator, `⟨D, c⟩` against `(D.reverse, c.reverse)` or `a.toList` against `a`, and closes each case with `simpa` over the step functions and the induction hypothesis at the next accumulator.  `LeanExe.Requests.foldl_splitByteRev` and `LeanExe.Requests.foldl_answerStepArray` have this form, and `LeanExe.Requests.split_eq_splitLinear` and `LeanExe.Requests.answerRun_eq_answerRunLinear` follow from them by `funext` and the lemma at the empty accumulator.  Compiled code then computes `LeanExe.Requests.segments` and `LeanExe.Requests.delimAnswers` through `LeanExe.Requests.splitLinear` and `LeanExe.Requests.answerRunLinear`, and every theorem about the definitions stays as it was.

A `@[csimp]` theorem changes only code compiled after it, including the definitions of the same file that call the replaced function, so `split_eq_splitLinear` precedes `segments` and `answerRun_eq_answerRunLinear` precedes `delimAnswers` in `LeanExe/Requests/Delimited.lean`.  Placed at the end of the file, the theorems would leave the compiled code of `segments` and `delimAnswers` calling the quadratic forms, as [the entry on transcriptions of standards](../spec-transcription/README.md) records for `keccakP`.  Rewriting the definition itself in the linear form would change every proof that unfolds it.

Repeated access from the head of a list costs the same way.  A definition that takes the `b`-th chunk of `k` elements as `(ws.drop (b * k)).take k` for each `b` walks the list from its head for every chunk, so its native evaluation takes time quadratic in the number of chunks, and tests on small inputs do not show it.  A recursion that takes each chunk from the rest of the list, as `Demos.Rcv.Spec.chunks` does, is linear, and the ranked-choice specification's proofs use that form.  Run a specification natively on the largest input of its tests before its review, so that such a cost appears before proofs depend on the definition.

`bms-replay` of `tests/TestSupport/Bms/Replay.lean` computes `delimAnswers` of each part of a log of the BMS bridge, and with the two theorems its replay of a part of 30,000 segments took about a tenth of its earlier time, with the times that `Demos/Bms/Host.md` records.  `Library.Hashing.Sha3.Spec.keccakP_eq_run` is the other worked example of a compiled form proved equal to a specification.
