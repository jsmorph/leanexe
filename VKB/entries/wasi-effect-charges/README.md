# Allocation charges of WASI effect functions

A WASI program's total-execution theorem needs a bound on what each effect function allocates: `begin`, each step, and the read and write steps that a step calls.  `Verified.Wasi.Resource.Bounded` states that every run and every prefix of a command spends at most a budget and its frames fit the call depth, and `CallBounded` states the same of a call.  The integer and binary64 running sums prove these bounds for their effect functions with one method, which a new WASI program can follow.

Apply `Verified.Wasi.Resource.bounded_of_rule` at each command of the body.  It reduces `Bounded` to `Rule`, which matches on the form of the command and requires only facts about its parts.  For a `bind`, `Rule` requires a bound on the continuation only at values that some run of the first command returns, through `Returns`, and `Verified.Wasi.Resource.Returns.read_size` bounds the count of a read by its buffer's size and states that the buffer keeps its size, which lets a read step's charge depend on the size of the read.  The reflector binds each argument of an effect command that is not a variable by a `bind` of a `ret` before the command, and `Verified.Wasi.Resource.Returns.bind_ret` carries a value that the step returns through each such `bind` to the command, as the read steps of the running sums and the order book do with three applications before `Verified.Wasi.Resource.Returns.read_size`.  A call takes its bound from its body's, through `callBounded_here` for the first function of the program and `callBounded_there` for a later one.

Each leaf of the proof is the cost of an expression.  Reduce it with `simp +decide only [PureContext.ownedCost, PureContext.exprCost, PureContext.ofProg, Expr.allocs, Var.cost, Expr.mode, argsSum, callCredits, ↓reduceIte, Nat.add_zero, Nat.zero_add, coerceCost]`, which leaves the table entry of the called pure function, then identify it with the generated bound by `show io.pureSources.f.bound … ≤ _` and bound that with a closed-form lemma of [the entry on closed-form allocation bounds](../verified-bound-closed-form/README.md).  `Verified.Ty.copyCost_of_scalar` removes the copy of a scalar argument whose type is an unreduced entry of a parameter list, and `Verified.Expr.fits_of_depthCalls` gives the frames of a condition that calls no function.

A loop's charge follows by induction on the number of passes left, over `Verified.Wasi.Resource.ResourceLoopExec` and `Verified.Wasi.Resource.ResourceLoopPrefix`, which bounds the spending by that number times the charge of one pass.  The private lemmas of `Verified/Examples/WasiRetainBudget.lean` do this for the loop of `Verified.Examples.WasiRetain.retain`, whose passes charge nothing, since its read moves the state's buffer, and `Verified.Examples.WasiRetain.call_prefix_bound` closes the prefix bound of the call with `Verified.Wasi.Resource.call_prefix_rule`.  [The entry on WASI process totality](../wasi-process-total/README.md) describes the total theorem that takes this bound.

`Verified.Wasi.Resource.ResourceLoopExec` adds the charge of each pass to that of the passes after it and credits no release, while the compiled code releases what a pass allocated and the allocator reuses the block, so a loop whose number of passes depends on the host's replies has a charge that grows with them unless its passes charge nothing.  A pass that writes part of its bytes therefore writes a window of a buffer in place, `LeanExe.Wasi.writeStdout buffer start count`, and allocates nothing: the loop of `LeanExe.Wasi.writeAll` binds the start and the count of the window that remains, words, and writes it from the borrowed buffer.  `Verified.Wasi.Resource.loop_bounded` bounds a loop whose test and step charge at most constants from the states of an invariant that every pass keeps, and with both constants 0 and the invariant `True` it gives the loop of `writeAll` the charge 0, as `Verified.Examples.WasiReadAll.writeAll_bounded` shows, and `writeAll_bounded` of `Demos/RandomHistogram/Budget.lean` for the histogram's output.  `Verified.Examples.WasiReadAll.budget_bounded` then bounds every prefix of `Verified.Examples.WasiReadAll.main` under every host by the block of `readAll`'s buffer, through `Verified.Wasi.Resource.call_prefix_rule` and `Verified.Examples.WasiReadAll.body_bounded`.

`Verified.Wasi.Resource.Bounded` and `Verified.Wasi.Resource.Rule` bound a command from every world, and the rule of a `bind` bounds the second command from every world for every value that a run of the first returns, so the bound of a loop whose charge depends on the replies is its charge in the worst world.  `Verified/Wasi/ResourceRulesAt.lean` states `Verified.Wasi.Resource.BoundedAt`, `Verified.Wasi.Resource.LoopBoundedAt`, and `Verified.Wasi.Resource.CallBoundedAt` from one world, and `Verified.Wasi.Resource.RuleAt` gives, for a `bind`, an `ite`, a call, and a loop, the facts from which they follow, with the second command of a `bind` bounded from the world in which the first returned, and `Rule` for every other command.  A bound that depends on the replies applies `Verified.Wasi.Resource.boundedAt_of_rule` along the body's spine, `Verified.Wasi.Resource.Bounded.at` at the commands whose charge depends on no reply, and `Verified.Wasi.Resource.call_prefix_rule_at` and `Verified.Wasi.Resource.callBoundedAt_here` at the calls, and carries a condition on the replies along the run, as [the entry on WASI hosts built on a lower layer](../wasi-host-from-layer/README.md) describes.

The reflected term decides each charge.  The reflector binds each argument of an effect command that is not a variable before the command, so `writeStdout output written (output.size - written)` of a process step reflects to a `bind` of the subtraction, and of the projection `written` where the state keeps it in a pair with another word, before the write, and the proof of the step's charge follows those bindings, as `Demos.RunningSum.writeStep_bounded` does with a `repeat` over the rules of a `bind`, a `ret`, and a `write`.  A review of a charge therefore reads the reflected term, as the goals of `RuleAt` print it.

The rule of a `sys` command in `Verified.Wasi.Resource.Rule` bounds the command's charge over the `Exec` and `Prefix` derivations of its action from any world, which `Verified.Wasi.Resource.ResourceExec.sys` and `Verified.Wasi.Resource.ResourcePrefix.sys` carry, rather than over every trace.  A bound over every trace fails for a charge that depends on the host's reply: a reported call, such as `LeanExe.Wasi.Call.argsGet`, allocates a block of the size that its reporter's reply gives, which reaches nearly `2^32` bytes over all traces.  `Verified/Wasi/SysRule.lean` derives both premises of the rule from a bound on the replies that the host permits, `Verified.Wasi.Resource.reported_rule` for a host and `Verified.Wasi.Resource.reported_rule_observed` for the observed host of a run, and `Verified.Wasi.Resource.sys_rule_of_bound` from a bound on every trace for a call whose charge does not depend on the reply.  The first event of a prefix follows by induction on `LeanExe.Wasi.PrefixProgress`, which `LeanExe.Wasi.Prefix.progress` gives from a `Prefix` and which has the constructors `refl`, `advance`, and `trans` and none for a bind, so each `advance` case is a step of the action's own head constructor, as in `Verified.Wasi.Resource.prefix_sys_first`.

The charge of a later command can depend on what a `sys` command returned.  The reflector destructures a record result, such as the `LeanExe.Wasi.ArgsResult` of `args`, in every later expression, and `Verified.Expr.allocs` charges `Verified.Var.cost`, a copy of the whole record, for each use of an owned variable that stays live, so the budget of `Verified.Examples.WasiSys.main`, of `Verified/Examples/WasiSys.lean`, holds a copy of the argument bytes for each later use of the result but the last (the module docstring of `Verified/Examples/WasiSysTotal.lean`, and `Verified.Examples.WasiSys.budget` there).  The first step of the full check builds `Verified/Examples/WasiSys.lean`, which the shim's example `Verified/Examples/WasiSysShim.lean` imports, and not `Verified/Examples/WasiSysTotal.lean`, and `tests/wasi/sys-example-run.sh` builds both and audits their axioms.  The `bind` rule gives the continuation only `Verified.Wasi.Resource.Returns` of the first command, so the bound needs a lemma that limits what a run of the call returns, as `Verified.Wasi.Resource.Returns.read_size` does for a read.  `Verified.Examples.WasiSys.args_bytes_le` of `Verified/Examples/WasiSysTotal.lean` bounds the bytes of a returned `args` result by the bound on the reporter's replies, through `LeanExe.Wasi.Host.sys_bound` of both calls, `LeanExe.Wasi.Host.sys_reports`, and `Verified.Wasi.littleEndian_four_lt` for the reporter's words, A call with an output buffer, such as `LeanExe.Wasi.randomGet`, writes into a buffer that the program builds, so the budget holds the block of the program's `LeanExe.Bytes.build`, and the call charges `Verified.Wasi.Resource.PureContext.sysTakeCost`, which is 0 when the buffer's variable dies at the call, as `Verified.Examples.WasiSys.body_bounded` shows with its `free_bound` tactic.

The order book's process states its charges for every state whose arrays have the program's sizes, whatever records the input holds.  A read step's charge covers every reply of at most 4,096 bytes and takes the generated bound of `run` on a batch through a term `R` with `Demos.OrderBook.Process.RunBound R`, which `Demos.OrderBook.Process.runBound_74` gives from the closed form of that bound, `Demos.OrderBook.Bound.run_bound_le_sized`.  `Demos.OrderBook.Process.begin_prefix_bound` and `Demos.OrderBook.Process.step_prefix_bound` give the prefix bounds of `begin` and of every step, the latter through `Demos.OrderBook.Process.stepBudget_le` with the one charge `Demos.OrderBook.Process.stepCharge R`.

The order book's effect bodies destructure the state's 13 fields, and each level of the environment holds the previous level twice, so the elaborator's conversion of a call's arguments to the state unfolds a tree exponential in the depth.  The simproc `envGetOfIndex` of `Demos/OrderBook/ProcessCharges.lean` reads `Env.get env (Var.ofIndex Γ i h)` as the `i`-th value of a chain of `Verified.Env.cons` in one definitional step, which `simp` applies once to each shared subterm (its docstring).  The cost of the stopping branch's status is an `if` whose condition `read_state` unfolds while its instance still holds the effect body's environment, so the instance's type matches the condition only at the default transparency and `ite_self` and `split` do not apply, as [the entry on tactics whose failures mislead](../tactic-combinator-pitfalls/README.md) describes, and `Demos.OrderBook.Process.ite_le_zero` bounds an `if` whose branches are at most 0 for any instance.  On the closed goal of `begin`, `simp +decide only []` evaluates the whole goal and reaches the recursion limit, so `Demos.OrderBook.Process.initial_entry` states the table entry of the called function by `decide +kernel`, and `Demos.OrderBook.Process.begin_bounded` uses that equation.

An effect body that binds the results of effect commands, as `Verified.Examples.WasiSys.main` binds the results of `sys` commands, builds its environment with `Verified.Wasi.ResultTy.bindEnv`, a definition that `whnfR` does not unfold.  The type and the context of each `Verified.Env.cons` of that chain are those of the command that bound the value, such as the type that `Verified.Wasi.SysForm.ty` gives a form, while the list `Γ` of the reflected variable states them in another form, and `simp` matches implicit arguments at reducible transparency, so a rewriting lemma for `Verified.Env.get` of `Verified.Env.cons` does not apply.  The `dsimproc` `envGet` of `Verified/Examples/WasiSysTotal.lean` reads the `i`-th value of the chain after `whnfD`, which unfolds `bindEnv`, while `envGetOfIndex` of the order book reads it after `whnfR`, which suffices for the order book's environments.  `Verified/Examples/WasiReadAllSteady.lean` holds a copy of `envGet`, since an import of `Verified/Examples/WasiSysTotal.lean` would make the readAll example depend on the flat call example, and a module of `Verified/Wasi/` that both import would hold one shared `envGet`.

For a body that is one chain of commands without a loop, `Verified/Examples/WasiSysTotal.lean` defines local macros for the forms of `Verified.Wasi.Resource.Rule` that its body repeats, `bind_bound`, `ite_bound`, `ret_bound`, and `write_bound`, and `flat_bound` for a flat call without an output, which reduce the proof of `Verified.Wasi.Resource.Bounded` to one budget for each `bind` and `ite`.  Its macro `charge` closes each leaf by a `simp +decide only` over the cost definitions and `envGet` followed by `omega`, and the `simp` evaluates every liveness test of the leaf, since the modes and the liveness functions are closed terms.  `ite_bound` bounds the budget term `if c then b else b` of the `ite` rule with the private lemma `ite_cost`, stated for any instance of the decision as `Demos.OrderBook.Process.ite_le_zero` is, before `charge` runs, since the `simp` of `charge` unfolds the condition, after which the `ite_self` of the same call does not apply.  `Verified.Examples.WasiSys.body_bounded` of the same file is the proof in this form, and it proves the reported `args` call and `randomGet` without the macros.

Call rules that fix the program and the callee before the case analysis fail by dependent elimination.  `CallBoundRule` instead cases on general indices and reduces by its own pattern matching, and a new rule over indexed commands should take the same form.  The inversion of a run fails in the same way: `cases` on a `Verified.Wasi.Resource.ResourceExec` whose command is fixed, such as `.ret value` or `.sys Call.argsGet .reported [] []`, fails by dependent elimination on the result index of the constructor `call`.  The private `ReturnFact` of `Verified/Examples/WasiSysTotal.lean` matches on the command and the outcome, and one proof by `cases` on general indices gives every inversion that the charges of `main` need: a `ret` returns its expression's value, a `sys` command ends as a run of its action, and a `bind` that returns has a first command that returns and a second command that returns the same value.  Each application's step theorems set `maxHeartbeats` to 4,000,000.  `Demos.RunningSum.writeStep_bounded` and `Demos.RunningSumFp.writeStep_bounded` have the same proof, as do the two `readStep_bounded`, and `Demos.RunningSum.step_body_bounded` shows the step that chooses between them.
