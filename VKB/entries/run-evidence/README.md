# Runs on boards and emulators

The entry applies when a run of an image on the NUCLEO-F767ZI, under QEMU, or in Renode is to support a theorem, a row of the trusted base, or a timing value of a requirement, and when a report states what such a run showed.  A Cortex-M7 board theorem holds in the model under the run conditions of the header of `LeanExe/M7/Proof/Board.lean`, as [the entry on Cortex-M7 board theorems](../m7-board-theorem/README.md) describes.  A board run supports it only when the flash holds the file whose kernel check passed and the run meets those conditions, and a claim about the bytes also needs a far end that keeps the assumptions of the trusted rows on USART3 and the channel, such as sending a record only after the whole answer to the record before.  An emulator run tests the program and the protocol on the emulator's model of the device, so it supports only what that model represents.

`tests/baremetal/m7-board.sh run` writes the image with `st-flash`, reads the flash back, and compares it with the file, the evidence that the row "The file reader and the flash" of [the Cortex-M7 document's trusted base](../../../docs/m7-bare-metal.md#trusted-base) cites.  The reset decides whether the run meets the conditions.  The reset of `st-flash` 1.8.0 leaves C_DEBUGEN set and `DBGMCU_APB1_FZ` at `0x1800`, and with C_DEBUGEN set a debug event halts the processor, so a run after it does not meet them.  `tools/baremetal/stlink_nrst.py` writes the power-on values of the debug registers that a system reset keeps, reads them back, leaves debug mode, and pulses NRST, and `m7-board.sh nrst` runs it in place of the reset of `st-flash`.  [The section on resets on the board](../../../docs/m7-bare-metal.md#resets-on-the-board) takes what `st-flash` writes from stlink's source, `stlink_force_debug` and `stlink_exit_debug_mode`, and what a system reset keeps from the manuals' sections on each register, and a new probe or tool needs the same reading of its source.  The diagnostic image of `tests/TestSupport/M7/Diag.lean` reads the debug registers and `RCC_CSR` at its reset entry and sends them on USART3.  `m7-board.sh diag` first requires the values that the reset of `st-flash` leaves, which shows that the image reads the bits that the probe sets, and then the power-on values after each run of the tool.

After the run, `m7-board.sh` reads over SWD the status that the program never clears, since a read during the run is a debugger access, which the run conditions exclude (follow-up finding 5 of [the BMS review](../../../Demos/Bms/review.md#follow-up-review)).  With the initialization `LeanExe.M7.Nucleo.init`, an overrun sets `ORE` in `USART_ISR`, which no program confined to `USART_ISR`, `USART_RDR`, and `USART_TDR` can clear, so `ORE` clear after the run shows that no byte arrived while `RXNE` was set.  With `LeanExe.M7.Nucleo.initOvrdis`, `OVRDIS` forces `ORE` to 0, so `m7-board.sh` reads `USART_CR3` instead and requires `OVRDIS` set, and the evidence of a lost byte comes from the step's answers (the row "USART3 and the channel").  The board's co-simulation follows a reset over SWD and reads its results from DTCM over SWD, so its runs lie outside the run conditions, as [the section on co-simulation](../../../docs/m7-bare-metal.md#co-simulation) states.  The section "Limits" of the same document lists the board runs that meet the conditions, and a report names the reset that preceded each run.

When the host receives no output, registers and the program's state separate a fault of the program from a fault of the channel.  [The section on limits](../../../docs/m7-bare-metal.md#limits) records sessions in which the ST-LINK's virtual COM port stopped passing the board's output: `USART_ISR` read afterwards showed `RXNE` clear and `TC` set, so the board had read the host's first byte and transmitted, and in the session of the echo of records the program's state in DTCM showed that it had read the host's bytes and answered.  A step added to restore the channel must keep the run conditions.  After a USB reset of the ST-LINK, DHCSR read `0x00010000`, DEMCR and `DBGMCU_APB1_FZ` read 0, and the program's count of segments continued, so `m7-board.sh nrst` with `USBRESET` runs one after the tool.  A filter on the host that drops some of the board's output needs an argument that it cannot hide a fault of the board.  The BMS bridge discards the bytes that it receives before its first record, and after a board reset before its next write, since the board has received no record then, and a board that answered a segment the bridge did not write would give its next answer a board sequence number that differs from the mirror's, which stops the run ([the BMS host's bridge](../../../Demos/Bms/Host.md#the-bridge)).

An emulator's model omits parts of the device, and each run records the omissions that bear on what it checks.  QEMU 8.2.2's CMSDK UART takes a byte from its character device only while `RXFULL` is clear, so its receiver never overruns ([the section on device registers and requests](../../../docs/native-bare-metal.md#device-registers-and-requests)).  Its timer counts on `QEMU_CLOCK_VIRTUAL`, which follows the host's clock while the machine runs without `-icount`, so a time measured under QEMU is the host's (item 12 of [the test plan](../../../docs/native-bare-metal.md#test-plan)).  Renode's USART3 reports `TXE` always set, models no time at the microcontroller's clock, and never overruns its queue ([the section on the NUCLEO-F767ZI](../../../docs/native-bare-metal.md#the-nucleo-f767zi)), and its model lacks bits 24 to 31 of `USART_RTOR` and the bit `OVRDIS` (the section on co-simulation and the header of `tests/baremetal/m7-board.sh`).  An emulator does not run a check of behavior that its model omits: `m7-board.sh emulate` refuses `sha-ovrdis`, whose run tests an overrun.  Where the specification's timing assumes the line's rate, the far end paces its bytes at the line time.  QEMU's UART and Renode's pseudo-terminal move bytes without line time, and without pacing Renode's BMS exchanges ran faster than the relays operate and check 17 failed in `PRECHARGE`, so `tests/baremetal/uart_bms.py` paces each byte at 2.083 ms on QEMU and with `--pace` in Renode, and on QEMU it waits `--start-delay` because QEMU connects the socket before the guest runs ([the BMS host's limits](../../../Demos/Bms/Host.md#limits)).

A run after the reset of `st-flash`, a run that read status over SWD while the program ran, and the co-simulation's runs pass their checks and still lie outside a board theorem's conditions.  `ORE` clear is no evidence for an image with `OVRDIS` set, since the bit forces `ORE` to 0.  A run in Renode or under QEMU is no evidence of the board's timing or of USART3's behavior after an overrun.  The verdict on a run comes from the check's own output, as [the entry on results that show a check passed](../result-validity/README.md) states, and a mirror that judges the answers is itself checked against the specification, as [the entry on executable mirrors of a specification](../mirror-cross-check/README.md) describes.

The worked examples are the runs that [the section on the BMS step](../../../docs/m7-bare-metal.md#the-bms-step) records: `m7-board.sh nrst bms` with `USBRESET` ran the fault-injection schedule, whose board resets go through `stlink_nrst.py` and a USB reset of the ST-LINK, every answer equaled the specification's in native Lean, and `USART_CR3` read `0x00001000` after the run.  `m7-board.sh nrst sha-ovrdis` sends blocks ahead with `uart_sha.py --overrun` and reads `USART_CR3` after the run, while the same phase against `sha.bin` ends with `ORE` set in `USART_ISR` ([the section on the programs on QEMU, in Renode, and on the board](../../../docs/m7-bare-metal.md#the-programs-on-qemu-in-renode-and-on-the-board)).  The row "Run conditions" of the trusted base names runs with the reset that preceded each, as its evidence.  [The entry on hardware facts and trusted assumptions](../hardware-facts/README.md) covers the sources of the facts that the runs test, and [the entry on encodings and co-simulation of machine forms](../machine-form-validation/README.md) covers the runs that validate the model's forms.
