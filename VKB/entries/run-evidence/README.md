# Runs on boards and emulators

The entry applies when a run of an image on the NUCLEO-F767ZI, under QEMU, or in Renode, or a run of a Linux executable on the host's processor or under QEMU's user-mode emulator, is to support a theorem, a row of the trusted base, or a timing value of a requirement, and when a report states what such a run showed.  A Cortex-M7 board theorem holds in the model under the run conditions of the header of `LeanExe/M7/Proof/Board.lean`, as [the entry on Cortex-M7 board theorems](../m7-board-theorem/README.md) describes.  A board run supports it only when the flash holds the file whose kernel check passed and the run meets those conditions, and a claim about the bytes also needs a far end that keeps the assumptions of the trusted rows on USART3 and the channel, such as sending a record only after the whole answer to the record before.  An emulator run tests the program and the protocol on the emulator's model of the device, so it supports only what that model represents.

`tests/baremetal/m7-board.sh run` writes the image with `st-flash`, reads the flash back, and compares it with the file, the evidence that the row "The file reader and the flash" of [the Cortex-M7 document's trusted base](../../../docs/m7-bare-metal.md#trusted-base) cites.  The reset decides whether the run meets the conditions.  The reset of `st-flash` 1.8.0 leaves C_DEBUGEN set and `DBGMCU_APB1_FZ` at `0x1800`, and with C_DEBUGEN set a debug event halts the processor, so a run after it does not meet them.  `tools/baremetal/stlink_nrst.py` writes the power-on values of the debug registers that a system reset keeps, reads them back, leaves debug mode, and pulses NRST, and `m7-board.sh nrst` runs it in place of the reset of `st-flash`.  [The section on resets on the board](../../../docs/m7-bare-metal.md#resets-on-the-board) takes what `st-flash` writes from stlink's source, `stlink_force_debug` and `stlink_exit_debug_mode`, and what a system reset keeps from the manuals' sections on each register, and a new probe or tool needs the same reading of its source.  The diagnostic image of `tests/TestSupport/M7/Diag.lean` reads the debug registers and `RCC_CSR` at its reset entry and sends them on USART3.  `m7-board.sh diag` first requires the values that the reset of `st-flash` leaves, which shows that the image reads the bits that the probe sets, and then the power-on values after each run of the tool.

After the run, `m7-board.sh` reads over SWD the status that the program never clears, since a read during the run is a debugger access, which the run conditions exclude (follow-up finding 5 of [the BMS review](../../../Demos/Bms/review.md#follow-up-review)).  With the initialization `LeanExe.M7.Nucleo.init`, an overrun sets `ORE` in `USART_ISR`, which no program confined to `USART_ISR`, `USART_RDR`, and `USART_TDR` can clear, so `ORE` clear after the run shows that no byte arrived while `RXNE` was set.  With `LeanExe.M7.Nucleo.initOvrdis`, `OVRDIS` forces `ORE` to 0, so `m7-board.sh` reads `USART_CR3` instead and requires `OVRDIS` set, and the evidence of a lost byte comes from the step's answers (the row "USART3 and the channel").  The board's co-simulation follows a reset over SWD and reads its results from DTCM over SWD, so its runs lie outside the run conditions, as [the section on co-simulation](../../../docs/m7-bare-metal.md#co-simulation) states.  The section "Limits" of the same document lists the board runs that meet the conditions, and a report names the reset that preceded each run.

When the host receives no output, registers and the program's state separate a fault of the program from a fault of the channel.  [The section on limits](../../../docs/m7-bare-metal.md#limits) records sessions in which the ST-LINK's virtual COM port stopped passing the board's output: `USART_ISR` read afterwards showed `RXNE` clear and `TC` set, so the board had read the host's first byte and transmitted, and in the session of the echo of records the program's state in DTCM showed that it had read the host's bytes and answered.  A step added to restore the channel must keep the run conditions.  After a USB reset of the ST-LINK, DHCSR read `0x00010000`, DEMCR and `DBGMCU_APB1_FZ` read 0, and the program's count of segments continued, so `m7-board.sh nrst` with `USBRESET` runs one after the tool.  A filter on the host that drops some of the board's output needs an argument that it cannot hide a fault of the board.  The BMS bridge discards the bytes that it receives before its first record, and after a board reset before its next write, since the board has received no record then, and a board that answered a segment the bridge did not write would give its next answer a board sequence number that differs from the mirror's, which stops the run ([the BMS host's bridge](../../../Demos/Bms/Host.md#the-bridge)).

An emulator's model omits parts of the device, and each run records the omissions that bear on what it checks.  QEMU 8.2.2's CMSDK UART takes a byte from its character device only while `RXFULL` is clear, so its receiver never overruns ([the section on device registers and requests](../../../docs/native-bare-metal.md#device-registers-and-requests)).  Its timer counts on `QEMU_CLOCK_VIRTUAL`, which follows the host's clock while the machine runs without `-icount`, so a time measured under QEMU is the host's (item 12 of [the test plan](../../../docs/native-bare-metal.md#test-plan)).  Renode's USART3 reports `TXE` always set, models no time at the microcontroller's clock, and never overruns its queue ([the section on the NUCLEO-F767ZI](../../../docs/native-bare-metal.md#the-nucleo-f767zi)), and its model lacks bits 24 to 31 of `USART_RTOR` and the bit `OVRDIS` (the section on co-simulation and the header of `tests/baremetal/m7-board.sh`).  An emulator does not run a check of behavior that its model omits: `m7-board.sh emulate` refuses `sha-ovrdis`, whose run tests an overrun.  Where the specification's timing assumes the line's rate, the far end paces its bytes at the line time.  QEMU's UART and Renode's pseudo-terminal move bytes without line time, and without pacing Renode's BMS exchanges ran faster than the relays operate and check 17 failed in `PRECHARGE`, so `tests/baremetal/uart_bms.py` paces each byte at 2.083 ms on QEMU and with `--pace` in Renode, and on QEMU it waits `--start-delay` because QEMU connects the socket before the guest runs ([the BMS host's limits](../../../Demos/Bms/Host.md#limits)).

A run of a Linux executable under `qemu-aarch64`, QEMU's user-mode emulator, tests the program and the call layer's descriptions against a second implementation of the calls.  QEMU 8.2.2 checks the whole region of each call that it forwards to the host's kernel with `lock_user` before it forwards the call, and returns `EFAULT` with nothing written where Linux copies until a fault.  It copies `clock_gettime`'s record from the host's C library with its own code, lacks `openat2`, and lets a guest open its own executable's file for writing, where Linux refuses with `ETXTBSY`, so that a guest's `write` to that file changes the guest's memory (the row "QEMU's user-mode emulator" of [the trusted base's section on AArch64 Linux executables](../../../docs/trusted-base.md#a64l-aarch64-linux-executables)).  Of these divergences only the write to the executable breaks the frame rule within its premise: the `EFAULT` lies outside the premise, and `openat2`'s `ENOSYS` and the clock's copy keep the frame with another result or other code.  Under the option `--qemu`, `tests/linux/sys/frame.c` skips the step that requires `ETXTBSY` from an `openat` of its own executable for writing, and the steps of `openat2`, whose results QEMU does not give, and `tests/linux/a64-elf.sh` skips the run of the stamp executable under the name of its output, each with its reason ([the AArch64 document's sections on the Linux call layer](../../../docs/a64-bare-metal.md#the-linux-call-layer) and [on runs](../../../docs/a64-bare-metal.md#runs)).  A skip's reason holds only for an emulator that has the behavior it states: the reasons of `frame.c` name QEMU 8.2.2, and `tests/linux/sys-run.sh` passes `--qemu` to whatever emulator `QEMU_USER` names, so a report of a run under another version states that version and checks the reasons against it.

QEMU's user mode passes its guest an environment that it rebuilds from its own: QEMU 8.2.2 adds each string of its environment, from the last to the first, through `envlist_setenv`, which drops a string without `=` and replaces a string already added of the same name, so the guest receives no string without `=` and only the first string of each name ([`util/envlist.c`](https://github.com/qemu/qemu/blob/v8.2.2/util/envlist.c) and [`linux-user/main.c`](https://github.com/qemu/qemu/blob/v8.2.2/linux-user/main.c)).  A test of an environment with empty strings, strings without `=`, or repeated names therefore runs on the host's processor alone, through `execve(2)` with the strings verbatim, as `tests/linux/a64-wasi.sh` runs `environ.elf` with `tests/linux/execve.py`.  An empty argument vector runs in the same way, and Linux then places an empty string as `argv[0]` and sets `argc` to 1 (`do_execveat_common` in [Linux 7.0's `fs/exec.c`](https://github.com/torvalds/linux/blob/v7.0/fs/exec.c)), so the program reads one empty argument.

A signal that a process ignores stays ignored in its children and across `execve` ([signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)), and systemd starts a service with SIGPIPE ignored unless the unit sets `IgnoreSIGPIPE=no` ([systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)).  A test run inside such a service gets `EPIPE` from a write to a closed pipe in place of the signal, so the case of `tests/linux/a64-elf.sh` in which a reader closes the pipe early reports status 66, the routine's status for a failed write, in place of 141.  A service that runs tests sets `IgnoreSIGPIPE=no`, and the field `SigIgn` of `/proc/PID/status`, in which bit `0x1000` is SIGPIPE, shows which signals a process ignores at the time of the read.

A command of the verified compiler passes its host functions regions that lie apart and far from the memory's end, and Linux answers only within its own range, so the runs of the commands reach few of the conditions that a stub of the shim's A64 binding tests.  Modules written for the stubs reach them: `tests/linux/wasi/prestat-numbers.wat`, the modules of `tests/TestSupport/A64/WasiStringEdges.lean`, the case modules of `tests/linux/a64-wasi-clocks.sh`, and the module that `tests/linux/wasi/files-cases.py` writes call the imports with descriptor numbers that the dialect cannot pass, pointers at and past the memory's end, overlapping and unaligned regions, invalid clocks, and lengths above 2^31.  The subcommands `wasm` and `module` of the executable `a64-wasi` write an executable for each module, the Wasmtime host runs the same modules, and each run writes the errno, the results, and the bytes around each region that the stub writes, so that a write outside the region shows in the output.  The comparison takes Wasmtime's output case by case against a list of the differences that the specification predicts, each with its reason, such as `tests/linux/wasi/files-expected.txt`.  Where Wasmtime orders its writes on overlapping regions differently from the specification, the comparison takes the specification's outputs, which a script such as `tests/linux/strings-edges.py` computes.  A known difference in bytes that no case concerns is removed before the call: Wasmtime 44's `fd_prestat_get` leaves the record's three bytes of padding as they were, while the shim writes all eight, so `prestat-numbers.wat` fills the record with zeros before each call (the row of `fd_prestat_get` in the table of [the WASI manual's differences from Wasmtime](../../../docs/wasi.md#differences-from-wasmtime)).

`tests/linux/a64-wasi-clocks.sh` requires, under `strace -X raw`, the calls of each case with every argument and no call of another name but `write` and `exit_group`, which excludes a stub that writes the timespec at another offset or passes flags to `getrandom` while its outputs are right.  strace's fault injection, such as `-e inject=openat:error=EPERM`, `inject=openat:retval=3`, or `inject=close:retval=5`, gives a routine results that no launch produces, without a seccomp filter or a launcher, among them a descriptor and a positive result of `close`, which no filter that returns an errno gives, and `tests/linux/a64-wasi-preopen.sh` and `tests/linux/a64-wasi-files.sh` run the error paths of the startup and of the stubs in this way.  With `-e raw=openat,close`, strace prints the arguments and the result in hexadecimal with the prefix `0x`, such as `0x3` for descriptor 3 and `0x84000` for the flags, and 0 as a bare `0`, so a script that reads a descriptor from the log parses both forms, as `tests/linux/a64-wasi-preopen.sh` does.  Without `-e trace=`, the log of a run that ends with status 67 shows that no call lies between the startup's calls and `exit_group(67)`, which tells the startup's status from a guest's `proc_exit(67)`, and a run with standard input closed writes strace's log to standard error, so that no file that strace opens takes descriptor 0 from the startup's `openat`.  QEMU 8.2.2 lacks `openat2`, so `a64-wasi-files.sh` compares each run under `qemu-aarch64` with a native run under strace's injection of `ENOSYS` into every `openat2`, and `tests/manifest-check/run.sh`, whose runs need the results of `openat2`, refuses an emulator older than QEMU 9.2, the first release that implements `openat2`.

strace's `-e inject=CALL:retval=N` gives a call a short count without a short read: it skips the call and returns N, so the buffer keeps its earlier bytes, which a theorem stated for every reply covers, and the run tests a program's loop on that count.  A short read that Linux returns into a valid buffer needs a pending signal, which `-e inject=getrandom:signal=SIGCONT` leaves at each call.  Linux 7.0's `get_random_bytes_user` in `drivers/char/random.c` tests for a pending signal only after each 4,096 bytes and only while bytes remain, so under that injection the 5,000-byte `getrandom` of `clockrandom.elf` returned 4,096 bytes and the shim asked for the other 904 at the buffer's address plus 4,096, while the random histogram's reads of 4,096 and 3,904 bytes returned in full (the section "The native executable writes the counts" of `Demos/RandomHistogram/README.md`).  A read of at most 4,096 bytes therefore returns fewer bytes only when the copy faults.  A C test of `getrandom` makes the raw system call, since glibc 2.41's `getrandom()` uses the vDSO (the section "Review of the premise on short reads" of `Demos/RandomHistogram/review.md`).

A run after the reset of `st-flash`, a run that read status over SWD while the program ran, and the co-simulation's runs pass their checks and still lie outside a board theorem's conditions.  `ORE` clear is no evidence for an image with `OVRDIS` set, since the bit forces `ORE` to 0.  A run in Renode or under QEMU is no evidence of the board's timing or of USART3's behavior after an overrun.  The verdict on a run comes from the check's own output, as [the entry on results that show a check passed](../result-validity/README.md) states, and a mirror that judges the answers is itself checked against the specification, as [the entry on executable mirrors of a specification](../mirror-cross-check/README.md) describes.

The worked examples are the runs that [the section on the BMS step](../../../docs/m7-bare-metal.md#the-bms-step) records: `m7-board.sh nrst bms` with `USBRESET` ran the fault-injection schedule, whose board resets go through `stlink_nrst.py` and a USB reset of the ST-LINK, every answer equaled the specification's in native Lean, and `USART_CR3` read `0x00001000` after the run.  `m7-board.sh nrst sha-ovrdis` sends blocks ahead with `uart_sha.py --overrun` and reads `USART_CR3` after the run, while the same phase against `sha.bin` ends with `ORE` set in `USART_ISR` ([the section on the programs on QEMU, in Renode, and on the board](../../../docs/m7-bare-metal.md#the-programs-on-qemu-in-renode-and-on-the-board)).  The row "Run conditions" of the trusted base names runs with the reset that preceded each, as its evidence.  [The entry on hardware facts and trusted assumptions](../hardware-facts/README.md) covers the sources of the facts that the runs test, and [the entry on encodings and co-simulation of machine forms](../machine-form-validation/README.md) covers the runs that validate the model's forms.
