# Linux calls through the call layer

The entry applies when a program makes Linux system calls through the call layer of `LeanExe/Linux/`, when a call joins the layer's table, when a binding maps an architecture's call instruction or a C semantics to the layer, and when a proof follows a run of `LeanExe.A64.ProcReachWith`.  The layer holds no instruction and no register, and an architecture's binding maps its call instruction and its registers to the layer, as `LeanExe.A64.pstepWith` does for A64, the only such binding.  [The AArch64 document's section on the Linux call layer](../../../docs/a64-bare-metal.md#the-linux-call-layer) describes the layer and the binding, and [its section on what the Linux target trusts](../../../docs/a64-bare-metal.md#what-the-linux-target-trusts) states the trusted claim with Linux's code for each call.

`LeanExe.Linux.Call` describes a call by its name, its numbers on arm64 and x86-64, the kinds of its parameters in argument order (`LeanExe.Linux.Param`), whether it returns a descriptor, and whether it ends the process, and `tools/linux-calls.py` generates `LeanExe.Linux.table` from syzkaller's `sys.txt` and `sys.txt.const` in `tests/linux/syzlang/`.  Syzlang supplies a call's shape: the order of its arguments, the direction of each pointer, the argument that holds each length, the layout of each structure, and whether the result is a descriptor.  It supplies little of the call's meaning: it does not state what the call returns otherwise, how much of an output it writes, or how many bytes of a file name the kernel reads, and its integer types, which serve the fuzzer, need not be the C type through which the kernel reads an argument, as `openat`'s mode is a `umode_t` in the kernel.  Its flag lists are values for the fuzzer to generate, and the kernel accepts others: the list `getrandom_flags` holds `GRND_NONBLOCK` and `GRND_RANDOM`, while Linux 7.0's `getrandom` in `drivers/char/random.c` also accepts `GRND_INSECURE`.  The meaning comes from the kernel's source, which the section on what the Linux target trusts cites call by call.

`LeanExe.Linux.step` is the frame rule.  When every byte of every region of the request is accessible, the memory after the call differs from the memory before only in the output region, which holds the reply's bytes, and the event, `LeanExe.Linux.Event`, records the call, its argument words, the bytes of its input regions, the bytes of its output region before and after the call, and its result.  A reply, `LeanExe.Linux.Reply`, is a result and a function from each offset of the output region to a byte, and `LeanExe.Linux.Replies` gives the reply to each call by the number of events before it.  The function is arbitrary, so for a memory determined by its bytes, as that of `LeanExe.A64.a64Memory` is, every memory that differs from the memory before the call only in the output region is the memory of some reply, the replies that describe a run of the kernel exist whenever the kernel keeps the frame, and a theorem stated for every record of replies holds for every value that the kernel returns.  The rule constrains no result, so a program tests each result before it relies on it, as the stamp routine tests that a read returned at most its count.  A property beyond the frame that a theorem needs and the program does not test goes into a predicate over the trace that the theorem assumes, so that the trusted rule stays the frame and only a theorem that assumes a property relies on it, as the row "Properties of replies" of [the trusted base's section on AArch64 Linux executables](../../../docs/trusted-base.md#a64l-aarch64-linux-executables) states.  `LeanExe/Linux/Replies.lean` names `LeanExe.Linux.FreshOpens`, `LeanExe.Linux.NsecBound`, `LeanExe.Linux.RandomCount`, and `LeanExe.Linux.WrittenPrefix`, and the stamp theorems assume none of them.

The layer reads and writes memory through `LeanExe.Linux.Memory`, a byte read, a byte write, and a test that each byte of a region is accessible, and `LeanExe.Linux.step_frame` proves the frame for every memory that meets `LeanExe.Linux.Memory.Lawful`.  The laws constrain writes only at accessible bytes, which a memory whose store fails outside a block's permissions can meet.  The laws `read_write_same` and `read_write_other`, of a read after a write at an accessible byte, do not give the frame of the byte-by-byte write of `LeanExe.Linux.Memory.writeBytes`: a memory whose test accepts every region of two bytes and refuses every single byte meets them vacuously, while its writes may change any byte.  The law `mapped_bytes`, that each byte of an accepted region is accessible, and the law `mapped_write`, that a write at an accessible byte keeps every answer of the test, close that gap: `step_frame` turns an accepted region into accessible bytes with `mapped_bytes`, and `LeanExe.Linux.Memory.writeBytes_other` keeps them accessible through its induction with `mapped_write`.  `LeanExe.A64.a64Memory` is a total memory that meets the laws of `LeanExe.Linux.Memory.Lawful` (`LeanExe.A64.a64Memory_lawful`), and a binding over a memory of blocks with a partial store states those laws from the start.

The frame is a claim about the table's calls together.  A `write` to `/proc/self/mem`, which `openat` can open, writes the process's own memory at the file's position, which the table's calls keep at 0, where Linux returns `EIO` without moving it.  A `write` to the running executable's file would change the process's private mappings of it, which Linux prevents by refusing with `ETXTBSY` to open that file for writing.  A call that moves a file's position, writes at a position, or maps a file would break the frame of `write`, so `tools/linux-calls.py` lowers only the calls of its list `ADMITTED`, and a call joins the list after a review of the kernel's code for the whole set.

`LeanExe.A64.pstepWith` binds the layer to A64.  At `SVC #0` it looks up X8 among the arm64 numbers of its table, ends the run at a call outside the table or at a terminal call such as `exit_group`, and otherwise applies the layer's rule through `LeanExe.A64.sysCall`, with the argument words `LeanExe.A64.argWords` from X0 upward and the replies at the number of events in the trace, sets X0 to the result, and appends the event as `LeanExe.A64.Event.sys`.  It never applies `LeanExe.A64.Kernel.svc`, so every `read` and `write` of a run takes the layer's rule, whose event names the descriptor, the addresses, and the counts.  `LeanExe.A64.pstepWith_svc` takes `SVC #0` at a call of the table to `sysCall`, and the lemmas `LeanExe.A64.sysCall_read`, `LeanExe.A64.sysCall_write`, `LeanExe.A64.sysCall_close`, `LeanExe.A64.sysCall_clockGettime`, `LeanExe.A64.sysCall_getrandom`, `LeanExe.A64.sysCall_openat`, and `LeanExe.A64.sysCall_openat2` evaluate each call from the premise that its regions lie in Normal memory, with the region lemmas that the generator writes for each call, such as `LeanExe.Linux.regions_read`, and with `LeanExe.A64.writeBytes_a64` and `LeanExe.A64.readBytes_a64`, which state the layer's byte functions as `LeanExe.A64.writeList` and `LeanExe.A64.readList`.  `LeanExe.A64.run_svcRet` follows the runtime's routine `SVC #0; RET` from its first word to the return to the address in X30.

Linux gives `openat` the lowest free descriptor (`fs/file.c`), so a process that its parent started with descriptor 0, 1, or 2 closed receives that number from an open.  The trace of `pstepWith` names the descriptor of every call, so a theorem over the trace needs no assumption about descriptors 0 to 2 when the program gives them no meaning, as the stamp routine does: `tests/linux/a64-elf.sh` runs it with standard input closed, and each `openat` then returns 0.  A program that gives 0 to 2 the meaning of standard streams checks that meaning at its start, for example by requiring its first `openat` to return 3, which Linux gives only when 0 to 2 are open.  No test of a descriptor's number excludes a path that names a standard stream, such as `/dev/stdin`, `/proc/self/fd/0`, or a symbolic link, which opens the same file under a larger number, so the documents of such a program state that limit.

A reply sets the whole output region, so a read into a block leaves the bytes that the read returned at the region's start and bytes of the reply after them, and a loop's invariant cannot state the block's content as the input alone.  `LeanExe.A64.ReadStore` states a store related to the machine, written only within the block (`LeanExe.Pipeline.WritesWithin`), whose prefix holds the bytes that the reads returned, and `LeanExe.A64.ReadStore.write` carries it through a read.  The compiler's theorem of the function needs only that prefix: `LeanExe.Pipeline.Heap.At.writesWithin` and `LeanExe.Pipeline.Heap.Block.writesWithin` carry the heap and the allocator's block through writes within the block's capacity, and `LeanExe.A64.block_buffer` reads the function's buffer from the block's first bytes, so `LeanExe.A64.stamp_runs_any` assumes no property of the replies, `WrittenPrefix` included.  The bytes that a trace moved through a descriptor count per event with the event's own result: `LeanExe.Linux.readData` and `LeanExe.Linux.writeData` take the first bytes of each read's output or each write's input, as many as its result, when the result is at most the count (`LeanExe.Linux.Event.readBytes` and `LeanExe.Linux.Event.writeBytes`), so a failed call, whose result is a negated error number, contributes nothing.

The worked examples are `LeanExe.A64.run_stampReadLoop`, which follows the stamp routine's read loop with `ReadStore` and records its calls as `LeanExe.A64.ReadLoop`, `LeanExe.A64.run_stampWriteLoop`, which records the write loop's calls as `LeanExe.A64.WriteLoop`, `LeanExe.A64.stampProgram_run`, and `LeanExe.A64.stamp_runs_any`.
