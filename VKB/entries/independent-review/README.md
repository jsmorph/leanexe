# Independent review of specifications and designs

The entry applies when a specification and its sample inputs, or a design note for an increment, are complete and nothing has been built on them.  A theorem that equates a program with its specification says what the specification says, and [the trusted base's section on specifications](../../../docs/trusted-base.md#specifications) trusts each such definition to say what its name says.  A review by an agent that did not write the specification checks that trust before a program and a proof depend on it, and a design review checks the claims of a plan before code depends on them.

[Step 5 of the verified-request skill](../../../.claude/skills/verified-request/SKILL.md#stage-1-the-specification) gives a fresh agent only the request, the specification, the samples, and the samples' outputs, and none of the author's reasoning or plans.  The reviewer decides for each case of the input whether the specification gives what the request asks, names every case that the request leaves open, and checks each sample's output by hand from the request.  It may build its own executable model from the request alone and compare it with the samples and on random inputs, and it runs no build or test of the repository's Lean code, so its wrong programs and wrong methods run in its model.  The two reviews of Dijkstra's specification each built a model of the program at 64-bit words and an oracle of the request, the first oracle Dijkstra's algorithm on exact integers checked against Bellman and Ford's and the second a search of every walk of at most `n` arcs, and compared model and oracle on 503,042 and 222,300 inputs (`Library/Graphs/Dijkstra/review.md`).

The reviewer runs wrong programs on the cases, and a wrong program that passes every case gets a case that detects it, or the review records that no input can and why.  A Dijkstra program without the test `s < n` passes every case in which each source of `n` or more reads empty ranges of `first`, so the cases include a source of `n` with a range of one arc.  A program without the skip of done vertices computes the same result on every input, so only the program text shows the skip that the request asks for.  In quicksort, step Q9 sorts every array, so a defect of steps Q1 to Q8 that keeps a permutation and finishes changes no result, and the theorems do not exclude it, since `Library.Sorting.Quicksort.quicksort_eq` depends on `Library.Sorting.Quicksort.stages_perm`, which states only that those steps permute the array (`Library/Sorting/Quicksort/review.md`).  `Library/Combinatorics/DancingLinks/review.md` pairs each wrong program with the inputs that detect it in one table and lists the classes that no case covers, with the reason, in another.

A specification made only of properties of the result admits a wrong method that has those properties, so it also states the equation with the algorithm that the request names.  An index `u mod (j + 1)` or a loop with increasing `j` meets the shuffle's other properties, so the first field of `Library.Random.Sampling.Shuffles` states the equation with Knuth's Algorithm P, `Library.Random.Sampling.algorithmP`.  The reviews of Algorithms S and R found wrong methods that meet the other three properties, so the specifications state `Library.Random.Sampling.algorithmS` and `Library.Random.Sampling.algorithmR` (`Library/Random/Sampling/review.md`).  Properties that determine the result exclude every other output, as `Library.Graphs.Dijkstra.distances_unique` shows of `Library.Graphs.Dijkstra.Distances`.  The properties of `Library.Trees.Avl.SearchTree` do not determine the tree, since another balanced insertion with the same keys and height meets them, so the AVL specification fixes the result by `Library.Trees.Avl.algorithmA` and proves the properties in `Library.Trees.Avl.algorithmA_props`.  `Library.Trees.AvlDelete.Removes` states properties of the result of `Library.Trees.AvlDelete.deleteA`, and its field `unchanged` states the request's sentence that an absent key leaves the tree unchanged, without which another balanced tree with the same keys and height meets the other fields.

The reviewer computes the coverage of the cases over the combinations that the method distinguishes.  The AvlDelete reviews found that the ten trees missed eleven of the 105 combinations of location, side, case, and depth that balanced trees admit, and two key sequences give the missing double rotations, which a model confirms against the 105 combinations (`Library/Trees/AvlDelete/review.md`).  The reviewer also checks each comment and docstring against the theorem it cites, as [the entry on claims and the theorems that state them](../claims-and-theorems/README.md) describes.  For each disagreement the author corrects the specification or the samples, or records in `review.md` why the request supports the specification, and a new agent reviews the result (steps 6 to 8 of the skill).

A design note for an increment gets the same review before code depends on it.  Its claims cite code, probes, and primary sources.  A fresh agent checks each citation, estimate, and hardware fact against the tree, with a model where the claim can be computed, and the revision records for each finding whether it is adopted and why.  The design review of Algorithms S and R compared both programs with Knuth's steps and Vitter's array form in exact rationals on 40,000 cases, and it noted that Knuth's Algorithm R keeps a table of indices and sorts it at the end, so the request names Vitter's array form.  The review of the BMS requirements recomputed the vectors, the CRCs, the line times, and the fault table with its own encoder and zlib, read the datasheet's pages, and tested M1 on its own machine, and [its table](../../../Demos/Bms/review.md#review) gives for each finding the verification and the response, a declined finding with its reason among them.

A review of a numerical program builds its own model of the arithmetic and runs its wrong programs through the final tests.  The reviewers of the passive-safety and gating requirements modelled the interval library's outward rounding from `Library/Numerics/Bounds/Program.lean` and `Library/Numerics/Interval/Program.lean` and found that it moves an exact 0 below 0, where a square root or a comparison with a zero threshold then rejects, before the modules ran (finding 3 of `Demos/PassiveSafety/review.md` and finding 1 of `Demos/Gate/review.md`).  The reviewer of the screening requirements kept its 24 wrong programs as variants of one model that computes the output of the interface, so that each variant ran through the checks of `tests/screening/oracle.py`, which measured what the final tests detect rather than what the plan describes.  The checks rejected 23 of them, among them a status 0 at the cap that the reviewer expected no check to detect, and only the proof excludes the last (the section "Wrong programs" of `Demos/Screening/review.md`).  An oracle that shares the method of the program under test agrees with that method's mistakes, so the gating demo's test computes the least cost of an assignment by enumeration, by dynamic programming over subsets, and by successive shortest paths with the Bellman–Ford method, none of which computes the dual potentials that its solver's certificate holds (the section "Tests" of `Demos/Gate/requirements.md`).  An oracle of a cover by boxes needs consistent samples of every parameter, and the geolocation oracle covers the region for each parameter by a Lipschitz subdivision, which drops a cell when a residual at its center exceeds the bound by more than a bound of the residual's change over the cell, after the review found that samples around the central parameter missed the consistent set of the parameter that produced the measurements (findings 3 and 13 of `Demos/Geolocation/review.md`).

A review that receives the author's reasoning reads the request through it, so the skill withholds the reasoning and plans.  A review without a model cannot find a wrong program that passes every case, a statement that a run falsifies, or a combination that no case reaches, and the reviews above recorded defects of each kind.  A wrong program that passes every case and that the review does not record leaves the next reader unaware that the cases admit it, so `review.md` names each such class.  The model and the cases are checks, to which [the entry on checks that can fail](../discriminating-checks/README.md) applies.

The worked examples are the `review.md` files of `Library/Random/Sampling`, `Library/Sorting/Quicksort`, `Library/Graphs/Dijkstra`, `Library/Trees/Avl`, `Library/Trees/AvlDelete`, and `Library/Combinatorics/DancingLinks`, `Demos/Bms/review.md`, and `Demos/Screening/review.md`.  [The entry on transcriptions of standards](../spec-transcription/README.md) covers specifications that transcribe a published standard, whose review compares the transcription with the standard, and [the entry on specification call theorems](../spec-call-theorem/README.md) gives the uniqueness theorems that make a property specification exclude every other output.  [The entry on testing a statement before its proof](../statement-testing/README.md) applies the reviewer's model to new theorems.
