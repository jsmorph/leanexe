# Types that elaboration chooses

The entry applies when a specification, a proof-side definition, or a trusted translation holds a binder or a numeric literal without a type, so that Lean chooses the type by unification, by a default instance, or by a coercion.  The chosen type can differ from the intended one without an error, and the statement then means something other than it seems to, a rewrite finds no match, or a translation computes another function.  The entry also applies to an elaboration error that names a heterogeneous operator over two types, such as `failed to synthesize HSub Int64 ℕ`.

Type every binder and every literal of a specification and of a proof-side definition, as in `fun n : Nat => …` and `(1023 : Int64)`, so that each term has the type that the statement intends rather than the one that elaboration reaches from its context.  A proof-side definition that restates an expression of the program should elaborate to the term that the program's unfolding gives, which a `simp only` with the definition, or `rfl`, confirms.  Test a trusted translation by `rfl` or by evaluation at a negative operand and at an extreme one, since a coercion to `Nat` maps every negative integer to 0 and agrees with the intended conversion at every nonnegative operand, so tests at nonnegative operands pass, as [the entry on code around an executable reference](../reference-harness-audit/README.md) describes.

The definition `Library.Numerics.Float64.Log10.Log10Bits.kWord10` restates the program's `k0 + UInt64.toInt64 (xw >>> 32 >>> 20) - 1023` with `k0 : Int64`, and with the literal untyped it failed with `failed to synthesize HSub Int64 ℕ`, while the program's `let` of the same text elaborated.  Written `(1023 : Int64)`, it elaborates to the program's term, as [the entry on signed quantities as `Int64` values](../signed-integer-values/README.md) records.  A specification that writes `(magnitude s).map fun n => -(n : Int)` with `magnitude s : Option Nat` elaborates the map over `Option Int` and lifts the coercion into a `do` block over `magnitude s`, so a rewrite with `Option.map_some` finds no `Option.map f (some a)`.  `Library.Numerics.Decimal.Int64Text.denote_minus` and `Library.Numerics.Decimal.Int64Text.denote_plain` restate the specification's branches with the binder typed, `fun n : Nat => …`, by `cases` on the option and `rfl`, as [the entry on decimal text](../decimal-conversions/README.md) describes.  In Sail's Lean translation, the back end writes an integer of the model where Lean expects a natural number, and lean-sail's coercion `CoeT Int x Nat` converted it with `x.toNat`, while `asl_Int`'s `result` took the type `Nat` from its first branch, so the translation's SInt, and FixedToFP of a signed operand, gave 0 for every negative value.  `tools/sail/lean-sail-v6.diff` deletes the coercion, and `tools/sail/fix-output.sh` types `result` as `Int` and writes `.toNat` at each other place, after which a comparison of the translation's constants with and without the coercion differs only at `asl_Int` ([the Sail README's section on elaboration](../../../tools/sail/README.md#elaboration), and [the entry on floating-point equations from Sail](../sail-fp-equations/README.md)).

The worked examples are `Library.Numerics.Float64.Log10.Log10Bits.normal_bits` and `Library.Numerics.Float64.Log10.Log10Bits.subnormal_bits`, which unfold `kWord10` together with the program's `Library.Numerics.Float64.Log10.log10`, and `Library.Numerics.Decimal.Int64Text.expectedRead_print`, which rewrites with `denote_minus` and then with `Option.map_some`.  The first two close with a `simp only` that unfolds `kWord10` and the program side by side, which succeeds because the typed literal gives the program's term.  The signed theorem of `tools/sail/F7/FixedToFP32.lean` holds for the translation in which `asl_Int`'s `result` has the type `Int` (its header).
