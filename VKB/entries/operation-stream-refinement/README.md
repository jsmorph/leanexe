# A loop over an operation stream that refines a list specification

This entry applies when the input of a program encodes a sequence of operations, such as the pairs `xs[2i], xs[2i + 1]` of a code and a value, and the program runs them in a `LeanExe.loop` over a data structure held in the loop's state.  Its specification runs the same operations over an abstract value, such as a list of the stored words, by structural recursion: `runOps (operations xs) [] []` for the binary heap's priority queue and for the linear-probing hash table.  The goal is that the program's outputs equal the specification's, `prog xs = (runOps (operations xs) [] []).toArray`.

Rewrite the specification as a fold of one step, `runOps ops s out = (ops.foldl specStep (s, out)).2`, by induction on the operations (`Library.Queues.BinaryHeap.runOps_eq`).  Define `Agrees s st`, which relates the loop's state to the abstract state, and prove that one operation keeps it (`step_agrees`): for the binary heap, the prefix `h[0, n)` is a heap whose words are a permutation of the queue's words, and the outputs are equal (`Library.Queues.BinaryHeap.Agrees`).  Run `LeanExe.Dialect.loop_induction` with `P k s := Agrees s (((operations xs).take k).foldl specStep init)`.  In the step, `List.take_add_one` writes the prefix of `k + 1` operations as the prefix of `k` with one operation appended, `List.foldl_append` splits the fold, and `generalize` names the fold over the old prefix so that `step_agrees` applies to it.  At the end, `List.take_of_length_le` removes the `take`, and `runOps_eq` with the output component of `Agrees` closes the goal, as `Library.Queues.BinaryHeap.heapQueue_eq` shows.

The words that count the stored items must not wrap, so the invariant or the precondition bounds them.  The binary heap's invariant bounds the heap's size and the array's size by the loop index `k`, which stays below `xs.size / 2 < 2^63`, so `n + 1` and the array's size as a word do not wrap (`Library/Queues/BinaryHeap/Proof.lean`, header), and `step_agrees` takes `h.size < 2 ^ 63` and `n.toNat < 2 ^ 63` and shows that each rises by at most one.  The hash table's `Agrees` states that the counter equals the number of keys, which `Library.HashTables.LinearProbing.Good` bounds by the number of slots, and `hashTable_eq` takes the precondition `slots xs < 2 ^ 63`, which `hashTable_call` carries to the call theorem with `Verified.call_on`.  `LeanExe.Common.toNat_add_one` states `(x + 1).toNat = x.toNat + 1` under such a bound, which both proofs derive inline instead.  `LeanExe.Dialect.get_set`, `push_get_lt`, and `push_get_size` give the words of an array after a write or a push, and `take_get_mem` gives the position of a word of a prefix.

The compiler does not accept a loop body that chooses among whole states with nested `if`s, so `Library.Queues.BinaryHeap.step` computes each component of its state with its own `if` and ends in one tuple (docstring of `step`).  `step_agrees` therefore unfolds `step` and `specStep` together and rewrites the conditions of each component with `ite_eq_left` and `ite_eq_right`.  The hash table states slot arithmetic with `adv` and `dist`, which avoid `%`, so that `omega` decides it after `split_ifs` (`Library/HashTables/LinearProbing/Proof.lean`, header).  The two modules each define `specStep`, `runOps_eq`, `Agrees`, and `step_agrees`, and one refinement lemma over a step would replace the loop part of both proofs.

The worked examples are `Library.Queues.BinaryHeap.heapQueue_eq` and `Library.HashTables.LinearProbing.hashTable_eq`, with `Library.HashTables.LinearProbing.hashTable_call` for the precondition.  The order book's specification has the same form: `Demos.OrderBook.Spec.run_eq` writes a run as `(records ws).foldl runStep (b, [])`, and `Demos.OrderBook.Spec.foldl_valid` keeps a book valid while its next id plus the number of records stays at most `2^64 - 1`.  The heap invariants that `Agrees` uses are in [the entry on array heaps](../heap-sift-invariant/README.md).
