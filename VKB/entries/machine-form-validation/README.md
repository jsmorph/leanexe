# Encodings and co-simulation of machine forms

The entry applies when the A64 or the Cortex-M7 back end gains a machine form, when a back end for a new target starts, and when a form's encoding or its meaning in the model changes.  The model's decoder gives an image's bytes their meaning in every image theorem, and the model's `exec` gives the instructions theirs, so each form needs evidence that the encoder writes the architecture's encoding and that the model agrees with the processor in the configuration in which the proved images run.  The rows on the instruction model of [the trusted base's A64 section](../../../docs/trusted-base.md#a64-aarch64-images) and [its M7 section](../../../docs/trusted-base.md#m7-cortex-m7-images) list that evidence: the comparison with the GNU assembler, co-simulation, and the Isla theorems.

The encoder writes each form as its fixed bits plus its fields at their positions, a sum of natural numbers, so that the proofs read each field back with `omega` and use no bit-vector decision procedure (headers of `LeanExe/A64/Encode.lean` and `LeanExe/M7/Encode.lean`).  `LeanExe.A64.decode_encode` states that the A64 decoder reads every encoded word back as itself.  The M7 decoder decides the length from the first halfword, reads the fields, and returns the candidate whose encoding equals the halfwords, so it accepts exactly the bit patterns that the encoder writes.  `LeanExe.M7.decode_encode` reads every instruction back with any halfwords after it, `LeanExe.M7.decode_sound` states that a decoded instruction's encoding is the prefix that the decoder read, and `LeanExe.M7.encodeNat_injective` that no two instructions share an encoding, and the proofs split on the forms and decide every field with `omega` ([the Cortex-M7 document's section on encoding](../../../docs/m7-bare-metal.md#encoding)).  A pattern that the encoder never writes, such as UMULL with equal destinations or B<cond>.W with condition 14 or 15, then decodes to nothing, and the model stops on it.

A comparison with the GNU assembler takes samples of every form, with each register field at its extremes and in each role, each immediate field at 0 and at its largest value, every condition, and the extreme branch offsets.  `tests/baremetal/m7-encode.sh` assembles the samples with `arm-none-eabi-as -march=armv7e-m -mthumb`, requires an object without relocations, so that the assembler resolved every branch, and checks that the assembler's halfwords of each sample are the encoder's and decode to the sample.  With one bit of the assembled bytes changed, the comparison reports that sample.  The A64 comparison takes register 31 in each role and the extreme branch offsets ([the AArch64 document's section on encoding and the image's bytes](../../../docs/a64-bare-metal.md#encoding-and-the-images-bytes)).

Co-simulation runs each form on the processor in the configuration that the model claims.  The A64 harness runs each case at EL1 with the MMU on and RAM as Normal memory, with FPCR's DN set as the back end's images set it, under TCG and under KVM pinned in turn to each core type ([the AArch64 document's section on co-simulation](../../../docs/a64-bare-metal.md#co-simulation) and the header of `tests/baremetal/a64-cosim.sh`).  The M7 harness of `tests/baremetal/m7-cosim.sh` saves the state in floating-point registers, so it runs under the C path's startup with the floating-point unit and the MPU enabled, outside the proved configuration.  The board's image of `tests/TestSupport/M7/BoardCosim.lean` boots from the table, self-loop, and initialization of the proved images, with no startup code, floating-point unit, or MPU, so each case runs in Thread mode on SP_main at reset clocking with the caches off.  A harness keeps its own state in resources that no modeled form names: the board's harness keeps the output record's address in r12 and uses encodings outside the model, `MSR APSR_nzcvq`, `MRS`, and `BX r0`, which the GNU assembler assembles.  The checker regenerates each case's inputs from the seed, runs `exec` from the case's state, and compares the registers, the flags, the landing address, the memory window, and the device register.  Random fields can miss a value that the generator emits, so fixed cases cover each class of immediate field, offset, condition, and branch direction that the generator and `udivmod64` emit.  Each fixed case continues the seeded sequence, so the seeded cases stay those of a run without the fixed ones, and `seeded` leaves the fixed cases out.  A device form needs a register that reads back as written and changes neither the transmitter nor the receiver, and the board's cases use `USART_RTOR` with its timeout disabled (the header of `tests/TestSupport/M7/BoardCosim.lean`).

A co-simulation counts as evidence only with a step that shows that it can fail.  `tests/baremetal/m7-board.sh cosim-check` also checks the board's results against the model with `ADC`'s carry in replaced by 0 and requires that check to fail, and in each run on the board exactly the `ADC` cases with C set differed ([the Cortex-M7 document's section on co-simulation](../../../docs/m7-bare-metal.md#co-simulation)).  `m7-board.sh cosim` requires the header's word `0x600DCAFE` and as many saved cases as the image holds, so a run that stopped early fails.  On the A64 side, a printed state with one register changed makes the checker report that case.  [The entry on checks that can fail](../discriminating-checks/README.md) states the general rule.

Each form also needs its theorem against Isla's trace, which [the entry on instruction forms against Isla](../isla-form-proofs/README.md) covers.  Isla's Arm model represents IMPLEMENTATION DEFINED choices as constants of its configuration and CONSTRAINED UNPREDICTABLE choices as symbolic values, so a theorem covers every operand value and exposes a dependence on either, which no test on particular processors can reveal ([the AArch64 document's section on Isla](../../../docs/a64-bare-metal.md#isla)).  The rows on the instruction model claim a theorem for every form that the generator emits, so the row names a form that an image runs without a theorem, with the form's other evidence, until the theorem exists.  [The entry on code around an executable reference](../reference-harness-audit/README.md) covers the harness functions and edits on which the traces rest.

Co-simulation covers sampled states on particular implementations, and the documents record what it leaves out.  The A64 cases keep their accesses inside the window, their branches within 16 words, and no store to the UART.  The board's cases test the Cortex-M7 r1p0 only in the states in which the model runs, and they do not test branches beyond 16 words, which rest on `decode_encode` and the GNU assembler, the self-loop and the trap stubs, or device registers other than `USART_RTOR`.  The board's runs follow a reset over SWD and read their results over SWD, so they lie outside the run conditions of the board theorems, as [the entry on runs on boards and emulators](../run-evidence/README.md) describes.  In Renode the same image runs to its end, and every difference lies in bits 24 to 31 of `USART_RTOR`, which Renode's model does not store, so a co-simulation also exposes what an emulator omits.  The floating-point forms add a vector test whose operand classes lie at ties, near ties, the overflow threshold, and the subnormal range, and a run of the single-precision code on every 32-bit word ([the AArch64 document's section on the exhaustive test of the single-precision forms](../../../docs/a64-bare-metal.md#the-exhaustive-test-of-the-single-precision-forms)).

The worked examples are the commands of [the Cortex-M7 document's section on running the tests](../../../docs/m7-bare-metal.md#running-the-tests): `tests/baremetal/m7-encode.sh`, `tests/baremetal/m7-cosim.sh`, and `m7-board.sh cosim-image`, `cosim`, and `cosim-check`, with `tests/TestSupport/M7/BoardCosim.lean`, which the full check does not build.  On AArch64 they are `tests/baremetal/a64-cosim.sh`, `tests/baremetal/a64-fpvectors.sh`, and `tests/baremetal/a64-fpexhaust.sh`.
