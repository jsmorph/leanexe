# Functions over `LeanExe.Bytes` as functions over lists

The entry applies when a theorem states the bytes of a `LeanExe.Bytes` value as a `List UInt8`, such as a program's output, or builds a `LeanExe.Bytes` value from a list, such as a message that a program reads from a device, `⟨⟨msg.toArray⟩⟩`.  The dialect's operations `LeanExe.Bytes.get`, `LeanExe.Bytes.build`, and `LeanExe.Bytes.size` read and build the `ByteArray` under the value, while the specification takes and gives lists.  The proof relates the two through the `Array` under the `ByteArray`.

Write the list as `b.data.data.toList`, `Array.toList` of the array under the `ByteArray`, so that `Array.length_toList` and `Array.getElem_toList` apply, as `Demos.Rcv.ReadProgram.bytesOf` and `Demos.StreamFold.byteWords` do and as `LeanExe.A64.BytesRuns` states a program's output.  For a value that `LeanExe.Bytes.build` gives, unfold the program's function and `LeanExe.Bytes.build` and let `simp` reduce `Array.toList (Array.ofFn _)`.  Prove the value of `LeanExe.Bytes.get` at a literal buffer as an equation of its own: unfold `LeanExe.Bytes.get`, rewrite with `dite_eq_left` whose proof is `exact` of the bound on the list's length, which holds against `{ data := l.toArray }.size` by definitional unfolding, and finish with `simp` and `ByteArray.getElem_eq_getElem_data`.  `LeanExe.A64.BytesRuns.congr` replaces the output of a `BytesRuns` theorem, `(f ⟨⟨msg.toArray⟩⟩).data.data.toList` in `LeanExe.A64.bytes_runs`, by a specification that agrees with it on every message within the limit.

`b.data.toList` is `ByteArray.toList`, a loop over the array's positions, which the lemmas about `Array.toList` do not cover.  `rw [Array.length_toList]` on its length still succeeds, since unification assigns `?xs := { toList := b.data.toList }` through the structure eta of `Array`, and it leaves `{ toList := b.data.toList }.size`, which `simp` turns back into the length of the loop.  `ByteArray.size` added to a `simp` call loops on the size of an array that is not a literal, such as `b.data.size`, because the simp lemma `ByteArray.size_data` folds back what the unfolding gives: the call stops with "maximum recursion depth has been reached", and when it also unfolds a definition of `LeanExe.Bytes`, such as `LeanExe.Bytes.get`, Lean first warns "Possibly looping simp theorem" and names `ByteArray.size` and `ByteArray.size_data` as the possible cause.  On a literal buffer, `{ data := l.toArray }`, the same call succeeds.  `simpa using h` with `h : i < l.length` fails against the goal `i < { data := l.toArray }.size` with "Type mismatch: After simplification", since `simp` leaves the goal's size as it is, while `exact h` succeeds by unfolding.

The worked examples are `TestSupport.A64.Flip.flip_toList` of `tests/TestSupport/A64/Flip.lean`, which states the output of `flipBit5` on a message as a map over the list with these steps, and `TestSupport.A64.Flip.flip_runs`, which joins it to `LeanExe.A64.bytes_runs_bounded` through `LeanExe.A64.BytesRuns.congr`, as `TestSupport.A64.RcvRuns.rcv_runs` of `tests/TestSupport/A64/RcvRuns.lean` joins the tabulator's output to `Demos.Rcv.Spec.reportFile`.  `LeanExe.A64.buffer_of_alloc` states the message's block as the buffer `⟨⟨bs.toArray⟩⟩`, which `bytes_runs` uses.  `Demos.Rcv.ReadProgram.bytesOf_length`, `Demos.Rcv.ReadProgram.get_eq`, and `Demos.StreamFold.byteWords_get` relate a buffer's length and bytes to its list.
