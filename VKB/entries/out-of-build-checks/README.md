# Theorems outside the full check

The entry applies when a theorem lies in a module that the full check does not elaborate, or when a change touches a definition that such a module imports, and when a file must elaborate against a module that no build has compiled.  The first step of `tools/full-check` builds the roots `LeanExe`, `Examples`, `Demos`, `Verified`, `Library`, and `TestSupport` with the test executables `native-verified`, `native-bare`, `verified-cases`, and `native-module-cases`, and it fails on a `sorry` warning and on an axiom report of the repository's files that names an axiom beyond `propext`, `Classical.choice`, and `Quot.sound` (the script's header and [the manual's section on the full check](../../../docs/verified-manual.md#the-full-check)).  Its later steps elaborate further modules only through their drivers, as `tests/verified/run.sh` elaborates the file-theorem modules of `.wasm` files.  A theorem in any other module is checked only when its own driver runs, and a passing full check says nothing about it.

The full check runs none of the drivers of the Isla, image, board, QEMU, and Sail theorems, so their modules are checked only by these drivers: `tests/isla/theorems.sh` and `tests/isla/m7-theorems.sh` for the Isla theorems of `tests/TestSupport/A64/Isla` and `tests/TestSupport/M7/Isla`, `tests/baremetal/a64-images.sh` for the A64 Image files, `tests/baremetal/m7-image.sh` for the M7 code images, `tests/baremetal/m7-board.sh check` for the board's file modules, such as `tests/TestSupport/M7/NucleoFile.lean` and `tests/TestSupport/M7/BmsBoardFile.lean`, `tests/baremetal/m7-qemu.sh` for the QEMU file modules, such as `tests/TestSupport/M7/QemuFile.lean` and `tests/TestSupport/M7/BmsQemuFile.lean`, and `tools/sail/check.sh` for the proofs over Sail's translation.  A file module holds the theorems over a written image, such as `TestSupport.M7.BmsBoardFile.bms_board_safe` of `tests/TestSupport/M7/BmsBoardFile.lean`, while the loop theorem that it applies, here `TestSupport.M7.Bms.board_safe`, lies in the build and takes the kernel's check of the file as a premise.  The full check thus checks the loop theorem for every file that passes the check, and only `m7-board.sh check bms` checks that `bms.bin` passes it.  The A64 row "Floating-point equations" of [the trusted base](../../../docs/trusted-base.md#a64-aarch64-images) states the same of the Sail proofs: a change of Talos, Mathlib, the toolchain, or the equations leaves them unchecked until `tools/sail/check.sh` runs again.

Lake does not track the files that `isla_trace%` and `isla_features%` read, so an olean can hold theorems about files that have since changed (the header of `tests/isla/theorems.sh` and the module doc of `LeanExe/A64/Isla/Trace.lean`).  `theorems.sh` therefore builds only the imports of the Isla modules with Lake and elaborates each module with `lean`, which reads the files as they stand.  `LeanExe.A64.Isla.Profile` lies in the build and reads the profiles' `features` files with `isla_features%`, so `TestSupport.A64.Isla.tcg_features` of `tests/TestSupport/A64/Isla/Profiles.lean`, with `kvm_features` and `sme_features`, states by `rfl` that each profile holds its file's settings, and `theorems.sh` elaborates that module on every run, where a profile built from an earlier version of a file fails.  The modules that read files with `file_nat%`, which gives `LeanExe.FileNat.natOfBytes` of a file's bytes, or with `binary_file%` of `LeanExe/Pipeline/FileBytes.lean`, which gives the bytes, lie outside every build target, and their drivers write the files and then elaborate them, as [the entry on image files](../image-file-checks/README.md) and [the entry on file theorems](../file-theorems/README.md) describe.

A module that no root imports is not built, so a module of theorems meant for the full check needs an import in a root, as `tests/TestSupport.lean` imports `TestSupport.A64.CicSigned`.  The build checks the axioms of a theorem only where a module prints them, so an audit inside the build fails it on a forbidden axiom: `Demos/OrderBook/ProcessAxioms.lean`, which `Demos.lean` imports, collects the axioms of every theorem in the order book's process and bound namespaces and throws an error on one beyond the three.  `lake build` of a new module's own name elaborates it and leaves it outside the full check, which reaches a module only through a chain of imports from a root such as `tests/TestSupport.lean` or `Demos.lean`.

A module that no build has compiled, such as a new module that a scratch file imports, compiles outside Lake into a directory of its own while other builds run in the same checkout, since a build of it would write to the `.lake` that they read.  `Lean.SearchPath.findWithExt` takes the first entry of `LEAN_PATH` that holds a directory named for the module's root, such as `Verified`, and does not check that the module's file lies there, so a directory placed first in `LEAN_PATH` that holds only the new `Verified/Wasi/X.olean` hides every other module of that root, whose import fails with `object file '…' of module … does not exist`.  The directory therefore mirrors the built tree with symbolic links, `cp -rsf "$PWD/.lake/build/lib/lean/Verified" "$out/"`, receives the new module from `lean -o "$out/Verified/Wasi/X.olean" Verified/Wasi/X.lean`, and comes first in the `LEAN_PATH` of the file that imports it, `LEAN_PATH="$out:$LEAN_PATH"`, all under `lake env` and `tools/leanrun`, so that nothing is written to `.lake`.

After a change to a definition that these modules import, such as the machine model's instructions or `exec`, the semantics of traces, a generator, or an initialization list, build the merged tree and run each driver whose modules reach the changed module.  The full check passes without those drivers, so a change that breaks an Isla or a file module goes unreported until its driver runs.  Each proof task names the root or the driver that checks its theorem, and [the entry on results that show a check passed](../result-validity/README.md) states which output of that run counts.  [The entry on instruction forms against Isla](../isla-form-proofs/README.md) and [the entry on floating-point equations from Sail](../sail-fp-equations/README.md) describe the modules that `theorems.sh` and `tools/sail/check.sh` check.

The worked examples are `TestSupport.M7.Bms.board_safe` in the build beside `TestSupport.M7.BmsBoardFile.bms_board_safe` in its file module, `TestSupport.A64.Isla.tcg_features` against the profiles' files, and the import of `TestSupport.A64.CicSigned` in `tests/TestSupport.lean`.  `Demos/OrderBook/ProcessAxioms.lean` is the audit inside the build.  The headers of `tests/isla/theorems.sh`, `tests/baremetal/m7-board.sh`, and `tests/baremetal/m7-qemu.sh` state which modules each driver elaborates and the axiom reports that it requires.
