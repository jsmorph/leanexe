# Simulations over a machine

The entry applies when a simulation proof of the A64 back end, stated for the program's model, must serve a model with more state or with imported functions, such as a Linux process whose state holds FPCR and a trace, or a module whose calls reach host functions through stubs.  `LeanExe.A64.Machine` holds the parts of a model that the simulation reads: the states `Q`, their projection `core` to the program's state, the runs `Rch`, the relation `SR` by which a state holds Talos's store, the states `Trapped` at which a trap ends with its message and store, and the host environment `env` of the module's imports.  The lemmas of the constructs, of calls, and of functions hold for every machine, so a new model proves the machine's laws and reuses them, as [the AArch64 document's section on the simulation theorem](../../../docs/a64-bare-metal.md#the-simulation-theorem) describes.

The laws are `refl` and `trans` of the runs, `storeRel`, by which `SR` implies `LeanExe.A64.StoreRel` of the core, and `lift`, by which a run of the program's model from a state that holds a store is a run of the machine to a state that holds every store that `StoreRel` relates to the run's end with the same host state, and that is a trap state for every store of the same host state when the run ends at the stub of a trap.  `lift` admits every run of the program's model from a related state, so every fact that `SR` adds to `StoreRel` must hold at every state that such a run reaches.  `LeanExe.A64.Test.procMachine` adds FPCR at `LeanExe.A64.fpcrValue` and a relation between the store's host state and the trace, which those runs keep, since they change only the core, while a fact about memory outside the area needs a proof that each such run keeps it.  `Trapped` takes the trap's store as well as its message, since an exit is a host trap whose store holds the status and the world, so a statement of the process's status and trace after an exit can take them only from that store, which `LeanExe.A64.Test.procMachine_trap` relates to the trace.

Each definition of the model's simulation has a general form over a machine, with the store relation in place of `StoreRel` and the core in place of the state.  At `LeanExe.A64.bare`, the model with the empty host environment, some forms equal the model's definitions by `rfl`, as `LeanExe.A64.Outcome.eq_bare`, `LeanExe.A64.CallResult.eq_bare`, and `LeanExe.A64.FunOutcome.eq_bare` state, and `LeanExe.A64.FunSim.iff_bare` and `LeanExe.A64.CallsOk.iff_bare` state equivalences with the forms at `bare` of every host type.  A definition that quantifies the host type inside a premise, as `LeanExe.A64.InstrSim` does through `LeanExe.A64.CallsOk`, is no instance of a form whose machine fixes the host type: `LeanExe.A64.InstrSim.of_bare` derives it from the forms at `bare` of every host type, and the converse does not follow from the definitions, since a machine's `CallsOk` at one host type does not give the model's at every host type, although both sides hold as theorems.  The model's theorems follow from the general ones at `bare` for every host type, and a premise that the general theorems discharge stays as an unused argument, so that each statement keeps its type, as [the entry on changes that keep statements and bytes](../unchanged-statements-and-bytes/README.md) asks: the model's `LeanExe.A64.sim_block` keeps `_hP`, the simulation of lists, which `LeanExe.A64.Machine.list_sim` proves without a premise.  A proof over a machine writes `(M.core q)` where the model's proof names the state, so the model's rewrites apply to the projection, as `LeanExe.A64.Machine.sim_call` does.

A form that neither calls nor reads the host carries its lemma from the program's model to every machine by `LeanExe.A64.Machine.InstrSim.of_leaf`, given `LeanExe.A64.Leaf`: Talos runs the form under any host environment as it runs it in `LeanExe.A64.withoutFuncs m` under the empty one, and its fall-through, branch, return, or trap keeps the store's host state (`LeanExe.A64.HostKept`).  The model's lemma assumes the model's `CallsOk`, which quantifies every host type under the empty environment and which a machine's `CallsOk` does not give for any module, and `of_leaf` supplies it at `withoutFuncs m`, where every call's run is `Invalid` and `CallResult` holds of it.  The tactic `leaf_tac` proves `Leaf` by `cases` on the fuel, `simp only [execOne.eq_def]`, `split`, and `rfl`, and `LeanExe.A64.Machine.instr_sim` applies `of_leaf` with it to each form other than a block, a loop, an `if`, a call, and the forms that the generator refuses.

An import needs no change of the call's simulation: `LeanExe.A64.Machine.sim_call` takes the callee's outcome from `LeanExe.A64.Machine.CallsOk`, whose `LeanExe.A64.Machine.FunSim` runs Talos under the machine's environment.  `LeanExe.A64.Machine.StubSim` states what a stub at an import's entry does for the host function's `invoke` on the arguments, first parameter first, in the registers of the heights from 0, and `LeanExe.A64.Machine.fun_sim_import` turns it into `FunSim` at every fuel.  `LeanExe.A64.Machine.callResult_success` gives `CallResult` from a return for a stub as for a generated function, and `LeanExe.A64.Machine.calls_ok` gives `CallsOk` for a table whose entries are stubs that meet `StubSim` or generated functions at `m.funcs[k - m.imports.length]`.  The generator emits no stubs, and the whole-program theorems assume a module without imports, so `calls_ok` states what a binding with stubs must prove.

A process whose steps carry conditions that the program's model lacks does not contain every run of the model: `LeanExe.A64.pstep` runs a floating-point form only while FPCR holds `fpcrValue` and every form only when the next program counter lies below 2^55, while `lift` must admit a run that returns to any address.  `LeanExe.A64.Test.ProcRun` is a run of the process followed by a run of the program's model from a process with FPCR at `fpcrValue`, which keeps FPCR and the trace, so it contains every such run.  `LeanExe.A64.Test.ProcRun.trans` composes two of them when the code lies below 2^55, by lifting the middle run with `LeanExe.A64.ProcReach.of_reach'`, since the next step starts at a word of the code, and `LeanExe.A64.Test.ProcRun.toProcReach` gives a run of the process when the end lies at a word of the code.  `LeanExe.A64.Test.procMachine` is the process as a machine, and `LeanExe.A64.Test.procMachine_calls` applies `calls_ok` to it.  No machine over `LeanExe.A64.ProcReachWith` exists yet, and one can take the same form with `LeanExe.A64.ProcReachWith.of_reach'` as its lift, since every step of `LeanExe.A64.pstepWith` also starts at a word of the code.

The worked examples are `LeanExe.A64.Machine.instr_sim`, `LeanExe.A64.Machine.sim_call`, `LeanExe.A64.Machine.calls_ok`, and the process machine of `tests/TestSupport/A64/ProcMachine.lean`.  [The entry on AArch64 Image theorems](../a64-image-theorem/README.md) covers the theorems that the simulation of the program's model gives, and [the entry on WASI hosts built on a lower layer](../wasi-host-from-layer/README.md) the shim, whose binding to a machine needs stubs that meet `StubSim`.  [The entry on tactics whose failures mislead](../tactic-combinator-pitfalls/README.md) records the `rfl` that closes a read of a register after a rewrite with a structure update.
