# Simulations over a machine

The entry applies when a simulation proof of the A64 back end, stated for the program's model, must serve a model with more state or with imported functions, such as a Linux process whose state holds FPCR and a trace, or a module whose calls reach host functions through stubs.  `LeanExe.A64.Machine` holds the parts of a model that the simulation reads: the states `Q`, their projection `core` to the program's state, the runs `Rch`, the relation `SR` by which a state holds Talos's store, the states `Trapped` at which a trap ends with its message and store, and the host environment `env` of the module's imports.  The lemmas of the constructs, of calls, and of functions hold for every machine, so a new model proves the machine's laws and reuses them, as [the AArch64 document's section on the simulation theorem](../../../docs/a64-bare-metal.md#the-simulation-theorem) describes.

The laws are `refl` and `trans` of the runs, `storeRel`, by which `SR` implies `LeanExe.A64.StoreRel` of the core, and `lift`, by which a run of the program's model from a state that holds a store is a run of the machine to a state that holds every store that `StoreRel` relates to the run's end with the same host state, and that is a trap state for every store of the same host state when the run ends at the stub of a trap.  `lift` admits every run of the program's model from a related state, so every fact that `SR` adds to `StoreRel` must hold at every state that such a run reaches.  `LeanExe.A64.Test.procMachine` adds FPCR at `LeanExe.A64.fpcrValue` and a relation between the store's host state and the trace, which those runs keep, since they change only the core, while a fact about memory outside the area needs a proof that each such run keeps it, which a platform of the module's code that leaves that memory out gives, as the machine of the Linux call layer below shows.  `Trapped` takes the trap's store as well as its message, since an exit is a host trap whose store holds the status and the world, so a statement of the process's status and trace after an exit can take them only from that store, which `LeanExe.A64.Test.procMachine_trap` relates to the trace.

Each definition of the model's simulation has a general form over a machine, with the store relation in place of `StoreRel` and the core in place of the state.  At `LeanExe.A64.bare`, the model with the empty host environment, some forms equal the model's definitions by `rfl`, as `LeanExe.A64.Outcome.eq_bare`, `LeanExe.A64.CallResult.eq_bare`, and `LeanExe.A64.FunOutcome.eq_bare` state, and `LeanExe.A64.FunSim.iff_bare` and `LeanExe.A64.CallsOk.iff_bare` state equivalences with the forms at `bare` of every host type.  A definition that quantifies the host type inside a premise, as `LeanExe.A64.InstrSim` does through `LeanExe.A64.CallsOk`, is no instance of a form whose machine fixes the host type: `LeanExe.A64.InstrSim.of_bare` derives it from the forms at `bare` of every host type, and the converse does not follow from the definitions, since a machine's `CallsOk` at one host type does not give the model's at every host type, although both sides hold as theorems.  The model's theorems follow from the general ones at `bare` for every host type, and a premise that the general theorems discharge stays as an unused argument, so that each statement keeps its type, as [the entry on changes that keep statements and bytes](../unchanged-statements-and-bytes/README.md) asks: the model's `LeanExe.A64.sim_block` keeps `_hP`, the simulation of lists, which `LeanExe.A64.Machine.list_sim` proves without a premise.  A proof over a machine writes `(M.core q)` where the model's proof names the state, so the model's rewrites apply to the projection, as `LeanExe.A64.Machine.sim_call` does.

A form that neither calls nor reads the host carries its lemma from the program's model to every machine by `LeanExe.A64.Machine.InstrSim.of_leaf`, given `LeanExe.A64.Leaf`: Talos runs the form under any host environment as it runs it in `LeanExe.A64.withoutFuncs m` under the empty one, and its fall-through, branch, return, or trap keeps the store's host state (`LeanExe.A64.HostKept`).  The model's lemma assumes the model's `CallsOk`, which quantifies every host type under the empty environment and which a machine's `CallsOk` does not give for any module, and `of_leaf` supplies it at `withoutFuncs m`, where every call's run is `Invalid` and `CallResult` holds of it.  The tactic `leaf_tac` proves `Leaf` by `cases` on the fuel, `simp only [execOne.eq_def]`, `split`, and `rfl`, and `LeanExe.A64.Machine.instr_sim` applies `of_leaf` with it to each form other than a block, a loop, an `if`, a call, and the forms that the generator refuses.

An import needs no change of the call's simulation: `LeanExe.A64.Machine.sim_call` takes the callee's outcome from `LeanExe.A64.Machine.CallsOk`, whose `LeanExe.A64.Machine.FunSim` runs Talos under the machine's environment.  `LeanExe.A64.Machine.StubSim` states what a stub at an import's entry does for the host function's `invoke` on the arguments, first parameter first, in the registers of the heights from 0, and `LeanExe.A64.Machine.fun_sim_import` turns it into `FunSim` at every fuel.  `LeanExe.A64.Machine.callResult_success` gives `CallResult` from a return for a stub as for a generated function, and `LeanExe.A64.Machine.calls_ok` gives `CallsOk` for a table whose entries are stubs that meet `StubSim` or generated functions at `m.funcs[k - m.imports.length]`.  `LeanExe.A64.genWasiProgram` places a stub at the entry of each import of a WASI command, and `LeanExe.A64.wasi_calls_ok` applies `calls_ok` to its table with a premise of `StubSim` for each stub.  The shim's binding proves those premises with `Verified.ShimA64.readStub_sim`, `Verified.ShimA64.writeStub_sim`, and `Verified.ShimA64.exitStub_sim` for the stream imports and with `Verified.ShimA64.flatStub_sim` for each stub of `LeanExe.A64.flatStubs`, so a stub added to that list adds a case to `flatStub_sim`.

A process whose steps carry conditions that the program's model lacks does not contain every run of the model: `LeanExe.A64.pstep` runs a floating-point form only while FPCR holds `fpcrValue` and every form only when the next program counter lies below 2^55, while `lift` must admit a run that returns to any address.  `LeanExe.A64.Test.ProcRun` is a run of the process followed by a run of the program's model from a process with FPCR at `fpcrValue`, which keeps FPCR and the trace, so it contains every such run.  `LeanExe.A64.Test.ProcRun.trans` composes two of them when the code lies below 2^55, by lifting the middle run with `LeanExe.A64.ProcReach.of_reach'`, since the next step starts at a word of the code, and `LeanExe.A64.Test.ProcRun.toProcReach` gives a run of the process when the end lies at a word of the code.  `LeanExe.A64.Test.procMachine` is the process as a machine, and `LeanExe.A64.Test.procMachine_calls` applies `calls_ok` to it.  `LeanExe.A64.withMachine` is the machine of the Linux call layer's binding, whose runs `LeanExe.A64.ProcRunWith` take the same form over `LeanExe.A64.ProcReachWith`, and whose `trans`, `LeanExe.A64.ProcRunWith.trans`, lifts the middle run with `LeanExe.A64.ProcReachWith.of_reach'`, since every step of `LeanExe.A64.pstepWith` also starts at a word of the code.  Its `lift` is `LeanExe.A64.ProcRunWith.ofReach` after `LeanExe.A64.Reach.le`, which takes no step of the layer, so only the stubs' proofs of `StubSim` take the layer's steps.

The store relation of `withMachine` adds to `StoreRel` FPCR at `fpcrValue`, X17 at the area, the stack's limit in X18 at least `gap` bytes above the area's end, a relation `H` between the store's host state and the trace, and a relation `K` between the store's host state and the memory.  A run of the program's model keeps the trace, and `lift` relates the run's end only to stores with the same host state, so `lift` keeps `H`.  The machine runs the module's code on a platform `P` and the process on a platform that maps more, related by `LeanExe.A64.Platform.Le`, which requires every byte of `P`'s Normal memory to be Normal memory of the other and the UART and receiver to be the same.  `LeanExe.A64.Reach.le` and `LeanExe.A64.IReach.le` carry a run on `P` to a run on the larger platform, and `LeanExe.A64.Reach.frame` states that a run keeps every byte that its platform does not map as Normal memory.  `withMachine` requires that two memories that agree outside `P`'s Normal memory meet `K` together, so `lift` keeps `K` by the frame of the model's run, and a fact about memory outside `P`'s Normal memory, such as the scratch and the initial stack, needs that one law in place of a proof about every run.  `Verified.ShimA64.shimMachine` runs the module's code on `LeanExe.A64.modulePlatform`, the data segment without the shim's scratch, and the process on `LeanExe.A64.wasiPlatform`, the data segment and Linux's initial stack, with `Verified.ShimA64.ScratchHolds` as `K`, whose law is `Verified.ShimA64.ScratchHolds.frame`.  A stub that writes memory keeps `K` by the frame of its own writes, which `Verified.ShimA64.writeList_outside` gives for bytes written to Normal memory of a platform.

`LeanExe.A64.Machine.StubSim` requires a stub's return to keep every byte from SP up (`LeanExe.A64.Returned`), while `LeanExe.A64.StoreRel` places the area's end at most at X18 and `LeanExe.A64.StackOk` admits SP equal to X18.  A stub that writes between the area's end and the stack's limit, where the shim's scratch lies, can show that its bytes lie below SP only from the bound that `withMachine`'s `gap` adds, and `shimMachine` takes the scratch's size as the gap, while the stream stubs and the stubs of `flatStubs` write only the area.  The machine keeps its facts about X17 and X18 by a check in the generator in place of a lemma for each form: `LeanExe.A64.genWasiProgram` rejects an instruction that writes X17 (`LeanExe.A64.Instr.keepsX17`) and, after `main`, which sets X18, an instruction that writes X18 (`LeanExe.A64.Instr.keepsX18`).  The machine's code map, `LeanExe.A64.wasiCode`, holds only the routine `SVC #0; RET` and the program after `main`, so `LeanExe.A64.Reach.x17` and `LeanExe.A64.Reach.x18` hold of every run over it by induction on the steps, with `LeanExe.A64.wasiCode_keeps` and `LeanExe.A64.wasiCode_all`.  `main` runs on the executable's full code map before the machine starts, and `LeanExe.A64.ProcRunWith.mono` with `LeanExe.A64.wasiCode_sub` carries the machine's runs to that map, as `Verified.ShimA64.wasiElf_run` does.

A stub's run lemma in the program's model takes the facts of the state that it reads as premises on any platform, as `LeanExe.A64.StubEntry` states them for the stubs of the arguments and the environment.  The stub's proof of `StubSim` derives them from the machine's store relation, as `Verified.ShimA64.stubEntry_of` does from `StoreRel` and `LeanExe.A64.Platform.Le` for the area, from the scratch's place in the data segment for the word of the saved SP, and from `ScratchHolds` for the saved SP and the initial stack.  Those stubs read the scratch and the initial stack, which `modulePlatform` leaves out, so they run on `wasiPlatform`, while their writes lie in the area, which `modulePlatform` maps, so `Verified.ShimA64.ScratchHolds.frame` with `writeList_outside` keeps `K` at the return (`Verified.ShimA64.sizesStub_sim`, `Verified.ShimA64.stringsStub_sim`).  The run of a loop over a zero-terminated string or a vector of pointers follows by induction on the strings that remain when its premise is a recursive predicate that carries the next address, as `LeanExe.A64.StrAt` and `LeanExe.A64.VectorAt` do: a nonempty string gives the byte at `p` and the predicate at `p + 1`, the loop's next state, with no index arithmetic.  The indexed form of `LeanExe.A64.InitialStack`, with the pointers at `sp + 8 · (i + 1)`, converts once to the recursive form (`LeanExe.A64.vectorAt_of`), and both predicates name only addresses from 2^32 up, so they hold across the writes below 2^32 that a pass makes while it reads the initial stack (`LeanExe.A64.StrAt.frame`, `LeanExe.A64.VectorAt.frame`).  A run of segments whose frame lemmas each take the form `∀ q, q ≠ 9 → q ≠ 10 → … → t.x q = s.x q` keeps the registers that the caller needs through a predicate such as `LeanExe.A64.KeptReg`, whose `LeanExe.A64.KeptReg.ne` gives `q ≠ k` for each written register `k` by `decide`, so each segment's frame composes into `∀ q, KeptReg q → u.x q = s.x q` in one line, from which X17, X18, and the return address follow (`LeanExe.A64.run_sizesStub`, `LeanExe.A64.run_stringsStub`).

The worked examples are `LeanExe.A64.Machine.instr_sim`, `LeanExe.A64.Machine.sim_call`, `LeanExe.A64.Machine.calls_ok`, the process machine of `tests/TestSupport/A64/ProcMachine.lean`, `Verified.ShimA64.shimMachine` with the stubs' proofs of `Verified/ShimA64/`, and the loops `LeanExe.A64.run_lenLoop`, `LeanExe.A64.run_copyLoop`, `LeanExe.A64.run_scanLoop`, `LeanExe.A64.run_pointerLoop`, and `LeanExe.A64.run_copyPass`.
