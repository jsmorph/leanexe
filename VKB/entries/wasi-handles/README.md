# Handles and brackets of WASI programs

The entry applies to proofs and changes that concern the descriptors of a WASI program: a typed function on `LeanExe.Wasi.Handle`, a call that opens, closes, or renumbers a descriptor, a change of `LeanExe.Wasi.withOpen` or of `Verified.Wasi.Command.HandleCheck`, and a statement of which descriptors a run uses and closes.  A program that passes the handle check reaches a descriptor only through `LeanExe.Wasi.Handle.preopened` and the handle that `withOpen` binds for its body, and `verified_compile_wasi` reflects `withOpen` as a fixed expansion into the existing commands: the open, a test of its errno, the error continuation or the body, and the close.  The check, which the kernel decides for each program, refuses an open, a close, or a renumbering outside that expansion and a handle argument that is not a marked variable: a bracket's handle, a variable bound to the value 3 of `LeanExe.Wasi.Handle.preopened`, or a marked parameter of a helper.  [The manual's section on handles](../../../docs/wasi.md#handles) states the surface and the theorems.

`LeanExe.Wasi.WellBracketed stack trace stack'` reads a trace with a stack of descriptor numbers, one for each open bracket, and `LeanExe.Wasi.Action.Handles stack action post`, defined by recursion over the action, states that every run of the action keeps that discipline and that a normal return leaves a stack that satisfies `post`.  `LeanExe.Wasi.Action.Handles.exec_run` and `LeanExe.Wasi.Action.Handles.prefix_run` derive `WellBracketed` for the `Exec` and `Prefix` runs of such an action, and `LeanExe.Wasi.Action.BracketRuns` states the result for a program's runs from no open bracket.  For commands, `Verified.Wasi.Command.handles` proves by one induction on the command that a command that passes the check at a stage meets that stage's statement, `Verified.Wasi.StageHandles`, given helpers that keep the discipline, `Verified.Wasi.EffectFuns.HandlesSafe`.  `Verified.Wasi.Command.handles_exec` and `Verified.Wasi.Command.handles_prefix` carry the result to runs from a stack that holds the values of the command's marked variables, `Verified.Wasi.EnvMarked`, and `Verified.Wasi.EffectProg.bracketRuns` discharges both premises for a function of a program that passes the check, called with no marked argument.  Both the check and `LeanExe.Wasi.callAllowed` require each call to be one of the generated descriptions of `LeanExe.Wasi.Call.table`, from which they read its `.handle` positions, for the reason that [the entry on checks that can fail](../discriminating-checks/README.md) gives together with the wrong programs that a reused move analysis would admit.

The check reads the expansion in stages, one constructor of `Verified.Wasi.Command` at a time.  `Verified.Wasi.Command.handleCheck` takes a stage, `Verified.Wasi.Stage`, matches one constructor of `Command` in each arm, and reads the parts below it with predicates of one level that do not recurse, such as `Verified.Wasi.Command.isOpen` and `Verified.Expr.isErrnoTest`, each with a lemma that states what it recognizes, such as `Verified.Wasi.Command.isOpen_handles` and `Verified.Expr.isErrnoTest_denote`.  The one predicate that recurses, `Verified.Expr.isPreopened`, recurses through `Verified.Expr.letPair` alone.  A recursive check that recognizes the whole expansion in one nested pattern, whose arms mix the constructors of `Command` with those of `Verified.Expr`, `Verified.Path`, and `Verified.Var` (`.proj x (.fst .here)` inside `.cmp` inside `.ite`), elaborates, but the toolchain's Lean cannot generate the equation theorems of its match.  Lean fails to realize its `eq_1` and `induct`, reporting that it failed to generate equality theorems for the `match` expression, and `simp` with the definition reports the same failure and makes no progress, so a proof can read the check only by `rfl`, on a command whose constructors select one arm.  The staged check needs no such equation, and its soundness proof is one `induction` on the command with a statement for each stage.

A stage's statement names variables whose types the context does not fix, such as the pair of words that the open returns in variable 0.  `Verified.Ty.word?`, `Verified.Ty.pair?`, and `Verified.Ty.bool?` return `none` at other types, so `env.at? Ty.pair? 0 = some (errno, word)` states the value with no cast, and `Verified.Env.at?_get` relates `Verified.Env.at?` to `Verified.Env.get` at any variable.  A lemma about the value of an expression cases on the expression with its type a variable, as `Verified.Expr.isErrnoTest_denote` does, since `cases` on an expression of the fixed type `.bool` fails with `Dependent elimination failed: Failed to solve equation` at the type `g.result` of the constructor `call`.

The binding of `LeanExe.Wasi.Handle.preopened` may hold the literal 3 under `Verified.Expr.letPair`.  The reflector gives the type `.pair` to a value whose `Flat` form is a pair with a component on the heap, such as `LeanExe.Wasi.FillResult` of `LeanExe.Wasi.fdPrestatDirName` and `LeanExe.Wasi.randomGet`, and `LeanExe.Wasi.ArgsResult` of `LeanExe.Wasi.args`, while a pair or a record of words is an element.  `Verified.Wasi.Reflect.pureOperand` reflects an operand that is not a variable through `Verified.Reflect.reflect.reflectSplit`, which puts around it a `letPair` of each variable of type `.pair` that the operand names and of each component of such a variable that is itself a `.pair`.  The literal names no variable, and the reflector splits the result of `args` where the action binds it, so a reflected program binds the preopened handle as `ret` of the literal alone, while a hand-written command may hold the literal under `letPair`s.  `Verified.Expr.isPreopened` reads the literal through any number of `letPair`s, whatever their values, and `Verified.Wasi.Command.preopened` uses it.  `Verified.Expr.isPreopened_denote` states, by one `induction` on the expression with its type a variable, that an accepted expression has the value 3 in every environment, since `Verified.Expr.denote` evaluates every expression without an effect, and `Verified.Wasi.Command.preopened_handles` gives the binding the stack unchanged.  The check reads a `Verified.Wasi.Command.letPair` with its components unmarked, so a component of a pair is never a handle argument, and `Verified.Wasi.Command.handles` passes its body the stack unchanged.  The bracket's own stages, the test of the open's errno, the binding of its handle, the close, and the last `ret`, come from the fixed expansion of `withOpen` and stay unwrapped, so `Verified.Expr.isErrnoTest` and the other recognizers of the expansion read the bare forms.  `Verified/Examples/WasiSysPrestat.lean` opens a file under the preopened handle and removes it with `pathUnlinkFile .preopened` after `fdPrestatDirName` in the same function, and `tests/wasi/HandleCheck.lean` compiles a program that opens a file after `args`.  A helper's `Handle` parameter is scalar, so the reflector passes the argument `.preopened` to a helper as the expression itself (`reflectCall?` in `Verified/Wasi/Reflect.lean`), which the check's arm for `call` refuses in every scope as an argument that is not a marked variable.  A helper that needs the preopened directory therefore names `LeanExe.Wasi.Handle.preopened` in its own body.

Wasmtime 44 reuses descriptor numbers, the largest free number first, and asserts that a new number is unused (`push` in [`crates/wasi/src/p1.rs`](https://github.com/bytecodealliance/wasmtime/blob/v44.0.0/crates/wasi/src/p1.rs)).  A statement over the numbers in a trace, such as one that each call's descriptor is open when the call is made, therefore holds for a program that uses a closed handle after a later open has returned the same number, and `WellBracketed`, which reads numbers, admits such a use.  The check excludes it, since a handle's variable is in scope only inside its bracket, so the theorems over traces need no semantics that records which open returned a number.  `LeanExe.Wasi.Action.BracketRuns.exec_descriptors` reads the stack as the open descriptors of the trace under the host assumption `LeanExe.Wasi.FreshOpens`, which Wasmtime's assertion meets, as the row "Handle discipline" of [the trusted base](../../../docs/trusted-base.md#wasi-wasi-preview-1-modules) records.

A theorem about whole runs constrains a bracket only through the events of the whole trace.  `Verified.Wasi.Command.handles_exec` states that a run's trace is well bracketed and that a normal return leaves the starting stack, but a bracket that returns normally makes no event at its return, so an action whose bracket returns without its close and then exits satisfies `LeanExe.Wasi.Action.BracketRuns`.  `Verified.Wasi.withOpen_closes` states the events and the result of every run of `withOpen` that returns normally, with one case for each path through the bracket.  When `LeanExe.Wasi.Call.reject` rejects the arguments of `path_open`, the trace is that of a run of the error continuation on the rejection's errno, well bracketed from `stack` back to `stack`, and the second component of the bracket's result is 0.  Otherwise the trace starts with the open event.  When its errno is 0, the rest is that of a run of the body on the descriptor `d` that the open returned, well bracketed from `d :: stack` back to `d :: stack`, followed by one `fd_close` event of `d`, whose errno is the second component.  When its errno is not 0, the rest is that of a run of the error continuation on that errno, well bracketed from `stack` back to `stack`, and the second component is 0.  In each case the first component is the result of that run.  The rejection and the open event's errno select the case, so the statement gives the close's errno for every open that succeeds.  A disjunction whose failure case lets the trace start with the open event or not, and requires only a nonzero errno, also holds of a run whose open succeeded, so a proof cannot select the close's case from it.  Its premises are what `handles_exec` states of the body and the error continuation, so the two theorems combine, as [the entry on claims and the theorems that state them](../claims-and-theorems/README.md) requires of a claim about one scope.

The worked examples are `Verified.Wasi.Command.handles`, with `Verified.Wasi.StageHandles` and the lemmas of each recognizer in `Verified/Wasi/Handles.lean`, `Verified.Wasi.withOpen_closes`, and `LeanExe.Wasi.Action.BracketRuns.exec_descriptors`.  `Verified.Wasi.Reflect.withOpen_rel` relates the expansion to `withOpen`, and [the entry on tactics whose failures mislead](../tactic-combinator-pitfalls/README.md) records the `rw` that fails in its proof until a `subst` gives the bound value the type of the equation.  `tests/wasi/HandleCheck.lean` decides the check in the kernel on accepted brackets and on refused commands: a close or an open outside a bracket, a handle argument bound to another word, hand-written descriptions outside `LeanExe.Wasi.Call.table`, and brackets of other shapes.
