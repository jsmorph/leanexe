# Checks that can fail

The entry applies when a check passes and its passes are to count as evidence: a co-simulation, the replay of a log against a specification, the kernel's check of an image file, a comparison of an encoder with an assembler, a driver's count of axiom reports, the self-test of an independent reference, or a host script that judges a run on a board.  Each of these passes vacuously when it compares nothing, compares a result with itself, or accepts every outcome.  A check counts as evidence after a recorded run in which a fault of the kind that it should catch makes it fail.  [The entry on independent review](../independent-review/README.md) applies the same test to a specification's cases with wrong programs, [the entry on testing a statement before its proof](../statement-testing/README.md) applies it to a statement's tests with false variants of the statement, such as a property that the procedure is known to fail, and [the entry on encodings and co-simulation of machine forms](../machine-form-validation/README.md) describes the co-simulations whose seeded faults appear below.

Keep a seeded fault whose failures can be predicted as a required step of the check.  `tests/baremetal/m7-board.sh cosim-check` checks the board's results against the model and then against the model with `ADC`'s carry in replaced by 0, the option `adc-carry` of `m7-cosim board-check`, and it fails unless the second check reports a differing case of `ADC` with registers.  On each run of the board's co-simulation exactly the `ADC` cases with the carry flag set on entry differed under the changed model, as the table of [the Cortex-M7 document's section on co-simulation](../../../docs/m7-bare-metal.md#co-simulation) records.  The step fails as well when the changed model's check fails without that difference, so the predicted set of failures separates a check that detects the fault from one that fails for another reason, such as an unreadable result file.

Give the self-test of an independent reference a negative control beside its positive cases.  `self_test` of `tests/cic/reference.py` requires that the 64-bit cascade agree with the exact outputs for inputs within Hogenauer's bound, and that a constant input of -2^B, one bit past the bound, give a reading that differs from an exact output.  The second requirement shows that the comparison detects the overflow that the bound excludes, and a reference whose comparison could not detect it would pass the first requirement as well.

Show for each kind of check that one changed byte or bit makes it fail, and record the run.  With one byte of an image changed, the kernel rejects the image's theorem, and for an image in parts it rejects the part that holds the byte ([the images and their kernel checks](../../../docs/m7-bare-metal.md#the-images-and-their-kernel-checks)).  With one bit of the assembled bytes changed, `tests/baremetal/m7-encode.sh` reports that sample ([encoding](../../../docs/m7-bare-metal.md#encoding)).  Altered copies of a mirror's log, with a changed digit of an answer, a missing or an extra answer, a missing `reset` line, or an input line that is not hexadecimal, each made `bms-replay` fail at the altered line ([the replay against the specification](../../../Demos/Bms/Host.md#the-replay-against-the-specification)).

A seeded fault in a file derives the new byte from the byte that it replaces, such as its complement or its exclusive or with 1, since a fixed value leaves the file unchanged wherever the byte already holds that value, and the check then passes on the original file.  Read the byte at offset N with `od -An -tu1 -j N -N 1 FILE`, write the new value V with `printf "\\$(printf %03o V)" | dd of=FILE bs=1 seek=N conv=notrunc`, and require `cmp -l ORIGINAL FILE` to print exactly one line before the check runs.  A seed that sets or clears a bit leaves the byte unchanged in the same way when the bit already has that value, while an exclusive or with the bit's mask always changes the byte.  A seed in a file that the check reads in place, such as an Image file that a theorem module reads with `file_nat%`, works on a copy of the original, and the step restores the file from the copy afterwards and requires `cmp` to find no difference between the two, so that later runs check the original.

Require a positive or an exact count of what the check reads.  `tests/isla/theorems.sh` and `tests/isla/m7-theorems.sh` fail when a module prints no axioms, `check_axioms` of `tests/verified/run.sh` fails when an audit prints no report, and `m7-cosim check` of `tests/TestSupport/M7/CosimMain.lean` fails when the harness's output holds no case line and no division line.  `m7-board.sh check`, `m7-qemu.sh`, `a64-images.sh`, and `m7-image.sh` require each file module to print an exact number of axiom reports, none of which names an axiom beyond `propext`, `Classical.choice`, and `Quot.sound`, so a new `#print axioms` line in a file module raises the count that its driver expects, as [the entry on bounds for a step's phases](../m7-phase-bounds/README.md) notes.  `m7-board.sh cosim` requires the result header's word `0x600DCAFE` and as many saved cases as the image holds.

Make the pass criterion exclude every outcome that the hypothesis under test rules out.  `tests/baremetal/uart_sha.py --overrun` tests the SHA-256 step with USART3's overrun detection disabled: after blocks A and B in one write, it sends single bytes until an answer arrives and requires the answer to equal the digest of the bytes before A, A, the last bytes of B, at least one, and the single bytes.  It stops after 63 single bytes, since an answer after 64 would mean that USART3 delivered no byte of B, while OVRDIS keeps B's last byte in `USART_RDR` until the step reads it.  The control run of the same phase against `sha.bin`, whose initialization leaves overrun detection enabled, got no answer after 63 single bytes and read `ORE` set ([the programs on QEMU, in Renode, and on the board](../../../docs/m7-bare-metal.md#the-programs-on-qemu-in-renode-and-on-the-board)).

Keep a control input for each edit of a reference's harness.  The A64 row "The Isla check" of [the trusted base](../../../docs/trusted-base.md#a64-aarch64-images) lists, as evidence for the edit `tests/isla/armv9p4-checked.diff`, which makes Isla's run stop when the decoder throws an exception, a control encoding that the edit stops.  Without such an input, an edit that stopped nothing would leave every trace as it was and pass every comparison.  [The entry on code around an executable reference](../reference-harness-audit/README.md) covers the audit of such edits.

A tolerance as large as the quantity that a check compares lets wrong values of it pass.  The q-method's bound `errOpt` lay between `1.1e-14` and `3.9e-13` on the generated inputs, so a comparison with its formula within `1e-12` accepted a halved and a doubled `errOpt`, as the review's wrong programs showed (finding 1 of `Demos/Attitude/review.md`).  The class `turned` of the cases, `TestSupport.Attitude.QCases.turnedResult` of `tests/TestSupport/Attitude/QCases.lean`, applies the certificate to the program's quaternion turned by `1e-6`, `1e-4`, and `1e-2`, where `errOpt` is 1.067 times the angle, and the oracle then rejects both wrong outputs on all 30 such inputs.  A check of a bound's accuracy against the true value needs a margin for the method's own limit, and a margin wide enough for every case admits a much less accurate program.  The passive-safety bounds approach the componentwise bound, the least distance of the box of each component's values at one time, which lies 0.736 m below the true minimum for the case `formation`, so a margin that covers that gap admitted a program seven times less accurate (finding 2 of the section "Review of the panel enclosure and the accuracy" of `Demos/PassiveSafety/review.md`).  `tests/passivesafety/reference.py` computes the componentwise bound apart from the program and requires each returned bound to lie within the accuracy plus a millionth of that bound, which every case meets with at least 2.3e-5 m to spare and a program that ignores the accuracy misses by up to 491.6 m.

A check of a program's outputs by their presence, their number, or a bound that every plausible value meets passes programs that compute wrong values.  The runs of the flat call example in Wasmtime, `tests/wasi/sys-example-run.sh`, require the realtime reading within a day of the system clock, which a 32-bit load of the reading fails, since the reading exceeds `2^32` ns, and the monotonic reading below `10^17` ns, far below the realtime clock's value, which a read of the wrong clock fails.  They run the module four times with the same arguments and require at least two values at each of the 16 random positions, which a correct module fails with probability at most `2^-20` and a module that leaves stale bytes fails on every run.  A fault that the engine hides passes every run: a block that the module allocates too short for a reply passes when the engine's write past it lands in heap that no check reads, and only the module's theorems exclude it.  A frame test that fills memory with a guard byte and, after each call, scans every byte outside the call's declared regions, as `tests/wasi/sys/frame.wat` does, detects a write outside the regions, so it detects a region declared too short only when the engine writes a byte that the shortened region leaves out, and never a region declared too long.  The frame's soundness needs the detection of a region declared too short, so the test's scenario makes the engine write every byte of each region, as `frame.wat` requires the argument strings to fill their region exactly.

A driver can judge a run whose input comes from the operating system's random source only by what every correct output shares, such as the number of lines, their form, their range, and a sum, and a program that maps words to wrong values passes such a check.  The Wasmtime host's option `--random-bytes FILE` of `tools/wasmtime-host.c` defines `random_get` over Wasmtime's, with `wasmtime_linker_allow_shadowing` and `wasmtime_linker_define_func`, as a function that gives the bytes of FILE in order and returns errno 29, `io`, when fewer bytes remain than a call asks for, so a driver chooses the bytes and compares the output byte for byte with what the specification gives for them.  The expected output comes from the reviewed specification evaluated with `lake env lean --run`, as `tests/random-histogram/Expected.lean` and `tests/random-choice/Expected.lean` evaluate it, and not from the compiled code, whose agreement with the specification is what the run tests.  A command's specification that is a relation over events, such as `Demos.RandomChoice.Meets` with `Demos.RandomChoice.Rounds`, admits one run under a host that answers every call from a file and whose writes take every byte, and `tests/random-choice/Expected.lean` computes that run with a recursion over the inductive's constructors and checks the clauses of `Meets` that the recursion does not compute, such as the output of a run with status 0, so an error in the recursion makes it fail.

Choose the bytes for the paths that the operating system's bytes reach rarely or never.  For a rejection sampler, these are rejected words, words at the bound `2^64 mod N`, values of N for which that bound is large, such as `2^63 + 1` and `⌊2^64 / 3⌋ + 1`, a pass that keeps fewer values than remain, and the cap of the passes, which zero bytes reach.  A file shorter than the run needs reaches the errno path of `random_get`, which the specification states and which a native run reaches only when Linux's `getrandom` fails, as under strace's fault injection, and the status and the output written before the failed call must equal the specification's.  Bytes from a fixed generator, such as the high bytes of a 16-bit linear congruential generator that `awk` computes exactly, give unequal counts to most residues, so a run that merges residues, or exchanges two residues of unequal count, fails.  The headers of `tests/random-histogram/run.sh` and `tests/random-choice/run.sh` list the cases.

A file that holds exactly the bytes that a run draws makes a seeded fault in the byte source, such as a host that skips a byte before each call's bytes, show only as a run that runs out, with status 29, and a file with bytes to spare shows it in the output, as the histogram's case of N of 512 on 4,196 bytes does.  No such fault shows in a refusal, a run with no bytes, or the histogram's run that runs out before its first write, which end with the same status and no output under both hosts.  A case meant to separate values of N needs words on which they differ: the random choice's run on three passes of zero bytes reaches the cap for N of 5 as for N of 6, since both reject the word 0.

A run that reaches only the replies that Linux usually gives cannot tell a program that handles a rare reply from one that does not, so a run of a native executable provokes the rare replies within the premises of its theorem.  A short write is hard to provoke on a pipe or a terminal, while appending to a file of 500 bytes under `ulimit -f 1`, 512-byte blocks in `/bin/sh`, with `SIGXFSZ` ignored makes Linux take 12 bytes of the next write and fail the write after it with `EFBIG`.  The run tells a program that writes once, which exits 0 with 12 bytes written, from a loop, which writes the rest and exits with `fbig`, 22, and QEMU's user mode passes the limit and the ignored signal to its guest.  The headers of `tests/random-choice/run.sh` and `tests/random-histogram/run.sh` state each such run and what it must show.

strace's fault injection provokes such replies at chosen calls: `-e inject=CALL:error=ERRNO` replaces the result of a call with a negated error number, `-e inject=CALL:retval=N` replaces it with the value N, and `:when=FIRST..LAST` restricts the injection to the matching calls numbered FIRST to LAST.  In `tests/random-choice/run.sh`, `inject=getrandom:retval=4096` returns the full count without filling the buffer, so the draw buffer keeps its zero bytes, which N of 6 rejects, and the run must reach the cap with status 77, and `inject=write:retval=0` makes every write take nothing, so the run must exit with status 78 after the passes of `writeAll`.  `tests/manifest-check/run.sh` makes the first read of a file fail with `EIO`, the first three and the first four `openat2` calls return `EAGAIN`, the manifest's `close` fail with `EIO`, and every `write` return 0, and it requires of each run the verdicts and the status that its header states.  The review of the manifest checker's executable found that the driver without these runs passed 22 of the reviewer's 39 wrong programs (the section "Review of the executable's theorems" of `Demos/ManifestCheck/review.md`).  A check of strace's decoded output matches the names that strace prints, `AT_STATX_SYNC_AS_STAT|AT_EMPTY_PATH` for the flags 0x1000 of `statx` and `STATX_ALL` for its mask 0xfff, and strace cuts a string at 32 bytes unless `-s` sets a larger limit, so the manifest checker's driver traces with `-s 4096` to read whole paths.  With `-e raw=…`, strace prints a zero argument as `0` and other numbers in hexadecimal, so a parser of the raw form reads both and fails on a line that it cannot read.

A seeded fault of a frame test must reach the check that it targets and change a byte that the engine writes on every run.  `FAULTS` of `tools/wasi-calls.py` changes or moves one region of one step of `tests/wasi/sys/frame-all.wat`, or changes one expected value: a record, an output, the strings of `environ_get`, the buffer of `fd_read`, and the events of `poll_oneoff` declared short, an 8-byte result word declared with 4 bytes, an output and the events declared one byte late, a record of alignment 8 and an iovec element of alignment 4 moved by half their alignment, and the count that the step of `fd_pread` expects raised by one.  Wasmtime traps on each moved address, and each result word and record of the test lies at a multiple of its alignment that is not a multiple of twice it, so that Wasmtime also traps when a description gives a region a smaller alignment.  `tests/wasi/sys-run.sh` requires of each fault the exit status of the check that should catch it: the number of steps plus the step's number, the frame check's status, for a region declared short or late, the step's value status for a changed expected value, and 1 with Wasmtime's message `Pointer not aligned` for a moved address.  A nonzero status alone would also pass a fault that an unrelated check caught, such as the check of the step's errno.  A status names a step and a check only below 126, since Wasmtime 44's `proc_exit` refuses a status of 126 or more with an error ([`crates/wasi/src/p1.rs`](https://github.com/bytecodealliance/wasmtime/blob/v44.0.0/crates/wasi/src/p1.rs)), after which `check_outcome` of `tools/wasmtime-host.c` exits with status 1.  The value checks of a step therefore exit with twice the number of steps plus the step's position among the steps that check values, which the step's comment in `frame-all.wat` gives, so that every status of the present list of steps lies below 126, and `tools/wasi-calls.py` refuses a list of steps whose statuses would reach 126.  The driver runs the frame test of every flat call and the test of each seeded fault under `timeout --preserve-status`, since `timeout` alone exits with 124 when a run times out, which is the value status of one of the steps.  The bytes that the engine writes into the part of a region that a fault drops must differ from the guard byte 0xA5 with certainty.  The last of the 32 random bytes of `random_get` equals the guard with probability 1/256, so a fault that dropped the last byte of that output would pass unnoticed in one run of 256, and the faults that shorten an output take steps whose value checks fix the dropped byte, such as the step of `path_readlink` with capacity 1, which writes the byte `f`.

A frame test of the Linux call layer's descriptions runs each call against guard pages, and each class of wrong description needs a requirement of its own.  A test that checks only the bytes outside the declared regions passes an output region declared too long, an input declared as an output, and a call number whose call writes the same shape, such as `clock_getres` in place of `clock_gettime`.  `tests/linux/sys/frame.c`, which `tools/linux-calls.py` writes, places each region once ending at a page without access and once beginning after one, so that the call's true region reaches into a page without access at one of the placements when its region is declared one byte short or late, and a count that the call returns, such as `getrandom`'s, detects a short or late region with certainty.  It runs each placement with each fill of `FILLS` and requires each byte of the output region that the call writes to differ from the fill in one of the runs, which detects an output declared too long.  Each of X0 to X5 that a description leaves unset holds a value whose low 32 bits, 0xFFFFFFF7, are an invalid descriptor, clock, and flag word of `getrandom`, and as `openat`'s flags they set `O_PATH` and `O_DIRECTORY`, under which `build_open_how` of Linux's `fs/open.c` keeps an open that succeeds only on a directory, so a description that omits such an argument fails with an error on the test's names, none of which names a directory, and one that omits `openat`'s mode or `exit_group`'s status fails the step's value check or its expected status.  Value checks also tell apart calls of one shape: the check that `tv_sec` lies within a few seconds of the C library's clock detects `clock_getres`.  `FAULTS` of `tools/linux-calls.py` seeds wrong descriptions, each with the check that must fail first, and `tests/linux/sys-run.sh` requires of each the exit status that the generator predicts.  No run observes the kinds `fd`, `dirfd`, and `value` or whether a call returns a descriptor, so a second lowering, `tests/linux/syzlang-lowering.py`, checks them.  The theorems use the Lean functions that compute the regions, and the lemmas that the generator writes for each call, such as `LeanExe.Linux.regions_read`, tie those functions to the regions that the test places.

A driver that runs a check over the files of a directory or the matches of a pattern passes when there are none, so it requires a nonempty set or the number of items that it expects, as the drivers above count axiom reports and saved cases.  A digest that combines many results by addition or by exclusive or lets an error in one result cancel an error in another, so compare the results one by one, or a cryptographic hash of their bytes.  A seeded fault that makes the check fail for an unrelated reason shows nothing, so the step that runs it requires the predicted difference, as `cosim-check` requires a differing case of `ADC`.

A check that a program must pass, with a theorem of its soundness, rests on assumptions about the terms it checks, and its tests include terms that break each of them.  A soundness proof that reads data from the checked term proves only what that data claims: `Verified.Wasi.Command.HandleCheck` takes the `.handle` positions of a `sys` command, and `LeanExe.Wasi.WellBracketed` those of a `sys` event, from the description of its call, so both require the description to be one of `LeanExe.Wasi.Call.table`, which `tools/wasi-calls.py` generates from the witx, and the kernel decides the membership with the rest of the handle check.  `tests/wasi/HandleCheck.lean` keeps hand-written descriptions of `fd_write` with a `.word32` descriptor and of `poll_oneoff` with a word in its descriptor field, each applied to the word 1, as cases that the check refuses, and without the membership both pass the check, whose soundness theorem then holds of them because the discipline reads the same descriptions.  An analysis reused for values that it was not written for has the same gap: the move analysis gives every scalar a borrowed mode (`Verified.Wasi.Command.paramChoice`) and leaves scalar arguments out of its alias tests (`Verified.callMoves` and `Verified.Wasi.EffectSig.callMoves`), so a check of handles represented as words that relied on it would accept one handle passed to two owned parameters.  A check that recognizes a reflected operand is tested on the forms that the reflector writes in the scopes of compiled programs, since hand-written commands show only the forms that their author wrote.  The reflector puts the binding of `LeanExe.Wasi.Handle.preopened` under a `Verified.Expr.letPair` for each variable of type `.pair` in scope and for each component of such a variable that is itself a `.pair`, so `tests/wasi/HandleCheck.lean` compiles, beside its hand-written commands with one and two `letPair`s, a program that opens a file after `args`, whose binding of the handle has three: a recognizer that reads through at most two `letPair`s passes the hand-written tests and refuses that program.  A model of such a check runs the wrong programs that the new values make possible before code depends on it, with the method of [the entry on independent review](../independent-review/README.md), and [the entry on handles and brackets](../wasi-handles/README.md) describes the check of the handle discipline.

The worked examples are the step of `m7-board.sh cosim-check` that runs `adc-carry`, the negative control in `self_test` of `tests/cic/reference.py`, the overrun phase of `uart_sha.py --overrun` with its control run against `sha.bin`, and the exact counts of axiom reports in `m7-board.sh`, `m7-qemu.sh`, `a64-images.sh`, and `m7-image.sh`.  `cosim-check` and the image drivers repeat their controls on every run, and `reference.py` runs its self-test by default.  The altered logs of the BMS replay and the changed bytes of the M7 images are single runs that the documents record, so a change to `bms-replay` or to the image checks needs them run again.
