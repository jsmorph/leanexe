# Isla traces with symbolic control registers

The entry applies when a form's Isla trace must hold for every state of a system whose kernel, hypervisor, or firmware sets the control registers, such as a Linux process at EL0, rather than for the state that the program's own startup writes.  A configuration that fixes such a register at a value that the system never holds gives a theorem that covers no state of the system while its proof succeeds, as [the entry on satisfiable hypotheses and complete conclusions](../non-vacuous-statements/README.md) states of premises copied from a tool's configuration.  The semantics of traces takes the register of the stack pointer as a parameter, `LeanExe.A64.Isla.SpReg`, so a trace of a process at EL0 states its theorem with `.el0`, SP_EL0, where the bare-metal traces state `.el1`.

Leave each control register that a trace reads symbolic, and fix only the bits whose values the system gives, each with a reset constraint written as an extract of one bit or one field.  `tests/isla/linux-traces.sh` declares such a register with `-R "HCR_EL2=undefined:%struct HCR_EL2_Type"` and fixes a bit with `--reset-constraint "= ((_ extract 34 34) HCR_EL2.bits) #b1"`, which Isla records as an `assume` event.  The walk evaluates the extract to `x / 2 ^ 34 % 2`, and `LeanExe.A64.Isla.LinuxUnknown.Holds` states each fixed bit in that form.  `LeanExe.A64.Isla.holds_vhe` and `LeanExe.A64.Isla.holds_el1` give the bits of HCR_EL2 and SCR_EL3 with the powers computed, `LeanExe.A64.Isla.holds_vhe_fp` gives those of the floating-point registers, and a proof restates each other field in the same way, as `svcVhe_bwd` does with `have h5 : u.mdcr.toNat / 256 % 2 = 0 := hu.tde`, so that the walk rewrites the event and every later test of the bit to a literal.  The profile `LeanExe.A64.Isla.linux` takes every bit of such a register from a field of `LeanExe.A64.Isla.LinuxUnknown`, `u.Holds ℓ` fixes the constrained bits, and a theorem that holds for every `u` with `u.Holds ℓ` covers every value of the others.  A run with the registers symbolic and unconstrained shows the bits that the trace tests as the extracts of each register's variable in the trace, and a tested bit gets a constraint only when the system gives it a value, the model must choose one, or the run's conditions fix it, while the theorem covers both values of every other tested bit.

A constraint fixes a value that the system gives, makes a choice of the model, or states a condition on the run, and each kind needs its own statement.  A value that the system gives cites the source that sets it, Linux 7.0's code or the boot protocol, as the script's header does for most bits, and it constrains the register that the system writes.  Linux writes ZCR_EL1, which HCR_EL2.E2H redirects to ZCR_EL2, and it writes no ZCR_EL3, so the floating-point traces fix the LEN field of ZCR_EL2 at 0, the 128-bit vector length of the host's cores, and leave ZCR_EL3 symbolic, and `LeanExe.A64.Isla.len_min` reduces to 0 the smaller of the two fields, which the walk computes.  A choice of the model has no such source, and the docstring of `LeanExe.A64.Isla.LinuxUnknown.Holds` and the AArch64 document name it as a choice: the host's cores lack FEAT_SME and with it SMCR_EL3, from which the Sail model computes the streaming vector length in each write of a D register, and the traces fix its LEN field at 0.  A condition on the run is a premise that a user of the theorem must meet, such as TDE of MDCR_EL2, SS of MDSCR_EL1, and SVC_EL0 of HFGITR_EL2 clear, which hold unless a VMM debugs the guest, a tracer or a uprobe steps the process, or the hypervisor traps SVC.  A profile's features describe one processor, and a profile used for another needs a comparison of the two.  The Linux traces take the features of the KVM guest, which lack the host's FEAT_SPE, with which a taken branch and exception entry also write the sampling state of the Statistical Profiling Extension, and the script's header and [the AArch64 document's section on what the Linux target trusts](../../../docs/a64-bare-metal.md#what-the-linux-target-trusts) state that difference as an assumption, as that section states the choices of the model and the conditions on the run.

A system's traces need premises that the bare-metal traces do not.  The semantics writes a field of a struct register by updating the whole struct that the state holds, while the premise of `LeanExe.A64.Isla.Agrees` names the accessor paths that the trace reads, such as the field EL of PSTATE, so a trace that writes fields of PSTATE, as exception entry does, needs a premise on the whole register beside those on its fields, and `TestSupport.A64.Isla.SvcAgrees` assumes `σ "PSTATE" = π "PSTATE"`.  `SvcAgrees` takes the place of `Agrees` for `SVC #0`, since the model's decoder rejects the instruction's word and `exec` gives no state to compare, and it states the registers that exception entry writes.  Exception entry branches to the vector base with the vector's offset in bits 10 to 0 through AArch64.BranchAddr, which sign-extends or zero-extends the address from bit 55 when TBI applies at the target level, so with the vector base and TCR symbolic the trace of `SVC #0` forks on bit 55 of the vector and on the TBI and TBID bits of the half of the address space that bit 55 selects, and the paths' program counters differ.  The premise that bits 63 to 55 of the vector base are set, `u.vbar2.toNat / 2 ^ 55 = 511` in `svc_vhe`, which holds for a kernel's vector table in the upper half of the address space, gives every path the same program counter, `TestSupport.A64.Isla.lowerSync` of the base, and refutes the paths that test bit 55 clear.

A proof's failures name the bits that the constraints and premises leave open.  A forward lemma whose refutation of a path's end fails stops with a counterexample of `omega` that names the bit: the trace of `SVC #0` under a kernel at EL1 tests the RW bit of HCR_EL2, whose paths with RW clear take the vector of a lower level that uses AArch32, at offset 0x600, and the script fixes RW at 1, the value that KVM's `HCR_GUEST_FLAGS` gives a 64-bit guest.  `mem_bwd` takes the right branch of each `cases` whose left condition it cannot prove and leaves the right condition as a later goal, beside the bounds of declared variables that `mem_side` closes, so the goals that remain name the bits on which the backward lemma must split.  `TestSupport.A64.Isla.svcVhe_bwd` splits on IESB and SPAN of SCTLR_EL2, on TBI1 and TBID1 of TCR_EL2, and, where IESB is clear, on EA and NMEA of SCR_EL3, all before `apply Exists.intro`, since after it the outcome is one metavariable that the branches of a later split would share.

Some configurations exceed Isla's memory.  With SVE enabled at the exception's target level, AArch64.TakeException calls MaybeZeroSVEUppers, whose CONSTRAINED UNPREDICTABLE choice for each of Z0 to Z31, P0 to P15, and FFR gives 2^49 paths, and a configuration that disables SVE at that level avoids them only with a value that Linux never holds.  `--abstract MaybeZeroSVEUppers` records an `abstract-call` with a unit result on each path, the theorems assume that the call returns, and the header of `tests/TestSupport/A64/Isla/Svc.lean` covers the function's effect, on bits that the model does not hold, by a reading of Arm's pseudocode under reading 11 of `LeanExe/A64/Isla/Trace.lean`.  The Armv9.4 Sail model, in the IR from which `tests/isla/traces.sh` traces, reads TTBR0_EL2 through `TTBR0_EL2_read`, which takes bits 47 to 1 from the AArch32 register HTTBR, so a configuration that sets `_TTBR0_EL2` alone leaves the table's base symbolic, `--fixed-memory` answers no read of the table walk, and the descriptors that Isla reads from symbolic memory fork the walk until Isla exhausts its memory.  A configuration of a translation at EL2 sets HTTBR.

A lemma of the walk that names one profile's unknowns applies to that profile alone.  `LeanExe.A64.Isla.rwchain_eq`, which folds the read that `V_set` makes between its two writes of an element of `_Z`, takes the upper bits as a function `z : Fin 32 → BitVec 1984`, so the walks under the profiles of `LeanExe/A64/Isla/Profile.lean` and under `linux` apply it with the field of each profile's unknowns.  A form of the lemma that names `LeanExe.A64.Isla.Unknown.z` finds no instance in the walk of a trace under another profile, and the walk leaves the chain of 32 elements in its goal.

The worked examples are `svc_vhe` and `svc_el1` of `tests/TestSupport/A64/Isla/Svc.lean`, with `svcVhe_bwd` for the splits, and `b_vhe` of `tests/TestSupport/A64/Isla/Branch.lean` for a branch under the host's kernel, with the script `tests/isla/linux-traces.sh` and the profile of `LeanExe/A64/Isla/Linux.lean`.  The modules of `tests/TestSupport/A64/Isla` read their traces at elaboration, so `entry.json` lists their theorems under `unimported`, and `tests/isla/theorems.sh` checks them.  [The entry on instruction forms against Isla](../isla-form-proofs/README.md) covers the walks and the forms' theorems, and [the entry on code around an executable reference](../reference-harness-audit/README.md) covers the review of a profile's values and of the edits of the IR.
