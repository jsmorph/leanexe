# A new command of the WASI effect IR

The entry applies when a change adds a constructor to `Verified.Wasi.Command`, the effect IR that `verified_compile_wasi` reflects a WASI program to, as `Verified.Wasi.Command.letPair` was added to split a pair where an action binds it.  The constructor needs a case in every definition and inductive that matches on commands, and the compiler's proofs need a part for its code and one for its charge.  The list below holds every such case that the addition of `letPair` changed.

The analyses of `Verified/Wasi/EffectAnalysis.lean` need a case each: `Verified.Wasi.Command.uses`, `Verified.Wasi.Command.useMask` with `Verified.Wasi.Command.useMask_testBit`, `Verified.Wasi.Command.literals`, `Verified.Wasi.Command.placeArgs`, `Verified.Wasi.Command.callsReady`, and `Verified.Wasi.Command.callsUsed`, and so do `Verified.Wasi.Command.denote`, `Verified.Wasi.Command.width`, `Verified.Wasi.Command.demands`, and `Verified.Wasi.Command.handleCheck`.  The code generator needs `Verified.Wasi.Command.codeWith` and its mask form `Verified.Wasi.Command.codeMask` with `Verified.Wasi.Command.codeMask_eq`, and the readiness check needs `Verified.Wasi.Command.fragments` and `Verified.Wasi.Command.fragmentsMask` with `Verified.Wasi.Command.fragmentsMask_eq`.  The proofs need cases in `Verified.Wasi.Command.handles`, `Verified.Wasi.Command.code_spec_with`, and `Verified.Wasi.Command.cost_code_spec_with`, in the resource semantics `Verified.Wasi.Resource.ResourceExec` and `Verified.Wasi.Resource.ResourcePrefix`, whose recursor applications in `Verified.Wasi.Resource.ResourceExec.erase`, `Verified.Wasi.Resource.ResourcePrefix.erase`, and `Verified.Wasi.Resource.ResourcePrefix.advance` list one goal for each constructor of the mutual block, in `Verified.Wasi.Resource.Rule` and `Verified.Wasi.Resource.RuleAt` with `Verified.Wasi.Resource.exec_rule`, `Verified.Wasi.Resource.prefix_rule`, `Verified.Wasi.Resource.exec_rule_at`, and `Verified.Wasi.Resource.prefix_rule_at`, and in `Verified.Wasi.Resource.command_coverage` and `Verified.Wasi.Resource.command_advance_coverage`.

`Verified/Wasi/CommandLetPair.lean` proves the code of `letPair` in three parts.  `Verified.Wasi.wp_letPair_head_with` runs the pair's code: for an owned pair it transports the pure `Verified.Expr.code_spec` of the variable, and for a borrowed pair it loads the words directly, since the pure `After` hides the words that the code pushes, and the regions of borrowed components lie apart from the command's scratch bytes only because they are the pair's.  `Verified.Wasi.wp_letPair_tail_with` stores the components and releases the unused owned ones through `Verified.Wasi.wp_releaseVars_with`, and `Verified.Wasi.After.letPair` composes the body's `After` with the binding's, as `Verified.After.bind2` does for pure code.  The tail lemma generalizes the mode expression `(Expr.var pair).mode (slots.map Slot.mode)` to a variable, since `rw` does not see through a `let` that names it, and `Verified.Wasi.command_letPair_spec_with` and `Verified.Wasi.cost_command_letPair_spec_with` give the command's correctness and its charge.

The reflector's proof of a split uses the eta law of the pair's view, which `Verified.Reflect.pairView` states for a function into `Type`, while an action lies in `Type 1`.  `Verified.Wasi.Reflect.splitThen` therefore applies the law at the identity and lifts it with `congrArg` to the action, which `Verified.Wasi.Reflect.rel_eta` then rewrites, and `Verified.Wasi.Reflect.letPair_rel` relates the reflected `letPair` to the native action.  [The entry on WASI effect charges](../wasi-effect-charges/README.md) describes the rules that bound the new command's charge in a program's budget.
