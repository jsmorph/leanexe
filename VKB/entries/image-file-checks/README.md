# Image files

The entry applies when a theorem must concern the bytes of an AArch64 Image or a Cortex-M7 image that a compiled generator wrote to a file.  The kernel compares the file with the generator's output, so the compiled generator and the code that wrote the file leave the trusted base, while the reading of the file and the kernel remain.  The Image theorems of the `a64-image-theorem` entry and the board theorems of the `m7-board-theorem` entry take such a check as a premise.  The `file-theorems` entry covers `.wasm` files, whose reader and comparison differ.

The file module defines the file's number, whose base-256 digits, the lowest first, are the file's bytes, with `file_nat% "NAME.img"` of `LeanExe/FileNat.lean`, and the file's length with `file_size% "NAME.img"`.  It proves the check, a `Bool` equal to `true`, by `decide +kernel`, so that the kernel runs the generator on the program's module, entry, and arguments.  For an A64 Image the check is `LeanExe.A64.bytesOk (LeanExe.A64.genImage m k args room cap o imageBase) XBytes XSize = true`, which `LeanExe.A64.of_bytesOk` turns into the image's bytes, and the A64 file modules set `maxRecDepth` to 100,000 for the whole file.  For an M7 image that starts from reset the check is `LeanExe.M7.bootFileOk boot program XBytes XSize = true`, over the vector table and the instructions, and for code without a head it is `LeanExe.M7.fileOk (genProgram …) XBytes XSize = true`, which `LeanExe.M7.fileOk_ok` turns into the instructions whose bytes the file holds.  Each check forms the number of the generated bytes with `LeanExe.FileNat.natOfBytesPaired`, and `LeanExe.FileNat.natOfBytesPaired_eq` and `LeanExe.FileNat.byteAt_natOfBytes` relate it to `LeanExe.FileNat.natOfBytes` and to each byte through `LeanExe.FileNat.byteAt`.

The checks of `LeanExe/M7/Parts.lean` divide a large M7 image of a program without an area into parts, each a declaration of its own.  Each part states its bytes as a slice of the file's number with `LeanExe.M7.sliceOk`: `LeanExe.M7.bootHeadOk` for the vector table, the self-loop, and the initialization, `LeanExe.M7.mainPartOk` for `main`, `LeanExe.M7.functionsPartOk` for a range of the functions that calls reach from the step, each through `LeanExe.M7.functionPartOk`, and `LeanExe.M7.tailPartOk` for the trap stubs with `udivmod64`.  A function's part takes the layout from a literal list of the functions' sizes in units, `TestSupport.M7.Gw.gwSizes` for the gateway, and checks the function's own entry of that list, so that its check evaluates the generator on that function alone, and a closed fact such as `TestSupport.M7.Gw.gw_count` states that the list has an entry for each function that `LeanExe.M7.reachedFns` gives.  `LeanExe.M7.functionsPartOk_append` joins adjacent ranges, and `LeanExe.M7.bootFileOk_parts` or `LeanExe.M7.fileOk_parts` joins the parts, with a closed fact on the file's length and on `n < 256 ^ len`, into the check that the theorems take.  The `closed-computations` entry states the general rule that splits a large kernel check into declarations.

The module reads the file at elaboration, and `file_nat%` resolves the path against the directory in which Lean runs.  A driver therefore writes the images and then elaborates each module with `lean` in their directory: `tests/baremetal/a64-images.sh` for the A64 Images, and `tests/baremetal/m7-board.sh`, `m7-qemu.sh`, and `m7-image.sh` for the M7 images.  No build target includes these modules and no module imports them, so no entry lists them in `modules`, and an entry names their theorems with their file paths.  When the file differs from the generator's output, the kernel rejects the image's theorem, and for an image in parts it rejects the part that holds the changed byte, as the section "The images and their kernel checks" of `docs/m7-bare-metal.md` records.

The kernel's evaluation of `natOfBytes` forms the number of every suffix of the bytes and keeps each, which takes memory in proportion to the square of the length, while `natOfBytesPaired` pairs adjacent digits in rounds and forms numbers of about the length in each round, as its docstring states.  `LeanExe.A64.genImage` joins its parts from the right, so that each byte of the code passes through one append (header of `LeanExe/A64/BootImage.lean`), and the fuel of `LeanExe.CallGraph.reachFrom` is the module's number of functions plus one, whose evaluation reads no function's body (its docstring), so the kernel evaluates the bodies of the reached functions and no others.  The check of the gateway's image as one declaration does not fit in 16 GiB (header of `LeanExe/M7/Parts.lean`), and the parts do.  The kernel's time and peak memory for each M7 image are in the table of the section "The images and their kernel checks" of `docs/m7-bare-metal.md`, and the A64 figures are in the section "Encoding and the image's bytes" of `docs/a64-bare-metal.md`.  The drivers cap each check's memory: `a64-images.sh` at 16G for each Image module, `m7-board.sh` at 12G for the echo, the area, and CRC-32 and at 16G for the gateway and SHA-256, `m7-qemu.sh` at 12G for the echo and CRC-32 and at 16G for the gateway and SHA-256, and `m7-image.sh` at 16G.

The worked examples are file modules, which no module imports.  `tests/TestSupport/M7/GwBoardFile.lean` checks the gateway's image from reset in parts and joins them with `bootFileOk_parts` in `gw_file`, and `tests/TestSupport/M7/GwImageFile.lean` does the same for the gateway's code with `fileOk_parts`.  `tests/TestSupport/M7/NucleoFile.lean` checks the echo's image in one declaration, `echo_file`.  `tests/TestSupport/A64/ImageFilesEuler.lean` holds the Euler solver's Image alone, which `a64-images.sh` elaborates on its own because of its memory, as the header of `tests/TestSupport/A64/ImageFiles.lean` states, and `tests/TestSupport/A64/ImageFilesFloor.lean` checks several Images of one module in one file.
