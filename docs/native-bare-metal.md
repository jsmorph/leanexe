# LeanExe native code on bare metal: design and plan

## Goal and end-to-end statement

The final result of [the translator's design](native-translator.md) is `p.f.native`, a theorem about one call of one C function in the Lean copy of CompCert's Clight.  A C host, linked with libc and run under an operating system, places that call's arguments and reads its results, and no proof covers it.  This design replaces the host, libc, and the operating system with a startup routine in assembly and a `main` that the translator writes and proves.  The binary runs on QEMU's `virt` machine for AArch64, under TCG and under KVM on AArch64 hardware, and on QEMU's `mps2-an500`, a Cortex-M7, under TCG.  The goal is one theorem per program that states the program's whole observable behaviour in the terms of CompCert's semantics, and an argument, checked in Rocq for the steps that CompCert's proofs cover, that transfers the theorem to the Asm program that `ccomp` produces.

The program is the translation of a module, a volatile global `lx_out` that the linker places at the UART's data register, and a generated `main`.  `main` calls `lx_init`, calls an entry `run` that the verified compiler compiled, on arguments fixed when the program is built, and writes the bytes of the result to `lx_out`.  The theorem `p.f.program` of an entry `f` has two cases.  Either the program terminates with result 0 and a trace of one volatile store per byte of the result's encoding, or, when `run` may abort, it terminates with result 1 and an empty trace.  Other forms of `main` [read input that a loader places in memory](#arguments-not-fixed-in-advance), [run a step function forever](#a-program-that-runs-forever), or [drive a device's registers with one access per step](#device-registers-and-requests).  The design covers no interrupts and no second core.  Time enters only as [values that a program reads from a timer](#clock-reads-and-deadlines), and no theorem bounds the time that code takes to run.

| Step | From | To | Covered by |
| --- | --- | --- | --- |
| 1 | Lean definition | `p.run.native` | existing proofs |
| 2 | `p.run.native` | `bigstep_program_terminates` of the whole program in the Lean copy | new Lean proof, described below |
| 3 | Lean copy | CompCert's `Clight2.bigstep_program_terminates` of the program that `clightgen` reads | review, differential tests, the per-build check, and a renaming lemma |
| 4 | program that `clightgen` reads | program that `ccomp` compiles | trusted: one front end, with identifiers numbered differently |
| 5 | Clight big-step termination | behaviour of the Asm program | composition of CompCert's proofs in Rocq, proved in `rocq/Clight2Asm.v` |
| 6 | Asm program | machine | trusted: printer, assembler, linker, startup code, CompCert's run-time functions on ARMv7-M, CPU, and devices |

## Target machine

One target is AArch64, on QEMU's `virt` machine with 1 GiB of RAM, compiled with CompCert's `aarch64-linux` configuration, and [the Cortex-M7 target](#the-cortex-m7-target) is the other.  QEMU runs the image on an emulated Cortex-A57 under TCG and on the processor of AArch64 hardware under KVM.  CompCert 3.18 has no bare-metal configuration for any 64-bit target: its `configure` lists `-eabi` variants only for PowerPC and 32-bit ARM (lines 43 to 62).  Of the 64-bit targets, x86-64, RISC-V, and AArch64, AArch64 needs the fewest components that no proof covers:

| Target | CompCert run-time functions that the translations need | Lean copy | Startup |
| --- | --- | --- | --- |
| AArch64 | none: `runtime/Makefile` builds only `vararg.o` for it (line 26), and a translated module links with no library | `Archi.aarch64`, with the corpus passing natively on AArch64 | QEMU enters the image at EL1 |
| x86-64 | `__compcert_i64_dtou` and `__compcert_i64_utod`, which `backend/SplitLong.vp` calls for unsigned conversions (lines 136 and 140), since `x86/SelectLong.vp` selects none of its own.  CompCert's proofs do not cover the library | `Archi.x86_64` | Multiboot loader enters in 32-bit protected mode with paging off, so page tables must exist before any CompCert code runs in 64-bit mode |
| RISC-V 64 | not checked.  `runtime/Makefile` builds the whole set of 64-bit helpers for RISC-V (line 28) | no `Archi` instance, so a new one and new differential tests | not tested |

`ccomp` passes the link to gcc and accepts `-nostdlib`, `-static`, `-T` with a linker script, and `-Wl,` (`driver/Linker.ml`, lines 66 to 95).  It always appends `-L<stdlib> -lcompcert` (lines 21 to 30), but on AArch64 that library holds only the variadic-argument helpers, which no translation calls.  In the experiments, the object file of the translation of each of eight corpus modules had no undefined symbol, and only the test host's replacement for `printf` used CompCert's library, for the variadic-argument helpers.  The generated code runs from RAM: QEMU's ELF loader writes `.text`, `.rodata`, and `.data` at their link addresses, so the startup code copies nothing.

QEMU documents two fixed addresses of `virt` for bare-metal guests, flash at 0 and RAM at `0x4000_0000`, and places the device tree at the start of RAM.  Every other device address may change between QEMU versions and must come from the device tree.  The image is linked at `0x4010_0000`, above the device tree.  The UART address is fixed in the linker script, and the test harness compares it with the device tree that `-machine virt,dumpdtb=FILE` writes for the QEMU in use: QEMU 8.2.2 gives `pl011@9000000` with `reg = <0x00 0x9000000 0x00 0x1000>` and `stdout-path = "/pl011@9000000"`.  Reading the device tree at startup would avoid the check at the cost of a parser in the trusted startup code.

A board differs in these ways, none of which the proofs cover: the exception level at entry, the UART's address and setup, the RAM base, and the state of the caches and TLBs at reset, which may need invalidation sequences that the implementation defines (DDI 0487 issue M.d, sections D7.5.6 and D8.16.1, pages D7-7650 and D8-7852).  QEMU 8.2.2 emulates the Raspberry Pi 3B (`raspi3b`, Cortex-A53) but not the 4B, which newer QEMU documentation lists.  The project has not chosen an AArch64 board.  B8 runs the programs under KVM instead, where the processor, its memory system, and its alignment checks are those of AArch64 hardware and the devices are QEMU's models of `virt`'s.

## The generated main and its outputs

The translator writes `main` after the translation's functions, in the same C file, so that `ccomp` compiles one whole program and `transf_c_program` covers it in one run.  `main` never takes the address of a local, so SimplLocals converts its locals to temporaries, as it does for the translation's functions.  For an entry `lxf_run` with scalar parameters and an `Array UInt64` result, `cmain` (`LeanExe/Native/Bare.lean`) writes:

```c
extern volatile unsigned int lx_out;
int main(void) {
  unsigned long long l0;
  unsigned long long l1;
  unsigned long long l2;
  lx_init();
  l0 = lxf_run(7ULL, 9ULL);                /* the arguments fixed at build time */
  if ((lx_status != 0U)) {
    return ((int)lx_status);
  }
  l1 = /* the word at l0, by the translator's loadBytes */;
  l1 = ((8ULL * l1) + 8ULL);               /* the length word and the elements */
  l2 = 0ULL;
  while ((l2 < l1)) {
    lx_out = ((unsigned int)(*(((unsigned char *)lx_mem) + (l0 + l2))));
    l2 = (l2 + 1ULL);
  }
}
```

`clightgen` and `ccomp` append `return 0;` to `main`.  For a `UInt64` result, eight stores `lx_out = ((unsigned int)((l0 >> 8kULL) & 255ULL));` replace the loop.  The output is the array's representation in `lx_mem`, the length word and then the elements, little-endian, which `Heap.Owned` and `MemRel` describe byte by byte.  Byte loads need no alignment fact about `l0`.  An entry with several results, such as a digest of four words, returns `void` and leaves the words in the translation's result globals (`ResultRel`), so for the kind `words k` `main` calls it without a result and writes the eight bytes of each of the first `k` result globals in order, with the stores of the `UInt64` case.  A program converts another result type to one of these forms with a Lean function that encodes it as an `Array UInt64`, compiled with the rest of the program.

Arguments fixed in advance take two forms.  A scalar argument is a constant in the call.  A heap argument, such as an array or a byte string, is a constant inside a Lean definition without parameters, `def run : Array UInt64 := encode (f input)`, for which the reflector's theorems take the argument type `Unit`, as [the compiler's internals](../Verified/README.md#the-reflector) state.  The verified compiler compiles the constant with the rest of the definition, and `p.run.implements` covers the construction of the value.  `main` therefore places nothing in `lx_mem` before the call, and no theorem about a sequence of host calls is needed.  The programs of B4 take their messages as words instead and build them in the heap, since the command `bare_program` does not cover `ImplementsStatic`, the theorem of a program with byte literals, which such a constant gives.  A constant table is an argument that a wrapper applies, as [the internals' section on tables](../Verified/README.md#theorem-statement-allocation-bounds-and-tables) states, so the CRC and SHA programs of B4 are wrappers.

The program can report results in these ways, and CompCert's semantics observes the first two:

| Channel | In CompCert's behaviour | Use |
| --- | --- | --- |
| `int` that `main` returns | yes: `Terminates t r` includes `r` | 0, the trap code of `lx_status`, or 64 when a program with input reads a length above `inMax`.  The startup code passes `w0` to QEMU's exit status through semihosting |
| Volatile stores to a volatile global | yes: each is an event `Event_vstore chunk id ofs v` of the trace, which every pass preserves | bytes of the result, through `lx_out` at the UART's data register |
| Memory region read after the program halts, by a debugger or QEMU's monitor | no: `program_behaves` records only the trace and the result, so CompCert's theorem says nothing about final memory | none |
| Semihosting calls from C, such as `SYS_WRITEC` | only as an external call, whose event and result come from `external_functions_sem`, a parameter of CompCert.  The Lean theorems hold for every such semantics and so conclude nothing about a call to one | exit call of the startup code, which no proof covers |

A volatile store becomes an event of the trace as follows.  C2C gives an `extern volatile` declaration an empty initializer and `gvar_volatile = true` (`cfrontend/C2C.ml`, lines 1278, 1279, and 1305 to 1307).  SimplExpr converts an assignment to a volatile lvalue to `Sbuiltin None (EF_vstore chunk)` with the lvalue's address and the value (`cfrontend/SimplExpr.v`, lines 184 to 226), and `clightgen`'s output shows this form for a store to `lx_out`.  `volatile_store` of a block that `Senv.block_is_volatile` marks emits `Event_vstore` and leaves memory unchanged, with no permission check (`common/Events.v`, lines 571 to 583).  The assembler and linker resolve `lx_out` by name to the address in the linker script, so the event means a 32-bit store to that address.

The exit status of a program is therefore one of these codes:

| Code | Meaning |
| --- | --- |
| 0 | `main` wrote its output and returned |
| 1, 2, 3 | `lx_status` after a trap at `unreachable`, an access outside memory, or a division by zero, which `main` returns |
| 64 | program with input read a length above `inMax` |
| 254 | startup code found an exception level other than 1 |
| 255 | exception, which the vectors report |

On QEMU, the PL011 model passed every byte to its output in the experiments.  On hardware the transmitter can be busy when `main` writes, and the `main` of `bareMain`, `inMain`, or `ctlMain` does not wait for it: a volatile read of the UART's flag register is an input event whose value a theorem of termination would have to quantify over, and a loop that waits on it has no termination proof.  Under KVM each store to the UART reaches QEMU's PL011 model, as under TCG, so B8 does not answer the question.  A program with requests polls instead: its step reads the status register in one window of a loop that never ends and writes in a later window, and its theorem quantifies over the values read, as [the section on requests](#device-registers-and-requests) describes.

## The program-level theorem

### Statement

The Lean copy adds CompCert's judgment for a whole program (`cfrontend/ClightBigstep.v`, lines 252 to 260):

```lean
inductive bigstep_program_terminates (A : Archi) (X : ExtSem) (p : program function) :
    trace → int → Prop
  | intro (b : block) (f : fundef function) (m0 m1 : mem) (t : trace) (r : int) :
      init_mem A p = some m0 →
      Genv.find_symbol (globalenv p) p.prog_main = some b →
      Genv.find_funct_ptr (globalenv p) b = some f →
      type_of_fundef f = .Tfunction [] type_int32s cc_default →
      eval_funcall A X (globalenv p) m0 f [] t m1 (.Vint r) →
      bigstep_program_terminates A X p t r
```

The program is `bareProgram pre T (bareMain cap k args kind)` (`LeanExe/Native/Proof/Whole.lean` and `LeanExe/Native/Bare.lean`): CompCert's external declarations `pre`, the translation's definitions in the order of the C text, the declaration of `lx_out`, and `main`, which calls the entry `k` on the words `args` and writes a result of the kind `kind`, with `prog_main` naming `main`.  `clightgen` puts its declarations of CompCert's built-in and run-time functions first, among them `__builtin_fsqrt`, which the translation places between `lx_pun` and the result globals, so `pre` includes that declaration.  The theorem holds for every `pre` of external function declarations whose identifiers are distinct from the program's and which declares `__builtin_fsqrt` at its signature, the hypotheses of `wholeOk_bare` that `PrefixOk pre` collects, and the per-build check confirms that the program `clightgen` reads has that shape.  The command `bare_program p.f x [args] r` (`Verified/Bare.lean`) states and proves it for the entry of `f`, its argument `x`, whose words are `args`, and its result `r`, which is `f x`:

```lean
theorem p.f.program (A : Archi) (X : ExtSem) (pre) (hpre : PrefixOk pre) :
    bigstep_program_terminates A X (bareProgram pre p.translation (bareMain nativeCap k args kind))
        (outTrace (encode r)) 0 ∨
      (aborts = true ∧ bigstep_program_terminates A X
        (bareProgram pre p.translation (bareMain nativeCap k args kind)) E0 (UInt32.ofNat 1))
```

`encode` is `encodeWord`, the eight bytes of a word from the lowest, or `encodeArray`, the eight bytes of the array's size followed by the eight bytes of each element, and `outTrace` maps each byte `b` to `Event_vstore Mint32 outId 0 (EVint b)`.  The proof has one step for each part of `main`'s body: `init_mem` of the whole program, with the prefix and `lx_out` before and after the translation's blocks; `lx_init_correct` for the call of `lx_init`; `p.f.native` for the call of the entry, with the premises that `start_whole` proves for the state after `lx_init`, and the quietness of the translation, which makes the call's trace empty; the test of `lx_status`; a loop lemma that produces one event per byte from `UInt64Array.At` and `MemRel`; and `outcome_result_value` for the returned `int`.  The proof uses the translation with the alignment test.  Under the translation without it, the call of the entry also needs `AlignedInput`, which the heap after `lx_init` meets: its `top` is `tablesEnd tables`, or the `top` of the literal pool for a module with literals, both multiples of 8, and its free list is empty.

The lemmas of this proof exist only for the translation with the test.  Each theorem in the table takes `translate cap m = some T`, whose option `alignedAccess` is `false` by default, and `translate_funcs_of_parts` in [the parts](../LeanExe/Native/Proof/Parts.lean), from which `p.translation_funcs` follows, concludes `(translate cap m).map Translation.funcs = some L` for the same translation.  Every other theorem in the table except `entry_type` depends on `translate_defs`, which lists the program definitions of that translation: directly, or through `lx_init_correct`, `funcs_found`, `wholeOk_of`, `init_whole`, or `translation_fun_quiet`.  No form of `bare_of_nativeA` or `bare_of_nativeTables` takes `NativeAlignedA` or `NativeTablesAlignedA`.  For the runtime's functions, `alloc_nativeA` and `release_nativeA` in [the aligned native step](../LeanExe/Native/Proof/AlignedNative.lean) exist in addition to `alloc_native` and `release_native`.

### From the Lean theorem to the machine code

**The program `clightgen` reads.**  The per-build check compares the whole program, prefix and `main` included, with `bareProgram`, up to a renaming of identifiers, and the renaming lemma transfers the theorem to the renamed program.  The check compares CompCert's external declarations, the translation's definitions, `lx_out`, `lx_in`, `lx_reg`, and `main`, and in the `main` that reads the input it renames the temporaries for volatile loads as it renames those of calls.  The program of the Coq file is `exportProgram` of the program inside `clightgen`, since the exporter prints `Ssequence Sskip s` and `Ssequence s Sskip` as `s` and two forms of loop as `Swhile` (`export/ExportClight.ml`, lines 104 to 115), and `bigstep_program_terminates_export` (`LeanExe/Native/Proof/Export.lean`) transfers the theorem from the program of the file to the program inside `clightgen`.  The whole program numbers its identifiers so that no two parts share one.  The translation takes 1 for `lx_status`, 8, 12, 16, 20, and 24 for `lx_pages`, `lx_mem`, `lx_init`, `lx_pun`, and `__builtin_fsqrt`, `4 i + 2` for the global `i`, `4 k + 3` for the function `k`, and `32 (i + 1) + 4 c` for the result global `i` of the value type with code `c`, a multiple of 4 from 36.  CompCert's `j`-th declaration other than `__builtin_fsqrt` takes `4 j + 5`, `main` takes 4, `lx_out` takes 28, `lx_in` takes 32, and `lx_reg` takes 0, below every identifier of the translation.  The check gives each name of `clightgen`'s program its number, a global by its name and a temporary within its function, and requires the numbers to be distinct, so the renaming is injective on the program's own identifiers.

**The program `ccomp` compiles.**  `clightgen` numbers identifiers by a canonical encoding of their names (`export/ExportDriver.ml`, line 207, and `lib/Camlcoq.ml`, lines 288 to 301 and 337 to 345), and SimplExpr's temporaries then start at 128.  `ccomp` numbers names from 1 in the order of their first occurrence, and its temporaries start after the last name (`lib/Camlcoq.ml`, lines 374 to 377).  The Clight program that `clightgen` prints and the one inside `ccomp` therefore differ by a renaming of identifiers, if the two front ends otherwise agree.  The renaming lemma holds for every renaming that is injective on the program's own identifiers (`bigstep_program_terminates_rename_on`), since every such map agrees there with a map injective on all identifiers (`exists_injective_extension`).  The trusted assumption therefore reduces to this: for the same C text, the Csyntax program `p` inside `ccomp` is the one inside `clightgen` with its identifiers renamed by a map injective on the program's own identifiers.

**From Clight to Asm.**  `transf_c_program_correct` (`driver/Compiler.v`, lines 446 to 451) is a backward simulation from `Csem.semantics p`, the semantics of CompCert C.  Applying it needs a fact about every behaviour of `p` under CompCert C's semantics, which the Lean theorem does not give, while `bigstep_semantics_sound` concerns `Clight.semantics2` of `p2`, the program after SimplExpr and SimplLocals.  The two theorems therefore do not compose.  CompCert proves a forward simulation for each pass from Cshmgen to Asmgen, the first from `Clight.semantics2` (`cfrontend/Cshmgenproof.v`, line 1962), and composes them inside the proof of `cstrategy_semantic_preservation` (`driver/Compiler.v`, lines 353 to 417), without stating the composition from Clight as a theorem.  `rocq/Clight2Asm.v` states and proves it in 110 lines of Rocq against CompCert 3.18's compiled proofs:

```coq
Theorem clight2_bigstep_to_asm:
  forall p p1 p2 tp t r,
  SimplExpr.transl_program p = OK p1 ->
  SimplLocals.transf_program p1 = OK p2 ->
  transf_c_program p = OK tp ->
  ClightBigstep.Clight2.bigstep_program_terminates p2 t r ->
  program_behaves (Asm.semantics tp) (Terminates t r).
```

The proof unfolds `transf_c_program` past SimplLocals, composes the forward simulations of the remaining passes as `cstrategy_semantic_preservation` does, and ends with `Clight2.bigstep_semantics_sound` (`cfrontend/ClightBigstep.v`, line 631), `behavior_bigstep_terminates`, and `forward_simulation_same_safe_behavior` (`common/Behaviors.v`, lines 826 and 337).  Its assumptions are those of `transf_c_program_correct`, CompCert's parameters and Coq's classical axioms, and also `ClassicalEpsilon.constructive_indefinite_description`, which `forward_simulation_same_safe_behavior` uses.  `driver/Complements.v` proves the corresponding result for CompCert C's big-step semantics, `bigstep_cstrategy_preservation` (line 94), in the same way.

**Uniqueness.**  `clight2_bigstep_to_asm` shows that the Asm program can terminate with `t` and `r`, not that it cannot do something else.  Asm's semantics is determinate (`aarch64/Asm.v`, line 1282): two steps from one state match in their events and, with equal events, reach one state.  For a trace of volatile stores, `match_traces` holds only between equal events (`common/Events.v`, lines 505 to 517), so every run from the initial state coincides with the terminating run.  `clight2_bigstep_asm_unique` (`rocq/Clight2Asm.v`) concludes that every behaviour of `Asm.semantics tp` is `Terminates t r` when `t` has no system call and no volatile load, the only events whose results `match_traces` lets differ.

With volatile loads, runs differ in the values read.  `determinate_behavior_leaves` shows that a behaviour of a determinate semantics with a termination is that termination or differs from its trace first at a pair of events that `match_traces` relates and that differ, and `vload_unique` that a behaviour has at most one `k`-th volatile load.  `clight2_bigstep_asm_reads` takes a predicate `Q` and, for every sequence `σ` of 32-bit values, a Clight termination whose trace `reads σ`, with no system call and with `EVint (σ k)` at its `k`-th volatile load, and that satisfies `Q`.  It concludes that the Asm program has such a termination for every `σ` and that every behaviour of the Asm program is one of them.  The proof chooses `σ` from the behaviour with `ClassicalEpsilon.epsilon`, so its assumptions are those of `transf_c_program_correct` and `ClassicalEpsilon.constructive_indefinite_description`, the same as those of `clight2_bigstep_to_asm`.  On a 32-bit target `Tptr` is `Tint`, so CompCert lets a volatile load of an integer type read a pointer event, which no `σ` describes.  The uniqueness half therefore takes the premise `int_loads beh`: every volatile load of the behaviour whose event has type `Tint` reads an integer.  The conclusions describe only behaviours that satisfy it (`reads_int_loads`, `reacts_int_loads`), and on a 64-bit target it holds of every behaviour (`int_loads_ptr64`), so `clight2_bigstep_asm_reads_ptr64` and `clight2_loop_to_asm_ptr64` state uniqueness without it.  One file checks against the AArch64 and the ARMv7-M trees, and `rocq/check.sh` reports the target and the value of `Archi.ptr64`.

**What the Asm behaviour says.**  The initial state has the memory of `Genv.init_mem tp`, the program counter at `main`, the return address and stack pointer null, and every other register undefined (`aarch64/Asm.v`, lines 1238 to 1247).  A final state has the program counter null and `X0` holding `Vint r` (lines 1249 to 1253), the low 32 bits of the register.  Each stack frame is a fresh block of unbounded memory, so the semantics has no stack size.  Under the assumptions that the section on the trusted base lists, the processor that runs `main` performs exactly the stores of `t` to the address of `lx_out`, in order, and returns to the startup code with `r` in `w0`.  Nothing follows about time, about memory outside the trace, or about a run whose stack overflows.

## Startup code

The startup code is GNU assembly, about 125 instructions and a table of exception vectors, linked first:

| Step | Instructions | Reason |
| --- | --- | --- |
| Mask interrupts | `msr daifset, #0xf`, after recording DAIF | DAIF was `0x3c0`, all masked, at entry under QEMU.  A board's firmware may differ |
| Check the exception level | `mrs CurrentEL` | QEMU enters the image at EL1.  At another level the code reports the level and exits with status 254, which QEMU's machines with the virtualization and security extensions, entering at EL2 and EL3, confirm |
| Record `SCTLR_EL1` | `mrs SCTLR_EL1` | value at entry, which `tests/baremetal/entry.c` reports: `0x00c50838` under TCG, with `M`, `C`, and `I` clear, and `0x30c509d8` under KVM |

| Turn on the MMU and the caches | `MAIR_EL1`, `TCR_EL1`, `TTBR0_EL1`, `dsb sy`, `isb`, `tlbi vmalle1`, `dsb nsh`, `isb`, then `SCTLR_EL1` with `M`, `C`, and `I` set and `A` and `WXN` clear, and `isb` | TLBs' contents at reset are IMPLEMENTATION DEFINED and might be UNKNOWN (section D8.16.1, page D8-7852) |

| Set the stack | `mov sp, __stack_top` | `SCTLR_EL1.SA` was 1 at entry, so the stack pointer must stay 16-byte aligned |

The startup code turns the MMU and the caches on in every build, under TCG and under KVM, so the runs under TCG execute the code that runs on hardware.  With stage 1 translation off, the architecture gives every data access the memory type Device-nGnRnE (Arm Architecture Reference Manual, DDI 0487 issue M.d, section D8.2.12.1, page D8-7730).  An unaligned access to Device memory generates an Alignment fault where the location cannot support unaligned accesses, and otherwise whether it faults is IMPLEMENTATION DEFINED (section B2.8.2, page B2-312).  QEMU 8.2.2 under TCG runs such an access without a fault (QEMU issue 1204).  Under KVM on AArch64 hardware, before the MMU was on, the probe's unaligned 8-byte load took a data abort with `ESR_EL1` `0x96000021`, exception class `0x25` and fault status `0x21`, an alignment fault, at `ELR_EL1` `0x40100074` with `FAR_EL1` `0x40102053`.

The tables map RAM, `0x4000_0000` to `0x7FFF_FFFF`, in blocks of 2 MiB as Normal Inner and Outer Write-Back Read-Allocate Write-Allocate memory, the attribute `0xFF` of `MAIR_EL1`, Inner Shareable.  The blocks below `__rw_start`, which `tools/baremetal/link.ld` places at the first 2 MiB boundary after the code and read-only data, are read-only and executable at EL1, with `AP[2]` set, and the rest of RAM is writable and not executable at EL1, with `PXN` set.  A store to the code therefore takes a permission fault, which the separate map of code words in the AArch64 back end's model assumes, and an instruction fetch from data takes one too.  They map the 4 KiB page of `lx_out` as Device-nGnRnE memory, the attribute `0x00`, not executable, and leave every other address unmapped.  A level 3 table covers the 2 MiB that hold the guard page below the stack, with an invalid entry for that page, so an access to it takes a level 3 translation fault.  `TCR_EL1` gives a 32-bit input address range, `T0SZ` 32, so walks start at level 1 (Table D8-18, page D8-7711), with the 4 KiB granule, no walks through `TTBR1_EL1`, a 32-bit output range, and Non-cacheable walks.  The code writes the tables with the MMU off, as Device-nGnRnE accesses, so Non-cacheable walks read what it stored without cache maintenance, and it fills the stack and clears `.bss` after the MMU is on, as Cacheable writes.  The descriptors' fields are those of section D8.3.1.2 (pages D8-7739 to D8-7744), and the registers' those of sections D24.2.126, D24.2.174, and D24.2.193 (`MAIR_EL1` from page D24-9450, `SCTLR_EL1` from D24-9690, and `TCR_EL1` from D24-9904).

With RAM as Normal memory and `SCTLR_EL1.A` clear, an unaligned load or store of single or multiple registers is performed (section B2.8.2.1.1, page B2-312).  The rule excludes the Load-Exclusive, Store-Exclusive, Load-Acquire, Store-Release, and atomic instructions, `SETG*`, and the memory copy and set instructions, which require alignment, and the 64-byte single-copy atomic and Read-Check-Write instructions fault on any unaligned address (section B2.8.2.1.2, page B2-313).  `tools/baremetal/access-check.sh` fails the build of a program or a corpus module whose assembly contains one of them, and CompCert's assembly of the programs of tests 2 and 7 and of every corpus module contains none.  The AArch64 path therefore needs no proof that the translated code makes only aligned accesses, which settles for that target the optional alignment proof of the translator's milestone M7.  Under KVM with the MMU on, the probe's unaligned load ran without a fault.

Semihosting is unavailable under KVM: the probe's `hlt #0xf000` raised `ESR_EL1` `0x02000000`, exception class 0, at `0x401000b8`, and the exception handler's own exit raised it again, so the run looped until its time limit.  Built with `PSCI_EXIT`, the startup code ends a run with PSCI `SYSTEM_OFF`, function ID `0x8400_0008` (Arm DEN0022E, section 5.1.9, page 36), through `hvc #0`.  The device tree names the conduit (DEN0022E, section 6.7, page 86), and QEMU 8.2.2 gives `method = "hvc"` under both accelerators, which the Linux binding defines as `HVC #0` with the binding's register assignments.  KVM converts the call to an exit to QEMU of type `KVM_SYSTEM_EVENT_SHUTDOWN` (Linux `Documentation/virt/kvm/api.rst`, section 5), and QEMU exits on a guest's shutdown unless given `-no-shutdown`.  QEMU's status is then 0, so the tests under KVM take the program's status from the report.  Builds for TCG keep semihosting, since QEMU's exit status is the program's there and the runs at EL2 and EL3 exit through it with status 254.

No proof covers the startup code, the vectors and their reporting code, the linker script with its addresses and stack size, and, in test builds, a reporting routine in C that runs only after `main` returns or after an exception.  That routine is a second compilation unit outside the program of the theorem.  It shares only the UART's symbol with that program and runs only after `main` returns or after an exception has stopped it, so the deployment build replaces it with assembly.  The startup code runs `lx_report_exit`, `lx_report_exception`, and `lx_report_level` on the exception stack of 4 KiB, and the bound tool gives them 112, 128, and 96 bytes.  A fault in `lx_report_exit` transfers control to the vectors, which start the exception's report from the top of the same stack and then exit, so no step reads the frames that they overwrite.

## The Cortex-M7 target

The second target is the Cortex-M7 of QEMU's `mps2-an500`, the FPGA image that Arm's Application Note AN500 describes, compiled with CompCert 3.18 configured `armv7m-eabihf`, whose hard-float ABI uses the processor's double-precision floating-point unit.  QEMU runs the image under TCG.  Pointers have 32 bits, and the Lean copy of Clight takes the width as the field `ptr64` of `Archi`.  The instance `Archi.arm` sets it false and has the NaN choices of AArch64, as CompCert's `arm/Archi.v` does.  Every offset that the translation forms into `lx_mem` lies below 2^32 for a cap of at most 65,535 pages, so the translation's theorems and `p.f.program`, `input_program`, `ctl_program`, and `req_program` hold for every `Archi`, `Archi.arm` included.  The Asm model is `arm/Asm.v`, and `rocq/check.sh` checks `rocq/Clight2Asm.v` against the ARMv7-M tree, where the uniqueness theorems keep the premise `int_loads`.

CompCert's ARM back end turns some 64-bit operations, such as shifts by a variable amount, divisions, and conversions from floats, into calls of the run-time functions of `libcompcert.a`, which no proof covers.  `ccomp` appends the library to every link, and `tools/baremetal/armv7m/build.sh` writes the run-time functions that an image contains to `OUT.helpers`: for the filter's program, `__compcert_i64_shl`, `__compcert_i64_shr`, `__compcert_i64_udiv`, and `__compcert_i64_udivmod`.  The linker script of `mps2-an500` places `lx_mem` in 4 MiB of SRAM, and that of [the NUCLEO-F767ZI](#the-nucleo-f767zi) in 128 KiB of DTCM, where `nativeCap`'s 4,096 pages would need 256 MiB, so the programs for this target come from `verified_compile (pages := 1) (cap := 1)`, which starts the module's memory with one page and gives `lx_mem` one page of 64 KiB, as [the compiler's manual](verified-manual.md#verified_compile) describes.

`tools/baremetal/armv7m/mps2-an500/link.ld` places the program in the memories of AN500 (DAI 0500B, Table 3-1, pages 3-5 and 3-6, and Table 3-3, page 3-8) as QEMU 8.2.2 models them (`hw/arm/mps2.c`, lines 165 to 216, 291 to 293, and 520):

| Memory | Address | Contents |
| --- | --- | --- |
| ZBT SSRAM1, `CODE` | 4 MiB at 0 | the vector table, code, read-only data, and the load image of `.data` |
| ZBT SSRAM2 and SSRAM3, `SRAM` | 4 MiB at `0x2000_0000` | `.data`, `.bss` with `lx_mem`, the exception stack of 4 KiB, the guard of 4 KiB at a 4 KiB boundary, and the stack of `STACK_SIZE` bytes, 1 MiB by default |

In the Armv7-M default memory map, the Code, SRAM, and RAM regions, which hold the memories, are Normal memory, and the Peripheral region, which holds the devices, is Device memory (DDI 0403E.e, Table B3-1, page B3-592).  QEMU's ELF loader places each segment at its physical address (`include/hw/elf_ops.h`, line 499), so the startup code copies `.data` from its load image in `CODE` to `SRAM`.  `lx_reg` covers the 32-bit registers of the APB devices: Timer0's `CTRL`, `VALUE`, and `RELOAD` at the indices 0, 1, and 2 (Cortex-M System Design Kit TRM, DDI 0479D, Table 3-1), and UART0's `DATA`, `STATE`, `CTRL`, and `BAUDDIV` at the indices `0x1000`, `0x1001`, `0x1002`, and `0x1004` (Table 4-7, page 4-9).  QEMU connects UART0 to its first serial port (`hw/arm/mps2.c`, lines 287 to 308).  `tests/baremetal/m7.sh` compares the memories and the address of `lx_out` with the regions that QEMU's monitor reports, and no check compares Timer0's address.

The boards share the startup code `tools/baremetal/armv7m/start.S`, and each board's directory under `tools/baremetal/armv7m/` holds its `board.S` and `link.ld`.  `board.S` defines the vector table `__vectors`, `board_init`, which sets up the board's devices, `board_exit`, which ends the program with the status in `r0`, and `lx_putc`, which writes a byte to the board's UART for the reports of `report.c`.  `tools/baremetal/armv7m/build.sh` takes the board's directory from `BOARD`, `mps2-an500` unless set, compiles `start.S`, the board's `board.S`, and `report.c` with CompCert, and links them with the program through the board's `link.ld`, whose stack size applies unless `STACK_SIZE` sets another.  On `mps2-an500` the startup code starts in privileged Thread mode on the main stack:

| Step | Registers | Reason |

Every exception other than reset enters `fault`, which reads the exception number, `CFSR`, `HFSR`, `MMFAR`, `BFAR`, and the stacked return address, or 0 after a stacking error, when the frame is incomplete.  It moves to the top of the main stack, reports through `lx_report_fault` of `tools/baremetal/armv7m/report.c`, and ends through `board_exit` with status 255.  The startup code enables no interrupt and leaves `PRIMASK` 0, since setting it raises the execution priority to that of the faults, which would then escalate to HardFault (section B1.5.4, pages B1-528 and B1-529).  The reports write each byte through the board's `lx_putc` and compute with 32-bit integers only, so they call no run-time function.

With `CCR.UNALIGN_TRP` clear, `LDRD`, `STRD`, `LDM`, `STM`, `PUSH`, `POP`, `LDREX`, `STREX`, `LDC`, `STC`, `VLDR`, `VSTR`, `VLDM`, `VSTM`, `VPUSH`, and `VPOP` still require a word-aligned address and take a UsageFault on any other (section A3.2.1, page A3-65).  `tools/baremetal/armv7m/access-check.sh` reads the disassembly of the whole image, the startup code, the reports, and the run-time functions included, and accepts such an instruction only when its base is `sp` with an offset that is a multiple of 4, since an ARMv7-M implementation treats bits 1 and 0 of `sp` as RAZ/WI (section B1.4.1, page B1-516), or when it reads a literal at a word-aligned address.  The check rejects a `VLDR` or `VSTR` through a computed address, such as the floating-point accesses to `lx_pun`, the global through which the translation replaces a NaN with the canonical NaN, so a module with such code does not build for this target.  The images of the filter, the echo, the deadline program, the records program, and the energy controller's program for `mps2-an500`, and those of the echo and the energy controller's program for the NUCLEO-F767ZI, pass the check.

## The NUCLEO-F767ZI

The NUCLEO-F767ZI is ST's board with the STM32F767ZI, whose Cortex-M7 has a double-precision floating-point unit, and `tools/baremetal/armv7m/nucleo-f767zi/` holds its `board.S` and `link.ld`, outside every proof.  `tests/baremetal/usart3.sh` builds the echo of `usart3Tick` and the energy controller's program of `gwTickUsart3` for the board and plays the far end of USART3 through a serial port.  No instruction of these images has run on a board, and they run in Renode's model of the board, which the end of this section describes.  `link.ld` places the program in the memories that ST's device header `stm32f767xx.h` gives:

| Memory | Address | Contents |
| --- | --- | --- |
| Flash, `FLASH` | 2 MiB at `0x0800_0000`, on the AXIM interface | the vector table, code, read-only data, and the load image of `.data` |
| DTCM, `DTCM` | 128 KiB at `0x2000_0000`, on the data TCM interface | `.data`, `.bss` with `lx_mem`, the exception stack of 4 KiB, the guard of 4 KiB at a 4 KiB boundary, and the stack of `STACK_SIZE` bytes, 32 KiB by default |
| SRAM1 and SRAM2 | `0x2002_0000` to `0x2007_FFFF` | unused |
| APB1 devices | from `0x4000_0000` | `lx_reg`, with USART3 at `0x4000_4800` |

The Armv7-M default memory map makes the Code and SRAM regions that hold flash and DTCM Normal memory and the Peripheral region Device memory (DDI 0403E.e, Table B3-1, page B3-592).  The startup code copies `.data` from its load image in flash to DTCM.  The sections after `.data` have no contents, so the image's program headers name flash only for the code and the load image of `.data`, and `NAME.bin`, the image's loadable sections from `0x0800_0000`, holds flash only.  The linker script defines `lx_reg` but neither `lx_out` nor `lx_in`, so the board's programs reach USART3 only through requests.

The vector table of `board.S` holds the initial main stack pointer `__exc_stack_top`, the reset entry `_start`, and `fault` for the 14 other system entries and the 110 interrupts of the STM32F767, 126 words at `0x0800_0000`.  With the pin BOOT0 low, the processor boots from the address that the option byte `BOOT_ADD0` names.  Its value `0x0080` names `0x0020_0000`, the same flash on the ITCM interface, and `0x2000` names `0x0800_0000`, and with either value the processor reads the table's first two words at reset.  `start.S` then sets `VTOR` to the table, whose address `link.ld` asserts to be `0x0800_0000`.

The processor leaves reset running from HSI, the internal oscillator of 16 MHz, and `board_init` keeps that clock, with no PLL, and keeps the reset values of the bus prescalers and the flash latency, so the trusted board code configures no clock tree, flash latency, or voltage scaling.  It selects HSI as USART3's kernel clock in `RCC_DCKCFGR2.USART3SEL`, so that the baud rate depends on no prescaler, and enables the clocks of GPIOD and USART3.  It gives PD8 and PD9 the settings of ST's example `USART_Communication_Rx_IT` for the board, high speed, push-pull, pull-up, and alternate function 7, and then the alternate function mode, which connects them to `USART3_TX` and `USART3_RX`.  The board connects those pins to the virtual COM port of its ST-LINK.  `board_init` clears `USART_CR2.STOP`, for one stop bit, sets `USART_BRR` to 3,333, for 4,800.5 baud, 0.01% above 4,800, and writes `USART_CR1` with `UE`, `RE`, and `TE` set and every other bit clear, for 8 data bits, no parity, and 16 times oversampling.  `USART_CR3` keeps its reset value, which the example states to be no hardware flow control.  No program for the board reads a timer, so `board_init` starts none.

USART3 holds one received byte, the ST-LINK's virtual COM port has no flow control, and the program polls, so it must read each byte before the next one arrives.  The program reads a byte in two windows: the first reads the status, sees `RXNE`, and requests the read of `USART_RDR`, and the second takes the byte.  A byte that arrives just after a status read is therefore read up to two windows later, and those windows must end before the next byte arrives.  In QEMU with one instruction per translation block and the execution log (`-accel tcg,one-insn-per-tb=on -d exec,nochain`), counting the instructions between consecutive calls of the step, a window of the energy controller's program for `mps2-an500` executed 3,346 instructions while idle, at most 4,477 while it received, and 11,867 when it ran the gateway after the last byte of a record, while `uart_gateway.py` waits for the output record before it sends the next input record.  At 16 MHz a byte at 4,800 baud lasts 33,333 cycles, 3.7 times the instructions of two windows that receive, while a byte at 9,600 baud lasts 16,667 cycles, 1.9 times as many.  No run has measured the cycles that a window takes on the board.  At 4,800 baud a tick of 192 bytes, 18 words in and 6 out, takes 400 ms, and a simulated day of 1,440 ticks about 580 s.

`board_exit` waits for interrupts forever, since without a debugger a semihosting call escalates to HardFault.  A program with requests never returns, so on the board `board_exit` runs only after `fault` has reported an exception.  `lx_putc` waits until `TXE`, bit 7 of `USART_ISR`, is set and then writes the byte to `USART_TDR`, so the reports reach the virtual COM port at 4,800 baud.

## Arguments not fixed in advance

A loader that writes input into a C global before the start makes the theorem's premise false.  CompCert's semantics starts from `init_mem`, which fixes the initial contents of every global, so a machine whose memory holds loaded bytes in a global starts from a state that no theorem describes.  Input must therefore come through volatile reads.  `volatile_load` of a volatile block returns an arbitrary value of the access's type and records it in the trace as `Event_vload` (`common/Events.v`, lines 557 to 565).

Milestone B7 implements inputs.  The program declares `extern volatile const unsigned char lx_in[];`, which `clightgen` describes as an array of no elements without initialization data, and the linker script places `lx_in` at `0x7000_0000` with 16 MiB of RAM after it and asserts that the stack ends below it.  QEMU's generic loader fills the region with `-device loader,file=FILE,addr=0x70000000,force-raw=on`.  The input is a length `n` of eight bytes, the lowest first, followed by `n` bytes, and `main` reads every byte with a volatile load of `unsigned char`.  The event value of such a load has type `int`.  With the 64-bit pointers of AArch64, the Lean copy's `eventval_match` covers all of its values, while a 64-bit volatile load could return a pointer event in CompCert (`ev_match_ptr`), which the copy omits, so a theorem over 64-bit loads would not cover every behaviour of the Asm program.

`inMain` (`LeanExe/Native/Bare.lean`) reads the length, returns 64 when it exceeds `inMax`, `2 ^ 24 - 8`, so that every read lies in the region that the loader fills, and calls `alloc`, the module's function 0, for the length word and `⌈n / 8⌉` words.  When `alloc` sets `lx_status`, `main` returns it.  Otherwise `main` stores the number of words at the returned address and the `n` bytes after it, and calls the entry on the address and `n`.  It then tests `lx_status` and writes the result as `bareMain` does.  The header that `alloc` writes, kind 2 and width 1, is the one that `Heap.Owned` of an array requires, `alloc` writes nothing in the payload, and `main` writes only the payload, so the array is owned by `main` and lent to the entry.

The entry takes the packed form of the hashing library in place of a parameter of type `LeanExe.Bytes`: an `Array UInt64` of the bytes eight to a word with the byte count, so that `main` calls the verified export `sha256` and its theorem unchanged.  Every export of the hashing library takes this form, so each gets a program with input without new compiled code, while an entry over `LeanExe.Bytes` for SHA-256 would need a compiled wrapper that packs the bytes and a proof of the packing.  The export returns `Words4`, four results in the result globals, and `main` writes them with the kind `words 4`.  The alternative, a compiled wrapper that packs the digest into an array as the SHA-256 program of B4 does, would call a new wrapper instead of the export, and `words` gives every export with several results a program.

`input_program` (`LeanExe/Native/Proof/Input.lean`) states, for every sequence `σ` of the 32-bit values that the loads read, that the program terminates with a trace and a result that `InResult` describes, given the run of the entry from the store after `main`'s writes that `EntryInRuns` states.  The trace begins with `inTrace σ 0 8`, the loads of the length, whose low bytes give `inLen σ`.  A length above `inMax` gives the result 64 after those loads, a trap of `alloc` gives the code 1 after them, a trap of the entry, when it may abort, gives the code 1 after the loads of the message as well, and otherwise the result is 0 and the loads are followed by the stores of the output.  `Reads σ t` holds of every such trace, the form of `reads` that `clight2_bigstep_asm_reads` takes.  `input_owned` gives the heap after the allocation and the writes: the allocator invariant, an owned array, and byte `i` of the array equal to byte `i` of the message.  `sha256_input` (`tests/TestSupport/Bare/Input.lean`) applies the theorem to the export `sha256`: for a length of at most `inMax`, the output is the 32 bytes of `SHS.SHA256.Impl.sha256` of the message, which `sha256_correct` equates with the digest of FIPS 180-4, or the code 1 when `alloc` traps.  The physical assumption is that each volatile read of the region returns the byte the loader placed there.

## A program that runs forever

A controller runs a step function in a loop that never ends, and its theorem must describe an infinite trace.  `ctlMain` (`LeanExe/Native/Bare.lean`) writes a `main` that calls `lx_init`, sets the state `l0` to `s0`, and repeats a window in `for (;;)`: it reads the word `l3` from `lx_in[0]` to `lx_in[7]` with volatile loads of `unsigned char`, calls the step `l0 = lxf_k(l0, l3);`, and stores the eight bytes of the new state to `lx_out`.  The step is a translated function from two `UInt64` values to a `UInt64` that allocates nothing and cannot trap, so its theorem `NativeA` applies in every window from the store that the window before left.

The Lean statement is the judgment `LoopReacts A X p t0 W` (`LeanExe/Native/Proof/Reacts.lean`).  It states that `main` runs its first statements with the trace `t0` and then a loop whose iteration `n` runs with the nonempty trace `W n`, through an invariant indexed by the iteration that holds after the first statements and that every iteration preserves.  It uses only the terminating judgments of the Lean copy, so no infinite object appears in Lean, and the nonempty traces exclude a loop that runs without events.  `LoopEntry` locates the loop in `main`'s body through sequences on either side and admits every sequence with `Sskip` that `clightgen`'s export drops, so `loopReacts_export` and `loopReacts_rename_on` carry the judgment to the program that `clightgen` reads, as their counterparts do for a termination.

`ctl_program` (`LeanExe/Native/Proof/Ctl.lean`) proves `LoopReacts` of `inProgram pre T (ctlMain k s0)` for every sequence `σ` of the values that the volatile loads read, with `t0 = E0` and `W = ctlTrace ctl s0 σ`.  Window `n` reads `σ (8 n)` to `σ (8 n + 7)` and stores the bytes of `ctlState ctl s0 σ (n + 1)`, the state after the step has run `n + 1` times on the words read.  `ctl_reads` states that the first `n` windows read `σ` in order, and `filter_program` (`tests/TestSupport/Bare/Ctl.lean`) states `LoopReacts` for a low-pass filter compiled by `verified_compile`.

`clight2_loop_to_asm` (`rocq/Clight2Asm.v`) carries the judgment to Asm.  Its premises are the compilation premises of `clight2_bigstep_asm_reads`, the Rocq twin `loop_reacts` of `LoopReacts` for every `σ`, and the `reads` facts.  On a 32-bit target its uniqueness half also takes `int_loads`, as for a termination.  It concludes that the Asm program has the behavior `Reacts (t0 *** concat (W σ) _)`, the concatenation of all windows, for every `σ`, and that every behavior of the Asm program is `same_behaviors` with one of these.  The proof builds a `Forever_reactive` execution in Clight by cofixpoint from the invariant, as Vélus's `reactive_loop` does, carries it through CompCert's forward simulation, and obtains uniqueness from the determinacy of Asm and the values read.

## Device registers and requests

A device such as the CMSDK UART of `mps2-an500` must be polled: its transmitter takes a byte only when its status register shows room, and its receiver holds a byte only when the status register shows one.  In a program with requests, the step function decides every access to the device, so the polling is part of the verified step, and a busy device costs windows of the loop instead of a wait inside `main`.  The step is a function `tick : G → UInt64 → G × UInt64` from the state and the value of the last read to the new state and a request word `q`, where the state's type `G` has a representation as a list of `n` words, `words s`.  When bit 63 of `q` is set, `q` requests a write of its low 32 bits to the register `(q >> 32) & 65535`, and otherwise a read of that register.

A program with requests declares `extern volatile unsigned int lx_reg[];`, which the linker script places at the base of the device registers, and its `main`, `reqMain k s0` (`LeanExe/Native/Bare.lean`), calls `lx_init`, sets the temporaries `l7` to `l(6 + n)` of the state to the words `s0` and the last value `l3` to 0, and repeats a window in `for (;;)`.  A window calls the step on the state's words and `l3`, whose `n + 1` results, the new state's words and the request, the translation leaves in the result globals `lx_r0_l` to `lx_rn_l`, and performs the request with one volatile 32-bit load or store of `lx_reg`, after which `l3` holds the value read, or 0 after a write.  For the echo of test 11, whose step is `cmsdkTick`, whose state is one word, and whose initial state is 3, the loop of `main` is:

```c
  for (;;) {
    lxf_cmsdkTick(l7, l3);
    l7 = lx_r0_l;
    l6 = lx_r1_l;
    if (((l6 >> 63ULL) != 0ULL)) {
      (*(lx_reg + ((l6 >> 32ULL) & 65535ULL))) = ((unsigned int)l6);
      l3 = 0ULL;
    } else {
      l3 = (*(lx_reg + ((l6 >> 32ULL) & 65535ULL)));
    }
  }
```

`ReqState` (`LeanExe/Native/Proof/Req.lean`) holds the step's state, the last value read, and the number of reads so far.  `reqNext` gives the state after a window, and `reqRun tick s0 σ n` iterates it from `⟨s0, 0, 0⟩`, so that the `k`-th read of the run returns `σ k`, zero-extended to 64 bits.  The trace of window `n`, `reqTrace tick s0 σ n`, is the one event `reqEvent` of `reqRun tick s0 σ n`: `Event_vstore Mint32 regId (regOfs q) (EVint v)` for a write of the low 32 bits `v` of the request `q`, and `Event_vload Mint32 regId (regOfs q) (EVint (σ k))` for the `k`-th read, where `regOfs q` is four times the register's index.  Every window performs one access, so no window's trace is empty, as `LoopReacts` requires.  The index has 16 bits, so every access lies within 256 KiB of the start of `lx_reg`.

`req_program` proves `LoopReacts` of `reqProgram pre T (reqMain k (words s0))` with `t0 = E0` and `W = reqTrace tick s0 σ`, for every `σ` and every `Archi`, from `ReqRuns`, the run of the step from every store that the loop's invariant allows.  `reqRuns_of_nativeA` derives `ReqRuns` from `NativeA` of a step that cannot trap, for a state of at least one word whose `Scalar` values are its words.  With at least two results, the translation leaves every result in a result global, the first in global 0.  `req_reads` states that the first `n` windows read `σ` in order, the `reads` premise of `clight2_loop_to_asm`.  `loopReacts_export`, `loopReacts_rename_on`, and `clight2_loop_to_asm` carry the judgment to the Asm program as they do for the controller, and on ARMv7-M the uniqueness half takes `int_loads`, since every load of `lx_reg` has the chunk `Mint32`, whose type is `Tint`.

The register map is a parameter of the step.  `echoTick rx tx status rxFull txMask txRoom` (`tests/TestSupport/Bare/Req.lean`) takes the indices of the receive, transmit, and status registers, the status bit `rxFull`, which is set while the receiver holds a byte, and the status bits `txMask`, which equal `txRoom` while the transmitter can take a byte.  It reads the status until the receiver holds a byte, reads the byte, reads the status until the transmitter has room, and writes the byte with bit 5 flipped, with the phase in the low byte of its state and the byte to write in the second.  `cmsdkTick` instantiates the map for UART0 of `mps2-an500`, whose `DATA` at index `0x1000` serves both directions, with `STATE` at `0x1001`, `RXFULL` in bit 1, and `TXFULL` in bit 0, so that `txMask` is 1 and `txRoom` 0.  `usart3Tick` instantiates it for USART3 of the NUCLEO-F767ZI's STM32F767ZI, `0x4800` bytes above `lx_reg`, with `USART_RDR` at index `0x1209`, `USART_TDR` at `0x120A`, `USART_ISR` at `0x1207`, `RXNE` in bit 5, and `TXE` in bit 7, which is set while the transmit data register is empty, so that `txMask` and `txRoom` are both `0x80`.  The module `reqCompiled` holds the steps of the echoes and of the deadline program and comes from `verified_compile (pages := 1) (cap := 1)`, and `echo_program` and `echo_usart3_program` state `LoopReacts` of the programs `reqMain 5 [3]` around `cmsdkTick` and `reqMain 9 [3]` around `usart3Tick` for every `σ`.

`echo_write_after_room` states that in every run of the echo of `cmsdkTick` from the state 3, for every `σ`, a window that requests a write directly follows a window that read the status register, and the value read has bit 0, `TXFULL`, clear.  `echo_first_read` states that the first window reads, so every write of the run follows such a status read.  No theorem states the corresponding property of the reads of `DATA`, that each follows a status read with `RXFULL` set, or either property of `usart3Tick`.  That the UART takes the byte written is an assumption about the device: only a write of `DATA` sets `TXFULL`, so the flag stays clear from the status read to the program's next write.  QEMU 8.2.2's model holds one received byte and takes the next from its character device only while `RXFULL` is clear (`hw/char/cmsdk-apb-uart.c`, lines 115 to 152), so its receiver never overruns, while a UART on hardware overruns when the program reads too slowly.  On the NUCLEO-F767ZI, USART3 holds one received byte and the ST-LINK's virtual COM port has no flow control, so the program must read each byte within about a byte's time, which determines [the board's baud rate](#the-nucleo-f767zi).

## Clock reads and deadlines

Time enters the theorems as values that the program reads.  The clock is a device register, each read of it is a volatile load whose value the theorem quantifies over, and a deadline is a property of the step's requests that a theorem about the step states.  `lx_reg` begins at `0x4000_0000`, the base of the APB devices of `mps2-an500`, so one register bank holds Timer0 and UART0.  `board_init` of `mps2-an500` starts Timer0 from `0xFFFFFFFF`, and `VALUE` counts down at the timer's clock, 25 MHz in QEMU 8.2.2 (`SYSCLK_FRQ` in `hw/arm/mps2.c`).

`elapsed t0 t1` (`tests/TestSupport/Bare/Req.lean`), `(t0 - t1) & 0xFFFFFFFF`, is the number of ticks that a down-counting 32-bit timer counts from the reading `t0` to the reading `t1`, modulo 2^32.  `deadlineTick rx tx status timer rxFull txMask txRoom limit` extends the echo's register map with the index `timer` of the timer's value and a limit.  After it reads a byte, it reads the timer and keeps the reading in its state, and after a status read that shows room it reads the timer again and writes the reply only when `elapsed` of the two readings is below the limit, dropping the byte otherwise.  Its state holds the phase in the low byte, the reply in the second byte, and the first reading from bit 16.  `deadlineCmsdkTick` takes the map of UART0, Timer0's `VALUE`, index 1, and a limit of `0x1000000` ticks, 671 ms at 25 MHz.

`deadlineCmsdkTick_write` states that the step requests a write only in phase 4, and only when `elapsed` of the reading in its state and the value just read is below `0x1000000`.  `deadlineCmsdkTick_phase4` states that the step enters phase 4 only with a request to read the timer.  `deadline_write_on_time` combines them for every run from the state 5 and every `σ`: a window that requests a write directly follows a window that read Timer0's `VALUE`, and fewer than `0x1000000` ticks separate the reading stored in the state from the value read.  `deadline_program` states `LoopReacts` of the program with the window traces `reqTrace deadlineCmsdkTick 5 σ`.  The deadline program runs on QEMU only: the NUCLEO-F767ZI's virtual COM port has no flow control, so USART3's transmitter never waits longer than a byte, and no test on the board could make the deadline expire.

The theorems bound the difference of two timer values that the program read.  The claim that a reply leaves within 671 ms of the read of its byte, apart from two delays, also assumes that the timer counts at its stated rate and that fewer than 2^32 ticks, about 172 s at 25 MHz, pass between the two readings.  The delays run from the read of the byte to the first reading, one window, and from the second reading to the store of the reply, the rest of that window and one call of the step.  No proof covers these assumptions or bounds the delays: CompCert's semantics has no notion of time, and the system bounds no execution time.

## Records over the UART

A record machine `mach : M → List UInt64 → M × List UInt64` takes its state and an input record of `kin` words and returns its new state and an output record of `kout` words.  `frameTick u kin kout mach` (`LeanExe/Native/Proof/Records.lean`) is a step of the program with requests that runs such a machine over a UART, whose register map `u : Uart` gives the indices `rx`, `tx`, and `status` of the receive, transmit, and status registers, the status bit `rxFull`, which is set while the receiver holds a byte, and the status bits `txMask`, which equal `txRoom` while the transmitter can take a byte.  The CMSDK UART has one data register for both directions and a bit that is set while the transmitter is full, so `cmsdkUart` and `gwUart` set `rx` and `tx` both to `0x1000`, and an STM32 USART has two data registers and `TXE`, which is set while the transmitter is empty.  Each word travels as 8 bytes, most significant first, with no framing bytes: the step reads the bytes of a whole input record, runs the machine, writes the bytes of the whole output record, and then reads the next input record.  Its state, `Framing M`, holds a phase, the counts of the bytes of the current word and of the words of the current record, the word being received, the input record, into which each received word shifts at the end, the output record, whose first word shifts out a byte at a time, and the machine's state.  The phase names the last request: a status read before a byte is read, a read of the receive register, a status read before a byte is written, or a write of the transmit register.  The step reads a byte only after a status read that shows `rxFull` set and writes one only after a status read whose bits `txMask` equal `txRoom`.  The requests are functions of the dialect in `LeanExe/Native/Requests.lean`: `readReq r` is `r * 2^32` and `writeReq r v` is `2^63 + r * 2^32 + v % 2^32`, sums of fields whose bits do not overlap, so that `reqWrite`, `reqReg`, and the low 32 bits of a request follow by linear arithmetic on its value.

`frame_prefix` states, for every sequence `σ` of the values that the volatile loads read and every `n`, that `dataOut u`, the values that the first `n` windows write to the transmit register, begin `outBytes mach m0 (decode kin (dataIn u ...)).recs`.  `dataIn u` gives the low bytes of the values that those windows read from the receive register, and `decode kin` groups them into words of 8 bytes, most significant first, with the accumulation `acc * 256 + b` that the step performs, and the words into records of `kin` words.  `outBytes` gives the bytes of the machine's output records for those records, from the state `m0`, each word's bytes by `wordBytes`, the shifts with which the step sends them, so the theorem needs no lemma about the inverse of the encoding.  Its premises are indices of the receive, transmit, and status registers below 65,536, a receive register other than the status register, record lengths from 1 to `2^32 - 1`, and a machine that answers every record of `kin` words with `kout` words.  The invariant `FrameInv` relates the framing's state to the decoder's state of the bytes read and to the bytes written, and each phase and branch of the step has its own lemma.  The theorem bounds what the program writes and states nothing about when it writes, which depends on the values that the status reads return.

`frameTick` holds the records as lists, while `reqRuns_of_nativeA` takes a state whose `Scalar` values are its words.  A compiled step therefore holds the records in structures with `Flat` instances, the input record as a shift register of fields, and a theorem states that it computes `frameTick` under a map `abs` to lists.  `reqTrace_map` states that a map that commutes with the steps leaves the window traces unchanged, so `frame_prefix` carries over to the compiled step's program.

`sumTick` (`tests/TestSupport/Bare/Records.lean`) frames the machine `sumMach`, which answers each record of three words with their sum modulo `2^64` and the number of records before it, over UART0 of `mps2-an500`.  Its state, `SumFrame`, has ten words, so the step takes eleven words and returns eleven, and the module `sumCompiled` comes from `verified_compile (pages := 1) (cap := 1)`.  `sumTick_abs` states that `sumTick` computes `frameTick cmsdkUart 3 2 sumSpec` under the map `sumAbs`, `sum_program` states `LoopReacts` of the program from the state `sumInit` for every `σ`, and `sum_prefix` is `frame_prefix` for the program.

The energy controller's step `gwTickWith` (`Demos/Energy/Loop.lean`) frames the gateway of [the energy controller](../Demos/Energy/README.md#the-gateway-in-the-loop) with input records of 18 words and output records of 6, over the UART whose register map its first six parameters give.  Its state of 45 words holds the framing's counters, the two records, and the gateway's state of 17 words.  `gwTick` instantiates it for UART0 of `mps2-an500`, the map `gwUart`, and `gwTickUsart3` for USART3 of the NUCLEO-F767ZI, the map `gwUsart3`, so each takes 46 words and returns 46, and the module `gwCompiled` holds the gateway, the authorizer over fields, and the steps, with `gwTick` and `gwTickUsart3` as its functions 33 and 34.  `gwTickWith_abs` states that `gwTickWith` computes `frameTick` of `gwSpec` over the UART of its parameters, under the map `gwAbs` to lists, and `gwTick_abs` and `gwTickUsart3_abs` instantiate it.  `gw_program` and `gw_prefix`, for the program `reqMain 33 (gwWords gwInit)`, and `gw_usart3_program` and `gw_usart3_prefix`, for `reqMain 34 (gwWords gwInit)`, state for these steps what `sum_program` and `sum_prefix` state for the records program: the bytes that a program writes to its UART's transmit register begin the bytes of the gateway's output records, from its initial state, for the input records that it reads from the receive register.

The framing does not resynchronize.  A lost or added byte shifts every later record, and `frame_prefix` then describes the records that the shifted bytes encode.  QEMU 8.2.2's UART model never overruns its receiver, as [the section on requests](#device-registers-and-requests) states, so the tests on QEMU lose no byte.  On the NUCLEO-F767ZI, USART3 holds one received byte and the virtual COM port has no flow control, so a record arrives whole only if the program reads each of its bytes before the next arrives, and [the board's baud rate](#the-nucleo-f767zi) gives the program about 16,667 cycles for each.  A board that loses bytes needs a framing that resynchronizes.

## The stack

CompCert's Asm semantics gives each frame a fresh block, so its theorem assumes that the stack never overflows.  The verified compiler bounds the nesting of calls: a guarded recursive function, and every function that calls one, takes the call depth, traps at `unreachable` when the depth reaches 1,000, and passes the depth plus one to the functions of this kind that it calls, as [the internals' section on recursion](../Verified/README.md#recursion) states.  The test comes after the callee's prologue, so at most 1,001 such frames nest below an entry.  Apart from the entries, which call such a function with depth 0, a function that does not take the depth calls none that does, since it would have no depth to pass, so those functions form an acyclic call graph below each chain.

`tools/baremetal/stack-bound.sh` computes a static bound from the assembly that `ccomp` prints.  `aarch64/Asmexpand.ml` emits a `.cfi_adjust_cfa_offset` for each part of a frame's allocation (lines 491 to 516), so a function's frame is the sum of its adjustments, and its callees are the targets of its `bl` and `b` instructions.  The tool fails on a call through a register and on a call of a function that the assembly does not define.  The translator lists the functions that take the depth, those whose code begins with the verified compiler's test of the depth (`Translation.depthNames`, after `guardCode` of `Verified/Compile.lean`), and the tool fails when a function on a cycle of the call graph is not in the list, since its recursion would have no bound.  The bound of a function is its deepest chain of calls, in which a function of the list at the depth 1,000 calls nothing and a function outside the list, an entry, calls one in it with the depth 0.  `tools/baremetal/build.sh` with `STACK_DEPTHS` fails when the bound of `main`, which covers every chain of calls from it, exceeds the stack size in the linker script.

| `gpt` | 368 bytes | 944 bytes | not measured | not measured |

The bounds and the stacks of calls are those of the tool and of test 3.  In the check of the stack mark of `main` alone, the largest stack of a call equals the bound of its function in every module with results but `fourier`, 368 bytes of 560, and `libfloatreductions`, 464 of 64,080, so the bounds are tight.  The largest calls of `libsearch` and `xxhash64` have bounds of 32 and 128 bytes, which include the temporary `lim` that holds the memory's size, and each call uses its whole bound.  The test host's frames on the path to an exported function take 5,792 bytes, and the locals of the generated calling code for the arguments add 16 bytes in some modules, which the whole stack's high-water mark shows: 230,144 bytes is 5,808 plus the 224,336 of `deep` at depth 0.  For `sha256` and `crc` the high-water mark lies in the host's own code.  The bound tool is unverified, so it is part of the trusted base, and two tests check it.  In the corpus under QEMU, the generated calling code measures each call of a module function: `lx_stack_mark` of the startup code fills the stack below the caller with the pattern, and `lx_stack_used` returns the bytes below it whose pattern changed, so the mark is the callee's alone, and a call whose mark exceeds its function's bound fails the test.  The report after `main` runs on the exception stack, so the whole stack's mark of a program of tests 2 and 7 covers `main` and its callees alone, and it must lie within the bound of `main`.  The largest bound of module code in the translations of the corpus is the 224,336 bytes of `deep` in `recursion`, so a stack of 1 MiB holds more than four times any of them, and the corpus run translates and builds every module of the registry.  The test host needs more: its recursion over nested arguments reaches 2,431,392 bytes in `taggedtypes`, so `tests/baremetal/verified.sh` gives it 4 MiB.  The unmapped guard page below the stack makes an overflow cause a level 3 translation fault when the overflowing frame's first access below the stack is in that page.  Under KVM, a store to the word below the stack reported `ESR_EL1` `0x96000047`, exception class `0x25`, a write, and fault status `0b000111`, with that word's address in `FAR_EL1`.

On the Cortex-M7, `tools/baremetal/armv7m/stack-bound.sh` applies the same rules to CompCert's Thumb-2 assembly, whose frames are the sums of the `.cfi_adjust_cfa_offset` directives that `arm/Asmexpand.ml` emits (lines 581 to 600).  A function that the assembly calls without defining it, a run-time function such as `__compcert_i64_udiv`, comes from the disassembly of the linked image.  Its frame is the sum of the bytes that its `push`, `stmdb sp!`, `vpush`, `vstmdb sp!`, `sub sp`, and stores with a negative pre-indexed offset from `sp` allocate, a bound that ignores the instructions that free stack, and its callees are the targets of its `bl` and of its branches to other functions.  The tool fails when such a function changes `sp` in another way, branches into the middle of another function, calls through a register, or writes `pc` other than by `bx lr` or a pop.  The bound excludes the frame that the processor pushes on an exception, since the startup code enables no interrupt and a fault ends the program.  `tools/baremetal/armv7m/build.sh` with `STACK_DEPTHS` fails when the bound of `main` exceeds the image's stack, from `__stack_bottom` to `__stack_top`, or when the access check fails.  The probe of test 10 has a high-water mark of 16,032 bytes, equal to the static bound of its `main`, and in the builds that the journal records the bound of `main` is 80 bytes for the filter, 264 for the echo, 360 for the deadline program, 544 for the records program, and 6,712 for the energy controller's program on `mps2-an500`, and 264 bytes for the echo and 6,720 for the energy controller's program on the NUCLEO-F767ZI, whose default stack is 32 KiB.  MPU region 0 denies the 4 KiB below the stack, so an overflow causes a MemManage fault when the overflowing frame's first access below the stack is in that region: with a stack of 8 KiB, below its bound, the probe stops with `MSTKERR`, the failed stacking of the exception's frame on the full stack, and an address of the guard in `MMFAR`.

## Trusted base

[The trusted-base document](trusted-base.md#b-bare-metal-images) lists these items, with the check and the source of each, together with the items of the other artifacts.  It also states the step from the Lean termination to the Coq judgment that the Rocq theorems take as their hypothesis.  The trusted base of a bare-metal image consists of these items:

1. Lean's kernel, with `propext`, `Classical.choice`, and `Quot.sound`.
2. The Lean copy of the Clight subset, with the program-level judgment, volatile accesses, and the pointer width, checked by review and by differential tests against `ccomp -interp` of a tree configured for each `Archi` instance.
3. The C printer and the front end that `ccomp` and `clightgen` share, checked per build up to a renaming of identifiers, the transcription `exportStmt` of the statement printer of `clightgen`'s exporter (`export/ExportClight.ml`, lines 88 to 136), and the assumption that `ccomp`'s numbering of identifiers renames `clightgen`'s by a map injective on the program's own identifiers.
4. CompCert's Rocq proofs of the passes from Cshmgen to Asmgen, of `bigstep_semantics_sound`, and of Asm's determinacy, with CompCert's parameters and Coq's classical axioms, and Coq's kernel, which checks the composition and the uniqueness lemma.
5. CompCert's extraction to OCaml and its printer of assembly.
6. The GNU assembler and linker, and the linker scripts, with the addresses of the memories, `lx_out`, `lx_in`, and `lx_reg`.
7. The startup code with its translation tables and its move to the exception stack before each of its reports, the exception vectors, and the reporting code of test builds, and on the Cortex-M7 the MPU guard and the fault handler of the shared startup code and the board code of each board: on `mps2-an500` the vector table, the setup of Timer0 and UART0, and the semihosting exit, and on the NUCLEO-F767ZI the vector table, the selection of USART3's clock, the setup of GPIOD and USART3, and the exit that waits for interrupts.
8. The static stack bound, its tool, and the stack size, with the translator's list of the functions that take the call depth and the verified compiler's passing of the depth plus one to them, and on the Cortex-M7 the frames of the run-time functions that the tool reads from the image.
9. CompCert's model of AArch64 in `aarch64/Asm.v`, or of ARM in `arm/Asm.v`, as a description of the processor.
10. QEMU, with KVM and the AArch64 hardware under KVM: the ELF loader, the generic loader of the input, the processor, and the UART's acceptance of each store to its data register.  On `mps2-an500`, the CMSDK UART takes the byte that the program writes after a status read that shows `TXFULL` clear, and Timer0 counts down at its clock.
11. QEMU's semihosting, for the exit status under TCG, and PSCI `SYSTEM_OFF` through KVM, which ends a run under KVM.  Semihosting serves only on QEMU, and on the NUCLEO-F767ZI `board_exit` waits for interrupts.
12. The absence from the compiled code of the instructions that require aligned accesses in Normal memory, which `tools/baremetal/access-check.sh` checks, and on ARMv7-M of such instructions on an address other than `sp` or a word-aligned literal, which `tools/baremetal/armv7m/access-check.sh` checks.
13. On ARMv7-M, CompCert's run-time functions in `libcompcert.a`, and the premise `int_loads` of the uniqueness theorems: every run of the machine is a behaviour whose integer volatile loads read integers.
14. For a deadline, a timer that counts at its stated rate and bounds on the time from the read of a byte to the first timer read and from the second timer read to the store of the reply.
15. For records over the UART, a channel that delivers every byte once and in order in each direction, since the framing does not resynchronize.  On the NUCLEO-F767ZI, whose virtual COM port has no flow control, the channel delivers a byte only if the program reads it before the next arrives.
16. On the NUCLEO-F767ZI, the STM32F767ZI and the board: `BOOT_ADD0` at `0x0080` or `0x2000`, PD8 and PD9 connected to the ST-LINK's virtual COM port, and USART3, which takes the byte that the program writes after a status read that shows `TXE` set and holds one received byte.

Compared with the translator's design, the trusted base excludes libc, the operating system, and the C host, and the proofs cover `main`.  The trusted base includes the startup code, the board code, the linker scripts, and the devices' behaviour.  The stack, an assumption about the size of a thread's stack in the translator's design, becomes a bound that a tool computes and the build compares with the stack it reserves.

## Test plan

1. **The corpus under QEMU.**  A freestanding build of `tools/native-host.c`, with small replacements for the parts of libc it uses, reads its command line from a block that QEMU's generic loader places in RAM and runs each case of `tests/native/verified.sh` in its own QEMU process.  Each case must give the line that the Wasmtime host and the native host give, under the same rules for traps and allocation counters.  `tests/baremetal/verified.sh` does this with `tools/baremetal/libc`, `JOBS` QEMU processes at a time, 4 by default.  In the run that the journal records, with 16 processes at a time, all 39,088 cases of the modules with cases passed in 1,538 seconds, the module cases of `euler` and `sums` included, and no case was left unrun.  No proof covers the test host, as none covers the native host.
2. **Programs with generated `main`.**  GCD on constants, CRC-32 of `123456789`, SHA-256 of `abc`, an Euler solve, and a recursion that reaches the depth limit run under QEMU.  The UART's bytes and the exit status must equal `encode` of the Lean result and Talos's result of the same entry, or, for a run that Talos ends at `unreachable`, be no byte and the code 1, and each program's theorem must check with the three standard axioms.  `tests/baremetal/programs.sh` runs this test.
3. **Stack.**  For every corpus module, the stack of every call of a module function in every case must stay within its function's static bound, the deep recursion cases at depths 999 and 1,000 included.  `tests/baremetal/verified.sh` runs this test.
4. **The Lean copy.**  The differential tests compare volatile stores and volatile loads with `ccomp -interp` under `Archi.aarch64`, `Archi.x86_64`, and `Archi.arm`, each against a CompCert tree configured for its target, `armv7m-eabihf` for `Archi.arm`.
5. **The per-build check.**  `clightgen` reads the whole program, CompCert's declarations and `main` included, and the check compares it with `bareProgram` up to renaming.
6. **The checks themselves.**  A build without the FP enable, a store to the guard page, a store to the code, a call into `.bss`, a stack below the bound, and a UART address that differs from the device tree must each fail visibly.
7. **Inputs.**  The program with input around SHA-256 runs under QEMU on messages of 0, 3, 55, 56, 63, 64, 65, 1,000, 65,536, 1,048,576, and `2 ^ 24 - 8` bytes, whose output must be the digest that `sha256sum` computes, and on the lengths `2 ^ 24 - 7` and `2 ^ 64 - 1`, which must give no output and the status 64.  `tests/baremetal/inputs.sh` runs this test.
8. **AArch64 hardware under KVM.**  With `ACCEL=kvm`, `tests/baremetal/run.sh`, `programs.sh`, and `inputs.sh` build with `PSCI_EXIT` and run under KVM, and the probes, the programs of test 2, and the program with input must give the results that they give under TCG.  The device tree must name PSCI with the method `hvc` and give the RAM of the linker script.
9. **Controller loop.**  `tests/baremetal/ctl.sh` builds the filter's program, compares `clightgen`'s Clight with the program of the theorem, and runs it under QEMU with `lx_in` loaded from a file.  The UART output of the first 16 windows must equal the states that the step computes in Lean, after which the script stops QEMU.  The startup code's report never comes, so the run checks the static stack bound and no high-water mark.  The step's module then runs in Wasmtime, one call per window, and the eight bytes of each new state must also equal the expected output.
10. **Cortex-M7.**  `tests/baremetal/m7.sh DIR` compares QEMU's memory map, from its monitor's `info mtree`, with `tools/baremetal/armv7m/mps2-an500/link.ld`: ZBT SSRAM1 at `CODE`, SSRAM2 and SSRAM3 at `SRAM`, 16 MiB of PSRAM at `lx_in`, and UART0 at `lx_out`.  The probe `tests/baremetal/m7probe.c`, a program in the form of the translator's output with a recursion past the depth limit, square roots, the NaN test through `lx_pun`, accesses of `lx_mem` within and outside its bound, and an initialized global, must write the words of `m7probe.expected` and exit with status 42 through semihosting, with a high-water mark of 16,032 bytes equal to the static bound of its `main`.  Its object may name no undefined symbol but `lx_out` and CompCert's run-time functions.  Built with an unaligned word load before `main`, it must give the same output.  Built without the floating-point enable, with an unaligned `ldrd` before `main`, with a store to the word below the stack, and with a stack of 8 KiB, it must stop with status 255, in that order, at UsageFault with `NOCP`, at UsageFault with `UNALIGNED`, at MemManage with that word's address in `MMFAR`, and at MemManage with `MSTKERR` and an address of the guard in `MMFAR`, and `access-check.sh` must reject the image with the `ldrd`.  Built without the UART's enables, it must write nothing and exit with status 42.  Each controller program that `native-bare emit-ctl` wrote to `DIR` is then built with the stack bound and the access check and runs with `lx_in` loaded, and its UART output must equal the states that the step computes in Lean, as in test 9.
11. **Device requests.**  `tests/baremetal/req.sh` writes the programs of `reqCases` with `native-bare emit-req`, compares the program that the ARMv7-M tree's `clightgen` reads from each with the program of its theorem through `native-bare check-req`, and builds each for `mps2-an500` with the stack bound and the access check.  For the echo, `tests/baremetal/uart_echo.py`, which runs under `uv run`, starts QEMU with UART0 on a Unix-domain socket and plays the far end of the UART.  It sends 322 bytes one at a time, bursts of 2, 16, 322, and 65,536 bytes, and 65,536 bytes whose replies it leaves unread until QEMU's trace event `cmsdk_apb_uart_tx_pending` shows the transmitter waiting, and then the 322 bytes one at a time again.  Every reply of the echo must be the byte sent with bit 5 flipped, as `cmsdkTick` computes, and QEMU must exit with status 0 when the script stops it.  Each wait of the script ends on an event of the socket or of QEMU's trace, and the timeout bounds only a failure.  A write while `TXFULL` is set replaces the waiting byte in QEMU's model (`hw/char/cmsdk-apb-uart.c`, lines 250 to 256), so a program that ignored the flag would lose replies, and in the runs that the journal records, programs altered to ignore the transmitter's flag, to ignore the receiver's flag, or to leave the receiver disabled each failed.  The Unix-domain socket makes the transmitter wait after 278 unread replies on the test's host, while a TCP socket on the loopback interface grows its send buffer to 2.5 MiB, which the echo fills only after a minute.
12. **Deadlines.**  `req.sh` runs the deadline program with `uart_echo.py --hold 2`, which sends the 65,536 held bytes with `0xff` only as the last, waits 2 s more after the transmitter waits, and then reads until the reply to `0xff`.  The replies to the held bytes must be the bytes sent with bit 5 flipped, in order, with at least one missing, the reply to the byte that the step read while the transmitter waited, and every other reply of the run must arrive.  QEMU's CMSDK timer is a `ptimer` on `QEMU_CLOCK_VIRTUAL` (`hw/core/ptimer.c`), which follows the host's clock while the machine runs without `-icount` (`system/cpu-timers.c`, `cpu_get_clock_locked`), so a hold of 2 s on the host exceeds the limit of 671 ms in Timer0's ticks.  In the runs that the journal records, exactly one reply was missing, the echo without a deadline failed the check with a hold of 2 s, and the deadline program failed it with a hold of 0.2 s and passed it with a hold of 1 s.
13. **Records.**  `req.sh` runs the records program with `tests/baremetal/uart_records.py`, which plays the far end of UART0 through `serve` of `uart_echo.py`.  It sends 100 records one at a time, reading each answer before it sends the next, a burst of 1,000 records from a second thread while it reads the answers, 5,000 records whose answers it leaves unread until QEMU's trace shows the transmitter waiting, and 100 records one at a time again.  A generator with a fixed seed draws the words, a tenth of them from 0, 1, `2^64 - 2`, and `2^64 - 1`, and each answer must hold the sum of its record's words modulo `2^64` and the number of records before it, so that a lost, repeated, or reordered record or answer fails the check.  In the run that the journal records, the script exchanged 6,200 records in 3.7 s, and it failed against the echo's program at the first answer.
14. **Energy controller.**  `req.sh` runs the energy controller's program with `tests/baremetal/uart_gateway.py`, which simulates the plant, the inverter, ingestion, and the optimizer for `TICKS` minutes, 10,080 unless set, of the minute series `SERIES`, and checks the commands and the monitoring, as [the energy controller's document](../Demos/Energy/README.md#the-gateway-in-the-loop) describes.  The script writes the input and output records, `native-bare gateway-run` runs the gateway in native Lean on the input records, and its output records must equal the program's.  In the runs that the journal records, 10,080 ticks gave 715 commands and 17 fallback requests in 31.4 s, and 43,200 ticks gave 2,977 commands and 72 fallback requests in 130 s, each with output records equal to native Lean's.  `tools/full-check` runs none of `m7.sh`, `req.sh`, and `usart3.sh`.
15. **NUCLEO-F767ZI.**  `tests/baremetal/usart3.sh build` writes the programs of `usart3Cases`, the echo of `usart3Tick` and the energy controller's program of `gwTickUsart3`, with `native-bare emit-usart3`, compares the program that the ARMv7-M tree's `clightgen` reads from each with the program of its theorem through `native-bare check-usart3`, builds each for `nucleo-f767zi` with the stack bound and the access check, and writes the image's loadable sections from `0x0800_0000` to `NAME.bin`.  In the builds that the journal records, both read-backs matched, the echo took 21,288 bytes of flash and the gateway 80,480, and the gateway's image held its vector table of 126 words at `0x0800_0000`, `lx_mem` at `0x2000_0308`, and a stack that ends at `0x2001_b000`, inside DTCM.  It also builds the fault images `guard` and `ldrd`.  On a board, after the user writes each image to flash, the reports of `guard` and `ldrd` under `usart3.sh run` must show a MemManage fault at the word below the stack and a UsageFault for an unaligned access, every reply of the echo under `usart3.sh run echo DEVICE` must be the byte sent with bit 5 flipped, and the gateway's output records under `usart3.sh run gateway DEVICE` must pass the checks of test 14 and equal native Lean's.  None has run on a board.  `usart3.sh emulate` runs the echo, the gateway, and `guard` in Renode, as [the NUCLEO-F767ZI section](#the-nucleo-f767zi) describes, and all three pass, while the echo built with `NO_UART` fails.  The serial-port mode of the host scripts also passes against pseudo-terminals: `uart_echo.py --device` passes against one whose far end answers each byte with bit 5 flipped and fails at the first reply when the far end flips bits 5 and 0, and `uart_gateway.py --device` ran 1,440 ticks through one that a bridge connects to UART0 of QEMU running the energy controller's program for `mps2-an500`, with output records equal to native Lean's.

## Open decisions

| Question | Recommendation |
| --- | --- |
| Do the Rocq files of B5 belong in the repository?  They add a build that needs a CompCert 3.18 tree with its proofs compiled. | Yes, in a directory of their own, checked by a script that takes the tree's path, outside the default build. |
| Renaming lemma in Lean (B3), or per-build check that treats the renaming as trusted? | Lemma, since the numbering differs between `clightgen` and `ccomp` in any case and the lemma covers every injective renaming. |
| How does output reach a device that may not accept every write? | Through requests (B11): the step polls the status register, and `echo_write_after_room` states that the echo writes only after a status read that shows room.  The `main` of `bareMain`, `inMain`, and `ctlMain` writes without polling, and B8 runs it under KVM, where QEMU's UART takes every store. |
| Are inputs not fixed in advance (B7) in scope? | Yes, as B7 implements them: a packed array for the hashing library's exports, and `LeanExe.Bytes` when an entry needs it. |
| MMU on QEMU: off, or on, which would give QEMU's runs a board's memory types? | On in every build.  Under KVM an unaligned load faulted with the MMU off, and one startup path lets the runs under TCG test the code that runs on hardware. |
| Proof that the translated code makes only aligned accesses, the optional alignment proof of the translator's milestone M7? | None on AArch64.  With RAM as Normal memory and `SCTLR_EL1.A` clear, unaligned loads and stores of single or multiple registers are performed (B2.8.2.1.1), and `tools/baremetal/access-check.sh` excludes the instructions that require alignment.  On the Cortex-M7, `tools/baremetal/armv7m/access-check.sh` rejects `VLDR` and `VSTR` through a computed address, so a module with such floating-point accesses does not build for that target, and admitting one needs a checked argument that its addresses are aligned. |
| Form of the entry: scalar constants in `main`, heap constants inside a Lean definition without parameters, and result of type `UInt64` or `Array UInt64` | As designed, with other result types encoded in Lean. |
| Address of the UART: fixed in the linker script and checked against QEMU's device tree by the test harness, or read from the device tree at startup? | Linker script and the harness's check. |
| Programs with byte literals, whose theorem is `ImplementsStatic`, in the command `bare_program`? | Add the case when a program needs it.  No program of test 2 or of the input test needs it, and no test exercises code that no program uses. |
