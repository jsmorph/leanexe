# Verified WASI Manual

`verified_compile_wasi` compiles Lean actions to core WebAssembly modules that import functions of WASI Preview 1: the stream imports `fd_read`, `fd_write`, and `proc_exit` for the standard streams and exit, and the flat calls of the pinned witx that a program uses.  The generated proofs relate execution of the exported functions to the original Lean actions, including their ordered I/O effects, returned values, and terminal outcomes.  The Linux shim implements the stream imports and the flat calls of `shimCalls` with Linux system calls, and its specification states each run of a command under the shim as the system calls that it makes.  [The verified compiler manual](verified-manual.md) describes the pure dialect used inside actions, and [the WASI design](verified-wasi-design.md) records the memory layout, the structure of the proofs, and the design decisions.  The interface follows the pinned [Preview 1 declarations](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/preview1/witx/wasi_snapshot_preview1.witx), [type definitions](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/preview1/witx/typenames.witx), and [application ABI](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/application-abi.md).

## Writing actions

### Operations and results

`import LeanExe.Wasi` provides the compiler-independent API and the native interpreter, and `import Verified.Wasi` adds `verified_compile_wasi`.  The API is in the namespace `LeanExe.Wasi` and uses `LeanExe.Bytes` for packed bytes.  Its stream operations reach the stream imports, and its loop runs a bounded sequence of effectful steps.

| Operation | Type | Behavior |
|---|---|---|
| `readSome capacity` | `UInt64 → Action ReadResult` | Calls `fd_read` once when `capacity < 2^32`, after any required allocation succeeds. |
| `readAll limit` | `UInt64 → Action ReadResult` | Calls `fd_read` with capacity 4,096 until a read returns an errno or no bytes, or until more than `limit` bytes are held, after allocating one buffer of `limit + 4096` bytes. |
| `writeStdoutSome bytes` | `Bytes → Action WriteResult` | Calls `fd_write` once for stdout. |
| `writeStderrSome bytes` | `Bytes → Action WriteResult` | Calls `fd_write` once for stderr. |
| `exit code` | `UInt64 → Action α` | Requests terminal exit with `code mod 2^32`. |
| `loop count init test step` | `UInt64 → σ → (UInt64 → σ → Bool) → (UInt64 → σ → Action σ) → Action σ` | Runs a bounded sequence of effectful steps. |

These call counts describe the compiled guest's WASI import invocations, and a host may use several operating-system calls for one import.  [The native interpreter](#native-interpreter) executes the same API through its own host adapter.  [The result definitions](../LeanExe/Wasi/Action.lean) give `ReadResult` the fields `errno : UInt64` and `bytes : Bytes`, and `WriteResult` the fields `errno : UInt64` and `count : UInt64`.  Zero errno means success.  A successful read may return fewer bytes than requested, and a successful write may report any count from zero through the supplied length.  The operations perform no retries.  Stream hosts report EOF through empty success.  A zero-capacity read still invokes the host once, so its empty result supplies no EOF evidence.  The abstract host relation has no separate EOF state and permits a read after an empty read to return more bytes.

A read capacity of at least `2^32` returns errno 61 and empty bytes before allocation or host invocation.  A nonzero read errno returns empty bytes, and a nonzero write errno returns count zero.  The host model records committed prefixes on error or trap, so these results do not prove zero device progress.  Returned errnos lie in the Preview 1 errno range, 0 through 76.

`readAll limit` reads the whole standard input into one byte string for a program that needs all of its input before it computes.  [Its definition](../LeanExe/Wasi/ReadAll.lean) is a `loop` of `limit + 2` passes, each a `readSome 4096` whose bytes the loop appends to the bytes held, so `Exec`, `Prefix`, and the native interpreter give it the meaning of those reads.  A read that returns an errno ends the loop with that errno and the bytes read before it, a read that returns no bytes ends it with errno 0, and a read that brings the bytes above `limit` ends it with errno 0 and those bytes, so the result exceeds `limit` only when the input does, and then by less than 4,096 bytes.  Each pass that continues adds a byte, so the passes always suffice.  A limit of `2^32 - 4096` or more returns errno 61 and empty bytes before any allocation or read.  The compiled code allocates one buffer of `limit + 4096` bytes and gives each read the buffer's unused tail as its iovec, so the host writes each reply in place and no byte is copied.  Its allocation charge is `Bytes.allocationCost (limit + 4096)`, which depends on the limit alone, and every read has capacity 4,096.

`Action` describes effects and their continuations.  `let action := readSome n` binds a description, and each `let result ← action` executes it once, so sequencing the same description twice makes two reads.  Reflection constructs typed code and its correspondence proof without executing guest I/O, while native execution constructs and interprets continuations as the action runs.  Actions use ordinary Lean `do` notation, as in [the stdio example](../Verified/Examples/WasiStdio.lean):

```lean
import Verified.Wasi

namespace StdioExample
open LeanExe LeanExe.Wasi

def copySome (capacity : UInt64) : Action UInt64 := do
  let input ← readSome capacity
  if input.errno != 0 then
    pure input.errno
  else
    let output ← writeStdoutSome input.bytes
    pure output.errno

def main : Action UInt64 := copySome 4096

verified_compile_wasi callable := [copySome, main]
verified_compile_wasi command (main := main) := [copySome, main]
end StdioExample
```

The stdio example makes at most one read and one write.  It returns the write's errno even when the host reports a short successful write.  A complete stream copy requires an explicit loop and handling of short transfers.

### Packed bytes

| Expression | Meaning |
|---|---|
| `Bytes.empty` | Empty bytes. |
| `bytes.size` | Length as `UInt64`. |
| `bytes.get index` | Byte as `UInt64`, or zero outside the buffer. |
| `Bytes.build count element` | `count` bytes, with the low eight bits of `element index` at each index. |
| `bytes![0, 65, 255]` | Packed literal.  Each numeral must lie between 0 and 255. |

[The byte dialect](../LeanExe/Dialect/Bytes.lean) wraps a native `ByteArray`.  Compiled byte values occupy two `i64` words: the payload address and logical length.  The representation requires a length below `2^32`, and a compiled builder requesting at least `2^32` bytes takes a guest resource trap.  `Bytes.build` evaluates its pure callback in index order, with a `UInt64` index.

Nonempty literals have deduplicated raw data in the module's static pool, after its constant word arrays.  Each literal evaluation makes an owned copy, including evaluations inside pure helpers, builders, branches, and loops.  Empty literals and empty builders return canonical empty values without allocation.  The pure verified compiler accepts the same byte operations.

Ownership follows the pure compiler's rules.  Writes borrow their buffer, and reads return owned bytes.  Passing bytes to an owned parameter or returning owned bytes transfers ownership, while returning borrowed bytes makes a copy.  The frontend splits a tuple or a structure that holds an array or bytes into its components where the action binds it, at a `←` or `let`, at the start of each step for a loop's state, and at the entry of an effectful function for a parameter, so an owned tuple moves into its components and each later use names a component.  An operand then copies an owned value only when it names the value and the value stays live after it.  Cleanup releases an unused owned allocation after its last use.  An empty argument may have a nonzero allocated root, so cleanup tests the root, and borrowed representations protect the allocation's header and capacity even when its logical length is zero.  [The byte representation](../LeanExe/Pipeline/Bytes.lean) states these memory requirements.

### Control and helper functions

An action may return `Unit` or a value accepted by the pure dialect.  Structures use the same `Flat` representation as pure functions.  Pure expressions, `let` bindings, action bindings, conditionals, and calls to listed helpers compose inside actions.  An unlisted `@[inline]` helper unfolds at its use.  A dependent conditional is accepted when its branches do not use the proof of the condition.

`LeanExe.Wasi.loop count init test step` starts with index zero and state `init`.  At each index below `count`, it evaluates the pure `test index state`.  False returns the current state.  True executes `step index state`, takes its returned state, and increments the index.  Reaching `count` returns the state without another test, and count zero skips both callbacks.  Exit or host trap in a step terminates the whole action.  Outer values captured by callbacks remain borrowed across iterations.

Effectful helper calls are acyclic, and the frontend rejects recursive effectful definitions.  Pure helpers keep the verified compiler's recursion and tail-loop rules.  General `IO` and `BaseIO` operations, arbitrary monadic recursion, and action values stored in runtime containers are outside the reflected dialect.

### Processes without an iteration bound

`Process σ` contains an initial state and `step : σ → Action (ProcessStep σ)`.  A step returns a `running` flag, a `UInt64` status, and its next state.  False ends the process with that status, and true continues with the returned state.  Exit or host trap terminates the process.  `process.runFrom host state` and `process.runStdio` interpret these steps natively.

The [typed process entry](../Verified/Wasi/ProcessCode.lean) composes separately compiled begin and step functions into a `_start` loop.  Begin returns the initial control flag, status, and owned state.  Step borrows the current state and returns its replacement.  After begin and after each completed step, the loop compacts the state: it copies the state above the heap's top and moves the copy down to the heap's base, the heap top when `_start` began, so between steps the heap holds the literal pool and one state.  The process theorems take `entry.state.compactable = true`, which holds for states built from scalars, arrays, byte strings, and pairs of them and fails for trees, and an initial heap with an empty free list.  A normally stopped process passes its status to `proc_exit`.  Begin and step take no hidden constant tables, so a program whose effectful functions use constant arrays cannot form a process entry.  [Running sum](../Demos/RunningSum/README.md) uses this API to read through EOF, retain partial lines, and finish short writes, and [the process theorems](#process-theorems-and-applications) state what the compiled loop does.

### Flat Preview 1 calls

Every function of `wasi_snapshot_preview1` except `proc_exit`, `sock_recv`, and `sock_send` has a description in [the call table](../LeanExe/Wasi/CallTable.lean), `fd_read` and `fd_write` among them, and a program reaches it as a flat call: an import whose request and reply its description fixes.  A description gives a call's import name, the core form of each parameter (`Param`), and the call whose reply gives the sizes of the regions that it writes.  A parameter is a word, an enum, flags, a descriptor, a string or bytes that the host reads, an output buffer, a pointer to a result word, to a record, or to a region whose size another call reports, an array of iovecs, or the subscriptions and events of `poll_oneoff`.  `tools/wasi-calls.py` generates the call table, [the typed functions](../LeanExe/Wasi/SysCalls.lean), [their reflection equations](../Verified/Wasi/ReflectSysCalls.lean), and the frame test `tests/wasi/sys/frame-all.wat` from the witx of WebAssembly/WASI commit `fae981bae14809d91f9bc2d63852d461f331d161`, kept in `tests/wasi/witx/`.  Its check fails when a committed file differs from its output or when another file of `LeanExe/Wasi` defines a `Call`, and [an independent lowering](../tests/wasi/witx-lowering.py) compares the parameter forms, record layouts, subscription fields, and reporters of the call table with its own reading of the witx.  The calls whose descriptions pass an array of iovecs or subscriptions are the nested calls: `fd_read`, `fd_write`, `fd_pread`, `fd_pwrite`, and `poll_oneoff`, which [the nested calls](#nested-calls) describe.

Each description has a typed function of its own except those of `args_get`, `environ_get`, `path_open`, `fd_close`, and `fd_renumber`.  `args` and `environ` call `args_get` and `environ_get` after their reporters, only `withOpen` calls `path_open` and `fd_close`, as [the handles](#handles) describe, and no program calls `fd_renumber`.  The typed functions share one action, `Action.sys call args next`.  A typed function takes each descriptor as a `Handle`, each word, enum, and flags argument as `UInt64`, and each string as `Bytes`.  It returns the errno for a function without results, `WordResult` for one result word, and `ArgsSizes` for the two result words of `environ_sizes_get`.  A function that writes a record returns `FdstatResult`, `FilestatResult`, or `PrestatResult`: the errno and each field of the record as a `UInt64`, named after the witx field.

A function with an output buffer, that of `random_get`, `fd_prestat_dir_name`, `fd_readdir`, `path_readlink`, `fd_read`, or `fd_pread`, takes a buffer that the program owns and a window of it, a start and a count, and returns `FillResult`: the errno, the count of bytes that the call placed, and the buffer.  [The window definitions](../LeanExe/Wasi/Window.lean) clamp the window to the buffer: its first position is the start, or the buffer's size when that is smaller, and its length is the count, or the bytes from that position on when they are fewer.  The call writes into the window, and the function allocates nothing.  The count is the window's length for `random_get` and `fd_prestat_dir_name`, which fill their buffer, and the call's result word, clamped to the window's length, for the calls that return how much they wrote.  After an errno, the count is 0 and the window's bytes are 0, and the buffer's other bytes keep their values.  `fd_write` and `fd_pwrite` take bytes and a window of them, clamped in the same way, and pass the window's bytes.

`Action.run` and the compiled code reject an argument before the call, without a host request, by the first rule of `Call.reject` that applies in parameter order.  Wasmtime 44 traps on an enum or flags argument outside its type before the function runs, and the rejection keeps such arguments from reaching it.  `Call.reject` gives 0 when no rule applies, and the request then reaches the host.

| Parameter | Rejected argument | Errno |
|---|---|---|
| 32-bit word or descriptor | `2^32` or more | 61 (`overflow`) |
| Enum of `n` values | `n` or more | 28 (`inval`) |
| 32-bit flags | `2^32` or more, or a bit outside the type's flags | 61, or 28 |
| 64-bit flags | A bit outside the type's flags | 28 |
| String, or bytes to write | A length of `2^32` or more | 61 |
| Output buffer | A window of `2^32` bytes or more | 61 |
| Word field of a subscription | A value that does not fit the field's width | 61 |

The generator writes each typed function except `clockTimeGet`, `randomGet`, and `argsSizesGet`, the functions of `clock_time_get`, `random_get`, and `args_sizes_get`, which are written by hand.  `args` and `environ`, also written by hand, call a reporter and then the reported call.  Without a description, `proc_exit` is reached only through `exit` and the return of `main`.

| Function | Type | Behavior |
|---|---|---|
| `clockTimeGet id precision` | `UInt64 → UInt64 → Action ClockResult` | Calls `clock_time_get`. |
| `randomGet buffer start count` | `Bytes → UInt64 → UInt64 → Action FillResult` | Calls `random_get` into the window of `buffer`. |
| `argsSizesGet` | `Action ArgsSizes` | Calls `args_sizes_get`. |
| `args` | `Action ArgsResult` | Calls `args_sizes_get` and then `args_get` into one buffer.  An errno of the first call ends the operation with that errno, and sizes for which the buffer, the pointer array, and three bytes of alignment reach `2^32` bytes give errno 61. |
| `environ` | `Action ArgsResult` | Calls `environ_sizes_get` and then `environ_get`, by the rules of `args`. |

`verified_compile_wasi` reflects each typed function, `args`, and `environ` to one `Command.sys` command, whose result is the `Flat` representation of the result structure: `(errno, value)` for `WordResult`, `(errno, count, buffer)` for `FillResult`, the errno and the fields in order for a record, and `(errno, count, size, bytes)` for `ArgsResult`.  An argument that is not a variable is bound first.  The command of a function with an output buffer takes the buffer from its variable before the call, a move when the variable dies at the call and a copy otherwise, and its result holds the buffer.  The reflector accepts a `sys` action only through these functions and `withOpen`, so a program reaches `args_get` only through `args`.  A program with `sys` commands compiles with `compileCalls p.sysCalls`, and its generated theorems are the general forms at `p.sysCalls`, while a program without them keeps the module and the theorems of the stream-only layout.  `command_sys_spec_with` and `cost_command_sys_spec_with` prove the code of each `Command.sys` command against the call's specification `sysContract`, in the forms that [the WASI design](verified-wasi-design.md#typed-commands-and-reflection) describes.  [The flat call example](../Verified/Examples/WasiSys.lean) writes its arguments, their count and size, readings of the realtime and monotonic clocks, and 16 random bytes.  [The input example](../Verified/Examples/WasiSysInputs.lean) creates and removes a directory in the preopened directory, [the record example](../Verified/Examples/WasiSysRecords.lean) writes the fields of the records of the preopened directory and of a file that it opens there with `withOpen`, [the environment example](../Verified/Examples/WasiSysEnviron.lean) writes the count, size, and bytes that `environ` returns, [the nested example](../Verified/Examples/WasiSysNested.lean) writes a file with `fdWrite` and `fdPwrite` in a bracket, reads it back with `fdPread` and `fdRead`, and polls the clock and the file, and [the prestat example](../Verified/Examples/WasiSysPrestat.lean) reads the name of the preopened directory with `fdPrestatDirName` and then copies it through a file in a bracket.

### Nested calls

`fd_read`, `fd_pread`, `fd_write`, and `fd_pwrite` take an array of iovecs, each a buffer's address and length.  Wasmtime 44 reads into and writes from only the first non-empty element of the array, so the descriptions use arrays of one element (`Param.iovec`): the code writes the element into the command's scratch bytes `[0, 8)` and passes its address and the length 1.  For a read, the element points to the window of the program's buffer, a shown output, and for a write it points to the window of the input bytes.  `poll_oneoff` takes an array of subscriptions, 48 bytes each, and an array of events, 32 bytes each.  Its descriptions (`Param.subscriptions`, one for each shape that a typed function uses) give each record's fields: a constant, such as the union's tag or the userdata, a word argument, or a handle argument, which the handle check treats as a `.handle` position.  The code allocates a block, aligns it to 8, zeroes the subscriptions, writes the fields, places the events after the subscriptions, and passes the number of records as the count.  `Call.reject` tests a word field only against its width, since Wasmtime reads a subscription from memory and answers an invalid tag or flags word, or a clock other than the realtime and monotonic clocks, with errno 28 and a descriptor that names no file of the subscription's kind with errno 8.

| Function | Type | Behavior |
|---|---|---|
| `fdRead h buffer start count`, `fdPread h buffer start count offset` | `… → Action FillResult` | Calls `fd_read` or `fd_pread` into the window of `buffer`.  The count is the call's count, clamped to the window's length.  Wasmtime 44 returns at most 65,536 bytes from one `fd_pread`. |
| `fdWrite h bytes start count`, `fdPwrite h bytes start count offset` | `… → Action WordResult` | Calls `fd_write` or `fd_pwrite` with the window of `bytes`.  The value is the count written, which may be less than the window's length.  On a handle opened to append, Wasmtime 44 ignores the offset of `fd_pwrite` and writes at the end. |
| `pollClock clock timeout precision flags` | `… → Action PollResult` | Calls `poll_oneoff` with one clock subscription of userdata 1. |
| `pollRead h clock timeout`, `pollWrite h clock timeout` | `Handle → UInt64 → UInt64 → Action PollResult` | Calls `poll_oneoff` with a read or write subscription on `h` (userdata 1) and a clock subscription (userdata 2). |

`PollResult` holds the errno, the count of events, and the first event's userdata, error, type, `nbytes`, and flags.  Wasmtime writes the events of the ready subscriptions in subscription order, so the first event's userdata tells which subscription fired.  A read subscription on a file is reported with `nbytes` 1, and with the flag `fd_readwrite_hangup` when the file is at its end.  A clock of timeout 0 is ready at once, while a file subscription first starts a read on Wasmtime's blocking pool, so a poll with such a clock returns the clock's event and, unless that read finishes first, only it.  Wasmtime 44 limits the iovec buffers and the paths of a call, the stream imports' buffers included, by its hostcall fuel, as [the differences from Wasmtime](#differences-from-wasmtime) state.  A module that calls `fdRead` or `fdWrite` imports `fd_read` or `fd_write` a second time, after the stream imports, with the specification of its description.  Wasm admits a function imported twice, and the two specifications govern different import indices.

### Handles

A descriptor is a `Handle`, a structure with one field, the descriptor as a word.  A program reaches a descriptor as `Handle.preopened`, descriptor 3, the directory that the host preopens, or as the handle that `withOpen dir dirflags path oflags rightsBase rightsInheriting fdflags onError body` binds.  `withOpen` calls `path_open` for `path` under `dir`, and its result has type `α × UInt64`.  On a nonzero errno it runs `onError errno` and returns the result of `onError` with 0.  Otherwise it runs `body` with the new handle, and when the body returns it calls `fd_close` on the handle and returns the body's result with the errno of `fd_close`.  `verified_compile_wasi` requires a source type for `α`, so it refuses a body that returns `Unit`.  A body that exits or traps ends the process with the descriptor open, and the repository's Wasmtime host closes it when it deletes the store after the run.  The check below refuses every handle argument other than a bracket's handle and 3, so descriptors 0, 1, and 2 stay reachable only through the stream operations as long as no bracket receives one of them, which the host assumption `LeanExe.Wasi.FreshOpens` below excludes.  The descriptions give each descriptor parameter the form `.handle`, which lowers like a 32-bit word and takes the 32-bit word's rejection rule.

`verified_compile_wasi` reflects `withOpen` as a fixed shape of commands, which the docstring of `withOpen` gives: the `path_open` call, a test of its errno, on failure the error continuation followed by its result paired with 0, and on success the body followed by the `fd_close` call and the body's result paired with the close's errno.  `Command.HandleCheck` ([the handle check](../Verified/Wasi/HandleCheck.lean)) refuses a call that is not one of the generated descriptions of `Call.table`, a `path_open`, `fd_close`, or `fd_renumber` call outside this shape, an argument of a `.handle` position that is not a marked variable, and a call of an effect helper whose argument for a `Handle` parameter is not a marked variable.  The marked variables are the handles that brackets bind, the variables bound to the literal 3, and the `Handle` parameters of the helper being checked.  The literal 3 may stand as the body of `letPair` bindings: the reflector reads each operand that is not a variable under a `letPair` of each variable in scope whose type is `.pair`, a pair with a component on the heap such as the `BytesResult` of `fdPrestatDirName` or the `RandomResult` of `randomGet`, and of each component of such a variable that is itself a `.pair`.  `Expr.isPreopened_denote` states that such an expression has the value 3.  Since every call must be a generated description, the check reads each call's `.handle` positions from the witx, whatever source produced the command.  For each program, `verified_compile_wasi` decides the check in the kernel (`p.handlesChecked`) and states `p.handles`, or `p.f.handles` for each export of a program without `main`.  A callable export takes and returns no `Handle`.

`p.handles` states `Action.BracketRuns` of `main` ([the bracket discipline](../LeanExe/Wasi/Bracket.lean)): every `Exec` run and every `Prefix` run of `main` satisfies `WellBracketed [] trace stack`, with `stack = []` when the run returns normally.  `WellBracketed` reads the trace with a stack of descriptor numbers, the open brackets with the innermost first.  Every event's call is a description of `Call.table`.  A `path_open` event that returns errno 0 pushes the number it returns, an `fd_close` event pops the top, which must be its argument, no `fd_renumber` event occurs, and every other call takes 3 or a number on the stack at each `.handle` position.  Every use of a handle therefore lies between its open and its close.  [The handle theorems](../Verified/Wasi/Handles.lean) `Command.handles_exec` and `Command.handles_prefix` give the discipline for every command that passes the check.

A trace has no event at a bracket's return, so `withOpen_closes` states the events and the result of each run of `withOpen` that returns normally.  When `Call.reject` rejects the arguments of `path_open`, the open makes no event, the trace is that of a run of `onError` on the rejection's errno, well bracketed from the stack back to the same stack, and the returned errno is 0.  Otherwise the trace starts with the open event.  When the open returns errno 0 and descriptor `d`, the rest of the trace is that of a run of the body on `d`, well bracketed from `d` on top of the stack back to the same stack, followed by the bracket's close, an `fd_close` event of `d`, and the returned errno is that event's.  `WellBracketed` reads numbers, so the theorem leaves open another close of `d` among the body's events: the close of a nested bracket whose open received `d` again, which `LeanExe.Wasi.FreshOpens` below excludes, or a close of `d` in the body followed by an open that the host numbers `d`, which the check refuses.  When the open returns another errno, the rest is the trace of a run of `onError` on that errno, well bracketed from the stack back to the same stack, the bracket adds no close, and the returned errno is 0.  In each case the first component of the result is the result of that run of the body or of `onError`.  Its premises are what `Command.handles_exec` gives for the body and the error continuation of a checked bracket.

`Action.BracketRuns.exec_descriptors` reads the stack as the open descriptors of the trace.  Descriptors 0 to 3 are open before the first event, a `path_open` event that returns errno 0 opens its number, and an `fd_close` event closes its argument, whatever it returns.  For a host that never returns from `path_open` a number that is open (`LeanExe.Wasi.FreshOpens`, a property of WASI traces, distinct from `LeanExe.Linux.FreshOpens` of the Linux call layer's events), as Wasmtime 44 asserts of every new descriptor, every `.handle` argument names an open descriptor other than 0, 1, and 2, every `fd_close` closes a descriptor that a bracket opened, and a normal return leaves open exactly descriptors 0 to 3.  Descriptor 3 is the preopened directory when the host preopens one, and otherwise it is open only by this definition.  `WellBracketed` reads descriptor numbers, so a use of a closed bracket's handle inside a later bracket that receives the same number would be well bracketed.  The check excludes such a use, since a handle's variable is in scope only inside its bracket, and `Command.handles_exec` holds for every host, among them hosts that never reuse a number, under which such a use breaks the discipline.

## Compilation and generated declarations

### Callable and command modules

The compiler collects pure definitions first, preserving their relative order, then reflects effectful definitions in their relative order.  A pure helper's listed pure callees must precede it among the pure definitions, and an effectful helper's listed effectful callees must precede it among the effectful definitions.  Pure helpers are available to every effectful definition.  The selected command `main` must appear among the effectful definitions and have type `Action UInt64` with no visible parameters.  Captured constant arrays become hidden borrowed table arguments.  The frontend rejects duplicate definitions, generated-name collisions within each of the pure and effectful groups, and callable names reserved by the runtime exports.  [The checked public examples](../Verified/Wasi/ReflectCommandCases.lean) include hidden tables, literals, byte ownership, records, computed call arguments, and both export forms.  The callable form lists the definitions, and the command form also selects `main`:

```lean
verified_compile_wasi p := [pureHelper, actionHelper, action]
verified_compile_wasi p (main := main) := [pureHelper, actionHelper, main]
```

Callable modules export each listed effectful definition under the last component of its Lean name.  They also export `alloc` and `release`, the allocation counters `allocCount` and `freeCount`, the linear memory `memory`, and the empty table `__indirect_function_table`, and pure helpers compile internally.  Command modules export `_start : () → ()`, `memory`, and the empty table.  `_start` invokes the selected main, then passes a normally returned status to `proc_exit`.  An explicit exit in main or a helper terminates before that final exit.

The module imports `fd_read`, `fd_write`, and `proc_exit` from `wasi_snapshot_preview1`, with the signatures and descriptors of the table below, followed by the flat calls of `p.sysCalls` when its program uses them.  The index of every defined function therefore grows by the number of calls, and each layout definition and theorem has a form over the list of imported calls, whose form at the empty list is the definition or theorem of the stream-only layout.  [The WASI design](verified-wasi-design.md#imports-and-scratch) gives the signatures of the flat calls' imports.

| Import | WebAssembly signature | Descriptor |
|---|---|---|
| `fd_read` | `(i32, i32, i32, i32) → i32` | 0: stdin. |
| `fd_write` | `(i32, i32, i32, i32) → i32` | 1: stdout, or 2: stderr. |
| `proc_exit` | `(i32) → ()` | None. |

[The ABI definitions](../Verified/Wasi/ABI.lean) reserve the command's scratch bytes `[0,16)` for one iovec and transfer count.  The read wrapper checks capacity before narrowing it to 32 bits, and heap and byte-representation premises prove that pointer and write-length narrowing preserves their values.  The module relocates pure calls by the number of imports and pure types by three positions, uses the shared allocator and release functions at the first two defined indices, which are 3 and 4 without flat calls, and passes a hidden depth through internal calls.  Public wrappers initialize depth to zero.  Effectful calls increment it, guarded pure calls use the same depth, and guarded calls enforce the depth limit of 1,000.

Pure functions that take the call depth keep the 32-position frame limit.  Acyclic effectful helpers may use larger frames when `p.stackFits` accepts the estimated whole-call-chain stack use.  [The stack check](../Verified/Wasi/Stack.lean) adds the 272,000 bytes of 1,000 guarded frames of 32 positions, pure-module frames, the WASI wrapper frames, effectful helpers' excess over 32 positions, and exported entry frames, and it requires the sum to fit within 512 KiB.  It estimates eight bytes per position and sixteen bytes per frame.  The check does not formalize a real engine's native stack layout, so engine stack behavior remains part of host validation and execution tests.

A callable host configures stdio before invoking an export and may invoke another export after normal return.  Exit and trap terminate the instance's lifecycle.  Command hosts invoke `_start` once.  The modules provide no `_initialize` hook, which the pinned application ABI permits to be absent.

## Execution proofs and their premises

### Results and traces

The exported-entry theorems quantify an initial store, host implementation, and native arguments.  They hold for every host that satisfies [the host assumptions](#resources-host-assumptions-and-total-execution).  They provide a fuel bound such that every modeled execution with at least that much fuel has one of the classifications of the table.

| Outcome | Proved relation |
|---|---|
| Normal return | Source execution returns the corresponding native value.  The machine words represent that value with owned result memory.  The allocator invariant and the caller's retained heap regions outside the command's scratch bytes are preserved. |
| Accepted exit or host trap | Source execution has the same terminal outcome, committed final world, and ordered I/O trace.  Accepted exit also has the designated exit marker and exact narrowed status. |
| Guest resource trap, when permitted | Source prefix has the same committed world and trace, with a residual action describing the remaining work. |

[The native result statement](../Verified/Wasi/NativeResult.lean) relates wrapper execution to native Lean actions, and [the command entry theorem](../Verified/Wasi/NativeCommand.lean) includes main's final exit.  Host relations may permit several replies, and each sufficiently fueled target execution has a matching source execution or permitted source prefix with the same committed effects.  The target host state contains the abstract world and an append-only joint event journal.  Events record reads, requested writes and their committed counts, flat calls and their replies, accepted exits, and rejected exit requests.  The final journal equals the initial journal followed by the source trace, which preserves ordering even when stdout and stderr refer to the same host destination.  The world is proof and host state, separate from the source program's arguments.

### Resources, host assumptions, and total execution

| Premise | Requirement |
|---|---|
| Host implementation | Talos host satisfies `hostSpec host` for the stream imports, including reply bounds, trace updates, terminal exit behavior, and guest-memory preservation.  A module with flat calls requires `hostSpecWith host p.sysCalls`, which adds `sysContract host call` for each call.  [The totality module](../Verified/Wasi/HostTotal.lean) and [the totality module for calls](../Verified/Wasi/HostTotalWith.lean) state when a satisfying host exists. |
| Heap and arguments | `Heap.At`, correctly represented argument words, and separation of consumed blocks from retained and borrowed memory. |
| Static input | Literal pool's bytes and region exist and are disjoint from consumed blocks.  Hidden table arguments represent their declared constants. |
| Scratch separation | Every live region read through an argument is disjoint from `[0,16)`, including the full allocation of an allocated-empty byte buffer. |
| Memory cap | At most 65,535 pages. |
| No guest resource failure | With `aborts = false`, `Heap.Within` holds for a budget and `Resource.CallPrefixBound` bounds every typed source resource prefix by that budget with its size and depth checks satisfied. |
| No reached host trap | Generated action `.total` theorems require `host.NoTrapsAlong` the native action in its initial world.  [The process theorems](#process-theorems-and-applications) use application-specific host-progress and final-exit premises. |

The host's memory rules preserve globals, memory limits and page count, and bytes outside the command's scratch bytes and a read's destination.  Read and write preserve the exit marker.  In [the host assumptions](../Verified/Wasi/HostSpec.lean), an accepted exit sets the exit marker, records its status, and uses the designated exit trap, and a host trap or a rejected exit leaves the marker unchanged and records its failure.  The guest wrapper follows `proc_exit` with `unreachable`, while the host specification requires the import to terminate.  A host trap may have any message, including the exit trap's message, so the journal and the exit marker distinguish the outcomes and the trap message alone does not.

`hostSpec host` constrains every invocation of each import from every store, so a satisfying Talos host must answer every request that reaches it.  [The totality module](../Verified/Wasi/HostTotal.lean) gives a sufficient condition and a necessary one, and they differ.  `Host.Total host` requires a permitted reply to every read and write and an accepted or rejected outcome for every exit, and `Host.Total.satisfiable` builds a host environment that satisfies `hostSpec host` for any module with the stream imports, from an oracle that chooses those replies.  `Host.Answers.of_satisfies` proves the converse for every request that the one-iovec ABI expresses with its payload at address 16: reads of capacity at most `2^32 - 16`, writes of at most `2^32 - 16` bytes, and every 32-bit exit status.  A theorem that assumes a satisfying host is therefore vacuous for a host relation that leaves such a request without a reply.  The sufficient condition also requires replies to requests that no execution makes, such as reads of capacity `2^32` or more, and the necessary one omits writes that the ABI can express at other addresses.  [The scripted host](../Verified/Wasi/ScriptHostContracts.lean) is the oracle of a queue world.

`hostSpecWith host calls` adds, for each call, `sysContract host call`, whose premise `SysRequest` admits a request that fits the call's parameters (`argsFit`: one argument of the parameter's kind for each parameter that takes one, within its core type), that the call does not reject, whose inputs lie in memory, and whose output regions lie in memory at multiples of their alignments, end below `2^32`, and lie apart from one another and from the inputs.  Inputs may overlap, since `path_rename` and `path_link` may name one path twice.  In a memory of 65,536 pages, Wasmtime 44 writes the output buffers of `fd_prestat_dir_name`, `fd_readdir`, `path_readlink`, and `random_get` and the strings of `args_get` and `environ_get` with `write_bytes` and `write_byte` of `crates/wasi/src/p1.rs`, and the pointers of the last two with `memory.write` and `add(1)`.  Each traps after it writes the last byte of a region that ends at `2^32`, since the pointer past that byte overflows.  A call that writes fewer bytes than its buffer holds, such as `path_readlink` of a shorter link, does not trap there, and neither does a read into an iovec buffer or the write of a result word or a record.  The bound below `2^32` excludes every such trap.  `Host.TotalFor host calls` adds to `Host.Total` a permitted reply to every such request of each call, and `Host.TotalFor.satisfiableWith` builds a host environment that satisfies `hostSpecWith host calls` for any module that imports the calls after the stream imports.  Its import for a call ([the flat call host](../Verified/Wasi/OracleSys.lean)) decodes the request from the core arguments and the inputs in memory, takes an oracle's reply, and writes each shown output into its region.  `Host.Answers.of_satisfiesWith` proves the converse, `Host.AnswersFor`, for each such request whose inputs and output regions end below `2^32` when laid out one after another from address 16, with result words, records, and reported regions at multiples of their alignments (`layoutEnd`), for a call whose reported regions have positive alignments.

The budget is a proof-level natural number.  It accounts for allocation and copying in pure fragments, read-buffer capacity, the blocks of flat calls, helper calls, and loop iterations along host-permitted paths.  The rule of a `sys` command bounds its charge on the runs and prefixes that the host permits.  A call with an output buffer charges the copy of its buffer when the buffer's variable stays live after the call and nothing otherwise, a call that writes a record the block of its record's size plus its alignment less one, a poll its block, and a call with reported regions the block that its reporter's reply asks for, so `reported_rule_observed` in [the rule premises](../Verified/Wasi/SysRule.lean) derives the rule's premises from a bound on the sizes that the host's reporter replies give.  Executable lengths, loop counts, byte values, and statuses are `UInt64`.  `p.f.callee`, `p.program`, and the source resource relations provide concrete terms for a resource proof.  `Bounded` and `Rule` of [the resource rules](../Verified/Wasi/ResourceRules.lean) bound a command's runs and prefixes from every world, and `BoundedAt` and `RuleAt` of [the rules from one world](../Verified/Wasi/ResourceRulesAt.lean) bound them from one world, with the second command of a `bind` bounded from the world in which the first returned, for a charge that depends on the host's replies, such as the passes of a loop of writes.  The frontend exposes this typed prefix condition and does not synthesize a bound from the original input for every I/O program.

[The retained-buffer example](../Verified/Examples/WasiRetain.lean) performs up to two one-byte reads, writes the previous buffer at each iteration, and returns the last buffer.  [Its budget proof](../Verified/Examples/WasiRetainBudget.lean) bounds every host-reply path and resource prefix by 112 bytes: each read charges a 48-byte header and eight-byte minimum capacity.  [The total-execution application](../Verified/Examples/WasiRetainTotal.lean) proves that this budget fits the modeled initial store, supplies the generated representation and separation premises, and applies `compiled.retain.total` under a satisfying host and `NoTrapsAlong`.  [The mixed-depth example](../Verified/Examples/WasiDepth.lean) combines effectful helpers, a hidden constant table, and guarded pure recursion, and its resource-prefix condition must cover the combined effectful and pure call depth below 1,000.

`NoTrapsAlong` quantifies only operations reachable through source prefixes, and returned nonzero errnos are ordinary results.  The premise excludes read and write traps and rejected exit requests along those paths.  Callable `.total` therefore allows a native return or accepted exit, while command `.total` proves accepted exit.  A host that rejects some statuses can satisfy the premise for a program whose reached exits use accepted statuses.  [The reached-host condition](../LeanExe/Wasi/NoTrapPrefix.lean), [typed prefix bound](../Verified/Wasi/ResourcePrefix.lean), and [command total theorem](../Verified/Wasi/CommandTotal.lean) give the exact statements.

With `aborts = true`, `.implements` and `.start` permit guest allocation or depth failure after earlier I/O, and their prefix classification keeps those effects.  Normal-return ownership and heap-preservation postconditions apply to a returned store.  Terminal exit and trap require the host to discard the instance.

### Initial store and external execution

[The trusted-base document](trusted-base.md#wasi-wasi-preview-1-modules) lists the trusted parts of the WASI theorems, with the check and the source of each.  `p.initial` proves properties of the store constructed from `p.module.initialStore`, with a supplied host world.  It initializes the allocator, constant arrays, and raw static bytes and proves the declared memory cap.  The exported-entry theorems apply to that store after their argument, host, separation, and resource premises have been established, and after a prior normal call when its postconditions establish the next call's premises.

The proofs use Lean's kernel, the project's definitions of source actions and memory representations, Talos's execution semantics, and the binary decoder.  Every WASI theorem also assumes that these definitions model Preview 1: `Host`, `Exec`, `exitStatus`, and `Transfer.validErrno` in [the semantics](../LeanExe/Wasi/Semantics.lean) and [actions](../LeanExe/Wasi/Action.lean), `observedHost` in [the observed host](../Verified/Wasi/Observed.lean), `ReadRequest`, `WriteRequest`, `GuestFrame`, and the stream import specifications of `hostSpec`, and `TerminalMessage` in [the command specification](../Verified/Wasi/CommandSpec.lean).  The theorems of a module with flat calls also assume `argsFit`, `SysRequest`, `sysContract`, and `hostSpecWith` in [the host assumptions](../Verified/Wasi/HostSpec.lean), `Call.reject` in [the parameter forms](../LeanExe/Wasi/Calls.lean), and the descriptions of [the call table](../LeanExe/Wasi/CallTable.lean).  Their axiom audit permits `propext`, `Classical.choice`, and `Quot.sound`.  Host installation in a real engine, operating-system I/O, the native stream adapter, emitted file contents, and Wasmtime's agreement with the modeled semantics require external validation.  Talos permits memory growth up to the declared cap, while `memory.grow` may fail earlier in an engine.  Fuel bounds describe modeled guest execution, and external reads may block.  [The shared proof scope](design.md#scope-of-the-theorem) describes the engine and file-emission limits.

### Process theorems and applications

[Process refinement](../Verified/Wasi/ProcessCorrect.lean) classifies every target run of a process entry that completes without exhausting Talos fuel.  The result preserves completed native steps, terminal outcomes, and pending action prefixes after guest resource failure.  [The total-process theorem](../Verified/Wasi/ProcessTotalCorrect.lean) proves eventual accepted exit when an application supplies a well-founded progress relation, bounded helper proofs, and final-exit acceptance, together with cost conditions on single steps.  A begin charge and a step charge bound the typed resource prefixes of begin and of the step from each represented running state.  The heap must have free memory above its base for each charge together with the copies of the state before and after it, and because the loop compacts the state, these conditions concern one step at a time.  The theorem requires begin and every step to return normally, so a process that may exit or take a host trap inside a step stops only through its running flag under this theorem.

[Running sum's integer theorem](../Demos/RunningSum/Correct.lean) proves canonical decimal output for the cumulative sum at each line before the first line that is not a decimal integer, and eventual accepted exit with status 0 when every line is one and 28 otherwise.  Its [stream-host assumptions](../Demos/StreamFold/StreamHost.lean) require successful I/O, input-prefix consumption, EOF, committed output prefixes, and a decreasing proof-only counter for zero-byte writes.  Independent [input bounds](../Demos/RunningSum/Model.lean) constrain each line's length and the digit count of each prefix sum of valid lines.  Limits on the bytes of each line and the digits of each total, `InputLimits L D`, and one inequality between the memory cap and `220 · (L + D) + 1,010,000` bytes above the literal pool replace the cost conditions, which the application proves from the generated bounds of its pure functions.  A corollary fixes both limits at 9,000,000, and `ExitAccepted` supplies the final-exit premise.  The [application guide](../Demos/RunningSum/README.md) states the exact scope.

[The floating-point running sum](../Demos/RunningSumFp/README.md) uses the same stream protocol with a binary64 total starting at positive zero.  Its [arithmetic proof](../Demos/RunningSumFp/ArithmeticProof.lean) uses the library's general float parser, IEEE-754 addition, and shortest scientific printer.  [Its compiled theorem](../Demos/RunningSumFp/Correct.lean) requires fewer than `2^32` bytes per line.  It proves the printed sequential totals of the lines before the first line that denotes no number, and accepted exit with status 0 or 28, under host progress and final-exit acceptance.  A limit on the bytes of each line up to and including the first line that denotes no number, `InputLimits L`, and one inequality between the memory cap and `80 · L + 64,031,000` bytes above the heap's base replace the cost conditions, which the application proves from the generated bounds of the parser, the printer, and its effect bodies.  A corollary fixes the limit at 50,000,000.  Both applications use [the shared stream proofs](../Demos/StreamFold/README.md).

Each running sum's `RunCharges` states its charges and free-memory conditions on native states and stream positions, independently of compiled stores and locals.  The integer program's `RunCharges` takes an invariant, and its termination theorem uses `LimitInv L D`: the state has a future under `limitSpec L D`, a run of the remaining input that meets the limits `L` and `D`, and its buffers are within their bounds.  The integer charges follow from the generated bounds of the pure functions: a step that consumes input pushes at most 4,096 bytes onto the pending line and completes at most one line.  `InputBounds` gives the kernel's size condition at each line, and `InputLimits` bounds the same sizes by `L` and `D` for the memory premise.  The binary64 program's `RunCharges` takes the invariant `LimitInv L` in the same way, and its charges follow from the generated bounds of the parser, the printer, and the effect bodies.  The printer's search for the shortest decimal stops within 27 steps of its start for every finite nonzero binary64 word (`PrintFloatSteps.search_le`), so it tests at most 28 exponents.  The search therefore takes at most 62 quotients, two for each tested exponent and six for the choice of the digits, of at most 953,376 bytes each, and the rendering of a total costs at most 59,112,378 bytes, 3,066 more than those quotients.  A parse costs at most `8 · L + 4,404,576` bytes for a line of `L` bytes.  The mathematical `Nat` and `Int` values and progress ranks are proof-only.

[The order book's process](../Demos/OrderBook/Process.lean) runs [the order book](../Demos/OrderBook/README.md) over stdin and stdout with StreamFold's host assumptions and its own framing.  It reads little-endian 64-bit words, passes the whole seven-word records of the carry and each 4,096-byte read to one call of the program's `run`, and writes the event words in the same form.  [Its compiled theorem](../Demos/OrderBook/ProcessCompiledCorrect.lean) proves that `_start` writes exactly the little-endian bytes of the specification's event words on the whole words of the input and exits with status 0 when the input is a whole number of words and 28 otherwise, under host progress, final-exit acceptance, and the requirements' bound of fewer than 2^64 − 1 records.  Its states have constant size bounds, so the memory condition is one closed inequality that the proof decides, 3,456,119,748 bytes above the literal pool for two copies of a state and a step's charge, and the theorem has no memory premise.  The charge of a read step holds for every reply, so it bounds `run` on any batch of 74 records from any book of the program's array sizes, by [the closed form of its bound](../Demos/OrderBook/Bound.lean) and a count of events over the program itself.  The state's 13 fields make the elaborator's conversion of a call's arguments in the effect bodies exponential in their depth, so [its charges](../Demos/OrderBook/ProcessCharges.lean) evaluate the destructured environment with a simproc and read the pure program's flags from a lemma that the kernel decides.

## Native and WebAssembly execution

### Native interpreter

`action.run host : IO (Outcome α)` executes an action through a `NativeHost`, and `action.runStdio` uses Lean's current stdin, stdout, and stderr.  Its result is `.returned value`, `.exited code`, or `.trapped message`.  Exit returns a terminal outcome to the Lean caller without terminating the Lean process.

`NativeHost.ofStreams` reports errno zero for successful stream reads and full successful count after a write and flush.  It accepts every narrowed exit status.  Stream operations may use several operating-system calls.  An `IO.Error` propagates to the Lean caller, including when a failed stream operation has already changed the outside world, while explicit `Transfer.trapped` replies produce an `Outcome.trapped`.  Invalid host reply lengths or errnos raise an `IO.Error`.  [The native interpreter](../LeanExe/Wasi/Interpreter.lean) defines this adapter policy.

`NativeHost.withSys` ([the native calls](../LeanExe/Wasi/NativeCalls.lean)) serves `clock_time_get` from the system's realtime and monotonic clocks, with errno 8 for clocks 2 and 3, `random_get` from the system's random bytes, and `args_sizes_get` and `args_get` from the given arguments, and it traps on the other calls.  The interpreter requires a call's outputs to have the sizes that its description and arguments give, and a reported region the size that the last successful reply of its reporter in the same run gives, and it raises an `IO.Error` otherwise.  No theorem relates the native interpreter to `Exec`, and its agreement with the semantics depends on inspection and on the native tests.

The [running-sum native executable](../Demos/RunningSum/Native.lean) uses a [POSIX fd 0 reader](../Demos/RunningSum/read.c) for short reads on pipes.  The pinned Lean stream reader uses `fread`, which can wait for the requested capacity or EOF.  The descriptor adapter returns after one successful `read`, retries interrupted calls, and propagates other OS errors through Lean's error decoder, and writes keep the stream adapter's flush policy.  `Process.runFrom` returns the status of a stopped process to its caller without a host exit, while the compiled `_start` passes that status to `proc_exit`, so the two differ for statuses that Wasmtime rejects.

### Wasmtime host

The [Wasmtime host setup](verified-manual.md#the-wasmtime-host) builds `build/tools/leanexe-wasmtime-host` against pinned Wasmtime 44.0.0, and the host uses Wasmtime's standard Preview 1 implementation.  It passes arguments with `--arg`, environment variables with `--env NAME=VALUE`, and preopens one directory as `.` with `--dir PATH`.  From the repository root, the following commands build and emit both forms of the stdio example and run them, the command form with `run`, which exits with `main`'s errno, and the callable form's `copySome : UInt64 → Action UInt64` export with `call`:

```sh
mkdir -p build/wasi
tools/leanrun --timeout 10m lake build Verified.Examples.WasiStdio
tools/leanrun --timeout 5m lake env lean --run tools/Emit.lean \
  Verified.Examples.WasiStdio StdioExample.command.module build/wasi/stdio-command.wasm
tools/leanrun --timeout 5m lake env lean --run tools/Emit.lean \
  Verified.Examples.WasiStdio StdioExample.callable.module build/wasi/stdio-callable.wasm
wasm-tools validate build/wasi/stdio-command.wasm
wasm-tools validate build/wasi/stdio-callable.wasm
build/tools/leanexe-wasmtime-host --stdin-file input.bin \
  --stdout-file output.bin --stderr-file errors.bin run build/wasi/stdio-command.wasm
build/tools/leanexe-wasmtime-host --wasi --stdin-file input.bin \
  --stdout-file output.bin --stderr-file errors.bin --control-file control.txt \
  call build/wasi/stdio-callable.wasm copySome i64 i64:4096
```

`run` enables WASI and invokes `_start`, and without stream-file options it inherits stdio.  Control output contains return values, allocation counts in `call-stats` mode, and the outcome records that [the verified compiler manual](verified-manual.md#the-wasmtime-host) lists.  Guest stream files contain guest bytes, and host diagnostics use host stderr.  Callable WASI modes require `--control-file` or a separate `--stdout-file`.  Script and session modes also require `--stdin-file` so guest input does not consume host instructions.

Exit always passes the low 32 bits of the source status.  [Wasmtime 44 accepts statuses below 126](https://github.com/bytecodealliance/wasmtime/blob/v44.0.0/crates/wasi/src/p1.rs#L2614-L2625) and rejects larger narrowed statuses as engine errors.  For example, `2^32 + 7` requests accepted status 7, and `2^32 + 126` requests rejected status 126.  An accepted exit produces a `wasi-exit STATUS` record when control records are enabled, and the host process uses the low eight bits as its status.  Rejection produces an error diagnostic and process status 1.  Both outcomes preserve previously written guest output.  The native stream adapter accepts every narrowed status.

### The Linux shim's specification

[The shim's environment](../Verified/Shim/Satisfies.lean) `linuxEnv F L I replies calls` implements the stream imports and the flat calls of `shimCalls` with requests of [the Linux call layer](a64-bare-metal.md#the-linux-call-layer), independently of an instruction set.  Its parameters are the open flags `F`, the layout `L`, the launch `I`, and the reply sequence `replies`.  `F` holds the open flags whose values differ between architectures, such as `arm64Flags`, and `L` the addresses of the guest's byte 0 and of the shim's scratch.  `I` holds the process's arguments, its environment, and whether descriptor 3 is a directory that the launcher grants, and `replies` gives the reply to the call made after that many layer events.  Each function makes its layer calls through the layer's rule `Linux.step`.

| Function | Layer calls | Reply |
|---|---|---|
| `fd_read` of the stream | One `read` of descriptor 0 into the guest's buffer, at `L.base` plus the guest's pointer | The count and the bytes |
| `fd_write` of the stream | One `write` of descriptor 1 or 2 | The count |
| `proc_exit` | None | Accepts a status below 126 and rejects 126 or more with `exitRejected` |
| `clock_time_get` | One `clock_gettime` into the timespec of the shim's scratch for clock 0 or 1, none for clocks 2 and 3 | The time in nanoseconds, errno 61 for a time before 1970 or of `2^64` ns or more, and errno 8 for clocks 2 and 3 |
| `random_get` | `getrandom` calls until the buffer is full, each asking for the bytes that remain | The bytes |
| `args_sizes_get`, `environ_sizes_get` | None | The count and the size of the strings of `I`, or errno 61 when either reaches `2^32` |
| `args_get`, `environ_get` | None | The strings of `I`, or a trap when the count or the size reaches `2^32` |
| `path_open` | The checks of `openCheck` in Wasmtime 44's order, then `openat2` with the path and an `open_how` record in the shim's scratch and the resolution flags `RESOLVE_BENEATH` and `RESOLVE_NO_MAGICLINKS`, again after `EAGAIN` up to four calls in all | The descriptor, or a trap for a descriptor of 1,024 or more |
| `fd_close` | One `close` | The errno |
| `fd_read`, `fd_write` on a handle | One `read` or `write` of the handle's descriptor with the buffer that the iovec element at the request's pointer names | The count, and for a read the bytes |
| `fd_prestat_get` | None | A directory whose name has one byte for descriptor 3, and errno 8 for every other number |
| `fd_prestat_dir_name` | None | The name `.` for descriptor 3, or errno 37 (`nametoolong`) for a buffer of no bytes, errno 54 (`notdir`) for 0 to 2 and the other numbers that the shim holds open, and errno 8 for every other number |

A result in the range that Linux gives for a request is a count, a descriptor, or a time, a negated error number gives the WASI errno of `errnoOf`, which follows Wasmtime 44's table with `EXDEV` as `perm`, and any other result traps with `shimTrap`.  The shim also traps for a `clock_gettime` that reports nanoseconds of `10^9` or more, a stream request that fails a premise of `ReadRequest` or `WriteRequest`, a flat request with a region outside memory, a clock above 3, and an iovec count other than 1.  It answers a flat request whose pointers are misaligned or whose regions overlap, which `SysRequest` excludes.

The shim holds open the descriptor numbers of `openNumbers I events`, which it reads from the world's layer events at each call: 3 when `I` grants it and each number below `descriptorLimit`, 1,024, that an `openat2` returned, each until a `close` of the number.  1,024 is Linux's default soft `RLIMIT_NOFILE`, below which Linux numbers every descriptor of a process that keeps it, and the shim does not change the limit.  `path_open`, `fd_close`, and the handle forms of `fd_read` and `fd_write` refuse every other number with errno 8 (`badf`) and no call, as Wasmtime 44 answers for a number outside its table.  A module then reaches no descriptor that the process inherited, other than the standard streams and a granted 3, when `openat2` returns only numbers that are not open, as Linux does, and no theorem of the shim assumes that property of the replies.  The prestat functions answer for descriptor 3 while `preopened I events` holds, from the grant until a `close` of 3.  `Image` takes the layer events before each call and reads the same numbers from them, so the host's relation fixes which requests the shim refuses.

[The shim's host](../Verified/Shim/Host.lean) `linuxHost F L I replies` relates a WASI request to a reply exactly when the layer events that it appends form an `Image` of the WASI event, hold their replies, and meet `WritesWithin L (2^32)`.  `Image` fixes each event's call and arguments, and the inputs and the bytes before the call where the shim determines them, and derives the WASI reply from the events' results.  It leaves free an address in linear memory and an output region's bytes before a call, which depend on the store.  The sizes of the regions of `args_get` and `environ_get` come from `I`, and the world records the outputs of every successful flat call by name, from which a call that names another reporter takes its sizes, as `Host.sys_reports` requires.  `linuxHost` admits no reply to a write of `2^32` bytes or more or to a flat call outside `shimCalls`, so a lemma proved by induction on `Exec` under it says nothing of an action that makes such a request.

`WritesWithin L size` bounds each output region by the `size` bytes from `L.base` or makes it the timespec of the shim's scratch, and the host and `shim_footprint` state it for `2^32` bytes, the guest's address space.  In an AArch64 executable whose data segment ends below `2^32` and holds the stack and the shim's scratch above linear memory, that window contains them, so the bound excludes no write into the data segment above the guest's byte 0.  `HostEnv.Satisfies` requires each import's specification at every store, and `linuxHost` sees a world and a request but no store, so a host that bound the writes by a native cap would have to answer a request whose buffer lies beyond the cap at a store whose memory exceeds it, with an event that names an address the environment did not use.  A binding whose relation keeps the store within a native cap at each call obtains that bound from `readEvent_writesWithin` and `randomEvent_writesWithin`, which bound the output region of a `read` or `getrandom` event by any size that holds its buffer, such as the memory's size at the call.  The requests of `clock_gettime` and `openat2` name only the shim's scratch, which lies outside the Talos store, and `step_clock` and `step_openat2` give their events for every memory that holds the cleared timespec, the path with its terminating zero, and the `open_how` record.  The AArch64 binding states the bound with `WritesNative` of [its machine](../Verified/ShimA64/Machine.lean): each event writes within the executable's linear memory, `WritesLinear`, or is a `clock_gettime` whose output region is the timespec of the shim's scratch, which lies between the area and the stack.  [The executable's theorems](../Verified/ShimA64/Elf.lean) state the run of a command's static Linux executable to `exit_group` with every layer event of its trace bounded so, as [the AArch64 document's section on WASI commands](a64-bare-metal.md#wasi-commands) describes.

`linuxEnv_satisfies` proves that the environment satisfies `hostSpecWith (linuxHost F L I replies) calls` for every module with at most the stream imports and `calls`, when `shimCalls` holds every call of `calls`.  [`shim_footprint`](../Verified/Shim/Footprint.lean) composes it with `compiled_native_start_run_with`: every run of `_start` with enough fuel traps with a world whose layer events extend the initial world's events by `Images` of a WASI trace of the command's action, which ran to an accepted exit, a rejected exit, a trap of the shim, or a guest trap after a prefix.  No statement assumes a property of the replies other than the frame of the layer's rule.  `shim_footprint` excludes the requests to which `linuxHost` admits no reply: a compiled module passes a length below `2^32`, and its premise `supported` excludes the other calls.  [The readAll example](../Verified/Examples/WasiReadAllShim.lean), [the flat call and environment examples](../Verified/Examples/WasiSysShim.lean), and [the file example](../Verified/Examples/WasiFilesShim.lean) instantiate the footprint, with a guest trap admitted after any prefix and each module's declared memory cap.

`Images.readData` and `Images.writeData` of [the trace lemmas](../Verified/Shim/Trace.lean) give the bytes that the layer's reads and writes of a descriptor moved as the bytes that the trace's events read from or wrote to it, through the stream imports and the handle forms alike.  [The descriptor corollary](../Verified/Shim/Descriptors.lean) `footprint_namesHeld` states, for every command and every reply sequence, that the layer events of every run that the footprint describes name only standard streams and the numbers that the shim holds open: the descriptor of each `read` and `write` is 0, 1, or 2 or a number of `openNumbers I` after the events before it, and the descriptor of each `close` and the directory of each `openat2` is such a number.  The file example states this corollary of its runs.  [The descriptor updates](../Verified/Shim/Held.lean) state how one layer event changes `openNumbers` and `preopened`: an event that opens no descriptor below `2^31` and is no `close` keeps both, an `openat2` whose result lies below 1,024 adds the result, and a `close` of a number below `2^32` removes it and ends the preopened directory when the number is 3.  A binding that keeps the shim's state in memory uses these lemmas to restore its relation to `openNumbers` and `preopened` after each call.  [The stream lemmas](../Verified/Shim/Streams.lean) state that the trace of an action without flat calls holds none, and that the images and the `Exec` and `Prefix` runs of such a trace under `linuxHost` read neither the open flags nor the launch, so they hold for every choice of both when the layout's guest byte 0 and timespec stay the same.

[The readAll message corollary](../Verified/Examples/WasiReadAllMessage.lean) `linux_message` states what the readAll command does under `linuxHost` when its reads and writes succeed.  For every reply sequence and every budget that fits between the heap's start at byte 4,096 and the end of the module's 65,535 pages and bounds every typed resource prefix of `main` under those replies, every run of `_start` with enough fuel traps.  When the final layer events hold no `read` that fails (`ReadsSucceed`: every `read` returns a count of at most its length) and no `write` that fails or returns 0 (`WritesAdvance`), the trap is the accepted exit with status 0 if the reads of descriptor 0 returned at most 1,000,000 bytes and 1 otherwise.  The events then meet `Copies`: reads of 4,096 bytes from descriptor 0, each but the last returning bytes, at most 1,000,000 bytes before the last read and 1,004,096 in all, the last read returning none unless the bytes exceed the limit, followed by writes of descriptor 1 that took the bytes that the reads returned.  Writes of count 0 are excluded because they can use up `writeAll`'s passes with bytes unwritten while the run still exits with the status of its input.  The budget is the resource model's, which charges the suffix that `writeAll` allocates for each write and credits no release, so the charge grows with the number of writes and exceeds the module's memory for an input of 100,000 bytes written one byte at a time.  `linux_exec_message` proves the same facts from an `Exec` run under `linuxHost` and the `Images` of its trace alone, the form in which a binding's footprint states a native run that ends in an exit or a trap of the shim, and `linux_exec_succeeded` proves them when the run's WASI events meet `Succeeded`.

[The corollary for a class of reply sequences](../Verified/Examples/WasiReadAllSteady.lean) meets the budget premise.  A reply sequence `R` belongs to `Steady F L I M R` when it answers every call that a prefix of `main` and its exit makes under `linuxHost F L I R`: a read with a result of at most its capacity, and a write of `n` bytes with a result of at most `n`, at least 1, and at least `min M n`.  A read of a regular file or a pipe returns at most its count, and a write of `n` bytes to a regular file or to a pipe in blocking mode takes all `n` bytes unless an error or a signal interrupts it ([read(2)](https://man7.org/linux/man-pages/man2/read.2.html), [write(2)](https://man7.org/linux/man-pages/man2/write.2.html), [pipe(7)](https://man7.org/linux/man-pages/man7/pipe.7.html)).  The class therefore holds Linux's replies to a run whose standard input is a regular file or a pipe and whose standard output is a regular file or a blocking pipe, when no call fails or is interrupted, and to a run whose writes each take at least `M` bytes or the rest.  It excludes every reply that reports an error, such as `EAGAIN`, `EINTR`, `EIO`, `ENOSPC`, `EFBIG`, or `EPIPE`, every result outside the request's range, and every write that takes fewer than `min M n` bytes: a write to a descriptor in nonblocking mode, which may take from 1 to `n` bytes, a write to a regular file at a full disk or at `RLIMIT_FSIZE`, and a write that a signal interrupts after some bytes.  With `M` at 4,096, `writeAll` makes at most 246 passes for the at most 1,004,096 bytes that `readAll` returns, and `budget_bounded` bounds the charge of `main` by `budget`, 247 times the 1,004,144 bytes that a block of 1,004,096 bytes charges: `readAll`'s buffer and the suffixes.  The reflector splits the input into its errno and its bytes where `main` binds it, so no later use copies it.  The heap's start at byte 4,096 and the budget fit in 3,785 pages, the least cap of `linux_footprint_steady`.  The charge depends on the replies, so the bound follows from the worlds that the runs reach: `BoundedAt` and `RuleAt` bound a command's runs and prefixes from one world, `SteadyAlong` carries the class along the run, and `WriteLoop.bounded` bounds the loop of `writeAll` by induction on its passes.  `linux_steady` states, for every reply sequence of the class with `M` at 4,096, that every run of `_start` from the command's initial store with enough fuel ends at the accepted exit with status `statusOf` of the bytes that the reads of descriptor 0 returned, and that its layer events meet `Copies`.

### Differences from Wasmtime

The shim follows the repository's Wasmtime host in its errnos and in the order of its checks, except for a file handle as the directory of `path_open`.  For the calls that it implements, it differs from the host in the replies that the table lists, each of which the calls' specifications admit.  A test that compares a native run with a run of the same module under the host, as [the AArch64 document's section on WASI commands](a64-bare-metal.md#wasi-commands) describes, expects these differences.  The table omits differences that no WASI reply shows, such as the bytes that Wasmtime's reader of standard input holds in its buffer when the instance ends, which the process consumed and the guest never receives.  It also omits requests outside the premises of those specifications, which a compiled module does not make: Wasmtime traps for an enum or flags argument out of range and, after the call's effects, for a misaligned result pointer, while the shim traps for a clock above 3, ignores flag bits outside the masks, and answers a misaligned flat request.  Where Wasmtime's reply depends on whether the host inherits standard input or reads it from `--stdin-file`, the row gives both.

| Case | Wasmtime host | Shim |
|---|---|---|
| A closed standard descriptor | With an inherited stream, end of input for a read and a full count for a write, from Rust's `handle_ebadf`, while no file that the host opens takes the number | Errno 8 (`badf`) |
| Reads of standard input after one that reports an error | End of input with an inherited stream, whose reader stops, and with `--stdin-file` the bytes that the reader queued before the error and then end of input | Each read's own result |
| A zero-length `fd_read` of standard input | A wait until a read of the stream completes, then errno 27 (`intr`) when input is pending, a count of 0 at its end, or the read's errno | A count of 0 |

| `fd_read` of standard input | At most 1,024 bytes with an inherited stream, from a helper thread that reads through Rust's buffer of 8 KiB, and at most 65,536 with `--stdin-file` | Linux's count, up to the capacity |
| `fd_write` to standard output | The whole count or an error, passed to the stream in pieces of 4,096 bytes | Linux's count, which may be short |
| An iovec buffer of more than `2^27 − 8` bytes, the stream imports' among them, or a path of more than `2^27` bytes, beyond the hostcall fuel of `2^27` bytes for each call | Errno 48 (`nomem`) | The call for a buffer and the checks of `openCheck` for a path |
| A realtime clock before 1970 | A panic of the host function | Errno 61 (`overflow`) |
| The monotonic clock's origin | The creation of the WASI configuration, `wasi_config_new` | Linux's boot |
| Random bytes | A user-space generator seeded once | `getrandom` for each call |

| Arguments and environment | `--arg` and `--env` values, each UTF-8 | The launch's byte strings |

| Descriptor numbers | Wasmtime's table, which reuses the largest freed number or takes one above the largest open number | Linux's lowest free number |
