# The Cortex-M7 back end

The Cortex-M7 back end compiles a step function, the Lean function of a program with requests, to Thumb-2 machine code for the STM32F767ZI of ST's NUCLEO-F767ZI board, with no C compiler, assembler, or linker.  Lean writes a flat image of the board's flash: a vector table, an initialization of the board's clocks, pins, and USART3, a `main` that calls the step forever and performs after each call the one device access that the step requests, the functions that the step's calls reach, and a routine that divides 64-bit words.  For each image, a theorem checked by Lean's kernel states that the image, started from reset, performs the initialization's accesses and then the accesses that the step requests, for every sequence of the values that device reads return and every number of the loop's iterations, in a Lean model of the processor.  The theorem is a chain of links: from the step to a WebAssembly module, from the module to the model, and from the model, the image's bytes, and reset to the board.

Two programs have images and theorems: the echo of `usart3Tick`, which sends back each byte that USART3 receives with bit 5 flipped, and the gateway of `gwTickUsart3`, which frames [the energy controller's gateway](../Demos/Energy/README.md#the-gateway-in-the-loop) with records over USART3.  The same generator writes images of the steps `cmsdkTick` and `gwTick` for QEMU's `mps2-an500`, whose Cortex-M7 QEMU emulates, with theorems of the same form.  Lean proofs compare every instruction form of the model with Isla's traces of Arm's A-profile specification in AArch32 Thumb state, a reading of each form's M-profile pseudocode against its A-profile pseudocode belongs to the trusted base, and co-simulation on QEMU and on the board tests the model against the processor.  Both programs run on the board at 4,800 baud: the echo answers every byte, and the gateway's output records over a simulated day equal native Lean's.  [The C path for the same board](native-bare-metal.md#the-nucleo-f767zi) compiles the same steps through CompCert.

## The steps and their compiler theorems

A program with requests runs a step function `tick : G → UInt64 → G × UInt64` forever.  Each call, a window, takes the step's state and the value that the last request read and returns the next state and a request: bit 63 of the request selects a write, bits 32 to 47 name a device register, and a write stores the low 32 bits.  [The C path's section on requests](native-bare-metal.md#device-registers-and-requests) describes the protocol and the steps: `usart3Tick` instantiates the echo for USART3, with `USART_ISR`, `USART_RDR`, and `USART_TDR` at the register indices `0x1207`, `0x1209`, and `0x120A`, and `gwTickUsart3` instantiates the gateway's framing for the same registers.  The steps are functions 9 and 5 of the module `reqCompiled`, `usart3Tick` and `cmsdkTick`, and functions 34 and 33 of `gwCompiled`, `gwTickUsart3` and `gwTick`, which `verified_compile (pages := 1) (cap := 1)` compiles.

The verified compiler's theorem of each step, `p.f.implements`, is an `ImplementsA` statement whose abort flag is false: from a store with the allocator's invariant, the module's run in Talos, the reference interpreter, returns the words of the step's result without a trap.  The step's state is a structure whose `Scalar` instance gives its words, one word for the echo, whose initial state is 3, and 45 for the gateway, whose initial state is `gwInit`, so each step takes and returns one word more than its state.  Talos serves as an intermediate language whose semantics only the proofs use, as [the AArch64 document](a64-bare-metal.md#from-the-lean-function-to-webassembly) describes: the interpreter's run appears in the conclusion of the compiler's theorem and in the premise of the simulation, and the composed statement does not mention it.  The functions that the steps reach use no linear memory, global, or floating point, so the simulation's relation holds no store.

## The machine model

`LeanExe/M7/Machine.lean` models the Thumb-2 forms that the generator emits, executed in sequence by one core in Thread mode, after the Armv7-M Architecture Reference Manual, DDI 0403E.e.  Its state holds r0 to r12, SP, LR, the program counter, the flags N, Z, C, and V, memory as a map from 32-bit addresses to bytes, the list of device accesses, and the number of device reads so far.  A step fetches the halfword at the program counter and the one after it from a fixed map of code halfwords, decodes the instruction that starts there, and executes it, and it stops the model when the fetch, the decoding, or the execution fails.  `step` takes the sequence `σ : Nat → UInt32` of the values that device reads return, so the run from a state is a function of `σ`, and `Reach` is the reflexive-transitive closure of `step`.  The model has no IT state, no exceptions, and no floating-point registers, and the decoder accepts no IT, floating-point, or system instruction other than `DSB SY`.

| Group | Forms | Uses |
|---|---|---|
| Data processing | `ADD{S}.W` with `LSL #k`, `ADC.W`, `SUB{S}.W`, `SBC{S}.W`, `AND.W`, `ORR{S}.W`, `EOR.W`, and `CMP.W` with registers; `SUB.W`, `AND.W`, `EOR.W`, `CMP.W`, and `MOV.W` with an 8-bit immediate; `LSL.W` and `LSR.W` by a register and by an immediate; `MOVW` and `MOVT` | pairs of words, comparisons, constants, and addresses |
| Multiply, divide, and count | `UMULL`, `MLA`, `MLS`, `UDIV`, and `CLZ` | `mulI64`, `udivmod64`, and equality |
| SP | `ADDW` and `SUBW` with SP as the source, and with SP as the source and the destination | frames and the prologue's check |
| Memory | `LDR.W` and `STR.W` at a register plus a 12-bit offset, at SP plus an offset, and of LR at SP plus an offset | slots, device accesses, and the return address |
| Control | `B<cond>.W` (T3), `B.W` (T4), `BL`, `BX LR`, and `DSB SY` | constructs, calls, returns, and the initialization |

A register field of type `Fin 8` names r0 to r7, so the constructors admit no register choice that the encodings make UNPREDICTABLE, such as SP or PC in most fields of the 32-bit data-processing forms, and each form with SP or LR in a register field is a constructor of its own.  The restriction also keeps Isla's traces small: a trace whose register fields range over r0 to r7 takes about 1 GB, and a probe of one over r0 to r12 took 10.9 GB.  Where an encoding splits an immediate, the constructor carries the parts, such as `imm4:i:imm3:imm8` of `MOVW` and `S`, `J1`, `J2`, `imm10`, and `imm11` of `B.W` and `BL`, and `exec` joins them.  `UMULL` carries a proof that its two destinations differ.  Every form but `BX LR` is 32 bits wide, and `BX LR` always branches, so a form that falls through places the next instruction at the program counter plus 4.

The flags follow the pseudocode.  `ADDS`, `SUBS`, `SBCS`, and `CMP` set N, Z, C, and V from `AddWithCarry` (section A2.2.1), `ORRS` sets N and Z and keeps C and V, since its shift amount is 0, and every other form leaves the flags.  A write to SP clears bits 1 and 0 of the value, as the register write of section B1.4.7 does, and only `ADDW SP, SP` and `SUBW SP, SP` write SP.  `LSL` and `LSR` by a register shift by the register's bottom byte and give 0 for an amount of 32 or more, an `LSR` whose immediate field is 0 shifts by 32, and `CLZ` gives 32 for 0.  A branch adds its offset to the instruction's address plus 4, `BL` sets LR to the next instruction's address with bit 0 set, `BX LR` branches to LR with bit 0 clear, and `DSB SY` is a step to the next instruction.

A word load or store needs an address that is a multiple of 4.  A platform names the bytes of Normal memory and the addresses of device words: at a device address a load appends `read a (σ k)` to the trace, where `k` counts the reads so far, and a store appends `write a v`, and in Normal memory a load or store reads or writes four bytes, the lowest first.  The board's platform names DTCM, `0x20000000` to `0x2001FFFF`, as Normal memory and the 65,536 words from `0x40000000`, which hold RCC at `0x40023800`, GPIOD at `0x40020C00`, and USART3 at `0x40004800`, as devices.  Every other access stops the model, among them any load from or store to flash, any access to the System Control Space, and a byte or unaligned access.  `exec` also stops on `UDIV` with a zero divisor and on `BX LR` with bit 0 of LR clear, where the processor takes an INVSTATE UsageFault (sections A7.7.20 and B3.2.15).

Wherever the architecture permits several behaviors, or depends on state that the model does not track, the model stops, as [the AArch64 model](a64-bare-metal.md#the-machine-model) does.  The model is therefore sound whatever `CCR.UNALIGN_TRP` and `CCR.DIV_0_TRP` hold, since it stops on every access that the first field governs and on every division that the second governs.  A theorem about a run that never stops excludes every such state, so the processor's behavior in those states has no bearing on the theorem, and tests of the model need to cover only the states in which it runs.

The model fetches from a fixed map of code halfwords that the theorem derives from the image file, so a store never changes what the model fetches.  On the board the map is the flash, which no store of the program reaches, since every store outside DTCM and the device window stops the model, and which changes during a run only through a debugger or DMA, both excluded by the run conditions.  The caches stay off from reset, and DTCM is never cached (DDI 0489F, section 5.8), so no cache maintenance enters the model.

## Encoding

The code is a list of halfwords, each stored with its low byte first, and a 32-bit instruction is two halfwords with the first at the lower address, the order in which the processor fetches them (section A3.3.1).  `encode` gives each form's halfwords as its fixed bits plus its fields at their positions, and `decode` decides the length from bits 15 to 11 of the first halfword (section A5.1), reads the fields, and returns the candidate whose encoding equals the halfwords.  The decoder therefore accepts exactly the bit patterns that the encoder writes: `UMULL` with equal destinations, `CLZ` with two different Rm fields, `UDIV` with a should-be-one bit clear, a modified immediate whose `i:imm3` is not 0000, and `B<cond>.W` with condition 14 or 15 decode to nothing.  The decoder belongs to the model, since it gives the halfwords their meaning in the theorems.

```lean
theorem decode_encode (i : Instr) (rest : List UInt16) :
    decode (encode i ++ rest) = some (i, (encode i).length)
```

`decode_encode` states that the decoder reads every encoded instruction back as itself, for every form and every value of its fields, with any halfwords after it.  `decode_sound` states that a decoded instruction's encoding is the prefix that the decoder read, and `encodeNat_injective` that no two instructions share an encoding.  The proofs split on the forms and decide every field with `omega`.  `tests/baremetal/m7-encode.sh` compares the encoder with the GNU assembler: 390 samples of the 39 forms, with every register field at r0 and at r7, each immediate field at 0 and at its largest value, every condition, and the branch offsets at ±1 MiB for `B<cond>.W` and ±16 MiB for `B.W` and `BL`, assemble with `arm-none-eabi-as -march=armv7e-m -mthumb` 2.42 to the encoder's halfwords, and the decoder reads each sample back from the assembler's halfwords.  With one bit of the assembled bytes changed, the comparison reports that sample.

## The code generator

`genProgram m k s0 base limit dev div` in `LeanExe/M7/Gen.lean` takes the module that the verified compiler emits, the index `k` of a step, the words `s0` of its initial state, the program's base, the stack's limit, the device window's base, and the code of `udivmod64`.  It gives a program of the model's forms: `main`, the functions that calls reach from the step, the step first, three trap stubs, or four for a program with an area, and `udivmod64`, and it requires the step to take and return `s0.length + 1` values of type `i64`.  The generator accepts the integer forms of the AArch64 back end's subset, the constructs, `br`, `br_if`, `return`, `unreachable`, calls, 64-bit loads and stores, and the accesses of globals, and it rejects floating point and every other form with a message.  It follows the AArch64 generator definition by definition, with an environment, size functions that give a construct's size before its body is emitted, and a table of the functions' entries, so that the proofs keep the AArch64 proofs' shapes.

Every operand-stack height lies in a frame slot of 8 bytes, its low word first, and r0 to r7 serve as working registers: an operation loads its operands into r0:r1 and r2:r3, computes in r0 to r7, and stores its result into the slot of its height.  Slots hold any number of values, which the gateway needs: its step takes and returns 46 words and calls `gwTickWith` with 52 parameters.  An `i32` lies in a slot whose high word is 0, so `extendUI32` emits nothing, `wrapI64` clears the high word, and the `i32` forms compute on the low words.  The table gives the sequence of each `i64` operation between the four `LDR` of its operands and the two `STR` of its result.

A program whose functions load, store, or access a global has an area at the base of DTCM, in the layout of the AArch64 back end's area: at `0x20000000` the size word, which holds the memory's size in bytes less 8, then global `i` in the slot at `0x20000000 + 8(i + 1)`, and from `0x20001000` the memory's bytes, one page, so that the area ends at `0x20011000`, and the stack's limit lies at or above that address.  The module's globals must be at most 511 `i32`s and `i64`s.  A load or a store of 8 bytes at an offset `off` of at most 4,088 takes 18 instructions: `LDR` of the address's two words into r0 and r1, `MOVW` and `MOVT` of the header's address, `LDR` of the size word into r3, `MOVW` of `off` and `SUB` from r3, `CMP r1, #0` and `BNE`, and `CMP r0, r3` and `BHI` to the trap stub of an access outside memory, `MOVW`, `MOVT`, and `ADD` of the memory's base and the address, and the two loads or stores at the offset.  The test compares registers before any addition, and it is exact for an `i32` and for an `i64` address.  An access of a global takes 6 instructions, `MOVW`, `MOVT`, and a copy of the slot's two words.  No proof covers these forms, and no theorem covers a program with an area.

| `andI64`, `orI64`, `xorI64` | the operation on each half | 2 |
| `mulI64` | `UMULL r4, r5, r0, r2`, `MLA r5, r0, r3, r5`, and `MLA r5, r1, r2, r5`, with the result in r4:r5 | 3 |
| `shlI64`, `shrUI64` | `AND r2, r2, #63` and the cross terms of CompCert's `__compcert_i64_shl` or `__compcert_i64_shr`, shifts by `32 - n` and `n - 32` that are exact because a register shift by 32 or more gives 0, after one `LDR` of the amount's low word in place of two | 10 |
| `eqI64`, `neI64` | `EOR` of each half, `ORR`, `CLZ`, `LSR #5`, and `MOV r1, #0`, and `EOR r0, r0, #1` for `neI64` | 6 and 7 |

The comparisons take the carry as a value and equality takes `CLZ`, which gives 32 only for 0, so no IT block or conditional move enters the model.  Every `ADC`, `SBC`, and conditional branch follows a flag-setting instruction in its sequence, so the flags, which reset leaves UNKNOWN, never reach a result.  A construct carries at most one value, a branch that carries one copies the top slot into the slot of the construct's base height, and `br_if` and `if` load the condition's low word, compare it with 0, and branch.

A function's frame holds, from SP upward, an outgoing area with one slot for each parameter or result of the largest call in its body, a slot for each declared local that the body names, one slot for each operand-stack height that the body reaches, and the slot of LR, each slot 8 bytes.  A declared local that the body never names has no slot: `gwTickWith` declares 794 locals and names 230, and its frame takes 2,656 bytes.  The parameters stay in the caller's outgoing area, parameter `i` at SP plus the frame's size `F` plus `8i`, and the epilogue copies result `k` from the slot of height `k` to `SP + F + 8k`.  A call copies its arguments from their slots into the outgoing area, branches with `BL`, and copies the results back into the slots of their heights, and the callee changes no memory from its caller's SP plus 8 times the larger of its numbers of parameters and results upward.  Every offset from SP must lie within the 4,095 bytes that the 12-bit immediates of `LDR`, `STR`, `ADDW`, and `SUBW` reach, which the generator checks for each frame as `F + 8 * max p r - 4 ≤ 4095`, and the gateway's largest offset is 3,068.

The prologue computes SP less the frame's size into r4 with `SUBW`, loads the stack's limit into r5 with `MOVW` and `MOVT`, and branches to a trap stub when r4 lies below r5, and it then lowers SP, stores LR, and clears the slots of the named locals.  The epilogue copies the results, reloads LR, raises SP, and returns with `BX LR`, followed by a second `BX LR` that never runs, so that each function takes a whole number of 4-byte units.  Each trap stub is a branch to itself: the compiler's theorem of the step excludes the traps of `unreachable` and of a division by zero, and the stack's bound excludes the overflow, so no proved run reaches a stub.

The generator places code as it emits it, in units of 4 bytes, so every function starts at the program's base plus a multiple of 4.  A size function gives the units of each construct before its body is emitted, so the target of a forward branch is known when the branch is emitted, and each branch's offset is checked against its field's reach, ±1 MiB for `B<cond>.W` and ±16 MiB for `B.W` and `BL`.  `genFunctions` checks that each function's halfwords number twice its size in units.  The board fixes every address, so the program holds the stack's limit and the device window's base as constants and runs only at the base for which it was generated.

`stackBound m k` is the number of bytes of stack that a call of the step uses: a function's frame plus the largest bound of the functions that it calls, over the frames that the generator gives the reached functions, and 2^64 when the calls form a cycle.  `udivmod64` uses no stack.  The kernel evaluates the bound as 312 bytes for the echo's steps and 7,216 bytes for the gateway's, and the board's theorem requires the outgoing area of `main` and the bound to fit in DTCM's 128 KiB, so the prologue's branch to the stub of an overflow is never taken.

### Division

`udivmod64` in `LeanExe/M7/Div.lean` divides a `UInt64` by a nonzero `UInt64`, since `UDIV` divides only 32-bit words.  It takes the dividend in r0:r1 and the divisor in r2:r3, low words first, returns the quotient in r0:r1 and the remainder in r2:r3, changes r4 to r7 and the flags, and accesses no memory.  When the divisor's low word is 0, `UDIV` and `MLS` divide the high words, and the dividend's low word becomes the remainder's low word, the path of the remainder by 2^32 that every write window of both programs computes.  When both high words are 0, `UDIV` and `MLS` divide the low words.  Otherwise a dividend below the divisor is the remainder with the quotient 0, and any other dividend takes a restoring shift-subtract loop over the bit positions that the two leading-zero counts leave, from 1 to 64 passes.  The routine takes 230 bytes and executes 8 instructions on either `UDIV` path, 12 when the dividend lies below the divisor, and 41 to 923 on the loop.

`udivmod64_spec` in `LeanExe/M7/Proof/Div.lean` states that from the routine's entry, with a nonzero divisor and bit 0 of LR set, the model returns to LR with bit 0 clear with the quotient and the remainder of Lean's `UInt64` `/` and `%` in r0:r1 and r2:r3, and with SP, LR, r8 to r12, memory, the device trace, and the read count unchanged, for every platform and every `σ`.  The loop's invariant states, after a pass with `k` passes left, that the shifted divisor is `d·2^k/2` and that the quotient `q` and the remainder `r` satisfy `n = q·d·2^k + r` with `r < d·2^k`.  The lemmas about pairs of words convert words to natural numbers and decide linear goals with `omega`, and no proof of the back end uses a decision procedure for bit vectors.

## The simulation theorem

The simulation theorem relates Talos's state at a point of a function's code to the model's state at the address of that point's code.  `Inv` places the value at each operand-stack height in that height's slot, each parameter in the caller's outgoing area, and each named declared local in its slot, with `SlotRel` relating an `i64` to its two words and an `i32` to its word and a high word of 0, and `FrameOk` places the frame and the parameters in Normal memory, SP at a multiple of 4, and the stack's limit at least 4096 and at most SP.  `Outcome`, `InstrSim`, `ListSim`, `CallsOk`, and `FunSim` are the AArch64 statements over this relation: a fall-through reaches the end of the code in a related state, with SP, the device trace, the read count, the word of the LR slot, and the bytes from the end of the parameters up unchanged.  A trap, an invalid state, and the end of the fuel give no claim, and a branch out of a construct and a return have the outcome `False`, which the covered forms never give.

The proof runs by strong induction on the interpreter's fuel, from a lemma for each covered form, lemmas for `if` and for calls, and lemmas that the generated code has the size that the size function computes.  The covered forms, `coveredInstr` of `LeanExe/M7/Proof/Sim.lean`, are those of the functions that the two programs' steps reach: `local.get`, `local.set`, `i64.const`, `andI64`, `orI64`, `xorI64`, `addI64`, `subI64`, `mulI64`, `eqI64`, `neI64`, `ltUI64`, `leUI64`, `eqzI64`, `extendUI32`, `shlI64`, `shrUI64`, `divUI64`, `remUI64`, `if`, and `call`.  The kernel's evaluation of `reachCovered` checks them for each step.  `sim_divrem` composes the divisor's test with `udivmod64_spec`, whose code lies at the address that the functions share, and `fun_sim` runs the prologue, the clearing of the named locals, the body, the copies of the results, and the epilogue, with the prologue's branch to the stub falling through because the stack's room holds the frame.

`step_call` of `LeanExe/M7/Proof/Step.lean` joins the compiler's theorem of the step with the simulation.  From the step's entry, with bit 0 of LR set, the stack that `StackOk` states for `stackBound m k` bytes below `main`'s outgoing area, and the words of the state `s` and the value `v` in that area, the model returns to LR with bit 0 clear, with SP, LR, the device trace, and the read count as they were, every byte from the end of the outgoing area up unchanged, and the words of `tick s v` in the outgoing area.  It quantifies over every Talos store with a heap at it and a memory cap that the compiler's theorem admits, and the store after the call meets the same conditions, so a loop's invariant carries them from one call to the next.  `usart3_step`, `cmsdk_step`, `gwUsart3_step`, and `gwTick_step` instantiate it, and every theorem of the back end depends on `propext`, `Classical.choice`, and `Quot.sound` at most.

## The reactive loop

`main` lowers SP by the outgoing area of the step's `n + 1` parameters and results, stores the `n` words of the initial state into slots 0 to `n - 1` and 0 into slot `n`, and then repeats a window from the loop's head.  A window calls the step, which leaves the next state in slots 0 to `n - 1` and the request in slot `n`, loads the request's high word, extracts the register index with `LSL #16` and `LSR #16`, and forms the address `dev + 4·index` with `MOVW`, `MOVT`, and `ADD` with `LSL #2`.  It then tests bit 63 and performs either a word load of the address, whose value slot `n` receives zero-extended, or a word store of the request's low word, after which slot `n` holds 0, and it branches back to the head.  Each window performs exactly one device access, and `main` copies nothing between windows, since the step's results and its parameters share the outgoing area.

`LeanExe/Requests/Windows.lean` states the windows of a program with requests for any back end.  `reqRun tick s0 σ n` is the state before window `n`, the step's state with the last value read and the number of reads so far, and `reqTrace B tick s0 σ n` is the trace of window `n`, its one access, built through a `Bus α` that gives the read and the write of each register in a trace of type `α`.  `windows W N` joins the traces of the first `N` windows.  The C path's instance `regBus` records an access as CompCert's volatile event of `lx_reg`, and this back end's instance `devBus dev` records it as the model's access at `dev + 4r`, so a statement about the board's trace names no definition of Clight, and `LeanExe/Requests/Records.lean` holds the framing of records, `dataIn`, `dataOut`, and `frame_prefix` over any bus.

`main_window` of `LeanExe/M7/Proof/Main.lean` states one window from `step_call`: from the loop's head with the state of `reqRun` in the outgoing area, the model returns to the head with the next state there and `reqEvent (devBus dev)` appended to the trace.  `main_loop` iterates it by induction on the number of windows, `main_start` runs `main`'s start to the head, and `main_run` joins them from `main`'s entry.  The model's step is a function, so the run from a state is unique for each `σ`.

## Reset and the initialization

Reset, as section B1.5.5 of DDI 0403E.e gives it, loads SP_main with word 0 of the vector table with bits 1 and 0 cleared, copies bit 0 of word 1 to EPSR.T, branches to word 1 with bit 0 cleared, sets LR to 0xFFFFFFFF, and leaves r0 to r12 and the flags UNKNOWN.  `Reset code vtor b` of `LeanExe/M7/Proof/Boot.lean` states that `b` is a state that reset gives from the table at `vtor`: SP and the program counter from words 0 and 1, bit 0 of word 1 set, since the model executes Thumb code only, LR 0xFFFFFFFF, an empty trace, and no read done, with r0 to r12, the flags, and memory arbitrary.  The Cortex-M7 reads the table at VTOR's reset value, which it takes from its configuration input INITVTOR (DDI 0489F, Table 3-1), and with BOOT0 low the STM32F767 boots from the address that the option byte BOOT_ADD0 names, `0x00200000` for this board's value `0x0080` (RM0410, section 2.5 and Table 2).  The code map holds the same bytes at both of the flash's addresses, so a reset that reads the table at either one gives a state that `Reset code flashItcm` describes, and the theorems need only that VTOR's reset value is one of the two.  That ST drives INITVTOR from BOOT_ADD0 is an inference that joins the manuals, since neither RM0410 Rev 4 nor Rev 5 names INITVTOR.

The image writes no system register.  The processor leaves reset with the caches off and `CCR.UNALIGN_TRP` and `CCR.DIV_0_TRP` clear (CCR 0x00040200), the MPU disabled, so that the default memory map makes flash and DTCM Normal memory and the peripherals Device memory, the floating-point unit disabled, and HSI at 16 MHz as the system clock with no flash wait state.  The program makes only aligned accesses, tests every divisor, uses no floating point, and takes no exception, and the model stops in every state that the two fields of CCR govern, so no field of a system register enters the theorem.  The addresses, register offsets, fields, and reset values that the layout and the initialization use read the same in RM0410 Rev 4 and Rev 5.

`LeanExe/M7/Boot.lean` lays out an image from reset: the vector table, a self-loop, an initialization of 32-bit forms that falls through, and the generator's program after it.  Word 0 of the table is the initial SP, word 1 the initialization's address with bit 0 set, and every other word the self-loop's address with bit 0 set, so that an exception, which no proved run takes, stops at the self-loop.  The board's layout, `boot` of `LeanExe/M7/Board.lean`, has the 126 words of the 16 system entries and the 110 interrupts of the STM32F767 at `0x00200000`, SP `0x20020000`, the top of DTCM, the reset entry `0x002001FD`, the self-loop at `0x002001F8`, the initialization from `0x002001FC`, and `main` at `0x002003A8`, 936 bytes after the table.  The stack's limit is DTCM's base, `0x20000000`.

The initialization performs the accesses of `board_init` of `tools/baremetal/armv7m/nucleo-f767zi/board.S`, the C path's board code, in its order.  `LeanExe/M7/Init.lean` describes an initialization as a list of `InitOp`: a read-modify-write of a register with a mask to clear and a mask to set, a read whose value is discarded, a write of a constant, and `DSB SY`.  The board's list `init` selects HSI as USART3's clock, enables the clocks of GPIOD and USART3, each read back after its write, completes the accesses with `DSB SY`, gives PD8 and PD9 high speed, push-pull, pull-up, alternate function 7, and the alternate function mode, clears `USART_CR2.STOP`, writes 3,333 to `USART_BRR` for 4,800 baud from 16 MHz, and writes `USART_CR1` with UE, RE, and TE set.  It holds nine read-modify-writes, two reads, two writes, and the barrier, 107 instructions with 11 reads in all.  `initTrace ops σ` is the trace of the accesses when the reads return `σ 0`, `σ 1`, and so on, so each written value is a function of the value read and no register's reset value enters the statement, and `init_runs` proves the code of each kind of access once and composes the list by induction.

`boot_image` turns the kernel's check of an image into the table's first two words and the placed code, and `boot_run` runs the initialization and then `main_run`, whose windows read the values of `σ` after the initialization's reads.  `board_run` of `LeanExe/M7/Proof/Board.lean` instantiates it for the board, for any step with a compiler theorem without a trap, covered forms, and a stack bound that fits in DTCM, and `board_runs` adds that the run succeeds for every number of steps.  The second follows from `runs_forever`: a step appends at most one access to the trace, so a run that reaches a trace of `c + N` accesses for every `N` takes at least `N` steps to get there.

The images for QEMU's `mps2-an500` take QEMU 8.2.2's layout: QEMU loads a raw image given with `-kernel` at address 0, in ZBT SSRAM1, and its Cortex-M7 reads the vector table at VTOR's reset value 0.  Their platform names SSRAM2 and SSRAM3, 4 MiB at `0x20000000`, as Normal memory and the same device window, which holds CMSDK UART0 at `0x40004000`, and their table holds the 48 words of the 16 system entries and AN500's 32 interrupts, with SP `0x20400000`.  Their initialization writes 16 to UART0's `BAUDDIV` and 3 to its `CTRL`, two stores that start the trace, and their theorems state the run from `Reset code 0 b`.

## The final theorems

The theorems of `tests/TestSupport/M7/NucleoFile.lean` and `tests/TestSupport/M7/GwBoardFile.lean` concern the files `echo.bin` and `gateway.bin`, whose bytes the kernel compared with the generator's output.  `tests/baremetal/m7-board.sh check` elaborates both files in the directory of the images, so that `file_nat%` and `file_size%` read them, and no build target includes the files.  The statements name the board's `platform`, the loop heads `echoHead` and `boardHead` of the layout, and the initialization `init` of `LeanExe/M7/Board.lean`.

```lean
def echoBytes : Nat := file_nat% "echo.bin"
def echoSize : Nat := file_size% "echo.bin"

theorem echo_board (σ : Nat → UInt32) (N : Nat) (code : UInt32 → Option UInt16)
    (hf : Flash code echoBytes echoSize) (b : State) (hb : Reset code flashItcm b) :
    ∃ s, Reach platform σ code b s ∧ s.pc = echoHead ∧
      s.trace = initTrace init σ ++
        windows (reqTrace (devBus devBase) usart3Tick 3 (fun k => σ (k + initReads init))) N

theorem echo_board_runs (σ : Nat → UInt32) (code : UInt32 → Option UInt16)
    (hf : Flash code echoBytes echoSize) (b : State) (hb : Reset code flashItcm b) :
    ∀ k, ∃ t, run platform σ code k b = some t

def gwBytes : Nat := file_nat% "gateway.bin"
def gwSize : Nat := file_size% "gateway.bin"

theorem gw_board (σ : Nat → UInt32) (N : Nat) (code : UInt32 → Option UInt16)
    (hf : Flash code gwBytes gwSize) (b : State) (hb : Reset code flashItcm b) :
    ∃ s, Reach platform σ code b s ∧ s.pc = boardHead ∧
      s.trace = initTrace init σ ++
        windows (reqTrace (devBus devBase) gwTickUsart3 gwInit
          (fun k => σ (k + initReads init))) N

theorem gw_board_runs (σ : Nat → UInt32) (code : UInt32 → Option UInt16)
    (hf : Flash code gwBytes gwSize) (b : State) (hb : Reset code flashItcm b) :
    ∀ k, ∃ t, run platform σ code k b = some t

theorem gw_board_prefix (σ : Nat → UInt32) (N : Nat) (code : UInt32 → Option UInt16)
    (hf : Flash code gwBytes gwSize) (b : State) (hb : Reset code flashItcm b) :
    let w := windows (reqTrace (devBus devBase) gwTickUsart3 gwInit
      (fun k => σ (k + initReads init))) N
    ∃ s, Reach platform σ code b s ∧ s.trace = initTrace init σ ++ w ∧
      dataOut (devBus devBase) gwUsart3 w <+:
        outBytes gwSpec gw0 (decode 18 (dataIn (devBus devBase) gwUsart3 w)).recs
```

`Flash code n len` states that the code map holds the file's bytes from `0x08000000`, where `st-flash` writes them, and from `0x00200000`, the flash's address on the ITCM interface, and `Reset code flashItcm b` states that `b` is a state that reset gives from the table at `0x00200000`.  For every sequence `σ` of the values that device reads return and every number `N` of windows, the model reaches the loop's head of `main` with the trace of the initialization's accesses followed by those of the first `N` windows, whose reads take the values of `σ` after the initialization's 11.  The run has no trap and no other outcome, and `echo_board_runs` and `gw_board_runs` state that it succeeds for every number of steps, so the model never stops.  `gw_board_prefix` adds, through `frame_prefix`, that the bytes that the windows write to `USART_TDR` begin the bytes of the gateway's output records, `outBytes gwSpec gw0`, for the input records of 18 words that the bytes that they read from `USART_RDR` encode.

`usart3_requests` and `gw_requests` state that every request of the two steps names `USART_ISR`, `USART_RDR`, or `USART_TDR`, and `echo_confined` and `gw_confined` that every access of the initialization lies in the register blocks of RCC, GPIOD, or USART3 and every access of the windows is an access of one of the three registers.  The assumption about the device therefore concerns those registers alone.  On QEMU, `echo_qemu` of `tests/TestSupport/M7/QemuFile.lean` and `gw_qemu` of `tests/TestSupport/M7/GwQemuFile.lean` state the same loop over `echo-cmsdk-qemu.bin` and `gateway-cmsdk-qemu.bin`, for every code map that holds the file's bytes from address 0 and every state that reset gives from the table at 0, with UART0's two writes in place of the board's initialization and the windows of `cmsdkTick` and `gwTick`.

The board's theorems hold of the processor under the conditions of the model, which the headers of `LeanExe/M7/Proof/Board.lean` and of the theorem files state: (a) a power-on reset with BOOT0 low and BOOT_ADD0 `0x0080`; (b) software watchdogs, which this board's option bytes select (OPTCR reads 0xFFFFAAFD, with IWDG_SW and WWDG_SW set), so that no watchdog runs; and (c) no interrupt, NMI, debug halt, debugger access, or DMA during the run.  A reset over SWD with the probe attached does not meet them, since the probe leaves DHCSR's C_DEBUGEN and DEMCR set, which the model does not track.  The flash must hold the file, which `st-flash write` puts there and a read-back compares.

## Validating the model against the processor

### The Isla check

No machine-readable specification of the M-profile is public, so the check compares each form of the model with Isla's trace of the form in Arm's A-profile specification in AArch32 Thumb state, where the forms have the same T32 encodings.  [The AArch64 document's Isla section](a64-bare-metal.md#isla) describes Isla, the Sail model that Arm's ASL generates, and the trace language.  A theorem covers every operand value and every value of the opcode's fields where tests cover samples, and it establishes the form's decoding, operand selection, register writes, flags, program counter, and memory and device accesses as the A-profile ASL defines them.  It establishes nothing about the M-profile, whose PSTATE, register banking, memory system, and exceptions differ, so a reading of each form's M-profile pseudocode against its A-profile pseudocode joins the trusted base.

`tests/isla/armv9p4-t32.diff` edits the IR of the Armv9.4 snapshot that the AArch64 check uses, `armv9p4-checked.ir`, in two ways.  It appends the harness functions `isla_footprint_t32` and `isla_footprint_t16`, which do for a 32-bit and a 16-bit Thumb opcode what Isla's `isla_footprint_no_init` does for an A64 opcode, with the decode retried once after an SEE exception as the Sail model's fetch loop does, and with `__currentCond` set to `__DefaultCond`, AL outside an IT block.  It also edits the decode clause of B T3 (`instrs32.sail` lines 1478 to 1487) to write the opcode's `cond` field to `__currentCond`, the condition that `CurrentCond()` of DDI 0403E.e section A7.3.1 gives, since Arm's ASL declares `AArch32.CurrentCond` without defining it and the Sail model's fetch loop supplies AL.  `tests/isla/armv9p4-t32-udiv.diff` edits a copy for UDIV, whose quotient the specification computes by dividing real numbers, which Isla does not implement, so that it divides integers with truncation, as the AArch64 check's edit does for its UDIV.

`tests/isla/m7-traces.sh` writes each form's opcode with the top bit of each register field 0 and the other three bits symbolic, so a field ranges over r0 to r7, and with every other field symbolic.  CLZ's two Rm fields, UMULL's distinct destinations, and B T3's conditions 0 to 13 enter as constraints, which the traces record as `assume` events and the theorems carry as premises.  The processor runs in AArch32 User mode at EL0 under an AArch64 EL1, in Thumb state outside an IT block with little-endian data, with the features and the EL2, EL3, and debug controls of the AArch64 check's TCG profile.  The loads and stores run under the stage 1 translation of the EL1&0 regime with VMSAv8-64 tables: TCR_EL1 `0x180a03520` gives a 32-bit input range with one level-1 descriptor for each GiB, TTBR0_EL1 holds `0x100000000`, above every address of the M7, MAIR_EL1 is `0xff00`, and SCTLR_EL1 is `0x30d0198d`.  Isla's `--fixed-memory` answers the walk with `0x745`, a block of the GiB from 0 as Normal write-back memory, and `0x0060000040000441`, a block of the GiB from `0x40000000` as Device-nGnRnE memory, both read-write at EL0, and a constraint keeps each access word-aligned and inside DTCM, `0x20000000` to `0x2001fffc`, or inside the device window, `0x40000000` to `0x4003fffc`.

The 41 traces in `tests/isla/m7`, one for each of the 33 forms without a memory access, one each for `LDR.W` and `STR.W` with a register base in DTCM and in the device window, and one for each of the four forms at SP, take about 4 s and 1 GB each, and CLZ's takes 6 s and 1.75 GB.  They are reproducible up to the order in which Isla prints the fields of a struct, which it keeps in a hash map with a random seed, and the reader drops the fields whose order varies.  Each register write in a trace forks once, on the fresh Boolean of `v8_base.sail` lines 13989 to 13993 that chooses between clearing bits 63 to 32 of the X register and keeping them.

`LeanExe/M7/Isla/Trace.lean` reuses the syntax, values, operators, and reader of the AArch64 check and defines a semantics over `Mach`: the model's state, bits 63 to 32 of X0 to X14, X15 to X30, and the bytes of memory from 2^32 up, where the translation table lies.  In User mode r0 to r12, SP, and LR are bits 31 to 0 of X0 to X14, `_PC` is the model's program counter zero-extended, and the flags of `PSTATE` are the model's, while every other register lies in a register state `σ` outside the model.  At the end of a path the program counter advances by the opcode's length while `__BranchTaken` is false, and a path ends in `fail` when the program counter would reach 2^32.  A read or write of 4 bytes at an address below 2^32 that the platform names a device address is a device access, which takes the next value of the device sequence or appends a write event, and every other access reads or writes the bytes of memory, since a trace's memory event carries no memory type.

`Agrees` in `LeanExe/M7/Isla/Check.lean` states, for one value of a form's fields and one machine, that the opcode's halfwords decode to the instruction with the opcode's length, and that for every register state `σ` that agrees with the profile on the registers outside the model that the trace reads, whenever `exec` gives a state `s'`, every outcome of the trace is the machine with `s'` and some high words of X0 to X14, one outcome keeps the machine's high words, and the registers outside the model change only at a listed set.  The high words appear only as an existential, since the A-profile model writes an AArch32 register with bits 63 to 32 cleared or kept, a choice that it leaves to the fresh Boolean.  The profile `sys u` of `LeanExe/M7/Isla/Profile.lean` gives the values of the registers that the configuration sets and leaves the others to `u`, and each theorem holds for every `u`, every platform, every device sequence, and every machine and field value that meet its premises.

| Register operands | Only the PC is UNPREDICTABLE in these forms' register fields | SP is also UNPREDICTABLE in most fields (A7.7.2, A7.7.4, A7.7.195) | Register fields name r0 to r7 |
| Reads of SP | All 32 bits of SP_usr, X13 | `SP<31:2>:'00'` (B1.4.7) | SP's bits 1 and 0 stay 0, and the theorems at SP take SP and the offset as multiples of 4 |
| Writes of SP | The value unmasked | The value with bits 1 and 0 cleared (B1.4.7) | The model masks, and the theorems of `ADDW SP, SP` and `SUBW SP, SP` take a result that is a multiple of 4 |
| SP banking | Banked by mode | SP_main or SP_process by `CONTROL.SPSEL` in Thread mode, SP_main after reset (B1.4.1, B1.5.5) | One SP, SP_main, since the program writes no `CONTROL` |
| `UDIV` by 0 | 0, with no trap | A UsageFault when `CCR.DIV_0_TRP` is 1, and 0 otherwise (A7.7.195) | The model stops |
| `BX LR` with bit 0 clear | The A32 state, with a CONSTRAINED UNPREDICTABLE choice on bit 1 | An INVSTATE UsageFault on the next instruction, and an exception return in Handler mode for bits 31 to 28 all set (A2.3.1, A7.7.20) | Thread mode only, and the model stops |
| `B<cond>.W` | `ConditionPassed()` on `__currentCond`, which the Sail model's fetch loop sets to AL | `CurrentCond()` gives the `cond` field (A7.3.1) | The IR edit writes the `cond` field, and `exec` tests the field |
| Branch targets | `BranchWritePC` clears bit 0 | The same (A2.3.1) | The theorems of branches take an even program counter |
| Loads and stores | `MemU` through the VMSAv8-64 translation, with endianness from `PSTATE.E` | `MemU` through the MPU or the default memory map, with `CCR.UNALIGN_TRP` and endianness from `AIRCR.ENDIANNESS` (A3.2.1, A7.7.43, A7.7.161) | Aligned words in Normal memory or in the device window only |
| `DSB SY` | A barrier event, which the reader takes as a step without effect | `DataSynchronizationBarrier` (A7.7.34) | A step to the next instruction |

### Co-simulation

`tests/baremetal/m7-cosim.sh SEED PER_FORM DIV` runs the model against QEMU 8.2.2's `mps2-an500`.  Lean writes an assembly harness of `PER_FORM` cases of each form from SplitMix64: a case sets r0 to r12 and LR to boundary values or random words, SP to such a word with bits 1 and 0 clear, the flags to random bits, and a window of 64 bytes to random bytes, and it runs one instruction with random fields.  A load or store gets a base that puts its word-aligned access inside the window, a shift by a register an amount below 64, at 32, at 255, or random, `UDIV` a nonzero divisor, and a branch a target among the 16 words on each side of the instruction.  The harness saves the state in floating-point registers, so it runs under the C path's startup code for `mps2-an500`, with the floating-point unit and the MPU enabled, and a C printer that CompCert compiles writes each case's state before and after.  `DIV` adds calls of `udivmod64`: every boundary dividend 0, 1, 2^32 − 1, 2^32, 2^63, and 2^64 − 1 with every nonzero boundary divisor, and `DIV` random pairs that reach every path and every number of the loop's passes.  Fixed cases follow, with the classes of immediate field values, offsets, conditions, and branch directions that the generator and `udivmod64` emit, among them `MOVW` and `MOVT` of the area's header, memory, and end, loads and stores at a register plus 0 and 4,092, `ADD` without a shift, and `BHI` and `BCS` taken and not taken.  The checker runs the model from each printed state and compares its result with QEMU's, and for a division it also compares the result words with Lean's `/` and `%` and the number of instructions with the path's count: runs of 89,739 instruction cases, of 39,429 instruction cases with 52,360 division cases, and of 7,868 instruction cases, 68 of them fixed, with 330 division cases, all agree.

`m7-board.sh cosim-image`, `cosim`, and `cosim-check` run the model's forms on the board in the configuration of the proved runs.  `tests/TestSupport/M7/BoardCosim.lean` writes an image that boots from the same 936 bytes of table, self-loop, and initialization as `echo.bin` and `gateway.bin`, with no startup code, floating-point unit, or MPU, so each case runs in Thread mode on SP_main at reset clocking with the caches off.  Each case comes from the QEMU harness's generator, with the window at DTCM's base, and two further forms load from and store to `USART_RTOR` at `0x40004814`, a register of 32 bits that reads back as written and that changes neither the transmitter nor the receiver while the receiver's timeout is disabled.  The harness keeps the output record's address in r12, which no form of the model names, and it uses encodings outside the model, `MSR APSR_nzcvq`, `MRS`, `BX r0`, `NOP`, and loads and stores with r12 as the base, which the GNU assembler assembles to the image's halfwords.  `st-flash` reads the results from DTCM over SWD, and the checker regenerates each case's inputs, runs `exec` with the board's platform, and compares r0 to r12, SP, LR, the flags, the landing address, the window's bytes, and `USART_RTOR`'s value.  DTCM holds the results of 963 cases, and fixed cases follow the seeded ones with every class of immediate field value that the generator and `udivmod64` emit, among them the shifts by 16 and by 1, the frame sizes 8 and 4,088, and the SP offsets 0 and 4,092.

| Run on the board | Cases | Result |
|---|---|---|
| Seed 1, 23 cases of each of the 41 forms | 943 | All agree |
| Seed 2, 23 cases of each form | 943 | All agree |
| Seed 1, 22 cases of each form and the 56 fixed cases | 958 | All agree |
| Each run's results against the model with `ADC`'s carry in replaced by 0 | 943, 943, and 958 | Exactly the `ADC` cases with C set differ: 10, 8, and 9 of them |

`USART_RTOR` read back every value written, so the device forms agree with the model in the address, the value loaded, and the value stored.  The processor cleared bits 1 and 0 of each result of `ADDW SP, SP` and `SUBW SP, SP` with an offset that is not a multiple of 4, as the model does, and the cases include shifts by a register of 32 or more and conditional branches with random flags in both directions.  In Renode the same image runs to its end, and every difference lies in bits 24 to 31 of `USART_RTOR`, which Renode's model does not store.  The board's cases test the Cortex-M7 r1p0 only in the states in which the model runs, with branches within 16 words, and they do not test longer branches, which rest on `decode_encode` and the GNU assembler, the self-loop and the trap stubs, which branch to themselves, or device registers other than `USART_RTOR`.  The runs follow a reset over SWD, and the read of the results is a debugger access, so they lie outside the theorems' run conditions.

### The programs on QEMU, in Renode, and on the board

`tests/baremetal/m7-qemu.sh` runs the QEMU images after their kernel checks, with UART0 on a socket.  `tests/baremetal/uart_echo.py` sent the echo 644 bytes in lockstep, bursts of 2, 16, 322, and 65,536 bytes, and 65,536 held bytes, and every reply was the byte sent with bit 5 flipped.  `tests/baremetal/uart_gateway.py` simulated 10,080 ticks of the plant for the gateway, with 715 commands and 17 fallback requests, and `native-bare gateway-run` gave output records equal to QEMU's on the same input records.  `m7-qemu.sh crc` runs the image of the CRC-32 step `crcCmsdkTick` of `tests/TestSupport/M7/Crc.lean`, which no theorem covers and whose test code sets up the area (`tests/TestSupport/M7/CrcImages.lean`), and `tests/baremetal/uart_crc.py` sent it 132,620 bytes in lockstep, in bursts, and held, and every reply was the low byte of `zlib.crc32` of the bytes sent so far.

`m7-board.sh emulate` runs the board's images in Renode 1.17.0, with a memory of the flash's size added at `0x00200000` and VTOR set there, since Renode's model of the board maps the flash at `0x08000000` alone.  The echo passed with at most 2 bytes unanswered, and the gateway's output records over 5 and over 60 ticks equaled native Lean's.  Renode's USART3 always reports `TXE` set and models no time, so these runs test the programs and the protocol and not the board's timing.

On the board, `m7-board.sh run` writes an image with `st-flash`, compares the flash read back with the file, resets the board, and plays the far end through the ST-LINK's virtual COM port, and `m7-board.sh host` plays the far end without `st-flash`, for a run from the power-on reset of a replug.  The echo passed with 644 bytes in lockstep and the four bursts, with at most 2 bytes unanswered, in about 170 s, after a reset over SWD and after a power-on with no SWD session.  The gateway passed a simulated day of 1,440 ticks in 579.4 s, with 94 commands, 4 fallback requests, and 1,342 ticks without output, the counts of the C path's run of the same day, after a reset over SWD and after a power-on with no SWD session.  `USART_ISR` read 0x006210D0 after each of the gateway's runs, with `ORE` clear, so no byte arrived while `RXNE` was set, and `m7-board.sh compare` found the output records equal to native Lean's.  `m7-board.sh measure-div` checked 60 calls of `udivmod64` on the board against Python's integer division.

The SHA-256 step `shaUsart3Tick` of `tests/TestSupport/M7/Sha.lean`, and `shaCmsdkTick` for UART0, hash the bytes that they receive in blocks of 64 and answer each block with 32 bytes, the SHA-256 digest of every byte received so far.  The state of 19 words holds the phase, a byte count, the number of blocks, the chaining value, and a buffer of 64 bytes that a shift by one byte fills on input and empties on output, and the window of a block's last byte runs `compress` of `Library/Hashing/Sha256/Program.lean` over the block and over the padding block of a message of that many blocks.  The round constants lie in linear memory, whose area the images' test code sets up as for CRC-32 (`tests/TestSupport/M7/ShaImages.lean`), and no theorem covers the images, since the simulation does not cover the loop of `compress`.  The generator's frames take 1,136 bytes for the step, which names 80 of its 282 declared locals, and 808 for `compress`, and `stackBound` gives 2,472 bytes.  `tests/baremetal/uart_sha.py` compares each answer with `hashlib.sha256` of the bytes sent.  Under QEMU, `m7-qemu.sh sha` passed 128 blocks in lockstep, 64 blocks sent ahead, and 16 blocks held until the transmitter waited, and in Renode and on the board, `m7-board.sh emulate sha` and `run sha DEVICE` passed 64 blocks in lockstep, the board's in 13.7 s after a reset over SWD, with `ORE` clear afterwards.  The step's protocol requires the host to send a block only after it has read the whole answer to the block before, since USART3 holds one byte and would overrun during the window of a block's last byte.

## Timing

At 16 MHz a byte at 4,800 baud lasts 33,333 cycles, and the program reads a received byte in two windows, a status read that sees `RXNE` and the read of `USART_RDR`, so each window that runs while bytes may arrive must end within about 16,667 cycles, half a byte time.  USART3 holds one received byte and the virtual COM port has no flow control, so a slower window would lose a byte, and the framing does not resynchronize.  Arm publishes no instruction timing for the Cortex-M7, so the margins rest on measurements, and no proof bounds a window's time.

`m7-windows run` runs a generated program in the model with a far end that answers the UART's registers and counts the instructions of every kind of window.  The echo's windows take 318 to 515 instructions and the gateway's windows that run while bytes may arrive 2,500 to 3,700, while the gateway's tick, the window after a record's last byte, took 11,614 to 29,962 over a simulated day, each count without the instructions of `udivmod64`.  `m7-windows static` computes the longest path through each function, which has no backward branch: 499 instructions for the echo's step and 30,007 for the gateway's, on a path with two calls of `udivmod64`, whose instructions the count omits.  The CRC-32 step's windows take 337 to 612 instructions, the longest the window of a received byte with its two loads from the table, and its step's longest path is 597 instructions.  The SHA-256 step's code has the backward branch of `compress`'s loop, so `static` fails on it, and `run` gives its counts, every window of a kind taking the same number: 1,120 and 1,121 for the status reads before a byte, 1,871 for a received byte, the longest of the windows that run while bytes may arrive, 1,492 to 2,157 for the windows of the answer, and 251,576 for the window of a block's last byte, which runs only while the host waits for the answer.

The measurement images of `tests/TestSupport/M7/Dwt.lean` differ from the proved images by a routine at the loop's head that records the cycles from its previous exit in a table indexed by the kind of window, so that each interval holds five instructions of that routine, and no theorem covers them.  They enable `DWT_CYCCNT` alone, since erratum 486321 miscounts stall cycles in the other counters, and they run from the ITCM address at reset clocking with the caches off, as the proved images do.  The echo's windows took 320 to 583 cycles with those five instructions, and with the 8 of `udivmod64` in a `tx` window, about one cycle an instruction.

## Limits

The simulation covers the forms of the functions that the echo's and the gateway's steps reach, and the generator emits further forms, among them `br`, `br_if`, `return`, `block`, `loop`, `local.tee`, and the `i32` operations, that no proof covers, so a program with those forms fails the kernel's check of `reachCovered`.  The generator rejects floating point and a memory of more than one page, so no program with a float or a larger memory has an image, no theorem covers a program with an area, and every program is a program with requests whose step takes and returns `i64` words.  A frame must keep every offset from SP within 4,095 bytes, and an image runs only at the addresses for which it was generated.

The Isla check establishes each form's behavior in the A-profile's AArch32 Thumb state, and the M-profile's behavior rests on the reading of the two pseudocodes, which no proof covers.  The check takes the configuration's descriptors and the platform's division of addresses into Normal and Device memory as given.  Co-simulation covers sampled states on QEMU's implementation and on one board's Cortex-M7 r1p0, with branches within 16 words, and its runs on the board follow a reset over SWD.

No proof bounds time, and the board's margins rest on cycle measurements under the conditions of the runs.  The theorems assume a power-on reset and no debugger during the run, which the echo's and the gateway's runs from a power-on meet and the other board runs do not.  In some sessions the ST-LINK's virtual COM port of the test board stopped passing the board's output to the host, while the host's bytes still reached the board and the board kept answering, and a USB reset of the ST-LINK or a replug of its cable restored it.  Whether the probe's firmware V2J39M27 or the USB passthrough of the test host's virtual machine causes the failure is not established.
