# Trusted base

This document lists, for each kind of artifact, what its theorem depends on without proof, how the project checks each item, and where each item is stated.  The codes of the sections are those of [the README's artifact table](../README.md#artifacts) and [the algorithm index](../index.md).  A theorem's conclusion holds of a running artifact only if every item of the artifact's section, and every item of [the shared components](#shared-components), does what its table says.  A row marked "Not trusted" names a part that a check of each build or a kernel-checked step removes from the trusted base.  [The definitions that statements reach](#definitions-that-statements-reach) lists the definitions whose meaning a reader of a theorem must accept, and the manuals that each row cites give the detail.

## Shared components

Every theorem depends on Lean's kernel and on the core definitions that give a Lean program its meaning.  The generators that produce programs, proofs, encodings, and translations run as meta code outside the trusted base, and the kernel checks what they produce.  The kernel of the pinned toolchain rejects the reproduction of the recorded kernel defect, and no independent kernel has checked the proofs, which is the open question of this layer.

## V: WebAssembly modules of the verified compiler

Code V's theorems are the compiler's generated theorems, such as `compiled.gcd.implements`, `compiled.gcd.trapFree`, and `compiled.bytes`, and the call theorems composed from them, in Talos's semantics. The universal theorem `Prog.correctStaticWith` and the reflector's meaning equations are kernel-checked, so neither the compiler nor the reflector is trusted.

## G: WGSL kernels

Code G's dispatch theorems state that a dispatch writes the Lean function's result and that distinct invocations store to distinct words, in `Module.dispatch`, a sequential semantics that runs the invocations one after another.  `Dispatch.executions` derives from such a theorem that every consistent execution of the dispatch, under a Lean statement of the parts of the Vulkan memory model that the kernels use, has every invocation end, has no data race, and leaves the same output words, and `Dispatch.execution_exists` shows that a consistent execution exists.  WGSL 14.5 adopts the Vulkan memory model.  The trusted items are the event semantics of one invocation, the assumption that no invocation on the device runs past a point where that semantics stops, the statement of the memory model, the guarantees of WebGPU and its implementations that the statement uses, the compiled shader, the GPU's arithmetic, and the driver, device, and host.  The printer is not trusted, because a proved parser inverts it and the emitter checks the printed text.

| Item | What is trusted | How it is checked | Source |
|---|---|---|---|
| Invocation semantics | `Module.invokeE` runs an invocation's statements as WGSL does, with operands evaluated in WGSL's order, a read of a buffer word returning the value an oracle gives, and each store recorded as a write.  An invocation on the device performs the accesses of `Module.invokeE` up to the point where it stops: an access outside a buffer, a read of the output, an ill-typed operation, or a loop past `loopBound` tests. | `Module.invokeE_input` proves that with the initial words as read values it computes `Module.invoke`, and the tests compare output words with native Lean | `LeanExe/WGSL/Events.lean` |

With the input words as read values every invocation ends, so an invocation on the device can run past a stop only after a read returns a value other than the input word.  The queue order and the memory model exclude the writes before and after the dispatch as the source of that value, and an invocation that has not run past a stop stores only to the output, so the value comes from a store of an invocation that ran past a stop.  Each departure therefore depends on a value that a departure produced, and in a finite execution these dependencies form a cycle.  WGSL 2.2 restricts the accesses after a dynamic error, such as an access outside a buffer, to the module's bound resources, but leaves the program's behavior unspecified and allows non-local effects, so neither WGSL nor the Vulkan memory model excludes such a cycle.

## P: PTX kernels

Code P's launch theorems state that in every consistent execution of a launch, under a Lean statement of the PTX memory model, no access of a thread is in a data race and the copy back reads the output of a sequential run of the threads, and that a consistent execution exists.  `Launch.executions` proves this for every race-free launch whose sequential run ends, and `addOne_executions` gives the output of the add-one kernel: the length followed by each input word plus one.  The trusted items are the meaning of the PTX subset, the assumption that no thread on the device runs past a point where that meaning stops, the statement of the memory model, the readings of the PTX ISA that give the edges of its causality order, the compiler that turns the text into machine code, and the driver and device.  The printer is not trusted, because a proved parser inverts it and the emitter checks the printed text.

| Item | What is trusted | How it is checked | Source |
|---|---|---|---|
| Thread semantics | `Stmt.exec` runs a thread's statements as PTX does.  A guard that does not hold leaves the instruction without effect (PTX ISA 9.3).  The printed labels and branches of `ite` and `while` mean the structured forms.  A shift by 64 or more gives 0.  `ld.param` of parameter `j` gives the address of buffer `j`, which the launch writes before the kernel starts and nothing writes during it, and `cvta.to.global.u64` keeps that address.  Buffers are disjoint allocations aligned to 8 bytes.  A thread on the device performs the accesses of `Stmt.exec` up to the point where it stops. | Tests on the GB10 compare output words with native Lean | `LeanExe/PTX/Semantics.lean` |

| No thread runs past a stop | In every execution on the device, each thread's memory operations are those of `Stmt.exec` for some oracle, so no thread runs past a point where `Stmt.exec` stops, such as an access outside a buffer. With the input words as load values every thread ends, so a thread on the device can run past a stop only after a load returns a value other than the input word.  Coherence and causality exclude the writes before and after the kernel as the source of that value, and a thread that has not run past a stop stores only to the output, so the value comes from a store of a thread that ran past a stop.  Each departure therefore depends, through instruction dependencies and reads-from, on a value that a departure produced, and in a finite execution these dependencies form a cycle.  No Thin Air forbids such a cycle, as its LB+deps litmus test shows.  The ISA states that axiom in prose and by litmus tests, without a formal definition.

## Specifications

A specification theorem states a property of a Lean function or of a module, and its meaning depends on the definitions of its specification.  The hashing theorems equate a program with a transcription of a standard, the numerical theorems bound a result against a real function through a rounding reference, and the application theorems state properties that the project defines.  Each of these definitions is trusted to say what its name says, and the vector checks compare the transcriptions with published vectors and reference outputs.
