# Verified compiler: WASI Preview 1 design

## Scope and sources

The verified compiler's WASI modules import the stream imports `fd_read`, `fd_write`, and `proc_exit` of `wasi_snapshot_preview1` for the standard streams and exit, and the flat calls of the pinned witx that a program uses.  A program reaches a descriptor other than the standard streams only as the preopened directory or through `withOpen`.  The Linux shim implements the stream imports and the flat calls of `shimCalls` with Linux system calls, and the AArch64 back end writes a command as a static Linux executable whose stubs implement the shim.  [The WASI manual](wasi.md) describes the public API, the generated declarations, the theorems, and the tests, and [the AArch64 document](a64-bare-metal.md#wasi-commands) the executables.  This document records the memory layout, the semantics and host assumptions, the structure of the proofs, and the decisions behind them.

The specification pin is WebAssembly/WASI commit `fae981bae14809d91f9bc2d63852d461f331d161`.  Its [interface definitions](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/preview1/witx/wasi_snapshot_preview1.witx), [type definitions](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/preview1/witx/typenames.witx), [generated reference](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/preview1/docs.md), and [application ABI](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/application-abi.md) are the external references.  `tests/wasi/witx/` holds the pinned witx files, from which `tools/wasi-calls.py` generates the descriptions of the flat calls.  A change of the pin requires review of the ABI, the generated descriptions, the host assumptions, and the proof statements.

The [pure typed source](../Verified/Source.lean) has value semantics.  Its [compiler](../Verified/Compile.lean) emits an import-free module, and its [runtime predicate](../Verified/RuntimeFacts.lean) requires that layout.  The [pure correctness theorem](../Verified/Correct.lean) and [representation API](../LeanExe/Pipeline/Implements.lean) use `Store Unit`.  [The effect language](../Verified/Wasi/Source.lean) embeds these pure expressions, and [its compiler theorem](../Verified/Wasi/Correct.lean) relates them to host-dependent execution through import relocation and host-state transport.

## Lean API and behavior

### Actions and results

The public namespace is `LeanExe.Wasi`, and [the manual's operations](wasi.md#operations-and-results) give its API.  [The native import](../LeanExe/Wasi.lean) supplies actions and their interpreter independently of the verified compiler, and the shared byte type is `LeanExe.Bytes`, with [its native operations](../LeanExe/Dialect/Bytes.lean).  Compiler representations and proofs are under `Verified`, and [the compiler import](../Verified/Wasi.lean) supplies `verified_compile_wasi`.

`Action α` is a semantic monad with Lean `pure` and `bind` instances, whose constructors are a returned value, the stream read and write, exit, `loop`, and `sys` for a flat call.  Reflection proves a program's correspondence with checked equations for `pure` and `bind`, with no correspondence for opaque `BaseIO` primitives, as [the review decisions](#review-decisions) choose.  Error results are ordinary values, so the source program determines whether to return, exit, continue, or report an error.

Native action descriptions and continuations can be constructed as the native interpreter runs.  Reflection translates accepted definitions into fixed typed code and performs no guest I/O.  Compiled runtime values have the compiler's value types, including bytes and result records.  The host world is part of the semantics and host state rather than the source program's arguments.

`loop` is a command-description node whose callbacks are statically known code, reflected with their captured values.  The native interpreter executes the loop, and the compiler emits a structured Wasm loop.  The proof uses natural indices, while the compiled counter stays in `UInt64` and reaches `count` without wrapping.

An effectful helper may return `Unit`.  Its result occupies zero Wasm slots, and a checked equation erases its unused result binding.  [The result descriptor](../Verified/Wasi/Source.lean) and [result adapters](../Verified/Wasi/Results.lean) cover `Unit` and accepted value types.

### Reads, writes, and exit

The read and write wrappers make at most one import call each and perform no retries, so a program sees every short transfer and every errno, as [the manual's operations](wasi.md#operations-and-results) state.  Neither allocates.  The read wrapper takes the address and the length of a window of a buffer that the command computes.  The write wrapper takes the buffer's root and size and the window's start and count, computes the window's address and length with the code of a flat call's window, and writes the window in place, so a write command emits only the pushes of its four words and the call.  The read wrapper returns the errno and, on errno 0, the count, and it ignores a count that the host leaves in guest memory with an errno.  The read command takes its buffer as a `sys` command takes its buffer, through `wp_take_with`, and after an errno it stores 0 into the window, with the zero fill of the flat calls.  `Exec.read_return` gives the read's continuation the bytes of the window after the call, its range, which begin with the bytes read and are otherwise free, and the compiler's proof `wp_read_fill_with` takes the bytes of memory there as the range.

`readAll limit` is a definition over the stream actions, a `loop` of `limit + 2` passes of a read of capacity 4,096, which unfolds to one `loop` node whatever the limit.  The kernel's checks of a reflected program that uses it therefore stay small, and `Action`, `Exec`, and the host assumptions need no rule of their own for it.  A recursion on a fuel of `limit + 2` reads has the same meaning, but the kernel's check of a generated command theorem unfolds it once per unit of fuel and exceeds its recursion depth at a limit of 10,000.  The compiler compiles it with a command of its own, as [the typed commands](#typed-commands-and-reflection) describe.

A write error returns a count of zero as a sentinel, so `count` describes transferred bytes only when `errno = 0`, and an empty write still calls `fd_write`, so host errors are observable.  `exit` and a returned command status pass `code mod 2^32` to `proc_exit`, which defines the import argument for every `UInt64` input.  The raw status of an accepted exit is separate from its operating-system process status.

### Flat calls and handles

A flat call is one `Action.sys call args next` node, whose `call` is a description generated from the witx and whose reply carries the errno and the content of each region that the call shows.  One node for every call keeps `Exec`, `Prefix`, the host relation, and the compiler's command rule independent of the call, and one generator writes the descriptions, the typed functions, and their reflection equations, which a second lowering of the witx checks.  `Call.reject` rejects before the call an argument that does not fit its core type or that lies outside its enum or flags, since Wasmtime 44 traps on an enum or flags argument outside its type.  The descriptions pass arrays of iovecs with one element, since Wasmtime 44 reads into and writes from only the first non-empty element.  [The flat calls](wasi.md#flat-preview-1-calls) and [the nested calls](wasi.md#nested-calls) give the API.

Apart from the standard streams, which the stream imports use, a program obtains a descriptor only as `Handle.preopened`, descriptor 3, or as the handle that `withOpen` binds for the extent of its body.  `withOpen` follows a successful `path_open` with an `fd_close` when the body returns, and the handle check, which the kernel decides for each program, refuses `path_open`, `fd_close`, and `fd_renumber` outside that shape and every handle argument that is not a bracket's handle or 3.  A program therefore never renumbers a descriptor, and under the host assumption `LeanExe.Wasi.FreshOpens` it closes only descriptors that its brackets opened, never 0 to 3, and each use of a bracket's handle names the descriptor that the bracket opened.  [The handles](wasi.md#handles) state the theorems.

### Byte operations

`Bytes` is an immutable value whose Lean meaning is a packed byte sequence, and [the manual's packed bytes](wasi.md#packed-bytes) give its API.  The logical length uses `Nat` where Lean's byte-sequence definitions require it, while compiled counters, comparisons, API arguments, and returned lengths use `UInt64`, and reflection proves their correspondence under the memory bound.  [Byte access](../Verified/Bytes/Get.lean) and [construction](../Verified/AlignedBytes.lean) have universal correctness rules.  Intermediate `UInt8` conversions in those rules do not require a general `UInt8` arithmetic dialect.

`ReadResult` flattens to an errno word and one byte value, `FillResult` to two words and one byte value, and `WriteResult` is scalar.  The accepted field representation includes `Bytes`, so these records supply the operation results without extending sums to arbitrary heap-valued fields.  The result structures of the flat calls flatten the same way, to their errno, their words, and at most one byte value.

The compiler keeps a nonempty literal's constant bytes in a protected data segment, and each evaluation copies them into an owned allocation.  Literal data stays protected across calls.  Construction contributes its allocation and copy cost to the charges.

## Packed memory and the WASI ABI

### Byte ownership

A represented byte value has two Wasm values: a `UInt64` allocation-root pointer `p` and a `UInt64` logical length `n`.  Bytes begin at `p` and occupy consecutive addresses.  A nonzero root has the runtime's 48-byte header, count one, capacity at least `max(8, n)`, kind two, width one, and child mask zero, and its full allocated region is included in separation and ownership.  [The byte representation](../Verified/Bytes/Basic.lean) states these fields and bounds.

New empty results use `(0, 0)`.  Incoming owned and borrowed empty values may also have a valid allocated root of length zero, as the host allocator gives.  Cleanup tests the root and releases a nonzero owned root once.  Borrowed-byte separation and frame predicates protect the allocation header and capacity even when the logical length is zero.  A byte value exposes its allocation root and length through the representation API, while source code operates on `Bytes`.

The compiler's mode and lifetime analysis applies the ownership rules of [the manual's packed bytes](wasi.md#packed-bytes) to bytes as to arrays.  Result construction, branch cleanup, unused results, and effectful helper returns have the separation and last-use obligations of arrays, and converting a borrowed byte value to an owned result copies its bytes.  [Owned copying](../Verified/AlignedBytes.lean) and [release](../Verified/Bytes/Release.lean) prove preservation of the caller's retained regions.

The [execution host](../tools/wasmtime-host.c) allocates raw packed bytes and passes byte values as pointer and length.  [The representation instance](../LeanExe/Pipeline/Bytes.lean) relates that ABI to owned and borrowed source bytes, and host execution tests check the external allocator and argument handling.  A read of stdin and a flat call with an output buffer take a buffer that the program passes, the host writes its bytes into a window of that buffer's block, and the result holds the block with its size unchanged.  After an errno the code sets the window's bytes to 0 and keeps the block.  No read, write, or flat call with a buffer allocates or releases a block, and a window of length 0 gives the host an empty writable range.

### Imports and scratch

All imports use the module name `wasi_snapshot_preview1`.  A module with `c` flat calls imports the stream imports at function indices 0 to 2 and the calls of `p.sysCalls` after them, with the signatures of the table.  The relocation of pure code and the indices of the defined functions follow from this order, as [pure code in an importing module](#pure-code-in-an-importing-module) describes.

| Function index | Import | Signature |
|---|---|---|
| 0 | `fd_read` | `(i32, i32, i32, i32) → i32` |
| 1 | `fd_write` | `(i32, i32, i32, i32) → i32` |
| 2 | `proc_exit` | `(i32) → ()` |
| `3 + i`, for `i < c` | The flat call `i` of `p.sysCalls` | `ABI.callType`: the core types of its parameters, then an `i32` errno |

For read and write the arguments are the fixed fd, the iovec pointer, one iovec, and the result-count pointer.  An iovec consists of a 32-bit buffer pointer and 32-bit byte count, and the count result occupies four bytes.  The wrapper zero-extends successful counts and errnos into `UInt64` values, and valid errno results are a host-ABI premise.  A flat call's parameters lower by `ABI.paramTypes`: one `i32` for a 32-bit value, a descriptor, an enum, 32-bit flags, or a pointer to a result, a reported region, or a record, one `i64` for a 64-bit value or 64-bit flags, a pointer and a length for an input, an output, or an iovec array, and two pointers and a count for subscriptions.

The command's scratch bytes are `[0, 16)`: the iovec at bytes 0 through 7, the count at bytes 8 through 11, and four padding bytes.  The wrapper initializes its metadata and count before calling the host.  A flat call uses the same bytes for the element of its iovec array and for its result words, at scratch addresses 0 and 8.  A record call places its record, and a `poll` call its subscriptions and the events after them, in the call area `[16, 176)`, `ABI.callArea`, and `callFits` admits a call whose record or subscriptions and events fit there at their alignment.  Constant arrays begin at 4096, byte literals follow them, and the allocator starts after the static data, so no value of a program lies in the low memory `[0, 4096)`, `ABI.low`, which holds the scratch bytes and the call area.  The compiler's invariant keeps every live region apart from the low memory, and a callable export requires the same of every region that an argument reads.

The layout preserves the pure program's constant-array addresses and places raw byte-literal data after those arrays.  The initial bump pointer starts beyond all static data, aligned to eight bytes, and the initial-memory proof includes that data and the page cap.  These arrays occupy linear memory, and the application ABI's function table is a separate Wasm resource.

Before narrowing a nonempty byte range, the proof establishes `p < 2^32`, `n < 2^32`, and `p + n` within the active memory and its cap.  Heap and representation bounds justify the narrowing of a window's address and length.  Empty pointer zero with length zero is a valid range.  Host count results are read only on success, and the host assumptions bound them by the requested range.

The memory frame of a read excludes the command's scratch bytes and the window, that of `readAll` the scratch bytes and its buffer's unused tail, and that of a write only the scratch bytes.  A flat call's frame excludes its output regions.  The host preserves allocator headers, globals, tables, memory caps, and every other guest region, and it returns control without invoking another guest export.  Calls into an instance are serialized.  These conditions make one reservation of the scratch bytes and the call area sufficient across repeated calls and separate instances.

## Observable semantics and host assumptions

[The trusted-base document](trusted-base.md#wasi-wasi-preview-1-modules) lists the host assumptions of the WASI theorems, with the check and the source of each.  It names the definitions of the Preview 1 model that a statement unfolds to and the theorems that state when a satisfying host exists.  The theorems depend without proof on the command meaning and on the rules for errors and traps that [the command meaning](#command-meaning) and [the rules for success, errors, and traps](#success-errors-and-traps) state.

### Command meaning

The command semantics relates a source environment and host world to a result, final world, and ordered event trace.  A normal return includes a value, and an accepted exit includes the narrowed status.  A host trap, including rejection of an exit request, includes its committed world and trap identity.  Bounded-loop execution repeats the body in source order and preserves every earlier event.  A separate prefix relation records completed events, the current world, and a residual command when a guest resource failure interrupts execution.

Events record host invocations: the operation, selected fd, requested bytes or capacity, returned errno and successful count, and committed transfer, and for a flat call the call, its arguments, and its reply.  Pure computation and argument rejection leave the trace unchanged.  Stdout and stderr events share one ordered trace, and the host world may map them to the same resource.  The model also permits stdin and output descriptors to alias.  Separate byte logs are derived observations and establish neither ordering across descriptors nor aliasing.

The abstract world and host-step relations specify the stream operations and the flat calls.  [Observed host state](../Verified/Wasi/Observed.lean) adds an append-only joint event journal.  The universal theorem ranges over every satisfying host, with arbitrary input, output length, and permitted transfer partition, and scripted worlds supply concrete semantic tests.  `Action` has this meaning through [its execution relation](../LeanExe/Wasi/Semantics.lean) and [prefix relation](../LeanExe/Wasi/Prefix.lean).  [The native interpreter](../LeanExe/Wasi/Interpreter.lean) executes actions through a stream or supplied adapter, whose conformance to the abstract host assumptions is external to the compiler proof.  Kernel-checked equations for `pure` and `bind` establish sequencing, while host assumptions establish transfers.

### Success, errors, and traps

The host specification combines ABI shape, transfer behavior, and the memory frame.  A successful stdin read supplies at most the requested bytes, and its returned bytes match the writable prefix.  A successful output write commits the reported prefix of the supplied sequence.  The host's specification of a flat call, `sysContract`, admits the requests of `SysRequest`, changes memory only in the request's output regions, and on errno 0 leaves each shown output in its region.  The frame protects all guest resources outside the specified writable regions.

On errno, the model may record a committed prefix for the failed operation, while the count exposed by the wrapper is the zero sentinel.  A read error may have consumed an input prefix and changed bytes within its window, which the code then sets to 0, and a write error may have committed an output prefix.  Previously completed effects stay in the world and trace.  A stronger error guarantee would be an additional host assumption requiring its own evidence, so the result-count slot after an error says nothing about device progress.

Host-trap outcomes also keep the world committed before the trap, and frame conditions still protect unrelated guest memory.  Normal-return ownership postconditions apply after a return.  A host trap, resource trap, or exit ends the host's use of that instance.

Talos models host invocation through `HostEnv`, `HostSpec`, and `HostResult`, as pinned by [the dependency manifest](../lake-manifest.json), and `HostResult` has `Return`, `Trap`, and `Throw` outcomes.  The exit model uses a distinguished world field `exited : Option UInt64`.  Accepted exit records the narrowed status and produces the designated exit trap, and exit failure produces a host trap and preserves the previous exit field and committed effects.  A host beginning a fresh lifecycle supplies a world with `exited = none`, and read, write, and flat call transitions preserve that field.  The accepted-exit theorem requires the designated outcome and recorded status, so an arbitrary trap message or a nonzero guest status cannot establish acceptance.  The host specification excludes ordinary return from `proc_exit` and thrown exceptions from every import.  [The host assumptions](../Verified/Wasi/HostSpec.lean) hold the exit marker and the exact trap identity, and execution tests check that Wasmtime's accepted exits and exit failures match their modeled outcomes.

### The Linux shim

The shim implements the stream imports and the flat calls of `shimCalls` with [the Linux call layer](../LeanExe/Linux), whose rule describes each system call independently of an instruction set.  [The shim's specification](../Verified/Shim) is a Talos host environment, `linuxEnv`, and a host relation, `linuxHost`, over the layer's events.  `linuxHost` relates a WASI request to a reply exactly when the layer events that the shim appends form an image of the WASI event, carry their replies, and write within the guest's address space or into the timespec of the shim's scratch.  `linuxEnv_satisfies` proves that the environment satisfies `hostSpecWith` of that relation for a module whose calls lie in `shimCalls`, so the compiler's command theorem applies to the shim unchanged, and `shim_footprint` composes the two.  The specification takes the kernel's replies as a sequence indexed by the number of layer events and assumes no property of them other than the frame of the layer's rule, so a statement that needs one, such as readAll's corollaries, states it as a premise or as a class of reply sequences.  A binding to an instruction set proves that its stubs simulate the environment's functions, as [the AArch64 binding](a64-bare-metal.md#wasi-commands) does for the static Linux executables of commands.  [The manual's shim section](wasi.md#the-linux-shims-specification) states the functions and the theorems, and [its differences from Wasmtime](wasi.md#differences-from-wasmtime) the replies in which the shim and the Wasmtime host differ.

## Module construction and compiler proofs

[The native action semantics](../LeanExe/Wasi/Action.lean) gives the source executions, and [the typed effect language](../Verified/Wasi/Source.lean) gives the compiler's commands.  The wrapper and transport results below supply the premises of [command correctness](../Verified/Wasi/CommandCorrect.lean) and [cost-aware command correctness](../Verified/Wasi/CostCommandCorrect.lean).  [Program correctness](../Verified/Wasi/Correct.lean) combines those rules for a complete effectful program, and [callable entry](../Verified/Wasi/NativeEntry.lean) and [command entry](../Verified/Wasi/NativeCommand.lean) relate it to reflected Lean actions.  For an unbounded process, [process refinement](../Verified/Wasi/ProcessCorrect.lean) supplies the execution relation, and [total process execution](../Verified/Wasi/ProcessTotalCorrect.lean) also needs the application's progress, resource, and exit premises, as [the manual's process theorems](wasi.md#process-theorems-and-applications) state.

### Pure code in an importing module

Let the pure module contain `N` defined functions, including its allocator, release routine, depth entries, and wrappers, and let the program use `c` flat calls.  The WASI module imports the stream imports and the flat calls and relocates those `N` definitions before appending the I/O wrappers and effectful functions.  [The module layout](../Verified/Wasi/Module.lean) shifts every defined function by the `3 + c` imports, so the allocator lies at index `3 + c`.

| Item | Defined-function position | Absolute function index |
|---|---|---|
| Allocator | 0 | `3 + c` |
| Release | 1 | `4 + c` |
| Pure function at pure position `k` | `k` | `3 + c + k` |
| First appended wrapper or effectful function | `N` | `3 + c + N` |
| Command `_start`, when requested | Last defined position | `3 + c` plus that position |

Function indices and type indices are separate mappings.  The layout reserves three type entries for the stream imports, including duplicate read and write signatures, relocates pure type index `t` to `3 + t`, and places the types of appended definitions after them and the types of the flat calls' imports after every other type.  All calls, depth entries, wrapper calls, exports, and function-type annotations follow the layout maps.  [The validity generator](../Verified/Wasi/ReflectValidity.lean) constructs proofs of import signatures, instruction typing, and export bounds for the concrete module.  [The shared encoder](../LeanExe/Encoding/Modules.lean) and [encoding-domain conditions](../LeanExe/Encoding/Domain.lean) account for function imports.

The encoder and its [module grammar](../LeanExe/Encoding/Spec/Modules.lean) admit one empty nullable-function-reference table with minimum zero and the export `__indirect_function_table` at table index zero.  The table section and table-export entry have encoding, decoding, domain, validity, and round-trip rules.  The empty-table-list case keeps the pure encoding scheme, and byte-for-byte preservation of the pure import-free corpus is an integration check.  Element segments and indirect calls lie outside this profile.

[Function renaming](../Verified/FunRelocation.lean) transfers typed source functions and meaning, and the [module-composition rules](../Verified/ModuleComposition.lean) keep the import-free runtime layout.  WASI reuse adds [instruction relocation](../Verified/Wasi/Relocation.lean), [pure execution transport](../Verified/Wasi/PureTransportSpecs.lean), and [module transport](../Verified/Wasi/ModuleTransport.lean), and the transport keeps the pure universal theorem.  Relocated pure code simulates the original code under the layout maps, preserving its data state, represented arguments and results, and resource outcome, with a relation that accounts for function identities and any added table resources.  Every reachable pure call targets a relocated definition, including allocator and release calls, and never reaches an import.  The store projection follows the layout relation and erases the host world, it commutes with pure execution, and lifting its result preserves that world on returns and guest traps.  Appended definitions and the empty application-ABI table do not change pure execution, and heap predicates and representation facts, the byte predicates among them, transport through the state relation.

The proof covers an explicit pure instruction profile, including nested control flow and direct calls.  Profile closure excludes host and indirect calls.  [The relocated runtime rules](../Verified/Wasi/Runtime.lean) reuse allocator and release correctness through this transport.  The effect proof preserves both the host world and its ordered event journal across pure calls.

### Typed commands and reflection

The effect IR embeds typed pure expressions and has constructors for return, binding, conditionals, first-order effectful calls, bounded loops, the stream read and write, the read of the whole input, exit, `sys` for a flat call, and `letPair` for the components of a pair.  Contexts record the types and ownership modes of live values, and its result descriptor permits ordinary accepted values and erased `Unit`.  Read and write constructors invoke their transfer imports through the wrappers.  `Command.write output buffer start count` borrows the byte variable `buffer` and takes the start and the count of a window of it from two word variables.  Its code pushes the buffer's root and size and the window's start and count and calls the write wrapper, which clamps the window to the buffer with the code of an output window of `Command.sys` and passes the window's address and length to `fd_write`.  `Command.read buffer start count` takes the buffer as `Command.sys` takes its buffer, computes the window's address and length, calls the read wrapper with them, and after an errno stores 0 into the window.  Exit emits the call to `proc_exit` followed by `unreachable`, which permits validation at any result type, and the host call terminates with a designated exit or a permitted host trap.

`Command.sys call form args inputs buffers` compiles a flat call with the word variables `args`, the byte variables `inputs`, which the host reads, and the byte variables `buffers`, at most one, whose window the host writes, in one of the forms of [`SysForm`](../Verified/Wasi/SysForm.lean).  The command borrows each input and releases an owned input that is not live after it.  It takes the buffer before the call with the buffer variable's code under the variables live after the take (`sysTakeLive`), a move when the variable dies at the call and a copy otherwise, stores its root and size at the command's base, and runs the call with the buffer as variable 0 of an extended context.  At an output buffer's parameter, the command's words hold the window's start and count, which the code clamps to the buffer and lowers to the window's address and length.  After an errno the code zeroes the window, and the result holds the buffer.  The form `.flat` serves a call with at most one output buffer and at most two result words, which the code places at scratch addresses 0 and 8, and the form `.record` a call whose last parameter is a record.  The form `.reported` serves `args_get` and `environ_get`, the forms `.iovecRead` and `.iovecWrite` the reads and writes of the nested calls, and the form `.poll` serves `poll_oneoff`.  The form `.record` passes the start of the call area as the record's address and loads each field into a result word when the errno is 0, and the form `.poll` writes the subscriptions at the start of the call area and receives the events after them, so neither allocates.  `command_sys_spec_with` and `cost_command_sys_spec_with` prove the code against `sysContract`, whose frame is the request's output regions.

The constructor `Command.readAll` compiles `readAll limit` into the calling function: the code of the limit, then [fixed code](../Verified/Wasi/ReadAllCode.lean) that uses six `i64` locals of the calling function.  It tests the limit, allocates the buffer with the shared allocator, and runs a structured loop whose body calls `fd_read` with an iovec at the root plus the bytes held, so that the module's functions, wrappers, and indices are those of a program without it.  [The loop's proof](../Verified/Wasi/ReadAllLoop.lean) carries an invariant of the buffer's header and bytes, the step from the start of the command, the locals, and a partial run of the source loop, and the bytes below the limit plus one decrease at every pass that continues.  [The command's rules](../Verified/Wasi/ReadAllCommand.lean) give its correctness and its charge, and its resource prefixes are the prefixes of its action with the whole charge, since the allocation precedes every read.

The constructor `Command.letPair pair body` gives its body the second component of the pair variable `pair` as variable 0 and the first as variable 1, and its code is that of `Expr.letPair (.var pair)`: `Var.code` of the pair, which moves an owned pair that dies there and copies one that stays live, the stores of the components into the locals from the command's base on, the release of each owned component that the body does not use, and the body's code.  The components take the pair's mode, so a borrowed pair gives borrowed components without a copy.  Its charge before the body is `Var.cost` of the pair, which is 0 for a borrowed pair and for one that dies there.  [The binding's rules](../Verified/Wasi/CommandLetPair.lean) prove its code against `CommandResult` and `CostCommandResult` from those of its body.

Compilation orders operand evaluation before its effect and materializes operation results before evaluating a continuation.  Cleanup uses liveness across both the operation and continuation, so an unused read result is still read and then released.  A borrowed write argument stays live through the WASI import call.  Branches and loop iterations have the ownership and caller-frame obligations of pure code.

The code generator learns the variables live after each command from use masks.  `Command.useMask` is the set of variables that a command reads as a bitmask, as `Expr.useMask` is for an expression, and `Command.useMask_testBit` equates its bits with `Command.uses`.  [`Command.codeMask`](../Verified/Wasi/Code.lean) takes the variables live after a command as a mask and returns the command's code together with the command's mask in one pass.  A binding compiles its continuation first and gives its first command the union of the variables live after the binding and the continuation's mask shifted past the bound variable, a branch joins the masks of its arms, and a loop computes its step's mask before the step's code, since the step's live variables include those that the test and the step read.  A command's expressions take their code from `Expr.codeMask`, which receives the variables live after the expression as a mask, `.unit` and `.read` take theirs from `Command.codeWith` under the mask's bits, and [`Command.fragmentsMask`](../Verified/Wasi/CommandReady.lean) does the same for the fragments of the ready check.  `Command.codeWith` and `Command.fragments`, which take liveness as a function and ask `Command.uses` about each variable, are the specification: `Command.codeMask_eq` and `Command.fragmentsMask_eq` equate the mask forms with them, and the proofs rewrite with `EffectFunc.functionWith_body` and `EffectFunc.checkReadyWith_eq`, which state a function's code and its ready check through the specification.  `EffectFunc.functionWith` and `EffectFunc.checkReadyWith` call the mask forms.  The kernel evaluates the code generator in a command's byte theorems and in its ready check.  It computes each mask once, from the masks of the command's parts, while `Command.uses` walks the rest of the command for each variable that it is asked about.  The release of the variables that die at a command is the `releaseMask` of a mask that bit operations compute from the command's reads and the variables live after it, and it walks the context up to the highest variable that it releases instead of testing every variable.

The reflector translates accepted Lean action definitions into this IR and proves `Action.Rel` after flattening accepted values.  [Execution transport](../LeanExe/Wasi/RelatedExec.lean) and [prefix transport](../LeanExe/Wasi/RelatedPrefix.lean) relate this relation to observable semantics.  The reflector recognizes the monad's `pure` and `bind`, supported control flow, the stream operations, the typed functions of the flat calls, `args`, `environ`, and `withOpen`, whose bracket it emits as a fixed shape of commands that the handle check recognizes.  It splits a value of a pair type where the action binds it, with `Command.letPair`: the result of a `bind`, a loop's state at the start of each step, and a tuple parameter at the entry of an effectful function, and a component of a pair type in turn.  The rest of the action names the components in place of the variable, so the variable dies at the split and an owned tuple moves into its components.  A pure operand destructures only the variables of a pair type that it names, with the pure reflector's `reflectSplit`, so the code copies no owned value at an operand that does not name it.  A sum whose tuple holds heap values stays whole, as in the pure reflector.  A failed reflection proof rejects the program, and [the manual's control rules](wasi.md#control-and-helper-functions), [module forms](wasi.md#callable-and-command-modules), and [declaration table](wasi.md#declarations) give the accepted dialect, the frontend's forms, and the public names.

The universal compiler theorem is proved by command structure, using the pure transport theorem and wrapper execution lemmas.  It quantifies every concrete satisfying host and related initial state and supplies a sufficient fuel bound.  Each target execution at or above that bound returning a value, exiting, or reporting a permitted host trap has a matching source execution with the same ordered events, final world, and corresponding outcome.  The proof constructs that source path from the host's replies, and since nondeterministic specifications permit several paths, each target path must belong to that relation.

On normal return, values have the declared ownership, and retained caller regions keep their contents and separation.  A permitted guest resource trap matches a source prefix and residual command, preserves the effects already committed, and is distinct from exit.  Terminal outcomes require the host to discard the instance.

A separate total-execution theorem establishes a return or designated exit when `Heap.Within` holds for the allocation bound, `Resource.CallPrefixBound` bounds every typed resource prefix and establishes its size and depth checks, and `host.NoTrapsAlong` excludes reached host traps and exit rejection.  Returned errnos are ordinary results.  Kernel-checked source-correspondence proofs specialize these statements to each reflected definition, and the general refinement theorem keeps committed effects on host or guest resource failure.

## Lifecycle, bounds, and execution host

### Callable and command forms

[The manual's module forms](wasi.md#callable-and-command-modules) give the exports and the lifecycle of both forms.  A callable instance persists across successful calls, so host code provides the streams before invoking exports, serializes calls, and releases owned returned byte roots, and the allocation-counter exports serve its tests.  A command's host invokes `_start` once and discards the instance afterward.  Both forms export an empty `__indirect_function_table` to follow the pinned application ABI, and source operations use no indirect function pointers.

[The initial-store theorem](../Verified/Wasi/ProgramInitial.lean) proves the allocator invariant, memory cap, borrowed constant tables, and static byte pool for the complete modeled module.  It preserves the supplied abstract host world.  Representation, consumed-block separation, and separation from the low memory are call premises, and real engine instantiation and OS-stream configuration are external to that theorem.

### Resources and termination

The allocator rounds a requested payload up to eight bytes, with a minimum of eight, and adds its 48-byte header, which `Bytes.allocationCost` states with proof-side natural arithmetic.  A read of stdin and a flat call with an output buffer charge the copy of the buffer when the buffer's variable stays live after the call or is borrowed, and nothing when an owned buffer's variable dies there.  A write, a record call, and a poll charge nothing, and `args` and `environ` charge the block that the reporter's reply asks for.  Copying, byte construction, pure calls, retained state, and call frames contribute their own proved charges, and the model counts no reuse of released blocks.

`readAll limit` charges `Bytes.allocationCost (limit + 4096)` for its buffer, or nothing for a limit that returns errno 61, and its reads add nothing to the heap top.  The charge holds the allocation header and the buffer's capacity, whatever the number of bytes that the reads return.  Cleanup makes released blocks available for reuse, and a memory bound must account for retained capacities throughout branches and loop iterations.

Each primitive read or write wrapper makes at most one WASI import call, and the host may use several operating-system calls to implement one import.  For the acyclic effect-call graph and bounded loops, termination follows from finite source control flow, terminating pure callees under their depth conditions, and return of each reached host call.  A blocked host call supplies no return-time guarantee.

The internal ABI gives every effectful function a hidden depth word that shares the guarded-call limit of 1,000 with depth-aware pure bodies, as [the review decisions](#review-decisions) choose, and [the manual's module forms](wasi.md#callable-and-command-modules) give the frame limits and the stack check.  The stack check is a compiler admission condition, and real engine stack layout is an external assumption.  The typed resource-prefix condition separately accounts for the combined call path, and pure functions whose code takes no depth keep their ABI.

A process may run to EOF without an iteration bound.  [The process compiler](../Verified/Wasi/ProcessCode.lean) places bounded begin and step functions inside an unbounded `_start` loop, which compacts the owned state after begin and after each completed step.  Compaction lets the total-process theorem bound the memory of one step at a time, and it requires a state type without trees.  [The manual's processes](wasi.md#processes-without-an-iteration-bound) and [process theorems](wasi.md#process-theorems-and-applications) give the entry, the theorems, and their applications.

Pure calls also need the generated binding of constant tables.  An internal call supplies those hidden table arguments and any depth argument to the relocated body, directly or through a proved depth-preserving wrapper.  Its source-correspondence and bound proofs compose the table binding with the body theorem.  Exported wrappers that initialize depth are reserved for host entry, and the mixed-call tests include table-using pure callees under effectful helpers and calls at the combined depth boundary.

The effect theorem records allocation and depth requirements along an execution path.  A caller proves an upper bound for all permitted resource prefixes and uses it for total execution.  Read lengths are bounded by their requests, which supports such bounds for byte processing, and pure fragments use the pure compiler's allocation bounds.  The public frontend exposes the typed prefix condition rather than synthesizing an input-only bound for every I/O program, since such a bound must account for host-dependent branches, result lengths, retained byte roots, and cleanup across loop iterations.

### Wasmtime integration

The host uses the repository's pinned Wasmtime 44.0.0 C API, configured through `wasi_config_t`, `wasmtime_context_set_wasi`, and `wasmtime_linker_define_wasi`, which reach Wasmtime's Preview 1 adapter.  It inherits or redirects stdin, stdout, and stderr through the standard WASI configuration and passes the arguments, environment variables, and preopened directory that [the manual's host section](wasi.md#wasmtime-host) lists.  The [download pin](../tools/download-wasmtime.sh), [host build](../tools/build-wasmtime-host.sh), and [canonicalizing engine setup](../tools/wasmtime-host.c) define the tested embedding, and the host resolves every import through the standard linker.

Execution tests redirect guest output to separate capture files and send returned values, allocation counts, and terminal records to control outputs, while host diagnostics go to host stderr.  This separation keeps guest bytes for exact comparisons.  Interactive command mode inherits stdio.  After an engine failure, the host reports the error on host stderr and returns a failure status.

The pinned [exit-code type](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/preview1/witx/typenames.witx#L605-L606) is `u32`.  The [exit declaration](https://github.com/WebAssembly/WASI/blob/fae981bae14809d91f9bc2d63852d461f331d161/preview1/witx/wasi_snapshot_preview1.witx#L426-L432) marks `proc_exit` as nonreturning and leaves nonzero meanings to the environment.  Wasmtime 44 accepts statuses below 126 and rejects the others as engine errors, as [the manual's host section](wasi.md#wasmtime-host) states.  The host identifies accepted exits through [`wasmtime_error_exit_status`](https://github.com/bytecodealliance/wasmtime/blob/v44.0.0/crates/c-api/src/error.rs#L52-L62), and captured guest output stays available after either terminal outcome.

Lean's kernel checks the compiler and byte proofs against Talos and the specified host relations.  Wasmtime, the C compiler, OS streams, native adapter conformance, and real host progress are external assumptions tested by execution.  Standard WASI linking supplies compatibility with the selected ABI.

### Review decisions

| Decision | Approved choice | Alternative and consequence |
|---|---|---|
| Zero-capacity read | One `fd_read` import call with a zero-length iovec.  EOF inference requires positive capacity. | `INVAL` before I/O, which adds a source validation rule. |
| Exit UInt64 to WASI u32 | Explicit low-32-bit conversion for direct exit and command return. | A checked exit-code type adds source representation work, and trapping on overflow adds a guest failure path. |
| Exit acceptance | Standard host linking with accepted-exit and terminal host-failure outcomes.  A guarantee of return or designated exit requires host acceptance of every reached exit request. | A custom callback that accepts every UInt32 changes embedding policy and exit classification. |
| Bytes | Single allocation root plus logical UInt64 length. | A length-prefixed, one-pointer object changes the byte host ABI and access proofs. |
| Buffers of reads and flat calls | The program passes the buffer and a window of it, and one form serves each call with an output buffer, so no read or fill allocates. | Allocating forms beside the buffer forms give each operation two code paths, and an allocating form in a loop charges a block at every pass. |
| A window outside the buffer | Clamped to the buffer, as `Bytes.window` states. | Errno 28 before the call adds a result path to every program's proof. |
| A buffer after an errno | Kept, with the window's bytes set to 0 and the count 0 (`FillResult`). | Releasing the buffer makes a program that reads again after an errno build a new one. |
| The bytes after the count of a read of stdin | Free in `Exec.read_return`, except that the window's bytes begin with the bytes read. | A zero fill of the rest of the window writes up to the window's length after every short read. |
| Result of `readAll` | Errno-and-bytes record, empty on error. | A heap-valued sum requires a broader accepted sum representation. |
| Host errors | The declared current-operation prefix, with prior effects preserved.  The count is valid on success. | An unchanged-world error rule needs a stronger host guarantee. |
| Pure proof reuse | Import relocation and host-state execution transport, composed with the pure theorem. | Generalized shared compiler rules, where the transport proof shows a need. |
| Source monad | Semantic `Action` with checked reflection equations. | Opaque BaseIO primitives require an additional primitive/state correspondence. |
| Frontend | Separate `verified_compile_wasi` command, with an optional command entry. | Inferring an effect profile in `verified_compile` changes that command's accepted types and output selection. |
| Native API placement | Compiler-independent `LeanExe.Bytes` and `LeanExe.Wasi` modules. | Compiler-specific source APIs couple consumers to one compiler's namespace and module organization. |
| Effectful control flow | Bounded loops and an acyclic helper graph inside actions, and an unbounded loop only in the process entry, between compiled steps. | Unbounded loops inside actions require a general trace-prefix theorem and separate termination premises. |
| Depth accounting | The guarded-call depth, shared through effectful and pure internal calls. | Independent counters require a combined frame bound to justify their interaction. |
| Application-ABI table | The narrow empty-table encoding profile and the export that the pinned convention requires. | An import-only profile without that export reduces proof work but differs from the pinned application-ABI convention. |
