# Design

The repository is one Lake package.  `Verified` contains the verified compiler, and `LeanExe` contains the dialect, the runtime, the statement `Implements`, the encoder and decoder, the proof kit, and the WGSL and C translators, which the compiler and the applications share.  `Library` groups reusable algorithms and their proofs, `Demos` contains applications, `Examples` contains compiler fixtures, and `TestSupport` contains shared cases and reference calculators under `tests/`.  The default targets are `LeanExe`, `Examples`, and `Demos`.  The `Verified` aggregate imports the verified application compilations through `Demos.Verified`.  The complete numerical proof build includes `Library`.  [The README](../README.md) gives the layout and commands, [the compiler manual](verified-manual.md) describes the dialect and the proof procedure, and [the development journal](../devnotes.md) records the work.

## Goal

The compiler translates Lean functions to WebAssembly, with execution proofs in Talos.  Its reflector writes a Lean definition as a program of a typed source language, `compileWith` translates the program to a `Wasm.Module`, and a universal theorem proves that the module computes the program's meaning.  A binary decoder defines what the bytes mean, and its test decodes the modules of the official WebAssembly testsuite that lie in the decoder's subset, 712 of the 2,214 valid modules in the run that the journal records on 2026-10-16.  `decode_encode` carries the module's execution theorem to its encoded bytes.

## Components

The `Verified` library is the verified compiler, written as a Lean function over a typed source language, whose one theorem covers every program it accepts.  [The compiler manual](verified-manual.md) describes the dialect and the theorems, and [the compiler's internals](../Verified/README.md) describe the code and the proof.  The first table gives the components that `LeanExe` provides and the second the compiler's own.  The trusted base is Lean's kernel, Talos's semantics, the decoder, the step from a module constant to a file, and any I/O adapter.

| Component | Design |
|---|---|
| Runtime | `alloc` and `release`, specified and proved once.  Every object has one owner.  The compiler's theorem covers the releases in its code. |
| Statement | `Implements`, over a `Represent` class that says how a value appears as WASM values and heap data.  A call either returns the correct result or traps at `unreachable`, with no premise about free memory.  It includes a frame clause: every region of the heap before the call, below `top` and outside every free block, that lies apart from the consumed blocks keeps its bytes, stays such a region, and lies apart from the result, and the memory's maximum size is unchanged.  The caller's arrays and owned trees therefore keep their contents.  `ImplementsA false` states total execution, a call that returns without a trap. |
| Bytes | Encoder, decoder, and `decode_encode`. |
| Floating point | WebAssembly deterministic profile, described [below](#floating-point). |

| Component | Design |
|---|---|
| Source language | `Expr S Γ t`, typed by the callees' signatures `S` and the context `Γ`, with a meaning `denote` in Lean.  Values include words, `Bool`s, binary32 and binary64 floats, scalar tuples and sums, flat arrays, packed byte buffers, records with array fields, sums whose fields hold packed bytes, arrays, and recursive values, `List UInt64`, and fixed-layout recursive types whose records hold words, `Bool`s, floats, and flattened structures, enumerations, and sums.  `LeanExe.loop` and `LeanExe.repeatWhile` use one loop construct with a condition. |
| Compiler | `compileWith`, a Lean function from a program, tables, wrappers, and a byte-literal pool to a module using the shared runtime. |
| Theorem | `Prog.correctStaticWith`, under heap, table, ownership, and literal-coverage premises.  Its proof combines one lemma per construct through the facts of `After`.  `Prog.correctWith` specializes to programs without nonempty byte literals, and `Prog.correct` also omits tables and wrappers. |
| Reflector | `verified_compile`, meta code that writes Lean definitions as source functions and proves each equation from one lemma per Lean form, and `verified_recursive_type`, which derives a recursive type's conversions, encoding theorem, and match lemmas once beside the type.  The kernel checks every equation, so the reflector is not trusted. |
| Modes | `Expr.paramChoice` chooses each array or recursive-value parameter's mode, borrowed or owned.  The theorem holds for every choice. |
| Bounds | `Expr.allocs` follows the code with the same modes and live sets, and an owned array has a potential, a number of bytes that covers its later moves to larger blocks. |
| Recursion | Recognized tail recursion uses a loop with a proved decreasing rank.  Other recursion and its callers take the call depth, trap at depth 1,000, and have at most 32 positions per frame.  An entry starts each depth-taking function at depth 0. |
| Tables | Data segments from the heap base, read as borrowed parameters, with wrappers that pass their addresses and `compileWith_initialStore` for the initial store. |
| Composition | Typed program reuse and call relocation transport source meanings across modules.  Generated scalar store-preservation proofs support calls from other compiled programs.  [The composition API](../Verified/README.md#module-composition) describes the rules and examples. |

`verified_compile_wasi` adds effectful compilation for `LeanExe.Wasi.Action`, with stdin reads,
stdout and stderr writes, bounded loops, and exit.  It reflects actions into typed effectful code
and compiles them to core WebAssembly using `fd_read`, `fd_write`, and `proc_exit` from WASI
Preview 1.  Exported-entry proofs relate target execution to native actions, including returned
values, terminal outcomes, committed effects, and a joint ordered trace.  [The WASI manual](wasi.md)
states the API, host assumptions, and conditional total-execution premises.  [The WASI design](verified-wasi-design.md)
records the architecture and reviewed decisions.

The translator to C, in `LeanExe/Native/`, carries the verified compiler's modules past WebAssembly.  For a module in its subset, `verified_compile` evaluates `translate nativeCap p.module`, a program of the Lean copy of CompCert 3.18's Clight, and proves `p.f.native` for each function from `p.f.implements` and the simulation theorem `translate_correct`.  `native-verified build` prints the C text, has `clightgen` read it back, compares that Clight with the translation, and compiles the file with `ccomp` for AArch64 or x86-64 only when they agree.  The command `bare_program` adds a generated `main` and proves that the whole program terminates in the Clight copy with a UART store for each byte of the result, and a Rocq proof composes CompCert's simulations from Clight to Asm.  [The translator's design](native-translator.md) and [the bare-metal design](native-bare-metal.md) describe both paths.

## Source changes and proofs

The [verified reflector](../Verified/Reflect/Definitions.lean) can translate an additional Lean
form into an existing typed source expression.  Its proof equates the source expression's
denotation with the represented Lean value.  A new typed source construct also requires
[syntax and denotation](../Verified/Source.lean), [code generation](../Verified/Compile.lean),
and [expression correctness](../Verified/AlignedExprCorrect.lean), including allocation costs
and ownership preservation.  The [Verified Compiler Manual's examples](verified-manual.md#examples)
show accepted forms and their generated theorems.  The compiler's proofs use the
[shared proof lemmas](../LeanExe/ProofKit/README.md) for memory layout, allocation, frame
preservation, and alignment.  The [test suite descriptions](../tests/README.md) identify checks
for the corresponding changes.

Algorithm definitions and mathematical specifications belong to [the library](../Library/README.md).
The [Verified Compiler Manual](verified-manual.md#proving) explains how to combine a specification
with a generated execution theorem.  The [verification knowledge base](../VKB/README.md) links
worked proofs.  [Application demos](../Demos/README.md) links the application proofs, host
programs, and recorded runs.

## Proved

`Prog.correctWith` states that the compiler's module of every program of its source language, with its tables and wrappers, computes the program's meaning, in the sense of `ImplementsP`, with the flags, bounds, and frames conditions that the compiler computes.  `Prog.correct` is its case for a program without tables.  `compileWith_initialStore` states that the store in which a module with tables starts meets the allocator invariant, caps the memory at 65,535 pages, and holds each table at its address, when the tables end below 65,535 pages.  For each example that `verified_compile` compiles, the command states that the bytes decode to the module and that the module computes each definition, with a theorem that excludes a trap under the definition's bound, and the examples built without the reflector, such as `Tuples.lean`, construct their source programs directly.  `drone_trapFree` bounds the drone planner's allocation by 2,251,064 bytes, `chain_trapFree` and `fill_trapFree` cover recursions below depth 1,000, `lcg_advance`, `parkMiller_advance`, and `xorshift_advance` state the generators' bytes together with their period theorems, and the order book's theorems show that a command stream run in two chunks gives the book of one run.  [The compiler manual](verified-manual.md#examples) lists the examples.

`primeFactors_call`, `lookup_call`, `below100_call`, `increment_call`, `removeZero_call`, `gcd_call`, and `treeLookup_call` state that the modules of the small examples compute their specifications, which are written apart from the programs.  Each composes the export's generated theorems with the example's proof that the program equals the specification, `compute_eq` or `gcd_eq`.  `lookup_call` in [the compilation of `Lookup`](../Examples/Lookup/Compiled.lean), for example, states that `compute`, called with a borrowed array from a store with the allocator invariant in which `top` can rise by 232 bytes, returns without a trap an owned array that holds `expected xs` and keeps every region of the heap before the call.

[The compiler's GPT module](../Demos/Gpt/Verified.lean) compiles the binary64 GPT functions, including cached inference and sampling.  `verified_compile` derives their execution theorems from `Prog.correctWith`, their allocation bounds, their trap-free theorems under those bounds, and the module's bytes theorem.  [The generation theorems](../Demos/Gpt/VerifiedGeneration.lean) follow the host's calls: `generating_step` and `generating_scores` show that `step`, called once per token on the cache that the previous call returned, followed by `scores`, returns row `p` of `forward`, and `generating_step_trapFree` and `generating_scores_trapFree` exclude a trap when `top` can rise by each call's bound.

[`Demos/Gpt/Causal.lean`](../Demos/Gpt/Causal.lean) proves `attention_rows` and `block_rows`: when two inputs agree on rows `0` to `i`, so do the outputs, for `t`, `nh`, and `dh` below `2 ^ 16` and `f` below `2 ^ 32`, which exclude overflow in the `UInt64` index arithmetic.  The two inputs may have different numbers of rows `t` and `t'`, both above `i`.  `forward_prefix` proves that row `i` of the scores depends only on tokens `0` to `i`, whatever the number of tokens, under the same bounds with `vocab` added, by induction over the layers.  `layers_rows` states the same for the input of every layer, and `forward_causal` is the case of equal numbers of tokens.

`steps_exact` in [`Demos/Gpt/Exact.lean`](../Demos/Gpt/Exact.lean) states that `step` run on tokens `0` to `p` from an empty cache, followed by `scores`, equals row `p` of `forward` on any `T > p` tokens, as `Array Float`: the same floating-point values bit for bit.  The hypotheses bound the dimensions so that no `UInt64` index wraps: `T`, `nh`, `dh`, and `layers` below `2 ^ 16`, `f` and `vocab` below `2 ^ 32`, `nh` and `dh` positive, and the whole cache, `T · (2 · layers + 1) · nh · dh` values, below `2 ^ 32`.  The proof uses an invariant on the cache: block `j` holds row `j` of the last layer's input and rows `j` of each layer's keys and values, as `forward` on all `T` tokens computes them.  Each kernel that `layerStep` runs on one row computes the corresponding row of `block`'s kernel, and the attention kernels `stepScores`, `stepSoftmax`, and `stepMix` compute row `p` of `maskedScores`, `softmaxRows`, and `causalMatMul` from the cached keys and values.  The causality and exactness theorems concern the Lean definitions, and the generation theorems carry `steps_exact` to the module.

[The compiler's Euler module](../Demos/Euler/Verified.lean) compiles the functions of both solvers with the same generated theorems, with buffered solvers that keep three grids in their loops in place of the runs that build a new grid for each sweep.  `solve_eq` and `reconstructedSolve_eq` equate the buffered solvers with `solve` and `reconstructedSolve`.  `euler_solve_call` states that both exports, called from the store in which the module starts with a memory cap of at least `solvePages n` pages, return the words of `solve n` and `reconstructedSolve n trials` without a trap, and `solvePages_le` bounds `solvePages n` by 1,563 for every grid.  `run_reference_balance` and `reconstructedRun_reference_balance` state conservation against the exact Rusanov flux through the boundary.  `drone_compute` and `drone_safe` state that the bytes of [the drone module](../Demos/Drone/Verified.lean) compute the planner, whose flight is optimal among admitted flights and safe in the point-mass model.

`alloc` and `release` follow Knuth's first fit and liberation with a sorted list (TAOCP vol. 1, §2.5, Algorithms A and B).  `alloc` takes the first free block that fits.  When at least 56 bytes would remain, it lowers the block's size word and places the object at the block's upper end, so the free block keeps its place and link.  `release` searches the free list, which is in address order, for the first block above the freed one, then merges the freed block with that block and with the block before it when their regions touch.  `FixedArrayReuse.program_spec` proves the split, `findPlace_spec` the search, `joinProgram_spec` one merge, and `freeObject_spec` the whole return of a block.  Safety does not depend on the order of the list, and a merged block's region is the union of two free regions.  `FreeListAt.release` proves that the list stays laid out, `insertFree_cover` that every new block starts and ends where an old block or the freed block does, and `insertFree_apart` that a region apart from the freed block and every free block stays apart from every new block.  `Heap.Borrowed.release` and `Heap.Owned.release` take `Heap.At`, because `release` writes the header of the free block below the freed one.  The proofs bound `top` within one call, and a test covers memory across a session.

The build of [the full check](../tools/full-check) fails when a `#print axioms` report of a file of the repository names an axiom other than `propext`, `Classical.choice`, and `Quot.sound`.  A bytes theorem checks the encoding in parts: the native encoder gives the bytes of the sections and of each function body, and `decide +kernel` checks each part in its own theorem.  The runtime proofs use ProofKit's kernel-checked `Memory.read64_write64` and remove CodeLib's `Mem.read64_write64_same`, which is proved with `bv_decide`, from the `simp` set in `RuntimeSpec.lean`.

## Tested

The decoder test runs the official testsuite: every valid module in the decoder's subset decodes to the reference and round-trips, and every malformed module in the subset is rejected.  [`tests/verified/run.sh`](../tests/verified/run.sh) compares each module of the compiler with native Lean, checks the blocks that each call leaves allocated, and checks the accuracy of the numerical examples.  Through [the module driver](../tests/modules/run.sh) it also runs the module cases of `euler` and of `shapes` on the `sums` module, and [`tests/modules/chunks.py`](../tests/modules/chunks.py) runs order-book command streams through `clob.wasm` whole, in chunks, and one command at a time.  [The drone README](../Demos/Drone/README.md) describes [`tests/drone/run.sh`](../tests/drone/run.sh), and [the compiler manual](verified-manual.md#testing) describes the compiler's tests, among them [the WGSL tests](verified-manual.md#wgsl-tests).

[`tests/gpt/run.sh`](../tests/gpt/run.sh) compares every export of `gpt.wasm` with native Lean on chosen inputs, with empty and zero-sized arrays, arrays shorter or longer than their dimensions, infinities, NaN, signed zeros, overflow, subnormals, one to three heads, zero to three stacked layers, and caches built step by step.  [`tests/gpt/sessions.sh`](../tests/gpt/sessions.sh) checks that every session frees every allocation, temporaries included.  `exp` matches native Lean bit for bit on special values, 400 points from -745 to 710, and arbitrary bit patterns.  Against the C library's `exp` in native Lean, its error is at most 1 unit in the last place on 400,000 points from -745 to 710, 90 percent of them exact, and the special values match exactly.

`forward` computes the same function as Hugging Face's `GPT2LMHeadModel` (transformers 5.18.0, PyTorch 2.14.1, float64, `attn_implementation="eager"`), with every parameter drawn from a normal distribution with standard deviation 0.5 and 1 added to the layer-norm gains.  Over ten configurations, with zero to twelve layers, one to four heads, widths up to 16, hidden widths up to 64, vocabularies up to 50, and up to eight tokens, and three seeds each, the largest difference between the two sets of scores is 2.7e-15 of the largest score.  The differences come from the order of summation and from `exp` and `tanh`.  The configuration with width 1 matches exactly.

On the GPT-2 124M weights, `forward` matches Hugging Face's model in float64.  `gpt2_compare.py` writes the twenty weight arrays, about 1.0 GB, to files that the host loads with its `file-u64:PATH` argument kind.  For prompts of 5, 30, and 224 tokens, every score differs from Hugging Face's by at most 6.4e-15 of the largest score, and the steps from an empty cache give `forward`'s last row bit for bit.  With the cache, the script runs one host session that loads the weights once with the session command `file-u64 ID PATH`, keeps each new cache with `keep ID VALUE`, and writes the scores to a file with `save-u64 VALUE PATH`.  Greedy generation from a 5-token prompt to 256 tokens chooses Hugging Face's token at every step, with differences of at most 1.16e-13 of the largest score, and the session ends with about 1.08 GB of memory, the weights and about 100 MB.

## Decisions

### Runtime, statement, and dialect

| Decision | Reason |
|---|---|
| Development proceeds in increments.  Each takes one program from Lean source to bytes, a proved `Implements`, a Wasmtime comparison with native Lean, an axiom audit, and a commit, adding only what that program needs. | Building whole layers before connecting them defers every integration error. |
| `Implements` is one statement over a `Represent` class.  Every compiled module has a memory and the runtime globals. | A module without memory would make `Heap.At` false and the theorem vacuous. |
| Every object has one owner, values move at their last use, and an owned array at its last use is updated in place. | Lean values can be shared, so ownership must be established in the source: moves make every reference count 1, and `release` needs no count. |
| Runtime integers are fixed-width only, and a read past the end of an array gives the element type's default. | Bounded `Nat` traps where Lean returns the exact value, and Lean's logic gives `default` for an out-of-bounds `a[i]!`. |
| I/O uses a pure step function, `State → Input → State × Output`, driven by a fixed adapter, trusted until proved. | Each `step` call is pure, so `Implements` covers it. |
| `release` and the runtime counters are absent from the source dialect.  Modules keep the counters as globals. | Their values are 0 in Lean and real in WASM. |
| Floating-point theorems describe the WebAssembly deterministic profile. | Talos implements it, and it matches Lean's float model. |
| Every module contains `alloc` and `release` at functions 0 and 1, with the allocation and free counters.  `release` is not recursive: it frees an object and, through a loop over its masked slots, the objects it owns. | A recursive `release` uses one WASM stack frame per node. |
| Python tools are added to the repository only as uv-runnable scripts with PEP 723 metadata, always run with `uv run`. | Each script declares its dependencies, and no environment outside the repository is needed. |
| `Implements` states that a call returns the correct result or traps at `unreachable`, with no premise about free memory.  `alloc` traps when memory cannot grow, and every compiled module declares at most 65,535 pages, which `Implements` assumes of the memory's cap. | A premise about free memory does not compose across calls, because each call's bound adds to `top` and nothing bounds fragmentation.  A trap is a visible failure, so the theorems describe every completed call.  With at most 65,535 pages every block ends below `2 ^ 32`, the bound the free-list proofs use.  Total execution is stated separately, with `ImplementsA false`, which `p.f.trapFree` gives under the function's allocation bound. |
| `release` checks the child mask before it reads any slots. | Freeing an array without child pointers would otherwise take one loop iteration per element to test a zero mask, and the check removes two nested loops from the proof of the common case. |
| `Heap.Owned` records that the object ends inside the 32-bit address space. | The freed block's free-list entry needs it, and every allocated block satisfies it. |
| Proofs may not use `bv_decide` or `native_decide`. | Both add an axiom that trusts compiled code. |
| The dialect's float array is `Array Float`, and `FloatArray` is not supported. | Lean core has no lemmas about `FloatArray`, and the loop of `FloatArray.foldlM` is private, so a proof about its fold depends on a private declaration.  `Array` has public lemmas and literal syntax.  In WebAssembly both types have the same unboxed layout.  In native Lean, `Array Float` stores each element as a separate heap object, which costs speed and memory in native runs only. |
| A function returns several values as WebAssembly multi-value results, one per component: a pair is its first component's values followed by its second's, as in `Represent` for pairs. | This follows the pair representation the proofs use and needs no heap object per tuple.  Arrays of flat records store each record as its words, as the `grids` example shows. |
| `Implements` has a frame clause that covers every region of the heap apart from the consumed blocks, which includes the caller's arrays and trees. | Composing a call with the callee's theorem requires it: a caller holding a new array must know the call leaves it intact. |
| `Implements` states that a call's result is fresh and that owned arrays keep their capacity. | Without freshness, `Implements` would allow a function to return its argument as its owned result, and a caller that released it would free its own argument. |
| `Implements` states that the memory's maximum size (`memoryCaps`) is unchanged. | A call after another call needs room in the store the first leaves, and room depends on the maximum size.  The allocation facts record it (`Heap.NewArray.caps`). |
| `Heap.At` requires at most 65,536 pages, and `Heap.Borrowed` requires only that the input lies below `top` and outside every free block. | A 32-bit memory has at most 65,536 pages. |
| `alloc` follows Knuth's first fit and `release` his liberation with a sorted list (TAOCP vol. 1, §2.5, Algorithms A and B).  `alloc` places the object at the upper end of the first free block that fits and shrinks the block when at least 56 bytes remain.  `release` inserts the block in address order, merges it with free neighbors, and leaves `top` unchanged. | First fit without splitting or merging leaks memory whenever allocation sizes change between calls: the growing cache would need 5.05 GB for 256 positions.  A simulation of the run peaks at 100 MB with splitting and merging. |
| Loops use `LeanExe.loop (n : UInt64) (init : α) (f : UInt64 → α → α) : α`, with `UInt64` indices and `xs[i.toNat]!`, which yields 0 out of bounds. | Compiled `UInt64` arithmetic equals Lean's, so no proof concerns overflow.  `Nat.fold` would need overflow facts for index arithmetic, and `for` loops would require recognizing the elaborated `forIn`.  `LeanExe.loop` does not stop early, and `LeanExe.repeatWhile` and tail recursion cover early exit. |

| Decision | Reason |
|---|---|
| GPT-2 is the target: the same function as OpenAI's published code and Hugging Face's PyTorch model.  Attention has `nh` heads of width `dh`, with `d = nh · dh`, and the four linear layers have biases.  Tests compare with Hugging Face's model in float64. | Passing `nh` and `dh` leaves no invalid head configuration.  Both sides in binary64 differ only in summation order and in `exp` and `tanh`. |
| The number of layers is a loop parameter: `forward` runs the blocks in `LeanExe.loop`, and the kernels read each layer's weights at an offset in stacked arrays. | A loop keeps the composition inside the proofs.  GPT-2 fixes the layer count only through its weights. |
| The GPT-2 124M test uses the pinned `openai-community/gpt2` checkpoint (revision `607a30d783dfa663caf39e06633721c8d4cfcd7e`), widened from binary32 to binary64, with prompts of at most 256 tokens.  The test script writes one file of little-endian words per array, and the host loads each with `file-u64:PATH`. | Binary64 keeps the proved pipeline unchanged.  The memory the calls use stays below 4 GiB. |
| Generation uses a key and value cache.  A theorem proves that the cached steps give the same bits as the corresponding row of `forward`, so `forward`'s softmax reads entries `j ≤ i` only, and `forward` and a step perform the same operations.  Attention reads earlier positions from the cache and the new position from the new key and value, the layer loop's state holds the row and the new keys and values, and `step` appends the new block.  The cache is one block per position, holding that position's key and value for every layer and its final hidden row, and a separate `scores` reads the last block. | Without a cache, generating to 256 tokens takes an estimated 3.8 hours.  The design needs no capacity parameter and keeps the cached path inside the proved functions.  Dropping the masked entries from the softmax leaves attention's output unchanged: Lean's `max` is `if x ≤ y then y else x`, so `max acc (−∞)` is `acc`, `exp` returns +0.0 below −745.2, and the running sum starts at +0.0, so adding +0 leaves it unchanged. |
| Attention is causal for all inputs: a masked score reads no key, and the product with `v` reads rows `0` to `i` only. | An additive mask over all keys lets a later row turn an earlier row into NaN. |
| `Demos.Gpt.exp` is a Lean definition, and the execution proof preserves its operations.  Tests measure its accuracy. | Lean's `Float.exp` is `opaque`, so its numerical behavior needs a separate specification. Without `--seed` it takes a seed from the operating system and prints it to stderr. | Sampling in Lean keeps the whole generation step proved, and the CLI only passes the generator state along. ### The compiler

| Decision | Reason |
|---|---|
| The verified compiler, `compileWith` in `Verified`, is a Lean function from a typed source language with a `denote` to a module.  It shares the trusted base and `Implements` with `LeanExe`. | One theorem can cover every program that a compiler over a source syntax accepts, and meta code over `Lean.Expr` admits no such theorem. |
| The verified compiler's reflector writes ordinary Lean definitions as source functions, and the kernel checks an equation for each.  The reflector builds the equations and theorems as terms. | Programs stay ordinary Lean, and other libraries' programs compile unchanged.  Terms let the kernel check each equation without unfolding a definition, which for a loop over literal data would run the loop pass by pass. |
| `Expr.fold` means the full `Array.foldl` and compiles to a `UInt64`-counted loop.  The proof derives the size bound from the represented array, and the reflector accepts the default whole-array bounds. | The logical fold retains Lean's meaning on every array, and executable lengths and indices remain words.  The rule reuses the loop's ownership, allocation, frames, and release proofs. |
| `Array.insertIdx!` uses a typed full-length comparison, the existing insertion, and an empty build.  The comparison's compiled word-sized length is justified by the heap representation. | Lean returns `#[]` for an index beyond the length.  The source preserves this result on every logical array, and the compiler reuses its conditional, comparison, insertion, and build rules. |
| A function's theorem is `ImplementsA aborts`, with `aborts` false when the code cannot allocate and takes no call depth. | Such a function gets a theorem that excludes a trap with no further proof. |
| `Expr.paramChoice` chooses each array parameter's mode, and an owned array at its last use is updated, extended, or shifted in its own block. | The theorem holds for every choice of modes, so the choice needs no trust and affects only the code's cost. |
| Recognized tail recursion uses typed return and continue nodes, fixed parameter modes, and a Wasm loop.  The reflector derives a rank from Lean's generated induction theorem.  `set_option verified.tailLoops false` retains guarded recursion. | The fixed-point equation establishes meaning, and the decreasing rank establishes termination.  Continuing steps move or copy the next state under the same ownership rules as calls.  Native step charges give the public allocation bound. |
| Guarded recursive functions and their callers take the call depth, trap at depth 1,000, and have at most 32 positions per frame.  A tail loop takes depth when it calls guarded code and preserves that depth between iterations. | Talos bounds no call depth, and Wasmtime's stack is finite.  At 8 bytes for each value live across a call and 16 bytes per frame, 1,000 frames of 32 positions take at most 272,000 bytes of Wasmtime's 512 KiB default stack. |
| The verified compiler computes an allocation bound from the code, and `p.f.trapFree` excludes a trap when `top` can rise by the bound within the memory cap.  `p.f.bound_eq` states the bound in the function's parameters. | `ImplementsA true` holds of a module that always traps.  A bound computed from the code needs no budget proof per program, and the equation lets a user prove a concrete bound by rewriting. |
| An owned array has the potential `4 · 8 (n + 1) ∸ 2c`, and every owned array parameter of a function whose body extends an array is paid: the caller charges its credit. | The potential covers the bytes of a growing array's moves to larger blocks, so a loop of `n` pushes has a bound linear in `n`. ## Floating point

Lean 4.34 defines `Float` and `Float32` through `Float.Model` and `Float32.Model`, IEEE binary64 and binary32 with round-to-nearest, ties to even.  Every NaN in both models is the positive quiet NaN with only the top fraction bit set, `0x7FF8000000000000` or `0x7FC00000`, and `ofBits` converts every NaN input to it.  Talos's `IEEE64` and `IEEE32` return the same constants for every NaN result.

ProofKit proves `LeanExe.Float32.xBits = Wasm.IEEE32.x` for `add`, `sub`, `mul`, `div`, and `sqrt`, for all inputs including NaN.  The binary64 counterparts for all five operations are the `F64*.lean` files and `F64Bits`.  Lemmas that do not depend on the format are in `FloatRounding`, `FloatShift`, `FloatRationalRounding`, `FloatSqrtRounding`, and `FloatCommon`, which both chains import.  `IEEE64.roundDyadicMagnitude` and `roundRationalMagnitude` pass `rounded * 2^shift` to `roundScaledMagnitude` where the binary32 rounders encode the fields directly, and `roundScaled_mul_pow` relates the two forms.  `F64Bits` restates the results as `(a + b).toBits = IEEE64.add a.toBits b.toBits` for Lean floats.  The wrappers are thin: `LeanExe.Float32.addBits` applies Lean's `Float32` addition to decoded bits, so the theorems also justify compiling Lean's float types directly.

Lean and WASM differ in three places:
1. Lean's `neg` and `abs` return the positive canonical NaN for a NaN input.  WASM `fneg` and `fabs` change only the sign bit.
2. Lean's `ofBits` canonicalizes NaN.  WASM `reinterpret` keeps the payload.
3. Lean's `min` and `max` choose an operand by `≤`.  WASM `fmin` and `fmax` return NaN for a NaN operand and order `-0` below `+0`.

The WebAssembly specification ([numerics](https://webassembly.github.io/spec/core/exec/numerics.html)) makes the sign of a generated NaN nondeterministic and its payload canonical only when every NaN input is canonical.  Its deterministic profile ([profiles](https://webassembly.github.io/spec/core/appendix/profiles.html)) requires that "All NaN values generated by floating-point instructions are canonical and positive," and Talos implements that behavior.  [`tools/wasmtime-host.c`](../tools/wasmtime-host.c) enables Cranelift's NaN canonicalization.  Browsers do not implement the profile, and on x86 `0/0` produces a negative NaN.  On aarch64, native Lean's `toBits` returns `0x7FF8000000000000` for a NaN with a payload, for `0/0`, and for `-(0/0)`.  Modeling the full profile in Talos, with an oracle choosing NaN results and the compiler canonicalizing NaN where bits become observable, is the route if theorems must cover results computed in a browser.

`IEEE64` has the same functions as `IEEE32` and calls `IEEE32.roundShift`, `roundQuotient`, and `roundSqrtIntegral` directly, so the binary64 proofs import the lemmas about those helpers.  Binary64 comparisons follow from `F64Compare.compare_canonical`: decoding a non-NaN bit pattern gives a canonical unpacked float whose value is Talos's `scaledValue`, and Lean's comparison of canonical floats orders them by value.  Negation compiles to `-0.0 - x` (`F64Sign.sub_negZero`), absolute value to `f64.abs`, and `min` and `max` to a comparison and a conditional, which removes the first and third differences.  For `Float.ofBits`, the compiler adds −0 after `f64.reinterpret_i64`, which gives the canonical NaN for a NaN pattern.  `F64Convert` proves the conversions between `UInt64` and `Float`, and `F32Compare` and `F32Sign` give the binary32 comparison and sign theorems.  Conversions between `Float` and `Float32` have no theorems.

## Scope of the theorem

The theorems' semantics, premises, frame, emitted files, WASI host, and native statements bound what they say.  [The trusted-base document](trusted-base.md) gives, for each artifact code, the trusted components behind these bounds, with the check and the source of each.  A theorem's conclusion holds of a running artifact only when those components do what that document states.

1. The claim is about Talos's semantics.  Wasmtime appears only in tests, and the Talos interpreter and the decoder are trusted.
2. The premises `Heap.At` and `Heap.Borrowed`, and a memory cap of at most 65,535 pages, are assumed.  Every compiled module declares that maximum.  For each module, `p.initial` proves that the store in which the module starts meets the allocator invariant and the cap and holds each table as a borrowed array.  The host executables remain outside the proofs.  A call may trap at `unreachable` when memory cannot grow or an array would exceed 32-bit memory, and the theorems state the result of every call that does not trap.  A module that always traps would satisfy them, which `p.f.trapFree` excludes under its bound.  Talos's `memory.grow` succeeds whenever the new page count is within the maximum, while the WebAssembly specification lets an engine refuse growth for its own reasons.  `alloc` checks the result of `memory.grow` and executes `unreachable` on failure (`MemoryGrowth.growProgram`), so on such an engine the call traps and returns no result, a path the theorems do not describe.
3. `Implements` states a frame: every heap region below `top`, outside the free blocks, and apart from the consumed blocks keeps its bytes and lies apart from the result, and the memory's maximum size is unchanged.  It states nothing about memory outside the heap that the allocator manages.
4. `Emit.lean` evaluates `encode` with compiled Lean code.  Each module of [the module registry](../tests/verified/modules.txt) except `byHand` of `Modes` has a file module, which [the file-theorem registry](../tests/verified/numerics.txt) lists and [the Verified test driver](../tests/verified/run.sh) checks in its loop over `name:TheoremModule:FileModule` entries after it writes the file.  [`Demos/Gpt/VerifiedFile.lean`](../Demos/Gpt/VerifiedFile.lean) proves that `gpt.wasm` holds the encoding of the GPT module and decodes to the module of its bytes theorem, and [`Library/Numerics/Float64/Exp/ExpFile.lean`](../Library/Numerics/Float64/Exp/ExpFile.lean) does the same for `exp.wasm`.  Each file module states its two theorems with one `file_theorems` command of [`LeanExe/Pipeline/FileBytes.lean`](../LeanExe/Pipeline/FileBytes.lean), and the kernel checks the proofs that the command writes.  The elaborator `binary_file%` that reads the file is trusted.  No theorem covers the file of `byHand`, which has no `p.module`.
5. WASI entry proofs assume a host satisfying the three import specifications, valid byte and static-data representations, and separation from scratch memory.  They preserve source effects through normal return, accepted exit, host trap, and permitted guest resource failure.  Total execution additionally requires a typed resource-prefix bound and no reached host trap.  [The WASI proof premises](wasi.md#execution-proofs-and-their-premises) state these conditions and the external assumptions about stream adapters, OS I/O, and real engines.
6. The native theorems are about the Lean copy of CompCert 3.18's Clight, in which Talos serves as an intermediate language that only the proofs use.  `p.f.native` assumes a C state related to a store that meets the premises of `p.f.implements`, and the C host that places the arguments, CompCert's unverified parts, the stack, and the platform remain trusted, while the per-build `clightgen` comparison checks the printer and the written file, as [the translator's trusted base](native-translator.md#trusted-base-of-the-native-path) lists.  The bare-metal theorem `p.f.program` covers a whole program with a generated `main` in the same semantics, a Rocq proof composes CompCert's simulations from Clight to Asm, and the startup code, the linker script, the static stack bound, and QEMU or the processor remain trusted, as [the bare-metal trusted base](native-bare-metal.md#trusted-base) lists.
