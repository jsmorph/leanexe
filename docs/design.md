# Design

The repository is one Lake package at its root, with the libraries `LeanExe` (the dialect, the compiler, the IR, the runtime, the pipeline, the encoding, and the general lemmas), `Examples` (one directory per example), and `Verified` (a second compiler with a correctness theorem, outside the default target).  [The README](../README.md) gives the layout and commands, [the user manual](manual.md) describes the dialect, the commands, the proofs, and the tests, and [the development journal](../devnotes.md) records the work.

## Goal

A compiler translates a Lean function to an IR, `compile` translates the IR to a Talos `Wasm.Module`, `encode` produces the bytes, and a per-program proof shows that the module computes the Lean function exactly.  A binary decoder, tested against the official WebAssembly testsuite, defines what the bytes mean, and `decode_encode` gives each theorem for the module that the decoder reads from the bytes.  The system is kept small, and the work proceeds in increments that each reach bytes and a theorem.

## Design

The `LeanExe` compiler is not verified as a whole.  Each of its rules gets its own theorem and an entry in the LTG knowledge base, so per-program proofs shrink while the trusted base stays the same.  Per-program proofs, using the LTG entries, cover what the rules do not.  [The `Verified` library](../Verified/README.md) is a second compiler, written as a Lean function over a typed source language, whose one theorem covers every program it accepts.

| Component | Design |
|---|---|
| IR | Embedded in Lean: expressions over locals, assignment, `if`, `while`, loads, stores, and calls.  Values are 64-bit words, Booleans, and binary64 and binary32 bit patterns.  Arrays, records, and ownership appear as memory operations in the compiler's templates and in the proofs. |
| Translation | `compile : IR → Wasm.Module`, with one `wp` rule per construct proved once against Talos.  The IR means what its compiled code does. |
| Compiler | Lean to IR, reading each definition's unfolding equation.  Verifying a rule means proving that its template implements its source construct, stated in terms of Lean's own functions, so no `Lean.Expr` semantics is trusted. |
| Hints | Untrusted annotations: the rule behind each fragment, its source term, its instruction path in the decoded module, and the name of each local.  A wrong hint costs proof time and cannot produce a false theorem. |
| Runtime | `alloc` and `release`, specified and proved once.  Every object has one owner.  The compiler places `release`, and per-program proofs check the placement. |
| Statement | `Implements`, over a `Represent` class that says how a value appears as WASM values and heap data.  A call either returns the correct result or traps at `unreachable`, with no premise about free memory.  It includes a frame clause: every region of the heap before the call, below `top` and outside every free block, that lies apart from the consumed blocks keeps its bytes, stays such a region, and lies apart from the result, and the memory's maximum size is unchanged.  The caller's arrays and owned trees therefore keep their contents.  `ImplementsA` with an allocator budget states complete execution, a call that returns without a trap. |
| Bytes | The encoder, `decode_encode`, and one decoder. |
| Floating point | The WebAssembly deterministic profile, described [below](#floating-point). |

[The manual](manual.md) describes what each component covers.  The trusted base is Lean's kernel, Talos's semantics, the decoder, and any I/O adapter.  The source dialect has fixed-width integers and IEEE floats, compiles `panic` to `default`, allows recursive values, and does I/O through a pure step function driven by a fixed adapter.  Rule lemmas state what their templates leave unchanged, meaning the locals they do not write and the memory outside the blocks they allocate or write, because lemmas for nested templates do not compose otherwise.

## Proved

`scale_implements` states that `scale.module` implements `scale a b c = a * b / c + 1` on every triple of `UInt64` arguments.  Its proof applies `Func.implements` and one `simp` call.  The only remaining step is Lean's `a * b / 0 = 0`.

`gcd_implements` states that `gcd.module` implements Euclid's algorithm on every pair of `UInt64` arguments.  The compiler produces a `while` loop over a `done` flag whose body branches on `b = 0`.  The proof applies `Func.tail_implements` and proves only `gcd_step`, one iteration.

`sumArray_implements` states that `sumArray.module` implements `sumArray xs = xs.foldl (· + ·) 0` on every borrowed `Array UInt64`.  The compiler produces an assignment of 0 to an accumulator followed by `Stmt.fold`, a loop that loads the length word and then each element.  `Func.foldl_implements` applies `Func.implements`, the assignment rule, and `Stmt.fold_spec` to any function whose body is this template with a word operation other than division and remainder, and `sumArray_implements`, `productArray_implements`, and `xorArray_implements` apply it.  `Stmt.fold_spec` needs the array's layout in memory, which `Heap.Borrowed` provides, and an obligation that the fold body evaluates to `g a e`.

`pairSum_implements` states that `pairSum.module` implements `pairSum a b = #[a, b].foldl (· + ·) 0` on every pair of `UInt64` arguments.  The compiled code calls `alloc`, stores the length and the two elements, folds, and calls `release`.  The proof applies `Func.implements_heap`, `Stmt.arrayLiteral_spec`, the assignment rule, `Stmt.fold_spec`, and `Stmt.release_spec` with `Heap.At.release`.

`sumCount_implements` states that `sumCount.module` implements `sumCount xs = #[xs.foldl (· + ·) 0, xs.size.toUInt64]` on every borrowed `Array UInt64`: the result is an array that the caller owns, and the argument stays borrowed.  The proof applies `Func.implements_heap`, `Stmt.fold_spec`, `Stmt.arraySize_spec`, and `Stmt.arrayLiteral_spec`, whose preservation clause keeps the argument borrowed.

`axpy_implements` states that `axpy.module` computes `axpy a x y = a * x + y` bit for bit on every triple of `Float` arguments, NaN included.  The proof applies `Func.implements` and one `simp` call with `F64Bits.toBits_add` and `toBits_mul`.  `scaledHypot_implements` does the same for `scaledHypot x y s = (x * x + y * y).sqrt / s`, adding `toBits_div` and `toBits_sqrt`.  `piecewise_implements` covers a function with `==`, `<`, `≤`, negation, `Float.abs`, `min`, `max`, three literals, and nested `if`.

`sumSquares_implements` states that `sumSquares.module` computes `sumSquares xs = xs.foldl (fun acc x => acc + x * x) 0.0` bit for bit on every borrowed `Array Float`.  An `Array Float` is stored as the `Array UInt64` of its elements' bit patterns, and the fold's accumulator and element locals have type `f64`.  The proof applies `Stmt.fold_spec` with a step on bit patterns, and a lemma converts the result with core's `Array.foldl_map` and `Array.foldl_hom`.

`mean_implements` proves `mean xs = xs.foldl (· + ·) 0.0 / xs.size.toUInt64.toFloat` bit for bit, with the fold, the array-size rule, and `F64Convert.toBits_toFloat`.  `bucket_implements` proves `bucket x lo width = ((x - lo) / width).toUInt64`, a histogram index, with one `simp` call and `F64Convert.toUInt64_eq`.  Both conversion theorems cover NaN, the infinities, and out-of-range values.

`marketBuy_implements` proves the first CLOB operation: `marketBuy askPrices askSizes qty` walks the ask levels with `LeanExe.loop`, taking `min remaining askSizes[i]!` at each level, and returns `#[filled, cost]`, an array the caller owns.  The source equals a loop over a named step function by `rfl`.  The loop rule `Stmt.loop_spec` needs one obligation about the body, which `body_run` proves by computing the body's effect with `Stmt.run` and `simp`, including two bounds-checked reads.  The assignments before the loop are proved the same way, and the result array by `Stmt.arrayLiteral_spec`.

`fillLevel_implements` proves `fillLevel sizes k amount = sizes.set! k.toNat (sizes[k.toNat]! - amount)`.  The array is consumed and updated in place by `Stmt.setInPlace` at its last use, and `set!_eq_build` equates `set!` with the copying template that a non-last use compiles to.  `insertLevel_implements` proves `insertLevel prices sizes k price size = (prices.insertIdx! k.toNat price, sizes.insertIdx! k.toNat size)`, which returns two arrays as two WebAssembly results.  `Func` holds a list of results, and `Implements` states the owned results in declaration order: Talos lists results with the top of the stack first, as it does arguments.  Chaining two templates uses the runtime lemmas that an owned object stays owned after another allocation and after writes to the new block (`Heap.Owned.allocate`, `Heap.Owned.writesWithin`).

`setLevel_implements` proves `setLevel prices sizes k size = (prices, sizes.set! k.toNat size)`.  `addBid` and `cancelBid` call `findLevel` and then, depending on whether the level at that position has the price, `setLevel`, `insertLevel`, or `removeLevel`.  `bid_spec` proves the part the two share, the search call, the number of levels, and the condition, once for any number of locals.  `pairCall_spec` proves a call whose two arrays become the caller's result, and `pairCopy_spec` copies of two arrays as the result, both for any result locals and caller arguments.  `applyCommand_implements` proves `applyCommand prices sizes kind price size`, which calls `addBid` for kind 0 and `cancelBid` for kind 1 and returns both arrays for any other kind.

The compiler allocates a conditional's result locals before its branches, and a call or array build in a branch writes into them directly, so no branch copies results between locals.  `Implements` states that the memory's maximum size is unchanged: a call after another call needs room in the store the first leaves, and `Heap.Room.after` derives it from that fact.

`depth_implements` proves `depth prices sizes limit`, the total size of the levels priced at or above `limit`, a loop whose state is one word, by `Func.implements` and `Stmt.loop_spec`.  `findLevel_implements` proves `findLevel prices price`, the search loop of `addBid`.  `removeLevel_implements` proves `removeLevel prices sizes k = (prices.eraseIdxIfInBounds k.toNat, sizes.eraseIdxIfInBounds k.toNat)`, and `eraseIdxIfInBounds_eq_build` equates the operation with the copying template, using core's `getElem_eraseIdx`.

`dot_implements` proves the first CPU GPT kernel, `dot xs ys`, a loop that sums `xs[i]! * ys[i]!` over the length of `xs`, bit for bit.  An `Array Float` read compiles to `Expr.ofBits` around the word read, and `Expr.ofBits` compiles to `f64.reinterpret_i64` and leaves the bit pattern unchanged.  `getElem!_map_toBits` relates the read of the bit patterns to Lean's read, which yields `UInt64.toFloat 0`, bit pattern 0, past the end.

`matVec_implements` proves `matVec m v rows cols`, the product of a `rows × cols` matrix stored by rows and a vector, returned as a new `Array Float`, bit for bit.  Each element is a loop over a row: `Stmt.buildWith` runs a statement before it stores each element, and `Stmt.build` is the case with `.skip`, which emits no instructions.  The compiler translates the element in a block whose statements become the per-element statement, and it rejects allocation and calls there, so that statement keeps the store.  A float element is stored through `Expr.toBits`, which compiles to `i64.reinterpret_f64`.

`layerNorm_implements` proves `layerNorm xs g b eps`: the mean and the variance by two loops, `1.0 / (var + eps).sqrt`, and a new array whose element `i` is `(xs[i]! - mean) * inv * g[i]! + b[i]!`, bit for bit.  It applies `Stmt.loop_spec` twice, straight-line runs for the float assignments, and `Stmt.build_spec`.

`exp_implements` proves that the compiled `exp` computes the Lean definition `exp` bit for bit.  `exp` reduces `x` to `k·ln 2 + r` with a two-part `ln 2`, evaluates the Taylor polynomial of degree 13 for `e^r`, and multiplies by `2^k` as a product of two powers of two built from their bits with `Float.ofBits`.  It returns `x` for NaN, infinity above 709.8, and 0 below -745.2.  `Float.ofBits` compiles to `f64.reinterpret_i64`, which keeps a NaN payload while Lean's model does not, so the proof shows that `v <<< 52` is never a NaN pattern (`F64Bits.shiftLeft_52_not_nan`).  No theorem bounds the error against the true exponential, and [the tests](#tested) measure it.

`softmax_implements` proves `softmax xs`, which takes the maximum by a loop, sums `exp (xs[i] - max)` by a second loop, and builds the array of each exponential divided by the sum, bit for bit.  It calls `exp` in its sum loop and in each element.  `ImplementsPure` states that a function of scalars returns `f x` and keeps the store, for every store: `Func.implementsPure` proves it for a compiled function whose body keeps the store, `ImplementsPure.implements` derives `Implements`, and `Stmt.callPure_spec` proves a call that keeps the store.  Call arguments are typed expressions, so a call can pass a float, and the compiler allows calls in loop bodies and array elements when every argument and result is a scalar.

`matVec2_implements` proves `matVec2 w1 w2 x hidden d = matVec w2 (matVec w1 x hidden d) d hidden`, in which the intermediate vector is a temporary array: a `let` at the top of the body binds it, the second call borrows it, and the compiler releases it at the end of the function.  Releasing it requires that every array still live lies apart from it, so `Implements` has a freshness clause: every object the result owns lies apart from each array borrowed or owned before the call, stated through the `Represent` method `outside`.  The keep clause for owned arrays also keeps their capacity, since an owned array's block is measured with it.

`matMul_implements` proves `matMul a b n k m`, the product of an `n × k` and a `k × m` matrix stored by rows, bit for bit.  Each element is a loop over the shared dimension, with read positions that use unsigned division and remainder by `m`.  The proof splits on `m = 0`, where the IR's operations test for a zero divisor and Lean's define that case directly.

The MLP of a transformer block is proved in pieces.  `add` (element-wise sum) and `geluArray` are kernels built with the copying template.  `tanh z = 1 - 2 / (e^(2z) + 1)` and GPT-2's `gelu` are functions that keep the store, proved with `Func.implementsPure`, so `geluArray`'s elements may call `gelu`, which calls `tanh`, which calls `exp`.  `mlp x w1 w2 t d f = matMul (geluArray (matMul x w1 t d f)) w2 t f d` is a composite with two temporaries, proved with `Live`.

Row-wise layer norm normalizes each of the `t` rows of a `t × d` matrix stored by rows.  Two kernels compute each row's mean and inverse deviation once, `rowMeans` and `rowInvStd`, each a build whose element runs a loop over the row.  `normalizeRows` builds each element from five reads at positions `e`, `e / d`, and `e % d`, and splits on `d = 0` as `matMul` does.  `layerNormRows x g b t d eps` calls the three kernels in turn and holds the means and the inverse deviations as temporaries.

Masked attention uses `nh` heads of width `dh` on rows of width `d = nh · dh`, as GPT-2 splits them.  `maskedScores q k t nh dh scale` builds `t` rows of `nh` blocks of `t` scores: element `(i, h, j)` is `scale · (q[i] · k[j])` over the columns of head `h` where `j ≤ i`, and a masked element reads no key.  Storing the scores by position first keeps rows `0` to `i` a prefix of every array.  Row-wise softmax consists of `rowMax` and `rowSumExp`, which read elements `0` to `r / nh` of row `r`, and `softmaxApply`, joined by the composite `softmaxRows`.  `causalMatMul p v t nh dh` multiplies each head's weights by that head's columns of the values, with row `i` summing over rows `0` to `i` of `v` only.  `attention x wq bq wk bk wv bv wo bo l t nh dh` computes `q`, `k`, and `v` with `linear`, the masked scores with `scale = 1 / √dh`, the softmax of each of the `t · nh` rows of scores, the product with `v` by `causalMatMul`, and the product of that with `wo`.

[`Examples/Gpt/Causal.lean`](../Examples/Gpt/Causal.lean) proves `attention_rows` and `block_rows`: when two inputs agree on rows `0` to `i`, so do the outputs, for `t`, `nh`, and `dh` below `2 ^ 16` and `f` below `2 ^ 32`, which exclude overflow in the `UInt64` index arithmetic.  The two inputs may have different numbers of rows `t` and `t'`, both above `i`.  The theorems concern the Lean definitions, and with `Implements` they hold for the bytes.

`block x g1 b1 wq bq wk bk wv bv wo bo g2 b2 wfc bfc wproj bproj l t nh dh f eps` is one transformer block in the form of GPT-2's: `r = x + attention (layerNormRows x g1 b1)`, then `r + mlp (layerNormRows r g2 b2)`.  Its four linear layers use `linear x w b n k m`, the product `x · w` plus the bias `b` in each column, summed before the bias is added, as in GPT-2's `conv1d`.  The weight arrays stack the layers one after another, and `linear`, `normalizeRows`, and the functions that call them read layer `l` at an offset: `w[l · k · m + …]` for a `k × m` matrix and `b[l · m + …]` for its bias.

`forward` is the forward pass of GPT-2 with `layers` blocks: `embed` adds row `tokens[i]` of the token embeddings to row `i` of the position embeddings, a loop over the layers applies the blocks, then a final layer norm, and `matMulT` scores each position against every token embedding.  The loop is `LeanExe.loop layers x0 fun l x => block x … l …`, which the compiler translates to `Stmt.arrayLoop`: a copy of `x0` into the loop's state, then one call of `block` per layer, each followed by the release of the previous state.  `Live.arrayLoop` proves the statement, and `Live` proves `forward`.  `forward_prefix` proves that row `i` of the scores depends only on tokens `0` to `i`, whatever the number of tokens, under the same bounds with `vocab` added, by induction over the layers.  `layers_rows` states the same for the input of every layer, and `forward_causal` is the case of equal numbers of tokens.

`steps_exact` states that `step` run on tokens `0` to `p` from an empty cache, followed by `scores`, equals row `p` of `forward` on any `T > p` tokens, as `Array Float`: the same floating-point values bit for bit.  The hypotheses bound the dimensions so that no `UInt64` index wraps: `T`, `nh`, `dh`, and `layers` below `2 ^ 16`, `f` and `vocab` below `2 ^ 32`, `nh` and `dh` positive, and the whole cache, `T · (2 · layers + 1) · nh · dh` values, below `2 ^ 32`.  The proof uses an invariant on the cache: block `j` holds row `j` of the last layer's input and rows `j` of each layer's keys and values, as `forward` on all `T` tokens computes them.  Each kernel that `layerStep` runs on one row computes the corresponding row of `block`'s kernel, and the attention kernels `stepScores`, `stepSoftmax`, and `stepMix` compute row `p` of `maskedScores`, `softmaxRows`, and `causalMatMul` from the cached keys and values.  With `step_implements` and `scores_implements`, the compiled cached generation computes `forward`'s rows exactly.  `step` consumes the cache, and `appendBlock`, `cache ++ s`, compiles to `Stmt.append`.

[`Examples/Gpt/SampleVerify.lean`](../Examples/Gpt/SampleVerify.lean) proves the sampler.  `negInfs` is a build, `insertTop` a build whose position comes from a loop counting the buffer entries not below the new score, and `sampleFrom` a function that keeps the store: one loop sums the weights of the kept scores, and the other chooses the token, with calls of `exp`, `splitMix`, and `unitFloat`, whose theorems `splitMix_pure` and `unitFloat_pure` hold in any module that contains them.  `topKBuffer` is an array-state loop of `insertTop` calls that starts from `negInfs k`, and `sampleTopK` calls `topKBuffer`, passes the buffer to `sampleFrom`, and releases it, using the `Live` rules `Live.callScalar_seq` and `Live.releaseFirst`.

`scale_bytes`, `gcd_bytes`, `sumArray_bytes`, `folds_bytes`, `pairSum_bytes`, `sumCount_bytes`, `axpy_bytes`, `scaledHypot_bytes`, `piecewise_bytes`, `sumSquares_bytes`, `mean_bytes`, `bucket_bytes`, `clob_bytes`, `gpt_bytes`, `prng_bytes`, and the bytes theorems of the other examples combine these with `round_trip`: `encode` succeeds on the module, and the decoder reads the bytes back as a module that implements its functions.  The kernel checks that encoding succeeds by evaluating the encoder (`decide +kernel`).  All of these theorems, the rule lemmas, the runtime specifications, and `decode_encode` depend only on `propext`, `Classical.choice`, and `Quot.sound`.  The proofs use ProofKit's kernel-checked `Memory.read64_write64` and remove CodeLib's `Mem.read64_write64_same`, which is proved with `bv_decide`, from the `simp` set in `RuntimeSpec.lean`.

`alloc` and `release` follow Knuth's first fit and liberation with a sorted list (TAOCP vol. 1, §2.5, Algorithms A and B).  `alloc` takes the first free block that fits.  When at least 56 bytes would remain, it lowers the block's size word and places the object at the block's upper end, so the free block keeps its place and link.  `release` walks the free list, which is in address order, to the first block above the freed one, then merges the freed block with that block and with the block before it when their regions touch.  `FixedArrayReuse.program_spec` proves the split, `findPlace_spec` the walk, `joinProgram_spec` one merge, and `freeObject_spec` the whole return of a block.  Safety does not depend on the order of the list, and a merged block's region is the union of two free regions.  `FreeListAt.release` proves that the list stays laid out, `insertFree_cover` that every new block starts and ends where an old block or the freed block does, and `insertFree_apart` that a region apart from the freed block and every free block stays apart from every new block.  `Heap.Borrowed.release` and `Heap.Owned.release` take `Heap.At`, because `release` writes the header of the free block below the freed one.  The proofs bound `top` within one call, and a test covers memory across a session.

`euler_solve`, `euler_reconstructed_solve`, and `euler_solve_total` state that the bytes of `euler.module` compute both Euler solvers.  The last states that, from the allocator state of a fresh instance with a memory cap of at least 1,407 pages, both solve exports return their words without a trap and end within 1,407 pages.  `run_reference_balance` and `reconstructedRun_reference_balance` state conservation against the exact Rusanov flux through the boundary.  `drone_compute` and `drone_safe` state that the bytes of `drone.module` compute the planner, whose flight is optimal among admitted flights and safe in the point-mass model, and `drone_compute_total` states complete execution within 70 pages.  `primeFactors_bytes`, `lookup_bytes`, `below100_bytes`, `increment_bytes`, `removeZero_bytes`, `gcd_bytes`, and `treeLookup_bytes` state that the bytes of the small examples compute their specifications, written apart from the programs, and `increment_total` states complete execution without memory growth.

## Tested

[`tests/modules/run.sh`](../tests/modules/run.sh) compares every case of each module's `Cases.lean` between Wasmtime and native Lean.  For `scale`, the cases include a zero divisor and products that wrap.  For `gcd`, they include zero arguments, consecutive Fibonacci numbers, and `(2^64-1, 2^64-59)`.  For `sumArray`, `pairSum`, and `sumCount`, the host allocates the input through `alloc`, and the allocation and free counters show every block freed after the host releases the result and the input.  A `pairSum` session shows the second call reusing the block the first freed, and releasing an array whose child mask marks its one element as a pointer frees both the array and the child.

The float modules return the same bits as native Lean on chosen and pseudo-random inputs.  `axpy` covers infinities, the canonical NaN, signed zeros, a subnormal result, overflow, and two-rounding cases.  `scaledHypot` covers division by both signed zeros, overflow and underflow in the squares, and NaN.  `piecewise` covers equal values, both signed zeros, NaN in each position, and inverted bounds.  `sumSquares` covers the empty array, infinities, NaN, subnormals, overflow, and small terms added before and after a large one.  `mean` covers empty arrays, and `bucket` covers NaN in each position, infinities, division by zero, and results at and beyond `2^64 - 1`.  The host passes and prints `f64` values as bit patterns (`f64:BITS`) and float arrays as `array-u64:` with the elements' bit patterns.

`clob.wasm` holds the ten CLOB operations, `runCommands`, which folds `applyCommand` over an array of commands, and `stepCommand` and `runOut`, which also append the best bid after each command to an output array.  The cases reach every path of `applyCommand`, including empty books, prices equal to an existing level, above every level, and below every level, positions at and past the end, quantities and costs that wrap past `2^64`, and arrays of different lengths.  Native Lean prints its panic message for out-of-bounds reads and for `insertIdx!` past the end, and it returns the default value, as the compiled code does.  In a session, eight `addBid` calls build a book from two empty arrays, `removeLevel` and two `cancelBid` calls change it, the host releases each superseded array, and the final book and the counters, with as many frees as allocations, match native Lean.  [`tests/modules/chunks.py`](../tests/modules/chunks.py) applies CLOB commands in chunks and one by one.

`gpt.wasm` holds the GPT kernels and composites, the cached step's functions, and the sampler.  [`tests/gpt/run.sh`](../tests/gpt/run.sh) compares every export with native Lean on chosen inputs, with empty and zero-sized arrays, arrays shorter or longer than their dimensions, infinities, NaN, signed zeros, overflow, subnormals, one to three heads, zero to three stacked layers, and caches built step by step.  [`tests/gpt/sessions.sh`](../tests/gpt/sessions.sh) checks that every session frees every allocation, temporaries included.  `exp` matches native Lean bit for bit on special values, 400 points from -745 to 710, and arbitrary bit patterns.  Against the C library's `exp` in native Lean, its error is at most 1 unit in the last place on 400,000 points from -745 to 710, 90 percent of them exact, and the special values match exactly.  A session that appends a block of 1,000 words to a cache 256 times with `appendBlock`, which appends in place, ends with 4,128,768 bytes of memory and 11 frees: nine when the cache outgrows its block and two at the end.

`forward` computes the same function as Hugging Face's `GPT2LMHeadModel` (transformers 5.18.0, PyTorch 2.14.1, float64, `attn_implementation="eager"`), with every parameter drawn from a normal distribution with standard deviation 0.5 and 1 added to the layer-norm gains.  Over ten configurations, with zero to twelve layers, one to four heads, widths up to 16, hidden widths up to 64, vocabularies up to 50, and up to eight tokens, and three seeds each, the largest difference between the two sets of scores is 2.7e-15 of the largest score.  The differences come from the order of summation and from `exp` and `tanh`.  The configuration with width 1 matches exactly.

On the GPT-2 124M weights, `forward` matches Hugging Face's model in float64.  `gpt2_compare.py` writes the twenty weight arrays, about 1.0 GB, to files that the host loads with its `file-u64:PATH` argument kind.  For prompts of 5, 30, and 224 tokens, every score differs from Hugging Face's by at most 6.4e-15 of the largest score, and the steps from an empty cache give `forward`'s last row bit for bit.  With the cache, the script runs one host session that loads the weights once with the session command `file-u64 ID PATH`, keeps each new cache with `keep ID VALUE`, and writes the scores to a file with `save-u64 VALUE PATH`.  Greedy generation from a 5-token prompt to 256 tokens chooses Hugging Face's token at every step, with differences of at most 1.16e-13 of the largest score, and the session ends with about 1.08 GB of memory, the weights and about 100 MB.

`lists.wasm` holds `listSum`, `listRange`, and `sumRange`, and `words.wasm` holds `Words.first`, `Words.sumAcc`, and `Words.range` over a user list type whose `Encode` instance gives the layout of `List UInt64`.  They match native Lean on lists whose sums wrap, long lists, and counts up to 1,000, and a `sumRange` call shows as many frees as allocations.  The host's `chain-u64:` argument kind allocates the records and writes their headers, and its result kind of the same name walks the records and checks each header.

The decoder test runs the official testsuite: every valid module in the decoder's subset decodes to the reference and round-trips, and every malformed module in the subset is rejected.  [`tests/drone/run.sh`](../tests/drone/run.sh), [`tests/verified/run.sh`](../tests/verified/run.sh), and the WGSL tests are described in the drone README, the verified compiler's README, and [the manual](manual.md).

## Decisions

| Decision | Reason |
|---|---|
| The system stays as small as possible, and per-program IR proofs carry more of the burden. | LTG knowledge bases help with those proofs. |
| The compiler is verified rule by rule, and each proved rule enters LTG. | Each rule's theorem shortens every proof that uses the rule, without enlarging the trusted base. |
| Development proceeds in increments.  Each takes one program from Lean source to bytes, a proved `Implements`, a Wasmtime comparison with native Lean, an axiom audit, and a commit, adding only what that program needs. | Building whole layers before connecting them defers every integration error. |
| The compiler reads unfolding equations (`getUnfoldEqnFor?`), so a recursive call appears as a call of the definition. | It avoids recognizing the term shapes Lean generates for structural and well-founded recursion. |
| The compiler emits the IR as a definition and the module as `compile ir`. | The module is tied to the IR by definition, and a wrong compiler match makes the proof fail. |
| The compiler emits hints keyed to positions in the decoded module.  They can move into a WASM custom section, with names in the `name` section, when proving from the bytes alone becomes a goal. | Hints need not be exact.  The decoder skips custom sections, so no theorem changes. |
| Statements get `wp` rules only, packaged as `Triple` over the store and IR state.  `while` is the only loop, with a `done` local for several exits. | It keeps one semantics, Talos's, and adds no simulation theorem.  Every IR rule is a lemma about WASM code, which serves proving from bytes. |
| `Expr.eval` with `Expr.program_spec` serves as the expression rule. | It is proved, and per-program proofs can rewrite with the evaluator. |
| `Implements` is one statement over a `Represent` class.  Every compiled module has a memory and the runtime globals. | A module without memory would make `Heap.At` false and the theorem vacuous. |
| Every object has one owner, values move at their last use, and an owned array at its last use is updated in place. | Lean values can be shared, so ownership must be established in the source: moves make every reference count 1, and `release` needs no count. |
| Runtime integers are fixed-width only.  `panic` compiles to `default`.  Recursive values are supported. | Bounded `Nat` traps where Lean returns the exact value, and Lean's logic gives `default` for an out-of-bounds `a[i]!`. |
| I/O uses a pure step function, `State → Input → State × Output`, driven by a fixed adapter, trusted until proved. | Each `step` call is pure, so `Implements` covers it. |
| `release` and the runtime counters are absent from the source dialect.  Modules keep the counters as globals. | Their values are 0 in Lean and real in WASM. |
| Floating-point theorems describe the WebAssembly deterministic profile. | Talos implements it, and it matches Lean's float model. |
| Programs use Lean's `Float` and `Float32`.  `neg`, `abs`, and `ofBits` get a NaN check, and `min` and `max` compile as a comparison and a select. | Lean's model and WASM differ on those operations. |
| LTG is a directory of entries, searched directly and checked by a Lean script. | The script checks that every declaration an entry names exists. |
| Expressions read memory: `Expr.eval` takes the memory, and `Expr.read` compiles `xs[i.toNat]!` to a bounds-checked load.  Statements are the only writers, through `store address value`, with 64-bit words and 32-bit address wrapping. | WebAssembly loads are expressions, and a read inside an expression keeps each program's proof close to evaluating the source. |
| Every module contains `alloc` and `release` at functions 0 and 1, with the allocation and free counters.  `release` is not recursive: it frees an object and, through a loop over its masked slots, the objects it owns. | A recursive `release` uses one WASM stack frame per node. |
| A value that needs statements (a load or a loop) compiles to statements before its expression, placed inside the branch that needs them, never hoisted out of an `if`.  `Array.foldl` with a lambda and default bounds becomes a counted loop, `Nat.toUInt64 xs.size` a load of the length word, and an array literal of k elements an allocation of 48 + 8(k + 1) bytes followed by stores. | Hoisting a load out of a guarding branch can trap where Lean returns a value. |
| The compiler places a fold's statements at the start of the function body, so it rejects a fold in a branch, in a fold body, or in a recursive definition. | Placement inside branches is added when a program needs it. |
| GPT-2 is the target: the same function as OpenAI's published code and Hugging Face's PyTorch model.  Attention has `nh` heads of width `dh`, with `d = nh · dh`, and the four linear layers have biases.  Tests compare with Hugging Face's model in float64. | Passing `nh` and `dh` leaves no invalid head configuration.  Both sides in binary64 differ only in summation order and in `exp` and `tanh`. |
| Python tools enter the repository only as uv-runnable scripts with PEP 723 metadata, always run with `uv run`. | Each script carries its dependencies, and no environment outside the repository is needed. |
| The number of layers is a loop parameter: `LeanExe.loop` has an array state, its body may call allocating functions, each iteration releases the previous state, and the kernels read each layer's weights at an offset in stacked arrays. | A loop keeps the composition inside the proofs.  GPT-2 fixes the layer count only through its weights. |
| The loop copies its initial array into its state, so the state is always owned and each iteration releases the previous one.  The loop body is one call that returns the next state. | With one call in the body, the loop rule needs one callee specification and one `Live` step per iteration. |
| The GPT-2 124M test uses the pinned `openai-community/gpt2` checkpoint (revision `607a30d783dfa663caf39e06633721c8d4cfcd7e`), widened from binary32 to binary64, with prompts of at most 256 tokens.  The test script writes one file of little-endian words per array, and the host loads each with `file-u64:PATH`. | Binary64 keeps the proved pipeline unchanged.  The memory the calls use stays below 4 GiB. |
| Generation uses a key and value cache.  A theorem proves that the cached steps give the same bits as the corresponding row of `forward`, so `forward`'s softmax reads entries `j ≤ i` only, and `forward` and a step perform the same operations.  Attention reads earlier positions from the cache and the new position from the new key and value, the layer loop carries the row and the new keys and values, and `step` appends the new block in place.  The cache is one block per position, holding that position's key and value for every layer and its final hidden row, and a separate `scores` reads the last block. | Without a cache, generating to 256 tokens takes an estimated 3.8 hours.  The design needs no capacity parameter and keeps the cached path inside the proved functions.  Dropping the masked entries from the softmax leaves attention's output unchanged: Lean's `max` is `if x ≤ y then y else x`, so `max acc (−∞)` is `acc`, `exp` returns +0.0 below −745.2, and the running sum starts at +0.0, so adding +0 leaves it unchanged. |
| The generated composite proofs take the arguments apart with `Represent.borrowed_float_pair`, prove argument evaluation with one `Expr.evalResults` lemma per argument, and release temporaries with `Live.releaseSecond_seq`. | `rintro` on the undestructured argument tuple grows with the fourth power of the number of arrays, and `simp` over long argument lists costs seconds per call. |
| Attention is causal for all inputs: a masked score reads no key, and the product with `v` reads rows `0` to `i` only.  Loops in value-level branches are unsupported. | An additive mask over all keys lets a later row turn an earlier row into NaN.  The loop counts implement the mask without a compiler change. |
| `Stmt.fold` is a definition built from existing statements, and its rule lemma is stated about that definition.  The fold body is an expression, so a nested fold is rejected. | The IR keeps six constructors, and the lemma needs no new `wp` rule. |
| Rule lemmas state what they leave unchanged with `State.Frame scratch writes before after`: the same numbers of parameters and locals, and the same value at every local below `scratch` outside `writes`.  A rule lemma takes a precondition that fixes the store and the state, and `Triple.of_forall` reaches that form from any precondition. | `State.Frame` is transitive, expressions preserve it (`Expr.eval_frame`), and the lengths let later assignments and scratch writes succeed. |
| `Func.implements_heap` takes arguments of any `Represent` type, and its body `Triple` may use `Heap.At`, the cap premise, and the arguments' representation in the initial store.  It aborts or ends with some heap for which the invariant and the arguments' representation hold.  `Func.implements` is its case for a body that keeps the store. | One entry rule serves every argument type. |
| The compiler computes hint positions from code lengths, which do not depend on the scratch index. | The number of compiler variables, and so the scratch index, is known only after translation. |
| `Triple` takes the module as a parameter. | A call rule needs the callee's `ReturnsOrAborts` in that module, which `wp_call_returnsOrAborts` consumes. |
| `Implements` states that a call returns the correct result or traps at `unreachable`, with no premise about free memory.  `Triple` assumes that its assertion accepts that trap.  `alloc` traps when memory cannot grow, the build template traps for `2 ^ 29` or more elements, and every compiled module declares at most 65,535 pages, which `Implements` assumes of the memory's cap. | A premise about free memory does not compose across calls, because each call's bound adds to `top` and nothing bounds fragmentation.  A trap is a visible failure, so the theorems describe every completed call.  With at most 65,535 pages every block ends below `2 ^ 32`, the bound the free-list proofs use.  Complete execution is stated separately, with `ImplementsA` and an allocator budget. |
| `call func args result` is one IR statement for any function, with a rule parameterized by the callee's specification. | The same statement serves the runtime functions and calls between compiled functions. |
| `release` checks the child mask before it walks any slots. | Freeing an array without child pointers would otherwise take one loop iteration per element to test a zero mask, and the check removes two nested loops from the proof of the common case. |
| `Heap.Owned` records that the object ends inside the 32-bit address space. | The freed block's free-list entry needs it, and every allocated block satisfies it. |
| An array literal that a fold consumes becomes a temporary: the compiler allocates it before the fold and releases it right after. | The fold is the temporary's only use. |
| Proofs may not use `bv_decide` or `native_decide`. | Both add an axiom that trusts compiled code. |
| IR `f64` values are bit patterns, and `Expr.eval` applies Talos's `IEEE64` functions.  Per-program proofs connect Lean's `Float` through `F64Bits.toBits_add` and its siblings. | The IR means what its compiled code does, and the equality theorems enter once, as `simp` lemmas. |
| `Func` is typed: `params` and `vars` list the types of the parameters and the compiler's variables, and `result` pairs a type with an expression of that type.  Scratch locals are 64-bit words. | `Float` arguments, results, and variables use WebAssembly's `f64` type, and a load of an `f64` adds `f64.reinterpret_i64`.  A dependent pair keeps equations such as `func.result = ⟨.u64, .get n⟩` free of casts. |
| Folds run over an `Array UInt64` or an `Array Float` with a `UInt64` or `Float` accumulator. | An `Array Float` is stored as the `Array UInt64` of its elements' bit patterns, so the fold rule and the heap specifications apply to it unchanged. |
| The dialect's float array is `Array Float`, and `FloatArray` is not supported. | Lean core has no lemmas about `FloatArray`, and the loop of `FloatArray.foldlM` is private, so a proof about its fold depends on a private declaration.  `Array` has public lemmas and literal syntax.  In WebAssembly both types have the same unboxed layout.  In native Lean, `Array Float` stores each element as a separate heap object, which costs speed and memory in native runs only. |
| Loops use `LeanExe.loop (n : UInt64) (init : α) (f : UInt64 → α → α) : α`, with `UInt64` indices and `xs[i.toNat]!`, which yields 0 out of bounds.  A loop state of several variables compiles to several locals. | Compiled `UInt64` arithmetic equals Lean's, so no proof concerns overflow, and the loop rule resembles the fold rule.  `Nat.fold` would need overflow facts for index arithmetic, a tail-recursive helper needs a proof of each iteration, and `for` loops would require recognizing the elaborated `forIn`.  Loops do not stop early.  Tail recursion covers early exit. |
| Programs build arrays with Lean's operations (`set!`, `insertIdx!`, `eraseIdxIfInBounds`, `push`).  An owned array at its last use is updated in place, and any other use copies through one copying template, whose rule is proved once.  One lemma per operation equates the operation to the template by `Array.ext` and core's `size_*` and `getElem_*` lemmas.  `LeanExe.build` builds arrays computed by index. | The source is the specification, and Lean's operation names state it more clearly than index functions.  Core's lemmas about these operations serve later proofs about programs. |
| A module holds several functions: `leanexe_compile name := [f, g, …]` compiles the listed definitions, exports each, and compiles a call to a listed function as `call`.  Each function has its own `Implements` theorem, and a call rule takes the callee's theorem as its premise. | Each callee is proved once.  Inlining would repeat callee proofs at every call site, and separate linked modules need theorems across instances.  The explicit list keeps the module's contents in the source. |
| A function returns several values as WebAssembly multi-value results, one per component: a pair is its first component's values followed by its second's, as in `Represent` for pairs. | This follows the pair representation the proofs use and needs no heap object per tuple.  Arrays of flat records store each record as its words, as the `grids` example shows. |
| `Implements` has a frame clause that covers every region of the heap apart from the consumed blocks, which includes the caller's arrays and trees. | Composing a call with the callee's theorem requires it: a caller holding a new array must know the call leaves it intact. |
| `Implements` states that the memory's maximum size (`memoryCaps`) is unchanged. | A call after another call needs room in the store the first leaves, and room depends on the maximum size.  The allocation rules prove the fact (`Heap.NewArray.caps`). |
| The copying template runs a statement per element (`Stmt.buildWith`), so an element of `LeanExe.build` may run a loop.  The statement may not allocate or call. | The matrix-vector product needs a loop per element.  One rule covers the template with and without the statement. |
| `exp` is a Lean definition proved exact against itself.  Its accuracy is measured by tests. | Lean's `Float.exp` is `opaque`, so no proof can state its value.  A proved error bound is a separate, larger piece of work. |
| A function of scalars may be called in a loop body or an array element when its theorem, `ImplementsPure`, states that it keeps the store. | Softmax calls `exp` there.  The general call rule cannot apply, because `Implements` does not say that a call keeps the store. |
| A `let` at the top of a function body may bind an array from a call or a build.  The compiler releases it at the end of the function.  `Implements` states that a call's result is fresh and that owned arrays keep their capacity. | Kernels combine by calls with intermediate arrays.  Without freshness, `Implements` would allow a function to return its argument as its owned result, and a caller that released it would free its own argument. |
| `-x` compiles to `-0.0 - x`, `Float.abs` to `f64.abs`, and `min` and `max` to `f64.le` and a conditional.  `min` and `max` evaluate their operands twice. | Subtracting from negative zero is exact and canonicalizes NaN as Lean's negation does. |
| The compiler computes a float literal's bits, and proofs check them with `decide`. | The kernel evaluates Lean's `Float.ofScientific` for ordinary literals.  Exponents beyond Lean's default threshold need options raised. |
| `Heap.At` requires at most 65,536 pages, and `Heap.Borrowed` requires only that the input lies below `top` and outside every free block. | A 32-bit memory has at most 65,536 pages. |
| `alloc` follows Knuth's first fit and `release` his liberation with a sorted list (TAOCP vol. 1, §2.5, Algorithms A and B).  `alloc` places the object at the upper end of the first free block that fits and shrinks the block when at least 56 bytes remain.  `release` inserts the block in address order, merges it with free neighbors, and leaves `top` unchanged. | First fit without splitting or merging leaks memory whenever allocation sizes change between calls: the growing cache would need 5.05 GB for 256 positions.  A simulation of the run peaks at 100 MB with splitting and merging. |
| Top-k sampling runs in `gpt.wasm` as proved Lean code: `sampleTopK scores k temperature state` returns a token and the next generator state.  It keeps every token whose score is at least the k-th largest score counted with repeats, as Hugging Face's `TopKLogitsWarper` does, and draws from weights `exp ((s − max) / temperature)`.  The generator is SplitMix64, in its own module `prng.wasm` with proofs and tests and also compiled into `gpt.wasm`.  The CLI stays greedy unless `--top-k` is given.  Without `--seed` it takes a seed from the operating system and prints it to stderr. | Sampling in Lean keeps the whole generation step proved, and the CLI only passes the generator state along.  Hugging Face's rule is the reference users know.  A printed seed makes every run repeatable. |
| The verified compiler is a separate library, `Verified`, written as a Lean function from a typed source language with a `denote` to a module.  It shares the trusted base and `Implements` with `LeanExe` and copies the parts of the IR it needs. | The `LeanExe` compiler is meta code over `Lean.Expr`, so no theorem can cover it as a whole.  A compiler over a source syntax can have one theorem for every program it accepts. |

## Floating point

Lean 4.34 defines `Float` and `Float32` through `Float.Model` and `Float32.Model`, IEEE binary64 and binary32 with round-to-nearest, ties to even.  Every NaN in both models is the positive quiet NaN with only the top fraction bit set, `0x7FF8000000000000` or `0x7FC00000`, and `ofBits` converts every NaN input to it.  Talos's `IEEE64` and `IEEE32` return the same constants for every NaN result.

ProofKit proves `LeanExe.Float32.xBits = Wasm.IEEE32.x` for `add`, `sub`, `mul`, `div`, and `sqrt`, for all inputs including NaN.  The binary64 counterparts for all five operations are the `F64*.lean` files and `F64Bits`.  Lemmas that do not depend on the format are in `FloatRounding`, `FloatShift`, `FloatRationalRounding`, `FloatSqrtRounding`, and `FloatCommon`, which both chains import.  `IEEE64.roundDyadicMagnitude` and `roundRationalMagnitude` pass `rounded * 2^shift` to `roundScaledMagnitude` where the binary32 rounders encode the fields directly, and `roundScaled_mul_pow` bridges the two forms.  `F64Bits` restates the results as `(a + b).toBits = IEEE64.add a.toBits b.toBits` for Lean floats.  The wrappers are thin: `LeanExe.Float32.addBits` applies Lean's `Float32` addition to decoded bits, so the theorems also justify compiling Lean's float types directly.

Lean and WASM differ in three places:
1. Lean's `neg` and `abs` return the positive canonical NaN for a NaN input.  WASM `fneg` and `fabs` change only the sign bit.
2. Lean's `ofBits` canonicalizes NaN.  WASM `reinterpret` keeps the payload.
3. Lean's `min` and `max` choose an operand by `≤`.  WASM `fmin` and `fmax` return NaN for a NaN operand and order `-0` below `+0`.

The WebAssembly specification ([numerics](https://webassembly.github.io/spec/core/exec/numerics.html)) makes the sign of a generated NaN nondeterministic and its payload canonical only when every NaN input is canonical.  Its deterministic profile ([profiles](https://webassembly.github.io/spec/core/appendix/profiles.html)) requires that "All NaN values generated by floating-point instructions are canonical and positive," and Talos implements that behavior.  [`tools/wasmtime-host.c`](../tools/wasmtime-host.c) enables Cranelift's NaN canonicalization.  Browsers do not implement the profile, and on x86 `0/0` produces a negative NaN.  On aarch64, native Lean's `toBits` returns `0x7FF8000000000000` for a NaN with a payload, for `0/0`, and for `-(0/0)`.  Modeling the full profile in Talos, with an oracle choosing NaN results and the compiler canonicalizing NaN where bits become observable, is the route if theorems must cover results computed in a browser.

`IEEE64` has the same functions as `IEEE32` and calls `IEEE32.roundShift`, `roundQuotient`, and `roundSqrtIntegral` directly, so lemmas about those helpers are imported, not copied.  Binary64 comparisons rest on `F64Compare.compare_canonical`: decoding a non-NaN bit pattern gives a canonical unpacked float whose value is Talos's `scaledValue`, and Lean's comparison of canonical floats orders them by value.  Negation compiles to `-0.0 - x` (`F64Sign.sub_negZero`), absolute value to `f64.abs`, and `min` and `max` to a comparison and a conditional, which removes the three differences listed above.  `F64Convert` proves the conversions between `UInt64` and `Float`, and `F32Compare` and `F32Sign` give the binary32 comparison and sign theorems.  Conversions between `Float` and `Float32` have no theorems.

## GPU

The GPU path is in [`LeanExe/WGSL/`](../LeanExe/WGSL/) and [`Examples/Gpt32/`](../Examples/Gpt32/): a WGSL subset with a printer and a parser proved to invert it, a semantics, a proved translation of IR builds into kernels, and GPT-2's binary32 kernels with the theorem of the host program, `generate_host`.  The theorems hold under a device model of strict binary32 arithmetic, race-free dispatch, and no dynamic errors, so the trusted base grows by that model, the WGSL compiler of the driver or browser, and the GPU.  [The manual](manual.md#wgsl-kernels-and-the-browser-pages) describes the path and its tests.

## Scope of the theorem

1. The claim is about Talos's semantics.  Wasmtime appears only in tests, and the Talos interpreter and the decoder are trusted.
2. The premises `Heap.At` and `Heap.Borrowed`, and a memory cap of at most 65,535 pages, are assumed.  Every compiled module declares that maximum.  No theorem covers instantiation or the host.  A call may trap at `unreachable` when memory cannot grow or an array would exceed 32-bit memory, and the theorems state the result of every call that does not trap.  A module that always traps would satisfy them.  Talos's `memory.grow` succeeds whenever the new page count is within the maximum, while the WebAssembly specification lets an engine refuse growth for its own reasons.  `alloc` checks the result of `memory.grow` and executes `unreachable` on failure (`MemoryGrowth.growProgram`), so on such an engine the call traps and returns no result, a path the theorems do not describe.
3. `Implements` states a frame: every heap region below `top`, outside the free blocks, and apart from the consumed blocks keeps its bytes and lies apart from the result, and the memory's maximum size is unchanged.  It states nothing about memory outside the heap that the allocator manages.
4. `Emit.lean` evaluates `encode` with compiled Lean code.  For `gpt.wasm`, `gpt_file` in [`Examples/Gpt/File.lean`](../Examples/Gpt/File.lean), checked after the file is written, proves that the file holds `encode gpt.module`.  The elaborator `binary_file%` that reads the file is trusted.  No theorem covers the other modules' files.

No work on items 2 and 3 is planned.
