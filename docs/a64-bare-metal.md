# The AArch64 bare-metal path

The AArch64 bare-metal path compiles a Lean function, applied to arguments fixed when the program is built or read from the UART when it runs, or to a message of bytes read from the UART, to machine code that runs without an operating system on QEMU's `virt` machine, under QEMU's emulation (TCG) and under KVM on an AArch64 host.  The program writes the bytes of the function's value to the UART.  The goal is one theorem per program, checked by Lean's kernel, that connects the bytes the machine writes with the Lean function's value, and a list of the components that the theorem's reader must trust, each with its evidence.  The theorem is a chain of links: from the Lean function to a WebAssembly module, from the module to a model of the processor, and from the model, the image's bytes, the loader, and the startup to the running machine.

Proofs establish the links from the Lean function to a model of the boot machine for programs of integer, single-precision, and double-precision arithmetic and comparisons, calls, globals, and linear memory.  For each test program, a theorem checked by Lean's kernel starts from a state of that model whose memory holds the bytes of the program's image file at a base in RAM that is a multiple of 4096, such as 0x40200000, where QEMU places it, and ends at the call that turns the machine off, with the encoding of the function's value or a trap's status on the UART.  Tests support the model's agreement with QEMU and with the processor, and the loader's placement of each image.  A check of the model against Arm's specification covers every form on which the program's model runs, with the results of Arm's floating-point functions, the comparison that sets `FCMP`'s flags among them, taken as equations with the reference interpreter's IEEE 754 functions.  Tests against QEMU and the processor support the equations, as do proofs over Sail's Lean translation of the functions, which a script checks outside the repository's build.

| Link | What it states | Established by | Status |
|---|---|---|---|
| Lean function to WebAssembly | The module's run in the reference interpreter returns a representation of the function's value or traps at `unreachable` | The verified compiler's universal theorem | Proved |
| WebAssembly to the machine model | The generated code, run in the model, writes the encoding of the interpreter's result or exits with a trap's status | The simulation theorem | Proved |
| Encoding | The model's decoder reads every encoded instruction back as itself | A lemma over every form, and a comparison with the GNU assembler | Proved, and tested |
| Image bytes | The file holds every byte of the image that the generator gives: the header, the startup, the program, the vectors, the translation table, and the area's nonzero prefix | The kernel's evaluation of the generator, on every test run | Checked |
| Model to processor | The processor executes each emitted word as the model does | Co-simulation against QEMU and the processor, and a check against Arm's specification of every form, with equations for the results of the floating-point functions | Tested, and checked up to the floating-point equations, which rest on tests and on proofs over Sail's Lean translation that a script checks outside the repository's build |
| Startup | From the boot state, the startup reaches the premises of the program's theorem | A proof in a model of the boot machine | Proved |
| Loader | QEMU places the file's bytes where the theorem assumes them | A comparison of guest memory with the file before the first instruction | Tested, and trusted |
| UART | A byte store to the data register transmits the byte, and the receiver's registers return the input's bytes in order | QEMU's model of the PL011 and its character backend | Trusted |
| Exit | The run reaches PSCI SYSTEM_OFF with the status byte last in the output and every store to the UART complete | A proof in the model of the boot machine, and a halt after the call | Proved, and trusted after the call |

## From the Lean function to WebAssembly

The verified compiler translates a Lean function, written in the compiler's dialect, to a WebAssembly module, and one universal theorem, checked by Lean's kernel, covers every program that the compiler accepts.  For each compiled function the theorem states that, for arguments that represent the Lean arguments, the module's run in a reference interpreter, a WebAssembly interpreter written in Lean, either returns a value that represents the Lean function's value or traps at the instruction `unreachable`.  The compiler emits that trap when a call depth passes its guard, and the allocator reaches it when linear memory cannot grow, so the theorem needs no premise about free memory or call depth.  The theorem asserts its outcome from some amount of the interpreter's fuel upward and bounds no call depth, a gap that the stack check of the generated code closes.

The machine-code path composes this theorem with a simulation theorem whose premise is the interpreter's result.  The interpreter's run appears in the conclusion of the first theorem and the hypothesis of the second, and the composed statement relates the Lean function's value to the machine's output with no mention of that run.  Both theorems hold of the interpreter's semantics as Lean defines it, whatever its fidelity to the WebAssembly standard, so a departure of the interpreter from the standard cannot make the composed statement false.  The interpreter serves the path as an intermediate language whose semantics only the proofs use, and the testsuite runs that compare it with the standard concern the modules that the compiler emits for WebAssembly engines.  The program's theorem has the premise that the area holding the module's globals and linear memory holds the bytes that the module's initial store determines.  The image carries the area's bytes through the end of the memory's data segments under the kernel's check, and the startup's proof covers the zeros that follow them, so the theorem about the image file has no such premise.

## From WebAssembly to the machine model

### The code generator

The code generator takes the module that the verified compiler emits, the function to call, and its arguments, and produces a bare-metal program of AArch64 instructions.  The program's entry routine loads the arguments, calls the function, writes the result's bytes to the UART, and returns status 0, and the function, every function that its calls reach, and the trap stubs follow it.  The function's parameters are `i64` or `f64` values, each of which the entry routine loads as its 64-bit word, and the entry routine writes a result of either type as its word.  The generator reads the same module that the C translator reads, so it inherits the compiler's theorem for every function and needs no proof about the compiler's source language.  It accepts the subset that the bare-metal test programs need: comparisons and arithmetic on integers, calls, globals, 64-bit loads and stores of linear memory, the byte load `i32.load8_u` and the byte store `i32.store8`, the query and growth of the memory's size, and every double-precision form that the verified compiler emits: constants, the reinterpretations between `i64` and `f64`, the conversion of an unsigned `i64` to an `f64`, the saturating conversion of an `f64` to an unsigned `i64`, addition, subtraction, multiplication, division, square root, absolute value, and the comparisons for equality, less than, and less than or equal.  It also accepts every single-precision form that the compiler emits: constants, the reinterpretations between `i32` and `f32`, the conversions of an unsigned `i64` and of a signed `i32` to an `f32`, the saturating conversions of an `f32` to an unsigned `i64` and to a signed `i32`, the four arithmetic operations, square root, rounding to an integral value with ties to even, absolute value, and the same three comparisons.  It rejects every other form with a message.

WebAssembly's typing fixes the operand stack's height and the types of its values at every reachable instruction, so the generator assigns each height a register: X0 to X15, then X19 to X28.  The generator tracks the types and rejects a function whose operand stack would need more registers.  An `i32` lies zero-extended in its register, so the extension of an `i32` to an `i64` emits nothing and the wrap of an `i64` to an `i32` is one 32-bit `ORR`.  An `f64` lies in its register as its 64-bit word, so the reinterpretations emit nothing, and frames, calls, spills, and memory treat it as they treat an `i64`.  A binary `f64` operation moves the two words into D0 and D1 with `FMOV`, computes into D0 with `FADD`, `FSUB`, `FMUL`, or `FDIV`, and moves D0's word back into the register of the lower operand, four instructions in all.  The square root goes through D0 in the same way with `FSQRT`, the conversion of an unsigned `i64` is `UCVTF` into D0 and an `FMOV` back, the saturating conversion to an unsigned `i64` is an `FMOV` into D0 and `FCVTZU` back into the register, and the absolute value is `ADD Xr, Xr, Xr`, which drops the sign bit, and `LSR Xr, Xr, #1`.  A comparison of two `f64` values moves the words into D0 and D1, compares them with `FCMP`, and sets the register of the lower operand to 1 or 0 with `CSINC` and the inverse of `EQ`, `MI`, or `LS`, the conditions that hold after `FCMP` exactly when the operands are equal, the first is less, or the first is less or equal, each false when an operand is a NaN, as WebAssembly's comparisons are.  An `f32` lies in its register as its 32-bit word, zero-extended as an `i32` is, and an `f32` operation takes the same path through S0 and S1, the low 32 bits of D0 and D1, with `FMOV Sd, Wn` into them and `FMOV Wd, Sn`, which zero-extends the word, out of S0.  Rounding to an integral value is `FRINTN`, the conversions to an `f32` are `UCVTF Sd, Xn` or `SCVTF Sd, Wn` into S0 and an `FMOV` back, the conversions from an `f32` are an `FMOV` into S0 and `FCVTZU Xd, Sn` or `FCVTZS Wd, Sn` back, the comparisons use `FCMP Sn, Sm` with the same conditions, and the absolute value is `ADD Xr, Xr, Xr`, which moves the sign bit to bit 32, a 32-bit `ORR` with the zero register, which keeps the low 32 bits, and `LSR Xr, Xr, #1`.  An integer operation becomes one instruction on registers, and an integer comparison becomes a flag-setting subtraction and a conditional select, with the conditions GE and GT for the signed comparisons.  The arithmetic shift right is the logical shift between two copies of the sign mask, which X16 holds: `LSR X16, Xa, #63`, `SUB X16, XZR, X16`, `EOR Xa, Xa, X16`, `LSRV Xa, Xa, Xb`, and `EOR Xa, Xa, X16`.  A branch out of a block, loop, or `if` moves the value it carries into the register of the construct's base height and branches to the construct's target.  X16 and X29 serve as scratch registers, X17 holds the address of the area that holds the module's store, and X18 holds the stack's limit.

Each function has a frame on the stack: 8 bytes for each parameter and local, slots for spilled operand registers, and a slot for the return address, rounded up to a multiple of 16 bytes.  The prologue compares SP less the frame's size with the stack's limit in X18 and branches to a trap stub when the frame would fall below it, and otherwise stores the parameters into their slots and zeros into the other locals.  The compiler's theorem bounds no call depth, so the check turns an overflow into an outcome of the theorem.  A bound computed from the module, each function's frame plus the largest bound among the functions that its body calls, and 2^64 for calls that form a cycle, removes that outcome when the stack's room holds it, since the frames of the calls in progress hold all the stack that the program uses.  A call spills the operand registers below its arguments to the caller's frame, moves the arguments into the registers of heights 0 upward, branches with `BL`, moves the results into the registers of their heights, and reloads the spilled registers.  The callee preserves SP, X17, X18, and every byte of memory from the caller's SP upward, so the caller's locals and spills keep their values.

The area starts with the linear memory's size less 8, followed by the module's globals, one word each, and holds the bytes of linear memory from 4096 bytes above its start up to a cap fixed when the program is generated.  A load or store compares its address with the size less the access's offset and width, and branches to a trap stub when the address exceeds that bound.  A byte access compares the address with the size less 8, plus 7 less the offset, and reaches its byte with `LDRB` or `STRB` at the immediate 4095 above X17 plus the address plus the offset plus 1, since the byte forms' immediate field holds at most 4095 and linear memory starts 4096 bytes above the area's start.  The comparison uses the address register before any addition, so an address near 2^64 cannot wrap around the check.  The relation between the machine and the interpreter's store covers every byte below the cap, so growth of the memory needs no code that clears pages and updates only the size word.  The cap lies below 65,536 pages, and growth compares the new number of pages with it: for a cap below 4096 pages as the 12-bit immediate of `SUBS`, and for a larger one through the new size less 8, which it compares with the cap's size less 8 that `MOVZ` and `SUB` build in the register of the growth's delta.  Both codes take 16 instructions, so the size function and the layout do not depend on the cap.  The area ends at or below the stack's limit, so a store into linear memory never reaches a frame.

A trap branches to a stub that sets X0 to a status code and branches to the program's exit: 1 for the instruction `unreachable`, 2 for an access outside linear memory, 3 for a division by zero, and 4 for an overflow of the stack.  `UDIV` returns 0 for a zero divisor where WebAssembly traps, so the generator tests the divisor with `CBZ` before each division.  The exit takes the status out of the program without unwinding the frames, so code that does not trap pays nothing for the traps.

A second entry routine reads the function's arguments from the UART in place of loading constants, for a function of at most eight `i64` parameters.  It reads each argument as eight bytes, the lowest first, into the register of its parameter, X0 upward.  For each byte it loads the PL011's flag register UARTFR, 0x18 bytes above the data register, with a 32-bit `LDR` until RXFE, bit 4, is clear, and then loads the data register UARTDR, whose word holds the byte in bits 7 to 0 and the byte's error flags in bits 11 to 8.  When a flag is set, it branches to a stub that sets X0 to 65 and branches to the exit, so the run ends with the status byte 65 alone.  Otherwise it masks the byte, shifts it to its place with `LSLV`, and ORs it into the register.  Each byte takes ten instructions, three of which form the loop on UARTFR, and the rest of the routine, the call, the output, and the return, is that of the first entry routine.

A third entry routine runs a function over bytes, which takes one `LeanExe.Bytes` and returns one, on a message read from the UART.  It reads a length L of eight bytes, the lowest first, as the second routine reads a word, and ends with status 64 when L exceeds a limit `inMax` fixed when the program is generated.  It calls the module's allocator, function 0, with L, and reads L bytes into the block whose root the allocator returns: for each byte it polls UARTFR, reads UARTDR, branches to the stub of status 65 when the word carries an error flag, and stores the word's low byte with `STRB`.  It then calls the function with the root and L in X0 and X1, the two words of a buffer, writes each byte of the buffer whose root and length the function returns to UARTDR with an `LDRB` and an `STRB`, and returns 0.  `STRB` writes to the UART when its address is the UART's, so the generator emits `i32.store8` only in the programs of this routine, whose theorem assumes that the UART lies outside Normal memory.

The generator places code as it emits it.  Each function receives the address of its first instruction, and a size function computes the length of a construct before its body is generated, so the target of a forward branch is known when the branch is emitted.  The generator encodes each branch only after a check that its word offset fits the instruction's field, 19 bits for conditional branches and 26 bits for `B` and `BL`.  The code holds no absolute address other than the UART's, since the entry routine receives the area's address in X17, and that property lets the image run at any base.

### The simulation theorem

The simulation theorem relates the interpreter's state at a point of a function's code to the machine's state at the address of that point's code.  The relation places the value at each operand-stack height in that height's register with its type, local i in the frame slot at SP plus 8i, SP at a multiple of 16, and the interpreter's store in the area.  For each instruction and each instruction list, the theorem states what the machine does for each continuation that the interpreter gives.  A fall-through reaches the end of the code in a related state, a branch reaches its construct's target with the carried value in the register of the construct's base height, a return reaches the epilogue, and a trap reaches the stub of its code.  Throughout, SP, X17, X18, the UART's output, and the memory above the function's frame keep their values.

The proof runs by strong induction on the interpreter's fuel, with a lemma for each instruction form, a lemma that the generated code has the length that the size function computes, and a lemma for each construct.  A call uses the callee's simulation at one less fuel, the fuel at which the interpreter runs a callee's body.  Every theorem of the path depends only on Lean's standard axioms, propositional extensionality, choice, and quotient soundness, and the proofs use no decision procedure for bit vectors.

A whole-program theorem joins the compiler's theorem for the called function with the simulation of the entry routine.  Its premises state that memory holds the code's bytes at the entry routine's address, SP is a multiple of 16, the stack's room below SP is Normal memory, X17 holds the area's address, and the area holds the initial store's bytes in Normal memory below the stack's limit.  Its conclusion allows a result or a trap.  With a result, the machine returns to the address in X30 with SP restored and status 0 in X0 after appending to the UART's output the encoding of the Lean function's value, a word as eight bytes with the lowest first or an array as its length word followed by its elements.  With a trap, it reaches the exit with status 1 or 4 in X0 and has written nothing, where status 1 is the compiler's trap at `unreachable` and status 4 an overflow of the stack.  Statuses 2 and 3 cannot occur, because the compiler's theorem excludes those traps.  Status 1 disappears where the compiler's theorem without a trap covers the program's arguments, and status 4 where the stack's room holds the stack's bound.  The model's step is a function, so the machine's run is unique and passes through the outcome that the theorem names.  Theorems of this form hold, with the result as the only outcome, for GCD by a loop, CRC-32, SHA-256, whose result is an array, a CIC decimation filter on a table of 64 samples, whose result is the array of its outputs, the Euler solver on a grid of 4 by 4 cells, whose result is the array that the solver packs, GPT-2's scores of a cache's last position, whose result is the array of the scores' words, one binary32 layer of GPT-2 at a cache's third position, whose result is the array of the words of the layer's output row, a program of binary32 conversions on 64 inputs, whose result is the array of four words for each input, the exponential of [the library](../Library/Numerics/Float64/Exp/README.md) on 1 and on -740, and [the library's sine](../Library/Numerics/Float64/Trig/README.md) on 10 and on 10^22, whose arguments and results are doubles.  GCD by recursion keeps status 4, since its calls form a cycle and the bound is 2^64.  A recursion whose run in the interpreter traps at the depth guard keeps statuses 1 and 4, and it ends with status 1 under QEMU.

The whole-program theorem of the entry that reads its arguments, `InputRuns` of `LeanExe/A64/Proof/InputRuns.lean`, adds the premise that the receiver stands at its first byte with no read of UARTFR done, and it has two parts.  When the receiver delivers the bytes of n words with no error flag, the program behaves as the first entry routine does on those words as arguments.  When a byte among the first 8n carries an error flag and no byte before it does, the program reaches the exit with status 65 and has written nothing.  The proof of one byte's reads, `run_readByte` of `LeanExe/A64/Proof/Input.lean`, runs by induction on the number of reads of UARTFR that find RXFE set, and the proofs of the words compose it over the bytes and the words.  The proof joins the reads to the simulation of the call through a generic form of the program's theorem, which takes the entry routine's code and its effect as parameters, so the first entry routine's theorems keep their statements.  GCD by a loop has a theorem of this form, on two words read from the UART.

The whole-program theorem of the third entry routine, `BytesRuns` of `LeanExe/A64/Proof/BytesRuns.lean`, has the premises of `InputRuns` and the premise that the platform's UART lies outside Normal memory, and it has three parts.  When the receiver delivers the eight bytes of a length L of at most `inMax` and then L bytes, none with an error flag, the program writes the bytes of the function's value on those bytes and returns 0, or reaches the exit with a status that the compiler's theorem allows.  When the first eight bytes give a length above `inMax`, the program reaches the exit with status 64, and when a byte that the program reads carries an error flag and no byte before it does, with status 65, in both cases with nothing written.  `bytes_runs` derives it from the compiler's theorem of the function and the allocator's specification.  The loop that reads the message, `run_readMessage` of `LeanExe/A64/Proof/BytesMain.lean`, runs by induction on the bytes that remain, and after its writes the allocator's block holds a buffer of the message (`buffer_of_alloc`), which the compiler's theorem takes as its argument.  The simulation lemmas of `i32.load8_u` and `i32.store8` lie in `LeanExe/A64/Proof/ByteMemory.lean`.  A function that flips bit 5 of each byte has a theorem of this form, with a limit of 8,800,000 bytes, and so does `tabulate` of [the Oakland tabulator](../Demos/Rcv/README.md#the-aarch64-image), with the same limit and a cap of 11,392 pages that holds the bound of the compiler's theorem without a trap for every file within the limit.

## The machine model

The model describes the AArch64 instructions that the generator emits, executed in sequence by one core at exception level 1 (EL1).  Its state holds the general registers X0 to X30, the floating-point registers D0 to D31, which are the low 64 bits of V0 to V31 and whose low 32 bits are S0 to S31, SP, the program counter, the condition flags N, Z, C, and V, memory as a map from 64-bit addresses to bytes, the list of bytes written to the UART, and the counts of the UART's reads.  A platform supplies the set of addresses that hold Normal memory, the address of the UART's data register, and the values that the UART's receiver returns.  A step fetches the word at the program counter from a fixed map of code words, decodes it, and executes it, and it stops the model when the fetch, the decoding, or the execution fails.  The model has no exceptions and no interrupts: the boot protocol masks interrupts, nothing unmasks them, and every fault stops the model.

The instruction forms cover the move-wide immediates, addition and subtraction with an immediate or a register, flag-setting subtraction, conditional select with increment, the logical operations on registers in 64 bits and the 32-bit `ORR`, immediate and variable shifts, multiply-add, multiply-subtract, unsigned division, conditional and unconditional branches, branch with link, compare-and-branch on zero or nonzero, return, 64-bit loads and stores with a scaled unsigned offset, the byte load and the byte store, the 32-bit load, which the model runs only at the UART, the PC-relative addresses of `ADR` and `ADRP`, and the single-precision and double-precision forms that [the floating-point section](#floating-point) describes.  The startup's system instructions, `MSR`, `MRS`, `ISB`, `DSB`, `TLBI`, and `HVC`, are forms on which the program's model stops, and the model of the boot machine gives them their meaning.  The model's treatment of the flags, the stack pointer, and register 31 follows the pseudocode of the Arm Architecture Reference Manual.  Register 31 names SP as the base of a load or store and as an operand or destination of addition and subtraction with an immediate, and the zero register elsewhere, as the manual's encodings give.

A load or store may touch only Normal memory, and a load or store based on SP requires SP to be a multiple of 16.  The architecture raises an SP alignment fault in that case only when SCTLR_EL1.SA is set, and the model stops in either case, so the model is sound for either value of the bit.  An unaligned load or store to Normal memory succeeds, as it does on the processor while SCTLR_EL1.A is clear, which lets WebAssembly's unaligned accesses run as single instructions.  A byte store to the UART's data register appends the byte to the output, and a 32-bit load of the data register or of the flag register 0x18 bytes above it reads the receiver.  A 32-bit load elsewhere stops the model, and every other form reaches the UART only through Normal memory, so on a platform whose Normal memory excludes the UART's registers, as that of `Boot.platform` does, every other access to the UART stops the model.

The record `Rx` of the platform gives what the receiver returns.  For byte j it holds the word that the read of UARTDR returns, with the byte in bits 7 to 0 and its error flags in bits 11 to 8, the number of reads of UARTFR that find RXFE set before the byte arrives, and the other bits of each read of UARTFR.  The state counts the bytes read and the reads of UARTFR since the last read of UARTDR.  A load of UARTFR returns the flag word of the current byte and read, with RXFE set while the count of reads lies below the byte's wait, and a load of UARTDR after a read of UARTFR that found RXFE clear returns the byte's word and moves to the next byte.  A load of UARTDR before such a read stops the model, so the theorems need no meaning for a read of an empty receiver.  `Rx.Delivers` states that the receiver's words hold given bytes with no error flag, and `Rx.Flagged` that a byte's word carries a flag.  The record gives each byte a finite wait, so the model describes the runs in which every byte that the program reads arrives, and the theorems say nothing of a run whose input stops.

The model fetches from a fixed map of code words that the theorem derives from the initial memory's bytes, so a store never changes what the model fetches.  On the processor, a fetch after a store to code may return the old instruction or the new one until software performs cache maintenance.  The fixed map therefore matches the processor only if no store reaches the code.  The condition that excludes such stores reads: the platform's Normal memory excludes every byte of the code and every other byte of the image that must not change, such as the translation table, and the UART's address lies outside those bytes.  Under that condition a store into the code stops the model, and the program's theorem, which shows that the run reaches its outcome, shows that no such store occurs.  In the model of the boot machine, Normal memory excludes every byte of the image below the end of its translation table, so the condition holds for every image that Lean writes.

Wherever the architecture permits several behaviors, or depends on state that the model does not track, the model stops.  It stops on a word outside its forms, a fetch outside the code map, an access outside Normal memory, a 32-bit load other than one of the UART's data or flag register, a load of the data register before the receiver holds a byte, and a load or store based on a misaligned SP, and so, on the boot platform, whose Normal memory excludes the UART's registers, on any UART access other than a byte store to the data register and a 32-bit load of the data or flag register.  A theorem about a run that reaches its outcome excludes every such state, so the processor's behavior in those states has no bearing on the theorem, and tests of the model need to cover only the states in which the model runs.

## Encoding and the image's bytes

Every AArch64 instruction is one 32-bit word, and the encoder writes each form's word as its fixed bits plus its fields at their positions, as a sum of natural numbers.  A lemma proves that the model's decoder reads every encoded instruction back as itself, for every form and every value of its fields, and its proof reads each field back with linear arithmetic.  The simulation proof uses the lemma to turn the bytes of the code into the instructions that the generator emitted.  The decoder belongs to the model, since it gives the words their meaning in the theorem, and comparisons with the GNU assembler found that sample instructions of every form, with register 31 in each role and the extreme branch offsets, assemble to the encoder's words.  `tests/baremetal/a64-encode.sh` repeats the comparison for `LDR Wt` and `LDRB` on 128 samples, with register 31 in each role and the immediate at 0, 1, 6, and 4095, and checks that each of the assembler's words decodes to its sample.

The image's bytes come from the generator, which the build runs as compiled code.  A theorem about the compiled generator's output would trust Lean's compiler and runtime, so the path checks the written file in Lean's kernel instead.  An elaborator reads the file when the theorem is elaborated and gives its bytes as one number, whose base-256 digits are the bytes, and the kernel runs the generator on the program's module, function, and arguments, lays out the whole image as bytes, and compares their number with the file's.  The joined theorem's premise states that memory holds the file's bytes, so the compiled generator and the compiled code that wrote the file leave the trusted base, while the elaborator's reading of the file and the kernel remain.  The test driver elaborates these theorems on every run, and with one bit of a program's image file changed, the kernel rejects that program's theorem.  The kernel keeps the result of every reduction until it finishes checking a declaration, so its memory grows with the work of the evaluation, and three definitions limit that work.  The search for the functions that calls reach spends a step of its fuel on a new function alone, with the module's number of functions as the bound, so the kernel evaluates the bodies of the reached functions and no others.  The comparison forms the number of the image's bytes by pairing adjacent digits in rounds, which forms numbers of about the image's size in each round, where forming the number of every suffix would take memory in proportion to the square of the size.  The image joins its parts from the right, so that each byte of the code passes through one append.  The kernel's check of the Oakland tabulator's Image, 27,826 instructions, takes 107 s and a peak of 26.6 GiB, that of the Euler solver's Image, 11,649 instructions, about 12 GB and a minute, and that of the GPT-2 kernel's Image, 4,160 instructions, about 4 GB and 15 s, while the checks of the binary32 GPT-2 layer's Image, 7,660 instructions, and of the binary32 conversions' Image, 1,108, take about 10 GB and 36 s together.  The driver elaborates the theorems of the Euler solver's Image, of the GPT-2 kernel's Image, of the exponential's Images, of the sine's Images, and of the binary32 Images in a file for each of these groups.

## The image and the boot protocol

The image is an arm64 Linux Image, the format whose header and entry state Linux's arm64 booting document defines.  The header starts with instructions that branch to the startup, and it records the offset from a 2 MiB-aligned base at which the image must lie, the size of memory that the image uses from its start, flags, and a magic number.  The protocol lets the loader choose any 2 MiB-aligned base in RAM, so the image must run at any such base.  The startup computes every address it needs relative to the program counter, the generated code holds no address inside the image, and the translation table holds none either, so the image's bytes do not depend on the base.  A proof shows that the generator gives the same bytes at two bases in the RAM GiB that differ by a multiple of 4096, so each theorem, whose kernel check compares the file with the image at 0x40200000, holds at every such base.  The size in the header must cover all the memory that the image uses, including the area's zero tail and the stack, because the protocol reserves that much memory from the image's start and QEMU places the device tree at a 2 MiB boundary above it.

At entry the protocol guarantees that X0 holds the device tree's address and X1 to X3 are zero, every interrupt is masked in DAIF, the core is in EL2 or in Non-secure EL1, the MMU is off, the instruction cache holds no stale entry for the image, and the image's address range has been cleaned to the point of coherency.  QEMU's `virt` machine enters the image at EL1 under TCG and under KVM, with SP_EL1 selected, SP 0, and floating point trapped.  For a processor with floating point, the protocol requires CPTR_EL3.TFP to be 0 where EL3 exists and CPTR_EL2.TFP to be 0 where EL2 exists and the image starts at EL1, so that firmware does not trap the image's floating point.  The protocol requires that firmware initialize every writable system register at or below the entry level, but it fixes no value, and it says nothing of the TLBs, of most fields of SCTLR_EL1, or of which stack pointer is selected.  The startup therefore writes a complete value into every system register that it relies on, so no field keeps a value that firmware chose.

## The startup

The startup is a sequence of instructions that Lean writes into the image and that takes the core from the boot state to the state that the program's theorem assumes.  The header's first instruction selects SP_EL1, and the startup checks that the core runs at EL1, halts at any other level, and installs a vector table whose entries branch to themselves.  With the MMU off it writes SCTLR_EL1 with every field at its final value but the MMU's enable bit, writes CPACR_EL1 as 0x300000, which enables floating point, writes MAIR_EL1, TCR_EL1, and TTBR0_EL1, the last with the table's address computed relative to the program counter, and writes TCR2_EL1 as zero when the processor implements that register.  After a synchronizing barrier it invalidates the TLB entries of EL1, waits for the invalidation to complete, writes FPCR as 0x02000000, writes SCTLR_EL1 again with only the MMU's enable bit changed, and synchronizes again.  It then clears the zero tail of the area, sets SP to the top of the stack and X17 to the area's address, and calls the entry routine.

The translation table is one level-1 table of 1 GiB blocks, each mapping addresses to themselves.  The GiB from 0x40000000, which holds RAM, is Normal write-back memory, readable, writable, and executable at EL1.  The first GiB, which holds the UART at 0x09000000, is Device-nGnRnE memory from which the core cannot execute, and every other address faults.  With a 4 KiB granule and a 4 GiB input range the walk starts at level 1, so no table of a lower level is needed.

The MMU must be on for the model's rule on unaligned accesses to hold.  With stage 1 translation off, every data access goes to Device-nGnRnE memory, and an unaligned access to Device memory faults whatever SCTLR_EL1.A holds.  WebAssembly programs make unaligned loads and stores, and the generated code performs each as one instruction, so RAM must be mapped as Normal memory.

The barriers and the TLB invalidation follow from the architecture's rules on system registers.  A write to a system register affects later instructions only after a context synchronization event, such as an instruction synchronization barrier, so the startup synchronizes after its writes and again after it enables the MMU.  The write of FPCR follows the first barrier, since `MSR FPCR` traps at EL1 while CPACR_EL1.FPEN is 0b00 or 0b10 (the pseudocode of `MSR FPCR`, section C5.2.8, page C5-983), and the write of CPACR_EL1 governs that check only after a context synchronization event (section D24.1.2.2, pages D24-8470 and D24-8471).  FPCR is a Special-purpose register (page C5-974), whose writes take effect in program order without synchronization (section C5.1.5.1, page C5-947), so only the boot model, which puts every register's write in effect at a synchronization, needs the second barrier for FPCR.  The TLBs reset to an implementation-defined state, entries left by software that ran before the image survive while the MMU is off, and a TLB may cache fields of the translation registers, so the startup invalidates the EL1 entries after it writes those registers and completes the invalidation with a data synchronization barrier before it enables translation.  The two writes of SCTLR_EL1, the first with the MMU off and the second changing only the enable bit, keep any field of that register that a TLB caches at its final value.

The startup enables floating point and fixes its control register.  CPACR_EL1 holds FPEN as 0b11, under which no access to the SIMD and floating-point registers, FPCR, or FPSR traps at EL1 or EL0 (section D24.2.35, page D24-8585), and every other field clear, which keeps SVE and SME instructions trapped.  Every field of FPCR resets to an architecturally UNKNOWN value on a warm reset (section C5.2.8, pages C5-974 to C5-981), so the startup writes the whole register.  It sets DN, under which "any operation involving one or more NaNs returns the default NaN" (page C5-975), and clears every other field.  With RMode at 0b00 operations round to nearest, with FZ, FZ16, and FIZ clear no denormalized number is flushed to zero, AH and NEP clear exclude the alternative behaviors of FEAT_AFP, and with every trap enable clear no floating-point exception traps.

A proof joins the startup to the program's theorem in a model of the boot machine.  That model tracks the system registers that the startup writes, both as written and as in effect after synchronization, the selection of the stack pointer, the TLB's state as unknown, invalidation pending, or clean, and whether every store to the UART has completed.  It gives each address's memory type from the table's bytes for the one configuration that the startup establishes and stops in every other, it requires each instruction fetch to succeed under both the written and the effective registers, and it runs every instruction other than a system instruction by the program model's step, with the platform that the table gives once that configuration is in effect.  Before then, an instruction that touches no memory runs by the program model's step only when its next program counter lies below 2^55 or address tagging is off in both copies of TCR_EL1, since a branch under tagging, which firmware may leave on, replaces the top byte of a larger target, and a floating-point instruction runs only when both copies of CPACR_EL1 and FPCR hold the values that the startup writes.  The startup executes no floating-point instruction, and the proof lifts its runs of the program model from the code map without the words that decode to one.  The configuration that the startup establishes includes CPACR_EL1 at 0x300000 and FPCR at 0x02000000, so every instruction of the program runs with floating point enabled under that FPCR.  The tracked registers include FPCR, whose writes the architecture puts in effect at once, so the model, which puts them in effect at the next synchronization, is stricter there than the architecture.  `MSR FPCR` steps only when FPEN is 0b01 or 0b11 in both copies of CPACR_EL1, since either copy may govern its trap before a synchronization.  The joined theorem starts from every state of that model at EL1 whose memory holds the image's bytes at its base, with the program counter at the base and the MMU off in both copies of SCTLR_EL1, whatever the values of the other system registers, the contents of the TLBs, the selected stack pointer, and the processor's support for TCR2_EL1.  The startup reaches the entry routine with the registers' target values in effect, the TLBs clean, SP at the stack's top, X17 at the area, the area's zero tail cleared, and X30 at the exit.  From there the program runs in the model of its instructions, whose platform a lemma derives from the table's bytes: Normal memory is the RAM GiB less the image's bytes below the end of its table, and the UART lies at 0x09000000.  The program's instructions include no system instruction, so the configuration that the startup establishes stays fixed until the exit.

Some conditions lie outside what the extended model can check and enter the trusted base as assumptions.  The implementation must support the 4 KiB translation granule and little-endian data at EL1, firmware must have performed any implementation-defined initialization of caches and TLBs, the system-register masks of FEAT_SRMASK must be zero, and RAM must back the whole GiB from 0x40000000, which the runs provide with 1 GiB of RAM.  No data cache may hold a clean line of the image that differs from memory: the boot protocol requires the image cleaned to the point of coherency, Linux's startup relies on the reading that no stale clean line remains, and the trusted base adopts that reading.  Under KVM, the hypervisor's second stage of translation must map the RAM GiB to itself as Normal memory and map or emulate the UART.

## The UART and the exit

The model treats the UART as an output list: a byte store to the data register appends the byte, and the theorem's conclusion concerns that list.  The device that turns the stores into bytes on the host is QEMU's model of the PL011 under both accelerators, and the theorem's reader trusts it and its address.  QEMU's documentation fixes only the addresses of flash and RAM on the `virt` machine and directs guests to the device tree for every other device, so the address 0x09000000 holds for QEMU 8.2's memory map, whose device tree names the PL011 there, and enters the theorem as the platform's.  The PL011 must also transmit every byte written to its data register, which depends on the device's enable bits and its FIFO and lies outside the architecture.

A program that reads its input also trusts the PL011's receiver and QEMU's character backend, in runs without a break on the line.  In QEMU 8.2.2, UARTFR's RXFE is set while the receiver's holding register is empty and clear while it holds a word, a read of UARTDR returns the held word, with the byte in bits 7 to 0 and its flags in bits 11 to 8, and empties the register (`hw/char/pl011.c` lines 153 to 176 and 340 to 365, and the PL011's manual, DDI 0183G, Tables 3-2 and 3-4 and section 2.4.3).  Nothing that the model's runs do empties it otherwise: a write of UARTLCR_H that changes FEN and the device's reset also empty it (lines 135 to 143, 289 to 293, and 493 to 510), and the model has no rule for either.  The backend gives the PL011 the bytes of the input file or pipe in order, none lost or repeated, since it stops reading while the holding register is full and passes one byte at a time (`chardev/char-io.c` lines 43 to 64, `chardev/char-fd.c` lines 48 to 85, `chardev/char.c` lines 186 to 195, and `chardev/char-fe.c` lines 150 to 162).  Under those readings the reads of every run in which each byte that the program reads arrives follow a record `Rx` whose words hold the input's bytes in order, which is the premise `Rx.Delivers` of the theorems.  A break reaches the receiver without the check of its room that precedes each byte, and with the FIFO disabled it overwrites the holding register's one slot (`hw/char/pl011.c` lines 129 to 133, 330 to 349, and 367 to 372), so a break replaces a byte that the register holds, and, by a reading of the source that no test reproduces, a byte that follows a break in the same pass of QEMU's main loop replaces the break word and is read twice.  The readings therefore exclude runs with a break.  UARTFR lies at 0x09000018 in the PL011's region (`hw/arm/virt.c` line 148 and DDI 0183G, Table 3-1).  Under KVM, a 32-bit load from the UART reports a valid syndrome, KVM exits to QEMU, and KVM writes QEMU's value, zero-extended, into the destination register (Linux 7.0, `arch/arm64/kvm/mmio.c` lines 108 to 150 and 218 to 258).  `tests/baremetal/a64-uart.sh` runs two images under each accelerator, on each input from a file and from a pipe that delivers the first bytes in pieces of 1, 3, 5, and 7 bytes and then the rest.  The GCD image that reads two words runs on nine pairs of words, and every run writes the pair's GCD and the status 0.  The image of a function that flips bit 5 of each byte runs on messages of 0, 1, 4,095, 4,096, 65,536, and 1,000,000 bytes, and every run writes the flipped message and the status 0, and on the lengths 8,800,001 and 2^64 − 1, above its limit of 8,800,000 bytes, where the run writes the status 64 alone.  `tests/baremetal/a64-rcv.sh` runs the Oakland tabulator's image on the 19 files of the RCV corpus, 26,587,260 bytes, and on its 726 edge files under each accelerator, from a file, and every run writes the report of the C translation and the WASI process and the status 0, and it runs the Maine tabulator's image on the 6 files of the Maine corpus and its 669 edge files in the same way.  Over the Oakland corpus the input takes 14.0 µs per byte under TCG and 15.3 under KVM with two cores' quota, and [the RCV document](../Demos/Rcv/README.md#the-aarch64-images-runs) gives the times.  A break that QEMU's monitor sends on the line while the receiver is empty, with no byte after it, puts a word with the break flag in the receiver, and that run of either image writes the status 65 alone.

The exit writes the status in X0 as one byte on the UART after the output: 0 after a result, or a trap's code with no byte before it.  It then completes the UART stores with a barrier and calls PSCI SYSTEM_OFF with `HVC #0` and the function identifier 0x84000008 in X0.  Semihosting, a debug interface through which a guest under TCG can give QEMU an exit status, is unavailable under KVM, so the UART carries the status under both accelerators and QEMU exits with status 0.  Under TCG the guest has no EL2, so the architecture makes `HVC` undefined at EL1, and QEMU intercepts the call as PSCI before that rule applies.  Under KVM, EL2 exists and KVM implements the call.  The instruction after the call branches to itself, and an undefined-instruction exception reaches a vector that halts, so the output is final at the call however the call ends, and the theorem needs no model of PSCI.

## The loader

QEMU loads the image and enters it, and the theorem assumes that memory holds the file's bytes at the image's address when the startup begins.  For an arm64 Image, QEMU 8.2 copies the whole file to the base of RAM, 0x40000000, plus the header's offset, adding 2 MiB when the offset lies below 4 KiB, where QEMU's boot stub lies, or using 0x80000 when the header's image size is 0.  An offset of 0 therefore places the image at 0x40200000 under both accelerators.  The boot stub at 0x40000000 sets X0 to the device tree's address, clears X1 to X3, and branches to the image.

A check compares the loaded memory with the file before the first instruction runs.  QEMU starts stopped, with the machine, the processor, and the RAM of the program runs, and its monitor saves the guest RAM over the file's length at the computed address, which must equal the file.  The test driver runs the check on every image that Lean writes, under TCG and KVM.  It shows the bytes in RAM before the first instruction of a stopped run and supports the placement rule, but it proves nothing about the run that executes, so the loader stays in the trusted base, together with the boot stub's register settings.

## Validating the model against the processor

### Co-simulation

The model's agreement with the processor is the link that rests on tests.  A bare-metal harness runs each case at EL1 with the MMU on and RAM mapped as Normal memory, the conditions under which the model claims to hold.  A case sets the general registers to boundary values or random words, the floating-point registers D0 to D31 to special doubles or random words, the flags to random bits, and a 64-byte window of RAM to random bytes, and it runs one instruction with random fields as the word that the encoder gives.  A load or store receives a base that puts its access inside the window, mostly at unaligned addresses, with SP at a multiple of 16 when SP is the base.  A branch receives an offset of up to 16 words in either direction, where landing code records which word execution reached.  The harness prints the state before and after each case, and a checker runs the model from the state before and compares its result with the state after.

A case of `FCMP` gives its second operand, each with probability 1/4, the word of its first operand, that word with the sign changed, or the next word, so that equal values, zeros of opposite signs, and neighbors occur among the unordered, equal, less, and greater pairs.  A case of `FCVTZU` gives its operand, with probability 1/2, a double of either sign whose magnitude lies from 2^-2 to 2^66, so that truncation toward zero, exact integers, and saturation at both ends occur.  Further cases run the forms of the signed comparisons and of the arithmetic shift on the values that their code meets: `SUBS XZR` on equal, adjacent, and different-signed words, the largest positive and the least negative `Int64` among them, `CSINC` with GE or GT on the flags that `SUBS` sets for such a pair, `LSRV` of a word with its sign bit set or clear by 0, 1, 63, 64, and 65, `LSR` by 63 of such a word, and `SUB` of 0 or 1 from `XZR`.  The harness runs under TCG, where QEMU emulates a Cortex-A57, and under KVM on the host's processor, pinned in turn to a core of each type that the processor has.  Every case has agreed, in tens of thousands of cases under each accelerator, and a printed state with one register changed makes the checker report that case.  The test covers only the states in which the model runs, with accesses inside the window, short branches, and no access to the UART, and it covers sampled values on particular implementations. A case of a single-precision form gives each D register a single's word in its low 32 bits and random upper bits, which the forms ignore and their writes clear. A second test, `tests/baremetal/a64-fpvectors.sh SEED COUNT`, runs the floating-point arithmetic forms, `FCMP`, and `FCVTZU` on operands at the corner cases of IEEE 754. ### The exhaustive test of the single-precision forms

`tests/baremetal/a64-fpexhaust.sh` runs the code that the generator emits for an `f32` operation on every 32-bit word.  A case names an operation and, for a binary operation, a fixed operand, and the Image's program runs the case's code on each word and writes, for each chunk of 2^16 consecutive words, a 64-bit digest of the results.  The digest starts at 0 and becomes h·M + lo and then h·M + hi for the low and high 32 bits of each result in turn, modulo 2^64, where M is the odd constant 0x9E3779B97F4A7C15, so one wrong result changes its chunk's digest, and since the order of M modulo 2^33 is 2^31, errors in the same bit of two results cannot cancel.  A checker compares each chunk's digest with that of the results of the interpreter's function, which Lean computes in parallel tasks, and reports every chunk that differs.  Computing the digests of every chunk takes hours of many cores, so the commands `stripes` and `join` of `a64-fpexhaust` split that work over hosts. ### Isla

Isla is a symbolic evaluator for instruction-set specifications written in Sail.  Arm writes its architecture's specification in its language ASL, and a translator generates from it a Sail model of the whole architecture, with its system registers and address translation.  For one instruction, with its opcode fields and register values symbolic, Isla produces a trace: the register and memory reads and writes that the instruction performs, their values as SMT expressions over the symbols, and the conditions of each path.  Islaris used such traces to verify machine code in Coq against Arm's specification.

The check is a Lean proof, for each form on which the program's model runs, that the model's execution agrees with the form's Isla trace.  It covers every operand value where tests cover samples, and the architecture as Arm specifies it where tests cover the implementations at hand.  Isla's Arm model represents IMPLEMENTATION DEFINED choices as constants of its configuration and CONSTRAINED UNPREDICTABLE choices as symbolic values, so a form's dependence on either would appear in its trace, which no test on particular processors can reveal.  The check replaces trust in the model's agreement with the processor by trust in Arm's ASL, its translation into Sail, Isla with the SMT solver that prunes its paths, and the meaning of a trace.

Isla traces each form with the Armv9.4 specification at EL1 in about 4 s and 1.1 GB, most of it spent parsing the specification's 156 MB intermediate representation.  With symbolic operands, the flag computations of `AddWithCarry` and the specification's devices at fixed addresses add paths, which an option of Isla and a constraint on the address remove.  A symbolic register number multiplies the paths by the number of registers, unless Isla reads the registers as a vector, which leaves one fork per register field, on register 31.  With the MMU off, the specification treats every data access as Device memory and faults on an unaligned access.  With the MMU on, in a configuration of Isla's own with a 1 GiB identity block over the RAM GiB, stage 2 translation on, and PAN fixed at 0, an unaligned load with concrete operands succeeds as the model states, and its trace, which includes the table walks of each byte, takes 54 s. Two CONSTRAINED UNPREDICTABLE choices appear in the traces.  One concerns Device memory, and its branches agree for Normal memory. A Lean check reads the traces into a definition of Isla's trace language and gives them the semantics that Islaris defines.  The reader takes the events `cycle`, `call`, `return`, `define-enum`, and `branch-address`, and the primitives `sail_take_exception` and `sail_barrier` with a unit result, as steps without effect, and rejects every event that the semantics does not define. An `abstract-call` event, which Isla records for a function left abstract, takes its result from a meaning of the function that each theorem states as a hypothesis.  For each form, a theorem states that whenever the model's execution succeeds from a state, every path of the form's trace from that state ends in the state that the execution gives, and some path reaches it, with the registers outside the model changed only at those that the theorem lists, for every value of the registers that Isla's configuration leaves unknown.  The traces of `tests/isla/tcg` and `tests/isla/kvm` take every opcode field symbolic in two processor profiles, QEMU's Cortex-A57 under TCG and the KVM guest on the host's Cortex-X925 and Cortex-A725 cores, and the check reads each profile's feature settings from the file that its traces used. The readers of the traces and of the feature settings, the semantics of traces, and the edits of the IR join the assumptions of this check.

The theorems cover, in both profiles, every integer form on which the program's model runs, for every value of every opcode field, register 31 included.  ADD, SUB, and SUBS with an immediate or a register, AND, EOR, ORR, ORR (W), MADD, MSUB, LSLV, LSRV, UDIV, MOVZ, MOVK, LSR with an immediate, CSINC, ADR, and ADRP agree from every state. On the paths that the premise excludes, the specification replaces the target's top byte.  The startup's system instructions, `MSR`, `MRS`, `ISB`, `DSB`, `TLBI`, and `HVC`, are forms on which the program's model stops, so they have no theorem against Isla, and the boot model gives them their meanings, as [the startup](#the-startup) describes.

LDR, LDRB, STR, and STRB agree from every state that meets the premises of the traces' configuration, which concern the translation table and the address. ## Floating point

The model's double-precision forms are `FMOV Dd, Xn` and `FMOV Xd, Dn`, which copy a word between a general register and a floating-point register, `FADD`, `FSUB`, `FMUL`, and `FDIV` on D registers, `FSQRT`, `UCVTF Dd, Xn`, which converts an unsigned 64-bit integer to a double, `FCMP Dn, Dm`, which sets the flags from a comparison, and `FCVTZU Xd, Dn`, which converts a double to an unsigned 64-bit integer.  Each computes the reference interpreter's function of the WebAssembly instruction that it implements, such as `Wasm.f64Add` for `FADD`, `Wasm.f64ConvertI64U` for `UCVTF`, and `Wasm.i64TruncSatF64U` for `FCVTZU`, so the simulation lemmas hold by the definitions, and the burden falls on the model's fidelity: for every operand, Arm's result under the startup's FPCR must equal the interpreter's function.  The interpreter rounds to nearest with ties to even, keeps subnormals, and returns the canonical NaN, 0x7FF8000000000000, for every NaN result of an arithmetic operation.  AArch64 returns that NaN as its default NaN when FPCR.DN is set and propagates NaN payloads when it is clear, and with RMode at 0b00, FZ and FIZ clear, AH and NEP clear, and every trap enable clear, it rounds to nearest and keeps subnormals, so the startup's value, 0x02000000, gives the interpreter's special values for these forms.  No square root lies halfway between two doubles, since the odd part of a midpoint's square exceeds 2^106 while that of a double's magnitude lies below 2^53, so Arm's rounding of the real square root and the interpreter's rounding of an integer square root give the same double.

`FCMP` sets N to the interpreter's `IEEE64.lt` of its operands, Z to `IEEE64.eq`, C to the negation of N, and V when an operand is a NaN.  The flags N, Z, C, and V are therefore 0011 for an unordered pair, 0110 for equal values, 1000 when the first operand is less, and 0010 when it is greater, the results of the pseudocode's `FPCompare`, which compares the operands' real values, so that zeros of opposite signs are equal and an infinity lies beyond every finite value.  `FPCompare` raises Invalid Operation for a signaling NaN, which sets FPSR.IOC and traps only when FPCR.IOE is set, and its inputs keep their subnormal values while FPCR.FZ and FPCR.FIZ are clear, as the startup leaves them.  After `FCMP`, the condition `EQ` holds exactly when the interpreter's `eq` does, `MI` when `lt` does, and `LS` when `le` does, while `LT` and `LE` also hold for an unordered pair, so the generator uses `EQ`, `MI`, and `LS`.

WebAssembly converts a double to an unsigned 64-bit integer in two ways.  `i64.trunc_f64_u` traps on a NaN and on a value whose truncation lies outside [0, 2^64), and `i64.trunc_sat_f64_u` saturates: the interpreter's `IEEE64.truncSatI64U` gives 0 for a NaN, truncates toward zero, gives 0 for every value whose truncation is at most 0, negative infinity included, and 2^64 − 1 for every value from 2^64 up, positive infinity included.  The verified compiler emits only the saturating form, as its translation of `Float.toUInt64`, and the generator rejects the trapping one.  `FCVTZU` computes `FPToFixed(D[n], 0, TRUE, FPCR, FPRounding_ZERO, 64)`, and the pseudocode's `FPUnpack` gives a NaN the value 0 and an infinity a value beyond every integer, its case of FPRounding_ZERO rounds toward zero, and `UnsignedSatQ` clamps the integer to [0, 2^64 − 1], so `FCVTZU` gives the saturating conversion for every operand, with FPSR's IOC or IXC as its only other effect under the startup's FPCR.

The model's single-precision forms are `FMOV Sd, Wn` and `FMOV Wd, Sn`, `FADD`, `FSUB`, `FMUL`, `FDIV`, `FSQRT`, and `FRINTN` on S registers, `UCVTF Sd, Xn` and `SCVTF Sd, Wn`, which convert an unsigned 64-bit and a signed 32-bit integer to a single, `FCVTZU Xd, Sn` and `FCVTZS Wd, Sn`, which convert a single to an unsigned 64-bit and a signed 32-bit integer, and `FCMP Sn, Sm`.  Each reads the low 32 bits of its D registers, writes a single's result zero-extended into its D register, as a scalar write does while FPCR.NEP is clear, and computes the interpreter's binary32 function of its WebAssembly instruction, such as `Wasm.f32Add` for `FADD` and `Wasm.f32Nearest` for `FRINTN`.  The interpreter's binary32 functions round to nearest with ties to even, keep subnormals, and return the canonical NaN 0x7FC00000, AArch64's default NaN of a single, for every NaN result.  `FRINTN` computes `FPRoundInt` with ties to even and without the Inexact exception, the rounding of WebAssembly's `f32.nearest`.  `FCVTZS Wd, Sn` computes `FPToFixed` toward zero with saturation at −2^31 and 2^31 − 1 and with 0 for a NaN, which is `i32.trunc_sat_f32_s`, and `FCVTZU Xd, Sn` gives `i64.trunc_sat_f32_u` as the double's form gives `i64.trunc_sat_f64_u`.  `FCMP Sn, Sm` sets the flags from the interpreter's `IEEE32.lt` and `IEEE32.eq` as the double's form sets them from `IEEE64`'s, so the generator's conditions hold for singles.

The absolute value uses no floating-point form.  The interpreter's absolute value clears the sign bit and keeps every other bit, a NaN's payload included, and `ADD Xr, Xr, Xr` followed by `LSR Xr, Xr, #1` computes the same word with two integer forms that the Isla check covers.  For a single, a 32-bit `ORR` between the two drops the sign bit, which the doubling moved to bit 32.  `FABS` changes only the sign bit when FPCR.AH is clear, but on a processor with FEAT_AFP, such as the KVM guest's cores, AH set makes it return a NaN operand unchanged, so the integer code also leaves the program independent of that field.

The boot model treats every form of this section as a floating-point instruction, which CPACR_EL1.FPEN traps.  Its rule for an instruction that touches no memory runs one only when both copies of CPACR_EL1 and FPCR hold the startup's values, and the configuration that the program's steps require includes those values, so every floating-point instruction of a program runs with floating point enabled and FPCR at 0x02000000.

Linux's boot protocol fixes no value of PSTATE.SM or of SMCR_EL1.FA64, so a processor with FEAT_SME may enter the image in Streaming SVE mode, in which most SIMD instructions trap.  In the pseudocode of Arm's Armv9.4 specification, as the Sail model gives it, and in Arm's release of 2026-06, each double-precision form of the model checks its access with `CheckFPEnabled64`, which reads CPACR_EL1.FPEN and the traps of EL2 and EL3 but not PSTATE.SM, while the vector forms check with `CheckFPAdvSIMDEnabled64`, which traps in Streaming SVE mode unless FEAT_SME_FA64 is enabled.  In the Sail model, the trace of each single-precision form reaches the lines of the specification that the double-precision form of the same shape reaches, those of the check among them.  The other reads of PSTATE.SM on the forms' paths leave their results unchanged under the startup's CPACR_EL1 and FPCR: (a) `IsMerging` takes FPCR.NEP as 0 in Streaming SVE mode without FEAT_SME_FA64 and reads it otherwise, and the startup clears NEP; (b) `FPProcessException` traps only for a set trap enable, and (c) the underflow test of `FPRoundBase` reads FPCR.UFE, and the startup clears every trap enable; and (d) `V_set` writes bits 0 to 127 of the register in either mode, since the startup's CPACR_EL1 leaves SVE and SME disabled, and the model holds no bit above 127.  The model therefore gives each form one meaning for either value of PSTATE.SM.  The same freedom reaches every integer form, the startup's system instructions, and exception entry, and none of them reads PSTATE.SM or SVCR on the program's paths, which take no exception before the final HVC.  The test processors implement no SME.  In the Isla profile sme, which implements FEAT_SME and FEAT_SME_FA64 and leaves PSTATE.SM unknown, the theorems of the floating-point forms hold for either value of PSTATE.SM and of the FA64 bits of SMCR_EL1 and SMCR_EL2, no trace of an integer form reads PSTATE.SM, and the traces of the loads and stores read it only in the exception entry of the alignment fault, where the model stops.  The startup and the exception entry of a trap rest on the reading, which the trusted base states as an assumption.

The Isla check covers each floating-point form, except the value that Arm's floating-point function computes, which the form's theorem takes as an equation with the interpreter's function, as [the Isla section](#isla) describes.  The equations of the 64-bit wrappers rest on two tests.  The co-simulation draws the operands from zeros, infinities, quiet NaNs with and without a payload, signaling NaNs, subnormals, the largest and smallest normals, and 1.0, each with either sign, and from random words.  QEMU and the processor have agreed with the model on every case, and every result of an arithmetic case with a NaN operand has been the canonical NaN.  [The vector test](#co-simulation) runs 24,000,000 vectors of each arithmetic form and of `UCVTF` under TCG and under KVM on each core type, with every ordered pair of special operands and operands whose exact results lie at ties, next to ties, at the overflow threshold, and in the subnormal range, and 20,000,000 vectors of `FCVTZU` at the boundaries of truncation and saturation, and every result word has equaled the model's.  The comparison of `FCMP` rests on the same tests, with 4,000,000 vectors in the vector test.  The equations of the 32-bit wrappers and of `FPCompare` on singles rest on the co-simulation and on [the exhaustive test](#the-exhaustive-test-of-the-single-precision-forms), which runs the code of each unary operation and conversion on every operand, and that of each binary operation on every operand against fixed second operands, a small part of the pairs, under TCG and under KVM on each core type, with every chunk's digest equal to that of the interpreter's results.  Proofs over Sail 0.20.3's Lean translation of the functions also support the equations.  For every operand and from every state that meets the translation's state hypothesis, they show that each translated function returns the interpreter's function of the operands, or the flags of the interpreter's comparisons, sets FPSR's bits, and changes no other register and no memory, and they derive each equation from a link stating that Isla's call returns what the translation returns. ## The final theorem

Each program's theorem concerns the image file whose bytes the kernel compared with the generator's output for the program's module, function, and arguments.  If memory holds that file's bytes at a base that is a multiple of 4096, with the memory that the header's size names inside the RAM GiB, and the core starts at the first byte at EL1 with the MMU off, then the machine, in the model of the boot machine, reaches the PSCI SYSTEM_OFF call with every store to the UART complete, after writing either the encoding of the Lean function's value on the program's arguments followed by the status byte 0, or a status byte alone: 1 when the compiled program reached `unreachable`, through its depth guard or its allocator's failure to grow memory, and 4 when a frame would have passed the stack's limit.  The theorems of GCD by a loop, CRC-32, SHA-256, the CIC filter, the Euler solver, the GPT-2 kernel, the binary32 GPT-2 layer, the binary32 conversions, the exponential, the sine, and the programs over `Int64` of the floor and conversion examples allow only the value, GCD by recursion allows the value or status 4, and the recursion that reaches the depth guard allows the value or status 1 or 4.  The run fetches its instructions from the image's words below its translation table, as the initial memory holds them, and no store reaches those words.  The statement names that code map, the protected bytes, and the image's size through functions of the generator's output, which the kernel evaluates for each program.

The Image of [the CIC decimation filter](../Library/Numerics/Filters/Cic/README.md) has a second theorem, `cic_outputs` of [the Image theorems](../tests/TestSupport/A64/ImageFiles.lean), whose statement names the filter's specification over ℤ in place of the Lean function.  The UART receives the encoding of an array of words and then the status byte 0, and the array's words, read as signed 64-bit integers, are the outputs `outputs 3 8 1` of [the filter's specification](../Library/Numerics/Filters/Cic/Spec.lean), of order 3, decimation 8, and differential delay 1, on the table's samples read as integers.  The proof joins the Image's theorem with the equation of the dialect's program with the block cascade at `UInt64`, for every input array, and with the exactness of the cascade under Hogenauer's bound, whose premise the kernel checks for the table's 16-bit samples.  Its reader needs the specification's definitions and the boot model's statement, and none of the program's.

The theorem of the GPT-2 kernel's Image, `gptscores` of [the GPT-2 kernel's Image theorem](../tests/TestSupport/A64/ImageFilesGpt.lean), names the demo's function in place of the wrapper.  The wrapper `scoresCheck` of [the kernel's program](../tests/TestSupport/A64/GptScores.lean) builds a cache of 3 positions, 32 token embeddings of width 16, and the final layer norm's gains and biases from the indices of their elements, calls `scores` of [the GPT-2 program](../Demos/Gpt/Program.lean) with one layer, two heads of width 8, and `eps` 1e-5, and returns the scores' words.  `scoresCheck_eq` equates that result with `Float.toBits` of each score, so the theorem states that the UART receives the encoding of the array of the words of the 32 scores of `Demos.Gpt.scores` and then the status byte 0.  The code of `scores` holds each of the model's floating-point forms: the layer norm adds, subtracts, multiplies, divides, takes a square root, and converts the row's width to a double, and the product with the embeddings adds and multiplies.

The theorem of the binary32 GPT-2 layer's Image, `gptlayer32` of [the binary32 Image theorems](../tests/TestSupport/A64/ImageFilesF32.lean), names the demo's function in place of the wrapper.  The wrapper `layerCheck` of [the layer's program](../tests/TestSupport/A64/GptLayer32.lean) builds a row of width 64, the caches of 2 positions, and the weights of one layer from the indices of their elements, applies the kernels of `layerStep32` of [the binary32 GPT-2 program](../Demos/Gpt32/Program.lean) for one head and an MLP of width 64 at position 2, and returns the words of the row after the layer.  `layerCheck_eq` equates that result with the words of the row that `Demos.Gpt32.layerStep32` gives, so the theorem states that the UART receives the encoding of the array of the 64 words of the layer's output and then the status byte 0.  The program has 7,660 instructions, and its code holds the single-precision arithmetic, the square root, `FRINTN` in the attention's exponential, `UCVTF Sd, Xn`, and `FCMP Sn, Sm`.  The theorem of the conversions' Image, `conv32`, states that the UART receives the encoding of `convCheck 64` of [the conversions' program](../tests/TestSupport/A64/Conv32.lean), four words for each of 64 inputs, whose code of 1,108 instructions holds `SCVTF Sd, Wn`, `FCVTZU Xd, Sn`, and `FCVTZS Wd, Sn`, which the layer's code lacks, and the integer code of the absolute value.

The Images of [the exponential](../Library/Numerics/Float64/Exp/README.md) on 1 and on -740 have second theorems, `exp1_accuracy` and `expsub_accuracy` of [the exponential's Image theorems](../tests/TestSupport/A64/ImageFilesExp.lean), whose statements name Mathlib's `Real.exp` in place of the Lean function. The run on -740, whose result is subnormal, executes `FCMP` in the exponential's special case.  The proof joins the Image's theorem with `exp_one_step`, the exponential's accuracy theorem for every finite double, and with the real values 1 and -740 of the input words, which the kernel computes.

The Images of [the sine](../Library/Numerics/Float64/Trig/README.md) on 10 and on 10^22 have second theorems, `sin10_accuracy` and `sin1e22_accuracy` of [the sine's Image theorems](../tests/TestSupport/A64/ImageFilesSin.lean), whose statements name Mathlib's `Real.sin` in place of the Lean function. The Images of [the floor example](../Examples/Floor/README.md) and [the conversion example](../Examples/Convert/README.md) have theorems that name the examples' specifications.  `floordiv_image_spec` and `average_image_spec` of [the floor Images' theorems](../tests/TestSupport/A64/ImageFilesFloor.lean) state that the UART receives the eight bytes of a word and then the status byte 0, and that the word, read as `Int64`, has the integer `Int.fdiv (-7) 2`, which is -4, or the floor of the mean of `-2^63` and -1, which is `-2^62 - 1`, by `floorDiv_spec` and `average_spec`.  `floordivmin_image` states that the Image of `floorDiv minValue (-1)` writes the word of `minValue`, the wrapped quotient outside the specification's domain.  `todouble_image`, `tosingle_image`, `ofdouble_image`, and `convscale_image` of [the conversion Images' theorems](../tests/TestSupport/A64/ImageFilesConvert.lean) state that the word is the one that WebAssembly's signed conversion instructions, as Talos defines them, give for the Image's arguments, and the kernel computes that word.

The Image of GCD by a loop that reads its two arguments from the UART has the theorems `gcd_uart` and `gcd_uart_flag` of [the UART Image's theorems](../tests/TestSupport/A64/ImageFilesUart.lean). The Image of the function `flipBit5` of [the flip program](../tests/TestSupport/A64/Flip.lean), which flips bit 5 of each byte of a buffer, has the theorems `flip_uart`, `flip_uart_over`, and `flip_uart_flag` of [the flip Image's theorems](../tests/TestSupport/A64/ImageFilesFlip.lean), at every base that is a multiple of 4096 with the image's memory in the RAM GiB, from the same boot state.
