# The AArch64 bare-metal path

The AArch64 bare-metal path compiles a Lean function, applied to arguments fixed when the program is built, to machine code that runs without an operating system on QEMU's `virt` machine, under QEMU's emulation (TCG) and under KVM on an AArch64 host.  The program writes the bytes of the function's value to the UART.  The goal is one theorem per program, checked by Lean's kernel, that connects the bytes the machine writes with the Lean function's value, and a list of the components that the theorem's reader must trust, each with its evidence.  The theorem is a chain of links: from the Lean function to a WebAssembly module, from the module to a model of the processor, and from the model, the image's bytes, the loader, and the startup to the running machine.

Proofs establish the links from the Lean function to a model of the boot machine for programs of integer and double-precision arithmetic, calls, globals, and linear memory.  For each test program, a theorem checked by Lean's kernel starts from a state of that model whose memory holds the bytes of the program's image file at a base in RAM that is a multiple of 4096, such as 0x40200000, where QEMU places it, and ends at the call that turns the machine off, with the encoding of the function's value or a trap's status on the UART.  Tests support the model's agreement with QEMU and with the processor, and the loader's placement of each image.  A check of the model against Arm's specification covers every integer form on which the program's model runs, and the floating-point forms, whose meanings in the model are the reference interpreter's IEEE 754 functions, rest on tests against QEMU and the processor.

| Link | What it states | Established by | Status |
|---|---|---|---|
| Lean function to WebAssembly | The module's run in the reference interpreter returns a representation of the function's value or traps at `unreachable` | The verified compiler's universal theorem | Proved |
| WebAssembly to the machine model | The generated code, run in the model, writes the encoding of the interpreter's result or exits with a trap's status | The simulation theorem | Proved |
| Encoding | The model's decoder reads every encoded instruction back as itself | A lemma over every form, and a comparison with the GNU assembler | Proved, and tested |
| Image bytes | The file holds every byte of the image that the generator gives: the header, the startup, the program, the vectors, the translation table, and the area's nonzero prefix | The kernel's evaluation of the generator, on every test run | Checked |
| Model to processor | The processor executes each emitted word as the model does | Co-simulation against QEMU and the processor, and a check against Arm's specification of the integer forms | Tested, and checked for the integer forms |
| Startup | From the boot state, the startup reaches the premises of the program's theorem | A proof in a model of the boot machine | Proved |
| Loader | QEMU places the file's bytes where the theorem assumes them | A comparison of guest memory with the file before the first instruction | Tested, and trusted |
| UART | A byte store to the data register transmits the byte | QEMU's model of the PL011 | Trusted |
| Exit | The run reaches PSCI SYSTEM_OFF with the status byte last in the output and every store to the UART complete | A proof in the model of the boot machine, and a halt after the call | Proved, and trusted after the call |

## From the Lean function to WebAssembly

The verified compiler translates a Lean function, written in the compiler's dialect, to a WebAssembly module, and one universal theorem, checked by Lean's kernel, covers every program that the compiler accepts.  For each compiled function the theorem states that, for arguments that represent the Lean arguments, the module's run in a reference interpreter, a WebAssembly interpreter written in Lean, either returns a value that represents the Lean function's value or traps at the instruction `unreachable`.  The compiler emits that trap when a call depth passes its guard, and the allocator reaches it when linear memory cannot grow, so the theorem needs no premise about free memory or call depth.  The theorem asserts its outcome from some amount of the interpreter's fuel upward and bounds no call depth, a gap that the stack check of the generated code closes.

The machine-code path composes this theorem with a simulation theorem whose premise is the interpreter's result.  The interpreter's run appears in the conclusion of the first theorem and the hypothesis of the second, and the composed statement relates the Lean function's value to the machine's output with no mention of that run.  Both theorems hold of the interpreter's semantics as Lean defines it, whatever its fidelity to the WebAssembly standard, so a departure of the interpreter from the standard cannot make the composed statement false.  The interpreter serves the path as an intermediate language whose semantics only the proofs use, and the testsuite runs that compare it with the standard concern the modules that the compiler emits for WebAssembly engines.  The program's theorem has the premise that the area holding the module's globals and linear memory holds the bytes that the module's initial store determines.  The image carries the area's bytes through the end of the memory's data segments under the kernel's check, and the startup's proof covers the zeros that follow them, so the theorem about the image file has no such premise.

## From WebAssembly to the machine model

### The code generator

The code generator takes the module that the verified compiler emits, the function to call, and its arguments, and produces a bare-metal program of AArch64 instructions.  The program's entry routine loads the arguments, calls the function, writes the result's bytes to the UART, and returns status 0, and the function, every function that its calls reach, and the trap stubs follow it.  The generator reads the same module that the C translator reads, so it inherits the compiler's theorem for every function and needs no proof about the compiler's source language.  It accepts the subset that the bare-metal test programs need: comparisons and arithmetic on integers, calls, globals, 64-bit loads and stores of linear memory, the query and growth of the memory's size, and the double-precision forms of the Euler solver, which are constants, the reinterpretations between `i64` and `f64`, the conversion of an unsigned `i64`, addition, subtraction, multiplication, division, square root, and absolute value.  It rejects every other form with a message.

WebAssembly's typing fixes the operand stack's height and the types of its values at every reachable instruction, so the generator assigns each height a register: X0 to X15, then X19 to X28.  The generator tracks the types and rejects a function whose operand stack would need more registers.  An `i32` lies zero-extended in its register, so the extension of an `i32` to an `i64` emits nothing and the wrap of an `i64` to an `i32` is one 32-bit `ORR`.  An `f64` lies in its register as its 64-bit word, so the reinterpretations emit nothing, and frames, calls, spills, and memory treat it as they treat an `i64`.  A binary `f64` operation moves the two words into D0 and D1 with `FMOV`, computes into D0 with `FADD`, `FSUB`, `FMUL`, or `FDIV`, and moves D0's word back into the register of the lower operand, four instructions in all.  The square root goes through D0 in the same way with `FSQRT`, the conversion of an unsigned `i64` is `UCVTF` into D0 and an `FMOV` back, and the absolute value is `ADD Xr, Xr, Xr`, which drops the sign bit, and `LSR Xr, Xr, #1`.  An arithmetic operation becomes one instruction on registers, a comparison becomes a flag-setting subtraction and a conditional select, and a branch out of a block, loop, or `if` moves the value it carries into the register of the construct's base height and branches to the construct's target.  X16 and X29 serve as scratch registers, X17 holds the address of the area that holds the module's store, and X18 holds the stack's limit.

Each function has a frame on the stack: 8 bytes for each parameter and local, slots for spilled operand registers, and a slot for the return address, rounded up to a multiple of 16 bytes.  The prologue compares SP less the frame's size with the stack's limit in X18 and branches to a trap stub when the frame would fall below it, and otherwise stores the parameters into their slots and zeros into the other locals.  The compiler's theorem bounds no call depth, so the check turns an overflow into an outcome of the theorem.  A bound computed from the module, each function's frame plus the largest bound among the functions that its body calls, and 2^64 for calls that form a cycle, removes that outcome when the stack's room holds it, since the frames of the calls in progress hold all the stack that the program uses.  A call spills the operand registers below its arguments to the caller's frame, moves the arguments into the registers of heights 0 upward, branches with `BL`, moves the results into the registers of their heights, and reloads the spilled registers.  The callee preserves SP, X17, X18, and every byte of memory from the caller's SP upward, so the caller's locals and spills keep their values.

The area starts with the linear memory's size less 8, followed by the module's globals, one word each, and holds the bytes of linear memory from 4096 bytes above its start up to a cap fixed when the program is generated.  A load or store compares its address with the size less the access's offset and width, and branches to a trap stub when the address exceeds that bound.  The comparison uses the address register before any addition, so an address near 2^64 cannot wrap around the check.  The relation between the machine and the interpreter's store covers every byte below the cap, so growth of the memory needs no code that clears pages and updates only the size word.  The area ends at or below the stack's limit, so a store into linear memory never reaches a frame.

A trap branches to a stub that sets X0 to a status code and branches to the program's exit: 1 for the instruction `unreachable`, 2 for an access outside linear memory, 3 for a division by zero, and 4 for an overflow of the stack.  `UDIV` returns 0 for a zero divisor where WebAssembly traps, so the generator tests the divisor with `CBZ` before each division.  The exit takes the status out of the program without unwinding the frames, so code that does not trap pays nothing for the traps.

The generator places code as it emits it.  Each function receives the address of its first instruction, and a size function computes the length of a construct before its body is generated, so the target of a forward branch is known when the branch is emitted.  The generator encodes each branch only after a check that its word offset fits the instruction's field, 19 bits for conditional branches and 26 bits for `B` and `BL`.  The code holds no absolute address other than the UART's, since the entry routine receives the area's address in X17, and that property lets the image run at any base.

### The simulation theorem

The simulation theorem relates the interpreter's state at a point of a function's code to the machine's state at the address of that point's code.  The relation places the value at each operand-stack height in that height's register with its type, local i in the frame slot at SP plus 8i, SP at a multiple of 16, and the interpreter's store in the area.  For each instruction and each instruction list, the theorem states what the machine does for each continuation that the interpreter gives.  A fall-through reaches the end of the code in a related state, a branch reaches its construct's target with the carried value in the register of the construct's base height, a return reaches the epilogue, and a trap reaches the stub of its code.  Throughout, SP, X17, X18, the UART's output, and the memory above the function's frame keep their values.

The proof runs by strong induction on the interpreter's fuel, with a lemma for each instruction form, a lemma that the generated code has the length that the size function computes, and a lemma for each construct.  A call uses the callee's simulation at one less fuel, the fuel at which the interpreter runs a callee's body.  Every theorem of the path depends only on Lean's standard axioms, propositional extensionality, choice, and quotient soundness, and the proofs use no decision procedure for bit vectors.

A whole-program theorem joins the compiler's theorem for the called function with the simulation of the entry routine.  Its premises state that memory holds the code's bytes at the entry routine's address, SP is a multiple of 16, the stack's room below SP is Normal memory, X17 holds the area's address, and the area holds the initial store's bytes in Normal memory below the stack's limit.  Its conclusion allows a result or a trap.  With a result, the machine returns to the address in X30 with SP restored and status 0 in X0 after appending to the UART's output the encoding of the Lean function's value, a word as eight bytes with the lowest first or an array as its length word followed by its elements.  With a trap, it reaches the exit with status 1 or 4 in X0 and has written nothing, where status 1 is the compiler's trap at `unreachable` and status 4 an overflow of the stack.  Statuses 2 and 3 cannot occur, because the compiler's theorem excludes those traps.  Status 1 disappears where the compiler's theorem without a trap covers the program's arguments, and status 4 where the stack's room holds the stack's bound.  The model's step is a function, so the machine's run is unique and passes through the outcome that the theorem names.  Theorems of this form hold, with the result as the only outcome, for GCD by a loop, CRC-32, SHA-256, whose result is an array, a CIC decimation filter on a table of 64 samples, whose result is the array of its outputs, and the Euler solver on a grid of 4 by 4 cells, whose result is the array that the solver packs.  GCD by recursion keeps status 4, since its calls form a cycle and the bound is 2^64.  A recursion whose run in the interpreter traps at the depth guard keeps statuses 1 and 4, and it ends with status 1 under QEMU.

## The machine model

The model describes the AArch64 instructions that the generator emits, executed in sequence by one core at exception level 1 (EL1).  Its state holds the general registers X0 to X30, the floating-point registers D0 to D31, which are the low 64 bits of V0 to V31, SP, the program counter, the condition flags N, Z, C, and V, memory as a map from 64-bit addresses to bytes, and the list of bytes written to the UART.  A platform supplies the set of addresses that hold Normal memory and the address of the UART's data register.  A step fetches the word at the program counter from a fixed map of code words, decodes it, and executes it, and it stops the model when the fetch, the decoding, or the execution fails.  The model has no exceptions and no interrupts: the boot protocol masks interrupts, nothing unmasks them, and every fault stops the model.

The instruction forms cover the move-wide immediates, addition and subtraction with an immediate or a register, flag-setting subtraction, conditional select with increment, the logical operations on registers in 64 bits and the 32-bit `ORR`, immediate and variable shifts, multiply-add, multiply-subtract, unsigned division, conditional and unconditional branches, branch with link, compare-and-branch on zero or nonzero, return, 64-bit loads and stores with a scaled unsigned offset, the byte store, the PC-relative addresses of `ADR` and `ADRP`, and the double-precision forms that [the floating-point section](#floating-point) describes.  The startup's system instructions, `MSR`, `MRS`, `ISB`, `DSB`, `TLBI`, and `HVC`, are forms on which the program's model stops, and the model of the boot machine gives them their meaning.  The model's treatment of the flags, the stack pointer, and register 31 follows the pseudocode of the Arm Architecture Reference Manual.  Register 31 names SP as the base of a load or store and as an operand or destination of addition and subtraction with an immediate, and the zero register elsewhere, as the manual's encodings give.

A load or store may touch only Normal memory, and a load or store based on SP requires SP to be a multiple of 16.  The architecture raises an SP alignment fault in that case only when SCTLR_EL1.SA is set, and the model stops in either case, so the model is sound for either value of the bit.  An unaligned load or store to Normal memory succeeds, as it does on the processor while SCTLR_EL1.A is clear, which lets WebAssembly's unaligned accesses run as single instructions.  A byte store to the UART's data register appends the byte to the output, and every other access to the UART stops the model.

The model fetches from a fixed map of code words that the theorem derives from the initial memory's bytes, so a store never changes what the model fetches.  On the processor, a fetch after a store to code may return the old instruction or the new one until software performs cache maintenance.  The fixed map therefore matches the processor only if no store reaches the code.  The condition that excludes such stores reads: the platform's Normal memory excludes every byte of the code and every other byte of the image that must not change, such as the translation table, and the UART's address lies outside those bytes.  Under that condition a store into the code stops the model, and the program's theorem, which shows that the run reaches its outcome, shows that no such store occurs.  In the model of the boot machine, Normal memory excludes every byte of the image below the end of its translation table, so the condition holds for every image that Lean writes.

Wherever the architecture permits several behaviors, or depends on state that the model does not track, the model stops.  It stops on a word outside its forms, a fetch outside the code map, an access outside Normal memory, any UART access other than a byte store to the data register, and a load or store based on a misaligned SP.  A theorem about a run that reaches its outcome excludes every such state, so the processor's behavior in those states has no bearing on the theorem, and tests of the model need to cover only the states in which the model runs.

## Encoding and the image's bytes

Every AArch64 instruction is one 32-bit word, and the encoder writes each form's word as its fixed bits plus its fields at their positions, as a sum of natural numbers.  A lemma proves that the model's decoder reads every encoded instruction back as itself, for every form and every value of its fields, and its proof reads each field back with linear arithmetic.  The simulation proof uses the lemma to turn the bytes of the code into the instructions that the generator emitted.  The decoder belongs to the model, since it gives the words their meaning in the theorem, and a test compares the encoder with the GNU assembler: sample instructions of every form, with register 31 in each role and the extreme branch offsets, assemble to the encoder's words.

The image's bytes come from the generator, which the build runs as compiled code.  A theorem about the compiled generator's output would trust Lean's compiler and runtime, so the path checks the written file in Lean's kernel instead.  An elaborator reads the file when the theorem is elaborated and gives its bytes as one number, whose base-256 digits are the bytes, and the kernel runs the generator on the program's module, function, and arguments, lays out the whole image as bytes, and compares their number with the file's.  The joined theorem's premise states that memory holds the file's bytes, so the compiled generator and the compiled code that wrote the file leave the trusted base, while the elaborator's reading of the file and the kernel remain.  The test driver elaborates these theorems on every run, and with one bit of a program's image file changed, the kernel rejects that program's theorem.  The kernel's evaluation of the Euler solver's Image, 11,649 instructions, takes about 22 GB, so the driver elaborates its theorem on its own with a larger memory limit.

## The image and the boot protocol

The image is an arm64 Linux Image, the format whose header and entry state Linux's arm64 booting document defines.  The header starts with instructions that branch to the startup, and it records the offset from a 2 MiB-aligned base at which the image must lie, the size of memory that the image uses from its start, flags, and a magic number.  The protocol lets the loader choose any 2 MiB-aligned base in RAM, so the image must run at any such base.  The startup computes every address it needs relative to the program counter, the generated code holds no address inside the image, and the translation table holds none either, so the image's bytes do not depend on the base.  A proof shows that the generator gives the same bytes at two bases in the RAM GiB that differ by a multiple of 4096, so each theorem, whose kernel check compares the file with the image at 0x40200000, holds at every such base.  The size in the header must cover all the memory that the image uses, including the area's zero tail and the stack, because the protocol reserves that much memory from the image's start and QEMU places the device tree at a 2 MiB boundary above it.

At entry the protocol guarantees that X0 holds the device tree's address and X1 to X3 are zero, every interrupt is masked in DAIF, the core is in EL2 or in Non-secure EL1, the MMU is off, the instruction cache holds no stale entry for the image, and the image's address range has been cleaned to the point of coherency.  QEMU's `virt` machine enters the image at EL1 under TCG and under KVM, with SP_EL1 selected, SP 0, and floating point trapped.  For a processor with floating point, the protocol requires CPTR_EL3.TFP to be 0 where EL3 exists and CPTR_EL2.TFP to be 0 where EL2 exists and the image starts at EL1, so that firmware does not trap the image's floating point.  The protocol requires that firmware initialize every writable system register at or below the entry level, but it fixes no value, and it says nothing of the TLBs, of most fields of SCTLR_EL1, or of which stack pointer is selected.  The startup therefore writes a complete value into every system register that it relies on, so no field keeps a value that firmware chose.

## The startup

The startup is a sequence of instructions that Lean writes into the image and that takes the core from the boot state to the state that the program's theorem assumes.  The header's first instruction selects SP_EL1, and the startup checks that the core runs at EL1, halts at any other level, and installs a vector table whose entries branch to themselves.  With the MMU off it writes SCTLR_EL1 with every field at its final value but the MMU's enable bit, writes CPACR_EL1 as 0x300000, which enables floating point, writes MAIR_EL1, TCR_EL1, and TTBR0_EL1, the last with the table's address computed relative to the program counter, and writes TCR2_EL1 as zero when the processor implements that register.  After a synchronizing barrier it invalidates the TLB entries of EL1, waits for the invalidation to complete, writes FPCR as 0x02000000, writes SCTLR_EL1 again with only the MMU's enable bit changed, and synchronizes again.  It then clears the zero tail of the area, sets SP to the top of the stack and X17 to the area's address, and calls the entry routine.

The translation table is one level-1 table of 1 GiB blocks, each mapping addresses to themselves.  The GiB from 0x40000000, which holds RAM, is Normal write-back memory, readable, writable, and executable at EL1.  The first GiB, which holds the UART at 0x09000000, is Device-nGnRnE memory from which the core cannot execute, and every other address faults.  With a 4 KiB granule and a 4 GiB input range the walk starts at level 1, so no table of a lower level is needed.

The MMU must be on for the model's rule on unaligned accesses to hold.  With stage 1 translation off, every data access goes to Device-nGnRnE memory, and an unaligned access to Device memory faults whatever SCTLR_EL1.A holds.  WebAssembly programs make unaligned loads and stores, and the generated code performs each as one instruction, so RAM must be mapped as Normal memory.

The barriers and the TLB invalidation follow from the architecture's rules on system registers.  A write to a system register affects later instructions only after a context synchronization event, such as an instruction synchronization barrier, so the startup synchronizes after its writes and again after it enables the MMU.  The write of FPCR follows the first barrier, since `MSR FPCR` traps at EL1 while CPACR_EL1.FPEN is 0b00 or 0b10 (the pseudocode of `MSR FPCR`, section C5.2.8, page C5-983), and the write of CPACR_EL1 governs that check only after a context synchronization event (section D24.1.2.2, pages D24-8470 and D24-8471).  FPCR is a Special-purpose register (page C5-974), whose writes take effect in program order without synchronization (section C5.1.5.1, page C5-947), so only the boot model, which puts every register's write in effect at a synchronization, needs the second barrier for FPCR.  The TLBs reset to an implementation-defined state, entries left by software that ran before the image survive while the MMU is off, and a TLB may cache fields of the translation registers, so the startup invalidates the EL1 entries after it writes those registers and completes the invalidation with a data synchronization barrier before it enables translation.  The two writes of SCTLR_EL1, the first with the MMU off and the second changing only the enable bit, keep any field of that register that a TLB caches at its final value.

The startup enables floating point and fixes its control register.  CPACR_EL1 holds FPEN as 0b11, under which no access to the SIMD and floating-point registers, FPCR, or FPSR traps at EL1 or EL0 (section D24.2.35, page D24-8585), and every other field clear, which keeps SVE and SME instructions trapped.  Every field of FPCR resets to an architecturally UNKNOWN value on a warm reset (section C5.2.8, pages C5-974 to C5-981), so the startup writes the whole register.  It sets DN, under which "any operation involving one or more NaNs returns the default NaN" (page C5-975), and clears every other field.  With RMode at 0b00 operations round to nearest, with FZ, FZ16, and FIZ clear no denormalized number is flushed to zero, AH and NEP clear exclude the alternative behaviors of FEAT_AFP, and with every trap enable clear no floating-point exception traps.

A proof joins the startup to the program's theorem in a model of the boot machine.  That model tracks the system registers that the startup writes, both as written and as in effect after synchronization, the selection of the stack pointer, the TLB's state as unknown, invalidation pending, or clean, and whether every store to the UART has completed.  It gives each address's memory type from the table's bytes for the one configuration that the startup establishes and stops in every other, it requires each instruction fetch to succeed under both the written and the effective registers, and it runs every instruction other than a system instruction by the program model's step, with the platform that the table gives once that configuration is in effect.  Before then, an instruction that touches no memory runs by the program model's step only when its next program counter lies below 2^55 or address tagging is off in both copies of TCR_EL1, since a branch under tagging, which firmware may leave on, replaces the top byte of a larger target, and a floating-point instruction runs only when both copies of CPACR_EL1 and FPCR hold the values that the startup writes.  The startup executes no floating-point instruction, and the proof lifts its runs of the program model from the code map without the words that decode to one.  The configuration that the startup establishes includes CPACR_EL1 at 0x300000 and FPCR at 0x02000000, so every instruction of the program runs with floating point enabled under that FPCR.  The tracked registers include FPCR, whose writes the architecture puts in effect at once, so the model, which puts them in effect at the next synchronization, is stricter there than the architecture.  `MSR FPCR` steps only when FPEN is 0b01 or 0b11 in both copies of CPACR_EL1, since either copy may govern its trap before a synchronization.  The joined theorem starts from every state of that model at EL1 whose memory holds the image's bytes at its base, with the program counter at the base and the MMU off in both copies of SCTLR_EL1, whatever the values of the other system registers, the contents of the TLBs, the selected stack pointer, and the processor's support for TCR2_EL1.  The startup reaches the entry routine with the registers' target values in effect, the TLBs clean, SP at the stack's top, X17 at the area, the area's zero tail cleared, and X30 at the exit.  From there the program runs in the model of its instructions, whose platform a lemma derives from the table's bytes: Normal memory is the RAM GiB less the image's bytes below the end of its table, and the UART lies at 0x09000000.  The program's instructions include no system instruction, so the configuration that the startup establishes stays fixed until the exit.

Some conditions lie outside what the extended model can check and enter the trusted base as assumptions.  The implementation must support the 4 KiB translation granule and little-endian data at EL1, firmware must have performed any implementation-defined initialization of caches and TLBs, the system-register masks of FEAT_SRMASK must be zero, and RAM must back the whole GiB from 0x40000000, which the runs provide with 1 GiB of RAM.  No data cache may hold a clean line of the image that differs from memory: the boot protocol requires the image cleaned to the point of coherency, Linux's startup relies on the reading that no stale clean line remains, and the trusted base adopts that reading.  Under KVM, the hypervisor's second stage of translation must map the RAM GiB to itself as Normal memory and map or emulate the UART.

## The UART and the exit

The model treats the UART as an output list: a byte store to the data register appends the byte, and the theorem's conclusion concerns that list.  The device that turns the stores into bytes on the host is QEMU's model of the PL011 under both accelerators, and the theorem's reader trusts it and its address.  QEMU's documentation fixes only the addresses of flash and RAM on the `virt` machine and directs guests to the device tree for every other device, so the address 0x09000000 holds for QEMU 8.2's memory map, whose device tree names the PL011 there, and enters the theorem as the platform's.  The PL011 must also transmit every byte written to its data register, which depends on the device's enable bits and its FIFO and lies outside the architecture.

The exit writes the status in X0 as one byte on the UART after the output: 0 after a result, or a trap's code with no byte before it.  It then completes the UART stores with a barrier and calls PSCI SYSTEM_OFF with `HVC #0` and the function identifier 0x84000008 in X0.  Semihosting, a debug interface through which a guest under TCG can give QEMU an exit status, is unavailable under KVM, so the UART carries the status under both accelerators and QEMU exits with status 0.  Under TCG the guest has no EL2, so the architecture makes `HVC` undefined at EL1, and QEMU intercepts the call as PSCI before that rule applies.  Under KVM, EL2 exists and KVM implements the call.  The instruction after the call branches to itself, and an undefined-instruction exception reaches a vector that halts, so the output is final at the call however the call ends, and the theorem needs no model of PSCI.

## The loader

QEMU loads the image and enters it, and the theorem assumes that memory holds the file's bytes at the image's address when the startup begins.  For an arm64 Image, QEMU 8.2 copies the whole file to the base of RAM, 0x40000000, plus the header's offset, adding 2 MiB when the offset lies below 4 KiB, where QEMU's boot stub lies, or using 0x80000 when the header's image size is 0.  An offset of 0 therefore places the image at 0x40200000 under both accelerators.  The boot stub at 0x40000000 sets X0 to the device tree's address, clears X1 to X3, and branches to the image.

A check compares the loaded memory with the file before the first instruction runs.  QEMU starts stopped, with the machine, the processor, and the RAM of the program runs, and its monitor saves the guest RAM over the file's length at the computed address, which must equal the file.  The test driver runs the check on every image that Lean writes, under TCG and KVM.  It shows the bytes in RAM before the first instruction of a stopped run and supports the placement rule, but it proves nothing about the run that executes, so the loader stays in the trusted base, together with the boot stub's register settings.

## Validating the model against the processor

### Co-simulation

The model's agreement with the processor is the link that rests on tests.  A bare-metal harness runs each case at EL1 with the MMU on and RAM mapped as Normal memory, the conditions under which the model claims to hold.  A case sets the general registers to boundary values or random words, the floating-point registers D0 to D31 to special doubles or random words, the flags to random bits, and a 64-byte window of RAM to random bytes, and it runs one instruction with random fields as the word that the encoder gives.  A load or store receives a base that puts its access inside the window, mostly at unaligned addresses, with SP at a multiple of 16 when SP is the base.  A branch receives an offset of up to 16 words in either direction, where landing code records which word execution reached.  The harness prints the state before and after each case, and a checker runs the model from the state before and compares its result with the state after.

The harness runs under TCG, where QEMU emulates a Cortex-A57, and under KVM on the host's processor, pinned in turn to a core of each type that the processor has.  Every case has agreed, in tens of thousands of cases under each accelerator, and a printed state with one register changed makes the checker report that case.  The test covers only the states in which the model runs, with accesses inside the window, short branches, and no UART store, and it covers sampled values on particular implementations.  Branches over longer distances rest on the encoding lemma and on the comparison with the GNU assembler.

### Isla

Isla is a symbolic evaluator for instruction-set specifications written in Sail.  Arm writes its architecture's specification in its language ASL, and a translator generates from it a Sail model of the whole architecture, with its system registers and address translation.  For one instruction, with its opcode fields and register values symbolic, Isla produces a trace: the register and memory reads and writes that the instruction performs, their values as SMT expressions over the symbols, and the conditions of each path.  Islaris used such traces to verify machine code in Coq against Arm's specification.

The check is a Lean proof, for each integer form on which the program's model runs, that the model's execution agrees with the form's Isla trace.  It covers every operand value where tests cover samples, and the architecture as Arm specifies it where tests cover the implementations at hand.  Isla's Arm model represents IMPLEMENTATION DEFINED choices as constants of its configuration and CONSTRAINED UNPREDICTABLE choices as symbolic values, so a form's dependence on either would appear in its trace, which no test on particular processors can reveal.  The check replaces trust in the model's agreement with the processor by trust in Arm's ASL, its translation into Sail, Isla with the SMT solver that prunes its paths, and the meaning of a trace.

Isla traces each form with the Armv9.4 specification at EL1 in about 4 s and 1.1 GB, most of it spent parsing the specification's 156 MB intermediate representation.  With symbolic operands, the flag computations of `AddWithCarry` and the specification's devices at fixed addresses add paths, which an option of Isla and a constraint on the address remove.  A symbolic register number multiplies the paths by the number of registers, unless Isla reads the registers as a vector, which leaves one fork per register field, on register 31.  With the MMU off, the specification treats every data access as Device memory and faults on an unaligned access.  With the MMU on, in a configuration of Isla's own with a 1 GiB identity block over the RAM GiB, stage 2 translation on, and PAN fixed at 0, an unaligned load with concrete operands succeeds as the model states, and its trace, which includes the table walks of each byte, takes 54 s.  The committed traces run with the startup's `SCTLR_EL1`, `TCR_EL1`, and `MAIR_EL1`, and those of the loads and stores answer the table walk with the startup's descriptors.  The traces never write the program counter after an instruction that does not branch, so the check supplies the increment from the pseudocode.  The model stops on a load or store based on a misaligned SP whatever SCTLR_EL1.SA holds, and with SA set, as the startup writes it, the specification agrees.  The only CONSTRAINED UNPREDICTABLE choice in any trace concerns Device memory, and its branches agree for Normal memory.

A Lean check reads the traces into a definition of Isla's trace language and gives them the semantics that Islaris defines.  The reader takes the events `cycle`, `call`, `return`, `define-enum`, and `branch-address`, and the primitives `sail_take_exception` and `sail_barrier` with a unit result, as steps without effect, and rejects every event that the semantics does not define.  For each form, a theorem states that whenever the model's execution succeeds from a state, every path of the form's trace from that state ends in the state that the execution gives, and some path reaches it, with the registers outside the model changed only at those that the theorem lists, for every value of the registers that Isla's configuration leaves unknown.  The traces of `tests/isla/tcg` and `tests/isla/kvm` take every opcode field symbolic in two processor profiles, QEMU's Cortex-A57 under TCG and the KVM guest on the host's Cortex-X925 and Cortex-A725 cores, and the check reads each profile's feature settings from the file that its traces used.  Every trace comes from a copy of the specification's IR that `tests/isla/armv9p4-checked.diff` edits, so that Isla's run stops when the decoder throws an exception other than an exception entry's, which Isla's harness would otherwise record as a completed path.  UDIV's trace comes from a further edit, `tests/isla/armv9p4-udiv.diff`, which computes the quotient by truncating integer division in place of the specification's division of real numbers, which Isla does not implement.  The readers of the traces and of the feature settings, the semantics of traces, and the edits of the IR join the assumptions of this check.

The theorems cover, in both profiles, every integer form on which the program's model runs, for every value of every opcode field, register 31 included.  ADD, SUB, and SUBS with an immediate or a register, AND, EOR, ORR, ORR (W), MADD, MSUB, LSLV, LSRV, UDIV, MOVZ, MOVK, LSR with an immediate, CSINC, ADR, and ADRP agree from every state.  B, BL, CBZ, CBNZ, B.cond, and RET agree from every state whose branch target lies below 2^55 or whose TCR_EL1, which their traces leave unknown, clears TBI0 and TBI1, the condition that the boot model's rule for an instruction that touches no memory places on its next program counter.  The startup's TCR_EL1 clears both bits, so the premise holds for every branch of a program, and a conditional branch needs it only when it branches.  On the paths that the premise excludes, the specification replaces the target's top byte.  The startup's system instructions, `MSR`, `MRS`, `ISB`, `DSB`, `TLBI`, and `HVC`, are forms on which the program's model stops, so they have no theorem against Isla, and the boot model gives them their meanings, as [the startup](#the-startup) describes.  The floating-point forms have no theorem against Isla either, for the reason that [the floating-point section](#floating-point) gives.

LDR, STR, and STRB agree from every state that meets the premises of the traces' configuration, which concern the translation table and the address.  The configuration constrains TTBR0_EL1, which it otherwise leaves unknown, to a multiple of 32 in the RAM GiB, and memory at that address plus 8 must hold `0x0040000040000705`, the descriptor of the RAM GiB in the startup's translation table, which the specification's table walk reads.  The access's address, the base register or SP plus the scaled immediate, must put every byte of the access in the RAM GiB, from 0x40000000 to 0x7FFFFFFF.  A second theorem of STRB covers the byte store to the UART's data register at 0x09000000, with the descriptor of the first GiB, `0x0060000000000401`, at the table's address.  That theorem leaves the platform's UART address open: when it is 0x09000000, the trace and the model both append the byte to the output, and otherwise both store it in memory.

STR needs two more premises, since an unaligned doubleword store under TCG, or one that crosses a 16-byte boundary under KVM, stores its bytes one at a time and translates the address of each byte after storing the bytes before it.  The platform's UART address must lie outside Normal memory, since the semantics of traces sends a byte written at that address to the output while the model stores all eight bytes in memory.  The eight bytes must also lie clear of the descriptor at the table's address plus 8, since the walk for a later byte reads the descriptor from the memory that the earlier bytes changed.  The platform of the program's runs, whose Normal memory excludes the UART and the translation table, meets both premises for every store that the model runs.  The theorems validate the model and take no part in the proof of a program's theorem, and `tests/isla/theorems.sh` elaborates their modules in `tests/TestSupport/A64/Isla`, one for each group of forms and one for each memory form, and prints each theorem's axioms.

## Floating point

The model's double-precision forms are `FMOV Dd, Xn` and `FMOV Xd, Dn`, which copy a word between a general register and a floating-point register, `FADD`, `FSUB`, `FMUL`, and `FDIV` on D registers, `FSQRT`, and `UCVTF Dd, Xn`, which converts an unsigned 64-bit integer to a double.  Each computes the reference interpreter's function of the WebAssembly instruction that it implements, such as `Wasm.f64Add` for `FADD` and `Wasm.f64ConvertI64U` for `UCVTF`, so the simulation lemmas hold by the definitions, and the burden falls on the model's fidelity: for every operand, Arm's result under the startup's FPCR must equal the interpreter's function.  The interpreter rounds to nearest with ties to even, keeps subnormals, and returns the canonical NaN, 0x7FF8000000000000, for every NaN result of an arithmetic operation.  AArch64 returns that NaN as its default NaN when FPCR.DN is set and propagates NaN payloads when it is clear, and with RMode at 0b00, FZ and FIZ clear, AH and NEP clear, and every trap enable clear, it rounds to nearest and keeps subnormals, so the startup's value, 0x02000000, gives the interpreter's special values for these forms.  No square root lies halfway between two doubles, since the odd part of a midpoint's square exceeds 2^106 while that of a double's magnitude lies below 2^53, so Arm's rounding of the real square root and the interpreter's rounding of an integer square root give the same double.

The absolute value uses no floating-point form.  The interpreter's absolute value clears the sign bit and keeps every other bit, a NaN's payload included, and `ADD Xr, Xr, Xr` followed by `LSR Xr, Xr, #1` computes the same word with two integer forms that the Isla check covers.  `FABS` changes only the sign bit when FPCR.AH is clear, but on a processor with FEAT_AFP, such as the KVM guest's cores, AH set makes it return a NaN operand unchanged, so the integer code also leaves the program independent of that field.

The boot model treats the eight forms as floating-point instructions, which CPACR_EL1.FPEN traps.  Its rule for an instruction that touches no memory runs one only when both copies of CPACR_EL1 and FPCR hold the startup's values, and the configuration that the program's steps require includes those values, so every floating-point instruction of a program runs with floating point enabled and FPCR at 0x02000000.

Linux's boot protocol fixes no value of PSTATE.SM or of SMCR_EL1.FA64, so a processor with FEAT_SME may enter the image in Streaming SVE mode, in which most SIMD instructions trap.  In the pseudocode of Arm's Armv9.4 specification, as the Sail model gives it, and in Arm's release of 2026-06, each of the eight forms checks its access with `CheckFPEnabled64`, which reads CPACR_EL1.FPEN and the traps of EL2 and EL3 but not PSTATE.SM, while the vector forms check with `CheckFPAdvSIMDEnabled64`, which traps in Streaming SVE mode unless FEAT_SME_FA64 is enabled.  The other reads of PSTATE.SM on the forms' paths leave their results unchanged under the startup's CPACR_EL1 and FPCR: (a) `IsMerging` takes FPCR.NEP as 0 in Streaming SVE mode without FEAT_SME_FA64 and reads it otherwise, and the startup clears NEP; (b) `FPProcessException` traps only for a set trap enable, and (c) the underflow test of `FPRoundBase` reads FPCR.UFE, and the startup clears every trap enable; and (d) `V_set` writes bits 0 to 127 of the register in either mode, since the startup's CPACR_EL1 leaves SVE and SME disabled, and the model holds no bit above 127.  The model therefore gives each form one meaning for either value of PSTATE.SM.  The same freedom reaches every integer form, the startup's system instructions, and exception entry, and none of them reads PSTATE.SM or SVCR on the program's paths.  Neither the test processors or the Isla profiles implement SME, so no test or proof covers a run with PSTATE.SM set, and the trusted base states the reading as an assumption.

Isla cannot trace the arithmetic forms, since Arm's pseudocode computes each result as a real number and rounds it, and Isla implements no operation on real numbers.  The equation of each floating-point form with the interpreter's function therefore rests on co-simulation, which draws the operands from zeros, infinities, quiet NaNs with and without a payload, signaling NaNs, subnormals, the largest and smallest normals, and 1.0, each with either sign, and from random words.  QEMU and the processor have agreed with the model on every case, and every result of an arithmetic case with a NaN operand has been the canonical NaN.  Removing the assumption requires a proof that the interpreter's IEEE functions equal Arm's pseudocode for the same operations.

## The final theorem

Each program's theorem concerns the image file whose bytes the kernel compared with the generator's output for the program's module, function, and arguments.  If memory holds that file's bytes at a base that is a multiple of 4096, with the memory that the header's size names inside the RAM GiB, and the core starts at the first byte at EL1 with the MMU off, then the machine, in the model of the boot machine, reaches the PSCI SYSTEM_OFF call with every store to the UART complete, after writing either the encoding of the Lean function's value on the program's arguments followed by the status byte 0, or a status byte alone: 1 when the compiled program reached `unreachable`, through its depth guard or its allocator's failure to grow memory, and 4 when a frame would have passed the stack's limit.  The theorems of GCD by a loop, CRC-32, SHA-256, the CIC filter, and the Euler solver allow only the value, GCD by recursion allows the value or status 4, and the recursion that reaches the depth guard allows the value or status 1 or 4.  The run fetches its instructions from the image's words below its translation table, as the initial memory holds them, and no store reaches those words.  The statement names that code map, the protected bytes, and the image's size through functions of the generator's output, which the kernel evaluates for each program.

The Image of [the CIC decimation filter](../Library/Numerics/Filters/Cic/README.md) has a second theorem, `cic_outputs` of [the Image theorems](../tests/TestSupport/A64/ImageFiles.lean), whose statement names the filter's specification over ℤ in place of the Lean function.  The UART receives the encoding of an array of words and then the status byte 0, and the array's words, read as signed 64-bit integers, are the outputs `outputs 3 8 1` of [the filter's specification](../Library/Numerics/Filters/Cic/Spec.lean), of order 3, decimation 8, and differential delay 1, on the table's samples read as integers.  The proof joins the Image's theorem with the equation of the dialect's program with the block cascade at `UInt64`, for every input array, and with the exactness of the cascade under Hogenauer's bound, whose premise the kernel checks for the table's 16-bit samples.  Its reader needs the specification's definitions and the boot model's statement, and none of the program's.

The theorem covers every base in the RAM GiB that the boot protocol permits, since those bases are multiples of 2 MiB.  The check against Isla's traces covers every integer form on which the program's model runs, under the premises that [the Isla section](#isla) states for branches, loads, and stores, the meanings of the floating-point forms rest on co-simulation, and the meanings of the startup's system instructions rest on the boot model's specification.  For a recursion the stack's bound is 2^64, so status 4 remains, and a bound from the depth guard's limit on calls would remove it.
