The LeanExe Subset: Types, Extraction, and Execution
Codex GPT-6, Jamie Stephens

Abstract
LeanExe compiles checked Lean declarations to WebAssembly through a restricted first-order
extraction path. The LeanExe subset is specified here by runtime typing and layout rules
together with an implementation-indexed relation from checked declarations to WebAssembly
execution. The report separates kernel typing, static specialization, extraction acceptance,
ownership analysis, binary validity, and artifact behavior. It defines the internal and public
type domains, proves two layout propositions, and states the numeric, collection, memory, and
fixed-adapter semantics, including binary32 arithmetic and packed word storage. It also states the
proof obligation for checking a compilation against its Lean algorithm. A source audit identifies
incomplete runtime export-name rejection and a child-mask width obligation. The reference
IR evaluator has a narrower comparison domain than compiled execution. Existing emitter,
decoder, validator, packed-memory, and arithmetic theorems support their named boundaries.
An independent source operational semantics, mechanized acceptance judgments, and a general
source-to-WebAssembly refinement theorem remain open.

3.4

Recognized control and recursion

The accepted control forms include Id, Option, and concrete Except sequencing, direct matches,
and ForIn.forIn over byte arrays, fixed-width arrays, legacy ranges, and Lean.Loop. The loop
accumulator must have a supported internal layout. Generated ForInStep.done, failure tags, and
accepted branch exits determine termination of the lowered loop [8, 6].
Recursion recognition has six relevant families: fuel recursion whose first retained function
parameter has source type Nat and supplies the fuel, direct structural recursion, expression-position
structural recursion with synthetic helpers, closed list-shaped folds and predicates, array descent
through the recognized WellFounded.fix shape, and mutual descent through a nested PSum form
of WellFounded.Nat.fix. Direct structural descent uses recognized generated below projections.
Array descent uses attached elements and the generated recursive handle. The mutual form
immediately dispatches to a supported family member [9, 6]. Lean termination checking precedes
these shape restrictions. Complete independent inference rules for these generated forms remain
part of the formalization work.

Value representation and operational rules

4.1

Memory and ownership

An abstract byte array is a finite byte sequence, an array is a finite sequence of values of its element
type, and a recursive value is a finite constructor tree. A physical representation may share tree
subvalues. Let µ be byte-addressed linear memory and load64 (µ, p) a valid little-endian word load.
Internal bytes have slots [o, p, n], where o is an owner root, p the visible byte pointer, and n the
length. Public bytes expose [p, n]. Internal arrays have [o, p], and public arrays expose [p].
For bytes b, the payload relation requires n = |b| and µ[p : p + n] = b. Owner zero permits
borrowed storage. A nonzero owner identifies an allocation that contains the visible byte range and
remains live while that range is used. For an array a : Array τ , the header and elements satisfy
load64 (µ, p) = |a|,

ai is represented at p + 8 + 8i wI (τ ).

Each element uses its internal layout, including embedded owner slots. Structures concatenate field
vectors. A variant stores its constructor index and all reserved payload areas. A recursive value
uses a pointer to a tagged slot object [11, 12, 14].
The representation relation includes valid ranges, live owners, and alias accounting appropriate
to the performed operations. These are program-theorem premises. A general representationpreservation theorem must justify them for every accepted operation. Inactive scalar payloads
7

have no source value. Inactive owner positions still participate in a type-derived child-mask walk if
retained in a container, so their contents require explicit heap premises. A public byte-array result
also omits the owner identity needed to distinguish an allocation root from a slice.
All address observations require bounds that prevent relevant machine arithmetic from wrapping
and place each access in linear memory. The emitted code computes addresses with i64 arithmetic
and converts them with i32.wrap_i64. The complete target relation retains this machine behavior
on every input. A source-facing theorem states the narrower represented-input and resource premises
under which the natural-number address formula applies.

4.2

Numeric semantics

Let U = 264 . Fixed-width unsigned addition, subtraction, and multiplication reduce modulo 2w .
Narrow operations and conversions normalize the result to width w ∈ {8, 32}. Unsigned division
returns zero for a zero divisor, and remainder returns the dividend in that case. Shift counts reduce
modulo the operand width. Comparisons use unsigned order [6, 14].
Runtime natural numbers lie in [0, U ). Their subtraction saturates at zero. Addition and
multiplication return the mathematical result when it lies below U and trap otherwise. Successor
uses checked addition, and predecessor uses saturating subtraction. The backend implements
the addition test by detecting wrapped order, and the multiplication test by comparing against
⌊(U − 1)/b⌋ after handling b = 0 [14].
The floating-point intrinsics retain binary32 encodings in U32 and binary64 encodings in U64.
For width w ∈ {32, 64}, the four binary operations and square root reinterpret words, execute the
corresponding f32 or f64 instruction, and reinterpret the result. The scalar ABI carries both widths
in i64. The binary32 sequence wraps to i32 before reinterpretation and zero-extends the result.
Each arithmetic instruction rounds at its own position in the sequence. The source type domain
continues to represent floating-point values through integer words [20, 14].
The compiler recognizes LeanExe.Float32 and LeanExe.Float64 operation names. It also
recognizes the five Wasm.IEEE64 operations from Talos. The binary64 aliases use the same emitted
instructions, allowing a source algorithm to name the arithmetic functions used by its execution model [5]. Binary32 promotion to binary64 uses f64.promote_f32, and binary64 demotion
uses f32.demote_f64. Finite promotion preserves the value exactly. Demotion applies binary32
rounding [17, 14].
For width w, write af = reinterpretfw (a) and bf = reinterpretfw (b). For p ∈ {+, −, ×, /}, let
Wasmp,w (af , bf ) be the set of results permitted by the WebAssembly operation. Define
Fpp,w (a, b, r) ⇐⇒ r ∈ {reinterpretiw (z) | z ∈ Wasmp,w (af , bf )}.
Square root and precision conversion have corresponding unary relations. WebAssembly permits
a set of NaN results in applicable cases [17]. A statement about every conforming engine must
account for that relation. Exact-word theorems in the pinned Talos model identify its deterministic
arithmetic result. Section 6.4 states the completed binary32 source-model equalities and the
remaining engine-level premise.

4.3

Collections, branches, and loops

Branches execute the selected arm, Boolean conjunction and disjunction short-circuit, and
Option/Except sequencing skips continuations on failure. The emitted instruction order fixes the
schedule after demand-based extraction. Direct calls evaluate materialized arguments in order and
bind their result slots for reuse [6, 14].

Array operations observe finite-sequence behavior under valid representation and allocation
premises. Reads return an indexed element or an optional/default result. Bang wrappers trap on
invalid indices. Set, insert, erase, and swap have their recognized conditional or trapping boundary.
Push, pop, append, extract, reverse, map, and filter preserve the stated sequence ordering. Updated
arrays allocate and copy as specified by their emitter. Unchanged conditional results preserve
their owner. Copying existing child roots retains them, while recognized fresh children can transfer
ownership [12, 14].
Find operations stop at the first true predicate result. Any and all stop at their first decisive result.
Equality checks length before its ordered scan. Forward array and byte folds visit [start, min(stop, n)).
Reverse array folds begin at min(start, n) and visit the preceding element while that index exceeds
the exclusive lower bound. Range loops increment through checked natural-number addition. A
zero step reaching that loop repeats the index until a body exit. Monadic folds and loops stop on
their first failure tag [14].
Accumulator replacement stages all new slots before releasing selected previous roots and copying
the staged slots. The first accumulator value is excluded from this release rule because source
aliases may retain it. Later release selection depends on fresh-owner and liveness analyses. The
emitted multi-slot assignment retains a shared fold computation when any result slot remains live.
Id binds materialize a fold result before a continuation selects its fields, and array map evaluates its
body once per visited element before storing the result fields. Nat-tail recursion materializes a used
supported let binding once. Explicit releases execute even when their counter results are unused.
For-in cleanup stages the next accumulator and stop condition before releasing eligible temporaries,
preserving the returned owner slots [6, 11, 12, 14].

5.2

Allocator and fixed entry adapters

Library mode exports memory, the selected entry, allocation and reference-count operations, and
four counters. Memory starts at 16 pages, and the heap starts at byte offset 4096. Each owned root
p has a 48-byte header containing magic value, reference count, capacity, kind, width or slot count,
and child mask. The allocator rounds payloads to eight-byte alignment with a minimum of eight
bytes, takes the first sufficiently large free block, or advances the heap and grows memory [14].
Retaining root zero changes no state. Retaining a nonzero root checks magic and positive count,
increments the retain counter, and increments the stored count. Release of zero is also a no-op.
Release of a valid nonzero root increments its counter, decrements a count above one, or recursively
releases marked children before adding the root to the free list. Invalid headers and zero-count
reuse trap. All counters and reference-count increments use word arithmetic. A natural-number
accounting theorem therefore needs suitable overflow premises.
10

Explicit source release requires validateModuleReleases. An accepted release consumes a
direct fresh allocation, a helper root identified as fresh, or a statically owner-zero array at its
supported final-use position. The direct-allocation cases include array map and concatenation. An
intervening fresh array with no owner fields cannot retain an earlier root, and the validator preserves
the earlier root’s release eligibility in that case [13]. Automatic cleanup additionally uses result-root,
borrowing, and liveness analyses. The source definitions of the runtime counters and release all
return zero, while generated execution reads and updates allocator state. A source refinement
statement that observes those operations needs their extended semantics.
For an exported heap result, extraction materializes the internal owner-bearing value before
projecting its public slots. Fields of a structured result therefore use the same evaluated owners and
payloads [6].
The exported reset function restores the heap top, free list, and counters to their initial values. It
leaves the page count and old payload bytes in memory. Earlier pointers lose their lifetime guarantee
because allocation can reuse those bytes. A public byte result’s pointer and length should therefore
be interpreted with its program-specific lifetime premise.
The five WASI command shapes accept a zero-argument byte result, a bounded stdin byte
transform, a stdin transform returning Except, an argv transform returning Except, or the combined
stdin/argv transform. The pure entry retains the corresponding source type. The generated adapter
supplies the fixed imports and output trace [14, 3].
For maximum stdin bytes b, maximum user arguments a, and maximum argv-buffer bytes g, the
source constants give
b ≤ 16 · 65536 − 4096 − 1,

R(a, g) = 8 + 24a + 4(a + 1) + g.

Argv mode requires R(a, g) ≤ 16 · 65536 − 4096, and combined mode requires b + 8 + R(a, g) ≤
16 · 65536 − 4096 as well as the stdin bound. Runtime readers enforce their configured counts, skip
argv[0], and pass borrowed-owner values. A successful result writes stdout. An error result writes
stderr and exits with status one. Invalid tags, failed imports, exceeded bounds, and short writes
trap. These statements assume WASI imports implement their specified interface.

5.3

Execution and observations

Let −→W be the selected WebAssembly small-step relation with memory, globals, locals, stack,
frames, and a host-import relation. Let Init(W, H, ā, c0 ) describe an instantiated module and
exported call in host state H. An observation includes return slots and relevant memory, a trap, or
a host exit and byte-output trace. Define
Runv (Q, H, ā, o) ⇐⇒ ∃b, W, c0 , cn . Executablev (Q, b, W )
∧ Init(W, H, ā, c0 )
∧ c0 −→∗W cn ∧ Observe(cn ) = o.
Infinite reduction defines divergence. An external process limit is a separate operational event. This
relation covers all emitted instructions through the selected target semantics, including wrapping
addresses, floating-point special values, and malformed host inputs. Only inputs satisfying a stated
representation relation acquire source-value interpretations.
The repository’s program proofs instantiate execution with the pinned Talos model. A claim
about every conforming engine additionally requires an appropriate relation to the WebAssembly
standard, or a theorem stated against that standard. Conformance and runtime tests provide finite
evidence for that relation. Their results do not expand a theorem’s quantified scope.

Source audit and existing proof boundaries

6.1

Export names and child-mask width

The source reserves only memory, alloc, and reset in Extract.Core.reservedExportNames.
Production export assembly also introduces retain, release, free, allocCount, retainCount,
releaseCount, and freeCount [6, 14]. The prose specification reserves all ten names. The production serializer bypasses the image-emitter duplicate-name check. These declarations expose
a gap between the documented rejection set and its implemented entry-name check. A general
emitted-validity theorem must resolve that gap. Report preparation changed no acceptance rule
and ran no example named after an omitted export.
The inspected layout predicates provide no general 64-slot bound for the ownership mask.
heapChildMaskFromType constructs a natural-number mask with a set bit at each owner position.
Binary.i64Const reduces a mask constant modulo 264 . coreReleaseInstrs scans object slots and
tests the stored mask through i64.shr_u, whose shift count is modulo 64 [12, 14, 17]. Consequently
a general ownership proof needs a bound connecting the accepted layout to mask representation, or
a verified wider representation. This is a source-level proof obligation and potential implementation
defect. A compiled reproducer remains open.

6.2

Reference IR evaluation

The IR reference evaluator has a restricted comparison interpretation. IR.Expr.eval returns zero
for traps, runtime counter reads, releases, heap allocation, heap loads, and collection cases that
need memory. Some update cases return an existing pointer expression. Its natAdd and natMul use
word arithmetic without the backend’s overflow checks. Its loops have a fixed evaluation bound [15].
Extract.Eval.evalEntry filters calls to scalar arguments, scalar-slot results, and a module
passing scalarModule [16]. That filter excludes heap operations but admits traps and checked-Nat
arithmetic. Thus equality with eval-ir supports a comparison only when the execution avoids
those differences and stays within the evaluator bound. The compiled execution relation above
instead uses production lowering and target execution.

6.3

Named theorem scope

The existing scalar certificates connect successful descriptor recognition to exact structured emission.
For example, ScalarDescriptor.Expr.ofIR_emitWithRelease assumes successful expression
reification and proves equality with the backend expression emitter. The condition, statement,
loop, and encoded-index certificates make corresponding statements [18]. These theorems establish
emitter equalities at the named boundary.
The exact-artifact path embeds bytes, decodes them, validates the restricted module, identifies
its Talos translation, and proves the package’s behavioral proposition. Wasm.Binary.Proof.decod
e_sound proves that successful decoding satisfies Grammar.Encodes. Wasm.Binary.Proof.valida
te_sound proves that successful validation satisfies CoreValid [19]. A package theorem identifies
the translated decoded module with the model used by its behavioral proof. The artifact format
also records the external-file comparison and the proof’s stated host assumptions.
The artifact profile excludes WASI imports, so its current decoder and validator theorems
give no automatic certificate for the command adapters in this report. Runtime helper theorems,
including recursive teardown of represented ownership trees, have their own memory and separation
premises [19]. The compiler’s source and the extraction passes remain outside an artifact-only

6.4

Per-compilation source correspondence

A per-compilation proof can establish that a selected generated module computes a named Lean
function. Fix a Lean function F : A → B, the generated Talos module W , its selected entry and
host environment, an input representation InputA (s, a, x) relating store s and argument slots a to
x : A, an output representation OutputB (s′ , r, y), and resource and ownership premises P (s, x). The
required statement has the form
∀s, a, x.

P (s, x) ∧ InputA (s, a, x) =⇒
TerminatesWithW (s, a, λs′ , r. OutputB (s′ , r, F (x)) ∧ Preserves(s, s′ , x)).

Here TerminatesWith is the Talos total-execution judgment, and Preserves states the theorem’s
memory, input-lifetime, or allocator conclusions. The method checks one proof for each selected
compilation, with its own module identity and premises. A separate exact-byte package can connect
W to a serialized binary through decoding, validation, and translation equality. This separates
source agreement from binary identity while allowing both in one result.
The checkpoint contains five unrestricted binary32 equalities:
LeanExe.Float32.pBits(a, b) = Wasm.IEEE32.p(a, b),

p ∈ {add, sub, mul, div},

LeanExe.Float32.sqrtBits(a) = Wasm.IEEE32.sqrt(a).
Their declarations are Project.ProofKit.F32Add.add_eq, F32Sub.sub_eq, F32Mul.mul_eq, F32
Div.div_eq, and F32Sqrt.sqrt_eq, where the last four share the Project.ProofKit prefix [23].
They quantify over all input words, including zeros, subnormals, infinities, and NaNs. The pinned
Lean definitions of these operations reduce to Float32.Model. The proofs identify that logical
model’s words with the deterministic Talos model. Both models canonicalize their arithmetic
NaN results. The emitted WebAssembly instructions retain the standard’s permitted NaN outcomes, so an all-engine exact-word claim needs a further premise or proof concerning exceptional
results. The binary32/binary64 precision conversions have implementation and test evidence at this
checkpoint [21]. Their source-model correspondence proofs remain open.
Project.PackedRead.Spec.readWord_exact proves that the generated read returns the Lean
function’s word and preserves the store under byte-array representation and valid-offset premises [24].
Project.PackedGenerate.Spec.makeWords_with_reuse_exact proves exact source bytes for the
compiled makeWords example, including first-fit free-block reuse and new-block allocation. Its count,
free-list, address, and page-capacity hypotheses state the permitted memory states. Project.Proo
fKit.PackedGenerateLoop.program_spec supplies the reusable sequential generator proof with
a premise for the generator body. Allocation-preservation lemmas prove that disjoint input bytes
remain represented through allocation and output writes [24]. Arbitrary compiled generator bodies
still need their own execution proofs.
A completed four-byte transformer example, Project.TinyGpt2Infer.Spec.infer_exact,
proves the full generated inference result against the named algorithm Project.TinyGpt2.infer,
with all 256 raw-word logits, preserved weights, and unchanged page count under its heap and
input premises [25]. The pretrained 124-million-parameter GPT-2 implementation uses binary32
and packed storage. At this checkpoint its full generated-module/source correspondence remains
open. Its arithmetic and packed-memory lemmas provide reusable components for that proof. The
complete-model execution tests and the checked component theorems have distinct scopes [26].

Independent formalization and refinement obligations

An independent formalization must replace the remaining recognizer references with declared syntax
and judgments and prove their agreement with the implementation. The abstract runtime typing
rules, domain definitions, and layout propositions above supply part of that specification. The shapesensitive recursion rules, demand semantics, and ownership relation need complete independent
definitions before a general preservation theorem can be stated precisely.
Extraction typing would prove that successful extraction produces a well-formed slot program
with valid local indices, direct-call indices, parameter and result arities, and fixed-width offsets. A
stronger invariant would connect those slots to represented source values and live owner roots. The
present IR.Expr and IR.Stmt datatypes have no source-type indices that establish those properties
by construction [15].
The remaining semantic obligations concern erasure, static substitution, demand analysis,
source-operation lowering, ownership transfer, emitted validity, and serialization. A source-to-target
theorem must state the selected source evaluation relation, trap and divergence behavior, bounded
arithmetic, representation, resources, and runtime-intrinsic observations. For a nondeterministic
target relation, it must constrain every allowed target outcome covered by the claim. A source
termination proof also needs the lowering relation before it establishes compiled termination.
A reference-evaluator comparison concerns its stated input and evaluator domain. An exactartifact theorem concerns its embedded binary and behavioral premises. The implemented acceptance
graph, the target execution relation, and the named artifact proofs each identify a concrete subject.
A general compiler-correctness theorem would prove those connections for every accepted input.
The per-compilation method proves the required connection for each selected module and Lean
algorithm under explicit premises.
