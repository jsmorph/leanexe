Exact Execution Verification of Cached GPT-2 in Lean and
WebAssembly
Codex GPT-6, Jamie Stephens
18 September 2026

Abstract
Compiling a neural-network implementation requires preserving its arithmetic order, tensor
representation, and memory behavior. We present a Lean specification and a checked execution
proof for a cached GPT-2 implementation with 124,439,808 parameters and a 128-token context.
In Talos’s WebAssembly semantics, the generated module terminates and returns exactly the
cache and logit bytes of the Lean token-step recurrence for every weight array of the required
length and every valid token sequence of length at most 128. The proof includes initialization,
packed input representation, all twelve transformer blocks, vocabulary projection, allocation
sufficiency, and buffer releases. Arithmetic lemmas connect Lean’s logical Float32 operations
to Talos for all input words. Wasmtime’s canonical-NaN mode supplies the selected runtime
behavior for exceptional arithmetic. Tests against CPU PyTorch compare 6,432,896 logits
across all supported context lengths, with a maximum observed absolute difference of 0.001450,
and produce text completions. The formal result concerns the corresponding Lean algorithm.
Artifact-to-model translation, the native host, and Wasmtime remain trusted. We defer proofs
connecting emitted binary bytes to the Talos model and bounds on numerical error.

In Talos’s WebAssembly semantics, the generated module terminates and returns exactly the cache
and logit bytes of the Lean token-step recurrence for every weight array of the required length and
every valid token sequence of length at most 128. The public theorem is Project.Gpt2CachedStep.

The specification is the executable Lean function LeanExe.Models.Gpt2.cachedStep, including

used by the compiler’s input. The terminal postconditions describe returned bytes and heap state.

Cached attention and token recurrence

The cache stores both 768-component key and value vectors for each layer and prior token. Within
a position, the twelve layers occur in increasing order, with keys preceding values in each layer. If s
is a prior position, ℓ is a layer, and o < 1536 selects a key or value component, its word index is
((12s + ℓ)1536) + o.
For the current position, cachedKv reads the key or value from the newly computed QKV projection.
The source calculates attention scores by a 64-term ordered dot product, scales by 1/8, normalizes
over positions zero through the current position, and computes the weighted value sum [7].
Each block returns a new hidden vector and its current key/value vectors. The enclosing twelvelayer loop concatenates those key/value vectors and appends them to the old cache. Token and
position embedding precede that loop. Final layer normalization and the tied 50,257-row vocabulary
projection follow it. The cached Lean function specifies this entire token step. The formal target
takes its recurrence as the algorithm. Comparison with the separate full-prefix implementation
appears as a runtime test in Section 5.

2.3

Arithmetic order and numerical routines

Matrix projections accumulate each output component in source loop order, with a separate FP32
multiplication and addition at each step, followed by bias addition. Layer normalization computes
an ordered mean, an ordered sum of squared deviations, division by 768, addition of the FP32 word
0x3727C5AC for epsilon, square root, and reciprocal. It then applies the centered value, inverse
standard deviation, scale, and bias in the written order [8]. These choices determine the exact
source result.
The source implements exponential evaluation by a degree-18 Horner polynomial with explicit
coefficient words. For finite nonpositive arguments, expNeg returns zero below −64, halves an
argument below −1 at most six times, evaluates the polynomial, and squares the result once per
halving. GELU uses an exponential form of the tanh approximation and a magnitude cutoff at eight.
Beyond that cutoff, the finite positive tail returns the input and the finite negative tail returns
zero [12]. The bitwise comparisons and branch definitions in the cited source determine behavior on
all other input words. The execution proof includes those branches.
The polynomial, constants, cutoff tests, and rounding order form part of the algorithm specification. The PyTorch reference uses its own tensor and transcendental implementations. The
report’s numerical comparisons measure their agreement on the recorded checkpoint and token
sequences. Proving a real-valued approximation bound would require a separate statement relating
these numerical routines to real formulas.

Statement and construction of the proof

3.1

Termination and observable results

For a fixed Talos module M , environment E, function index i, initial store S, argument stack a,
and postcondition P , write TW(E, M, i, S, a, P ) for Talos’s TerminatesWith. Its definition is
∃N ∀f ≥ N ∃v, S ′ .

run(f, M, i, S, a, E) = Success(v, S ′ ) ∧ P (S ′ , v).

The natural number f is interpreter fuel. This predicate proves eventual successful execution and
the postcondition for every sufficiently large fuel value [13]. The generated GPT-2 module has no
imported functions, and the theorem quantifies over the host environment.
Theorem 1 (Cached GPT-2 invocation). Fix the generated module M at the report’s source revision.
Let W be a byte array of length 497,759,232, and let T = [t0 , . . . , tn−1 ] be a list of UInt32 tokens
with n ≤ 128 and tp < 50,257 for every p < n. Starting from M ’s initial store, reset and weight
allocation terminate successfully. After the specified byte copy of W into the allocated payload, the
token calls and releases described below terminate successfully. At each position p, their observable
cache and logit bytes equal Cp+1 and Lp in Equation (1).
The checked declaration for Theorem 1 is Project.Gpt2CachedStep.Spec.gpt2_128_exact [2].
Its only input restrictions are the three conditions in the statement. The result includes the empty
token list. For a nonempty list, Session.Runs calls cachedStep, observes the new cache, releases
the previous cache when its pointer is nonzero, observes the logits, releases the logit buffer, and
continues with the returned cache. The final cache and weights remain available in the instance.
The source trace specifies the outputs of this call sequence.
The weight-copy step is the pure store update PackedInput.write. Its theorem establishes the
required byte representation and heap ownership after allocation [14]. This specifies the byte I/O
boundary used by the execution theorem. The native host performs the corresponding copy with
memcpy. The proof’s trust boundary includes that implementation.

3.2

Arithmetic correspondence

For each binary operation ◦ ∈ {+, −, ×, /}, the arithmetic proof establishes
∀a, b : UInt32,

LeanExe.Float32.opBits(a, b) = Wasm.IEEE32.op(a, b).

An analogous theorem covers square root. Here opBits and op stand for the corresponding named
operation. The source intrinsics reduce to Lean’s logical Float32.Model, and the proofs compare
its encoding and rounding definitions with Talos’s IEEE32 operations [15, 16].
The proofs split exceptional values from finite values, including zero and subnormal cases. Shared
lemmas relate encodings, significands, exponents, scaling, and rounding. Finite multiplication,
division, and square root require their respective rounding arguments. NaN and infinity cases close
against the explicit logical definitions. The resulting equalities quantify over every input word and
supply the scalar facts used by the tensor-loop proofs. The formal source meaning comes from
Lean’s logical definitions. Native Lean evaluation appears in separate execution tests.

alignment and allocator overhead. A successful free-list reuse preserves the heap top, as does
release. Thus the argument applies to the existing allocator independently of which reusable block
it selects [18].

Artifact and runtime boundary

The source-driven check recompiles cachedStep, renders the resulting binary as WAT with
wasm-tools, generates a Talos module, and requires the generated Program.lean to match the
tracked module used by the theorem. It then builds the complete proof import [19]. The proof
establishes the generated model’s behavior without assuming general compiler correctness. The
generation and comparison tools remain trusted for the correspondence between the emitted binary
and that model.
The recorded runtime binary and the proof check’s generated binary have SHA-256
e93de126e00d7f5c5b9b30ca014a13b1385e9f91e3cb6b4e56a4aacf7a2b4ade.

This hash comparison identifies the tested file. A checked derivation from embedded binary bytes
through decoding, validation, and translation would close the exact-byte obligation. That obligation
remains deferred for this GPT-2 report. The present evidence consists of regeneration, model
comparison, and the checked behavioral theorem.
Report preparation reran the source-driven check at the stated checkpoint. Artifact generation
and tracked-model comparison passed, and Lake accepted the complete proof import using cached
proof objects. The accompanying evidence directory retains the command output and public axiom
reports. The runtime measurements in Section 5 use the saved canonical-mode test record.
WebAssembly permits multiple NaN results for some floating-point operations [20]. Lean and
Talos choose a canonical arithmetic NaN word, 0x7FC00000 for binary32. The C host selects Cranelift
and enables wasmtime_config_cranelift_nan_canonicalization_set [21, 22]. Wasmtime’s
implementation of that mode remains trusted. The recorded FP32 tests check its exact NaN words,
including signaling inputs and negative or noncanonical payloads [23]. The selected runtime mode
is part of the deployment boundary for exact raw-word agreement.
The Lean kernel checks the proof terms. The public theorem’s axiom report contains propext,
Classical.choice, and Quot.sound. Talos’s execution definitions supply the modeled semantics.
Applying the result to a native run also trusts model translation, Wasmtime, its native-code backend,
the C host, and the host’s byte I/O. Tokenization and token selection occur outside the proved
recurrence. The theorem accepts vocabulary indices and produces logit bytes, which lets either a
user-selected sequence or a generated sequence supply the next valid token.
The proof quantifies over the module’s fixed architecture and supported context length. A larger
architecture or context needs corresponding source, generated-module, and proof updates. The
scalar arithmetic and packed-memory lemmas accept inputs beyond this one model. The composed
transformer and allocation theorems retain their stated dimension bounds. Numerical accuracy
against real arithmetic, equivalence between the cached and separate full-prefix Lean algorithms,
and language-quality properties remain separate obligations.

PyTorch comparisons and command-line inference

The runtime tests use the pinned pretrained checkpoint with CPU PyTorch 2.9.1 and Transformers
4.57.6. The manifest checks model files by hash and records checkpoint revision 607a30d783dfa663
caf39e06633721c8d4cfcd7e [6]. The CPU reference uses FP32, eager attention, and one PyTorch
thread. The WASM driver keeps weights and cached key/value data in a resident Wasmtime
instance [22].
The 128-position test starts with the story prompt “Once upon a time, in a small village” and
appends repetitions of a fixed sentence before taking the first 128 token IDs. For each prefix length

logits [24]. This gives 128 × 50,257 = 6,432,896 comparisons. Every component satisfies the test

|ℓwasm − ℓtorch | ≤ 0.002 + 10−4 |ℓtorch |.

The canonical-mode run took 100.2 seconds and reached approximately 1.03 GiB of WASM
linear memory. Its allocation counters recorded 33,025 allocations and 33,023 frees, leaving the
weights and current cache. The allocator reuses whole freed blocks. The final cache contains
128 × 73,728 = 9,437,184 payload bytes. The test also checks the four rejected-input conditions,
cache reset and replay, and byte-exact agreement between cached and full-prefix WASM logits for
the nine-token story prompt [23, 24]. These timings describe the recorded local runs and support
execution feasibility. They provide no cross-system speed comparison.
Three recorded completions generated 64, 32, and 16 tokens in 55.6, 27.8, and 15.4 seconds. The
16-token greedy completion matched PyTorch’s token sequence. The 64-token sampled completion
began:

Proof reuse and verification scope

The construction isolates scalar arithmetic, packed representation, loop correspondence, and allocation accounting into reusable lemmas. The final session proof uses an induction on the token list,
with one step theorem carrying output ownership into the next call. Its numerical inputs range over
arbitrary weight bits, so the proof’s size depends on algorithm structure and dimensions rather than
7

checkpoint values. The heap budget uses allocation sizes to close the concrete invocation premises
without inspecting numerical weights.
The earlier LeanExe subset report describes the compiler’s accepted types, packed layouts,
and per-compilation correspondence obligation [3]. The present result discharges that obligation
for the named cached GPT-2 module under Talos semantics and the stated byte I/O boundary.
The original GPT-2 source supplies the architecture and cached-attention organization [5]. The
checked Lean algorithm fixes the FP32 numerical choices used here, and the PyTorch tests provide
checkpoint-specific comparison evidence. Exact-byte closure and a proof of the native runtime would
address separate links in the execution chain.
